# ADR-0005 — String properties render at execution time, not definition time

**Status:** Accepted

**Context.** Task parameters — `cmd`, paths, messages, input defaults — often depend on inputs, env values, or upstream XCom data that does not exist when the task object is constructed.

**Decision.** A string property may be a plain string or an f-string referencing `{ctx.input.x}` / `{ctx.env.Y}`. It is rendered with `ctx.render(value)` immediately before use, never at definition time.

**Consequences.** One definition adapts to runtime inputs and can pipe upstream outputs in. The cost is a documented footgun: a property is never trustworthy as a literal, so engine code must remember to render before use.

**Alternatives rejected.** *Static strings only* — inflexible, and forces users into callables for trivial interpolation. *Arbitrary inline Python expressions* — more powerful, but harder to audit and an injection risk when the template text comes from an input.

**Where it lives.** `ctx.render` in `src/zrb/context/context.py`; `docs/advanced-topics/architecture.md`.
