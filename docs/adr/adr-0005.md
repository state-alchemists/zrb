# ADR-0005 — Deferred attributes: rendering is opt-in through `Tpl`

**Status:** Accepted

**Context.** Task parameters — `cmd`, paths, messages, input defaults — often depend on inputs, env values, or upstream XCom data that does not exist when the task object is constructed. Rendering every string implicitly made shell `${VAR}` or `awk '{print}'` an f-string by default, and every attribute needed an opt-out flag.

**Decision.** Every typed attribute (`StrAttr`, `BoolAttr`, `IntAttr`, ...) is a plain value, a `Tpl`, or a callable taking `ctx`, and is resolved immediately before use, never at definition time. A plain `str` is a literal. Rendering is opt-in: `Tpl("echo {ctx.input.name}")` is rendered against the context with `ctx.render`. `Tpl` is itself a callable, so one resolution path (`get_attr`) handles both deferred shapes.

**Consequences.** One definition adapts to runtime inputs and can pipe upstream outputs in, while a literal is always trustworthy as written and no `render_*` flags exist. The cost is a footgun in the other direction: a `{ctx.` placeholder in a plain string reaches the shell verbatim. `CmdTask` warns on it at construction, and an architecture test guards the docs and examples.

**Alternatives rejected.** *Render every string implicitly* — turned shell syntax into templates and needed an opt-out flag on every attribute. *Static strings only* — inflexible, and forces users into callables for trivial interpolation. *Arbitrary inline Python expressions* — more powerful, but harder to audit and an injection risk when the template text comes from an input. *Lambdas instead of `Tpl`* — still supported, but a closure in a loop captures the variable rather than its value.

**Where it lives.** `src/zrb/attr/tpl.py` (`Tpl`), `src/zrb/attr/type.py` (the attribute types), `src/zrb/util/attr.py` (`get_attr` and the typed getters), `ctx.render` in `src/zrb/context/`; the warning in `src/zrb/task/cmd_task.py`; `test/architecture/test_doc_tpl_placeholders.py`.
