# ADR-0019 — XCom is a per-task FIFO queue with push and pop callbacks

**Status:** Accepted

**Context.** Tasks must exchange data without calling each other directly, and triggers must react the moment data arrives.

**Decision.** Each task owns an `Xcom` — a `deque` subclass — at `SharedContext.xcom[task_name]`. A task action's return value is auto-pushed to its own queue; downstreams `pop()` or `peek()` an upstream queue. Push and pop callbacks are what let `BaseTrigger` fire on arrival. Templates reach it as `{ctx.xcom['task'].pop()}`.

**Consequences.** Data flow is decoupled, ordered, and needs no external broker. The cost is that it is in-process only: not durable, not cross-machine, and suited to small or medium payloads.

**Alternatives rejected.** *Direct return values* — break under skip and retry, and cannot express a pipeline. *Shared globals* — no ordering and no dependency semantics. *A database or message broker* — heavyweight for in-process flow, and a new operational dependency.

**Where it lives.** `src/zrb/xcom/xcom.py`, `src/zrb/task/base/execution.py` (auto-push), `src/zrb/task/base_trigger.py`, `docs/core-concepts/xcom-deep-dive.md`.
