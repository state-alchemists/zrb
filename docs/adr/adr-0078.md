# ADR-0078 — Mid-turn messages steer the live run via pydantic-ai's `enqueue`, falling back to the queue

**Status:** Accepted

**Context.** A message sent while a turn runs waits in `MessageQueue`/`QueuedMessage` (ADR-0077) until the turn ends, so a same-second correction — "no, check the home directory instead" — may wait through many tool-call rounds before the assistant sees it. Claude Code and opencode instead absorb such a message into the *live* turn at the next safe boundary.

pydantic-ai provides this: `RunContext.enqueue(*content, priority="asap" | "when_idle")`.
- `"asap"` delivers at the next model request, or redirects the run into one more request if it would otherwise end. Its docstring calls this "steering an in-flight agent" and allows retaining the `RunContext` and calling `.enqueue()` later from a different asyncio task, since the drain never races a concurrent `list.append`.
- `"when_idle"` delivers only when the run would otherwise terminate — equivalent to queue-only behavior.

A live `RunContext` is reachable only through `agent.run(event_stream_handler=...)`, whose handler receives `(ctx: RunContext, events: AsyncIterable[AgentStreamEvent])`. `agent.run_stream_events()` exposes the `RunContext`/`AgentRun` only via a private accessor. Switching is low-risk: `run_stream_events()` is itself a thin wrapper around `agent.run(event_stream_handler=...)`, not the lower-level `agent.iter()`/node-streaming API.

One trap: `run_stream_events()`'s internal handler forwards events 1:1 into a memory stream, and the trailing `AgentRunResultEvent` is synthesized separately by its consumer-facing iterator *after* the run finishes — it is never in the raw stream `event_stream_handler` receives. zrb's `StreamEventHandler.__call__` (`llm/util/stream_response.py`) dispatches `AgentRunResultEvent` to `_handle_run_result`, which drives session usage accounting (the status-bar token meter) and the "Requests/Tool Calls/Total" summary line; a naive swap would silently drop both.

**Decision.**

1. **`_execution_loop` (`agent/run/runner.py`) calls `agent.run(event_stream_handler=...)`** instead of `agent.run_stream_events()`. The handler registers the live `RunContext` on `effective_ui` for the call (`_set_active_run_context`, cleared in a `finally` when `agent.run()` returns or raises) and forwards every event to the existing per-event handler. After `agent.run()` returns, `_execution_loop` constructs `AgentRunResultEvent(result=result)` from the real `AgentRunResult` and feeds it through the handler once, restoring what `run_stream_events()` supplied. Each retry/deferred-tool-resume/STOP-continuation `continue` of the outer `while True:` loop re-enters with a fresh `agent.run()`, so registration is set and cleared per iteration. The one path that does not re-enter — a `DeferredToolRequests` pending-approval suspension — leaves no live run context, correctly: no model turn is in flight to steer into.

2. **`BaseUI` and `MultiUI` each expose an `active_run_context` property** (same getter/setter shape as `multi_ui_parent`). Their `_submit_user_message` tries `steer_into_live_run(self.active_run_context, text, attachments)` (`ui/base/message_queue.py`) before building a `QueuedMessage`. Steering wins whenever a live run context exists; there is no toggle, matching opencode's and Claude Code's default. The ADR-0077 queue is untouched and remains the fallback when there is no live run yet, the run is suspended on a pending tool approval, or `enqueue()` failed because the run ended between the check and the call.

3. **`/exec` jobs (`ui/base/exec_commands.py`) never steer.** `_handle_exec_command` already refuses to run while `_is_thinking` and never calls `_submit_user_message`, so a shell command cannot become model input mid-turn.

4. **Rapid successive messages** each call `.enqueue(..., priority="asap")` independently; pydantic-ai's drain (an append-only list, drained between graph nodes) orders and batches them without zrb-side sequencing.

**Consequences.** A typo'd or refined mid-turn message is absorbed at the next tool-call/model-request boundary instead of waiting for the turn to finish. A steered message never enters the queue, so it cannot be recalled or edited via ADR-0077's Up-arrow flow — accepted as the simplest option; queued messages (no live run context, pending approval) keep full recall/edit support. `EnqueuedMessagesEvent` (emitted when an enqueued message is delivered into history) is not yet surfaced in the UI — a documented future polish item (e.g. confirming delivery in the transcript), not needed for correctness.

**Alternatives rejected.**
- *Reimplementing steering via `agent.iter()`/node-level streaming* — `agent.run(event_stream_handler=...)` already delegates to `iter()` and exposes the same events plus a documented `RunContext`; hand-rolling the node loop would duplicate pydantic-ai's cooperative task hand-off for no added capability.
- *An explicit "queue vs. steer" user toggle* — a command/flag for a distinction users rarely need; steer-when-possible, queue-when-not matches the tools this is modeled on.
- *Re-registering the run context on every graph node* — every `RunContext` in one run shares the same pending-message queue, so registering once per outer-loop iteration covers every tool-call round in that call without gaps.

**Where it lives.** `src/zrb/llm/agent/run/runner.py` (`_execution_loop`, `_build_event_stream_handler`, `_set_active_run_context`), `src/zrb/llm/ui/base/ui.py` (`active_run_context`, `_submit_user_message`), `src/zrb/llm/ui/multi_ui.py` (same), `src/zrb/llm/ui/base/message_queue.py` (`steer_into_live_run`).
