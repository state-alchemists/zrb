# ADR-0078 — Mid-turn messages queue, and Ctrl+G steers them into the live run

**Status:** Accepted, revised 2026-10-23 (a checkpoint now delivers the ready messages on its own; the edit hold and the grace are what keep them recallable; see "Revision 2"). Revised 2026-10-22 (submit-time steering withdrawn; see "Revision"). Originally accepted 2026-08-13.

**Context.** A message sent while a turn runs has to wait somewhere until the model can read it. ADR-0077's `MessageQueue`/`QueuedMessage` holds it until the turn ends. The first version of this record had the submit path absorb it into the live turn instead, at the next model boundary, through pydantic-ai's `RunContext.enqueue(priority="asap")` — the argument being that a same-second correction ("no, check the home directory instead") should not wait through many tool-call rounds before the assistant sees it.

That default was withdrawn. Steering at submit makes the message uneditable the moment it is sent: it never becomes a `QueuedMessage`, so ADR-0077's recall/edit/delete flow cannot reach it, and the entry Up Arrow found depended on whether a live `RunContext` happened to be registered at that instant — which flickers with the agent's `agent.run()` boundaries, retries and approval suspensions. A mistyped correction was unrecoverable, while the transcript still showed a `⏳` line that looked queued. ADR-0116 then added a send-now action (`Ctrl+G`) that hands the queue to the live run on request — the same capability asked for explicitly, and the moment it landed the two halves became separable.

**Decision.**

1. **Every submission is queued, whatever is running.** `submit_user_message_via_queue` builds a `QueuedMessage` and nothing else; it takes no run context. A message typed mid-turn waits in the queue and is listed above the input box until its turn runs. This is the one funnel that makes Up Arrow deterministic: a message is either still queued (and therefore editable, deletable, mergeable) or its turn has started.

2. **A checkpoint hands the ready messages to the live run by itself.** The run loop already marks the moment a `ModelRequest` is being assembled — a structurally complete history — and that is when `BaseUI.deliver_queued_messages_early` runs (`submit → queue → deliver → next model request reads it`). Two entries are left out of that pass, which is what makes delivery safe to do without being asked:

   - **the one being edited.** `UIMessageEditing` sets `QueuedMessage.is_being_edited` while the message is in the input box, and clears it on Enter (resubmit), Ctrl+X (drop) or Down past the newest. The flag is on the entry, not on the editing helper, because the checkpoint runs in the turn's own thread, where the helper is not in hand. A held entry is skipped, not treated as a barrier: the messages behind it go, and the edited one rejoins at the checkpoint after Enter — so one edit in progress cannot stop the queue.
   - **any younger than `EARLY_DELIVERY_GRACE_SECONDS`** (one second). A checkpoint can land a fraction of a second after Enter, and without the pause there is no moment in which Up Arrow could reach the message at all. The clock is `QueuedMessage.queued_at`, refreshed when a paste line merges into the entry, so a burst the terminal delivers one line per `Enter` is not delivered halfway through.

3. **An explicit `Ctrl+G` sends everything; speech only sends its own fresh utterance.** `send_queued_messages_now` (ADR-0116) takes everything queued for `Ctrl+G` — no grace or edit hold — drains it into the registered `RunContext` with `priority="asap"`, waits while a dialog owns the input, and otherwise interrupts the turn so the queue runs next. A checkpoint passes `only_ready=True` and `may_interrupt=False`, taking only ready entries without interrupting. Hands-free speech uses the same safe selection but exempts only its own newly queued entry from the grace period: it never sends a different entry the user is editing or a younger draft. A queued `/exec` remains an ordering barrier even inside its grace period. Each delivered entry gets `delivered_at` and `DELIVERED_MARKER` as it leaves the queue; `redraw_echoes` updates its echo in every UI so the transcript says what the model read.

4. **Hands-free speech asks for delivery at the earliest safe point.** A hands-free message has no keyboard behind it — the user is not typing, and may not be looking — so `submit_message_now(..., may_interrupt=False)` submits it and then asks the ladder to hand it to the live run, which happens at the next model request; when that is not possible the message waits for the next turn instead of interrupting the current one. A trigger that speaks for the user marks its `TriggerReply` `send_now` so the loop does the same (ADR-0076). Push-to-talk does not take that step: it submits through the keyboard's own path, so the message waits for the grace like a typed one. The message still becomes a `QueuedMessage` in every case — a dialog, a failed enqueue or an ending run holds it exactly as it holds a typed one — so speech never bypasses the queue.

5. **The queue panel advertises the three keys** — `📥 n queued · ↑ edit · Ctrl+X drop · Ctrl+G send now` — because an accelerator nobody is told about is not a default, it is a hidden feature.

6. **pydantic-ai's `enqueue` is still the steering mechanism.** It is now reached from a checkpoint, from Ctrl+G, and from the sub-agent session path (ADR-0108), which has no editable queue of its own. `/exec` jobs still never steer (ADR-0116).

**Consequences.** A mid-turn message is read at the next checkpoint instead of after the turn — the latency the withdrawn version wanted, without the unrecoverability that made it wrong: the message is a real `QueuedMessage` for at least `EARLY_DELIVERY_GRACE_SECONDS`, and for as long as it is being edited, so Up Arrow and Ctrl+X still reach it. What the grace costs is that a second is the shortest the user can have. What it does not cost is the queue: a message typed mid-turn is delivered at the next boundary rather than held to the end, so the queue drains during the turn instead of after it. A held edit is the one thing that waits, and only for itself.

The queue is in memory only, so a message typed but not yet delivered is lost with the process — the exposure a draft in the input box always had. The queue is also unbounded (`MessageQueue(maxsize=0)`); a cap on pending entries and on their attachments is the next bound to add, tracked separately.

**Alternatives rejected.**

- *Steering at submit (the withdrawn decision).* It is genuinely lower-latency, and it is what opencode v2's TUI does by default (`delivery: "steer"`, with `Ctrl+X Enter` for queue). It is rejected here because its failure is unrecoverable and its behavior depends on run-context timing the user cannot see; Claude Code, which this UI is modeled on, queues on `Enter` and sends on `Ctrl+Enter`. The same pair of behaviors ships either way — only the default differs.
- *An explicit per-submit "queue vs. steer" toggle.* Two keys already say it: `Enter` queues, `Ctrl+G` sends. A config knob would add a third way to express the same choice, and ADR-0116 rejected the same knob for the same reason.
- *Reimplementing steering via `agent.iter()`/node-level streaming.* `agent.run(event_stream_handler=...)` already delegates to `iter()` and exposes the documented `RunContext`; hand-rolling the node loop would duplicate pydantic-ai's cooperative task hand-off for no added capability.

**Where it lives.** `src/zrb/llm/ui/base/message_queue.py` (`submit_user_message_via_queue`, `steer_into_live_run`, `MessageQueue.deliverable`, `EARLY_DELIVERY_GRACE_SECONDS`), `src/zrb/llm/ui/base/queue_delivery.py` (`send_queued_messages_now`, `DELIVERED_MARKER`), `src/zrb/llm/ui/base/ui.py` (`deliver_queued_messages_early`, `submit_message_now`, `redraw_echoes`), `src/zrb/llm/agent/run/runner.py` (`_deliver_queued_messages`, called on the checkpoint boundary), `src/zrb/llm/ui/default/message_editing.py` (the edit hold), `src/zrb/llm/ui/trigger.py` (`TriggerReply.send_now`), `src/zrb/llm/ui/multi_ui.py`, `src/zrb/llm/ui/default/output.py` (the panel), `src/zrb/llm/ui/default/keybindings.py` (Ctrl+G).

**Revision 2 (2026-10-23).** Point 2 said Ctrl+G was the only path from the queue into a live run, and the consequence recorded there — a mid-turn correction waits for the turn to end unless the user presses a key — turned out to be the wrong default for a chat that runs long tool loops. The run loop now delivers the ready messages at each checkpoint, which is the latency the withdrawn submit-time steering was after, with the recall the queue exists for: a message is delivered only once it is no longer being edited and no longer younger than its grace. Ctrl+G did not change meaning; it now means "do not wait for either".
