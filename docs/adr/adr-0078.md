# ADR-0078 — Mid-turn messages steer the live run via pydantic-ai's `enqueue`, falling back to the queue

**Status:** Accepted

**Context.** A message sent while a turn is running has always waited in `MessageQueue`/`QueuedMessage` (ADR-0077) until the current turn fully ends. A same-second correction — "no, check the home directory instead" — has to wait for potentially many more tool-call rounds before the assistant even sees it, unlike Claude Code and opencode, which absorb such a message into the *live* turn at the next safe boundary.

pydantic-ai 2.27.0 (zrb's pin: `pydantic-ai-slim[mcp]>=2.27.0,<2.28.0`) ships exactly this primitive: `RunContext.enqueue(*content, priority="asap" | "when_idle")`. `"asap"` delivers at the next model request (or redirects the run into one more request if it would otherwise end) — its own docstring calls this "steering an in-flight agent," and explicitly allows retaining the `RunContext` and calling `.enqueue()` later, from a different asyncio task than whatever first received it, since the drain never races a concurrent `list.append`. `"when_idle"` delivers only when the run would otherwise terminate — this matches zrb's queue-only behavior before this change.

The only way to reach a live `RunContext` is via `agent.run(event_stream_handler=...)`, whose handler receives `(ctx: RunContext, events: AsyncIterable[AgentStreamEvent])`. zrb was instead calling `agent.run_stream_events()`, whose returned handle exposes the underlying `RunContext`/`AgentRun` only through a private accessor — no public way to reach it. Switching the call shape is small: `run_stream_events()` is itself a thin wrapper around `agent.run(event_stream_handler=...)`, not the lower-level `agent.iter()`/node-streaming API, so this is not a switch to a riskier primitive — it's reaching the same mechanism `run_stream_events()` was already built on.

That switch carries one correctness trap: `run_stream_events()`'s own internal handler just forwards every event 1:1 into a memory stream; the trailing `AgentRunResultEvent` its consumers see is synthesized separately, by its consumer-facing iterator, *after* the background run finishes — never part of the raw stream `event_stream_handler` receives. zrb's `StreamEventHandler.__call__` (`llm/util/stream_response.py`) dispatches `AgentRunResultEvent` to `_handle_run_result`, which drives session usage accounting (feeding the status-bar token meter) and the "Requests/Tool Calls/Total" summary line. A naive swap would have silently dropped both.

**Decision.**

1. `_execution_loop` (`agent/run/runner.py`) calls `agent.run(event_stream_handler=...)` instead of `agent.run_stream_events()`. The handler registers the live `RunContext` on `effective_ui` for the duration of the call (`_set_active_run_context`, cleared in a `finally` once `agent.run()` returns or raises) and forwards every event to the existing per-event handler exactly as before.

   After `agent.run()` returns, `_execution_loop` manually constructs `AgentRunResultEvent(result=result)` — the same `AgentRunResult` object, not a synthetic imitation — and feeds it through the event handler once, restoring what `run_stream_events()` used to supply automatically.

   The outer `while True:` loop's retry/deferred-tool-resume/STOP-continuation `continue` points each re-enter with a fresh `agent.run()` call, so the registration is set and cleared every iteration; the one path that does not re-enter within the same `_execution_loop` invocation — a `DeferredToolRequests` pending-approval suspension — correctly leaves no live run context behind, since there is no model turn in flight to steer into while an approval is pending.

2. `BaseUI` and `MultiUI` each expose an `active_run_context` property (mirroring `multi_ui_parent`'s getter/setter shape). `_submit_user_message` on both tries `steer_into_live_run(self.active_run_context, text, attachments)` (`ui/base/message_queue.py`) before building a `QueuedMessage`.

   Steering wins whenever a live run context exists — no user-facing toggle for v1, matching opencode's and Claude Code's default behavior. The existing `MessageQueue`/`QueuedMessage` machinery (ADR-0077) is untouched and remains the fallback: no live run yet, a run suspended on a pending tool approval, or an `enqueue()` call that failed because the run ended in the gap between the check and the call.

3. `/exec` jobs (`ui/base/exec_commands.py`) never steer — `_handle_exec_command` already refuses to run at all while `_is_thinking` (a pre-existing guard, unrelated to this change) and never calls `_submit_user_message` in the first place, so a shell command can never be silently turned into model input mid-turn.

4. Multiple messages sent in quick succession during one turn each call `.enqueue(..., priority="asap")` independently; pydantic-ai's own drain (an append-only list, drained between graph nodes) orders and batches them without any zrb-side sequencing.

**Consequences.** A typo'd or refined message sent mid-turn is absorbed into the current turn at the next tool-call/model-request boundary instead of waiting for it to finish. A steered message is not recallable or editable via the Up-arrow flow ADR-0077 built, since it never enters the queue — accepted for v1 as the simplest option; queued messages (the no-live-run-context and pending-approval cases) keep full recall/edit support unchanged. `EnqueuedMessagesEvent` (emitted when an enqueued message is actually delivered into history) is not yet surfaced in the UI — a documented future polish item (e.g. confirming delivery in the transcript), not required for correctness today.

**Alternatives rejected.** *Reimplementing steering via `agent.iter()`/node-level streaming* — `agent.run(event_stream_handler=...)` already delegates to `iter()` internally and exposes the same events plus a documented `RunContext`; hand-rolling the node loop would duplicate pydantic-ai's own cooperative task hand-off machinery for no added capability.

*An explicit "queue vs. steer" user toggle* — adds a command/flag for a distinction the user rarely needs to make explicitly; steer-when-possible, queue-when-not already matches the tools this feature is modeled on. *Re-registering the run context on every graph node instead of once per `agent.run()` call* — every `RunContext` handed to one run shares the same underlying pending-message queue, so registering once per outer-loop iteration and clearing once at the end is simpler and covers every tool-call round within that call without gaps.

**Where it lives.** `src/zrb/llm/agent/run/runner.py` (`_execution_loop`, `_build_event_stream_handler`, `_set_active_run_context`), `src/zrb/llm/ui/base/ui.py` (`active_run_context`, `_submit_user_message`), `src/zrb/llm/ui/multi_ui.py` (same), `src/zrb/llm/ui/base/message_queue.py` (`steer_into_live_run`).
