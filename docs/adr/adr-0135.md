# ADR-0135 — An approval's answer is its own hook event, `PermissionResolved`

- **Status:** Accepted
- **Date:** October 31, 2026

## Context

`PermissionRequest` fires while the user is being asked, and `PostToolUse` fires at execution,
not approval (`llm/agent/run/deferred_calls.py`: "PostToolUse fires at execution, not
approval"). Between those two events nothing is announced, and the gap is as long as the tool
runs — a second for a listing, minutes for a build. An observer that reacts to the question —
a status line, a sound, an avatar holding a waiting posture — has no event telling it the wait
is over, so it keeps showing "waiting for you" for the whole call.

`PermissionRequest` cannot be extended to cover this. Hooks run before the question is shown to
the user, so whatever they return is read as a decision; there is no second call at the moment
the answer exists. `PostToolUse` is not a substitute either: it marks the end of the work, not
the end of the wait, and a denied call never executes, so it never fires at all.

## Decision

A new hook event, `HookEvent.PERMISSION_RESOLVED = "PermissionResolved"`, fired at the two
points where `_resolve_approval` returns past the interactive gate — after the approval channel
answers, and after the CLI prompt — carrying `{"tool": <name>, "approved": true | false | null}`.

- `null` means the channel returned no verdict and the policy answers next. It is deliberately
  not `false`: "asked, nobody answered" is not "denied".
- It is **observe-only**: the result of its hooks is ignored, so a listener cannot change what
  the user decided. Nothing about the approval can be resolved by listening to its own outcome.
- It fires only on the interactive path, so a tool the policy approved outright announces
  nothing — nobody was asked, so there is no wait to end.
- Matchers pair it by `tool_name`, exactly as `PermissionRequest` does.

## Consequences

An observer can now end what the question started, and can tell approved, denied and
unanswered apart. The avatar's waiting posture, which prompted this record, is one such
observer.

Costs: a second event to keep beside `PermissionRequest` — both are fired from the same
function, which is what keeps them from drifting; hooks run inside the approval await, so a
slow listener adds its time to every interactive decision; and the event set is now one wider,
which every consumer that enumerates `HookEvent` sees.

## Alternatives rejected

- **Let listeners time out.** The duration of an approval is the user's to choose; a timer is
  wrong in both directions, and it clears a waiting state while the user is still deciding.
- **Reuse `PostToolUse`.** Wrong moment, and absent for denied calls — the case where the user
  most wants to see that their "no" was taken.
- **Let the avatar poll for it.** The avatar polls the face server for model and music, but the
  approval answer exists only inside this process; polling would need exactly this event to
  exist first.
- **Make it blocking, so a listener could decide.** That duplicates the approval channel and
  gives hooks a second way to answer the same question, in a place where the answer would not
  be attributable.
