# ADR-0140 — The UI contract is five roles, and a UI composes them

- **Status:** Accepted
- **Date:** November 7, 2026

## Context

`AnyUI` is the type every task's `ui` slot is declared against, and it had grown to **52 abstract members** across **55 names**, mixing five unrelated jobs: writing output, asking the user, rendering a choice widget, tracking a tool call, and knowing which conversation is open.

`BaseUI` implemented all of it in one class: **141 method definitions, 125 distinct names**. A backend that wanted one behaviour had to accept the other four, and "customizable UI" meant "subclass this and hope".

Two measurements from the review that opened this change:

- **47 of those 141 were pure one-line delegators** to parts that already existed (`BaseUICommands`, `BaseUIReplay`, `BaseUIUsage`, `BaseUIStatusBar`, `BaseUIPersonaState`, `BaseUISystemInfo`). The composition had already started; `BaseUI` was the leftover hub.
- **694 references** to `AnyUI` members across `src/` — which is why the split is mostly call-site work, not declaration work.

## Decision

**Five role contracts, one aggregate, one part per role.**

| Contract | Members | Owns |
| --- | --- | --- |
| `AnyUIDisplay` | 21 | output, answers, markdown, block markers, echo spans, replay |
| `AnyUISession` | 15 | open conversation, model choice, turn state, history, usage meters |
| `AnyUIInput` | 12 | asking, answering, the message queue, attachments, interactive commands |
| `AnyUITools` | 5 | a tool call's lifecycle, `yolo`, pending confirmations |
| `AnyUIPicker` | 1 | the structured choice widget |

`AnyUI` keeps three members — `run_async`, `is_local`, `multi_ui_parent` — plus the shared writer `append_to_output` and the five role accessors, for **nine**.

Specific choices, each against an alternative:

- **ABCs, not Protocols.** The other `any_*.py` contracts are ABCs, and `AnyUI`'s documented promise is that a missing member fails with `TypeError` at construction. A structural `Protocol` would allow a part to be any shape, but it would also drop that promise and leave a part mismatch to be discovered at call time.
- **Roles live in `src/zrb/llm/ui/any_ui_*.py`.** R9 (`test_boundaries.py`) requires `Any<Thing>` in `any_<thing>.py`; the layering ratchet already treats every `any_*.py` as L0, so a role contract adds no upward edge. `any_ui_session.py` sits beside `zrb.session.AnySession` without colliding: different objects, different files.
- **Picker stays its own contract although it is one method.** A choice widget is a real swap — an arrow-key list, a numbered prompt, a Telegram inline keyboard — and folding it into `AnyUIInput` would hide the seam it exists to expose.
- **The session role is an accessor onto the UI, not a part beside it.** The display role's bodies are *derived* — everything it writes comes from `append_to_output` and `stream_to_parent` — so moving them into `BaseUIDisplay` costs nothing. The session role's members are the state itself: the model, the open conversation, the turn flags, the meters. A part holding a copy would let the copy and the host disagree the first time a subclass overrode `model`, and `MultiUI` and `BufferedUI` would each need an adapter that only re-implemented forwarding. So `ui.session` returns the UI itself, exactly as `ui.display` does for a UI that keeps its own surface: `UIStateDefaultsMixin.session` casts the object to `AnyUISession`, and each decorator answers through the overrides it already had — `MultiUI` reads the session off its primary child, `BufferedUI` forwards the conversation name and the usage meter to the UI it wraps. A subclass override keeps working because there is nothing in front of it. `AnyUISession` stays the narrow contract a caller can be typed against; `AnyUI` simply stops inheriting it.
- **Approval folds into `AnyUITools`.** Its two members (`yolo`, `cancel_pending_confirmations`) belong to the object that renders the call, and zrb already has a separate approval extension point, `AnyApprovalChannel`. A sixth contract with two members would give one concern two homes.
- **`ChoiceSpec`/`ChoiceOption` move to `any_ui_picker.py`** and are re-exported from `any_ui.py`, because a contract file may not import the aggregate it is part of.
- **A documented break is acceptable.** This is a deliberate break of third-party implementations, at a minor version. The two documented backend primitives — `append_to_output` and `ask_user` — keep their meaning: the display and input parts call them on the host, so a subclass that overrides only those two behaves as before. Everything the parts absorb is no longer a host member.
- **An accessor promises the whole role.** `ui.input` must hand back something that answers all twelve members, on every host: by a real implementation, by forwarding, or by the inert default in `UIStateDefaultsMixin`.

A composite cannot simply forward, because the members mean different things across several children. `MultiUI` therefore carries a rule for each:

| Rule | Members |
| --- | --- |
| any child | `is_waiting_for_answer`, `is_prompt_answered_since`, `pending_answer_since` (the earliest of them) |
| the child holding the prompt | `submit_answer`, `withdraw_message` |
| the main child | `record_submitted_message`, and the session members it fronts |
| the composite's queue | `submit_message`, `send_queued_messages_now`, `deliver_queued_messages_early` |
| the one terminal, or the race | `run_interactive_command` (main child); `ask_user` and `ask_user_choice` (every child, first answer wins) |

Guessing at one of these is what produced this change's review findings: a member whose home moved but whose meaning did not.

## Consequences

The targets: **`AnyUI` at or under 25 members, `BaseUI` at or under 50.** The contracts exist and `AnyUI` is composed of them; each part's implementation moved in its own change, and the reachable count followed the ones that moved. After the last role — tools — moved behind `ui.tools`, `AnyUI` declares 9 members of its own and exposes those same 9: the aggregate no longer promises anything a role owns. `BaseUI` still answers every member a subclass overrides, because the host keeps them; what shrank is the contract, not the implementation.

The cost, stated plainly:

- **The split is six changes, not one.** Contracts first, then display, session, input, picker and tools, then the aggregate shrink. Doing it in one change would mean a diff nobody can review and a rollback that takes everything.
- **`MultiUI` and `BufferedUI` need a per-role adapter each.** They are decorators, not backends: one fans out to children, the other forwards to a wrapper. Their parts are permanent adapters, not a migration step.
- **`test/architecture/test_ui_contract_roles.py` now polices the partition, and the hosts.** A member declared in two contracts fails, so does one `AnyUI` does not expose, and so does a host whose accessor hands back an object short of its role — `StdUI`, `BufferedUI` and `MultiUI` are walked role by role against every abstract member. `ANY_UI_MEMBERS` and `REACHABLE_MEMBERS` are 9 and may only be lowered; raising one to admit a member is the thing that test exists to prevent.
- **`UIStateDefaultsMixin` splits with the roles**, into the defaults a UI without that surface mixes in. `StdUI`, `BufferedUI` and `MultiUI` keep exactly the defaults for the roles they do not render.
- **`docs/llm/llm-custom-ui.md` and `examples/` were rewritten in the same series**, because the documented Level-3 surface — "state every `AnyUI` must define" — is what this decision removes.
