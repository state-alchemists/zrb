# ADR-0092 — Env/input inheritance is one stateless walk, upstream-first

**Status:** Accepted

**Context.** ADR-0009 makes inputs and envs inherit down the task graph, and `runner/cli.py` reads `task.inputs` while building a task's kwargs — before any `Session` exists. The first implementation had `BaseTask.inputs` and `.envs` recurse by reading the *same aggregated property* on each upstream, so every node re-derived its entire closure once per incoming edge. Measured cost: O(n³) on a linear chain (one `.inputs` read on 800 chained tasks took 1.0s), O(2^depth) on a diamond (44 tasks over 22 levels took 13.0s for one read, and a 40-task lattice made `zrb <task>` never return), plus a `RecursionError` past ~450 levels of chaining and an env list that grew 2^depth long — 131,070 entries for 32 distinct envs at 16 levels. It stayed hidden because zrb's own `zrb_init.py` peaks at 97 tasks and depth 6.

Precedence was also undefined rather than chosen. Within one chain a task's own envs landed last and won; across a diamond, the second branch re-appended a shared ancestor's envs *after* the first branch's, so an ancestor could beat the downstream task that overrode it. Which task wins was a function of branch enumeration order.

**Decision.** Aggregation is a pure function of the graph, computed by one iterative post-order DFS (`_upstream_closure`) that visits each task once and emits upstreams before their dependents. Each node contributes only what it declares itself, via two new `AnyTask` members — `own_inputs` and `own_envs` — since the aggregated `inputs`/`envs` cannot answer "what does this node add". Inputs keep first-per-name; envs are applied in order, so **a task's own envs always override every env it inherits**, at any graph shape. Cycle detection is the walk's on-path set, which is what distinguishes a diamond from a cycle.

Nothing is cached. The closure is O(n) to walk and a read returns O(n) items, so there is no asymptotic gain left for a cache to capture — only an invalidation contract to get wrong. There is no reverse edge to invalidate along either: `append_successor` is on the contract but nothing populates it.

**Consequences.** One `.inputs` read on a 45-task lattice went 13,019ms → 0.12ms, and the 41-task pipeline that never returned now runs in 2.1s. Env lists are one entry per env. `RecursionError` is gone at any depth — a 50,000-deep chain resolves. Deleted along the way: the `_walking_envs`/`_walking_inputs` re-entrancy flags and an identity-dedupe helper the recursive form would have needed. Costs: two more members on `AnyTask` (breaking for a third-party implementer; `BaseTask` is the only one in-tree), and repeated reads pay O(n) each rather than amortizing — measured at 2.9ms for 401 tasks, which is why it is not worth a cache. Residual O(n²) from `_combine_inputs` copying each closure is irrelevant at real sizes (66ms at 2,001 tasks) and has no shape-dependent blowup left.

**Alternatives rejected.** *Memoize per task, invalidated by a module-level graph epoch that `append_upstream` bumps* — the first attempt. Correct and fast (0.52ms on the same lattice), but it kept global mutable state, an invalidation contract, a staleness bug class, both re-entrancy flags and the dedupe helper, all to fix redundant work that removing the recursion deletes outright; it also left the `RecursionError` in place. *Thread a memo dict through the recursion* — needs the memo as a parameter, and `inputs`/`envs` are properties, so it demands a new `AnyTask` method anyway and buys less than the walk. *Cache and never invalidate* — silently wrong for `<<` after a read, which the CLI's own ordering makes reachable. *Leave it and document a graph-size limit* — the limit landed at roughly 40 tasks in a common shape.

**Where it lives.** `src/zrb/task/base/context.py` (`_upstream_closure`, `get_combined_inputs`, `get_combined_envs`), `src/zrb/task/any_task.py` and `src/zrb/task/base/base_task.py` (`own_inputs`, `own_envs`), `test/task/test_dag_shape.py`, `test/task/base/test_context_cycle.py`.
