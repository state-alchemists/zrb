# ADR-0092 — A tool result reaches the model once, through `ToolReturn.return_value`

**Status:** Accepted

**Context.** `ToolReturn` exposes two model-facing fields, and they are additive
rather than alternative:

* `return_value` becomes the `ToolReturnPart` — the tool-result message.
* `content` is *"Content sent to the model as a separate `UserPromptPart`"*
  (pydantic-ai 2.8.0, `messages.py`). It exists for payloads a tool result
  cannot carry natively — an image or PDF a tool produced.

Every zrb tool wrapper populated both, passing the stringified result to
`content` and the structured value to `return_value` (`agent/common.py`), on the
reading that `content` was "the model-facing string" and `return_value` "the
structured value for programmatic consumers". There were no programmatic
consumers: the only two readers of `.return_value` in the tree passed it
straight back into another `ToolReturn`.

Two consequences, both measured against a real 9-turn session
(`~/.zrb/llm-history/weak-dust-0334.json`, deepseek-v4-flash):

1. **Every tool result was sent twice.** 73,321 chars of `ToolReturnPart`
   against 74,025 chars of byte-identical `UserPromptPart`. Because no
   sanitizer strips a `UserPromptPart` — `sanitize_history`,
   `filter_nil_content`, and `sanitize_orphaned_tool_calls` all key off
   `tool_call_id`, which a user part does not have — the duplicate persisted
   into saved history and was re-sent every following turn. Billed cost:
   **73.6k of 356.3k input tokens, 21%**.
2. **The user-turn boundary was erased.** pydantic-ai appends all user parts
   after all tool-return parts, so each tool batch was followed by a `role:
   user` message containing the tool output. Over that session the model saw
   eight apparent user turns that were tool results. A model that cannot locate
   the user's last turn re-derives its answer against what looks like fresh
   input, which is the shape of the observed re-analysis loops.

The size backstop (`agent/truncate.py`, `CFG.LLM_MAX_TOOL_RESULT_CHARS`) was
applied to `content` only, while `return_value` went through whole — so it never
bounded what the model reads; it shrank the duplicate.

The gate and error paths had the mirror-image bug: `return_value=None` with the
real message in `content` meant the model read a literal `null` tool result
(`message.py::TOOL_RETURN_NULL_PLACEHOLDER`) with the explanation arriving
separately as a user turn.

**Decision.** Everything the model should read goes in `return_value`.
`content` is left unset. The invariant gets a named home,
`agent/tool_result.py::tool_return`, imported by both `agent/common.py` and
`agent/gates.py` (a leaf module, since `common` already imports `gates`), so the
rule is stated once and cannot be re-broken silently.

**`return_value` keeps the tool's own shape** — it is not stringified. Each
provider serialises that field differently, and two behaviours depend on it:

* `model_response_object()` (Google) passes a dict through as the native
  `functionResponse`; a string is wrapped as `{"return_value": "<escaped
  json>"}` instead, and `structured_content()` degrades to `None`.
* `model_response_str_and_user_content()` (OpenAI, Anthropic, Mistral, …)
  extracts multimodal parts *out of* `return_value` into a trailing user
  message. Stringifying replaces the image with a Python repr and drops the
  file: `files` goes 1 → 0. This is the hazard `tool/mcp.py::cap_mcp_result`
  already refuses to take.

**The size cap is not made real here.** Because it only ever applied to the
duplicate, capping `return_value` now would silently truncate payloads the model
previously received in full — a behaviour change smuggled into a bug fix.
`_oversize_metadata` records `{"oversized": True, "original_chars": N}` in
metadata (never sent to the model) and passes the value through untouched, so a
real cap can be decided separately, on evidence.

Consequently:

* A PostToolUse hook's `updatedToolOutput` replaces `return_value`;
  `additionalContext` is appended to it, so the model reads the result and the
  hook's note in one tool-result message.
* Gate denials and tool errors are the tool result, not a null plus a user turn.
* `_tool_response_payload` reads `return_value` (hooks would otherwise receive
  `None`), which also hands them the structured dict rather than its string form.

**Consequences.** Tool-result tokens are halved and no longer compound across
turns. Tool results stop presenting as user turns. Everything a provider reads
off `return_value` is unchanged: a differential over 14 payload shapes (str,
dict, nested dict, list, int, bool, None, empty str, empty dict, `BinaryContent`,
list-with-image, unicode, oversized str, oversized dict) against
`model_response_str`, `model_response_object`, `files`, and `structured_content`
reports **0 provider-visible deltas** — the only difference is the removed
duplicate user part.

Assertions on `ToolReturn.content` across nine test files move to
`.return_value`. `test/llm/agent/test_tool_result.py` pins the invariant
end-to-end with `FunctionModel` — payload occurrence count *and* the exact
part-kind sequence — plus the two cases that the first draft of this change got
wrong: multimodal survival (`files` == 1) and Google's structured shape.

**Alternatives considered.** *Keep `content` and drop `return_value`* — not
possible; `return_value` is required and becomes the tool result. *Stringify
`return_value` via `to_string`* — the first draft; it reads uniformly but breaks
Google's structured `functionResponse` and destroys every image an MCP tool
returns. *Strip the duplicate `UserPromptPart` in `sanitize_history`* — treats
the symptom, leaves the double payload inside the run that produced it, and adds
a pass that must distinguish a real user turn from an echoed tool result. *Revert
and keep the duplicate* — costs 21% of input tokens and leaves the turn-boundary
corruption in place, for a change measured at zero provider-visible delta.
*Patch pydantic-ai* — the library matches its documented contract; the misuse
was ours.

**Evidence.** pydantic-ai 2.8.0 `messages.py` `ToolReturn.content` docstring;
`_tool_execution.py:558-566`, `:610-611`, `:690` (the split, the
`UserPromptPart`, the append order). Token accounting above from the linked
history file. Behavior confirmed by a `FunctionModel` probe: with `content=`
set, the payload appears twice and the request carries
`['tool-return', 'user-prompt']`; without it, once and `['tool-return']`.
