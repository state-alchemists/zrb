# ADR-0090 — Registries, managers, and a layered resolution for configurable components

**Status:** Accepted

**Context.** zrb's LLM system grew several overlapping "configure the thing" abstractions, and the terminology drifted. Before this record, a reader met:

| Concept | Examples then | Where it landed |
| --- | --- | --- |
| **Managers** | `PromptManager`, `SkillManager`, `SubAgentManager`, `HookManager` | Kept, narrowed to per-occasion consumers (Part 1) |
| **Module-level singletons** | `skill_manager`, `sub_agent_manager`, `hook_manager`, `llm_config`, `llm_limiter` | Kept, except `llm_config` — deleted in 3.0.0, its jobs split between `CFG` and `ModelResolver` (R12) |
| **Ad-hoc internal registries** | `SkillManager._skills` (a dict), `SubAgentManager._tool_registry` (a dict), `SubAgentManager._agents` (a dict), `HookManager._hooks` | Retired in Phase 7 into `SkillRegistry`, `SubAgentRegistry` and `HookRegistry` — none of those attributes exist now |

`_ProviderRegistry` in `prompt/manager.py`, once listed among the ad-hoc registries too, turned out on inspection to fail every clause of this record's own registry definition — no `CFG` twin, no discovery layer, no layering, one call site — so Phase 7 reclassified it as a part instead of migrating it: `LiveContextProviders` in `prompt/live_context_providers.py`, public per ADR-0035, with the R6 verb set.

Those overlapped in confusing ways. `SkillManager` and `SubAgentManager` were *both* the canonical collection of skills/agents **and** the service that scanned directories and resolved them, while `PromptManager` was a per-task view pulling its defaults from `CFG`. There was no single named concept for "the canonical list of all X," no way to **replace** a collection wholesale (only `add_*`/`append_*` existed), and no documented precedence telling a user *which* value wins when they set the same thing at the task level, on a manager, on `CFG`, and in an env var.

The goal (stated in the framing discussion that produced this record): zrb should be **intuitively configurable** — readable without a manual. The three intended configuration channels are fixed:

1. **Environment variables** — `ZRB_*` set outside any code.
2. **`zrb_init.py` appending** components/tools to the canonical collections.
3. **`zrb_init.py` replacing** a component (a custom UI in place of the default, a custom registry, a fully custom `PromptManager`).

**Decision.** Establish one vocabulary and one *layered* resolution model, and make replacement as first-class as appending.

**Part 1 — Terminology.** Two concepts are named, and they are different things:

- A **registry** is the *canonical collection of all X* — the source of the defaults. It is registered by name (`skill_registry`, `sub_agent_registry`, `hook_registry`, …) and configured from `zrb_init.py` and `CFG`. It owns the full set of X (tools, skills, agents, hooks, prompts) found by filesystem discovery *plus* everything appended in code. A registry does not resolve; it stores and answers queries.
- A **manager** (or the owning task) is the *per-occasion consumer* that resolves a value at use time. It reads the registry for a default and lets a task pin something narrower.

`PromptManager` and `SkillManager`/`SubAgentManager`/`HookManager` are *not* the same flavor of thing and should not pretend to be. `SkillManager`/`SubAgentManager`/`HookManager` are closer to registries (they own the canonical set), while `PromptManager` is a resolved per-task view. The resolution model below applies to both: a manager sits between the registry and the value a task actually uses.

**Part 2 — Layered resolution, not winner-take-all precedence.** Every component resolves by *layering*, not by picking the highest layer wholesale. A layer is defined by three things — its **fallback** (the layer below it), its **own value** (set with `set_*`, or the constructor), and its **deltas** (`append_*`/`prepend_*`/`remove_*`):

- **Fallback chain.** A manager that sets nothing reads its registry; a registry that sets nothing reads its `CFG`/env twin (or its seeded code default). Each layer is the default for the one above it.

- **Deltas layer over the resolved base.** `append_*`/`prepend_*`/`remove_*` at any layer are recorded as ordered delta ops and replayed over that layer's *freshly-resolved* base at query time. Deltas never freeze the base: a change to `CFG`/env or the registry below stays visible on the next resolved read.

- **`set_*` replaces the layer's own value.** It sets the layer's explicit value (which ignores the layer below) and clears that layer's pending deltas. `None`/unset re-defers to the fallback.

- **Concrete or deferred.** A layer's own value may be a concrete list or a zero-argument callable resolved at query time (Part 3).

So a user who wants *their own* behavior either `set_*`s the value (wins from up here, ignoring the baseline) or layers `append_*`/`prepend_*`/`remove_*` deltas on the shipped baseline; a user who wants the shipped behavior sets nothing. Each layer's resolved value is observable, and every layer is explicitly overrideable by a `set_*` above it.

**Part 3 — Evaluation is deferred.** A value in any layer — especially a `CFG`-level or registry-level override — may be a **callable/lambda** that is not evaluated until the value is actually consumed (at task execution, per prompt compose, per run). This is the existing `*Attr` / `get_attr` doctrine from ADR-0005 for strings, generalized to structured components:

- `CFG` may be mutated in `zrb_init.py` *after* a task/manager has been constructed, and env vars may be read lazily — so a value captured eagerly at construction time would go stale.
- Structured values (prompt lists, tool sets) cannot carry lambdas through an env-var string anyway, so they are set in `zrb_init.py` as callables and resolved at use.

Concretely:

```python
# Environment variable — scalars only (lists of arbitrary objects can't round-trip an env var)
ZRB_LLM_MODEL=gpt-4o

# zrb_init.py — a delta appended to the resolved default, layered at query time
prompt_registry.append_prompt(my_prompt)
```

The rule: **`CFG` stays the scalar home** (ADR-0021/0022); structured, swappable components (tools, skills, agents, prompts, hooks, UI) are set through the registry/manager API. Their values may be deferred callables so later `CFG` or registry changes are honored (Part 2).

**Part 4 — Replacement is first-class.** Every registry toggles half the story today: only `add_*`/`append_*`/`prepend_*` exist. To make "swap the component" (channel 3) possible without losing the ability to start from the default, a registry offers, in addition to appending:

- `remove_<name>(...)` — drop by key.
- `set_<name>(...)` — replace the whole collection. The replacement ignores the layer below and clears the layer's pending `append_*`/`prepend_*`/`remove_*` deltas (Part 2). Like every other layer, the replacement may be a concrete list **or** a deferred callable (Part 3) that produces the list at use time.

A replacement does not have to be "empty then add": `set_()` accepts the default-derived value too, so `set_(skill_registry.get_all() + [mine])` is legal, and `set_([only_mine])` is the clean-slate swap.

**Consequences.** A reader can tell, for any value, *which* layer holds it and *when* it is evaluated — the two questions that make configuration intuitive. Users get all three channels: env vars for scalars now; append-or-replace for structured components in `zrb_init.py`.

The cost is that **the LLM subsystem is not yet fully on this model**: the vocabularies are consolidated here first (this record), and migrating each owner (skills, agents, hooks, prompts, tools) to a named registry + resolved manager plus `remove_`/`set_` mutation surface is follow-on work, done one family at a time under the same order. Managers that are genuinely singletons may become the *default instance* of their registry reader rather than the only reader, so multiple tasks can share one collection.

**Alternatives rejected.**

- *Make `CFG` hold structured lists of objects.* — `CFG` is a flat scalar store backed by `EnvField` (ADR-0021/0022); lists of arbitrary callables cannot round-trip env vars, and serializing them would couple config to the object model. Kept as-is; structured overrides go through registries.

- *Merge "registry" and "manager" into one class everywhere.* — They answer different questions (what is canonical vs. what does this task use); forcing one class makes the shared-collection case (two tasks sharing one tool set) awkward. The split is a naming job, not a new abstraction layer.

- *Keep only `add_*`, no `remove_*`/`set_*`.* — Leaves channel 3 (replace a component) only achievable by never-adding-then-adding, which can't express "default plus mine" and hides the swappable intent ADR-0035 and this record aim for.

- *Resolve registry defaults eagerly at construction.* — A value captured at construction goes stale if `zrb_init.py` then mutates `CFG` or the registry before the task runs; deferred callables are how the config system already works and are kept.

**Where it lives.** Today: `src/zrb/llm/skill/manager.py`, `src/zrb/llm/agent/subagent/manager.py`, `src/zrb/llm/hook/manager.py`, `src/zrb/llm/prompt/manager.py`, `src/zrb/llm/task/llm_task.py` (`LLMTask.__init__` default `PromptManager`), `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/common_tools.py` (tool registry surface), `src/zrb/config/mixins/llm_prompt.py`, `src/zrb/zrb_init.py` discovery (`__main__.py`, `util/init_path.py`), ADR-0021/0022/0023 (config), ADR-0005 (deferred evaluation), ADR-0035 (composition). The registries named here are the migration target; follow-up ADRs/commits bring each family onto this model.
