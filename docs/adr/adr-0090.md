# ADR-0090 — Registries, managers, and a layered resolution for configurable components

**Status:** Accepted

**Context.** zrb's LLM system grew several overlapping "configure the thing" abstractions with drifting terminology:

| Concept | Examples then | Where it landed |
| --- | --- | --- |
| **Managers** | `PromptManager`, `SkillManager`, `SubAgentManager`, `HookManager` | Kept, narrowed to per-occasion consumers (Part 1) |
| **Module-level singletons** | `skill_manager`, `sub_agent_manager`, `hook_manager`, `llm_config`, `llm_limiter` | Kept, except `llm_config` — deleted in 3.0.0, its jobs split between `CFG` and `ModelResolver` (R12) |
| **Ad-hoc internal registries** | `SkillManager._skills` (a dict), `SubAgentManager._tool_registry` (a dict), `SubAgentManager._agents` (a dict), `HookManager._hooks` | Retired into `SkillRegistry`, `SubAgentRegistry` and `HookRegistry` — none of those attributes exist now |

`_ProviderRegistry` in `prompt/manager.py` failed every clause of this record's registry definition — no `CFG` twin, no discovery layer, no layering, one call site — so it became a part rather than a registry: `LiveContextProviders` in `prompt/live_context_providers.py`, public per ADR-0035, with the R6 verb set.

The overlaps confused readers. `SkillManager` and `SubAgentManager` were *both* the canonical collection **and** the service that scanned directories and resolved them, while `PromptManager` was a per-task view pulling defaults from `CFG`. Nothing named "the canonical list of all X"; a collection could not be **replaced** wholesale (only `add_*`/`append_*` existed); and no documented precedence said which value wins when the same thing is set on the task, a manager, `CFG`, and an env var.

The goal is that zrb be **intuitively configurable** — readable without a manual — through three fixed channels:

1. **Environment variables** — `ZRB_*` set outside any code.
2. **`zrb_init.py` appending** components/tools to the canonical collections.
3. **`zrb_init.py` replacing** a component (a custom UI, a custom registry, a fully custom `PromptManager`).

**Decision.** One vocabulary, one *layered* resolution model, and replacement as first-class as appending.

**Part 1 — Terminology.** Two distinct concepts:

- A **registry** is the *canonical collection of all X* and the source of defaults. It is registered by name (`skill_registry`, `sub_agent_registry`, `hook_registry`, …), configured from `zrb_init.py` and `CFG`, and owns the full set of X (tools, skills, agents, hooks, prompts) from filesystem discovery *plus* everything appended in code. It stores and answers queries; it does not resolve.
- A **manager** (or the owning task) is the *per-occasion consumer* that resolves a value at use time, reading the registry for a default and letting a task pin something narrower.

`SkillManager`/`SubAgentManager`/`HookManager` are closer to registries (they own the canonical set); `PromptManager` is a resolved per-task view. They should not pretend to be the same kind of thing. The resolution model below applies to both: a manager sits between the registry and the value a task uses.

**Part 2 — Layered resolution, not winner-take-all precedence.** A layer has a **fallback** (the layer below), an **own value** (set with `set_*` or the constructor), and **deltas** (`append_*`/`prepend_*`/`remove_*`):

- **Fallback chain.** A manager that sets nothing reads its registry; a registry that sets nothing reads its `CFG`/env twin (or seeded code default). Each layer is the default for the one above.
- **Deltas layer over the resolved base.** Deltas at any layer are recorded as ordered ops and replayed over that layer's *freshly resolved* base at query time, so a later change to `CFG`/env or the registry below stays visible.
- **`set_*` replaces the layer's own value**, ignoring the layer below and clearing that layer's pending deltas. `None`/unset re-defers to the fallback.
- **Concrete or deferred.** An own value may be a concrete list or a zero-argument callable resolved at query time (Part 3).

To customize, a user either `set_*`s a value (ignoring the baseline) or layers deltas on the shipped baseline; to keep shipped behavior, they set nothing. Each layer's resolved value is observable, and any layer can be overridden by a `set_*` above it.

**Part 3 — Evaluation is deferred.** A value in any layer — especially a `CFG`- or registry-level override — may be a **callable/lambda** evaluated only when consumed (at task execution, per prompt compose, per run). This generalizes ADR-0005's `*Attr` / `get_attr` doctrine from strings to structured components:

- `CFG` may be mutated in `zrb_init.py` *after* a task/manager is constructed, and env vars may be read lazily, so an eagerly captured value would go stale.
- Structured values (prompt lists, tool sets) cannot carry lambdas through an env-var string, so they are set in `zrb_init.py` as callables and resolved at use.

```python
# Environment variable — scalars only (lists of arbitrary objects can't round-trip an env var)
ZRB_LLM_MODEL=gpt-4o

# zrb_init.py — a delta appended to the resolved default, layered at query time
prompt_registry.append_prompt(my_prompt)
```

**`CFG` stays the scalar home** (ADR-0021/0022); structured, swappable components (tools, skills, agents, prompts, hooks, UI) go through the registry/manager API, and may be deferred callables so later `CFG` or registry changes are honored.

**Part 4 — Replacement is first-class.** Besides `add_*`/`append_*`/`prepend_*`, a registry offers:

- `remove_<name>(...)` — drop by key.
- `set_<name>(...)` — replace the whole collection, ignoring the layer below and clearing the layer's pending deltas (Part 2). The replacement may be a concrete list **or** a deferred callable (Part 3).

`set_()` accepts a default-derived value too: `set_(skill_registry.get_all() + [mine])` is legal, and `set_([only_mine])` is the clean-slate swap.

**Consequences.** For any value, a reader can tell *which* layer holds it and *when* it is evaluated — the two questions that make configuration intuitive. All three channels work: env vars for scalars; append-or-replace for structured components in `zrb_init.py`.

The cost: **the LLM subsystem is not yet fully on this model.** This record consolidates the vocabulary first; migrating each family (skills, agents, hooks, prompts, tools) to a named registry plus resolved manager with the `remove_`/`set_` surface is follow-on work, one family at a time. Managers that are genuine singletons may become the *default instance* reading their registry rather than the only reader, so multiple tasks can share one collection.

**Alternatives rejected.**

- *Make `CFG` hold structured lists of objects* — `CFG` is a flat scalar store backed by `EnvField` (ADR-0021/0022); lists of arbitrary callables cannot round-trip env vars, and serializing them would couple config to the object model.
- *Merge "registry" and "manager" into one class* — they answer different questions (what is canonical vs. what this task uses), and one class makes the shared-collection case (two tasks sharing one tool set) awkward. The split is a naming job, not a new abstraction layer.
- *Keep only `add_*`, no `remove_*`/`set_*`* — channel 3 would only be reachable by never-adding-then-adding, which cannot express "default plus mine" and hides the swappable intent ADR-0035 and this record aim for.
- *Resolve registry defaults eagerly at construction* — the value goes stale if `zrb_init.py` then mutates `CFG` or the registry before the task runs; deferred callables are how the config system already works.

**Where it lives.** `src/zrb/llm/skill/manager.py`, `src/zrb/llm/agent/subagent/manager.py`, `src/zrb/llm/hook/manager.py`, `src/zrb/llm/prompt/manager.py`, `src/zrb/llm/task/llm_task.py` (`LLMTask.__init__` default `PromptManager`), `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/common_tools.py` (tool registry surface), `src/zrb/config/mixins/llm_prompt.py`, `zrb_init.py` discovery (`__main__.py`, `util/init_path.py`); related: ADR-0021/0022/0023 (config), ADR-0005 (deferred evaluation), ADR-0035 (composition). The registries named here are the migration target; follow-up ADRs/commits bring each family onto this model.
