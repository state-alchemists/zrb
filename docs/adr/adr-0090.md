# ADR-0090 — Registries, managers, a layered resolution, and three configuration channels

**Status:** Accepted

**Context.** zrb's LLM system grew several overlapping "configure the thing" abstractions with drifting terminology:

| Concept | Examples then | Where it landed |
| --- | --- | --- |
| **Managers** | `PromptManager`, `SkillManager`, `SubAgentManager`, `HookManager` | Kept, narrowed to per-occasion consumers (Part 1) |
| **Module-level singletons** | `skill_manager`, `sub_agent_manager`, `hook_manager`, `llm_config`, `llm_limiter` | Kept, except `llm_config` — removed; its jobs are split between `CFG` and `ModelResolver` (R12) |
| **Ad-hoc internal registries** | dicts and lists held privately inside each manager | Retired into `SkillRegistry`, `SubAgentRegistry`, `HookRegistry`, `PromptRegistry` and `ToolRegistry` |

A per-manager provider list that had no `CFG` twin, no discovery layer, no layering and one call site was not a registry by this record's definition, so it became a part instead: `LiveContextProviders` in `prompt/live_context_providers.py`, public per ADR-0035, with the R6 verb set.

The overlaps confused readers. `SkillManager` and `SubAgentManager` were *both* the canonical collection **and** the service that scanned directories and resolved them, while `PromptManager` was a per-task view pulling defaults from `CFG`. Nothing named "the canonical list of all X"; a collection could not be **replaced** wholesale (only `add_*`/`append_*` existed); no documented precedence said which value wins when the same thing is set on the task, a manager, `CFG`, and an env var; and tools — the family users touch most ("make my CLI a tool", "drop the worktree tools") — were hardwired in `common_tools.py` with a mutation shape of their own.

The goal is that zrb be **intuitively configurable** — readable without a manual — through three fixed channels:

1. **Environment variables** — `ZRB_*` set outside any code.
2. **`zrb_init.py` appending** components/tools to the canonical collections.
3. **`zrb_init.py` replacing** a component (a custom UI, a custom registry, a fully custom `PromptManager`).

**Decision.** One vocabulary, one *layered* resolution model, replacement as first-class as appending, five component families with one shape, and a stated rule for which channel to use.

**Part 1 — Terminology.** Two distinct concepts:

- A **registry** is the *canonical collection of all X* and the source of defaults. It is registered by name (`skill_registry`, `sub_agent_registry`, `hook_registry`, …), configured from `zrb_init.py` and `CFG`, and owns the full set of X from filesystem discovery *plus* everything added in code. It stores and answers queries; it does not resolve.
- A **manager** (or the owning task) is the *per-occasion consumer* that resolves a value at use time, reading the registry for a default and letting a task pin something narrower.

**Part 2 — Layered resolution, not winner-take-all precedence.** A layer has a **fallback** (the layer below), an **own value** (set with `set_*` or the constructor), and **deltas** (`append_*`/`prepend_*`/`remove_*`):

- **Fallback chain.** A manager that sets nothing reads its registry; a registry that sets nothing reads its `CFG`/env twin (or seeded code default). Each layer is the default for the one above.
- **Deltas layer over the resolved base.** Deltas at any layer are recorded as ordered ops and replayed over that layer's *freshly resolved* base at query time, so a later change to `CFG`/env or the registry below stays visible.
- **`set_*` replaces the layer's own value**, ignoring the layer below and clearing that layer's pending deltas. `None`/unset re-defers to the fallback.
- **Concrete or deferred.** An own value may be a concrete list or a zero-argument callable resolved at query time (Part 3).

To customize, a user either `set_*`s a value (ignoring the baseline) or layers deltas on the shipped baseline; to keep shipped behavior, they set nothing.

**Part 3 — Evaluation is deferred.** A value in any layer may be a **callable/lambda** evaluated only when consumed (at task execution, per prompt compose, per run). This generalizes ADR-0005's deferred-attribute doctrine from strings to structured components:

- `CFG` may be mutated in `zrb_init.py` *after* a task/manager is constructed, and env vars may be read lazily, so an eagerly captured value would go stale.
- Structured values (prompt lists, tool sets) cannot carry lambdas through an env-var string, so they are set in `zrb_init.py` as callables and resolved at use.

**`CFG` stays the scalar home** (ADR-0021/0022); structured, swappable components (tools, skills, agents, prompts, hooks, UI) go through the registry/manager API.

**Part 4 — Replacement is first-class.** Besides `add_*`/`append_*`/`prepend_*`, a registry offers:

- `remove_<name>(...)` — drop by value or key.
- `set_<name>(...)` — replace the whole collection, ignoring the layer below and clearing the layer's pending deltas (Part 2). The replacement may be a concrete list **or** a deferred callable (Part 3).

`set_()` accepts a default-derived value too: `set_(skill_registry.get_all() + [mine])` is legal, and `set_([only_mine])` is the clean-slate swap.

**Part 5 — Five component families, one shape, and one mutation surface chosen by collection shape.**

| Family | Registry (canonical set) | Manager / resolved consumer | CFG twin |
| --- | --- | --- | --- |
| Prompts | `prompt_registry` | `PromptManager` | `CFG.LLM_PROMPT` |
| Tools | `tool_registry` | the task's tool lists (`LLMTask.tools`, …) | `CFG.LLM_TOOLS` |
| Skills | `skill_registry` | `SkillManager` (catalogue + activation) | `CFG.LLM_SKILLS` |
| Sub-agents | `sub_agent_registry` | `SubAgentManager` (roster + delegation) | `CFG.LLM_AGENTS` |
| Hooks | `hook_registry` | `HookManager` (hydration + dispatch) | `CFG.LLM_HOOKS` |

- **Ordered pipeline** (order is the semantics — tools, prompts): `append_X`, `prepend_X`, `set_X` (wholesale), `remove_X` (by value).
- **Unordered, name-keyed set** (a key owns its entry — skills, agents, hooks): `add_X`, `set_X` (wholesale), `remove_X(name)` (by key).
- There is no `add_X` alias on ordered collections: position is the whole semantics, and `add_` cannot say front or back.

**Part 6 — Every registry's `CFG` twin is a name allowlist over the default layer.** An env var can only round-trip strings, and most registry content is code or files — so a twin *names* the members it touches:

> **When a twin is non-empty, only the named members of the registry's default (discovered) layer are visible — for prompts, only the named prompt strings.** An empty twin means "everything" and is the shipped default.

| Twin | Name key | Semantics when set |
| --- | --- | --- |
| `CFG.LLM_PROMPT` | prompt text | The default appended prompts (strings). The one content twin, because a prompt is a string. |
| `CFG.LLM_TOOLS` | registered tool name | Only these tools are available to agents. |
| `CFG.LLM_SKILLS` | skill name | Only these skills are visible in the catalogue (`LLM_ENABLE_BUILTIN_SKILLS` still gates built-ins independently). |
| `CFG.LLM_AGENTS` | agent name | Only these agents are in the roster. |
| `CFG.LLM_HOOKS` | hook config name | Only these hooks are dispatched. |

A twin filters the discovered/default layer only. Content registered in code — `zrb_init.py` `add_*`/`set_*` — layers on top and is always visible: env sets the baseline, code builds on it. Where a family has no manual/discovered split (tools, hooks), the twin filters the whole single-layer registry.

**Part 7 — The three channels, in user terms.** **Env vars name things; `zrb_init.py` builds things.**

```python
# 1. Environment — scalars and coarse name sets
#    ZRB_LLM_MODEL=gpt-4o   ZRB_LLM_TOOLS=Read,Write,Shell

# 2. zrb_init.py — appending, layered over whatever env configured
tool_registry.append_tool(my_cli_tool)       # ordered: appended last
skill_registry.add_skill(team_skill)          # name-keyed
prompt_registry.append_prompt("Remind me to update the changelog.")

# 3. zrb_init.py — replacing a collection, or swapping a manager on the task
prompt_registry.set_prompts(lambda: [...])
LLMChatTask(name="chat", prompt_manager=PromptManager(prompts=[...]))
```

**Consequences.** For any value, a reader can tell *which* layer holds it and *when* it is evaluated — the two questions that make configuration intuitive. One sentence — "registries hold the defaults, managers read them, env names the allowed members, `zrb_init.py` builds or swaps them" — lets a reader predict the API of the next family. Costs:

- Five env twins add named surface (`ZRB_LLM_TOOLS`, …) whose usual value is empty (defaults are full) — a deliberate trade.
- `PromptManager` is a resolved per-task view rather than a roster resolver, so it does not carry the full manager verb set; `test_mutation_surface.py` excludes it on purpose.

**Alternatives rejected.**

- *Make `CFG` hold structured lists of objects* — `CFG` is a flat scalar store backed by `EnvField` (ADR-0021/0022); lists of arbitrary callables cannot round-trip env vars, and serializing them would couple config to the object model.
- *Merge "registry" and "manager" into one class* — they answer different questions (what is canonical vs. what this task uses), and one class makes the shared-collection case (two tasks sharing one tool set) awkward.
- *Keep only `add_*`, no `remove_*`/`set_*`* — channel 3 would be unreachable, and "default plus mine" could not be expressed.
- *Resolve registry defaults eagerly at construction, or copy twins at startup* — the value freezes before `zrb_init.py` has run or mutated `CFG`. Each twin is read lazily at resolution, so env, `zrb_init.py` mutation order and later `CFG` edits all compose.
- *Give every twin content semantics (an env-var JSON list becomes the whole set)* — JSON-in-env is hostile to edit and quote. Name lists stay greppable.
- *Make `LLM_TOOLS` a denylist* — it would invert the meaning of "twin" (mirroring `remove_` rather than the set). Per-item exclusion belongs to `zrb_init.py`'s `remove_`.
- *Let each family keep its own mutation shape* — mixed `add_`/`append_` per family re-opens the confusion ADR-0035 addressed; one rule keyed on whether order matters is teachable and checkable.
