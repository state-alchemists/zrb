# ADR-0143 — One usage line per request, with its reason and a digest of its prompt

- **Status:** Accepted
- **Date:** November 19, 2026

## Context

ADR-0127 made the log a faithful copy of what pydantic-ai reports, summed per round. ADR-0142 named the call that spent the tokens. Both are right, and both answer questions about *who* and *when* — neither can say *which request*, because a round is one line however many requests it made. ADR-0142 wrote that consequence down: "No per-request row, so a miss is still not attributable to a round… `run_id` and `parent_run_id` are deferred to the per-request work, where they would earn their keep."

That deferral is the blocker under board 0003 §4. Four live levers cannot be read at round level: a restarted thread's 113 single-request turns, the hook agent's four model-calling configs under one name, a compaction trigger that fires mid-turn, and the question §7.7 asks outright — what makes a request read zero cached tokens in the middle of a warm session. A round of fifty-four requests pays for one number, and a summary cannot say whether the input rose because the history grew or because zrb rewrote a prefix it had already sent.

## Decision

**A second file, not a second meaning.** Request rows go to `request-YYYY-MM.jsonl` beside `usage-YYYY-MM.jsonl`, written by `contracts/shared/request_log.py`. The summed line stays the bill and every table built on it keeps its meaning; the request rows explain where that bill came from, and the two join on `turn` — the id `TurnCursor.turn_id` already gave every round of one turn, which `UsageRecord` now carries too.

**A row per model request, read off the messages the run returned.** Every `ModelResponse` in a round's new messages carries its own `RequestUsage`, so the row is a read after the round rather than a hook on the streaming path — no per-event work, and no second place that knows how a request is made. The rows a round writes are its own responses only: the history it was handed was already filed by the round that sent it.

**A run outside the turn loop writes the same rows, on a turn id of its own.** The auxiliary call sites — the hooks, the shell judge, the namer, the summarizer, a side question, dictation's judge, speech — run an agent themselves and never enter the turn loop, so `record_standalone_requests` serves them from the same `_rows_for` the turn's writer uses: one writer for what a row says, two callers for where the turn id and the starting index come from. Such a run has no turn, so one is minted per call — its rows join on it and it joins nothing else. A run handed a `message_history` folds that history into the count and the digest without giving it rows, the same rule the round's writer follows: a side question reads the conversation so far, and a row that ignored it would describe a prompt that was never sent.

**Four fields carry what the sum cannot.** `reason` says what the request is in its turn — `opening`, `follow_up`, `retry`, `resume`, `continue` — and is set by the loop, because the loop is the only thing that knows why it went round again. `prompt_hash` is a digest of the messages as sent, and `prompt_messages` is how many of them there were. `index` numbers the requests of one turn across its rounds, retries included.

**The digest is folded forward, one message at a time.** Folding the base history once per round and then each new message keeps the cost linear in what was sent rather than quadratic in what it carried. What is folded in is what the provider receives: the parts, and the request's instructions, since a changed system prompt is part of what the cache reads. What is stripped first is what it does not: part and message timestamps, the metadata zrb hangs on a message, provider details, response ids, and a response's own cost and model. A tool call's id stays, because the wire carries it.

The strip is the decision's second half, and the review of this pull request is why it exists. The first version hashed the serialized message as pydantic-ai dumps it, and a `UserPromptPart` is stamped when it is made — so a retry that rebuilt its request message produced a different digest for the same prompt, which is the one comparison the digest exists to make. Tool definitions are left out entirely: they are not in the message list, and they are constant per configuration and priced separately (ADR-0058).

What the pair then settles is two-sided — an equal digest with a different cache read says the provider was handed the same prompt twice, while a digest that changes with `prompt_messages` unchanged says zrb rewrote the prefix in place. One hash alone cannot tell those apart; the count can.

**Only numbers, a reason and a digest.** No prompt text, no tool arguments, no file content — the same rule the summed log keeps, for the same reason: it is written by default, so it must not become a transcript.

**A log that cannot be written costs its rows.** A full disk or a read-only home must not fail the turn that produced the numbers, and must not fail a second time on the file beside it.

## Consequences

- **A zero-cache read mid-session becomes attributable.** §7.7's five miss records on 11-16 and the 10:57 pair today can be told from a rewrite of zrb's own.
- **The next three steps of board 0003 can be read, not estimated.** A restarted thread's single-request turns, a hook's four configs, and a trigger that fires inside a turn are all per-request questions.
- **Every model call in the tree writes rows, except the ones that are not model calls.** The seven auxiliary sites now write their own, each with a reason that names it — `hook`, `memory_week`, `shell_judge`, `namer`, `summarizer`, `side_question`, `dictation_judge`, `speech`. The four model-calling hooks share one reason on purpose: telling them apart is §4 step 2, and it needs the hook read first.
- **A digest is only as honest as its field list.** The first version hashed the message as pydantic-ai dumps it, timestamps included, and could not tell a resend from a rewrite. Two tests now hold that line: one sends the same prompt in a rebuilt request, one changes only bookkeeping on a copy of the same round.
- **`/usage` does not read the new log.** Nothing in the report changes. The sections that would — a thread's restart price, which request of a round missed — are later steps.
- **The rows repeat numbers the summed line holds.** About half a megabyte a month at today's rate, bought back as the only way to see a single request.
- **The shared month-file reader no longer knows what a record holds.** The window moved into the caller's `select`, so one reader serves both logs without either owning the other's shape.

## Alternatives

- **Replace the summed line with request rows.** Rejected: every table in board 0003 counts a record as a run, and a bill that changed meaning in the same diff as its new detail could not be checked against the old one.
- **A row per round, carrying its request count and one reason.** Rejected: the reason and the digest are per request — a round's fifty-four requests send fifty-four different prompts, and the zero-cache question is about one of them.
- **Hook the streaming path to observe each request.** Rejected: the messages already carry each response's own usage, so a hook would be per-event work to re-learn what the result hands over for free.
- **Fold the tool definitions into the digest.** Rejected: they are not in the message list, they are constant per configuration, and they are priced separately (ADR-0058) — a digest that moved with them would answer the cache question less clearly, not more.
- **One log file with a `kind="request"`.** Rejected: `/usage` sums every line it reads, so a request row beside a summed row would be counted twice — the one failure a log whose job is a bill cannot survive.
