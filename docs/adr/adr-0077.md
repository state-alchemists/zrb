# ADR-0077 — Queued messages are editable entries, edited in place from the input field

**Status:** Accepted

**Context.** A chat message typed while a turn is in flight waits in the UI's message queue, since the message loop runs one job at a time. Users often spot a typo or want to refine the instruction right after pressing Enter; without editing, the only recourse is to let the bad message run and send a correction.

Editing a queued message should replace its text in place — so the turn streams the corrected wording when it starts — and rewrite the echoed transcript line to match. A queue of bare `async def job()` closures cannot support this: nothing identifies, indexes or mutates a waiting message, or tells whether it has started.

**Decision.** The message queue holds `QueuedMessage` entries instead of raw jobs, and the default TUI lets the user recall, edit and replace a still-queued message from the input field.

1. **The queue is an `asyncio.Queue` of `QueuedMessage` objects.** Each entry carries `text`, `attachments`, a `kind` (`message` vs `exec`), and `run` — an async job that reads `entry.text`/`entry.attachments` **at execution time** rather than capturing them. Only the consumer pops entries (`get()`), so anything still queued is not yet running; editing never races the turn.

2. **`MessageQueue` subclasses `asyncio.Queue`**, so existing consumers keep `get`/`put_nowait`/`task_done`/`join` semantics (the web chat awaits `join()`). It adds peek/navigation (`peek_latest`, `latest_editable`, `editable_before`, `editable_after`), `contains`, and `remove`; `remove` decrements the unfinished-task counter (the entry will never reach `task_done`), so `join()` still resolves. `latest_editable` and the navigation methods skip `exec` jobs — a shell command is not a user message. All producers (`BaseUI.submit_user_message`, `MultiUI`, the `/exec` handler) build entries.

3. **Editing is a field write plus an echo redraw.** `BaseUI.edit_queued_message(entry, new_text)` refuses if the entry's turn has started; otherwise it replaces `entry.text` and asks each child UI to rewrite the echoed line. The echo span is recorded at submit time only when the line landed verbatim in the output buffer. A pending tool confirmation diverts content into a confirmation buffer; then the span stays unset and the edit takes effect without a visible redraw.

4. **Up/Down recall in the default TUI.** With the input field focused, Up recalls the newest queued message into the buffer (saving the in-progress draft); further Ups walk older queued messages, Down walks newer ones and then restores the draft. It is a buffer-level keybinding (layout), because buffer bindings shadow app-level ones, and it falls through to prompt-toolkit history recall when nothing is queued.
   - The cursor is pinned to the end of recalled text (`Buffer.text` would otherwise leave it mid-message).
   - An unedited recalled message keeps Up active even when multi-line (the line-position guard would otherwise steal the press, since the cursor is not on the first line).
   - The saved draft survives a stale recall — the message's turn started mid-edit and a later Up drops edit mode.
   - Typing or moving the cursor returns the arrows to cursor movement.

5. **Enter edits instead of submitting.** While a queued message is in the buffer, Enter replaces that entry's text, broadcasting the redraw to every child UI of a `MultiUI` (entries are shared). An empty edit cancels back to the saved draft. If the recalled message's turn already started, or the recall came from previous-message history, the first Enter is consumed with a note that the message is no longer waiting and the next Enter sends the text as a new message. This prevents an edited recall from silently becoming a duplicate submission.

6. **The echo redraw splices by recorded span.** The default UI rewrites the echoed line in its output buffer and shifts the tracked re-wrap blocks (`_rendered_blocks`) after it, so a later resize still re-wraps markdown at correct offsets. The entry remembers the echoed text its span points at; if a redraw finds different text there (a resize re-wrapped an earlier block and shifted the transcript), it drops the span rather than splice at the wrong offset — the edit stays effective, only the echo is not rewritten. Non-terminal UIs (telegram, polling, http) override nothing: their `redraw_echo` is the base no-op, so edits update the message without a redraw.

7. **Ctrl+X drops a queued message, out of every transcript.** `BaseUI.delete_queued_message(entry)` refuses once the entry's turn has started; otherwise the entry leaves the shared queue and every UI holding an echo of it is asked to splice that line out (`remove_echo`, the delete-side counterpart to `redraw_echo`; `_broadcast_echo` does the best-effort broadcast for both). Removal is per UI because the output buffers are per UI — a child left out keeps a line for a message that never runs. While a sub-agent's live view is up, the pane holds that agent's transcript and the main one is parked in `saved_main_output`; `remove_echo` splices the *parked* copy, since that is the text the view restores — skipping it would bring the deleted line back on screen. Either way the input returns to the draft saved before the recall, so the recalled text cannot be submitted again when the turn started under the recall.

**Consequences.** A typo'd or refined message can be fixed — or dropped — while the assistant works, with no corrective turn. The queue becomes a structured, introspectable collection that future features (reordering, per-message status, cancelling a specific queued turn) can build on. Costs: the redraw assumes nothing else rewrites the transcript inside a tracked span (already implicit in `rewrap_output`), and the queue holds entry references until their turn starts.

**Alternatives rejected.**
- *Recall-only via prompt-toolkit history* — Enter would send a *new* message, indistinguishable from a duplicate.
- *Text-matching at Enter time* — treating an Enter whose text equals a queued message as an edit is ambiguous when a user genuinely sends the same message twice.
- *A separate edit mode (`/edit <n>`)* — forces the user to know queue positions and adds a command for what a keybinding does.
- *Rewriting the whole output buffer on edit* — correct but heavy; span splicing with block-offset shifting keeps re-wrap intact.

**Where it lives.** `src/zrb/llm/ui/base/message_queue.py` (`MessageQueue`, `QueuedMessage`), `src/zrb/llm/ui/base/ui.py` (`edit_queued_message`, `delete_queued_message`, `_fan_out_echo`, `effective_message_queue`), `src/zrb/llm/ui/any_ui.py` (the `track_echo_span`/`redraw_echo`/`remove_echo` echo contract, with inert defaults in `src/zrb/llm/ui/state_defaults.py`), `src/zrb/llm/ui/default/message_editing.py` (recall/Enter/delete/echo part), `src/zrb/llm/ui/default/app/layout.py` (Up/Down buffer bindings), `src/zrb/llm/ui/default/output.py` (`replace_output_span`).
