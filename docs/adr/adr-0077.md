# ADR-0077 — A run is bounded at three scales: requests, repeated calls, and repetition inside one response

**Status:** Accepted

**Context.** An agent run has three ways to never finish. They look alike and none of the three instruments sees the other two.

The first is a model that stops converging *across* requests — re-editing the same file from memory, re-reading output it has already seen. The prompt tells it to change approach by the third attempt, but prose cannot enforce itself; the worst case measured reached 343 tool calls, 267 of them edits, and would have kept going. `LLM_MAX_REQUEST_PER_RUN` (default 300) is the enforcement half of that rule, and until now it was the only bound and had no record.

The second is a model that stops converging *inside* one response: a decoding loop that emits the same handful of lines forever. Benchmarking caught one — a `copywriting` trial that made two tool calls and then wrote `I have now created the MIGRATION.md file. I will save it to a file.` **2,510 times**, filling 244KB of transcript until a 600s wall-clock kill. Nothing in the system could see it. The request cap counts requests, and this was one request. The empty-completion guard tests for an *absent* response, and this response was the opposite of absent. The provider will stream a degenerate continuation for as long as it is read, so wall clock was the only backstop, and by the time it fires the run has spent its entire budget producing nothing.

The third is the commonest and was the most expensive: the same tool call, byte-identical arguments, back to back. It survives every guard because each call is individually legitimate. Across one 288-trial grid it accounted for half the timeouts — an agent that completed a 44-site migration *correctly*, then issued the same `grep -rl "new_auth("` roughly a hundred times until the clock stopped it (validator score 1.0, recorded as a timeout); and weaker models re-issuing the same failing `Edit` against a file they never re-read, degrading it further each time. The request cap is the wrong scale: 100 repeats is well inside 300, and by the time a cap that low would bite it would also be cutting legitimate work.

**Decision.** Bound all three, each with the signal that actually separates the pathological case from the healthy one.

- **Across requests: count requests.** `UsageLimits(request_limit=CFG.LLM_MAX_REQUEST_PER_RUN)`, surfaced as an actionable halt rather than pydantic-ai's raw `UsageLimitExceeded` — a run that hits the cap should be inspected, not simply given a larger cap.
- **Inside one response: measure repetition, not volume.** `RepetitionDetector` watches the text deltas of the current response and trips when the last `LLM_MAX_REPEATED_LINES` (default 32) non-blank lines carry four or fewer distinct values. On a trip the stream is abandoned mid-flight, so the provider stops being paid to repeat itself, and the identical request is re-issued up to twice — nothing was committed, because the result event never arrived. A third trip raises, naming the knob.
- **Across calls: count *consecutive* identical ones, and answer rather than halt.** `RepeatedCallDetector` sits at the one tool chokepoint (`SafeToolsetWrapper.call_tool`) and, past `LLM_MAX_REPEATED_TOOL_CALLS` (default 6), refuses the call and returns a `[SYSTEM SUGGESTION]` (ADR-0057) naming both exits: the work is already done, so report it — or the approach is not working, so read the file, widen the search, or say what blocked you. It does not halt the run, because the two cases are indistinguishable from outside and only the model can tell them apart; the agent that had already finished needed to be told to stop, not killed.

Two design points carry the safety of the third guard. **Consecutive, not cumulative:** a run-fix-run debug cycle re-issues the same `pytest` many times and is the loop working as intended, but an `Edit` lands between the runs and resets the streak — a streak means nothing happened in between, so the repeat cannot return anything new. And **polling tools are exempt** (`MonitorProcess`, `GetDelegationResult`), because "call me again with the same arguments" is their contract rather than a symptom.

**Consequences.** A decoding loop now costs a window of repeated lines — seconds — instead of the whole timeout, and reports itself as a provider fault rather than a mute timeout. A call loop costs six repeats and then becomes a prompt to finish or change approach — which is what the `Recovery` prompt rule asked for and could not enforce, so **that clause is now deleted from `workflow.md` and `workflow.lean.md`** rather than duplicated here (ADR-0049 measured it unfollowed by every preset: `full` 0/7, `lean` 1/7, `minimal` 2/7). The guidance also arrives where it applies, in the tool result, instead of ~10,000 characters earlier in a rulebook. Measured against the grid this targets: cells that hit the request limit are 15% of scored cells and **55% of all input tokens**, at 86,988 tokens and 74.4 tool calls each against 12,618 and 2.5 for a completed one. The three knobs are independent and each can be set to 0. Costs: a response that legitimately emits 32 near-identical lines is misread; a cycle that never emits a newline is invisible until it does; and a non-polling tool that genuinely wants seven identical consecutive calls now needs a raised knob.

**Alternatives rejected.** *Halt the run on a call loop, as the other two scales do* — the measured case had already produced correct work and needed to be told to stop, not killed; halting would have converted a 1.0 score into a failure. *A cumulative count of identical calls rather than a consecutive streak* — condemns the run-fix-run cycle, which is the debug loop the prompt asks for. *Lower `LLM_MAX_REQUEST_PER_RUN` instead* — 100 repeats sits well inside 300, and a cap tight enough to catch it would cut legitimate wide migrations (the largest honest run measured was 212 calls). *A cumulative output-token cap* (`UsageLimits.output_tokens_limit`, which pydantic-ai does check mid-stream, so it was the cheapest possible fix) — the populations overlap and volume cannot tell them apart: the degenerate response had emitted ~44k output tokens when the clock killed it, while a healthy `research` run in the same grid legitimately emitted 73,440. Any cap that spares the second lets the first run for most of an hour. *Wall-clock timeout per response* — punishes a slow provider and a long legitimate answer identically, and still burns the timeout. *Rely on `LLM_MAX_REQUEST_PER_RUN`* — it cannot see inside a request, which is where this failure lives. *Suffix-based cycle detection over a rolling character window* — handles the no-newline case the line detector misses, at the cost of a period-search on every delta; deferred until a real cycle is observed that the line test does not catch. *Feed the degenerate text back as an error for the model to recover from* — it is a provider-side decoding fault, not something the model reasoned its way into, so there is nothing for it to learn from and re-issuing the request clears it more often than not.

**Where it lives.** `llm/agent/run/repetition.py` (both detectors), `llm/agent/run/runner.py` (`_execution_loop`, `_request_limit`, `_explain_usage_limit`), `llm/agent/run/retry_loop.py` (`RetryState`), `llm/agent/common.py` (`SafeToolsetWrapper.call_tool`), `config/mixins/llm_limits.py` (`LLM_MAX_REQUEST_PER_RUN`, `LLM_MAX_REPEATED_LINES`, `LLM_MAX_REPEATED_TOOL_CALLS`).
