# ADR-0083 — Delegated sub-agent sessions: persisted, listed, resumable, and swappable in place

**Status:** Accepted

**Context.** A comparison against opencode's delegation model (its `task` tool spawns a real, durable, parent-linked child `Session` a user can navigate into, list, and keep chatting with) found zrb's `DelegateToAgent`/`DelegateToAgentBackground` (ADR-0068/0069) had no equivalent: `_run_agent_task` calls `run_agent(..., message_history=[])` and the result lives only in the returned string — the transcript is discarded, nothing is addressable, and nothing is resumable.

Porting opencode's model directly does not fit zrb: opencode's sessions are SQLite rows with a `parent_id` column and one uniform session-viewing route component; zrb's conversations are flat JSON files under `LLM_HISTORY_DIR` (`FileHistoryManager`), the web runner drives every session through one shared `LLMChatTask` instance reconfigured per message (`chat_session_runner.py`), and the CLI TUI drives a single `LLMTask` instance for the life of the process. A parent/child *database* has no home here without inventing one; the naming convention and existing per-session config-swap pattern already do.

Four phases were scoped, each independently shippable:

**Decision.**

**Phase A — persist the transcript.** `_run_agent_task` (`delegate.py`) saves the sub-agent's message history through the existing `FileHistoryManager` under a derived conversation name — `{parent_session}-sub-{agent_name}-{agent_id}` (`format_delegated_session_name`, `llm/util/subagent_session_naming.py`) — for every completed delegation, unconditionally. The transcripts live in `LLM_HISTORY_DIR/subagent/{agent_type}/`, separate from ordinary main-agent conversations (which stay flat in the history root), so a listing/backup/prune never mixes the two; delegated files written before that layout shipped remain readable flat in the root as a fallback, never auto-migrated.

The name is appended to the tool's result string so it's discoverable immediately, not only once Phase B's listing exists. Persistence failures are best-effort (logged, never break delegation) — matching `_fire_subagent_hook`'s posture.

Persistence is **not** gated by a config flag. An early gate was dropped once two bounds made always-on safe: no backup is written for a session that's never resaved (`write_backup=False`), and `_prune_old_subagent_history` deletes the oldest files past `LLM_SUBAGENT_HISTORY_RETAIN` (default 50, global across agent types) right after every write.

**Phase B — addressable and listable, at zero new storage.** `ChatSessionManager._session_listing()` (`runner/chat/chat_session_manager.py`) already groups history files by base name for the web session list; `parse_delegated_session` (same naming module) recognizes Phase A's shape and adds `parent_session_id`/`agent_name` to each listing entry — `None` for an ordinary session.

`chat_api_route.py` needed **no changes at all**: it already forwards `get_sessions()`'s dicts verbatim, so list/attach/message endpoints work for delegated transcripts for free. A session actively driven under a name that happens to match the shape is never misclassified — the check only applies to history-file-only (non-active) entries.

**Phase C — resume through the correct persona, not the main agent.** `SubAgentManager.create_agent`'s tool/model/prompt resolution was extracted into a public `resolve_agent_build` (shared by three callers now, so all three cannot drift against each other) and reused by a new `SubAgentManager.create_llm_chat_task(name)`, which builds a real `LLMChatTask` — same resolved system prompt, tools (still delegate-tool-free), and model as the raw pydantic-ai `Agent` `create_agent` returns, but wrapped in the zrb `Task` type the web runner's `.async_run(session=...)`/`.history_manager`/`.ui_factories` contract needs.

`chat_api_route.py`'s `stream_chat` resolves which task drives a session via `_resolve_llm_chat_task_for_session`: a delegated `session_id` resumes via `create_llm_chat_task`, never silently falling back to the shared main task. Returns `None` (surfaced as a named error, not a crash) for a definition built from `agent_instance`/`agent_factory` — a pre-built `Agent` has no system_prompt/tools/model triple to re-derive a task's config from.

**Phase D — the CLI TUI gets the same resume, in place, plus the activity-registry prerequisite fix.** Three parts:

- `agent_activity_registry` (`llm/agent/activity.py`) was keyed by a flat dict — the `ponytail:` note already on it flagged cross-session bleed if a process ever hosted multiple sessions, which the web runner already does. Every entry (`start`/`update`/`finish`/`active`/`snapshot`/`clear`) is now keyed by `session_id` (default `""` — the single-session CLI case, unchanged for every existing caller), threaded through `BufferedUI` and `_run_agent_task` via the ambient `get_current_tool_session()`.

  `finish()` only empties an agent out of its session's bucket, not the bucket itself, so `ChatSessionManager.remove_session()` calls `agent_activity_registry.clear(session_id=...)` on teardown — otherwise a long-running web process accumulates one empty bucket per session_id it has ever seen, for the life of the process.

- The CLI's `/load <name>` (`llm/ui/base/conversation_commands.py`) already replayed any named history file; it now also swaps *which persona* drives new messages when `name` matches the delegated shape, and restores the main agent's original persona when loading back to an ordinary name — `/load` is the single, symmetric verb for both directions, needing no new command.

  Swapping mutates the CLI's single long-lived `LLMTask` instance in place (`ui.llm_task.tools = ...`, `.toolsets = ...`, `.prompt_manager = ...`, plus `ui.model`) rather than replacing the object, because the UI holds a fixed reference to it for the process's lifetime; this required adding `tools`/`toolsets` setters and a `prompt_manager` setter to `LLMTaskBuilding` (previously append-only / getter-only), and recording the *original* config once, on first swap, so `_restore_main_persona` never restores an intermediate sub-agent's config as if it were the main one.

- The status/info bar shows `🎭 Sub-agent: <name>` while swapped, absent otherwise — the same "collapses when idle" posture as the existing activity panel, and the UI clue Claude Code/opencode give via their session-position footer.

**Phase E — cancelled-then-continued sub-agents report back.** A sub-agent a human cancels (Esc while viewing it in the TUI) and then keeps chatting with directly runs its follow-up turns purely inside its own live view (`live_session.py`'s `_continue_live_session`): the main agent only ever heard `"Cancelled by user"` from the delegation and never learns what the continued conversation produced.

When such a session then ends *naturally*, the continuation's **latest response** is handed to the main agent as its next turn — just the response text itself, nothing more — delivered through a new `submit_message` channel on the parent UI: steered into the live main turn when one is still in flight (ADR-0078), otherwise queued on the main `MessageQueue` as its next turn. A session the user cancels *again* suppresses the report (the user's latest word was cancel), as does one whose history holds no assistant reply; delivery is best-effort.

The trigger is a sticky `notify_parent_on_end` flag set by `cancel()` on the live session, so only cancel-then-continue sessions report — ordinary continuations of a normally-finished delegation do not (their result already reached the main agent).

**Consequences.** A delegated sub-agent's transcript is inspectable, listable, and — through the web API and the CLI's `/load` alike — actually resumable as that sub-agent, not the main agent, closing the gap the initial review identified as zrb's largest deficit next to opencode. The naming convention is the only new "index": no new table, no new registry, so Phase B cost nothing beyond a regex.

Costs: every delegation writes a history file — bounded by `LLM_SUBAGENT_HISTORY_RETAIN`, but always-on means a transcript is persisted even for sub-agents whose work nobody will read (the trade: a cap-kept few files per delegation against always-resumable work); the name-parsing approach is best-effort, not a hard parser — an agent or session name that itself contains the literal `-sub-` delimiter can misparse (acceptable for a listing feature).

The CLI persona swap is a genuinely new capability on `LLMTaskBuilding` (`tools`/`toolsets`/`prompt_manager` setters) that did not exist before — low-risk (additive, mirrors the already-established `history_manager`/`approval_channel` setter pattern in the same file) but real new surface area; and Phase E's report-back can trigger a fresh main-agent turn the user did not type (the requested payoff — the main agent learning the sub-agent's latest response — at the cost of an occasionally unsolicited response).

**Deliberately left out of this decision — not a rejection, an explicit boundary:** the shared-`LLMChatTask`-serialization ceiling the web runner already has (`chat_session_runner.py`'s `task_lock`, one message drives *a* task at a time) is untouched. A delegated session resumed via `create_llm_chat_task` gets its own `LLMChatTask` instance — but `run_chat_session` still acquires `session_manager.task_lock` unconditionally for every message regardless of which instance it's driving, since the lock is one global lock on `ChatSessionManager`, not scoped per task.

A resumed delegated session therefore still serializes against ordinary sessions on that same lock; only its post-lock wiring differs (its own task instance, not the shared main one). This decision does not attempt to raise that ceiling for ordinary sessions or scope the lock per task instance — that would be its own, unrelated refactor.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| A real session-tree store (opencode's model) | A parent/child database with a uniform session-viewing route; rejected because zrb's conversations are plain JSON files with no existing row-based session table to extend, and building one just for this would dwarf the feature it serves. |
| A primary/subagent `mode` distinction on `SubAgentDefinition` (opencode's `mode: primary \| subagent \| all`) | Would let any sub-agent be driven directly as a top-level chat (the `--agent` CLI-flag idea raised in the initial review); explicitly not built in this pass, since resuming a *specific delegated session* doesn't need a general primary-agent concept, only the narrower "which persona does this one resumed session use." |
| Teach `/load` nothing and add a separate `/resume-subagent <name>` command | A second verb for what is, from the user's perspective, the same action ("switch what I'm looking at"); `/load` already existed and already switches sessions, so extending it kept the surface smaller. |
| Rebuild a whole new `LLMTask` object for the CLI swap, mirroring the web path's `create_llm_chat_task` | Rejected because the CLI's `BaseUI` holds one fixed `_llm_task` reference for its entire process lifetime; replacing the object would require re-wiring every place that reference is threaded through, whereas mutating its config in place reuses the exact mechanism `/model` already established for live reconfiguration. |
| Gate persistence behind a config flag (opt-in) | The original design, `CFG.LLM_ENABLE_SUBAGENT_HISTORY` off by default: without a retention cap, every delegation silently grew `LLM_HISTORY_DIR` with brand-new never-reused names, so the gate kept disk growth opt-in. Dropped once `LLM_SUBAGENT_HISTORY_RETAIN` pruning bounded the growth — with the cap, always-persisting is strictly more useful (every delegation stays browsable/resumable) at bounded cost and leaves one less knob to reason about. |
| Auto-migrate legacy flat delegated files into `subagent/{agent_type}/` on upgrade | Migration would move files under the user's feet and write to disk as a side effect of reading; the read-fallback keeps old transcripts working with no writes. |
| Defer the Phase E report until the user exits the sub-agent view | Rejected: delivery happens on the session's natural end regardless of the active view, because the main transcript is where the report belongs and the user asked for immediate notification; a second cancel is the escape hatch. |
| Wrap the Phase E report with context (which sub-agent it came from, its transcript name) | Rejected: the main agent receives only the continuation's latest response, bare, so it treats it exactly like any other follow-up it needs to act on rather than as a meta-note about a sub-agent. |

**Where it lives.** Shared naming: `src/zrb/llm/util/subagent_session_naming.py` (naming convention + `subagent/{agent_type}/` layout).

Phase A/B: `src/zrb/llm/tool/delegate.py` (Phase A call site; `persist_subagent_history`/`_prune_old_subagent_history`), `src/zrb/llm/history_manager/file_history_manager.py` (subagent-aware path resolution, backups, rotation, legacy fallback, search), `src/zrb/config/mixins/llm_content.py` (`LLM_SUBAGENT_HISTORY_RETAIN`), `src/zrb/runner/chat/chat_session_manager.py` (`_session_listing`, Phase B; `remove_session`'s activity-registry teardown, Phase D).

Phase C: `src/zrb/llm/agent/subagent/manager.py` (`resolve_agent_build`, `create_llm_chat_task`), `src/zrb/runner/chat/chat_api_route.py` (`_resolve_llm_chat_task_for_session`).

Phase D: `src/zrb/llm/agent/activity.py` (session-scoped registry), `src/zrb/llm/ui/buffered_ui.py` and `src/zrb/llm/tool/delegate.py`/`delegate_background.py` (session-scoped activity wiring; `buffered_ui.parent_ui` also Phase E), `src/zrb/llm/task/building.py` (`tools`/`toolsets`/`prompt_manager` setters), `src/zrb/llm/ui/base/conversation_commands.py` (persona-swap-on-`/load`), `src/zrb/llm/ui/default/output.py` (the status-bar indicator).

Phase E: `src/zrb/llm/agent/subagent/live_session.py` (report-back trigger and latest-response extraction), `src/zrb/llm/ui/base/ui.py` and `src/zrb/llm/ui/multi_ui.py` (`submit_message`).
