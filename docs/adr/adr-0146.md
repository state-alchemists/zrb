# ADR-0146 — A write to the MCP config is a hard ASK, above yolo

**Status:** Accepted

**Context.** The MCP loader reads a JSON file — `mcp-config.json` by default — whose `mcpServers` entries carry `command` and `args`. Those values reach `StdioTransport`, which starts a host process: outside `build_sandboxed_argv`, outside the filesystem gate, and outside every approval prompt. The file the agent can write therefore decides what a *later* session runs.

No level of the approval chain said so. A `Write` to that path is an ordinary `EDIT`: under yolo it was auto-approved, and under a ruleset with no opinion it fell through to the same yolo. The model could grant itself a process with a file write.

The rule could not be expressed either, for a second reason. A deferred `ToolCallPart` carries a tool name and its arguments and nothing else, while the capability tag lives on the registered callable, so `tool_capability(part)` answered `UNKNOWN` for every deferred call. A ruleset keyed on a capability therefore never matched: `edit:ask` fell through to a later `*:allow`, and a write the user had gated ran unprompted.

**Decision.** One built-in rule, evaluated where a permission-policy ASK would be: when a call's capability is `EDIT` or `UNKNOWN` and one of its path-shaped arguments realpaths to a config the loader reads, the decision becomes a hard ASK. It carries the same authority as a policy ASK, so it skips yolo and yolo's exempt-tool set, and an unattended run resolves it through the existing non-interactive branch (ADR-0062) as a denial rather than a prompt.

- **ASK, not DENY.** The file is ordinary workspace content; a user may well mean to edit it, and only they can say.
- **DENY still wins.** The rule raises the floor and never lowers a ceiling — a policy `DENY` that already answered is left alone.
- **A config that does not exist yet counts.** Creating the file is the case the rule is for.
- **The path set mirrors the loader's walk** from the working directory to the home directory, and is computed without importing the MCP client: the approval cascade must not pay for a client library to answer a question about a path.
- **Shell redirects stay out of reach**, exactly as they do for `sandbox_gate`. A `Shell` call's capability is `EXECUTE` and its redirect target is not a path argument.

The capability is now resolved by LLM-visible name from a map registered when the agent is built, which is the same map the pre-deferral skip decision already built for itself. A name nobody registered stays `UNKNOWN`, which every consumer treats conservatively. This is a restoration of ADR-0062's intent — an `ask` is hard — rather than a new rule.

**Consequences.** The model cannot hand itself a host process next session by writing a file; the human is asked once, at the moment the path is visible. A capability-keyed `ask` now survives the deferred round-trip, so the ruleset behaves the same before and after it.

Costs:

- A genuine "add this MCP server" edit needs a click even under yolo.
- The path walk exists twice — in the loader and in the cascade — because importing the client into the approval path is worse than keeping two walks in step. A change to config discovery has to change both.
- A shell redirect into the file is not covered by this rule; what bounds that is the sandbox and the shell judge.
- The name → capability map is process-global and last writer wins. That is sound because a capability belongs to the tool rather than to the call — `Write` is `EDIT` in every run — but a tool registered under two capabilities is decided by whichever build ran last.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| `DENY` a write to the config | The file is a normal part of a user's workspace; refusing it outright blocks an edit the user alone can authorize. |
| Leave it to yolo like any other edit | yolo is a session toggle about edits in general, not an authorization to choose what the next session executes. |
| A per-tool `auto_approve` entry in one runner | Does not travel: sub-agents, the web runner and bare `LLMTask`s each wire their own list, which is how this class of gap appeared before (ADR-0062). |
| Refuse the config at load time and stop there | Not sufficient on its own: it cannot stop the write, so the user meets a file silently ignored instead of being asked whether to write it. A provenance check where the config is read is its own decision, recorded where that code lives. |
| Key the rule on the capability of the deferred part | Always `UNKNOWN`, which would make the rule fire on every call or on none. |
| Treat the write as `EXECUTE`, since a server is a process | Wrong layer: the tool being called is a file edit, and the process starts in a later session. |

**Where it lives.** `src/zrb/llm/engine/agent/run/deferred_calls.py` (`_is_mcp_config_write`, `_mcp_config_paths`, `_has_mcp_config_arg`, and the hard-ASK insertion), `src/zrb/llm/engine/agent/run/tool_capabilities.py` (the name → capability map), `src/zrb/llm/orchestration/task/chat/execution.py` and `src/zrb/llm/orchestration/task/shared_getters.py` (registration at build), `src/zrb/llm/capabilities/tool/mcp.py` (`_get_config_files`, the walk this mirrors).
