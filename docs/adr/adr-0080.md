# ADR-0080 — Mermaid renders as Unicode diagram art via `termaid`; PlantUML stays deferred

**Status:** Accepted

**Context.** ADR-0079 deferred Mermaid and PlantUML rendering, on the assumption both needed external tooling (`mmdc`/Node+Chromium for Mermaid, `plantuml.jar`/Java for PlantUML) and a terminal graphics protocol (sixel/Kitty/iTerm2) unreliable across the terminals zrb actually runs in. A follow-up spike re-checked that assumption for each separately, since they turned out not to be symmetric.

**Mermaid:** [`termaid`](https://pypi.org/project/termaid/) (PyPI) is a pure-Python, zero-required-dependency library — `termaid.render(source: str) -> str` — that renders a real subset of Mermaid syntax (flowcharts, sequence diagrams, and more) as Unicode box-drawing art, entirely in-process. No subprocess, no Node, no Chromium, no image protocol needed at all — the diagram is just text. Verified directly: flowcharts and sequence diagrams render legibly; unparseable input returns `""` rather than raising, which is a silent-failure mode (same shape as an unrecognized LaTeX macro in ADR-0079) that needs the same "empty result → keep the raw fence" fallback.

**PlantUML:** no equivalent exists. PlantUML *can* emit ASCII/Unicode art (`-txt`/`-utxt`), but only by running the real `plantuml.jar`, which needs a local Java runtime — reintroducing exactly the external-binary problem this ADR is trying to avoid for Mermaid. The public `plantuml.com/plantuml/txt/...` server avoids the local Java requirement, but sends diagram source to a third party over the network (an opt-in-only proposition, unlike a pure-Python import) and its own documentation notes ASCII output there is reliable only for sequence diagrams — class/component/activity diagrams rely on Graphviz-driven layout with no text-mode equivalent. Neither option matches the "no subprocess, no network, works everywhere" bar Mermaid actually clears, so PlantUML stays on the deferred list.

**Decision.** `render_markdown` calls `convert_mermaid_to_art` (`src/zrb/util/cli/mermaid_diagram.py`) on the markdown string, gated by `CFG.LLM_UI_ENABLE_MARKDOWN_MERMAID` (default on) — a second, independent pass alongside `convert_math_to_unicode`, mirroring that module's shape rather than extending it.

1. **Its own module, its own toggle; a core dependency, like `pylatexenc`.** Mermaid and LaTeX are unrelated libraries solving unrelated problems; sharing one file or one CFG flag would only make the fallback story harder to reason about. `termaid` is a core dependency (pinned `<0.9.0`, since it's pre-1.0), not an extra: it has zero transitive dependencies and a ~1.6MB footprint, so there's no install-weight case for gating it, and `LLM_UI_ENABLE_MARKDOWN_MERMAID` defaults on — an optional dependency would mean that default silently renders nothing on a bare install. The import stays lazy and memoized (`functools.lru_cache`-wrapped `_get_renderer`) purely for cold-start latency, matching `pylatexenc` in `latex_math.py` and the same reasoning ADR-0079 gives for other core deps like `markdownify`/`pyperclip`.
2. **No masking pipeline needed.** Unlike `$...$` math, a ```` ```mermaid ````/```` ```mmd ```` fence is an unambiguous, already-delimited marker — there is no equivalent to "$5 and $10" prose to guard against, so the module is just a fence-matching regex (the same fence-parsing shape as `latex_math.py`'s `_FENCED_CODE`) plus a per-fence render-or-fallback, with no code/inline-span protection required.
3. **A successful render stays fenced, not inlined as flowing text.** This is the one place this feature's fallback shape differs from LaTeX's: converted math is short enough to flow safely as prose, but diagram art is multi-line box-drawing whose spacing must survive verbatim. Dumping it into the document as plain paragraph text would let Rich's Markdown paragraph reflow re-wrap and corrupt it. The successful-render fence keeps its original delimiters and drops the `mermaid` info string, so Rich renders it as a plain, unhighlighted code block via `rich.markdown.CodeBlock`.
4. **Fallback is per-fence, not all-or-nothing.** A fence `termaid` can't parse, or one whose result is empty after stripping (the silent-failure mode observed in the spike), is left exactly as its original fence — today's pre-existing behavior (pygments has no `mermaid` lexer, so it already rendered as an unhighlighted code block via the same `ClassNotFound` fallback documented in ADR-0079). One broken diagram doesn't affect any other fence in the same document.
5. **The diagram shrinks to fit the console width instead of relying on Rich not to wrap it.** `CodeBlock.__rich_console__` (`rich/markdown.py`) always builds `Syntax(code, lexer_name, ..., word_wrap=True)` — unconditionally, for every fence, no matter the language — so a diagram wider than the console gets word-wrapped mid-line by Rich, splitting box-drawing characters across lines and corrupting the art. This surfaced as "resize breaks the diagram": `rewrap_output` (`llm/ui/default/output.py`) re-renders tracked markdown blocks from their original source at the new width whenever the terminal resizes, and a diagram that fit the old (wider) width often doesn't fit the new one. `convert_mermaid_to_art` now takes the caller's console `width` and, mirroring termaid's own CLI `--width` auto-fit exactly (`termaid/cli.py::_auto_fit`), progressively shrinks `gap` then `padding_x` until the diagram's widest line fits `width - 2` (the empirically measured cost of `Syntax`'s `padding=1`), falling back to the narrowest attempt if even that doesn't fit — the same residual case termaid's own CLI accepts (and warns about) rather than solves, since a box's minimum width is bounded by its label text.

**Consequences.** Assistant markdown containing a ```` ```mermaid ````/```` ```mmd ```` fence renders as a Unicode diagram wherever `render_markdown` is used, with zero behavior change for every other fence language because the regex only matches those two info strings. A bare `pip install zrb` renders Mermaid diagrams out of the box — no extra to remember. PlantUML fences are unaffected by this change and keep the same plain-fence fallback they already had.

**Alternatives rejected.** *Shell out to `mmdc` (Node/Chromium) or render to SVG/PNG* — needs a terminal graphics protocol that isn't reliably available across the terminals zrb runs in (confirmed with the user: "all possible terminals" is the real deployment target), and was already rejected in ADR-0079 for the same reason. *Extend `latex_math.py` to also handle mermaid fences* — the two features share no logic (no masking, no math-span heuristics, different fallback shape for a successful render), so combining them would only muddy one module's fallback story with another's. *Implement PlantUML alongside Mermaid* — no pure-Python, no-subprocess, no-network option exists; a local-Java or public-server path remains available as a future opt-in if it becomes a real pain point, but isn't implemented here.

**Where it lives.** `src/zrb/util/cli/mermaid_diagram.py`, `src/zrb/util/cli/markdown.py`, `src/zrb/config/mixins/llm_ui_styles.py` (`LLM_UI_ENABLE_MARKDOWN_MERMAID`).
