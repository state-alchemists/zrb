# ADR-0050 — The prompt states the risky runtime state, never its absence

**Status:** Accepted

**Context.** Priority Order rank 1 tells the model to confirm anything "irreversible, external, or destructive" before doing it. Nothing in the composed prompt said whether *irreversible* was even true.

`LLM_SANDBOX_ENABLED` defaults to `false`, and with it off both enforcement layers are inactive — the Python FS gate in `agent.gates` and the OS shell wrapper in `sandbox.os_sandbox`. Every `Write`, `Edit` and `Shell` call in the default configuration lands on the user's real disk. The model had no way to know that; `grep -n sandbox src/zrb/llm/prompt/*.py` returned nothing. A rule whose stakes are invisible is a rule that gets under-applied, and this is the one rule where under-applying it destroys the user's work.

opencode states it outright in `kimi.txt`: *"The operating environment is not in a sandbox. Any actions you do will immediately affect the user's system."* It is the one thing that file does which zrb's system context did not.

The design question is not *whether* to say it but **which state to announce**. The prompt already has a precedent with the opposite polarity: ADR-0038's parallel-tool-call line announces the rare *exception* (a deny-listed model) and has no affirmative branch, because an affirmative branch gated on a value that is never `True` is unreachable prose.

**Decision.** `system_context` emits a sandbox line **when the sandbox is off**, and emits nothing when it is on.

    - Sandbox: none — file writes and shell commands take effect on this machine directly and are not contained.

The affirmative branch is deliberately absent. A "you are sandboxed" line is a *licence to relax* rank 1, granted on the strength of a config the model cannot verify and whose enforcement it cannot observe. Silence leaves the unconditional rule in force, which is the safe way to be wrong: the cost of an unnecessary confirmation is one round-trip, the cost of a skipped one is the user's data.

The line reads `get_effective_sandbox_policy()`, not `CFG` directly, so a task constructed with `sandbox=True` or a runner-bound policy is honoured. It lives in `system_context` rather than `live_context` because the policy is bound once per run — putting it in the per-turn block would churn a fact that never changes and buy nothing.

**Consequences.** The default configuration spends ~20 tokens per request stating its own danger, on every preset. That is the correct trade for a line backing a rank-1 rule, and it is cheaper than the ADR-0038 line it sits beside (~50 tokens) which fires far less often.

Two lines in one section now branch on runtime state with opposite polarity — ADR-0038's on the *rare* case, this one on the *risky* case. That is not an inconsistency to normalise away: the polarity follows from what silence means in each case. Silence about parallel calls means "batch, as the rulebook says"; silence about the sandbox means "the unconditional rule stands". Both fail safe.

**Alternatives rejected.** *Announce both states* — the informative option, and the one that hands a ~3B model an explicit reason to skip confirmations it cannot check. *Announce only when sandboxed* — inverts the risk: the dangerous configuration is the default, so the silent branch would be the one that needs the words. *Put it in `live_context`* — the policy is session-invariant, so this would only cost cache stability. *Say nothing and rely on rank 1* — what the code did for eleven releases; rank 1 is unconditional but its stakes are not legible, and "confirm destructive actions" reads very differently to a model that believes it is in a container.

**Where it lives.** `src/zrb/llm/prompt/system_context.py` (`_format_sandbox_line`), `src/zrb/llm/sandbox/state.py` (`get_effective_sandbox_policy`), `src/zrb/config/mixins/llm_sandbox.py` (`LLM_SANDBOX_ENABLED`), `test/llm/prompt/test_system_context.py` (`test_system_context_states_that_tool_calls_reach_the_real_machine`, `test_system_context_claims_no_containment_when_sandboxed`), `AGENTS.md` (LLM Prompt System).
