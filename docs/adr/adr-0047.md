# ADR-0047 — Prompt profiles vary phrasing, never rules, and `mini` is selected from a declared size

**Status:** Accepted

**Context.** zrb is meant to run on both weak and strong models, but the
phrasing of each section was fixed — one `persona.md`, one `workflow.md`,
written in a dense, principle-led register well suited to a strong model and
lossy on a weak one.

A study of opencode's prompt set surfaced two findings. First, it selects a
whole hand-tuned monolith per model family by substring-matching the model id;
the cost is heavy duplication, with the same safety rules copy-pasted across
nearly every file — exactly the MECE violation composition avoids. Second, and
counter-intuitively, **weak does not mean fewer instructions**: the prompt for
the weaker family is the *longest and most repetitive*, full of few-shot
`<example>` blocks, while the strong-model prompt is shorter and leans on
judgment. The axis is register, not amount.

So the gap was that zrb could vary *which topics* appear but not *how each is
phrased for the model in use*, with no default that adapts.

Three later corrections shaped the final form:

*The "more directive" premise did not survive measurement.* The first variant
pair re-phrased `persona` imperatively and added worked examples. Measured, the
variant was **+638 tokens (+8.3%)** over the base, with **37 negative phrasings**
against 27, while **82% of its lines were byte-identical**. Meanwhile the
sections a weak model most plausibly trips on — the Priority Order's
precedence-not-sequence abstraction, the Working Loop's routing table, long
activation paragraphs — carried no variant at all. Three findings contradict
the premise: added constraints reduce task performance more for smaller models
(arXiv 2601.22047); prohibitions decay as context grows while affirmative steps
persist (arXiv 2604.20911), and the variant added ten more of the decaying
kind; and demonstrations are the lever the evidence actually supports. The
re-phrased `persona` variant had *already* drifted — it had lost a rule the base
file still had.

*The registry shipped empty, so nothing fired.* `auto` resolved to the base for
**every** model, and the worked examples reached zero sessions.

*The name argued for the banned behaviour.* Once re-phrasing was removed,
"explicit" described a register the profile no longer used, and invited exactly
the mistake the rule forbids.

**Decision.** A second axis over section composition, with three rules.

1. **A profile is a variant overlay, not a second prompt.**
   `get_prompt(name, profile="mini")` resolves `{name}.mini.md` through the full
   override chain and falls back to the base `{name}.md`. A profile only needs
   files for the sections that actually change; currently that is
   `examples.mini.md` alone.

2. **A variant may add demonstrations. It may not add, re-phrase, or restate
   rules.** `mini` is the base plus worked examples — never longer in rule text.
   Because a variant *replaces* its base file rather than appending,
   `examples.mini.md` must stay a strict superset of `examples.md`; a test pins
   that. The corollary is an invariant that has been violated twice in this
   codebase's history and is worth stating plainly: **a behavioural rule never
   lives only in a variant**, because a variant reaches only the models that
   resolve to it.

3. **Selection reads a declared size, never a family name.** `ZRB_LLM_PROFILE`
   takes `terse`, `mini` or `auto` (default). `auto` consults user declarations
   from `register_model_profile(pattern, profile)` first, then
   `DEFAULT_MODEL_PROFILES`, which matches two things and only two: a stated
   parameter count of 14B or less (`-7b`, `-8B`, `gemma-2-9b`; the regex accepts
   1–14, so `-32b`, `-70b`, `-405b` do not match), and a vendor's own small-tier
   label (`mini`, `nano`, `tiny`, `small`, `lite`, `haiku`). A **family** name is
   still never read as a capability signal — `deepseek`, `qwen`, `llama` span
   tiny to frontier, and an early draft that matched families misclassified a
   frontier DeepSeek model as weak. What changed is the recognition that a size
   token is the vendor stating its size, not a guess about it. `flash` is
   deliberately excluded: it is a *latency* tier that spans weak to strong.

The profile is named `mini` after the model class it serves, so "the `mini`
variant adds a rule" reads as obviously wrong in a way "the `explicit` variant
adds a rule" did not. There is **no alias** for the old value: the
preserve-the-old-key rule (ADR-0026) covers released env *keys*, where a stale
config silently loses a setting, whereas this is a knob *value* whose two
consumers both fail loudly — an unrecognized `ZRB_LLM_PROFILE` falls through to
`auto`, and `register_model_profile(..., "explicit")` raises `ValueError`.

A narrow escape hatch remains for cross-cutting voice that genuinely does not
decompose into a variant — response channels, a vendor formatting dialect —
which stays expressible as a whole alternate section or preset.

**Consequences.** Small models receive worked demonstrations with no
configuration, and the risk is asymmetric in the safe direction: a false
positive costs example tokens, while a false negative costs a weak model the
one adaptation that helps it. Any entry is reversible in one line and a user
declaration always beats a built-in. Variant drift is bounded to one file that
carries no rules, so a rule updated in the base cannot go stale in a variant.
The axis is deliberately thin — whether it still earns a separate axis versus an
examples-only knob is left open.

`examples` is also thin *in the base*, on purpose: the base keeps only the few
examples that fix a zrb-specific stance, and the rest live in the variant.
Adding a demonstration means adding it to the variant unless it teaches a
stance a frontier model gets wrong — and if it teaches a *rule*, it belongs in
neither file.

**Alternatives rejected.** *Per-model monolith selection, opencode's model* —
simple to reason about per model, but duplicates shared rules across files and
abandons composition; retained only as the narrow escape hatch. *Weak = drop
sections* — the intuitive read, contradicted by the evidence. *A full
per-vendor variant matrix* — maximal fidelity and a maintenance bomb. *Keep the
re-phrased `persona` variant but shorten it* — still spends tokens on a
mechanism the evidence does not support. *Build the missing `workflow` variant*
— the register-sensitive behaviours all live there, so it looked like the
obvious gap; rejected because it adds rule text to the models least able to
carry it. The gap is better closed by converting prohibitions to affirmative
form **in the base**, which helps every model. *Leave `auto` inert* — honest,
but the mechanism never fires. *Match on a curated model list* — accurate, and
stale the week it ships; a size token stays true. *Retire profiles entirely* —
premature; the examples axis is doing real work. *Ship an alias for the old
profile name* — no silent-loss failure to prevent, and it keeps a discarded name
discoverable in docs and autocomplete. *Name it `weak` or `small`* — reads as a
judgement; vendors already ship the word `mini`.

**Where it lives.** `src/zrb/llm/prompt/profile.py` (`MINI_PROFILE`,
`DEFAULT_MODEL_PROFILES`, `resolve_profile`, `register_model_profile`),
`src/zrb/llm/prompt/prompt.py` (variant-aware loading),
`src/zrb/llm/prompt/manager.py` (profile threading),
`src/zrb/config/mixins/llm_prompt.py` (`LLM_PROFILE`),
`src/zrb/llm/prompt/markdown/examples.md` and `examples.mini.md`.
