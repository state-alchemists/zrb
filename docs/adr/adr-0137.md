# ADR-0137 — A background command that ends wakes the session that started it

- **Status:** Accepted
- **Date:** November 1, 2026

## Context

A `Shell(background=True)` command, or one that outran its `Shell` timeout, is held by `_ShellBackgroundRegistry` and named in every turn's live context: `exited, code 0` once it has ended (`llm/prompt/live_context.py`). That is a standing fact for the *next* turn. Nothing makes a next turn happen. On 2026-11-01 a CI watcher ended with code 0 eighteen minutes after the turn that started it, and the result sat there until the user asked, because an idle session runs no turn of its own.

The registry is the only holder of the ending, and the moment the process ends is the only moment a push is free. The UI already has the mechanism that turns a push into a turn (ADR-0078, ADR-0108): every submission lands in the UI's `MessageQueue`, a running turn reads it at its next model request, and an idle session runs it as the next turn. A finished background delegation already reports to its parent this way (`parent_ui.submit_message(text, None)`).

## Decision

The registry notifies the UI that started the process, through the queue every other submission uses.

- **Who is told:** `_BackgroundProcess.ui` is `get_current_ui()` at `start`/`adopt` — the UI of the run that started the command, which is the one thing the registry can reach the waiting session through. It is called through `AnyUI.submit_message`, which a UI that keeps no queue (a headless run, `StdUI`) leaves as a no-op: a headless run has no idle session to wake, and a sender that is not the user never assumes the message arrived.
- **What is sent:** `[Background process <handle> finished (exit N): <description>. MonitorProcess(handle='<handle>') reads its output.]` — the handle and the exit code, never the output, which can hold a token and is the model's to read with `MonitorProcess`. The description is named only when the caller wrote one: without it the description is the command line, which can carry a credential, and this lands in the transcript. Its source is `BACKGROUND_INPUT` (`"background process"`), so the model is not told the user typed it.
- **When it is sent:** once, when the exit is heard (`_wait_exit`), or when an adopted process reaches its time limit (`_stop_adopted`) — nobody asked for that stop. It is **not** sent when the model, the user or a shutdown asked for the stop (`stop_requested`), when the handle was already consumed by a poll, or while a `MonitorProcess(wait=...)` is blocked on the process (`waiters`), because that call returns the ending itself.
- **It is taken back when it becomes moot.** The registry keeps the message it queued, and consuming the handle (`poll` releasing a finished process) calls `AnyUI.withdraw_message`: the model has read the ending, so a wake-up still waiting would start a turn about a handle that no longer exists. A wake-up already delivered is beyond recall and is left alone. The match is on the text and the source's channel, not the whole source, because a queued entry's source also carries how long the chat was quiet when it arrived.
- **It does not take the user's rights.** The submit funnel treats it differently in two ways. It never calls `_hush_speech`: a command ending is not the user moving on, so it does not cut a reply being read aloud. And the number of wake-ups in a row with no message from the user is bounded by `LLM_BACKGROUND_WAKE_MAX_CONSECUTIVE` (default 5, `0` for no limit): a turn a wake-up starts can start another command, which wakes it again. The count is on the `MessageQueue` and is reset by any submission from a source that is the user's; a message with no source (a sub-agent's) neither resets nor spends it. A wake-up past the limit prints one line and is dropped — the command is still listed as exited in the next turn's live context, so nothing is lost, only the nudge.
- **It can be turned off:** `LLM_BACKGROUND_WAKE` (default on). Off leaves today's behaviour: the exit shows up in the next turn's live context.

## Consequences

A result that arrives while nobody is typing is read when it arrives. The state lives in one place, the registry, and there is one new path: exit event, then UI queue, then a turn. The wake-up is visible in the transcript like any queued message, so the user sees why an unprompted turn started.

Costs and limits, all deliberate:

- **An idle session spends a model turn by itself.** That is the point, and the reason for the consecutive limit and the off switch.
- **It does not survive a restart.** If zrb exits, the registry and its processes go with it (`cancel_all`), and the wake-up goes with them. A command that outlives zrb would need a supervisor that owns background processes, which is a design of its own and not a side effect of this one.
- **Two commands that end together wake the session twice**, as two queued messages. They are not merged.
- **A command started inside a sub-agent is not announced.** A sub-agent's `BufferedUI` keeps no queue, so it takes the `AnyUI` default and the message is left alone; the command is still listed in that run's live context.
- **A background delegation** is not covered by this record; it already reports to its parent through `live_session.py`.
- **A command that daemonizes itself** is reported when its direct process ends, as `MonitorProcess` reports it.

## Alternatives rejected

- **A durable ledger of watches, written before the work starts and read back by the next turn.** It answers a different question — surviving a restart — and to do it the ledger had to *infer* an ending: from a recorded pid, then from an exit file written by a shell wrapper around the command. Each inference had a window (a recycled pid, a crash between spawn and the record, an ending that could not be written), and the incident it was written for was never a storage problem: the live context already reported the exit.
- **A `Stop` hook.** It fires at the turn boundary, which is the one moment the answer cannot exist.
- **Polling the registry on a timer from the UI.** The registry already knows the instant the process ends; a poll adds a delay and a second place that decides when a result is ready.
- **Putting the output in the message.** A tail can carry a credential, and a long one would spend the turn's context on something the model may not need.
