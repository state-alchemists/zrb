# ADR-0095 — On Windows, a real POSIX shell is preferred, and shells are compared by name

**Status:** Accepted

**Context.** `CFG.SHELL` decides what `CmdTask` and the `Shell` tool run commands under. On Windows it used to resolve to `pwsh`, `powershell` or `cmd`. Almost every command zrb itself ships — its builtin tasks, its scaffolded templates, the scripts the LLM agent writes — is POSIX shell syntax, so that choice made the default experience on Windows one of syntax errors.

Git for Windows ships a genuine `bash`, it is present on GitHub's `windows-latest` runner, and it is a near-universal developer install. Preferring it makes the Windows default match the POSIX branch instead of assuming Windows means no POSIX shell.

Finding it is not `shutil.which("bash")`. Windows ships `System32\bash.exe` — the WSL *launcher* — and it wins the PATH lookup on a stock install. It is not a shell: with no distro installed it prints "Windows Subsystem for Linux has no installed distributions" as UTF-16 and exits 1, so every command fails while appearing to produce output; with a distro installed it runs inside the WSL filesystem namespace, where the caller's `D:\…` working directory does not exist.

Preferring it also changes the *shape* of the setting. `CFG.SHELL` becomes an absolute path with an `.exe` suffix rather than a bare word, and the codebase compared shells as bare words: `shell.endswith("bash")` gated the POSIX-command lint, and a `{"pwsh": "-Command", "cmd": "/c"}` table keyed on the raw string picked the interpreter's flag. Both answer wrongly for `C:\Program Files\Git\bin\bash.exe`, so the lint silently stopped running on the one platform whose default shell is now Git Bash, and a configured `…\pwsh.exe` would have been handed the POSIX `-c`.

**Decision.**

**1. On Windows, `get_current_shell()` returns a real POSIX shell when one exists**, falling back to `pwsh` → `powershell` → `cmd`. The lookup is `get_windows_posix_shell()`: Git's own prefix first (located from `git` on PATH, so it follows whatever root the user installed into), then the standard install roots, then PATH — and a PATH hit under the Windows directory is rejected as the WSL launcher. It returns `""` off Windows.

**2. That lookup is memoized.** `EnvField` re-runs `default_factory` on every `CFG.SHELL` read (ADR-0023) and `resolve_shell` asks again for a bare `bash`/`sh`, so an uncached lookup means a PATH scan plus four filesystem probes per command executed. The answer cannot change within a run.

**3. Every comparison against a shell setting goes through `get_shell_name()`**, which reduces `bash`, `/bin/bash` and `C:\Program Files\Git\bin\bash.exe` alike to `bash`. It splits on both separators regardless of the running platform, so the answer does not depend on who is asking — which is what lets a POSIX test suite cover the Windows shapes.

**4. `resolve_shell` substitutes a path only for a bare `bash`/`sh`.** An already-absolute setting is passed through untouched; only a bare name is ambiguous enough to need resolving.

**Consequences.** zrb's own POSIX-syntax commands run on a stock Windows developer machine, and the same `CmdTask` definition behaves the same on all three platforms. The unrecommended-command lint and the interpreter-flag table work for absolute settings, so a user pointing `ZRB_SHELL` at a full path gets the right flag instead of `-c`.

The cost is that `CFG.SHELL` is no longer guaranteed to be a bare word — anything reading it must go through `get_shell_name()` to compare, which is why that helper exists rather than each site trimming for itself. A Windows user who wants PowerShell sets `ZRB_SHELL` explicitly; the detection only chooses a default.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Keep PowerShell/cmd as the Windows default | zrb's own tasks, templates and agent-written scripts are POSIX syntax, so the default was broken for the majority of what zrb runs. |
| `shutil.which("bash")` | Finds `System32\bash.exe`, the WSL launcher — commands fail while looking like they produced output, or run in a filesystem namespace where the working directory does not exist. |
| Return the bare name `"bash"` and let PATH resolve it later | Same launcher problem, moved to execution time where the failure is harder to attribute. |
| Translate POSIX commands to PowerShell | An unbounded translation problem, and it would silently change the meaning of commands users wrote themselves. |
| Leave the `endswith`/raw-string comparisons alone | They answer wrongly for the default this ADR introduces: the POSIX lint stops running, and an absolute PowerShell path gets `-c`. |

**Where it lives.** `src/zrb/config/helper.py` (`get_windows_posix_shell`, `get_shell_name`, `get_current_shell`), `src/zrb/util/cmd/command.py` (`resolve_shell`), `src/zrb/task/cmd_task.py`, `test/config/test_config_platform_detection.py`. See ADR-0023 for `default_factory` resolution.
