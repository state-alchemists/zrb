# ADR-0101 — Parallel tool calls are the default; System Context announces only the exception

**Status:** Accepted (amends ADR-0100)

**Context.** ADR-0100 moved the model-aware parallel-tool-call block out of
`tool_guidance` and into `system_context` as a tri-state line, and phrased the
`workflow` rule to match:

> **Batch independent calls** into one response where System Context says the
> model supports it.

The line renders from `model_capabilities.get(model).supports_parallel_tool_calls`.
That field is resolved by `_resolve_parallel_tool_calls`, which is a **deny-list**:
it returns `False` for the two models known to malform parallel calls
(`minimax-m2.7`, `glm-4.7`) and `None` for everything else. No built-in pattern
returns `True`.

So the affirmative branch of `_format_parallel_tool_call_line` was unreachable,
and the `workflow` rule was gated on a precondition that could never be
satisfied — for `gpt-4o-mini`, `gemini-2.5-flash`, `claude-*`, `deepseek`, every
model zrb ships against. Users could reach it only by calling
`model_capabilities.register(..., supports_parallel_tool_calls=True)` from
`zrb_init.py`, which nobody has reason to do for a mainstream model.

A benchmark run measured the cost. Wall clock on a 44-site migration tracks
**round-trips**, not tool calls:

| model | responses | calls | avg batch | duration |
|---|---|---|---|---|
| deepseek-v4-flash | 10 | 101 | 10.10 | 142s |
| gemini-2.5-flash | 17 | 91 | 5.35 | 71s |
| gpt-4o-mini | 17 | 125 | 7.35 | 168s |
| gpt-4o-mini | 71 | 186 | 2.62 | 434s |
| gpt-4o-mini | — | 236 | — | **timeout at 600s** |

Same model, same task, 2.6× wall clock apart — and one trial lost outright. The
models batch when they happen to; nothing was asking them to.

**Decision.** Invert the gate.

- `workflow`'s Tool usage rule states batching as the unconditional default,
  names what to sequence (a write and the read that must see it), and ends with
  "Unless System Context says this model cannot batch."
- `_format_parallel_tool_call_line` keeps only the negative branch. When
  `supports_parallel_tool_calls` is `False` it emits a line that explicitly
  overrides the prompt default; for `True` and `None` alike it emits nothing.
  There is no affirmative branch to fall out of sync again.
- `read_file`'s docstring carries the same instruction at the point of use, plus
  the corollary the benchmark also surfaced: prefer one wide range over repeated
  narrow slices of the same file.

The deny-list is what zrb actually knows. Encoding the default in the prompt and
the exception in the capability registry matches that, where the previous shape
required an allow-list nobody was maintaining.

**Consequences.**

- Every model now reads an unconditional instruction to batch. Models that
  cannot are still corrected, both in the prompt and at the provider request
  level (`parallel_tool_calls=False`), which was already the reliable mechanism.
- `ModelCapabilities.supports_parallel_tool_calls` stays tri-state. `True` is now
  meaningful only as a user override that says "ignore any future deny-list
  entry for this model"; it no longer drives any rendering.
- A regression test asserts no model is told batching is *supported*, so the
  unreachable branch cannot come back.

**Alternatives considered.**

- *Populate an allow-list.* Add `gpt-4`, `gemini-`, `claude-`, … to a
  `_PARALLEL_TOOL_CALLS` tuple. Rejected: it is a per-model table to maintain
  forever, it is wrong by default for every model not yet in it (the exact
  failure being fixed), and the safe answer for an unknown model is "batch" —
  malformed parallel calls are a rare, identifiable defect, not the norm.
- *Leave the prompt conditional and fix only the registry.* Same maintenance
  burden, and it keeps a rule whose precondition most readers cannot verify.
- *Say nothing in the prompt and rely on tool docstrings.* Batching is
  cross-tool turn policy, which `workflow` owns per ADR-0098; the docstring line
  reinforces it where a read is being planned but should not be the only
  statement of it.

**Evidence.** `experiment/` in `llm-challenges`, run of 2026-08-05: 156 cells
across 5 models. `google:gemini-3.5-flash` averaged 1.04 calls per response
across 583 responses; `deepseek:deepseek-v4-flash` averaged 2.29. Neither had
any parallel-tool-call line in its system prompt, because none renders.
