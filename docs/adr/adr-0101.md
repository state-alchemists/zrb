# ADR-0101 — Rewind snapshots are commits in a private git directory whose work tree is the project

**Status:** Accepted

**Context.** `/rewind` restores the working directory and the conversation to the point before an earlier turn. Its snapshots used to be a *shadow copy*: before every turn the manager copied the working directory, file by file, into `<LLM_SNAPSHOT_DIR>/<session>/` and ran `git add -A && git commit` there; restore ran `git reset --hard` in the copy and copied it back, deleting what the snapshot lacked. So every file was read twice, written twice and stored twice — once as a plain copy, once as a git object. On this repository (106 MB, 1,420 files) the first snapshot took 1.2 s and 85 MB, and the TUI awaited it before it drew. After a few weeks `~/.zrb/llm-snapshots` held 994 MB for 11 sessions, up to 302 MB each, because each session had its own copy of the whole project and nothing was ever shared. The copy honoured no `.gitignore`: only a hardcoded list of cache directories kept `node_modules` and `.venv` out.

The self-review gate (ADR-0100) had meanwhile shown the cheaper shape: git can hash a work tree it does not own, given a separate git directory and index.

**Decision.**

- **No copy.** A snapshot is `git add -A` into a private index, `write-tree`, `commit-tree`, `update-ref`, run with `--git-dir` pointing at a private bare repository and `--work-tree` at the project. Restore is `git add -A` (so files created since the snapshot are in the index), `read-tree -u --reset <sha>` — which rewrites changed files, recreates deleted ones and removes the rest — and moving the session's ref back to `<sha>`, so later snapshots drop out of the list as they did before.
- **One git directory per project, one ref and one index per session.** The store is `<LLM_SNAPSHOT_DIR>/<work-tree name>-<hash of its real path>.git`; a session's history is `refs/zrb/<session>-<hash>` and its index `index-<session>-<hash>`, the hash taken over the session name and the workdir's path inside the work tree — so a conversation resumed from another directory of the repository gets its own history, since restoring a snapshot taken in one directory would delete files the other never snapshotted. The hashes matter because sanitizing alone collides: `/tmp/a:b` and `/tmp/a?b` both become `a_b`, and would share a store and restore each other's files. Unchanged files are stored once across every session of a project, and two concurrent sessions never contend for one index lock.
- **Git's ignore rules apply.** A gitignored file is neither snapshotted nor touched by a restore. `git add -A` never untracks a path already in an index, so a file that becomes ignored after a snapshot captured it would otherwise stay in every later one: each snapshot drops now-ignored paths from its private index (`ls-files --cached --ignored` into `update-index --force-remove`), and a restore filters them out of the target tree first, so an old snapshot never overwrites a file ignored since. The self-review snapshots do the same, since their index persists between a turn's two snapshots. When the workdir is inside a repository, the work tree is the repository root and every command is limited to the workdir by pathspec, so `.gitignore` files above the workdir apply and nothing outside it is restored. `SnapshotManager.DEFAULT_IGNORE_DIRS` is written to the store's `info/exclude`, so cache directories stay out of a workdir outside git too. So is the store itself, as an anchored, glob-escaped pattern, when `LLM_SNAPSHOT_DIR` lies inside the work tree: otherwise a snapshot would capture the store's own objects, index and lock files, and a restore would rewrite the store mid-restore and lose its history. The exclusion is written before the first `git add`, and restore's ignored-path filter keeps it off snapshots taken before it existed. The snapshot dir is resolved to an absolute path, since git runs with the work tree as its cwd.
- **The store holds its own objects.** Unlike the self-review store, it does not read the project's object database as an alternate: rewind history outlives the session, and a `git gc` in the project after a branch is deleted could prune a blob an old snapshot relies on.
- **A file git cannot index does not fail the snapshot.** `git add --ignore-errors` leaves out an unreadable file or a nested repository with no commit, adds the rest, and the count is reported. The same flag applies to the self-review snapshots, which also keep their index between the turn's two snapshots rather than re-hashing the tree.
- **Rewind is on by default inside a git repository.** `LLM_ENABLE_REWIND` defaults to `auto`, which resolves to on when the working directory is in a repository and off otherwise. Inside one, `.gitignore` bounds a snapshot and the cost above is paid once per project; outside one only `DEFAULT_IGNORE_DIRS` does, and a chat started in `~` would hash — and store — the whole home directory, SSH keys included. An explicit `on` still enables it anywhere.
- **Restores are byte-exact.** The store's `info/attributes`, which outranks the project's `.gitattributes`, sets `* -text -filter -ident -working-tree-encoding`: no line-ending or encoding conversion, and no clean/smudge filter — a git-lfs smudge against this store would otherwise write pointer files into the user's work tree. Git output is decoded as UTF-8 with `surrogateescape`, so a non-UTF-8 file name survives `ls-files -z` and `update-index --stdin` intact instead of failing the snapshot, and a global `core.fsmonitor` is overridden so no watcher daemon starts per store.
- **A cancelled snapshot or restore holds the lock until its git work stops.** Cancelling cannot stop the worker thread. Releasing the lock while it still ran would let the next snapshot or restore race it on the same index, and a cancelled snapshot's late `update-ref` could move the session's history forward again after a rewind. So a cancellation tells the thread to stop before its next git command, and awaits it, before it propagates.
- **The first snapshot runs in the background.** The TUI starts it as a background task instead of awaiting it before drawing; the manager's lock makes the first turn's snapshot wait for it. Teardown cancels and awaits it with the UI's other background tasks, so it never reports progress to a UI that is gone; a git command already running in its worker thread still finishes, within the git timeout.

**Consequences.** Measured on this repository, the first snapshot drops from 1.2 s to 0.4 s and from 85 MB to 14 MB, a per-turn snapshot from 0.04 s to 0.01 s, and further sessions of the same project add only the objects that changed. About 150 lines of copy, sync and delete code are gone. Two behaviours change. Edits to gitignored files — a `.env`, a build directory — are no longer rewound; that is the same boundary the project's own git draws, and the reason the snapshot is cheap. A nested repository with commits is recorded as a gitlink, so rewind no longer restores its contents. Shadow copies written before this change are not migrated; they can be deleted from `LLM_SNAPSHOT_DIR`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Keep the shadow copy, make it incremental | It already skipped unchanged files by mtime; the cost that remains is the second copy of every file on disk and the walk in Python, which git's stat cache does better. |
| Snapshot into the project's own `.git` | Writes untracked files' contents — secrets included — into the project's object database (see ADR-0100), and mixes zrb's refs into the user's repository. |
| Read the project's objects as an alternate | 0.07 s instead of 0.4 s for the first snapshot, but a long-lived snapshot could lose objects to a `git gc` in the project. |
| Force-add gitignored files (`add -f` with exclusion pathspecs) | Rewinds `.env` edits, but snapshots every build output and dependency directory the project ignores, which is exactly the cost this removes. |
| Track only the files the file tools touched (Claude Code's approach) | Misses changes made through `Shell`, which is how most generated and moved files change. |
| On by default everywhere | Outside a repository nothing bounds a snapshot; see the default above. |
| Stay off by default | The reason it was off — a copy of the project per session, taken before the TUI drew — is gone, and an undo that has to be enabled beforehand is rarely there when it is needed. |
| One git directory per session | Stores every file again per session; that duplication is what filled 994 MB. |

**Where it lives.** `src/zrb/llm/snapshot/manager.py`, `src/zrb/config/mixins/llm_content.py` (the `auto` default), `src/zrb/llm/ui/default/lifecycle.py` (background init, progress lines), `src/zrb/util/git/worktree.py` (the self-review snapshots). Tests: `test/llm/snapshot/` (`test_manager_store.py` for the store layout), `test/util/git/test_worktree.py`, `test/llm/ui/default/test_lifecycle.py`.
