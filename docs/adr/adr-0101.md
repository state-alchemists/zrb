# ADR-0101 — Working-directory snapshots are git trees in a private store, listed repository by repository

**Status:** Accepted

**Context.** Two features snapshot the working directory. `/rewind` restores the directory and the conversation to the point before an earlier turn, so it needs a snapshot per turn it can write back exactly. The self-review gate (ADR-0100) diffs the directory at Stop against its state at turn start, so it needs two snapshots per turn it can diff exactly. Both run before a turn does any work, so a snapshot must cost little after the first. Both hash untracked files — a `.env`, a private key — so their copies must never land in a project's `.git` or be readable by other users. And both must hold for every layout a chat starts in: a repository, a subdirectory of one, a repository holding nested clones or submodules, a directory holding several repositories, and a directory with no git at all, `~` included.

Git gives most of this: it can hash a work tree it does not own into a separate git directory and index, keep a stat cache so unchanged files are not hashed again, and apply a repository's ignore rules. What it does not give is a walk into nested repositories — its directory walk stops at any directory holding a `.git` and records a gitlink, so `git add -A` never sees inside one — and any bound on a directory no `.gitignore` covers.

**Decision.**

- **A snapshot is a tree in a private bare repository whose work tree is the working directory itself** (`SnapshotStore`, `util/git/snapshot_store.py`). Nothing is copied, and nothing is written into the directory or into any repository under it.
- **Zrb lists the files; git hashes them.** `util/git/snapshot_listing.py` builds the list repository by repository. A directory inside a repository is listed by that repository — `git ls-files --cached --others --exclude-standard` — so its `.gitignore` files, above the directory too, its `info/exclude` and the user's global excludes apply. Each nested repository is listed the same way, by itself, recursively: one the listing reports — an untracked one as `dir/`, a submodule as a gitlink — and one inside a directory the repository ignores, which is searched for repositories (`git ls-files --others --ignored --directory` names those directories) and nothing else. A directory outside every repository is walked — taking, like git, only regular files and symlinks (a FIFO, socket or device cannot be stored) and following neither a symlink nor a Windows junction, which may point anywhere — and a repository found there is listed by itself; so is a working directory its own repository ignores — a scratch folder — since it is still what the user works on, and listing it through the repository would leave it empty. The list goes to `git update-index --add --remove --stdin` in the store's own index, which keeps git's stat cache, and `write-tree` makes the snapshot. An index entry the listing no longer returns — deleted, or ignored since — is dropped first, so a snapshot holds exactly what was listed. `DEFAULT_IGNORE_DIRS` (`node_modules`, `.venv`, caches) and the store itself are left out everywhere, tracked files included, and never searched for repositories.
- **A snapshot records what exists but it does not hold.** A restore must tell a file that did not exist when the snapshot was taken from one the snapshot never saw, and only the snapshot can know which is which. So the listing records, beside the files it takes, what it leaves out: every path a repository ignores — whichever rules did it, a `.gitignore`, `info/exclude` or the user's global excludes — as `git ls-files --others --ignored --directory` reports it, the search for repositories above running it anyway; every directory that cannot be read, which git skips with only a message, found by a walk of the directories alone; and an uninitialized submodule's directory, which git lists nothing in. A snapshot is its tree plus that record: the files git could not read, the paths left out, and the repositories listed.
- **Outside every repository a budget bounds the listing.** No ignore rule applies there — a `.gitignore` outside a repository means nothing to git either — so those loose files count toward `LLM_SNAPSHOT_LOOSE_MAX_FILES` (5,000) and `LLM_SNAPSHOT_LOOSE_MAX_MB` (200). Past either, the listing stops with `SnapshotBudgetError`. Files inside repositories do not count: their ignore rules bound them. Rewind turns itself off for the session and says why — on its first snapshot and on `/rewind` — without walking the directory again; the self-review gate warns once and reviews from the file tools' paths. Within the budget, a working directory outside every repository is told once, with its first snapshot, that its rewind reaches less far than a repository's would: no rule applies there, so nothing is left out on purpose and a `.gitignore` it holds has nothing to say.
- **Rewind is on by default, everywhere.** The budget, not the presence of a repository, is what keeps a chat started in `~` from hashing the home directory, so a directory of repositories — which is not a repository itself — gets rewind too.
- **Restore rewrites the working directory to a snapshot, never destroying what no snapshot holds.** It re-snapshots first, so the index holds the directory as it is now, then decides each path by its state now:

  | Path now | The snapshot has it | The snapshot lacks it |
  | --- | --- | --- |
  | listed and readable | rewritten to the snapshot's version | removed only when the snapshot shows it did not exist then — it is in neither the tree nor the record, and its repository is one the snapshot listed |
  | unreadable, or under a directory that cannot be read | left alone: its content is in no snapshot | left alone |
  | ignored or excluded | left alone | left alone |
  | absent | recreated | — |

  - *Scope now* is judged by the repository owning each path: `git check-ignore`, which, like the listing, never counts a tracked file as ignored (a force-added file, `.env.example` under `.env*`), plus `DEFAULT_IGNORE_DIRS` and the excluded paths.
  - *Did not exist then* is read from the snapshot's record, never reconstructed: the present is judged by looking, the past only by what the snapshot wrote down. A file the record names — unreadable then, or ignored then, alone or under an ignored directory — or one under a directory the snapshot could not read, is kept. A left-out directory covers what its own repository would have listed there, not a repository inside it, which listed itself: a file created in a worktree under an ignored `.zrb/worktree/` is still removed. Left-out paths are matched ignoring case and repositories exactly, both erring toward keeping. One `read-tree -u --reset` then writes the result.
  - *A repository made since* — one the snapshot did not list, a worktree or clone — keeps every file the snapshot lacks: removing them would leave it hollow, and its own history holds its work. A file the snapshot holds there is restored like any other. A repository that existed then, even empty, was listed, so what was created in it since is removed.
  - *Letter case*: on a filesystem that ignores it (macOS, Windows), a current path the snapshot holds in another case is the same file. It gets the snapshot's version and is never removed as created since, which would delete it.
  - *A refused write* — a file another program holds open, a directory without write permission — does not stop the rest: git writes every file it can. The restore then compares the directory with what it meant to write, and `RestoreOutcome.left_behind` names each path left behind. The chat rewinds with the files, `/rewind` lists what was left behind, and running the same `/rewind` again finishes once the cause is gone.
  - *A failure* — a git command past its cap, say — before the write raises, with nothing changed, and `/rewind` reports it failed. One during the write leaves the directory partly rewound, so the restore does not raise: it reports every path it meant to change as left behind, and the chat rewinds. A ref that cannot be moved back afterwards is logged; the files are restored either way.
  - *Something unlisted in the way* — a directory holding an ignored file where the snapshot has a file, a FIFO where it has a file or needs a directory — is never written over, though `read-tree -u --reset` would remove it: that path is left behind and reported. So is a snapshot path a kept file stands in the way of. A listed file or a directory of listed files in the way is the restore's own to replace.
  - Restore puts back files, nested repositories' files included; it does not move any repository's `HEAD` or branches, nor a submodule's pointer in its parent — those are history, like any commit, not the working tree.
- **Rewind keeps one store per working directory and one ref per conversation.** The store is `<LLM_SNAPSHOT_DIR>/<directory name>-<hash of its real path>.git`, with one stat cache every conversation there shares — any state of it is a valid start (below) — and a conversation's history is `refs/zrb/<name>-<hash>`. The hashes matter because sanitizing alone collides: `/tmp/a:b` and `/tmp/a?b` both become `a_b`, and would share a store and restore each other's files. The key is the conversation's name — the identity its chat history is saved and resumed under, random unless the user names it — since each snapshot records that conversation's message count, and a resumed conversation must find its snapshots again. Unchanged files are stored once across every conversation in a directory. The manager follows the conversation the UI is on: the UI builds it with a callable returning the conversation's current name, read at the start of each operation, so after `/load` snapshots and `/rewind` use the loaded conversation's history, and `/save` copies the current history to the new name as it copies the chat history — recorded at once, in memory and in a file beside the store, and applied at once under the manager's lock, so a snapshot right after `/save` builds on the copied history and a copy of a copy takes the original's — a saved copy with no snapshots leaves the new name with none, since old ones would carry message counts of a chat history that is gone. A copy the store could not take — busy, or the session ended first — stays recorded in that file, so it is no less durable than the chat history saved beside it: the next operation of this or any later manager applies it before doing anything of its own, and until it lands `list_snapshots` shows the saved name the history it is about to receive. Two processes running the same conversation at once share its rewind history as they share its chat history; neither is supported. Restore accepts only a commit in the conversation's own history, then moves its ref back to it, so later snapshots drop out of the list: another conversation's commit is not in this one's list, so restoring it would rewind the files without rewinding the conversation to match.
- **A rewind commit carries its snapshot's record where its label cannot reach.** The subject is the label, joined onto one line, followed by ` [mc:<message count>]`, read from the end of the subject; the record follows in the body as `zrb-snapshot: {"unreadable": …, "left_out": …, "repositories": …}`, read from the body alone. A label is the user's text, so none can pass for either. A commit without a readable record is not restored, since without it a file that did not exist then cannot be told from one it never saw. A snapshot matching the latest commit's tree still gets a commit of its own when its record differs — a file ignored since — or a rewind to that point could remove that file.
- **Rewind's store keeps its own objects; a review store borrows them.** Rewind history outlives the session, and a `git gc` in a repository could prune a blob an old snapshot relies on, so the persistent store copies every file once. A per-turn review store lives for one turn, so it reads the object database of every repository it lists as an alternate and writes only untracked files' contents.
- **Stores are owner-only and never snapshot themselves.** A store's top directory is `0700` whatever the umask, applied on every open, since it holds copies of untracked files; on Windows, where access comes from the folder's ACL instead, the default locations — `%TEMP%` and the user profile — are already private to the user. A store inside the working directory — an `LLM_SNAPSHOT_DIR` there, say — is excluded from its own listing, so a restore never rewrites the store mid-restore; an `LLM_SNAPSHOT_DIR` that is the working directory itself turns rewind off with that reason, since other directories' stores would land in it, and a store whose own directory holds its work tree is refused outright — deleting it would delete the work tree. Any failure to set the store up — that refusal, a snapshot directory that cannot be written, git not installed — will not pass by itself, so it too turns rewind off for the session with its reason, rather than failing again on every turn.
- **Snapshots are byte-exact.** The store's `info/attributes`, which outranks a project's `.gitattributes`, sets `* -text -filter -ident -working-tree-encoding`: no line-ending or encoding conversion, and no clean/smudge filter — a git-lfs smudge against the store would otherwise write pointer files into the user's work tree. Git output is decoded as UTF-8 with `surrogateescape`, so a non-UTF-8 file name survives the listing and `update-index --stdin` intact, and a global `core.fsmonitor` is overridden so no watcher daemon starts per store. Files the store writes, `alternates` included, use LF on every platform.
- **A file git cannot read does not fail the snapshot.** `update-index` stops at the first file it cannot read. Its message naming the file is not relied on — its wording differs between git versions and is translated into the user's language — so when a run fails, the unreadable files are found by opening each one — never a FIFO, socket or device, which count as unreadable unopened, since opening a FIFO blocks; they are left out — its entry dropped too, should the cached index hold an earlier version, so a snapshot never holds stale content for it — the rest are fed again — the rerun re-stats rather than re-hashes them — and the snapshot names the files it left out. Its record holds them (above), so a restore never removes them for being absent from it; the self-review gate lists them rather than showing them as deleted.
- **A rewind store's operations take turns, across processes too.** Two sessions in one directory — in one process, as the web UI runs them, or in two — share a store. Their snapshots are safe together (below), but two restores would interleave their writes, and a snapshot taken mid-restore would hold a half-written directory. So every snapshot and restore on a rewind store, and setting the store up — two processes running `git init` on it at once fail on each other's config lock — holds an OS lock on `zrb-operation.lock` in it (`util/file_lock.py`: `flock` on POSIX, `msvcrt.locking` on Windows), which the OS releases when its holder exits or is killed. The wait is bounded: a store still busy after `LLM_SNAPSHOT_LOCK_TIMEOUT` (60 s) — another process stuck mid-restore — fails that one operation, not the session's rewind. The wait comes before the operation's own budget (below), not out of it — a store another process holds is contention, and a budget spent on it would turn rewind off as if the directory were too slow to snapshot — and it stops at once when the operation's caller is cancelled, since a lock taken afterwards would guard work whose result has no reader. Listing snapshots takes no lock: it reads the ref once and the commits it names, which never change, and a lock would hold the UI up behind another operation. A review store is private to its turn and takes none.
- **Every operation works on an index of its own.** A snapshot, restore or graft copies the store's named index — a stat cache, so unchanged files are not hashed again — to a file named for that one operation, keeping its timestamp (git re-hashes an entry as new as the index file, which is what catches a file rewritten within the same second at the same size), works on the copy, and replaces the named index with it when done. A git command killed at its timeout cannot remove the lock it took, and a lock left behind would fail every later command on its index — for rewind, across restarts. The lock is on the operation's own copy, so deleting the copy and its lock can never take another process's lock: `update-index` keeps working while another process holds its index's lock and fails only when it writes, so a timeout says nothing about whose lock a named index carries. Any state of the named index is a valid start, since each operation first brings its copy to the current listing; concurrent operations on it never contend for a lock, and the last to finish leaves its cache. An older cache left last — two sessions in one directory snapshotting at once — is colder, not wrong: an entry claims only that a file with that stat held that content, a claim that does not expire, and each named index is one git process's complete write with that write's timestamp, so git's check for an entry as new as its index still applies.
- **Every git command is bounded and cancellable** (`util/git/snapshot_command.py`). Each has a cap, `LLM_SNAPSHOT_COMMAND_TIMEOUT` (30 s), and, for the self-review gate, the time left before its deadline; the listing's own directory walks check the same deadline, and the same cancellation, before each directory. Once it holds the store's lock, an operation — the walk and every command in it — runs within one budget as well, `LLM_SNAPSHOT_OPERATION_TIMEOUT` (120 s): commands that each fit their cap are a sequence, and without a budget for the sequence a directory too large to hash ends up holding a turn up one command at a time, failing only at the end. A directory too large to snapshot within the cap is treated like one over the budget: rewind turns itself off for the session and says why, instead of holding every turn up for 30 seconds only to fail again. None inherits a variable that would point git at another repository, index or object database. An operation run through `run_in_worker` stops before its next command once its caller is cancelled, and the caller waits for it before the cancellation propagates: rewind's lock is not released while git still runs on the index, and a review store is not deleted while git still writes to it. A step that waits without running a command — the lock — watches the same cancellation, since the deadline is never consulted while it waits.
- **Stores are bounded by age, not by count.** At a session's first snapshot, a conversation whose newest snapshot is older than `LLM_SNAPSHOT_RETENTION` (30 days) loses its ref — never the current conversation's — and `git gc --auto`, detached, packs the store and prunes what no ref reaches, a timed-out snapshot's orphaned objects included. A whole history goes or stays: dropping old commits from a live one would refuse rewinds the UI still offers. A listed file over `LLM_SNAPSHOT_FILE_MAX_MB` (50) is left out as if ignored — recorded in the snapshot's left-out paths, so a restore neither writes over nor removes it — since nothing else bounds an untracked dataset copied into the store in full. The store's `info/attributes` is rewritten only when it differs, by rename: truncated mid-rewrite, it would let another process's snapshot hash under the project's filters.
- **Every limit is a `CFG` knob, read when it applies.** The file-size cap, the loose-file budget, and the command, operation and lock timeouts are `LLM_SNAPSHOT_*` fields read at each listing, command or operation rather than bound to module constants at import, so an environment variable or an assignment in `zrb_init.py` changes them for the next snapshot. The listing reads its budget once when it starts, not per file.
- **Without git, rewind is off from the start.** `GIT_MISSING_REASON` is the manager's `unavailable_reason` from construction; the TUI prints nothing for it — not news every session — and `/rewind` says why.
- **Rewind's first snapshot runs in the background.** The TUI starts it as a background task instead of awaiting it before drawing; the task is started before the one that runs turns and takes the manager's lock in its first step, so the first turn's snapshot waits for it. The order is not what makes the first turn rewindable: a turn's snapshot is taken before its first model request, so one that came first would hold the directory as it was before the turn, and the first snapshot would find it and report the history up to date. Nor can anything zrb runs change files before that snapshot: a trigger only submits a turn. A change another program makes before the first turn is not a turn's, and rewind undoes turns; a first snapshot taken synchronously would only move the history's start earlier, while the UI waited for it. Teardown cancels and awaits it with the UI's other background tasks, so it never reports progress to a UI that is gone.

*Platforms:* case-insensitive and normalization-insensitive filesystems (macOS, Windows) fold names before matching (`_fold`); Windows junctions are never followed; object files git writes read-only are deleted anyway; the store's own files are LF; the OS lock is `msvcrt.locking` on Windows and `flock` elsewhere; git 2.11 or later (`cat-file --filters`).

**Consequences.** Measured on this repository (1,422 tracked files): rewind's first snapshot takes 0.58 s and 9 MB, each later one 0.02 s; a review store's turn-start snapshot takes 0.10 s and 0.3 MB, and — since a review store starts each turn with an empty index — grows with the directory: 0.30 s for a 30,000-file, 119 MB repository. Further conversations in the same directory add only the objects that changed. Gitignored files — a `.env`, build output — are neither snapshotted nor rewound, the same boundary the project's own git draws. A nested clone, a submodule, a directory of repositories, a repository its parent ignores — a folder of cloned child repositories, the worktrees `EnterWorktree` creates under `.zrb/worktree/` — is snapshotted and rewound file by file, each by its own ignore rules. Rewinding past the removal of a worktree or nested repository brings its files back as a plain directory, since no `.git` is ever snapshotted. Recording what a snapshot leaves out costs a walk of its directories — directories only, no file read — on every snapshot: 6 ms for this repository's 245 directories, 155 ms for 19,500 with a warm cache. The record rides in every rewind commit's message — 183 entries, 6 KB, for this repository; tens of KB for one with thousands of scattered ignored files. Searching the ignored directories costs a walk of them on every snapshot — none here, since `DEFAULT_IGNORE_DIRS` are skipped; roughly 1.7 s per 100,000 entries in a large ignored build directory. A directory with more loose files than the budget allows gets no rewind, and is told so. Stores from the shadow-copy layout of earlier releases are not migrated; they can be deleted from `LLM_SNAPSHOT_DIR`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Copy the working directory into a per-session shadow repository | Reads, writes and stores every file twice — as a copy and as a git object. Measured on this repository: 1.2 s and 85 MB for the first snapshot, awaited before the TUI drew; 994 MB across 11 sessions, since nothing was shared. It honoured no `.gitignore`. |
| `git add -A` over the working directory | Git's walk stops at a nested repository and records a gitlink, so a nested clone, a submodule, and every repository in a directory of repositories are neither snapshotted nor restored. |
| Leave out a nested repository its parent ignores | A repository is often ignored only so its parent stops reporting it — a folder of cloned child repositories, `.zrb/worktree/` — and its files are no less the user's. |
| Find worktrees through `git worktree list` | Covers worktrees only, not a clone in an ignored directory; the search for repositories in ignored directories finds both. |
| Remove a timed-out command's lock from the shared index | Only safe if the lock is the command's own, which a timeout does not show: `update-index` runs on while another process holds the lock. |
| Read the metadata as git trailers (`%(trailers)`) | A trailer is any `key: value` line in the message's last paragraph, and a label is part of the message, so a label could supply or shadow one. |
| Copy the history on `/save` in a background task alone | A snapshot of the new name taken before the task runs lands with no parent, and the copy then overwrites it — even one started in the same task, when a queued message follows `/save`. So the copy is registered synchronously when `copy_history` is called, and the task only lands it. |
| Record pending copies beside the store, so a later session applies what this one did not | It covers one corner — the session ending while another process holds the store — and turns the copy into a queue shared across processes over git refs. Each interleaving then needs its own guard: the target's head at record time so a record left behind cannot overwrite newer snapshots, no record once the copy landed, stale entries skipped in chains and in `/rewind`, a lock for the record itself. Review found a new interleaving in each round. In that corner the chat history is saved regardless; only its rewind history starts fresh. |
| Bound the store's history by keeping the last N commits | Rewind accepts a commit in the conversation's own history, and N would silently refuse a rewind the UI still offers. Pruning immutable commits is a separate decision from correcting them. |
| Raise when a restore fails partway | The directory is partly rewound, so "failed" leaves it neither where it was nor where the chat is, with no word of which files differ. |
| Serialize a store's operations with an in-process lock | Covers the managers in one process but not two processes in one directory, which is how two sessions there usually run. |
| Serialize them with a lockfile | A lockfile's holder killed mid-operation leaves it behind, failing every later operation; an OS lock is released when its holder dies. |
| Hold the first turn until the first snapshot finishes | Delays the first turn by the first snapshot's cost for no gain: the turn's own snapshot, taken before its model request, is the same starting point. |
| Parse git's messages or reflog subjects | Their wording differs between git versions, is translated into the user's language, and — for reflog subjects — can be replaced through `GIT_REFLOG_ACTION`. Only machine formats (`-z` listings, `--format` strings, exit codes) and git's structure are read. |
| Reconstruct what a snapshot left out from its ignore rules, written back to disk before a second pass removes what they would have captured | Rules outside the tree — `info/exclude`, the global excludes file — are not written back, so a file they excluded then and no longer do was removed though it existed then. |
| Judge whether a repository existed then by the files the snapshot holds under it | A repository empty then, or whose every file was ignored, passes for one made since, and what was created in it survives the rewind. |
| Trust git to list everything that exists | Git skips a directory it cannot read with only a message; a file in one — a root-owned container volume — was then removed once the directory became readable. |
| Hold a submodule's gitlink in the snapshot | A tree cannot hold `lib` as a gitlink and files under `lib/` at once, and the files are what a rewind restores and a review reads: moving a submodule to another commit changes its files, which both see. The pointer is the parent's index and history, which a rewind never moves. |
| Remove every current file the restore target lacks | Removes files that existed when the snapshot was taken but were not captured — ignored by rules the rewind restores, or unreadable then. |
| Treat a refused write as a failed restore | Git has already written every other file, so "failed" would leave the directory mostly rewound, the chat not rewound, and no word of which file stayed behind. |
| Remove the files of a repository made since the snapshot | Leaves a hollow repository whose `.git` a rewind never touches, and loses its uncommitted work. |
| One stat cache per conversation | Every conversation snapshots the same directory, and each operation starts from a private copy it brings up to date, so a shared cache is as correct and stays warm across `/load`. |
| Pin the history to the conversation the session started with | After `/load`, snapshots of the loaded conversation would land in the first one's history, and `/rewind` would cut the loaded chat at the first one's message counts. |
| `git add --pathspec-from-file` with the listing | Keeps `git add`'s error handling, but silently skips a path inside a nested repository. |
| Make the enclosing repository's root the work tree | Brings the `.gitignore` files above a subdirectory into play, but has the same gitlink blindness; listing through the repository from the subdirectory itself gives the same rules without widening the work tree. |
| One store per repository found | A snapshot would be several trees and a restore several coordinated writes; one tree over the whole directory is one commit and one `read-tree`. |
| Snapshot into the project's own `.git` | Writes untracked files' contents — secrets included — into the project's object database, and mixes zrb's refs into the user's repository. |
| Borrow the repositories' objects for rewind too | 0.10 s instead of 0.58 s for a first snapshot here, but a long-lived snapshot could lose objects to a `git gc` in a repository. |
| Force-add gitignored files | Rewinds `.env` edits, but snapshots every build output and dependency directory the project ignores. |
| Track only the files the file tools touched | Misses changes made through `Shell`, which is how most generated and moved files change. |
| Honour a `.gitignore` outside any repository | Git does not; it would take git's full walk of an unbounded directory before the budget could stop it. |
| Rewind only inside a git repository | Leaves out a directory of repositories, the layout with the most to lose; the budget bounds a directory with no repository. |
| No budget | A chat started in `~` would hash — and store — the whole home directory, SSH keys included. |
| Key the history by the live process instead of the conversation | A resumed conversation would lose its rewind history, and the key would have to be persisted and restored with the chat history — which is what the conversation's name already is. |
| One git directory per session | Stores every file again per session; that duplication is what the shadow copy filled 994 MB with. |
| Rewind off by default | An undo that has to be enabled beforehand is rarely there when it is needed, and a snapshot after the first costs 0.02 s. |
