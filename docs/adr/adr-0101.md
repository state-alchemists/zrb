# ADR-0101 — Working-directory snapshots are git trees in a private store, listed repository by repository

**Status:** Accepted

**Context.** Two features snapshot the working directory. `/rewind` restores the directory and conversation to before an earlier turn, so it needs one exactly restorable snapshot per turn. The self-review gate (ADR-0100) diffs the directory at Stop against turn start, so it needs two exactly diffable snapshots per turn. Both run before a turn does any work, so every snapshot after the first must be cheap.

Both hash untracked files — a `.env`, a private key — so the copies must never land in a project's `.git` or be readable by other users. Both must work in every layout a chat starts in: a repository, a subdirectory of one, a repository with nested clones or submodules, a directory of repositories, and a directory with no git at all, `~` included.

Git gives most of this: it hashes a work tree it does not own into a separate git directory and index, keeps a stat cache, and applies ignore rules. It does not walk into nested repositories — its walk stops at a `.git` and records a gitlink, so `git add -A` never sees inside — and it does not bound a directory no `.gitignore` covers.

**Decision.**

- **A snapshot is a tree in a private bare repository whose work tree is the working directory itself** (`SnapshotStore`, `util/git/snapshot_store.py`). Nothing is copied, and nothing is written into the directory or any repository under it.
- **Zrb lists the files; git hashes them** (`util/git/snapshot_listing.py`).
  - A directory inside a repository is listed by that repository (`git ls-files --cached --others --exclude-standard`), so its `.gitignore` files (above the directory too), `info/exclude` and global excludes apply.
  - Each nested repository lists itself, recursively: one the listing reports (untracked as `dir/`, a submodule as a gitlink), and one inside an ignored directory. Ignored directories (`git ls-files --others --ignored --directory`) are searched for repositories and nothing else.
  - A directory outside every repository is walked, taking only regular files and symlinks, following neither symlinks nor Windows junctions. A repository found there lists itself. So does a working directory its own repository ignores (a scratch folder), which listed through the repository would be empty.
  - The list feeds `git update-index --add --remove --stdin` on the store's index (keeping git's stat cache), then `write-tree`. Entries the listing no longer returns are dropped first, so a snapshot holds exactly what was listed.
  - `DEFAULT_IGNORE_DIRS` (`node_modules`, `.venv`, caches) and the store itself are excluded everywhere, tracked files included, and never searched.
- **A snapshot records what exists but it does not hold**, since only the snapshot can tell a restore whether a file did not exist then or was never seen. The record holds: every path a repository ignores, by any rule, as `git ls-files --others --ignored --directory` reports it; every unreadable directory (git skips these silently), found by a directories-only walk; each uninitialized submodule's directory; the files git could not read; and the repositories listed.
- **Outside every repository a budget bounds the listing.** No ignore rule applies there (git ignores a `.gitignore` outside a repository too), so loose files count toward `LLM_SNAPSHOT_LOOSE_MAX_FILES` (5,000) and `LLM_SNAPSHOT_LOOSE_MAX_MB` (200); past either, `SnapshotBudgetError`. Files inside repositories do not count.
  - Over budget, rewind turns off for the session and says why (first snapshot and `/rewind`) without walking again; the self-review gate warns once and reviews from the file tools' paths.
  - Within budget, a working directory outside every repository is told once that its rewind reaches less far: nothing is left out on purpose, and its `.gitignore` has no effect.
- **Rewind is on by default, everywhere.** The budget, not a repository's presence, keeps a chat in `~` from hashing the home directory, so a directory of repositories gets rewind too.
- **Restore rewrites the directory to a snapshot, never destroying what no snapshot holds.** It re-snapshots first, then decides each path by its current state:

  | Path now | Snapshot has it | Snapshot lacks it |
  | --- | --- | --- |
  | listed and readable | rewritten | removed only if the snapshot shows it did not exist then: in neither tree nor record, in a repository the snapshot listed |
  | unreadable, or under an unreadable directory | left alone | left alone |
  | ignored or excluded | left alone | left alone |
  | absent | recreated | — |

  - *Scope now* is judged by each path's owning repository via `git check-ignore` (never counting a tracked file as ignored, e.g. `.env.example` under `.env*`), plus `DEFAULT_IGNORE_DIRS` and excluded paths.
  - *Did not exist then* is read from the record, never reconstructed: the present is judged by looking, the past only by what the snapshot wrote down. A left-out directory covers only what its own repository would list there, not a nested repository, so a file created in a worktree under an ignored `.zrb/worktree/` is still removed. Left-out paths match case-insensitively and repositories exactly, both erring toward keeping. One `read-tree -u --reset` writes the result.
  - *A repository made since* (unlisted then) keeps every file the snapshot lacks; its own history holds its work. A repository that existed then, even empty, was listed, so files created in it since are removed.
  - *Case and Unicode form*: on a folding filesystem (macOS, Windows), a path the snapshot holds in another form is the same file — rewritten, never removed.
  - *A refused write* (file held open, no write permission) does not stop the rest. `RestoreOutcome.left_behind` names each path not written; the chat rewinds, `/rewind` lists them, and repeating it finishes once the cause is gone.
  - *A failure before the write* raises with nothing changed. One during the write reports every intended path as left behind and does not raise; the chat rewinds. A ref that cannot be moved back is logged.
  - *Something unlisted in the way* (a directory holding an ignored file, a FIFO) is never overwritten; that path, or one a kept file blocks, is left behind and reported. Listed files in the way are replaced.
  - Restore never moves a repository's `HEAD`, branches, or a submodule's pointer: those are history, not the working tree.
- **Rewind keeps one store per working directory and one ref per conversation.**
  - The store is `<LLM_SNAPSHOT_DIR>/<directory name>-<hash of its real path>.git`; the hash prevents sanitized-name collisions (`/tmp/a:b` and `/tmp/a?b` both become `a_b`). Conversations there share one stat cache and store unchanged files once.
  - A conversation's history is `refs/zrb/<name>-<hash>`, keyed by the conversation name its chat history is saved and resumed under, since snapshots record message counts. The UI passes a callable returning the current name, read per operation, so after `/load` the loaded conversation's history is used.
  - Restore accepts only a commit in the conversation's own history, then moves the ref back to it, dropping later snapshots; another conversation's commit would rewind the files but not the conversation.
  - Two processes running one conversation at once share its rewind history as they share its chat history; neither is supported.
- **`/save` copies the rewind history like the chat history.** `copy_history` registers the copy in memory before returning, and every later operation applies registered copies first under the operation lock, so no snapshot of the new name lands before it — even one started in the same task without yielding.
  - Copies land in order and are forgotten one at a time, so a partial failure never replays one already taken. A copy of a pending copy takes the original source. Copying an empty history leaves the target empty, since old snapshots would carry a dead chat's message counts.
  - If the store is busy, the next operation applies the copy, and `list_snapshots` shows the target its incoming history meanwhile. A copy git refuses is dropped with a warning rather than failing every later operation.
  - Copies live only as long as the session: one still pending at exit (only possible while another process holds the store) leaves the target without rewind history; its chat history is saved regardless.
- **A rewind commit carries its record where its label cannot reach.** Subject: the label on one line, then ` [mc:<message count>]`, read from the subject's end. Body: `zrb-snapshot: {"unreadable": …, "left_out": …, "repositories": …}`, read from the body alone. A commit without a readable record is not restored. A snapshot whose tree matches the latest commit still gets a commit if its record differs, or a rewind there could remove a file ignored since.
- **Rewind's store keeps its own objects; a review store borrows them.** Rewind history outlives the session and a repository's `git gc` could prune its blobs, so it copies every file once. A per-turn review store uses listed repositories' object databases as alternates and writes only untracked contents.
- **Stores are owner-only and never snapshot themselves.**
  - The store's top directory is `0700` regardless of umask, reapplied on every open. On Windows the default locations (`%TEMP%`, the user profile) are already private by ACL.
  - A store inside the working directory is excluded from its own listing. An `LLM_SNAPSHOT_DIR` equal to the working directory turns rewind off with a reason. A store whose directory contains its work tree is refused.
  - Any setup failure (that refusal, an unwritable directory, no git) turns rewind off for the session with its reason rather than failing every turn.
- **Snapshots are byte-exact.** The store's `info/attributes`, which outranks `.gitattributes`, sets `* -text -filter -ident -working-tree-encoding`, so no conversion or clean/smudge runs (a git-lfs smudge would write pointer files into the work tree). Git output is decoded UTF-8 with `surrogateescape` so non-UTF-8 names survive. A global `core.fsmonitor` is overridden so no daemon starts per store. Store files, `alternates` included, are LF everywhere.
- **A file git cannot read does not fail the snapshot.** `update-index` stops at the first one, and its message is not parsed. On failure each file is opened to find the unreadable ones (a FIFO, socket or device counts as unreadable unopened, since opening a FIFO blocks). They are left out, with any cached entry dropped so no stale content is held, and the rest are re-fed (re-stat, not re-hash). The record names them, so restore keeps them and the self-review gate lists them rather than showing them deleted.
- **A rewind store's operations take turns, across processes too.** Sessions in one directory — one process (web UI) or several — share a store; concurrent restores would interleave, and a snapshot mid-restore would capture a half-written directory.
  - Every snapshot, restore and setup (concurrent `git init`s collide on the config lock) holds an OS lock on `zrb-operation.lock` (`util/file_lock.py`: `flock` on POSIX, `msvcrt.locking` on Windows), released when the holder dies. Within one manager, `self._lock` orders operations.
  - The wait is capped at `LLM_SNAPSHOT_LOCK_TIMEOUT` (60 s); past it only that operation fails. The wait precedes the operation budget rather than spending it, since contention does not mean the directory is too slow. It stops at once on cancellation.
  - Listing snapshots takes no lock (it reads the ref once and immutable commits) and never sets a store up. A review store is turn-private and takes none.
- **Every operation works on an index of its own.** A snapshot, restore or graft copies the store's named index (the stat cache) to a per-operation file, preserving its timestamp so git still re-hashes a same-second, same-size rewrite. It replaces the named index when done; on failure the copy and its lock are deleted. A command killed at its timeout cannot remove its own lock, and a stale lock on the named index would fail every later command, across restarts.
  - Any state of the named index is a valid start, since each operation first brings its copy up to date. Concurrent operations never contend; the last to finish leaves its cache. An older cache left last is colder, not wrong: an entry only claims that a file with that stat held that content.
- **Every git command is bounded and cancellable** (`util/git/snapshot_command.py`).
  - Each command is killed at `LLM_SNAPSHOT_COMMAND_TIMEOUT` (30 s) or, for the self-review gate, its deadline. Directory walks check the deadline and cancellation per directory.
  - Once it holds the lock, a whole operation runs within `LLM_SNAPSHOT_OPERATION_TIMEOUT` (120 s), so a directory too large to hash cannot stall each turn one command at a time. Exceeding either raises `SnapshotTimeoutError` and turns rewind off for the session with a reason.
  - No command inherits a variable pointing git at another repository, index or object database.
  - Through `run_in_worker`, a cancelled operation stops before its next command, and the caller awaits it (retrieving its error) before cancellation propagates — so the lock is never released, nor a review store deleted, while git still runs. Cancellation during store setup raises `SnapshotCancelledError` and leaves rewind on.
- **Stores are bounded by age, not count.** At a session's first snapshot, a conversation whose newest snapshot is older than `LLM_SNAPSHOT_RETENTION` (30 days) loses its ref (never the current one), and a detached `git gc --auto` packs and prunes unreachable objects. A history goes or stays whole. A file over `LLM_SNAPSHOT_FILE_MAX_MB` (50) is left out as if ignored, and recorded. `info/attributes` is rewritten only when it differs, by rename, so a truncated file never lets another process hash under the project's filters.
- **Every limit is a `CFG` knob, read when it applies.** The `LLM_SNAPSHOT_*` size cap, budget and timeouts are read per listing, command or operation, not at import, so an env var or `zrb_init.py` assignment affects the next snapshot. The listing reads its budget once at start.
- **Without git, rewind is off from the start.** `GIT_MISSING_REASON` is the manager's `unavailable_reason`; the TUI stays silent and `/rewind` says why. Git 2.11+ is required (`cat-file --filters`).
- **Rewind's first snapshot runs in the background.** The TUI starts it before the turn task; it takes the manager's lock first, so the first turn's snapshot waits for it. Order is not what makes turn one rewindable: a turn snapshots before its first model request, and nothing zrb runs changes files earlier (a trigger only submits a turn). Teardown cancels and awaits it with the UI's other background tasks.
- **Known unbounded cases.** A hung filesystem call (a dead network mount) cannot be interrupted. A process killed mid-turn leaves its owner-only review store in the temp directory (ADR-0100); sweeping it would require telling a dead process's store from a live one's. A file edited mid-snapshot is held at whichever version git read.

**Test coverage.** Each class of state — what exists but is not held, what a restore may change, who else touches a store, `/save` copies, what can block, and platforms (case and Unicode folding, junctions, deleting the read-only object files git writes, LF store files, the per-OS lock) — is pinned case by case in `test/util/git/test_snapshot_listing.py`, `test/util/git/test_snapshot_store.py`, `test/util/git/test_snapshot_store_restore.py`, `test/util/git/test_snapshot_store_lifecycle.py`, `test/util/git/test_snapshot_command.py`, `test/util/test_file_lock.py`, `test/llm/snapshot/` and `test/llm/hook/`. A new case gets a test there before its fix lands.

**Consequences.** Measured on this repository (1,422 tracked files):

| Measure | Cost |
| --- | --- |
| Rewind, first snapshot | 0.58 s, 9 MB |
| Rewind, later snapshots | 0.02 s |
| Review store, turn-start snapshot (empty index each turn) | 0.10 s, 0.3 MB; 0.30 s for a 30,000-file, 119 MB repository |
| Left-out record walk, every snapshot | 6 ms for 245 directories; 155 ms for 19,500, warm cache |
| Record size per rewind commit | 6 KB (183 entries); tens of KB with thousands of scattered ignored files |
| Searching ignored directories, every snapshot | ~1.7 s per 100,000 entries in a large ignored build directory |

Further conversations in a directory add only changed objects. Gitignored files (`.env`, build output) are neither snapshotted nor rewound, the project's own git boundary. Nested clones, submodules and ignored child repositories (including `EnterWorktree`'s `.zrb/worktree/`) are rewound file by file under their own rules. Rewinding past a nested repository's removal restores its files as a plain directory, since no `.git` is snapshotted. Over-budget directories get no rewind and are told so. Stores in the older shadow-copy layout are not migrated; delete them from `LLM_SNAPSHOT_DIR`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Per-session shadow-copy repository | Every file stored twice: 1.2 s and 85 MB first snapshot, 994 MB across 11 sessions; no `.gitignore`. |
| One git directory per session | Re-stores every file per session. |
| `git add -A` | Stops at nested repositories, recording a gitlink. |
| `git add --pathspec-from-file` | Silently skips paths inside nested repositories. |
| Enclosing repository's root as work tree | Same gitlink blindness; listing from the subdirectory gives the same rules. |
| One store per repository | Several trees and coordinated writes instead of one commit and one `read-tree`. |
| The project's own `.git` | Writes untracked secrets into its object database and mixes in zrb's refs. |
| Borrow objects for rewind too | 0.10 s vs 0.58 s, but a repository's `git gc` could delete a long-lived snapshot's objects. |
| Skip nested repositories the parent ignores | Often ignored only to silence the parent; their files are the user's. |
| `git worktree list` | Finds worktrees, not clones in ignored directories. |
| Hold a submodule's gitlink | A tree cannot hold `lib` as a gitlink and files under `lib/` at once; the files are what matter. |
| Force-add gitignored files | Snapshots every build output and dependency directory. |
| Track only file-tool paths | Misses `Shell` changes. |
| Honour `.gitignore` outside repositories | Git doesn't; would need an unbounded walk before the budget applies. |
| No budget | A chat in `~` would store the home directory, SSH keys included. |
| Rewind only inside a repository | Excludes directories of repositories, the layout with most to lose. |
| Rewind off by default | Rarely enabled before it is needed; later snapshots cost 0.02 s. |
| Trust git to list everything | Unreadable directories are skipped; their files were removed once readable. |
| Reconstruct left-out paths from ignore rules | `info/exclude` and global rules aren't restored, so files they excluded then get removed. |
| Infer "repository existed then" from its files | An empty or all-ignored repository passes as new, keeping files created since. |
| Remove every file the target lacks | Deletes files that existed but were ignored or unreadable. |
| Remove a new repository's files | Leaves a hollow repository and loses uncommitted work. |
| Raise on partial restore or refused write | Leaves the directory matching neither state, with no list of differences. |
| Git trailers for metadata | A label could supply or shadow a trailer. |
| Parse git messages or reflog subjects | Vary by version and locale; `GIT_REFLOG_ACTION` rewrites them. Only machine formats and structure are read. |
| In-process lock only | Misses two processes in one directory. |
| Lockfile | Left behind when its holder is killed. |
| Remove a timed-out command's lock from the shared index | A timeout doesn't show whose lock it is. |
| One stat cache per conversation | A shared cache is equally correct and stays warm across `/load`. |
| Key history by process | Resumed conversations would lose rewind history. |
| Pin history to the starting conversation | After `/load`, snapshots land in the wrong history. |
| `/save` copy in a background task alone | A snapshot taken first lands parentless, then is overwritten. |
| Persist pending copies beside the store | A cross-process queue whose every interleaving needs a guard, for one corner case where chat history is saved anyway. |
| Keep the last N commits | Would refuse rewinds the UI still offers. |
| Block the first turn on the first snapshot | No gain: the turn's own snapshot is the same start. |
