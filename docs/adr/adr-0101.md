# ADR-0101 — Working-directory snapshots are git trees in a private store, listed repository by repository

**Status:** Accepted

**Context.** Two features snapshot the working directory. `/rewind` restores the directory and the conversation to the point before an earlier turn, so it needs a snapshot per turn it can write back exactly. The self-review gate (ADR-0100) diffs the directory at Stop against its state at turn start, so it needs two snapshots per turn it can diff exactly. Both run before a turn does any work, so a snapshot must cost little after the first. Both hash untracked files — a `.env`, a private key — so their copies must never land in a project's `.git` or be readable by other users. And both must hold for every layout a chat starts in: a repository, a subdirectory of one, a repository holding nested clones or submodules, a directory holding several repositories, and a directory with no git at all, `~` included.

Git gives most of this: it can hash a work tree it does not own into a separate git directory and index, keep a stat cache so unchanged files are not hashed again, and apply a repository's ignore rules. What it does not give is a walk into nested repositories — its directory walk stops at any directory holding a `.git` and records a gitlink, so `git add -A` never sees inside one — and any bound on a directory no `.gitignore` covers.

**Decision.**

- **A snapshot is a tree in a private bare repository whose work tree is the working directory itself** (`SnapshotStore`, `util/git/snapshot_store.py`). Nothing is copied, and nothing is written into the directory or into any repository under it.
- **Zrb lists the files; git hashes them.** `util/git/snapshot_listing.py` builds the list repository by repository. A directory inside a repository is listed by that repository — `git ls-files --cached --others --exclude-standard` — so its `.gitignore` files, above the directory too, its `info/exclude` and the user's global excludes apply. Each nested repository is listed the same way, by itself, recursively: one the listing reports — an untracked one as `dir/`, a submodule as a gitlink — and one inside a directory the repository ignores, which is searched for repositories (`git ls-files --others --ignored --directory` names those directories) and nothing else. A directory outside every repository is walked, and a repository found there is listed by itself; so is a working directory its own repository ignores — a scratch folder — since it is still what the user works on, and listing it through the repository would leave it empty. The list goes to `git update-index --add --remove --stdin` in the store's own index, which keeps git's stat cache, and `write-tree` makes the snapshot. An index entry the listing no longer returns — deleted, or ignored since — is dropped first, so a snapshot holds exactly what was listed. `DEFAULT_IGNORE_DIRS` (`node_modules`, `.venv`, caches) and the store itself are left out everywhere, tracked files included, and never searched for repositories.
- **Outside every repository a budget bounds the listing.** No ignore rule applies there — a `.gitignore` outside a repository means nothing to git either — so those loose files count toward `LOOSE_FILE_LIMIT` (5,000) and `LOOSE_BYTE_LIMIT` (200 MB). Past either, the listing stops with `SnapshotBudgetError`. Files inside repositories do not count: their ignore rules bound them. Rewind turns itself off for the session and says why — on its first snapshot and on `/rewind` — without walking the directory again; the self-review gate warns once and reviews from the file tools' paths.
- **Rewind is on by default, everywhere.** The budget, not the presence of a repository, is what keeps a chat started in `~` from hashing the home directory, so a directory of repositories — which is not a repository itself — gets rewind too.
- **Restore rewrites the working directory to a snapshot, and removes a file only when the snapshot would have held it.** It re-snapshots first, so files created since are in the index, and filters the target tree down to what the listing would take now — each path judged by the repository that owns it (`git check-ignore`, which, like the listing, never counts a tracked file as ignored — a force-added file, `.env.example` under `.env*`), plus `DEFAULT_IGNORE_DIRS` and the excluded paths — so an old snapshot never overwrites or recreates a file ignored since. A current file the target lacks is not always one created since: it may have existed then, ignored by rules the target restores (a `.gitignore` edit being rewound), or unreadable when the snapshot was taken. So `read-tree -u --reset` first writes the target keeping every file it lacks; then, with the target's own ignore rules back on disk, a second `read-tree` removes only those files those rules would have captured, never one the snapshot recorded as unreadable. A repository the target holds nothing of — a worktree or clone made since — is left as it is: removing its files would leave it hollow, and its own history holds its work. Restore puts back files, nested repositories' files included; it does not move any repository's `HEAD` or branches.
- **Rewind keeps one store per working directory and one ref per conversation.** The store is `<LLM_SNAPSHOT_DIR>/<directory name>-<hash of its real path>.git`, with one stat cache every conversation there shares — any state of it is a valid start (below) — and a conversation's history is `refs/zrb/<name>-<hash>`. The hashes matter because sanitizing alone collides: `/tmp/a:b` and `/tmp/a?b` both become `a_b`, and would share a store and restore each other's files. The key is the conversation's name — the identity its chat history is saved and resumed under, random unless the user names it — since each snapshot records that conversation's message count, and a resumed conversation must find its snapshots again. Unchanged files are stored once across every conversation in a directory. The manager follows the conversation the UI is on: the UI builds it with a callable returning the conversation's current name, read at the start of each operation, so after `/load` snapshots and `/rewind` use the loaded conversation's history, and `/save` copies the current history to the new name as it copies the chat history — a saved copy with no snapshots leaves the new name with none, since old ones would carry message counts of a chat history that is gone. Two processes running the same conversation at once share its rewind history as they share its chat history; neither is supported. Restore accepts only a commit in the conversation's own history, then moves its ref back to it, so later snapshots drop out of the list: another conversation's commit is not in this one's list, so restoring it would rewind the files without rewinding the conversation to match.
- **Rewind's store keeps its own objects; a review store borrows them.** Rewind history outlives the session, and a `git gc` in a repository could prune a blob an old snapshot relies on, so the persistent store copies every file once. A per-turn review store lives for one turn, so it reads the object database of every repository it lists as an alternate and writes only untracked files' contents.
- **Stores are owner-only and never snapshot themselves.** A store's top directory is `0700` whatever the umask, applied on every open, since it holds copies of untracked files. A store inside the working directory — an `LLM_SNAPSHOT_DIR` there, say — is excluded from its own listing, so a restore never rewrites the store mid-restore; an `LLM_SNAPSHOT_DIR` that is the working directory itself turns rewind off with that reason, since other directories' stores would land in it, and a store whose own directory holds its work tree is refused outright — deleting it would delete the work tree. Any failure to set the store up — that refusal, a snapshot directory that cannot be written, git not installed — will not pass by itself, so it too turns rewind off for the session with its reason, rather than failing again on every turn.
- **Snapshots are byte-exact.** The store's `info/attributes`, which outranks a project's `.gitattributes`, sets `* -text -filter -ident -working-tree-encoding`: no line-ending or encoding conversion, and no clean/smudge filter — a git-lfs smudge against the store would otherwise write pointer files into the user's work tree. Git output is decoded as UTF-8 with `surrogateescape`, so a non-UTF-8 file name survives the listing and `update-index --stdin` intact, and a global `core.fsmonitor` is overridden so no watcher daemon starts per store. Files the store writes, `alternates` included, use LF on every platform.
- **A file git cannot read does not fail the snapshot.** `update-index` stops at the first unreadable file and names it, unquoted — so each listed path is matched against the end of its output rather than a path parsed out of it, which a newline in a name would split; that file is left out, the rest are fed again — the rerun re-stats rather than re-hashes them — and the snapshot names the files it left out. A rewind commit records them as a trailer, so a restore never removes them for being absent from it; the self-review gate lists them rather than showing them as deleted.
- **Every operation works on an index of its own.** A snapshot, restore or graft copies the store's named index — a stat cache, so unchanged files are not hashed again — to a file named for that one operation, keeping its timestamp (git re-hashes an entry as new as the index file, which is what catches a file rewritten within the same second at the same size), works on the copy, and replaces the named index with it when done. A git command killed at its timeout cannot remove the lock it took, and a lock left behind would fail every later command on its index — for rewind, across restarts. The lock is on the operation's own copy, so deleting the copy and its lock can never take another process's lock: `update-index` keeps working while another process holds its index's lock and fails only when it writes, so a timeout says nothing about whose lock a named index carries. Any state of the named index is a valid start, since each operation first brings its copy to the current listing; concurrent operations on it never contend for a lock, and the last to finish leaves its cache.
- **Every git command is bounded and cancellable** (`util/git/snapshot_command.py`). Each has a 30-second cap and, for the self-review gate, the time left before its deadline. None inherits a variable that would point git at another repository, index or object database. An operation run through `run_in_worker` stops before its next command once its caller is cancelled, and the caller waits for it before the cancellation propagates: rewind's lock is not released while git still runs on the index, and a review store is not deleted while git still writes to it.
- **Rewind's first snapshot runs in the background.** The TUI starts it as a background task instead of awaiting it before drawing; the manager's lock makes the first turn's snapshot wait for it. Teardown cancels and awaits it with the UI's other background tasks, so it never reports progress to a UI that is gone.

**Consequences.** Measured on this repository (1,422 tracked files): rewind's first snapshot takes 0.58 s and 9 MB, each later one 0.02 s; a review store's turn-start snapshot takes 0.10 s and 0.3 MB, and — since a review store starts each turn with an empty index — grows with the directory: 0.30 s for a 30,000-file, 119 MB repository. Further conversations in the same directory add only the objects that changed. Gitignored files — a `.env`, build output — are neither snapshotted nor rewound, the same boundary the project's own git draws. A nested clone, a submodule, a directory of repositories, a repository its parent ignores — a folder of cloned child repositories, the worktrees `EnterWorktree` creates under `.zrb/worktree/` — is snapshotted and rewound file by file, each by its own ignore rules. Rewinding past the removal of a worktree or nested repository brings its files back as a plain directory, since no `.git` is ever snapshotted. Searching the ignored directories costs a walk of them on every snapshot — none here, since `DEFAULT_IGNORE_DIRS` are skipped; roughly 1.7 s per 100,000 entries in a large ignored build directory. A directory with more loose files than the budget allows gets no rewind, and is told so. Stores from the shadow-copy layout of earlier releases are not migrated; they can be deleted from `LLM_SNAPSHOT_DIR`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Copy the working directory into a per-session shadow repository | Reads, writes and stores every file twice — as a copy and as a git object. Measured on this repository: 1.2 s and 85 MB for the first snapshot, awaited before the TUI drew; 994 MB across 11 sessions, since nothing was shared. It honoured no `.gitignore`. |
| `git add -A` over the working directory | Git's walk stops at a nested repository and records a gitlink, so a nested clone, a submodule, and every repository in a directory of repositories are neither snapshotted nor restored. |
| Leave out a nested repository its parent ignores | A repository is often ignored only so its parent stops reporting it — a folder of cloned child repositories, `.zrb/worktree/` — and its files are no less the user's. |
| Find worktrees through `git worktree list` | Covers worktrees only, not a clone in an ignored directory; the search for repositories in ignored directories finds both. |
| Remove a timed-out command's lock from the shared index | Only safe if the lock is the command's own, which a timeout does not show: `update-index` runs on while another process holds the lock. |
| Remove every current file the restore target lacks | Removes files that existed when the snapshot was taken but were not captured — ignored by rules the rewind restores, or unreadable then. |
| Remove the files of a repository made since the snapshot | Leaves a hollow repository whose `.git` a rewind never touches, and loses its uncommitted work. |
| One stat cache per conversation | Every conversation snapshots the same directory, and each operation starts from a private copy it brings up to date, so a shared cache is as correct and stays warm across `/load`. |
| Pin the history to the conversation the session started with | After `/load`, snapshots of the loaded conversation would land in the first one's history, and `/rewind` would cut the loaded chat at the first one's message counts. |
| `git add --pathspec-from-file` with the listing | Keeps `git add`'s error handling, but silently skips a path inside a nested repository. |
| Make the enclosing repository's root the work tree | Brings the `.gitignore` files above a subdirectory into play, but has the same gitlink blindness; listing through the repository from the subdirectory itself gives the same rules without widening the work tree. |
| One store per repository found | A snapshot would be several trees and a restore several coordinated writes; one tree over the whole directory is one commit and one `read-tree`. |
| Snapshot into the project's own `.git` | Writes untracked files' contents — secrets included — into the project's object database, and mixes zrb's refs into the user's repository. |
| Borrow the repositories' objects for rewind too | 0.10 s instead of 0.58 s for a first snapshot here, but a long-lived snapshot could lose objects to a `git gc` in a repository. |
| Force-add gitignored files | Rewinds `.env` edits, but snapshots every build output and dependency directory the project ignores. |
| Track only the files the file tools touched | Misses changes made through `Shell`, which is how most generated and moved files change. |
| Honour a `.gitignore` outside any repository | Git does not; it would take git's full walk of an unbounded directory before the budget could stop it. |
| Rewind only inside a git repository | Leaves out a directory of repositories, the layout with the most to lose; the budget bounds a directory with no repository. |
| No budget | A chat started in `~` would hash — and store — the whole home directory, SSH keys included. |
| Key the history by the live process instead of the conversation | A resumed conversation would lose its rewind history, and the key would have to be persisted and restored with the chat history — which is what the conversation's name already is. |
| One git directory per session | Stores every file again per session; that duplication is what the shadow copy filled 994 MB with. |
| Rewind off by default | An undo that has to be enabled beforehand is rarely there when it is needed, and a snapshot after the first costs 0.02 s. |
