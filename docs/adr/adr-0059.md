# ADR-0059 — Tool output is capped at the source; global overflow is separate

**Status:** Accepted

**Context.** Read, list, search, and shell output can become large enough to flood a model context. These tools know their own retrieval shape: file-oriented results are useful from the beginning, while build and test output usually matters at the end. Other tool sources, especially MCP, have no equivalent source-specific retrieval semantics.

**Decision.** Tools that can control their own output cap it against `CFG.LLM_MAX_OUTPUT_CHARS` (default 100k). `Read`, `LS`, and `Grep`-style tools retain the head. `Shell` retains the tail — where a successful command's result lands — and, when the command failed, both ends: the first traceback line or the first compiler error is at the top and only the summary is at the bottom, so a tail-only cut hides the cause. `StreamCapture.head_text` reads the discarded beginning back from the spill file it already keeps, so the excerpt costs no second copy of the output: 40% of the retained budget goes to the head, the remainder to the tail, and one `… [N characters elided] …` marker joins them. `Shell(background=True)` and `MonitorProcess` stay tail-only — they report a running process's recent output, not a finished command's result. Cuts snap to line boundaries. Shell also writes complete stdout and stderr to a temporary file and surfaces its path, so the model can recover a narrower slice with `Read` or `Grep`. `Shell(background=True)` and `MonitorProcess` share the same `StreamCapture` implementation, including its `flush()` support while a background process is still running.

`LLM_MAX_TOOL_RESULT_CHARS` is not a second truncation layer. Its global, lossless overflow behavior is owned by ADR-0089: with `LLM_ENABLE_TOOL_SPILL` enabled, an oversized result is replaced by a preview and a queryable spill handle; when disabled, it is recorded as oversized metadata only.

**Consequences.** Ordinary high-volume tools remain bounded with retrieval-aware output and no extra model call. Tool types that cannot safely decide which text to discard remain intact until the opt-in global spill mechanism handles them. A typical result is below both thresholds and unchanged. A failed command's head now takes 40% of the retention budget from its tail, so a failure whose explanation really is in the last few thousand characters shows fewer of them — the dump path still holds all of it, and a spill that could not be opened degrades to the tail rather than to no output.

**Alternatives rejected.** *One universal truncation strategy* — source tools know whether their head or tail is useful. *Per-tool caps only* — MCP and future tool sources can still return unbounded payloads. *No cap* — a large repository or command output becomes a context-flooding failure. *Read both ends out of the dump file after the fact* — the excerpt has to exist in the message itself, and a failed `mkstemp` would then cost the excerpt as well as the dump; the spill is already open and already holds the head. *Both ends for every command* — a successful command's beginning is progress chatter, and spending 40% of the budget on it would keep less of the result the caller ran the command for.

**Where it lives.** `src/zrb/util/truncate.py`, `src/zrb/config/mixins/llm_limits.py`, and `src/zrb/llm/tool/stream_capture.py` (`StreamCapture` and `head_text`, shared by `shell.py` and `shell_background.py`; the excerpt itself is `_display_text`/`_head_and_tail` in `shell.py`). Global overflow lives in the ADR-0089 locations.
