# ADR-0059 — Permissions are an ordered ruleset, first match wins

**Status:** Accepted

**Context.** Approval was effectively binary — auto-approve everything, or ask
for everything — with no hard deny and no per-argument granularity. A sub-agent
could not be given narrower permissions than its parent.

**Decision.** A `PermissionPolicy` is an ordered list of `Rule`s, where `key` is
a tool name, a capability, or `*`; `action` is `allow`, `ask` or `deny`; and an
optional `arg_pattern` glob narrows it further. Evaluation is first-match-wins.
The policy travels through the `current_permission_policy` ContextVar, so
sub-agents inherit it. `allow` and `ask` resolve in the approval chain
(ADR-0060), while `deny` is enforced by a pre-execution gate in the tool
wrapper, so a denied call never reaches a prompt. With no policy set, behaviour
is exactly the legacy auto-approve semantics.

**Consequences.** Permissions are expressive, testable and per-argument, and a
latent gap — sub-agents not inheriting edit restrictions — is closed. The cost
is a policy model and resolver to maintain, and a rule ordering that users must
reason about.

**Alternatives rejected.** *A deny-list only* — scales poorly; every new tool is
allowed by default. *Capability-only rules* — too coarse for `Shell`, where the
argument is the risk. *Derive rules from docstrings* — fragile and implicit.

**Where it lives.** `src/zrb/llm/permission/policy.py`,
`src/zrb/llm/permission/state.py`, `src/zrb/llm/agent/common.py`
(`_permission_gate`), `docs/advanced-topics/permission-policy.md`.
