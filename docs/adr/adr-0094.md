# ADR-0094 — A vendor's own API-key variable outranks the generic `LLM_API_KEY`

**Status:** Accepted

**Context.** zrb is provider-agnostic (ADR-0037): one `LLM_MODEL` names the model, and `LLM_API_KEY` / `LLM_BASE_URL` carry the credentials, whichever vendor is behind them. pydantic-ai works the other way round — each provider reads its own variable (`ANTHROPIC_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, …). `ModelResolver` sits between the two.

For a model whose prefix names a provider pydantic-ai supports natively, the resolver used to hand the bare `"anthropic:claude-…"` string back and let pydantic-ai build the provider from the vendor variable. That silently dropped an explicit `LLM_API_KEY`: a user who set only zrb's own knob got "set the `DEEPSEEK_API_KEY` environment variable" for a variable they had deliberately not used.

Injecting `LLM_API_KEY` into every native provider fixes that case and breaks a commoner one. `LLM_API_KEY` is provider-*agnostic* — it says nothing about which vendor it is a key for. The moment two providers are in play it is ambiguous, and the ambiguity is not hypothetical: `LLM_SMALL_MODEL` and `LLM_MULTIMODAL_MODEL` resolve through the same credentials as `LLM_MODEL`, so `LLM_MODEL=openai:gpt-5` plus `LLM_SMALL_MODEL=anthropic:claude-haiku-…` force-fed the OpenAI key to Anthropic and 401-ed on every summarization.

**Decision.** For a natively-supported provider, credentials are chosen by specificity — the most provider-specific source that exists wins.

**1. A `Provider` instance the caller passed for that same vendor wins outright.** It is already configured; nothing may second-guess it. Vendor identity is checked with `Provider.name`, so the `OpenAIProvider` the resolver builds from `LLM_API_KEY` upstream never qualifies for a non-openai prefix.

**2. The vendor's own environment variable is next.** It is provider-specific by construction — `ANTHROPIC_API_KEY` can only mean Anthropic — so it beats a key that names no vendor. This is also the behavior that existed before, so honoring it breaks nobody.

**3. `LLM_API_KEY` / `LLM_BASE_URL` are last**, passed as whichever keyword arguments the provider's constructor actually declares (`AnthropicProvider` takes `base_url`, `DeepSeekProvider` does not).

**4. With none of those, the bare model name is returned unchanged**, so pydantic-ai raises its own "set `<VENDOR>_API_KEY`" message instead of this code inventing a worse one.

**An explicit `LLM_BASE_URL` skips rung 2.** A custom endpoint is a deliberate override of the vendor default, so it must not lose to a vendor variable that only supplies a key. When the native provider cannot accept a `base_url` at all, resolution falls through to the OpenAI-compatible path rather than dropping the setting — every provider reached this way speaks the OpenAI wire format.

**Rung 2 is probed by constructing the provider with no arguments.** pydantic-ai providers read their variable in `__init__` and raise when it is missing, so a successful construction *is* the answer, and the instance it produces is the one used — nothing is built and discarded. A provider that legitimately needs no credential (Ollama on localhost) succeeds, which is the right outcome for the same reason.

**Consequences.** Setting only `ZRB_LLM_API_KEY` works against any native provider, and setting a vendor variable keeps working exactly as it did. A mixed setup — one vendor for the main model, another for the small model — resolves each from its own variable instead of failing.

The cost is that a stale vendor variable now shadows zrb's knob for that one provider; the fix is to unset it, and the error surfaces as a 401 from a named vendor rather than silently using the wrong endpoint. The precedence also cannot be read off a single variable, which is why it is written down here and in `_resolve_native_model`'s docstring.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Always inject `LLM_API_KEY` (the behavior this replaces) | Breaks any setup where `LLM_SMALL_MODEL` or `LLM_MULTIMODAL_MODEL` names a different vendor from `LLM_MODEL` — a 401 with no hint that a key meant for another provider was substituted. |
| Never inject; always return the bare name | The original bug: an explicit `LLM_API_KEY` is silently ignored and the user is told to set a vendor variable they chose not to use. |
| Per-provider knobs (`LLM_ANTHROPIC_API_KEY`, …) | A new knob per vendor, and the vendor's own variable already is that knob. Provider-agnostic configuration (ADR-0037) is the point. |
| Inject only when the prefix matches `LLM_PROVIDER` | `LLM_PROVIDER` is usually unset, so the common mixed-vendor case is unchanged and the knob acquires a second, non-obvious meaning. |
| A hand-maintained provider → env-var table | Duplicates pydantic-ai's own registry and rots on every provider it adds. The no-argument construction asks the provider itself. |

**Where it lives.** `src/zrb/llm/config/model_resolver.py` (`_resolve_native_model`, `_build_from_vendor_env`, `_is_native_provider`), `test/llm/config/test_model_resolver.py`. See ADR-0037 for provider-agnostic configuration.
