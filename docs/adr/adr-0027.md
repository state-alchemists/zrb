# ADR-0027 — Semantic style names, and one `ZRB_THEME` that supplies every default

**Status:** Accepted

**Context.** Two problems, one under the other.

*Colour meaning was scattered.* `util/cli/style.py` exposed physical helpers (`stylize_yellow`, `stylize_cyan`, …) and a thin semantic layer that was a hardcoded alias of them. Around ninety call sites across twenty-one files called the physical helpers directly, so "warning is yellow" was re-decided in every file, and a user whose terminal already reserves yellow had no way to remap it.

*Nothing coordinated the defaults.* Styling spread across the LLM chat TUI (`LLM_UI_STYLE_*`, prompt-toolkit strings), the CLI colours, and the markdown renderer — which was not configurable at all, building a hardcoded `rich.Theme`. Restyling for a light terminal meant setting roughly forty env vars by hand.

**Decision.** Two layers plus a theme axis, all reusing the ADR-0023 precedence chain rather than inventing new machinery.

1. **Physical helpers stay literal.** `stylize_green`/`red`/`yellow` remain for cases where the colour *is* the convention — git diff added/removed/modified in `builtin/git.py` is left calling them deliberately.
2. **A fixed set of semantic helpers** — `stylize_muted`, `stylize_warning`, `stylize_error`, `stylize_success`, `stylize_highlight`, `stylize_info`, and the three todo slots — each backed by a `CLIStyleMixin` field and overridable through `ZRB_CLI_COLOR_*` / `ZRB_CLI_STYLE_*`. All call sites were migrated to these.
3. **A theme is a named palette.** `config/theme.py` holds `THEMES: dict[str, dict[str, str]]`, shipping `dark` and `light`. `dark` reproduces the historical hardcoded values exactly, so a default install is byte-for-byte unchanged. The module is pure data and imports no config, keeping `zrb.config` cycle-free.
4. **`ZRB_THEME` selects it, and every style knob takes its default from it** via `EnvField(default_factory=theme_default("KNOB_NAME"))`. Because `EnvField` reads the env var first, an explicit `ZRB_*` style var always wins over the theme. The per-knob `DEFAULT_*` constants were removed — the theme dict is now the single source of defaults.
5. **The stragglers became real knobs** — markdown link/heading/code styles, the title-bar background, the input prompt colour — which is what makes `light` coherent rather than half-applied.
6. **`register_theme(name, values)`** lets `zrb_init.py` add a theme. Values are merged onto `dark`, so a partial theme lists only what it changes instead of blanking every unspecified knob. An unknown `ZRB_THEME` warns and falls back to `dark`.

**Consequences.** Colour meaning is declared once and every consumer inherits an override; the whole tool restyles from one env var; individual knobs stay independently overridable. Costs: a semantic call pays one dict lookup (negligible for CLI output); adding a themed knob means adding its value to *both* built-in themes, guarded by a parametrized test asserting both palettes cover the same key set; and the palette dict mixes prompt-toolkit and Rich colour vocabularies, which is safe only because each key has exactly one known consumer.

**Alternatives rejected.** *Keep the semantic layer hardcoded* — leaves users unable to remap, which is the reported problem. *A module-level registry populated at startup* — avoids per-call config reads but needs an explicit initialisation order and a public mutate API, for no measurable gain on CLI output paths. *Expose raw ANSI integers as env vars* (`ZRB_CLI_COLOR_WARNING=33`) — precise and unusable. *Ship a "light preset" as a documented env-var dump* — no code, but forty variables to paste and no single toggle. *A Theme object threaded through the UI* — cleaner in isolation, but bypasses the `EnvField` precedence that already provides per-knob overrides, and every consumer would need rewiring. *Separate theme knobs per group* (`ZRB_LLM_THEME`, `ZRB_CLI_THEME`) — defeats the point of theming the whole tool at once.

**Where it lives.** `src/zrb/config/theme.py`, `src/zrb/config/mixins/theme.py`, `src/zrb/config/mixins/cli_style.py`, `src/zrb/config/mixins/llm_ui_styles.py`, `src/zrb/util/cli/style.py`, `src/zrb/util/cli/markdown.py`, `examples/themes/` (a full worked theme).
