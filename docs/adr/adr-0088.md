# ADR-0088 — A shared leaf module lives outside the package that happens to write it, not nested inside it

**Status:** Accepted

**Context.** `agent/run/runtime_state.py` (ambient `ContextVar`s: current UI, YOLO, hook manager, ...) and `agent/tool_result.py` (`ToolReturn` construction) had zero real dependencies on the rest of `zrb.llm.agent` — both were already documented as "leaf modules" in their own docstrings. But both lived *inside* the `zrb.llm.agent` package, because `run_agent()`/`create_agent()` are their main callers.

Importing either from outside — `zrb.llm.tool.ask`, `zrb.llm.tool.plan`, `zrb.llm.ui.base.ui`, `zrb.llm.tool.wrapper`, and others needed just a `ContextVar` getter or `tool_return()` — forced Python to run `zrb.llm.agent`'s package `__init__` first, since parent packages load before their submodules. That made `zrb.llm.ui`, `zrb.llm.tool.plan`/`ambient_state`, and `live_context.py` genuinely circular with `zrb.llm.agent` whenever they needed either leaf: five `# lazy: circular` workarounds existed for exactly this reason (a sixth, structurally identical, was in `hook/creator.py`, fixed separately by deferring its two eager importers instead — see `test_circular_import_allowlist.py`).

A closure walk (every module-level import, transitively, excluding `if TYPE_CHECKING:` blocks) found `zrb.llm.agent` and `zrb.llm.ui` each eagerly reach roughly 400 of this repo's ~430 `zrb.*` modules. At that density, a shared leaf module nested inside either one is reachable from many independent directions — `live_context.py` alone had 4 separate eager entry points into it from within `zrb.llm.agent`'s closure. A fix that only defers the one import site a comment happens to name doesn't remove the module from the closure, since the others keep it reachable; the "circular" tag just moves.

**Decision.** When a module has no real dependency on the package it's nested in — the two above qualified because both docstrings already said so, and both were verified to import nothing from `zrb.llm.agent` at all, not even lazily — and something *outside* that package needs it, move the module to a plain top-level sibling instead of deferring the import. `runtime_state.py` moved to `zrb.llm.agent_state`; `tool_result.py` moved to `zrb.llm.agent_tool_result`. Neither new location is nested under any package whose own `__init__` reaches back into `zrb.llm.agent`, so importing either no longer triggers `zrb.llm.agent`'s package `__init__` at all.

Every one of the 5 lazy imports this fixed was then hoisted to a real, non-lazy, module-level import — the "lazy: circular" tag didn't move to a new category, it was deleted, because there was no cycle left to defer around. Verified empirically both ways (hoisting each import in a scratch copy and confirming `ImportError` before the move, confirming success after) rather than by re-reasoning about the import graph by hand — the mechanism is subtle enough (partially-initialized modules, package-init ordering) that manual tracing missed a second, unrelated cycle hiding behind the first one during this same investigation.

**Consequences.** Five formerly-circular imports are now ordinary top-level imports with no special comment at all — not merely recategorized to a different `# lazy:` reason, genuinely not circular. `zrb.llm.tool.ask`, `tool.plan`, `tool.shell`, `tool.web`, `tool.delegate`, `tool.delegate_background`, `tool.file_observation`, `ui.base.ui`, and `tool.wrapper` no longer pull in `zrb.llm.agent`'s construction/run-loop machinery just to read a `ContextVar` or build a `ToolReturn` — a real reduction in eager-import closure size for all of them, not just an accounting change.

The cost is two more top-level modules under `zrb.llm` (`agent_state.py`, `agent_tool_result.py`) instead of two nested ones, and both are named for what they hold rather than for the package that used to contain them, so a reader has to know the convention (a `agent_*` top-level module is a leaf `zrb.llm.agent` depends on, not agent-construction logic itself) rather than finding it by package nesting alone.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Defer more of the importing side's own imports | This is what fixed `hook/creator.py`'s cycle, and it was tried here too as the first instinct; it doesn't work when the target module has many independent eager entry points (`live_context.py`'s 4), since fixing one or two leaves the others intact and the module never actually leaves the closure. |
| Leave the `# lazy: circular` comments as the permanent fix | They're not wrong, but they document a workaround for a misplaced module rather than removing the misplacement; every future consumer of the same leaf module inherits the same tax and has to rediscover the same "must stay lazy" rule. |
| Split `zrb.llm.agent.__init__` itself to import less eagerly | Would help, but `common.py`, `runner.py`, and `hook_agent.py`'s own eager imports are each load-bearing for the package's real job (constructing and running an agent); trimming those risks breaking the actual agent-construction/run-loop machinery for a problem that, for these two modules, was really about *their* placement, not the package's. |

**Where it lives.** `src/zrb/llm/agent_state.py`, `src/zrb/llm/agent_tool_result.py`, and every former importer of `zrb.llm.agent.run.runtime_state` / `zrb.llm.agent.tool_result` (now `zrb.llm.agent_state` / `zrb.llm.agent_tool_result`). `test/architecture/test_circular_import_allowlist.py` (empty allowlist, with the closure-walk finding in its own docstring). ADR-0033 (the lazy-import discipline this decision works alongside, not a replacement for — most `# lazy:` imports are correctly deferring genuine third-party weight, not standing in for a misplaced module).
