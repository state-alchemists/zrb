# ADR-0087 — Web server binds to loopback by default; non-loopback is an explicit, warned-about choice

**Status:** Accepted

**Context.** `start-server` hardcoded `host="0.0.0.0"` in the uvicorn `Config`, with no config knob to change it. Combined with `WEB_AUTH_ENABLED` defaulting off and a default super-admin password of `admin`, the documented "local development" server was in fact reachable from any interface — LAN, container network, or otherwise — while able to execute shell commands and user-defined tasks through the unauthenticated `default_user`. An external review flagged this as the project's most concrete operational-safety issue.

**Decision.** `WEB_HTTP_HOST` (`src/zrb/config/mixins/web.py`) defaults to `127.0.0.1`; `start_server` (`src/zrb/runner/cli.py`) binds uvicorn to it instead of a hardcoded address. Binding elsewhere requires setting `ZRB_WEB_HTTP_HOST` explicitly. The server never refuses to start on a non-loopback bind — that would break existing intentional LAN/container deployments — but `_warn_if_insecure_bind` prints a loud stderr warning for either of two distinct risks a non-loopback bind can still carry: `WEB_AUTH_ENABLED` off (unauthenticated exposure), or auth on but `WEB_SUPER_ADMIN_PASSWORD`/`WEB_SECRET_KEY` still at their default, publicly-documented values (an authenticated deployment anyone who read the docs can still walk into). The two are surfaced as separate messages rather than folded into one, since a reader fixing the first should not assume the second is also handled.

**Consequences.** The out-of-the-box experience (`zrb server start` with no config) is now actually local-only, matching what the docs already claimed. A deliberate network-exposed deployment still works unchanged, just requires one explicit env var, and gets a warning for whichever risk it still carries rather than failing silently into an open door. Cost: one more env var to document; existing deployments that relied on the implicit `0.0.0.0` bind (with no `ZRB_WEB_HTTP_HOST` set) will need to set it explicitly after upgrading — a deliberate breaking change for a security default, not preserved via alias since there was no prior config key to alias.

**Alternatives rejected.** *Refuse to start on non-loopback + auth-off* — rejected: would break existing deployments that accept the exposure knowingly (e.g. behind a reverse proxy or in an isolated container network with no other auth layer), turning a safety net into an outage. *Leave the default at `0.0.0.0` and only add the warning* — rejected: a warning nobody reads on an already-insecure default doesn't fix the default; the point is that reaching the insecure state now requires one explicit, legible action. *Gate the warning behind a new config flag* — rejected: it is only ever emitted, never controls behavior, so a toggle would just be an extra knob to reach the same one line of stderr.

**Where it lives.** `src/zrb/config/mixins/web.py` (`WEB_HTTP_HOST`), `src/zrb/runner/cli.py` (`start_server`, `_warn_if_insecure_bind`), `docs/advanced-topics/web-ui.md`, `docs/configuration/env-vars.md`.
