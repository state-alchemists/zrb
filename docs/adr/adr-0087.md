# ADR-0087 — Web server binds to loopback by default; a non-loopback bind must be secured or the server refuses to start

**Status:** Accepted

**Context.** `start-server` hardcoded `host="0.0.0.0"` in the uvicorn `Config`, with no config knob to change it. Combined with `WEB_AUTH_ENABLED` defaulting off and a default super-admin password of `admin`, the documented "local development" server was in fact reachable from any interface — LAN, container network, or otherwise — while able to execute shell commands and user-defined tasks through the unauthenticated `default_user`. An external review flagged this as the project's most concrete operational-safety issue.

**Decision.** `WEB_HTTP_HOST` (`src/zrb/config/mixins/web.py`) defaults to `127.0.0.1`; `start_server` (`src/zrb/runner/cli.py`) binds uvicorn to it instead of a hardcoded address. Binding elsewhere requires setting `ZRB_WEB_HTTP_HOST` explicitly.

A non-loopback bind that is not actually secured fails closed: `_refuse_insecure_bind` prints the reason to stderr and exits `1` before the app is built, for either of two distinct risks: `WEB_AUTH_ENABLED` off (unauthenticated exposure), or auth on but `WEB_SUPER_ADMIN_PASSWORD`/`WEB_SECRET_KEY` unusable — empty, still at their default, publicly-documented values, or shorter than 12 and 32 characters respectively (an authenticated deployment anyone who read the docs can still walk into).

Loopback is decided by parsing the address (`ipaddress.ip_address(host).is_loopback`), so any spelling of loopback passes and a hostname that cannot be proven loopback-only is treated as exposed. The check inspects the effective `WebAuthConfig`, not `CFG` alone, so programmatic overrides are honored. There is deliberately no override flag.

The two risks are surfaced as separate messages, and every failing credential is listed at once, so a reader fixing the first problem is not refused again for the next.

**Consequences.** The out-of-the-box experience (`zrb server start` with no config) is local-only, matching what the docs claim. A deliberate network-exposed deployment requires one explicit env var plus real credentials; the supported alternative is to bind loopback and put one's own proxy in front. Cost: one more env var to document; deployments that relied on the implicit `0.0.0.0` bind must set `ZRB_WEB_HTTP_HOST` explicitly (not preserved via alias, since there was no prior config key to alias), and an existing unauthenticated public deployment stops starting until auth is enabled with unique credentials.

**Alternatives rejected.** *Warn but never refuse on a non-loopback bind* — the earlier behavior: a warning the operator scrolls past still served task execution on the documented `admin`/`admin` credentials and default signing key, so the safety net was only prose. *Leave the default at `0.0.0.0` and only add a check* — a check on an already-insecure default doesn't fix the default; the point is that reaching an exposed state requires one explicit, legible action. *An override flag to start anyway* — it would recreate the warn-only path behind one more knob; binding loopback behind a proxy already covers the legitimate case.

**Where it lives.** `src/zrb/config/mixins/web.py` (`WEB_HTTP_HOST`), `src/zrb/runner/cli.py` (`start_server`, `_refuse_insecure_bind`), `test/runner/test_cli.py`, `docs/advanced-topics/web-ui.md`, `docs/configuration/env-vars.md`.
