# ADR-0130 — Compaction hands over a briefing, and the tail is a handover too

**Status:** Accepted

**Context.** Measured on a real session (2026-10-24, a 375,000-token window, compaction at 341,603 tokens and 366 messages): the compacted history came back as one message of 94,097 tokens, of which the summary was 6,494 and a "verbatim tail" 87,603. The banner said `chunk 1/1 (366 messages)` — every message summarized, no tail kept — and then `Conversation compressed (87815/375000)`, which was true and answered nothing: whether a tail had survived could only be established by reading the artifact afterwards.

Looking for the 87,815 turned up the defect underneath it. `_find_first_user_message` skips prior summary parts but not the *rendered tail* a previous compaction wrote in the same turn, so compacting an already-compacted history re-appended the whole tail it had just replaced — 88,000 tokens of it — beside the new summary. On the same real history with the tail ceiling in place, the replacement measured 91,527 tokens until that was fixed and 17,988 after. Two compactions in a row could not shrink the history to what the summary said.

The schema had its own problem, visible in the summary this work started from. Six sections (`overall_goal`, `active_constraints`, `active_skills`, `key_knowledge`, `work_log`, `task_state`) restate one another; none says what was happening at that moment; and the `[DONE]`/`[IN PROGRESS]`/`[TODO]` vocabulary cannot express "ready, and nobody has started it" or "waiting on the user", so an item whose precondition had been satisfied for a day still read as a pending task. Liveness words — "current focus", "awaiting an answer" — carried no time, so a resumed session read hours-old labels as the present.

opencode's compaction is the reference that shaped the response: `DEFAULT_KEEP_TOKENS = 8_000` of tail against `SUMMARY_OUTPUT_TOKENS = 4_096` of summary, each tool result cut to `TOOL_OUTPUT_MAX_CHARS = 2_000`, and a template of Objective / Important Details / Work State (Completed, Active, Blocked) / Next Move / Relevant Files, with explicit rules for merging a prior summary forward.

**Decision.**

1. **The snapshot is a briefing, in the order a resumed agent reads it.** `where_we_are` (the world as `git status` would show it), `now` (the last turn: action, command, result), `next` (numbered), `open_questions` (asked, unanswered, with the time and the options), `done` (one line per finished workstream, with its PR and hash), `decisions` (decision, reason, where it lives), `landmines` (gates, conventions, traps), `constraints` (the user's standing rules), `files` (`path: why it matters`), `active_skills` (names; bodies are re-attached separately).

2. **Every `next` item carries a state:** `[READY]`, `[BLOCKED: what]` or `[WAITING: on whom]`.

3. **No fact is stated twice, every liveness claim names the time it was true, and the prompt forbids mentioning compaction.** A briefing that repeats itself costs the room it needs to say what is happening.

4. **The prompt and the code are held together by a test.** `test_summary_schema_contract.py` reads the Output Schema out of `conversational_summarizer.md` and fails when it and `_SUMMARY_SECTIONS` disagree, and when a section that resumes the work appears in `_SUMMARY_DROP_ORDER`.

5. **The tail has an absolute ceiling, and the ceiling binds the retry too.** `LLM_HISTORY_TAIL_MAX_TOKENS` (24,000) applies on top of `LLM_HISTORY_TAIL_BUDGET_RATIO`, whichever is smaller; the fallback budget is capped the same way, because a cap a looser retry could walk past is not a cap.

6. **The tail is measured as content, not as a request.** `count_tail_tokens` asks the limiter for `count_content_tokens`, which ignores the usage anchor a response carries: that anchor reports the input the provider charged for the request that produced the response, which covered the whole history up to it. Read as the size of a *suffix*, it returns the unsplit history's size however much the suffix dropped — and since compaction runs only once the history is at the threshold, no tail ever fit and every compaction kept nothing, ceiling or no ceiling. Measured on the real 414-message, 345,387-token history: 0 messages kept by the anchored count, 62 messages and 23,977 tokens by the content count. A counting subclass keeps its own `count_tokens`, for the same reason `_can_binary_search` declines to trust it.

7. **Each tool result in the rendered tail is cut to 2,000 characters**, with the number omitted stated in its place. The replaced messages reach the verbatim archive in full, so what the tail loses is output nobody reads again, not evidence.

8. **The banner prints the split when it is decided:** `Summarizing N messages (X tokens); keeping M verbatim (Y tokens)`, with the number read added when a tail is kept (`reading all T`, decision 12), because what is kept stopped being what is read.

9. **Compaction's own output is not the user speaking.** `_find_first_user_message` skips summary parts and rendered-tail parts alike, so a compaction of a compacted history carries the user's words forward without carrying the previous handover a second time.

10. **The tail is measured in the currency it is spent in, and the whole history in its own.** The clip in decision 7 happens before the tail is sent, so it has to happen before the tail is measured. Budgeting on the unclipped messages kept a tail that measured 22,614 tokens in hand and sent 5,358 on a real 76-message history, and 23,727 against 15,111 on a 406-message one: the budget was never spent, and the banner reported the number that was not sent. `count_tail_tokens` now renders through `render_verbatim_messages` and counts that. The whole-history question is asked the other way round, by `count_history_tokens`: at split zero nothing is converted to text, and a tool-heavy history renders to a fifth of itself, so the rendered question answers "it fits" about a history the next request pays for in full — a compaction that summarizes nothing, leaves the history over the threshold, and tries again next turn, each attempt reporting success. The index-zero check therefore asks the content count and the suffix scan asks the rendered one. A pending deferred call rides along in rendered form rather than switching the currency inside a suffix: the difference is a few tokens on one message, and switching it broke the monotonicity the bisected scan depends on — measured, a shorter suffix could count higher than the longer one it was cut from.

11. **A split that keeps nothing although the newest message fits says so.** Keeping nothing is correct when the newest message alone overruns even the retry budget, and silent otherwise; the run that kept nothing on every compaction for months printed a zero in the banner's ordinary style and looked healthy. The check measures the newest message with `count_content_tokens` directly, so a regression inside `count_tail_tokens` cannot hide behind the same broken number.

12. **The snapshot is written from the whole conversation, and the tail is still sent verbatim.** The split decides what is replaced, not what is read, so the summarizer saw a conversation that ended at the boundary: on a real compaction its `<now>` read "started reading the checkpoint path" and its `<next>` asked for a review verdict the kept tail had already delivered, with the pull request the tail built, reviewed and merged in between. The reader of a briefing takes `<where_we_are>`, `<now>` and `<next>` as the present, so a boundary-stale snapshot is a to-do list of finished work. The summarizer now reads `to_summarize + to_keep`; the replacement still drops only `to_summarize`, the archive still holds only what was replaced, and the tail is unchanged. The added input is bounded by the tail ceiling (decision 5, 24,000 tokens), and `chunk_and_summarize` already bounds every request at 90% of the summarizer model's own window, so reading the tail cannot overrun the context of the model that summarizes. The price is duplication — the newest turns appear twice, once as prose and once verbatim — so the prompt now says the tail is attached after the snapshot, that `<where_we_are>`, `<now>` and `<next>` describe the end of the conversation rather than an earlier moment, and that the tail is not to be transcribed: the snapshot is the part the verbatim tail cannot tell.

**Consequences.** On the real 316-message, 304,987-token history the replacement is 17,988 tokens — 94% freed instead of 70% — and the history no longer grows back through the tail it already replaced. With the tail measured as content, a compaction of a 414-message, 345,387-token history now keeps 62 messages and 23,977 tokens beside the summary (18,923 tokens in that run) instead of the summary alone, so what the next turn re-reads is roughly 43,000 tokens of a 375,000-token window. Decision 10 supersedes those tail numbers rather than contradicting them: measured after it, the same two real histories keep 74 of 76 messages at 16,812 tokens and 80 of 406 at 23,877, so a compaction keeps more conversation for the budget it was already allowed. The summary is the durable artifact and the tail is a few turns of exact conversational context, which is the balance opencode keeps at a smaller scale (8,000 + 4,096 against a 24,000-token ceiling and an 18,593-token summary cap here). The costs are real: a single message larger than the ceiling can no longer be kept verbatim (it is summarized instead; a pending deferred call is still widened into native form, because pydantic-ai resumes it by matching a live call), long tool output in the tail loses its exact bytes, and a model that ignores the schema now fails more sections — `_is_state_snapshot_well_formed` warns rather than failing the compaction, which is the reason the contract test exists.

**Alternatives rejected.**

- *Keep the ratio alone* — measured at 87,603 tokens of tail on a real session, twenty times the room the summary got.
- *Keep tool output lossless in the tail* — a 350,414-character tail of test logs, PR bodies and changelog dumps, re-read on every later turn.
- *Add two sections to the existing six* — the six already overlapped (`overall_goal`, `work_log` and `task_state` restated the same events); a seventh and eighth would not have removed the restatement or added the missing "what is happening now".
- *Summarize the tail as well* — the tail is the one part of the history with no information loss; paying tokens for it is the point.
- *Re-append the previous opener as "the original goal"* — this is what the code did, and it measured 88,000 tokens of a summary-of-a-summary at every chain of compactions.

**Where it lives.** `src/zrb/llm/prompt/markdown/conversational_summarizer.md` (the schema and its rules), `src/zrb/llm/summarizer/history_summarizer.py` (`_SUMMARY_SECTIONS`, `_SUMMARY_DROP_ORDER`, `_find_first_user_message`, the split banner, `_warn_when_the_split_kept_nothing`), `src/zrb/llm/summarizer/history_splitter.py` (`tail_max_tokens`, `tail_budgets`, `_capped_budget`, `count_tail_tokens`, `count_history_tokens`), `src/zrb/llm/message_text.py` (`TAIL_TOOL_OUTPUT_LIMIT`, `render_verbatim_messages`), `src/zrb/llm/config/limiter.py` (`count_content_tokens`), `src/zrb/config/mixins/llm_content.py` (`LLM_HISTORY_TAIL_MAX_TOKENS`), `test/llm/summarizer/test_summary_schema_contract.py`, `test/llm/summarizer/test_summarizer_history_splitter.py`, `test/llm/summarizer/test_tail_measured_as_sent.py`, `test/llm/summarizer/history_processor/test_verbatim_tail.py`, `test/llm/summarizer/history_processor/test_summary_handoff.py`.
