# ADR-0072 — `LLMTask` and `LLMChatTask` expose the same first-class knobs

**Status:** Accepted

**Context.** The two task classes had drifted into different configuration surfaces, and users worked around the gaps in ways that misused the APIs that did exist.

*Hooks.* Only `LLMChatTask` had a task-level registration API. It builds a **fresh** `HookManager` per execution and replays registered factories onto it, while `LLMTask` holds a **persistent** manager defaulting to the process-wide singleton. Registering hooks on an `LLMTask` after construction had no first-class path.

*Permissions.* `LLMTask` accepted a `permissions=` argument; `LLMChatTask` did not, and did not forward one to its inner task. The only programmatic route was to register a "hook factory" that ignored its `HookManager` entirely and exploited the fact that factories run synchronously before the agent run, just to set a ContextVar at the right moment. It worked, it read like a `SessionStart` hook, it was neither a hook nor tied to any event, and it repeatedly caused confusion — including in the examples that carried the boilerplate.

**Decision.** One verb per concern, on both classes.

- **`append_hook_factory(*factory)`** where each factory is `Callable[[HookManager], None]`. `LLMChatTask` keeps replaying onto its per-execution manager. `LLMTask` applies immediately, and — to keep task hooks isolated by default — the first registration swaps the shared global default for a fresh per-task manager. A manager passed explicitly to the constructor is never swapped, so opting into the global one stays possible.
- **`permissions` and `sandbox` are constructor arguments *and* read/write properties on both classes**, with `LLMChatTask` forwarding to its inner `LLMTask`. `history_manager` gets the same symmetry — along with `conversation_name`/`render_conversation_name`, it's also readable as one group via a `history_config` property (`HistoryConfig`, `task/history_config.py`) on both classes, computed fresh on every read (never cached, so `history_manager`'s setter stays immediately visible through it). This is an internal forwarding convenience for `chat/execution.py`'s wrap boundary — `_create_llm_task_core` builds the inner task's history knobs via `dataclasses.replace(llm_chat_task.history_config, ...)` instead of listing each field, so a future history-related field that's a pure passthrough only needs adding to `HistoryConfig` and wherever it's consumed (`task/history.py`), not a fourth site at the wrap boundary. It does not change the public constructor/property surface described above. Precedence: an explicit argument beats `ZRB_LLM_PERMISSIONS`, which beats the ambient ContextVar set by a parent run — with plan mode's read-only preset still overriding all of them while active.
- The accepted input shapes are named types rather than `Any`, and the policy classes stay frozen dataclasses. Immutability is load-bearing, because the plan-mode policy is a shared module-level singleton propagated through a ContextVar and snapshotted per tool call; the read/write properties provide the "change it later" affordance by reassigning a new frozen instance, never by mutating one.

**Consequences.** One mental model works on both task types even though the implementations differ underneath — replay-per-execution versus apply-once — and the common case ("this chat task runs under this policy") is a one-liner with no ContextVar knowledge required. `LLMTask` hooks are leak-free by default rather than silently mutating shared state. The ContextVar remains the mechanism and the documented escape hatch for *dynamic* policies chosen at runtime, and stays the channel for sub-agent inheritance. The price of hook isolation is that an `LLMTask` registering a factory no longer participates in the global filesystem hook set unless explicitly constructed with the global manager — called out in the method docstring.

**Alternatives rejected.** *Apply `LLMTask.append_hook_factory` to the global default* — symmetric API, asymmetric safety: it silently mutates state shared by every task. *Defer registration to `HookManager.scan()`* — the run path never scans, so registrations would never fire. *Keep the hook-factory workaround for permissions and document it well* — documenting a workaround is strictly worse than removing the need for one, and the "looks like a `SessionStart` hook" confusion is inherent to the shape, not the wording. *A dedicated `set_permissions()` method* — inconsistent with the sibling property-based setters.

**Where it lives.** `src/zrb/llm/task/llm_task.py`, `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/task/chat/building.py`, `src/zrb/llm/task/history_config.py`, `src/zrb/llm/task/chat/execution.py`, `examples/plan-mode/`, `examples/permission-policy/`.
