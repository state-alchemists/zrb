# ADR-0129 — A lazy registration holds the configuration it was given until it loads

**Status:** Accepted

**Context.** Every `zrb` run imports `zrb.builtin`, so the built-in chat task — an `LLMChatTask` built out of pydantic and pydantic-ai — is registered as a `LazyTask` stand-in and its module loads only when a command line addresses it. That deferral is worth about 0.2 s per command, and it survives only as long as nothing else resolves the stand-in early.

A `zrb_init.py` that customizes the chat does exactly that. Adding a tool, a hook factory or a tool policy needs the task object, and `from zrb.builtin import llm_chat` returns the *resolved* task, so the project pays the import the stand-in exists to avoid — on every command, including the ones that never open a chat. Measured on a real init script: `zrb --help` at 0.39–0.43 s, and 0.21–0.22 s once the same customization stopped importing the task. The deferral was in place and undone by its first user.

The two goals are not in conflict. The init script needs the customization to happen, not to happen *now*.

**Decision.**

1. **`LazyTask.on_resolve(configure)` registers the work instead of the task.** The callback runs on the real task when it loads, in registration order, exactly once, before the first caller sees it. It returns the stand-in, so an init script reads as a list of declarations.

2. **Registering after a resolution applies immediately.** A dispatch may already have resolved the stand-in before an init script ran; a queued callback there would never run, and the failure would be a chat task silently missing its tools.

3. **The task is configured before it is published.** The callbacks run before the resolved task is cached, so no caller observes it in the state its declaring module left it in. A callback that raises caches nothing, and the next caller retries the load and the configuration rather than using a half-configured task.

4. **The stand-in is reachable without resolving it.** `from zrb.builtin.llm.deferred import llm_chat` yields the `LazyTask`. `from zrb.builtin import llm_chat` still yields the real task, because an init script written against it has to keep working — the point of the change is to give that script a cheaper option, not to break it.

**Consequences.** An init script configures the chat for the price of a lambda, and `zrb --help` in a project that customizes the chat costs what it costs in a project that does not. The configuration runs at dispatch instead of at startup, which is the only ordering the deferral allows: the callback cannot read the task while the script is still executing, and it should not need to — it is handed the task it is meant to configure. The stand-in gains one list, so `resolve()` is no longer a pure import; anything that resolves it inherits the project's configuration, which is what the registry dispatching the task requires anyway.

**Alternatives rejected.**

- *Keep importing the task* — the status quo: every command pays ~0.2 s for a customization that only the chat uses, and the deferral earns nothing for the projects that need it most.
- *Return the stand-in from `zrb.builtin.__getattr__`* — `llm_chat.append_tool(...)` then raises `AttributeError` in every existing init script, at import time, before the CLI starts. A breaking change to fix a cost.
- *Mutate a copy and register that* — the registry would dispatch the original, unconfigured task; identity with the registered task is the whole contract.
- *A configuration file listing tools and hooks* — a second configuration surface, in a format that cannot express a tool factory, for something the init script already writes as code.

**Where it lives.** `src/zrb/task/lazy_task.py` (`on_resolve`, `resolve`), `src/zrb/builtin/llm/deferred.py` (the stand-in an init script imports), `test/task/test_lazy_task_on_resolve.py`.
