# ADR-0118 — A skill declares the skills it preloads, and one activation renders them together

**Status:** Accepted

**Context.** Five built-in utility skills (`/debug`, `/refactor`, `/review`, `/testing`, `/research`) opened with a prose instruction: *"Ensure `core-coding` is activated… re-activate via `ActivateSkill('core-coding')`."* The skill's body arrives as the user's message when the slash command expands, so the model then had to spend an entire model request activating the dependency before it could start the work — two requests for every invocation, and one that exists only to repeat a fact the skill already knew.

The prose also drifted from the catalogue. `core-research` told the model to activate `core-coding` for deep code reading, while `core-coding`'s own description said it activates when the turn *changes* source, test, or config files. A read-only evaluation therefore met an instruction its trigger said did not apply.

The formats leave no field to borrow. The Agent Skills specification has exactly six frontmatter fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`); Claude Code preloads skills only for **subagents** (`skills:`, first 32 names); opencode puts vendor behavior under namespaced `metadata` keys. zrb already rendered task-level preactivated skills (`active_skills` → *Active Skills (Fully Loaded)*), but nothing was per-skill and nothing could happen mid-turn.

**Decision.**

1. **A skill declares its dependencies in frontmatter.** `preload:` accepts a YAML list or a comma-separated string and becomes `Skill.preload`. It is additive and optional.

2. **Resolution is a soft, bounded walk.** `resolve_preload` renders dependencies deepest-first, in declaration order, deduplicated and cycle-safe, with a depth cap of three. Only model-invocable skills load; an unknown name, a user-only skill, a cycle, or a chain past the cap becomes a problem string.

3. **One activation returns every block.** Both paths — the slash command built by `skill_command_factory` and the model's `ActivateSkill` call — use `build_activation_block`. Each dependency is its own `<ACTIVATED_SKILL name="…" preloaded-by="…">` block ahead of the activating skill, so the model can tell which body came from which declaration.

4. **A failed declaration never fails the skill.** The skill still activates, followed by a `[SYSTEM SUGGESTION]` naming what did not resolve. Preload is context, not permission.

5. **The rendered body drops the YAML frontmatter.** Frontmatter is metadata for the loader; re-sending it repeated the description as prose and cost tokens on every activation.

6. **The built-in utility skills use it, and keep one fallback sentence.** `/debug`, `/refactor`, `/review`, `/testing` declare `preload: [core-coding]`; `/research` declares `[core-research]`. The body still says "if that block is missing, activate it now", because a harness that ignores the field (Claude Code silently ignores unknown frontmatter fields) needs the old path.

7. **A skill that must also upload to claude.ai uses `metadata: {zrb/preload: "…"}`.** Those surfaces reject unknown top-level keys; the `metadata` map is the portable form.

**Consequences.** A utility skill now costs one model request instead of two, and its dependency body is in the same context window as the task that needs it. The activation response is larger — bounded by the depth cap and the 500-line guidance for a skill body — and the dependency stays in context for the conversation, as every activated skill already does; nothing unloads it. Under Claude Code the field is ignored, so the fallback sentence still costs a round trip there, and a skill that relies on preload must keep that sentence to remain portable.

**Alternatives rejected.**

- *Keep the prose instruction* — the status quo: non-deterministic (a model may decide it already remembers the layout), one wasted request, and it had already drifted out of sync with the trigger.
- *Jinja or another template expansion* — skill bodies are user-authored content; a template evaluator adds an injection surface and indirection to express a one-line list.
- *`requires:` / a hard dependency* — a missing dependency must not break `/refactor`; the skill is useful without its methodology body, and a hard failure would make a user-visible command depend on catalogue state.
- *Only `metadata`* — portable, but verbose in zrb's own skills and invisible to a reader scanning the frontmatter; kept as the documented portability form instead.
- *Fork into a subagent that preloads skills (Claude Code's `skills:` shape)* — changes the context the skill runs in. `context: fork` is an independent axis in zrb, and a skill may want its dependency in the main conversation.
- *Auto-activate at slash-command dispatch only* — `ActivateSkill` is a second entry point, and a model may activate a skill the user did not type.

**Where it lives.** `src/zrb/llm/skill/preload.py` (resolution and the problem line), `src/zrb/llm/skill/activation.py` (the block, frontmatter strip), `src/zrb/llm/skill/manager.py` (`Skill.preload`, frontmatter parsing), `src/zrb/llm/tool/skill.py`, `src/zrb/llm/custom_command/skill_command_factory.py`, `src/zrb/llm_plugin/skills/*/SKILL.md`, `test/llm/skill/test_skill_preload.py`, `test/llm/tool/test_skill.py`, `test/llm/custom_command/test_skill_command_factory.py`.
