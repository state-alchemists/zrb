# ADR-0108 — The main agent and a delegated sub-agent message each other through the live-session registry, and every message names its sender

**Status:** Accepted

**Context.** ADR-0083 gave a delegated sub-agent a live, in-memory session (`LiveSubAgentSessionRegistry`) that a *human* can message from the TUI: `send_message` injects text into the in-flight run (`steer_into_live_run`, ADR-0078) or queues it and starts a continuation when the session is idle. The reverse direction exists in exactly one case: a cancelled-then-continued sub-agent hands its latest response to the main agent through `parent_ui.submit_message` (ADR-0083 Phase E).

Neither agent can start a message. The main agent has no tool to talk to a sub-agent it delegated to — it can only wait for the envelope — and a sub-agent has no way to ask the main agent a question or report progress before it finishes. Claude Code lets both happen. The transport already exists in zrb; what is missing is a tool on each side, and a way for the receiver to tell who is speaking, because a message that arrives as a plain user turn is indistinguishable from the human.

**Decision.** Two tools over the existing delivery paths, with provenance on every message.

- `send_message_to_subagent(agent_id, text)` — main agent only. Calls `live_subagent_session_registry.send_message`, so delivery keeps its current semantics: injected live when the sub-agent's turn is in flight, queued and continued when idle. An unknown `agent_id` returns a `[SYSTEM SUGGESTION]` error naming the live agent ids (ADR-0057).
- `send_message_to_parent(text)` — attached to every sub-agent built from a prompt-based definition, so it exists only inside a delegated run. A definition given as `agent_instance` or `agent_factory` is used as is (ADR-0083) and does not get it: adding a tool would mean mutating the user's agent. Calls `parent_ui.submit_message`, which steers into the main agent's live turn or queues it as the next one — the channel Phase E already uses.
- **Provenance is a header on the text.** The receiver sees `[message from sub-agent "<name>" (<agent_id>)]` or `[message from the main agent]` ahead of the body. The sender's identity comes from the run's own UI (`current_ui` is the sub-agent's `BufferedUI`, which knows its `agent_id` and session), never from an argument the model could spoof. A typed `InputProvenance` was not added: a non-keyboard source does not steer a live run (`submit_user_message_via_queue`), and steering is the point.
- **Ping-pong is bounded.** A per-session counter limits agent-originated messages to `LLM_AGENT_MESSAGE_LIMIT` (default 20) per delegation; past it the tool returns an error telling the sender to finish or wait. A human message resets nothing — the cap exists for agent-to-agent loops only.
- **Phase E stays bare.** The cancelled-then-continued report is the user's own follow-up conversation reaching the main agent, and ADR-0083 rejected wrapping it. That path keeps its wording; the new tools wrap because their sender is an agent the receiver must tell apart from the user.

**Consequences.**

- The main agent can steer a background sub-agent mid-run and a sub-agent can ask a question without ending. The second is useful only when the parent is not blocked: synchronous `delegate_to_agent` holds the parent's turn, so a message a sub-agent sends then lands in the parent's *next* turn. Background delegation (ADR-0069) is the case this serves.
- A message can start a main-agent turn the user did not type, as Phase E already can.
- The receiver treats the header as untrusted data about the sender, not as authority: it grants no permission and bypasses no approval (ADR-0069).
- A sub-agent resumed as its own chat (`create_llm_chat_task`, `/load` persona swap) has no parent to message, so it is not given `send_message_to_parent`; the user is the one talking to it.
- Delivery is in-memory and process-scoped, like the registry. A message to a session that no longer exists fails loudly.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| A new broker/queue object between agents | `steer_into_live_run`, `MessageQueue` and `submit_message` already are the queue, with the live-versus-queued split solved (ADR-0078). A second queue would need that solved again. |
| Send as an unmarked user turn | The receiver cannot tell an agent from the human, so a sub-agent's question reads as a user instruction. |
| Sender id as a tool argument | The model could name any sender; identity is ambient state (ADR-0004). |
| No cap | Two agents answering each other's replies never terminate on their own. |
| Let a sub-agent message a sibling | No use case yet; the topology stays a tree, and a sibling channel can be added when one appears. |

**Where it lives.** `src/zrb/llm/subagent/live_session.py` (delivery, counter), `src/zrb/llm/tool/delegate_message.py` (the main agent's tool), `src/zrb/llm/subagent/parent_message.py` (the sub-agent's tool, kept in the sub-agent package so `building.py` imports it without a cycle), `src/zrb/builtin/llm/chat.py` (main-agent registration), `src/zrb/llm/subagent/building.py` (sub-agent registration), `src/zrb/llm/ui/buffered_ui.py` (`agent_id`, `session_id`), `src/zrb/config/mixins/llm_content.py` (`LLM_AGENT_MESSAGE_LIMIT`).
