# ADR-0136 — The injected journal index is ranked, not sliced from the top

- **Status:** Accepted
- **Date:** November 1, 2026

## Context

`<journal-index>` is the only journal file injected unprompted, and it is capped by `LLM_JOURNAL_INDEX_MAX_CHARS`. The cap was applied as `content[:limit]`, then cut back to a line boundary — a head-first slice, on the theory that the index is ordered most-durable-first, so cutting from the end drops the least durable part.

That theory stopped holding once the `## User` section grew. The order protects *sections from each other*, but a slice cannot see section boundaries: it spends the whole cap inside whichever section comes first. Measured on a real 15,167-character journal on 2026-11-01, a 2,500-character cap kept one section out of seven — `## User`, cut mid-section — and none of `## Constraints` (13 pinned lines), `## Agent`, `## Recent`, `## Directories`, or `## Recent Insights`. Every note marked as holding every turn was absent from the prompt, and the block said nothing about it: the overflow summary counted hidden *note categories*, so a section lost whole read as a handful of notes.

Two further facts about the same index:

- **The catalog duplicates the claims.** `## Recent Insights` was 27 lines and 3,460 characters — 23% of the index — and 25 of those 27 titles named notes whose claim (the note's `hud_line`) already appeared in a HUD section above. Inside the injected block that is one fact stated twice, the second time in the weaker form.
- **The cap did not bound the block.** The limit applied to the slice of the file, and the header (614 characters) and the overflow summary (~700) were added on top, so a 2,500-character cap produced a 4,049-character block. The knob did not describe the cost it named.

## Decision

The cap is spent by **rank**, not by position, in a new pure module `src/zrb/llm/prompt/journal_core.py`:

1. a pinned line, wherever it sits — a note whose `hud_line` is pinned is one that said it holds every turn;
2. a claim, `- text ([note](path))` — the readable half of a note;
3. a line linking into a category index (`## Directories`);
4. anything else — a catalog title, a footer, a hand-written line.

Within one rank the sections **take turns**: each round every section with a line of that rank left takes one, so a section holding twice the lines does not take twice the cap. A `## Recent Insights` title is dropped only once the claim for the same note is actually in the block — a claim too long to fit leaves the short title as the note's only trace.

The index's own **preamble** — the title, and any hand-written lines above the first `## ` heading — is one more block at rank 4 rather than fixed text, so no part of the file can push the block past the cap on its own.

The overflow note names the **sections** that lost lines, ordered by the best line each section lost and then by how many — counting alone would let the catalog, whose lines are the weakest in the index, lead the note every time it is the longest — and counts any pinned line that did not fit. The content stops a quarter of the cap short so the note has room, and the note then takes whatever the content could not use. Under a cap too small for the sentence the note degrades to a bare `(...more)`; under a cap that keeps no line of the index, or cannot hold even the marker, `plan_index_core` returns nothing and `render_journal_index` injects no block at all — a truncated index that does not say it is truncated reads as the whole index, and a wrapper of instructions over an empty index costs prompt to say nothing.

Two structural rules hold the cap, and they are in the decision because the four review findings on the first draft were each one of them being violated:

- **The cap is measured, never predicted.** A line is kept only when the text re-rendered with it still fits. There is no second copy of the layout arithmetic to drift from the emitter: the first draft charged a block's heading and separator with a formula (`_open_cost`) and emitted them with another (`_emit`), so a preamble bigger than the cap was charged and could not be trimmed.
- **The document is parsed by its writer.** `journal_index` owns what a heading, a claim (a trailing `([note](path))`) and a catalog entry (`- [title](path)`) are, and this module imports those predicates rather than reading the rendered text again with regular expressions of its own. The first draft's private copies were cruder: it suppressed any line that linked a note whose claim was kept, which deleted hand-written content that exists nowhere else.

`DEFAULT_LLM_JOURNAL_INDEX_MAX_CHARS` moves from 2,500 to 3,600 — not to buy more prompt, but to describe the one already being spent: the old behaviour injected 4,049 characters while claiming a 2,500 cap, and 3,600 buys a 4,112-character block. Since the pins alone are ~2,400 characters, 2,500 could hold them and almost nothing else.

## Consequences

On the measured journal the block now carries four sections, all 13 pinned lines, and a pointer at the same ~40-token cost as before (4,112 characters against 4,049). A session's first turn sees the constraints that hold every turn, which it previously never saw.

Costs and limits: the ranking is structural, not semantic — it knows a line is pinned and that a claim outranks a title, but not which claim this conversation is about; that judgement is `SearchJournal`'s and, per turn, the claims block's (`journal_claims.py`). A journal with a large pinned set will still spend most of the cap on pins, which is the intended trade but leaves few slots for anything else. Long lines are indivisible: one 400-character claim can be passed over for a 40-character one, and a section whose only lines are long can lose its turn to a shorter section. The instruction header that `render_journal_index` wraps around the index still sits outside the cap, because it is fixed text rather than index content.

The contract is checked where it broke. `test/llm/prompt/test_journal_core.py` walks nine adversarial indices — empty, title alone, preamble only, one 400-character line, no headings at all, catalog heavy, pin heavy, a hand-written line beside a claim, and the journal's real shape — against every cap up to 160 characters and a spread up to each index's own length, and asserts four things at each point: the cap holds, a truncated block says it is truncated, nothing is emitted that is not a whole line of the index, and no heading stands over an empty section. The suite that missed the four review findings was green at 2,323 tests because every one of them sat in the middle of the range; two mutations of this module — keeping every line, and emitting the note uncharged — are both caught by that walk.

## Alternatives rejected

- **Raise `LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION`.** It caps lines per section, which is what already happened; the failure was in the character budget, not the line budget, and 20 long lines per section still exceed any cap.
- **Inject the whole index.** 15,167 characters, ~3,800 tokens, on every session's first turn and again after each compaction.
- **Rank claims semantically, against the opening message.** That is what the first-turn auto-search already does, and it answers a different question: "what does this session start by asking about", not "what must arrive regardless".
- **Leave the overflow note outside the cap.** It is the same 1,549-character overshoot this record exists to end.
- **Drop `## Recent Insights` from the index file.** It is useful when a human or the agent reads the file; the redundancy only exists inside a capped block that has already stated the same claims.
