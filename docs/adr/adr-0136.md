# ADR-0136 — A watch outlives its turn in a ledger, and reports itself once

- **Status:** Accepted
- **Date:** November 1, 2026

## Context

Work that outlives a turn — a background command, a delegation, a pipeline — is started by a tool call that returns long before the work ends. Everything that knows the work exists lives in memory: `_ShellBackgroundRegistry` holds the handle, its capture and its return code (`llm/tool/shell_background.py`), and the live context lists the handles the process still owns. Once a handle has been polled away, or the process has restarted, that knowledge is gone.

The failure this record answers: on 2026-11-01 a background watcher was started for a CI matrix, the turn ended, and the watcher exited with code 0 eighteen minutes later. Nothing read it. The result sat in a temporary file until the user asked about it, because the only way it could have been seen was for the model to remember to poll a handle it no longer had any reason to think about.

A `Stop` hook is not the answer. It fires at the turn boundary, which is the one moment the answer cannot exist, so it can only say "something is pending" on every turn and never what came of it. The trigger has to be the work's own end.

## Decision

A watch is recorded in a **per-session append-only ledger** before its work starts, and closed by whichever path observes the end.

- **Where:** `<CFG.LLM_WATCH_DIR>/<session>.jsonl`, defaulting to `~/.zrb/llm-watch/`. One file per chat session, so one window's result can never be delivered into another. Mode `0600`.
- **What a row holds:** id, session, kind, a one-line description, opened/ended timestamps, the exit code, and a pointer to the output. Never the output itself — a log tail can carry a token, and this file has to stay boring on disk.
- **Written before the work starts:** an `opened` row costs one append and leaves a record of what was about to happen, which is what a crash otherwise destroys.
- **Closed once:** the exit wait, a kill and a deadline kill all reach `_end_watch`, which sets a flag so a second path cannot report a second ending. A kill is recorded as `killed`, not as `finished`, or a timeout reads as success.
- **Delivered when rendered:** a finished watch that is not delivered appears in `<live-context>`, and rendering marks it delivered. A watch the registry still reports in full is skipped, so the block says each fact once rather than twice.
- **Metadata, not memory:** the live half of a watch — the task being awaited, the cancel token, the loop — stays with the registry that owns it and is deliberately absent from the file.
- **The pid that runs the work is recorded** (`started`, once the process exists), so a later run can ask whether the work is still going. A row left `running` by a previous run is reconciled to `lost` **only** when that pid is gone (signal 0 on POSIX); on Windows the pid is never probed, because `os.kill` there terminates the process the question is about, and the row stays running rather than being declared lost.
- **Compaction takes a lock** on `<file>.lock`. Several zrb processes can share one session's ledger; an append is a single small write, but a compaction is read-modify-write, and without the lock it would drop rows another process had just appended.

## Consequences

A result that arrives while nobody is looking is a standing fact in the next turn instead of something a model has to remember to fetch, and it survives a restart, a closed laptop and a consumed handle. The ledger also says when a watch's ending was never seen, so "unknown" stops being indistinguishable from "still running".

Costs, all deliberate:

- **Rendering is at-most-once.** A turn that fails after its prompt was built has been shown the line and will not see it again; the row survives in the file, but nothing re-renders it. Deliver-once is worth more than a duplicate line every turn, and duplicating would make a quiet session noisy.
- **A restarted session cannot recover the output.** The row names the exit code and says the output did not outlive the process. A `recheck` command, once a watch carries one, is what turns that into a late answer.
- **One more file per session**, compacted to the watches that still say something when a session opens its ledger.

## Alternatives rejected

- **A `Stop` reminder hook.** Fires before the answer exists, and cannot carry an outcome.
- **Memory only.** The registry is exactly what dies with the process, which is the case this design exists for.
- **Storing the output in the ledger.** A tail can hold a credential; a pointer cannot.
- **A delivery queue in this change.** Pushing an outcome into the session's input queue, so an unattended session takes a turn of its own, is the next step and needs the open question settled first: whether a queued message can arrive mid-run or only between turns.
