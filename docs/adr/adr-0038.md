# ADR-0038 — Model capabilities are a deny-list, and the prompt states the default

**Status:** Accepted

**Context.** Models diverge in what they support — image and audio input, parallel tool calls — and some OpenAI-compatible endpoints *ignore* `parallel_tool_calls=False` and emit malformed parallel calls anyway. There is no standard API to discover any of this at runtime.

An earlier design carried this into the prompt as a tri-state line: the prompt told the model to batch calls "where System Context says the model supports it". That was gated on a precondition that could never be satisfied. The resolver is a **deny-list** — it returns `False` for the two models known to malform parallel calls and `None` for everything else, and no built-in pattern ever returns `True` — so the affirmative branch was unreachable for every model zrb ships against.

A benchmark measured the cost: the same model on the same 44-site migration took 71s at an average batch of 5.35 calls per response and 434s at 2.62, with one trial timing out entirely at 600s. Models batched when they happened to; nothing asked them to.

**Decision.** Keep one per-model capability registry — a name-pattern table plus user overrides, tri-state fields where `None` means unknown and pass-through. Apply constraints at two layers: the provider level (`parallel_tool_calls=False` in `model_settings`) and the prompt level, which is defense in depth for endpoints that ignore the flag.

**The prompt states the default; System Context announces only the exception.** `workflow`'s tool-usage rule tells every model to batch independent calls unconditionally, names what must stay sequential (a write and the read that must see it), and ends with "unless System Context says this model cannot batch". `_format_parallel_tool_call_line` keeps only the negative branch: for `False` it emits an explicit override line, and for `True` and `None` alike it emits nothing. There is no affirmative branch left to fall out of sync.

**Consequences.** Known-bad models are corrected at both layers while every other model reads an unconditional instruction that matches what zrb actually knows. `supports_parallel_tool_calls` stays tri-state, but `True` is now meaningful only as a user override meaning "ignore any future deny-list entry", and it drives no rendering. A regression test asserts no model is ever told batching is *supported*, so the unreachable branch cannot return. The registry still has to be kept current as providers ship new models.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| No capability tracking | Silent malformed calls and retry storms. |
| Prompt-only enforcement | Does not stop a model from emitting a malformed parallel call. |
| Per-call runtime discovery | Inconsistent across providers and slow. |
| Populate an allow-list (`gpt-4`, `gemini-`, `claude-`, …) | A per-model table to maintain forever that is wrong by default for every model not yet in it, which is the exact failure being fixed; the safe answer for an unknown model is "batch", since malformed parallel calls are a rare identifiable defect, not the norm. |
| Leave the prompt conditional and fix only the registry | Same maintenance burden, and it keeps a rule whose precondition most readers cannot verify. |
| Say nothing in the prompt and rely on tool docstrings alone | Batching is cross-tool turn policy, which `workflow` owns per ADR-0045; the docstring line reinforces it at the point of use but should not be the only statement. |

**Where it lives.** `src/zrb/llm/util/capabilities.py`, `src/zrb/llm/agent/common.py` (`_apply_capability_constraints`), `src/zrb/llm/prompt/system_context.py` (`_format_parallel_tool_call_line`), `src/zrb/llm/prompt/markdown/workflow.md`, `docs/advanced-topics/extending-the-llm.md`.
