# ADR-0066 — `Shell` is the only shell tool, and background is a flag

**Status:** Accepted

**Context.** The shell tool was originally named `Bash`, which is a Claude/ChatGPT-shaped name: the model's strong prior is a Bourne-again shell on Linux, while the tool actually runs whatever the host shell is — including PowerShell or cmd. The name also carried no distinction between foreground and background execution. A later step renamed the tool `Shell` while keeping `Bash` as a thin alias, on the reasoning that a conversation that already called `Bash` must keep working. That left the model seeing two tools that resolve to one implementation — a redundant choice to make on every command, at a token cost on every request (ADR-0058).

An intermediate design also split background execution into its own tool, `ShellBackground`, on the reasoning that "call this, get a handle, call that to poll" cannot be expressed as one tool. That reasoning conflates *launch* with *poll*: only the poll step needs a separate tool.

**Decision.** One tool, one name, one flag.

- **`Shell`** is the only shell tool — `command`, `cwd`, `timeout`, truncation parameters, plus `shell` (defaulting to the user's shell; pass `"bash"` for bash specifically) — streaming stdout and stderr live and returning truncated output. The generic name works regardless of the host shell.

- **Claude-authored sub-agent files that list `Bash`** in `tools:` / `disallowedTools:` map onto `Shell` when the agent loads, so a conversation written against the Claude name keeps working and the model never sees two tools. The Claude-name alias survives only for hook matchers (`CLAUDE_TOOL_ALIASES`), where a Claude hook config's `{"matcher": "Bash"}` still fires on Shell calls.

- **`background: bool = False`** (plus an optional `description`) short-circuits to the background registry and returns a handle immediately, with no timeout and no foreground streaming. `MonitorProcess(handle)` polls, waits or kills (ADR-0069).

**Consequences.** The naming matches what the tool does on any host OS, and the model sees one shell tool instead of two — fewer decisions, fewer tokens shipped on every request. Background launches flow through the same command-validation approval path as any other shell call, rather than a blanket auto-approval on a separate tool. A boolean flag is selected marginally less reliably than a distinct tool name — accepted as the symmetric counterpart to the same trade in ADR-0068.

**Alternatives rejected.** *Keep `Bash` as a second tool* — two tools doing one thing is a coin flip a small model has to win on every command (ADR-0049). *Keep `Bash` as the only name* — the OS mismatch persists. *Keep `ShellBackground` as a separate tool* — redundant surface, and the argument for it does not hold for the launch step. *One tool that also polls* — the poll genuinely needs its own tool, which is why `MonitorProcess` stays.

**Where it lives.** `src/zrb/llm/tool/shell.py`, `src/zrb/llm/tool/shell_background.py` (registry and `MonitorProcess`), and the Bash→Shell mapping in `src/zrb/llm/agent/subagent/manager.py`.
