# ADR-0012 — Readiness checks are concurrent, task-based probes

**Status:** Accepted

**Context.** A task that starts a long-running service never returns. Downstreams must proceed when the service is *ready*, not when the action *completes*.

**Decision.** A task may declare `readiness_check` tasks such as `HttpCheck` or `TcpCheck`. The action runs as a deferred background coroutine while the checks poll; once they pass, the task is "ready" and downstreams proceed. `monitor_readiness=True` keeps probing and restarts the action on failure.

**Consequences.** Server-style tasks integrate into the DAG and crashes can trigger restarts. The cost is a second execution path (deferred coroutines) and timing parameters to tune.

**Alternatives rejected.** *Await action completion* — never returns for a daemon. *Inline sleep-and-retry inside the action* — couples waiting to the action and cannot be reused. *A task-level timeout only* — no flexible probing, and no restart story.

**Where it lives.** `src/zrb/task/base/execution.py` (`execute_action_until_ready`), `src/zrb/task/base/monitoring.py`, `src/zrb/session/session.py` (`defer_action`/`wait_deferred`), `docs/task-types/readiness-checks.md`.
