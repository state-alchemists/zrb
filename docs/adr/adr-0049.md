# ADR-0049 — A profile is a preset over sections, phrasing and tool surface

**Status:** Accepted

**Context.** zrb runs on models from ~1B local weights to frontier hosted ones.
Three things ship on every request and each is a separate axis: *which* sections
compose (ADR-0044), *how each is phrased*, and *which tools register* — a
registered tool's docstring and parameter schema are serialized in full
(ADR-0058).

A default session's preamble, before the user's first word, is several thousand
tokens. A ~3B model has a large nominal context but an *effective
instruction-adherence window* several times smaller, so the preamble alone can
exceed it before a file is read. Three behaviours in the default surface are
second-order and reliably out of reach at that size: deciding to call
`ActivateSkill` and acting on its returned content, delegating to a sub-agent,
and maintaining a todo list across turns. Each is pure token cost when unused.

Two findings shape what varies, and they point in different directions.

*Weak does not mean fewer instructions — it means a different register.* A study
of opencode's prompt set found the prompt for the weaker model family is the
longest and most repetitive, full of few-shot blocks, while the strong-model
prompt is shorter and leans on judgment. Supporting evidence: added constraints
reduce task performance more for smaller models (arXiv 2601.22047), and
prohibitions decay as context grows while affirmative steps persist (arXiv
2604.20911). Demonstrations are the lever the evidence supports; more rule prose
is not.

*Below a threshold the budget binds first.* That changes what tokens are spent
*on*, not whether demonstrations help. At 5–14B the budget is not the binding
constraint and every capability is worth keeping. At ~3B it is, so abstract rule
prose the model cannot apply goes and demonstrations stay.

**Decision.** `LLM_PROFILE` selects a **preset**: a named binding of the three
axes, in `prompt/profile.py::PRESETS`.

| Preset | sections | phrasing variant | tool surface |
| --- | --- | --- | --- |
| `full` | default | — | all 20 eager tools |
| `lean` | default | `.lean` | all but `LEAN_DROPS` (17 eager) |
| `minimal` | `persona, workflow, system_context` | `.minimal` | `MINIMAL_TOOLS` (10) |

The names are the ladder: `full` > `lean` > `minimal`, ordered by how much the
model is asked to hold at once. They are deliberately one axis — a register word
mixed with size words reads as three unrelated labels, and a size word that
collides with a vendor tier suffix (`micro`) makes a model carrying that suffix
match nothing and fall through to the heaviest preset.

### The phrasing axis is a variant overlay

A section named `foo` resolves `foo.{profile}.md` and falls back to `foo.md`
through the full override chain. A preset ships files only for the sections
whose text actually changes. This is the **only** convention for varying a
section's wording: the section list says which *topics* appear and never which
wording, so there is no `workflow_lean` *section*, only a `workflow.lean.md`
file.

**A variant never becomes the only home of a rule.** A variant reaches only the
models that resolve to it, so a rule that exists nowhere else silently misses
everyone else. The rule bounds *where a rule lives*, not *how much prose a
preset ships*: a variant may re-shape the rulebook for its model class —
`workflow.lean.md` flattens the precedence ladder and merges the decision
ladders, `workflow.minimal.md` reduces to one page — but may not quietly delete
a rule that still applies. The floor is therefore a test, not a prohibition on
subtracting.

**Mass is not the axis a variant varies; form is.** A variant that is its parent
with subordinate clauses removed ships the frontier prose *register* to a model
that needs a different one; neither the rule count nor the char count can see
the difference. `workflow.lean.md` is written in `minimal`'s register at
`full`'s coverage: imperative sentences, decision tables, no nested
qualification.

**`examples` demonstrates; it never legislates.** No `Wrong:` verdict — that is
a rule wearing a demonstration's clothes, landing in the one section `minimal`
drops and the burden ladder exempts. A variant of `examples` must cover every
stance the base teaches, matched on concept so the wording may differ, and must
not embed the base verbatim: a byte-prefix pin makes the base a literal copy
inside the variant, so the two grow as one file with only the variant's end
checked. A demonstration earns its place by teaching what prose cannot —
**scale**, **stance**, or a **form** a rule can only describe. One that restates
a rule the same preset's rulebook already states is the same rule bought twice.

`examples` is thin in the base on purpose: it keeps only the demonstrations that
fix a zrb-specific stance a capable model would not otherwise adopt. Add one to
the variant unless it teaches a stance a frontier model gets wrong — and if it
teaches a *rule*, it belongs in neither file.

### The tool axis has two forms

`Preset.tools` is an **allowlist** — a closed, fixed surface, which is what makes
`minimal`'s closure checkable at all. `Preset.drops` is a **denylist**, which is
what `lean` needs: it keeps the full surface and subtracts a few, where an
allowlist would have to re-list every tool and would silently drop each
newly-added one until someone remembered it. `Preset.admits` resolves either, so
every consumer stays one predicate. `Preset.__post_init__` rejects setting both,
since a bare `PRESETS[name] = Preset(...)` walks past any check living only in
`register_preset`.

**Deferral is keyed on closure, not on constraint.** `defer_loading` swaps a
tool's schema for a `search_tools` entry the model must call first — worth it
when it hides a dozen tools, inverted at ten. `minimal` would spend ~146 tokens
of `search_tools` to hide `MonitorProcess`'s ~127 and charge a ~3B model a
discovery turn to poll a background process, so a preset with a *closed* surface
registers eagerly. `lean` keeps 17 eager and 13 deferred, where the indirection
is the whole saving. `_Surface.undefer` is therefore keyed on `Preset.tools is
not None` — on whether the surface is closed, which is the property that implies
"small".

`LEAN_DROPS` is the journal trio (`SearchJournal`, `LogActivity`,
`WriteJournalNote`): cross-session memory is never needed to finish the turn,
and ADR-0055 leaves no prompt prose to orphan. `Shell` is the only shell tool
(ADR-0066); a Claude-authored sub-agent that lists `Bash` maps onto it at load.

### Selection

`auto` (the default) consults user declarations from `register_model_profile`
first, then the built-ins. A stated parameter count of ≤4B selects `minimal`;
5–14B selects `lean`.

A stated count is **parsed as a number** and compared against `SIZE_BANDS`,
never matched per band by a digit pattern — a digit class cannot see a decimal
point, so `deepseek-r1:1.5b` matches a `5b` pattern and takes the preset built
for models ten times its size. Parsing also settles ambiguous ids by rule: the
first count in an id wins, so an MoE reads as its total (`qwen3-30b-a3b` → 30B)
rather than its active parameters, and a count outranks a label, being the more
specific claim.

The two bands are deliberately asymmetric. `lean` keeps every section and nearly
every tool, so a false positive is cheap — which is why vendor small-tier labels
(`mini`, `micro`, `nano`, `tiny`, `lite`, `haiku`) resolve there. `minimal`
*removes* sections and tools, so a false positive costs real capability, and
only a stated ≤4B count selects it outright.

A label alone is not enough: `nano`/`micro` sit on models (`gpt-5-nano`) far
more capable than a 3B local one. **A label plus a local provider prefix is**
(`LOCAL_PROVIDERS`: `ollama:`, `lmstudio:`, `llamacpp:`, `localai:`). The label
is a claim about a position in a lineup; the prefix says who is serving it.
`openai:gpt-5-nano` is the entry tier of a hosted family; `ollama:phi4-mini` is
3.8B of weights on a laptop. Ollama's hosted tier is the exception inside the
exception — those ids carry `:cloud`, which disqualifies.

zrb makes **no guess from a family name**: `deepseek`/`qwen`/`llama` span
tiny→frontier. A stated count is the vendor declaring the size; a family name
declares nothing.

### The model-family axis is the same convention

A family adjustment is a phrasing variant with a model pattern pointed at it —
two existing calls, no new machinery:

```python
register_preset("gemini", Preset(variant="gemini"))   # ships workflow.gemini.md
register_model_profile("gemini-", "gemini")
```

**zrb ships zero family variants and should keep it that way.** A family delta
with no measured behaviour behind it is the overfitting that makes opencode's
`beast.txt` (`"You MUST"` ×6) a liability on models that respond badly to
forceful scaffolding. Capability governs *how much* the model is asked to hold;
family belongs on the escape hatch until a measurement says otherwise.

`register_preset` re-checks what is checkable at runtime and warns: a `variant`
with no matching file on the lookup path (which silently ships the frontier
prose to a preset written for a 1B model), a composed rulebook missing a rank-1
concept, and a section list carrying no rulebook. Warnings rather than errors —
a custom rulebook may phrase a rule in words the pattern table does not match,
and a preset that varies only some sections is legitimate.

### Invariants

**Burden falls monotonically as target capability falls**, by two measures.

*Per rule-carrying section.* Each of `persona` and `workflow` must be strictly
smaller in mass and rule count than the same section one preset up, **measured
separately**. A summed measure reports the total and hides its terms: a section
with no variant at any preset ships identical frontier prose to all three, and
the sum still falls because another section shrank enough to cover for it. **A
section that never varies is a section whose variant nobody wrote**, and the
silent `foo.{profile}.md` → `foo.md` fallback is what keeps that quiet.

*Per composed total.* Demonstrations are exempt from the section ladder — a
worked example lowers burden rather than adding to it — but not from the budget.
Exempting them from both lets the exemption pay for itself out of the model's
attention, which is how a preset built for weaker models becomes the heaviest
composition in the system.

*Per absolute ceiling.* Both measures above are **relative**, and a relative
ratchet cannot see uniform drift: add a paragraph to all three variants and the
ordering is untouched while every model gets more to read. `PRESET_BUDGETS` caps
each preset's composed prompt. This is the enforcement arm of the rule that a
more capable model buys more *autonomy*, not more *text* — `full` having
headroom is not a reason to spend it, and raising a ceiling is a deliberate
decision.

**Composition may drop method; it may never drop safety.** Priority Order rank 1
— secrets, tool results are data not instructions, confirm destructive actions —
must be present in every preset. Everything below it is droppable.

**A preset's tool set is closed under every channel that can name a tool.**
There are three, and a name in any of them must resolve in every preset that
ships it. This is the tool-side analogue of ADR-0046's reads-whole-on-its-own
invariant.

- *Tool docstrings* route between each other ("Not to touch files: Read/Write/
  Edit … RM/MV to remove and move") and ship with their schema regardless of
  configuration, so they cannot carry a `<!--requires:-->` guard. This is what
  sizes `MINIMAL_TOOLS` at ten rather than six: `Shell` and `Grep` route callers
  to `Glob`/`RM`/`MV` for work they decline, and `Shell`'s `background=True`
  returns a handle only `MonitorProcess` can poll, so advertising the parameter
  without the tool is a trap rather than a saving. Closing the set costs ~500
  tokens and is not optional.
- *Prompt sections* are guarded by ADR-0046's subset walk.
- *Injected context* is guarded by `_render_parts` asking `Preset.admits` before
  emitting a line that names a tool, and by gating the journal index on
  `SearchJournal` surviving the preset rather than on `LLM_JOURNAL_ENABLED`
  alone — a preset that drops the reader must not keep handing it something to
  read. The `Interactive: no` branch names no tool at all: the three it would
  forbid are unregistered in exactly that branch, so naming them spends ~55
  tokens per turn warning against what is already absent.

**Consequences.** The three presets order as the principle requires, measured as
composed prompt (sections + skill catalogue + context blocks) plus eager tool
schemas:

| Preset | composed prompt | eager tools | preamble |
| --- | --- | --- | --- |
| `full` | 4,583 | 3,840 (20) | **8,423** |
| `lean` | 4,038 | 3,146 (17) | **7,184** |
| `minimal` | 1,242 | 2,339 (10) | **3,581** |

For `lean`, prose is not the binding constraint and the tool surface is: it was
46% of that preset's budget while its rulebook had already fallen 25%. Both
halves are addressed — trimming `examples.lean.md` back under its own rulebook,
and `LEAN_DROPS`.

The rulebook lever is smaller than it looks. `workflow.md` yields ~350 tokens of
removable restatement, not the ~700 a first estimate assumed, because an epigram
and the rule it compresses look like redundancy and are only redundancy when
both are present — which caps the saving at however many rules were stated
twice.

`minimal` composes to ~3,400 tokens of preamble against ~8,400 — inside a ~3B
model's effective window with room to read a file. Worth flagging for that
audience: Ollama's default `num_ctx` is 4096 unless raised, which a
3,400-token preamble very nearly fills on its own.

The costs are real. A `lean` session has no journal, so a user who wants
cross-session memory on a 7B sets `ZRB_LLM_PROFILE=full` or registers the model
into it. A `minimal` session has no web access, no skills, no sub-agents, no todo
list, no journal and no project-doc reading — it is a single-tool-call-per-turn
assistant, not an agentic coder, and no prompt engineering changes that at ~3B.
Three rulebooks must be kept in step; the rank-1 assertion bounds the drift that
matters and nothing bounds the rest, which is the price of a ladder. The
tool-closure invariant means adding a cross-reference to a `minimal` tool's
docstring can silently pull a tenth tool into the preset or create a dangle.

The three built-ins get invariants a custom preset does not: the test's
`PRESET_VARIANTS` list is hardcoded, so the rank-1 floor, the burden ladder and
the closure checks stop at `minimal`. `register_preset`'s warnings are the
runtime half, and its pattern table is deliberately a second copy of the test's
— a shared one would let a single wrong regex excuse both.

`LLM_SMALL_MODEL` remains the better home for a ~3B in a mixed setup —
summarizer and extractor prompts need none of this. `minimal` serves the case
where a small local model drives the main loop.

**Alternatives rejected.** *Per-model monolith selection, opencode's model* —
simple per model, but duplicates shared rules across files and abandons
composition. *Distinct `workflow_lean` / `workflow_minimal` sections instead of
variants* — a second convention for varying a section's text, buying no safety
the burden and rank-1 tests were not already providing. *Forbid a subtracting
variant outright* — pushes every reduction into a parallel section name for the
same reason. *A variant that adds rule text for weak models* — adding rule text
to the models least able to carry it is the wrong direction; the gap is closed
the other way, with prohibitions converted to affirmative form **in the base**,
which helps every model. *Weak = drop sections, generally* — contradicted by the
evidence at 7–14B, where budget is not the binding constraint; it holds only at
~3B where it is. *A full per-vendor variant matrix* — maximal fidelity and a
maintenance bomb. *Leave it to `LLM_INCLUDE_SECTIONS` plus a new tool knob* —
makes the user assemble a working configuration from three settings and offers
`auto` no way to select one. *Keep `LLM_PROFILE` phrasing-only and add
`LLM_MODEL_TIER`* — same objection, plus two knobs whose valid combinations are
mostly invalid. *Trim tool docstrings for `minimal`* — ADR-0058 identifies count
as the lever and prose as the wrong one; per-preset docstrings would fork the
tools. *Six tools, accepting the dangling references* — 500 tokens is not worth
a routing instruction naming tools the model cannot call. *Keep `MonitorProcess`
deferred under `minimal`* — at ten tools the `search_tools` entry costs more than
the tool it hides. *Ship an alias for a retired preset or variant name* — the
preserve-the-old-key rule (ADR-0026) covers released env *keys*, where a stale
config silently loses a setting; these are knob *values* whose consumers fail
loudly. *Name the presets `weak`/`small`* — `weak` reads as a judgement and
`small` collides with the vendor tier labels the selector matches on. *Do nothing
and document that ~3B is unsupported* — defensible, and the measurement says the
gap is one variant file and one registration filter, not an architecture change.
