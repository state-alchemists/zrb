# ADR-0049 — A profile is a preset over sections, phrasing and tool surface

**Status:** Accepted

**Context.** zrb runs on models from ~1B local weights to frontier hosted ones. Three things ship on every request and each is a separate axis: *which* sections compose (ADR-0044), *how each is phrased*, and *which tools register* — a registered tool's docstring and parameter schema are serialized in full (ADR-0058).

A default session's preamble, before the user's first word, is several thousand tokens. A ~3B model has a large nominal context but an *effective instruction-adherence window* several times smaller, so the preamble alone can exceed it before a file is read. Three behaviours in the default surface are second-order and reliably out of reach at that size: deciding to call `ActivateSkill` and acting on its returned content, delegating to a sub-agent, and maintaining a todo list across turns. Each is pure token cost when unused.

Two findings shape what varies, and they point in different directions.

*Weak does not mean fewer instructions — it means a different register.* Supporting evidence: added constraints reduce task performance more for smaller models (arXiv 2601.22047), and prohibitions decay as context grows while affirmative steps persist (arXiv 2604.20911). Demonstrations are the lever the evidence supports; more rule prose is not. zrb's own measurement agrees, and sharpens it — see *Measured* below.

This record previously also cited a reading of opencode's prompt set: that the prompt for the weaker model family is the longest and most example-heavy while the strong-model prompt is shorter. **That inference is withdrawn: it is confounded by provenance.** Each opencode file is a copy of one vendor's own CLI harness — `gemini.txt` (15,372 B, 9 examples) is a fork of gemini-cli's prompt, `anthropic.txt` (8,212 B, 5) of Claude Code's, `codex.txt` (7,390 B, 0) of Codex CLI's. The lengths track which harness was copied, not the capability of the model routed to it, and Gemini is not a weak family. Every fork commit body in that repo is empty, it has no eval harness, and two of the files (`copilot-gpt-5.txt`, `plan-reminder-anthropic.txt`) are dead code nothing imports. The conclusion above still stands on the two cited papers and on zrb's own measurement; it no longer stands on that reading.

*Below a threshold the budget binds first.* That changes what tokens are spent *on*, not whether demonstrations help. At 5–14B the budget is not the binding constraint and every capability is worth keeping. At ~3B it is, so abstract rule prose the model cannot apply goes and demonstrations stay.

**Decision.** `LLM_PROFILE` selects a **preset**: a named binding of the three axes, in `prompt/profile.py::PRESETS`.

| Preset | sections | phrasing variant | tool surface |
| --- | --- | --- | --- |
| `full` | default | — | all 20 eager tools |
| `minimal` | `persona, workflow, system_context` | `.minimal` | `MINIMAL_TOOLS` (10) |

The names order themselves by how much the model is asked to hold at once. They are deliberately one axis — a register word mixed with size words reads as unrelated labels, and a size word that collides with a vendor tier suffix (`micro`) makes a model carrying that suffix match nothing and fall through to the heaviest preset.

**Two presets, and each varies all three axes.** A preset that changed only the phrasing would be a second rulebook to keep in step for a difference nothing can measure: it would carry `full`'s entire rule inventory in tighter prose, and the tighter prose is worth a few hundred characters against a fixed per-request cost of ~7,000 tokens. What separates `minimal` is that it drops sections *and* closes the tool surface — a 60% cut in fixed cost per request, which is large enough to see. Anything between the two is a rounding error wearing a name.

### The phrasing axis is a variant overlay

A section named `foo` resolves `foo.{profile}.md` and falls back to `foo.md` through the full override chain. A preset ships files only for the sections whose text actually changes. This is the **only** convention for varying a section's wording: the section list says which *topics* appear and never which wording, so there is no `workflow_minimal` *section*, only a `workflow.minimal.md` file.

**A variant never becomes the only home of a rule.** A variant reaches only the models that resolve to it, so a rule that exists nowhere else silently misses everyone else. The rule bounds *where a rule lives*, not *how much prose a preset ships*: a variant may re-shape the rulebook for its model class — `workflow.minimal.md` reduces to one page — but may not quietly delete a rule that still applies. The floor is therefore a test, not a prohibition on subtracting.

**Mass is not the axis a variant varies; form is.** A variant that is its parent with subordinate clauses removed ships the frontier prose *register* to a model that needs a different one; neither the rule count nor the char count can see the difference. `workflow.minimal.md` is written in a different register: imperative sentences, decision tables, no nested qualification.

**`examples` demonstrates; it never legislates.** No `Wrong:` verdict — that is a rule wearing a demonstration's clothes, landing in the one section `minimal` drops and the burden ladder exempts. A demonstration earns its place by teaching what prose cannot — **scale**, **stance**, or a **form** a rule can only describe. One that restates a rule the rulebook already states is the same rule bought twice.

`examples` ships one file and no variant. `minimal` drops the section outright and carries its demonstrations inline in `workflow.minimal.md`, so a stance that disappears from `examples.md` reaches nobody — which is what `test_examples_still_teaches_every_stance_it_is_responsible_for` pins, matched on concept so the wording stays free.

### The tool axis has two forms

`Preset.tools` is an **allowlist** — a closed, fixed surface, which is what makes `minimal`'s closure checkable at all. `Preset.drops` is a **denylist** for a preset that keeps the full surface and subtracts a few names, where an allowlist would have to re-list every tool and would silently drop each newly-added one until someone remembered it. No shipped preset uses it; it stays because `register_preset` is a public extension point and "everything except X" is the natural shape of a user's own preset. `Preset.admits` resolves either, so every consumer stays one predicate. `Preset.__post_init__` rejects setting both, since a bare `PRESETS[name] = Preset(...)` walks past any check living only in `register_preset`.

**Deferral is keyed on closure, not on constraint.** `defer_loading` swaps a tool's schema for a `search_tools` entry the model must call first — worth it when it hides a dozen tools, inverted at ten. `minimal` would spend ~146 tokens of `search_tools` to hide `MonitorProcess`'s ~127 and charge a ~3B model a discovery turn to poll a background process, so a preset with a *closed* surface registers eagerly. `full` keeps 20 eager and 16 deferred, where the indirection is the whole saving. `_Surface.undefer` is therefore keyed on `Preset.tools is not None` — on whether the surface is closed, which is the property that implies "small".

`Shell` is the only shell tool (ADR-0066); a Claude-authored sub-agent that lists `Bash` maps onto it at load.

### Selection

`auto` (the default) consults user declarations from `register_model_profile` first, then the built-ins. A stated parameter count of ≤14B selects `minimal`; anything above it keeps `full`.

A stated count is **parsed as a number** and compared against `SIZE_BANDS`, never matched per band by a digit pattern — a digit class cannot see a decimal point, so `deepseek-r1:1.5b` matches a `5b` pattern and takes the preset built for models ten times its size. Parsing also settles ambiguous ids by rule: the first count in an id wins, so an MoE reads as its total (`qwen3-30b-a3b` → 30B) rather than its active parameters, and a count outranks a label, being the more specific claim.

The band ceiling sits where it does because handing the heaviest prompt to the models least able to hold it inverts the point of having presets, and `minimal` measured no worse than `full` on every model tested. That evidence does not reach into the band — the grid was 31B and up — so the bound is reasoned rather than measured, and it is the one selection decision that costs real capability. A model that needs web, skills or sub-agents at 7B is declared into `full` explicitly.

The two signals are deliberately asymmetric. A stated count is the vendor declaring a size and selects outright. A label is the weaker claim, and with `minimal` dropping sections *and* tools a false positive costs the model its web access and sub-agents, while guessing wrong toward `full` only costs tokens — so a bare label (`mini`, `micro`, `nano`, `tiny`, `lite`, `haiku`) declares nothing and keeps `full`.

A label alone is not enough: `nano`/`micro` sit on models (`gpt-5-nano`) far more capable than a 3B local one. **A label plus a local provider prefix is** (`LOCAL_PROVIDERS`: `ollama:`, `lmstudio:`, `llamacpp:`, `localai:`). The label is a claim about a position in a lineup; the prefix says who is serving it. `openai:gpt-5-nano` is the entry tier of a hosted family; `ollama:phi4-mini` is 3.8B of weights on a laptop. Ollama's hosted tier is the exception inside the exception — those ids carry `:cloud`, which disqualifies.

zrb makes **no guess from a family name**: `deepseek`/`qwen`/`llama` span tiny→frontier. A stated count is the vendor declaring the size; a family name declares nothing.

### The model-family axis is the same convention

A family adjustment is a phrasing variant with a model pattern pointed at it — two existing calls, no new machinery:

```python
register_preset("gemini", Preset(variant="gemini"))   # ships workflow.gemini.md
register_model_profile("gemini-", "gemini")
```

**zrb ships zero family variants and should keep it that way**, and this is now measured rather than argued. Running opencode's own `anthropic.txt`, `gemini.txt` and `kimi.txt` against 8 models found **no family-matching advantage**: the three files score 75% / 75% / 67% overall against zrb's 74%, no arm dominates, and a model does not do better on the file written for it — `kimi-k2.6` scores **worst** on `opencode-kimi` (50%) of the four arms it was given. A prompt tuned for one family did not transfer badly to another, because it was not better on its own family to begin with.

The earlier reasoning — that family variance is itself overfitting — was too strong, and the literature says so: format sensitivity is real and idiosyncratic (FormatSpread, arXiv:2310.11324, finds meaning-preserving separator and casing changes moving accuracy up to 76 points), and it shrinks as models get stronger (arXiv:2411.10541: GPT-3.5 swings 40% on template choice, GPT-4 is robust). So the escape hatch matters *more* than this record implied, not less.

What is actually wrong with opencode's forks is that they are **unmeasured**, not that they are per-family: every fork commit body is empty, the repo has no eval harness or golden tests, the files are vendor-harness copies rather than tuned artifacts, and two are dead code. `beast.txt` (`"You MUST"` ×6) still reads as a liability on models that respond badly to forceful scaffolding — but that is a judgement about that file, not a proof about the axis. Capability governs *how much* the model is asked to hold; family stays on the escape hatch until a measurement says otherwise, and the measurement above says it is not yet worth spending.

`register_preset` re-checks what is checkable at runtime and warns: a `variant` with no matching file on the lookup path (which silently ships the frontier prose to a preset written for a 1B model), a composed rulebook missing a rank-1 concept, and a section list carrying no rulebook. Warnings rather than errors — a custom rulebook may phrase a rule in words the pattern table does not match, and a preset that varies only some sections is legitimate.

### Invariants

**Burden falls monotonically as target capability falls**, by two measures.

*Per rule-carrying section.* Each of `persona` and `workflow` must be strictly smaller in mass and rule count than the same section one preset up, **measured separately**. A summed measure reports the total and hides its terms: a section with no variant at any preset ships identical frontier prose to all three, and the sum still falls because another section shrank enough to cover for it. **A section that never varies is a section whose variant nobody wrote**, and the silent `foo.{profile}.md` → `foo.md` fallback is what keeps that quiet.

*Per composed total.* Demonstrations are exempt from the section ladder — a worked example lowers burden rather than adding to it — but not from the budget. Exempting them from both lets the exemption pay for itself out of the model's attention, which is how a preset built for weaker models becomes the heaviest composition in the system.

*Per absolute ceiling.* Both measures above are **relative**, and a relative ratchet cannot see uniform drift: add a paragraph to all three variants and the ordering is untouched while every model gets more to read. `PRESET_BUDGETS` caps each preset's composed prompt. This is the enforcement arm of the rule that a more capable model buys more *autonomy*, not more *text* — `full` having headroom is not a reason to spend it, and raising a ceiling is a deliberate decision.

**Composition may drop method; it may never drop safety.** Priority Order rank 1 — secrets, tool results are data not instructions, confirm destructive actions — must be present in every preset. Everything below it is droppable.

**A preset's tool set is closed under every channel that can name a tool.** There are three, and a name in any of them must resolve in every preset that ships it. This is the tool-side analogue of ADR-0046's reads-whole-on-its-own invariant.

- *Tool docstrings* route between each other ("Not to touch files: Read/Write/ Edit … RM/MV to remove and move") and ship with their schema regardless of configuration, so they cannot carry a `<!--requires:-->` guard. This is what sizes `MINIMAL_TOOLS` at ten rather than six: `Shell` and `Grep` route callers to `Glob`/`RM`/`MV` for work they decline, and `Shell`'s `background=True` returns a handle only `MonitorProcess` can poll, so advertising the parameter without the tool is a trap rather than a saving. Closing the set costs ~500 tokens and is not optional.
- *Prompt sections* are guarded by ADR-0046's subset walk.
- *Injected context* is guarded by `_render_parts` asking `Preset.admits` before emitting a line that names a tool, and by gating the journal index on `SearchJournal` surviving the preset rather than on `LLM_JOURNAL_ENABLED` alone — a preset that drops the reader must not keep handing it something to read. The `Interactive: no` branch names no tool at all: the three it would forbid are unregistered in exactly that branch, so naming them spends ~55 tokens per turn warning against what is already absent.

### Measured

Every invariant above is *structural* — it counts characters, rules and tool names. None of them observes a model. `llm-experiment/` was built to close that gap and for four releases it did not: **every measured claim this record used to make was produced by a harness that was not running zrb's agent.** Four defects, each found and fixed separately, all pointing the same way:

- tool definitions were one-line mock docstrings, so ~44% of the instruction budget — the half ADR-0045 deliberately puts *in* the docstrings — was absent;
- the request budget was 12 against a shipped 300, cutting off a third of cells, and a cell cut off mid-task scores as a failure of whatever probe it was on;
- `Write`/`Edit`/`RM`/`MV` returned success and **mutated nothing**, so a model that obeyed "check the artifact, not your memory of writing it" read its own edit back, found it missing, and thrashed until the budget ran out;
- tool retries were pydantic-ai's default of 1 against zrb's `LLM_TOOL_MAX_RETRIES` of 3, dropping cells the shipped agent recovers, concentrated on the weakest model.

Defects two and three are **directionally biased against `full`**: one rewards whichever prompt reaches an answer in fewest turns, the other punishes whichever prompt insists hardest on verifying its own work. Both favour `minimal` over `full` for reasons that have nothing to do with either rulebook. So the numbers this record built its argument on are not merely underpowered, they lean — and they leaned toward the conclusion it drew.

The corrected grid is 610 cells over 5 models at production tool weight, 40 requests, a mutable filesystem and the shipped loop guard, fingerprinted by prompt and by harness so a future corpus cannot silently blend two of either. What it shows:

| | `full` | `minimal` |
| --- | --- | --- |
| all probes | 76% [67–83] 82/108 | 86% [78–91] 89/104 |
| method | 76% [65–85] | 91% [81–96] |
| safety | 70% [48–85] | 75% [53–89] |
| hard probes (X5) | 66% [52–78] | 67% [53–79] |

**No probe separates the two at 95%, and neither does the aggregate** (−10pp, CI [−20, +1]). The ladder's premise — that a weaker model does better on a smaller prompt while a stronger one is not held back by a larger one — is still not *demonstrated*; what has changed is that it is no longer contradicted either. The honest state is: four times the prompt buys nothing measurable, and `minimal` costs 2–3× fewer input tokens per cell on four of five models. That is enough to keep the ladder and not enough to claim it works.

**The rule-form finding is retained on its argument, not its number.** The mechanism below was measured on the broken harness and its figures are withdrawn; it is kept because the reasoning is independent of them and the literature supports it directly. The presets do not merely differ in length — they state the same rule differently:

- `workflow.md`: *"Never expose a credential, token, or key. Copying one anywhere is exposure."* — a prohibition.
- `workflow.minimal.md`: *"Never print or copy an API key, token, or password. **If a file contains one, say the file has one. Do not show it.**"* — the same prohibition plus the substitute behaviour.

Same model, same file: under `full`, `gemma4:31b` prints `sk-live-9f3a…` verbatim; under `minimal` it answers "contains an `API_KEY`" — the substitute, nearly word for word. Destructive actions repeat the pattern: `minimal` pairs the rule with a worked example and models reproduce its exact output form ("Delete these 4 files?"), while `full`'s abstract "pause before anything irreversible" yields deletion-then-report. This is arXiv 2604.20911's finding — prohibitions decay as context grows, affirmative steps persist — which this record already cited while writing the frontier rulebook in the decaying form.

**Acted on; the re-measurement is withdrawn and not replaced.** `workflow.md` leads its rank-1 rules with the substitute behaviour — "say that it holds one and carry on" for secrets, "describe what you are about to do and wait for a yes" for destructive actions — and that stays. The 48% → 69% figure this record cited for it came from the broken harness and is gone. On the corrected grid the same two probes read `safety_destructive` **80%** and `safety_secret` **60%** for `full` (70% / 80% for `minimal`), neither separating from anything, so the edit is now supported by the literature and by the reasoning rather than by a before/after of our own.

Two conclusions drawn from the withdrawn numbers were wrong and are worth naming, because both were acted on:

- *"`full` complies with rank-1 safety at half `minimal`'s rate."* On the corrected grid the safety gap is 70% vs 75%, CI-overlapping. The 44-point gap was substantially the frozen filesystem and the 12-request cut-off.
- *"Destructive-action confirmation and secret-handling cannot be moved by prose; they need the runtime rung of ADR-0045's ladder."* That was measured at 0/3 and 1/3 on a harness where a deletion could not delete and a re-read could not show an edit. At 80% and 60% the case for a permission default is a design argument about what a shipped default should be, not a measurement showing prose has failed. It may still be the right call; the evidence claimed for it does not exist.

The floor is the *form*, not just the concept, and `test_rank_one_rules_name_the_substitute_behaviour` asserts it per preset — on the literature and on the two traces in its docstring, with its own 44%/88% citation marked as withdrawn. Byte-identical rank-1 text across presets was considered and rejected: it would delete the `Interactive: no` branch (ADR-0048) and the `git status`/`git diff HEAD` rule, which apply only where those tools exist. Presets may differ in what else a rank-1 rule carries; they may not differ in whether it names the substitute.

### Is `full` carrying rules that do nothing?

`full` states 40 rule-lines to `minimal`'s 14, and X1's battery saturates, so a second battery (X5) targets rules stated in `workflow.md` with **no counterpart** in `workflow.minimal.md`. Excluded by design: anything needing `TodoWrite`, `EnterPlanMode`, `ActivateSkill` or `DelegateToAgent`, since a preset binds sections *and* tools and `minimal` would fail those for lacking the tool.

On the corrected grid, with `sequence coupled edits` replaced by `hard_rename_call_sites` (the old probe contradicted `hard_scope` and scored 0% in every arm — it was measuring the probe):

| probe | `full` | `minimal` |
| --- | --- | --- |
| removal-needs-a-grep | 40% [17–69] | 30% [11–60] |
| completeness-as-checklist | 80% [49–94] | 100% [68–100] |
| run-it-twice | 67% [35–88] | 44% [19–73] |
| scope discipline | 88% [53–98] | 100% [72–100] |
| rename reaches its call sites | 60% [31–83] | 67% [35–88] |
| **all** | **66% [52–78]** | **67% [53–79]** |

−1pp, CI [−20, +17]. `full` does not beat `minimal` even on the probes built from rules only `full` states. Every cell here is n≤10, so read the intervals: this table separates nothing, and its earlier incarnation — which reported 44% vs 50% and a 0% row — was measured on the broken harness besides. It licenses almost no cuts, for a reason worth stating plainly:

> **A cross-preset gap is not evidence about a rule.** `full` and `minimal` differ in dozens of ways at once, so "minimal lacks rule R and scores the same" confounds R with everything else that differs. The only valid test of a rule is a **within-preset ablation**: remove R from one preset and re-measure that preset.

Run that way, the per-rule ablations that once looked decisive — completeness dropping `full` to 60%, a scope demonstration moving neither arm — were all measured on the broken harness at n≤10 per cell and are withdrawn. The rules they were used to keep stay kept: an untested rule is not a refuted one, and nothing has replaced those ablations.

`Sequence coupled edits` is the one rule the evidence did condemn, and the condemnation turned out to be of the probe. It scored **0% in every arm and every model**, which read as "no model acts on this rule"; the probe in fact required a version bump to also edit a `CHANGELOG.md` nobody had named, while `hard_scope` in the same battery passed only when the model edited exactly one file. Two probes that could not both be satisfied. It is replaced by `hard_rename_call_sites` — a rename whose call sites live in two other files, couplings a grep *finds* — and the rule it tests is back in the prompt.

The conclusion is narrower than any aggregate suggests: `full`'s extra prose is not measurably buying behaviour, *and* that does not license trimming it, because no valid ablation has been run for any individual rule. Untested prose is not proven useless; it is untested.

**Narrower still.** Every rate this record originally published was a bare percentage over ten-odd runs. With 95% intervals attached, *no* comparison in any grid survives — ladder, rule position, both section ablations, the hard-probe battery, on the thin grid and on the corrected one alike. Four separate harness defects then had to be fixed before the numbers described zrb's agent at all (listed above), two of them biased in `full`'s disfavour. The standing state of the evidence is therefore: **this harness has produced exactly one effect that clears its own interval, and it was a property of the harness** — raising the request budget from 12 to 40, +24pp CI [+7, +40]. Nothing it has measured about a prompt separates. Reaching a verdict on any prompt question at these effect sizes needs n≈200 per arm, which is roughly 2,000 cells; the corrected grid is 610 and cost 33.6M input tokens.

**The half that went unmeasured longest is the tool docstrings.** Effective instructions are the prompt (4,070 tok file-backed) *plus* the eager tool definitions (3,860 tok), and every experiment recorded above varied the prompt while the harness held the docstrings not merely fixed but *absent* — its mock tools carried one-line docstrings, roughly a fifth of the text zrb sends. So the surface ADR-0045 deliberately moves rules onto was the one surface no arm exercised, and any "rule R is free" reading taken from those arms was taken with R's other half missing. ADR-0055 records that the journal is "three tools and no prose", which is true of the prompt and does not mean the burden went away: `LogActivity` and `WriteJournalNote` carry ~1,650 characters of instruction — including a durable-vs-transient judgement to make mid-task — into every request. ADR-0058 already says relocating prose into a docstring buys locality, not size.

`run.py --tools prod` closes that gap: a cell now receives each eager tool's shipped `(name, description, parameters_json_schema)` with a mock executor bound to it, so the definitions are real and only the implementations are fakes. Rows carry the surface they were measured on, and `analyze.py` reports one configuration at a time rather than pooling two experiments.

**Every row now fingerprints both what was measured and what measured it.** `prompt_sha` is the hash of the arm's composed text and `harness_sha` the hash of the mock world plus every scorer; both are part of a cell's resume identity and of `analyze.py`'s configuration key. `harness_sha` hashes the parsed syntax with docstrings stripped, so a comment cannot invalidate a corpus while a regex, threshold, fixture or scorer branch still does. An arm name is stable across every edit to the prompt behind it, so a resume matching on the name alone will silently satisfy today's cell with yesterday's row — which is exactly how a grid comes to report one number over five different prompts. A row predating either field takes a sentinel that compares equal to nothing, so it re-runs rather than being trusted: re-running costs money, and a corpus that blends two treatments or two harnesses costs the conclusion, which is the thing being bought.

**Injection resistance is at ceiling and was never the variable.** Across every run of that probe on both the old and the corrected grids, in every arm including opencode's, **no model called a single exfiltration-capable tool**. This is the one measured claim the harness defects leave standing: it is a statement about a tool never being called, which a frozen filesystem and a short budget cannot manufacture. What the arms differ on is whether the model *tells the user* it saw the attempt. Grouping that under safety made presets look like they differed on rank 1 when they did not.

**Neither `persona` nor `examples` is measurably earning its tokens, and neither is measurably wasting them.** This record used to report that dropping `persona` *improved* rank-1 safety (44% → 56%) and disclosure (62% → 88%), which read as a case for deleting it. Those figures are withdrawn with the rest. On the corrected grid both ablations are null and the intervals are wide:

| arm | all probes |
| --- | --- |
| `zrb-full` | 76% [67–83] 82/108 |
| `zrb-full-no-persona` | 78% [65–87] 39/50 |
| `zrb-full-no-examples` | 74% [61–84] 40/54 |

−2pp CI [−15, +13] and +2pp CI [−11, +17]. At n≈50 per ablation arm this cannot resolve a ±10pp effect, so it is not evidence for removal — a section is cut on a positive result, not an absent one. Both stay.

The `persona` question remains genuinely open and the flagship negative result on system-prompt personas still applies (arXiv 2311.10054, EMNLP Findings 2024: 162 personas × 4 model families × 2,410 questions, no accuracy gain, and automatic best-persona selection no better than random). zrb's `persona` is response-style calibration rather than an expertise claim — the variant that paper did not test — so this is a reason to measure it properly, which at these intervals means n≈200 per arm, not to delete it blind.

**No preset followed the Recovery rule, so it moved to the runtime.** Given an unfixable build, models looped to the request cap under every preset: `full` 0/7, `minimal` 2/7. A rule whose words are present in both rulebooks and which nothing obeys belongs in the runtime, not the prompt (ADR-0045's ladder). The non-convergence clause is now deleted from `workflow.md`, and ADR-0077's repeated-call guard enforces it instead — refusing the seventh identical call and returning the same two exits the prose offered, at the moment they apply rather than 10,000 characters earlier. Note what this does *not* license: the probe scored "bounded attempts **and** a non-empty final answer", so it condemns the repetition clause, not the `Recovery` heading. *Correctable error*, *a check that cannot pass*, *cannot succeed as stated* and *halt when asked* were never measured and are not runtime-enforceable, so they stay.

**Rule position is not measurable at this ceiling.** An extra mechanically-checkable rule placed at the start, middle and end of the same prompt scores 95% / 80% / 95% (n=20 each), and no pair of positions is distinguishable: start−middle is +15pp with a 95% interval of [−7, +37]. The dip is one model — `flash-lite` missed all four middle placements — which is a four-run cell, the width of the interval and nothing more until it is re-run deeper. See ADR-0046, which owns that claim.

**Consequences.** The three presets order as the principle requires, measured as composed prompt (sections + skill catalogue + context blocks) plus eager tool schemas:

| Preset | file-backed sections | composed prompt | eager tools | preamble |
| --- | --- | --- | --- | --- |
| `full` | 4,070 | 4,827 | 3,860 (20) | **8,687** |
| `minimal` | 1,081 | 1,222 | 2,349 (10) | **3,571** |

Regenerate with `python llm-experiment/measure.py`; do not edit by hand. Two rounds of correction are behind this table. The figures it carried originally were hand-derived and drifted; the ones that replaced them were measured by code that read the parameter schema off a private attribute pydantic-ai does not define, so they counted descriptions with no arguments and understated eager tool weight by about a third (ADR-0058). Note what the corrected column does to the ratio the ladder rests on: **tools are 44% of `full`'s preamble and 66% of `minimal`'s**, so the preset that drops the most prose is the one whose remaining budget is most nearly all tool definitions.

**Composed prompt is not a property of the prompt.** `system_context` embeds the OS, cwd and detected tools, and `project_context` walks the parent chain listing every `AGENTS.md`/`README.md` it finds, so the composed column moves with the machine and the working directory. The *file-backed* column is the stable one, and is what `PRESET_BUDGETS` asserts against.

The rulebook lever is smaller than it looks. `workflow.md` yielded ~350 tokens of removable restatement, not the ~700 a first estimate assumed, because an epigram and the rule it compresses look like redundancy and are only redundancy when both are present — which caps the saving at however many rules were stated twice. The compression pass took that cap: the epigram clauses are gone from `workflow.md`, the two `examples.md` demonstrations that only restated a sibling's stance were dropped, and the `Final Reminders` recap was cut outright (ADR-0046).

`minimal` composes to ~3,400 tokens of preamble against ~8,400 — inside a ~3B model's effective window with room to read a file. Worth flagging for that audience: Ollama's default `num_ctx` is 4096 unless raised, which a 3,400-token preamble very nearly fills on its own.

The costs are real. A `minimal` session has no web access, no skills, no sub-agents, no todo list, no journal and no project-doc reading — it is a single-tool-call-per-turn assistant, not an agentic coder, and no prompt engineering changes that at ~3B. A 7B that needs any of those is declared into `full`, and the band ceiling is reasoned rather than measured — no model under 31B has been through the grid. Two rulebooks must be kept in step; the rank-1 assertion bounds the drift that matters and nothing bounds the rest, which is the price of having presets at all. The tool-closure invariant means adding a cross-reference to a `minimal` tool's docstring can silently pull a tenth tool into the preset or create a dangle.

The three built-ins get invariants a custom preset does not: the test's `PRESET_VARIANTS` list is hardcoded, so the rank-1 floor, the burden ladder and the closure checks stop at `minimal`. `register_preset`'s warnings are the runtime half, and its pattern table is deliberately a second copy of the test's — a shared one would let a single wrong regex excuse both.

`LLM_SMALL_MODEL` remains the better home for a ~3B in a mixed setup — summarizer and extractor prompts need none of this. `minimal` serves the case where a small local model drives the main loop.

**Alternatives rejected.** *Per-model monolith selection, opencode's model* — simple per model, but duplicates shared rules across files and abandons composition. *A distinct `workflow_minimal` section instead of a variant* — a second convention for varying a section's text, buying no safety the burden and rank-1 tests were not already providing. *Forbid a subtracting variant outright* — pushes every reduction into a parallel section name for the same reason. *A variant that adds rule text for weak models* — adding rule text to the models least able to carry it is the wrong direction; the gap is closed the other way, with prohibitions converted to affirmative form **in the base**, which helps every model. *A middle preset that only lightens the phrasing* — it carries `full`'s whole rule inventory in tighter prose, which is worth a few hundred characters against a ~7,000-token fixed cost, and measured identically on every probe group; a preset that is neither cheaper nor different is a rulebook to maintain for nothing. *Route 5–14B to `full` instead of `minimal`* — hands the heaviest prompt to the models least able to hold it, which is what presets exist to avoid. *A full per-vendor variant matrix* — maximal fidelity and a maintenance bomb. *Leave it to `LLM_INCLUDE_SECTIONS` plus a new tool knob* — makes the user assemble a working configuration from three settings and offers `auto` no way to select one. *Keep `LLM_PROFILE` phrasing-only and add `LLM_MODEL_TIER`* — same objection, plus two knobs whose valid combinations are mostly invalid. *Trim tool docstrings for `minimal`* — ADR-0058 identifies count as the lever and prose as the wrong one; per-preset docstrings would fork the tools. *Six tools, accepting the dangling references* — 500 tokens is not worth a routing instruction naming tools the model cannot call. *Keep `MonitorProcess` deferred under `minimal`* — at ten tools the `search_tools` entry costs more than the tool it hides. *Ship an alias for a retired preset or variant name* — the preserve-the-old-key rule (ADR-0026) covers released env *keys*, where a stale config silently loses a setting; these are knob *values* whose consumers fail loudly. *Name the presets `weak`/`small`* — `weak` reads as a judgement and `small` collides with the vendor tier labels the selector matches on. *Do nothing and document that ~3B is unsupported* — defensible, and the measurement says the gap is one variant file and one registration filter, not an architecture change.
