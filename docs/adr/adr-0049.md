# ADR-0049 — Three explicit profiles, one optional auto ladder

**Status:** Accepted

**Context.** zrb runs on models from ~1B local weights to frontier hosted ones. The default system prompt is tuned for a capable model, and a ~3B model spends most of its effective instruction window on prose before a file is read. But binding a profile to model capability is guesswork: a family name spans sizes, a small-tier label alone sits on capable hosted models (`gpt-5-nano`), and a silent behavior change on model swap surprises users.

**Decision.** `LLM_PROFILE` selects one of three named operating profiles — `minimal`, `standard`, `capable` — or `auto`, the default, which picks one from the model id. A profile selects exactly one file, `profile.{name}.md`, which adjusts the final `profile` section; it does not alter the core sections or their wording. The rendered heading says **Operating Profile** to make clear that it adjusts operating posture, while the public config name stays `LLM_PROFILE`.

One tool difference ships with the ladder: `minimal` registers no delegate (sub-agent) tools, which are second-order capabilities a small model cannot use well and pure token cost otherwise (ADR-0058). The minimal adjustment says this explicitly. Tool availability is otherwise unchanged by profile: skill activation remains available at every profile.

`auto` consults the model id and never guesses from a family name. A declared parameter count is compared numerically against `SIZE_BANDS` (≤4B → `minimal`, ≤14B → `standard`, above → `capable`). A small-tier label alone selects `standard`; a label on a locally served model (`ollama:`, `lmstudio:`, `llamacpp:`, `localai:`) selects `minimal`, and Ollama's hosted `:cloud` tier is not local. An id that declares nothing falls back to `standard`. An explicit name selects that profile outright; `auto` is the only path model capability affects, and it falls back to `standard` whenever the id is ambiguous, so the default never guesses.

**Consequences.** A user can read the selected adjustment directly from one file. Every profile shares the same safety and truthfulness baseline — `minimal` subtracts sub-agent delegation, not skill activation or the rank-1 rules. Under the default, a model swap can change the profile; a user who wants a fixed posture names a profile explicitly, which stays stable across model changes.

**Alternatives rejected.** *A fixed `standard` default* — leaves a ~3B model spending its instruction window on prose meant for a capable one; `auto` only moves off `standard` when the id declares a size or a local small-tier label, so the ambiguous case keeps the fixed behavior. *Guessing from a family name* — a family spans sizes, so `auto` never does it. *Per-profile tool allowlists* — tool registration is a runtime concern, and a closed surface would demand a separate closure check; only the delegate tools are second-order enough to drop. *Per-section phrasing variants* — several prompt copies drift and obscure the shared operating principle. *More than three profiles* — each extra rung multiplies the files that must be kept in step for no measured gain.

**Where it lives.** `src/zrb/llm/prompt/profile.py` (`PROFILES`, `SIZE_BANDS`, `SMALL_TIER_LABELS`, `LOCAL_PROVIDERS`, `builtin_profile`, `resolve_profile`, `active_profile`), `src/zrb/config/mixins/llm_prompt.py` (`LLM_PROFILE`), `src/zrb/llm/prompt/markdown/profile.*.md`, `src/zrb/builtin/llm/chat.py` (delegate gating).
