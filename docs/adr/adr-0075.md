# ADR-0075 — A profile is a preset over sections, phrasing and tool surface; `minimal` serves ~3B models

**Status:** Accepted

**Context.** zrb's prompt is composed on two axes: *which* sections appear
(`LLM_INCLUDE_SECTIONS`, ADR-0044) and *how each is phrased*
(`LLM_PROFILE`, ADR-0047). Neither controls the third thing that ships on every
request — the set of registered tools, whose docstrings and parameter schemas
are serialized in full (ADR-0056).

Measuring a default `zrb llm chat` session (`lean` profile, git repo,
interactive) gives the preamble before the user's first word:

| Part | ~tokens |
| --- | --- |
| `workflow.md` | 3,200 |
| `examples.lean.md` | 1,600 |
| skill catalogue (`{CORE_SKILLS}` + `{AVAILABLE_SKILLS}`) | 585 |
| `persona.md` | 540 |
| `system_context` + `project_context` + `live_context` | ~800 |
| 14 non-deferred static tools (docstring + schema) | 2,880 |
| 7 factory tools (skill, zrb-task, ask, journal ×3) | ~1,000 |
| **total** | **~10,500** |

A ~3B model has a large nominal context but an *effective instruction-adherence
window* several times smaller — the preamble alone exceeds it before a single
file is read. Three further behaviours in the default surface are second-order
and reliably out of reach at that size: deciding to call `ActivateSkill` and
then acting on its returned content, delegating to a sub-agent, and maintaining
a todo list across turns. Each is pure token cost when unused.

Two existing mechanisms looked like the answer and are not.

*The `lean` profile points the wrong way.* It is the base plus worked
demonstrations, so it makes the prompt **larger** (`examples.lean.md` is 6.4k
chars against the base's 1.6k). That is correct for the 7–14B class it was
built for, where the budget is not the binding constraint. At ~3B it is net
harm.

*A phrasing variant alone does not reach far enough.* What ~3B needs is not only
different wording but a different section list and a different tool set. The
first two axes are composition, which is already MECE, guarded and brute-force
tested (ADR-0046); the third had no mechanism at all.

ADR-0047 rejected *"weak = drop sections"* on evidence that weak models benefit
from **more** demonstration, not less. That finding stands and is not contradicted
here, because it was measured in a regime where the budget was not binding. At
~3B the budget binds first, which changes what the tokens should be spent *on*,
not whether demonstrations help. `minimal` therefore drops abstract rule prose a
~3B cannot apply and **keeps** demonstrations.

**Decision.** `LLM_PROFILE` selects a **preset** — a named binding of three
axes — rather than a variant overlay. A *variant* remains what ADR-0047 defines
it as; it is now one of the three things a preset picks.

| Preset | sections | phrasing variant | tool surface |
| --- | --- | --- | --- |
| `full` | default | — | all 21 tools |
| `lean` | default | `.lean` | all 21 tools |
| `minimal` | `persona, workflow, system_context` | `.minimal` | `MINIMAL_TOOLS` (10) |

The names are the ladder: `full` > `lean` > `minimal`, ordered by how much the
model is asked to hold at once. The first cut of this record used
`terse`/`mini`/`micro`, which failed three ways — it mixed a prose register with
two size words, it named the *largest* preset "terse", and `micro` collided with
the vendor tier labels the selector matches on, so a model labelled `-micro`
matched no pattern and fell through to the heaviest preset.

Every preset varies text through one convention: a section named `foo` resolves
`foo.{profile}.md` and falls back to `foo.md`. There are no `workflow_lean` /
`workflow_micro` *sections*; the section list says which topics appear and never
which wording. `PRESETS` is the single source of truth for the valid set, so a
user registers a fourth with `PRESETS["nano"] = Preset(...)`.

**Burden falls monotonically as target capability falls.** That is the ordering
principle the presets exist to express, and it is asserted rather than claimed:
`test_rule_burden_falls_as_the_target_model_gets_weaker` requires each preset's
rule-carrying sections to be strictly smaller in mass and in rule count than the
preset above it. Demonstrations are excluded from the measure and move the other
way — a worked example lowers burden rather than adding to it (ADR-0047), which
is why `lean` both loses rule text and gains `examples.lean.md`.

`lean` was the counter-example that motivated the principle. It shipped a 5-14B
model the frontier `workflow.md` **plus** 1,200 extra tokens of examples, making
it the heaviest composition in the system — the model class least able to carry
the load received the most of it.

`lean` therefore takes `workflow.lean.md`: the same behaviours with the
precedence abstraction flattened to "the one higher in this list wins", the
decision ladders merged, and the meta-commentary dropped. It keeps every
capability — skills, todos, delegation, plan mode, the full tool surface —
because a 5-14B model can use them, so trimming there would cost behaviour
rather than burden. Note that this does not make `lean` smaller in total: the
rulebook falls ~700 tokens and `examples.lean.md` adds ~1,200 back, so `lean`
remains marginally the largest composition. That is the trade the burden metric
encodes deliberately, not an unfixed regression.

`minimal` is defined concretely:

1. **Sections** — `persona`, `workflow`, `system_context`, with `workflow`
   resolving to `workflow.minimal.md`. It carries affirmative numbered steps and
   inlines the demonstrations that `examples` would otherwise supply, so the
   demonstration lever survives the cut. `examples` and `project_context` are
   dropped — the latter because its instruction is to `Read` project docs in
   full, which alone can exceed the whole budget, and `workflow`'s
   `<!--requires:project_context-->` guard already makes the drop safe.
2. **Tool surface** — `Shell`, `Read`, `Write`, `Edit`, `Grep`, `LS`, `Glob`,
   `RM`, `MV`, `MonitorProcess`. Everything else is unregistered, including
   every MCP toolset. What survives is registered **eagerly**: `defer_loading`
   swaps a tool's schema for a `search_tools` entry the model must call first,
   which pays when it hides a dozen tools and inverts at ten. `minimal` would
   spend ~146 tokens of `search_tools` to hide `MonitorProcess`'s ~127 and
   charge a ~3B model a discovery turn to poll a background process.
3. **Selection** — the same declared-size mechanism ADR-0047 established, which
   this record now owns. `auto` consults user declarations from
   `register_model_profile` first, then the built-in table. `minimal` matches a
   stated parameter count of 4B or less; `lean` keeps 5–14B.

   The two bands are deliberately asymmetric. `lean` keeps every section and
   tool and only reshapes prose, so a false positive is cheap — which is why
   vendor small-tier labels (`mini`, `micro`, `nano`, `tiny`, `lite`, `haiku`)
   all resolve there. `minimal` *removes* sections and tools, so a false
   positive costs real capability. Only a stated ≤4B count selects it: a label
   is never enough, because `nano`/`tiny` sit on models (`gpt-5-nano`) far more
   capable than a 3B local one. A local model is declared into `minimal`
   explicitly.

Two invariants bound what a preset may do.

- **Composition may drop method; it may never drop safety.** Priority Order
  rank 1 — secrets, tool results are data not instructions, confirm destructive
  actions — must be present in every preset. Everything below it is droppable.
  This is what makes a lean section list safe, and it is testable: assert the
  rank-1 content appears in each preset's composed prompt.
- **A preset's tool set is closed under docstring cross-reference.** Tool
  docstrings route between each other ("Not to touch files: Read/Write/Edit …
  RM/MV to remove and move"). A docstring naming a tool the preset does not
  register is a dangling pointer with nothing to catch it — the docstring ships
  with its schema regardless of configuration, so it cannot carry a
  `<!--requires:-->` guard. This is the tool-side analogue of ADR-0046's
  reads-whole-on-its-own invariant, and it is what sets the size of the set.

  The obvious six — `Shell`, `Read`, `Write`, `Edit`, `Grep`, `LS` — leave four
  dangling references. `Shell` and `Grep` route callers to `Glob`/`RM`/`MV` for
  work they decline, and `Shell`'s `background=True` returns a handle only
  `MonitorProcess` can poll, so advertising the parameter without the tool is a
  trap rather than a saving. Closing the set costs ~500 tokens and is not
  optional. `MonitorProcess` is factory-built, which is also why a preset
  filters the tool factories rather than skipping them.

**Consequences.** The three presets now order as the principle requires:
`full` 9,020 tokens of preamble, `lean` 8,897, `minimal` 3,468.

The `lean` figure is the honest disappointment. Its rulebook fell 25%
(3,295 → 2,464 tokens) but its total moved 1.4%, because the 1,200 tokens of
added demonstrations very nearly cancel the saving, and because the full tool
surface is 4,070 tokens — **46% of `lean`'s budget**. Its rule *count* barely
moved either (43 → 41): `workflow.lean.md` compresses rules rather than removing
them, which is the right conservative default but is not a large lever. The
measurement therefore says something useful about where to look next: for
`lean`, prose is not the binding constraint and the tool surface is.

`minimal` composes to roughly 3,500 tokens of preamble against ~9,000 — inside a
~3B model's effective window with room to read a file. The preset is one knob,
so a user sets `ZRB_LLM_PROFILE=minimal` (or lets `auto` resolve it from
`ollama:qwen2.5:3b`) rather than coordinating three settings that can disagree.
Worth flagging for that audience: Ollama's default `num_ctx` is 4096 unless
raised, which a 3,500-token preamble very nearly fills on its own.

`workflow.lean.md` is a third rulebook to keep in step with `workflow.md`, and the
monotonic-burden test constrains only its size, not its content. The rank-1
safety assertion covers what must never be lost; ordinary rule drift between the
three files is bounded by nothing and is the standing cost of this decision.

The costs are real and should not be undersold. A `minimal` session has no web
access, no skills, no sub-agents, no todo list, no journal and no project-doc
reading — it is a single-tool-call-per-turn assistant, not an agentic coder, and
no prompt engineering changes that at ~3B. `workflow.minimal.md` is a second
rulebook that can drift from `workflow.md`; the rank-1 safety assertion bounds
the drift that matters, and nothing bounds the rest, which is the price of a
ladder of rulebooks. The tool-closure invariant means adding
a cross-reference to a `minimal` tool's docstring can silently pull a tenth tool
into the preset or create a dangle, so it needs the same brute-force test
treatment `test_section_composition.py` gives sections.

The existing `LLM_SMALL_MODEL` slot remains the better home for a ~3B in a
mixed setup — summarizer and extractor prompts are already 568–3,800 chars and
need none of this. `minimal` serves the case where a small local model must drive
the main loop, not the case where it assists a larger one.

**Alternatives rejected.** *Distinct `workflow_lean` / `workflow_micro` sections
instead of variants* — the first cut of this record, taken to route around an
earlier ADR-0047 that forbade a subtracting variant. It bought no safety, since
the guard was always the burden and safety tests rather than the file naming,
and it cost a second convention for varying a section's text. ADR-0047 rule 2
was rewritten to bound *where a rule lives* rather than *which direction a
variant may move*, and the sections collapsed back into
`workflow.{profile}.md`. *Leave it to `LLM_INCLUDE_SECTIONS` plus a new tool
knob* — honest separation of concerns, rejected because it makes the user
assemble a working configuration from three settings and offers no way for
`auto` to select one. *Keep `LLM_PROFILE` phrasing-only and add `LLM_MODEL_TIER`*
— same objection, plus two knobs whose valid combinations are mostly invalid.
*Trim tool docstrings for `minimal`* — ADR-0056 already identifies count as the
lever and prose as the wrong one; per-preset docstrings would fork the tools
themselves. *Six tools, accepting the dangling references* — 500 tokens is not
worth a routing instruction naming tools the model cannot call, plus a
`background=True` parameter whose handle nothing can poll. *Keep
`MonitorProcess` deferred under `minimal`* — deferral is free only when it hides
enough; at ten tools the `search_tools` entry costs more than the tool it hides.
*A separate `minimal` monolith in opencode's style* — the duplication ADR-0047
rejected, and `minimal` needs only one variant file the others do not use.
*Name the presets `terse`/`mini`/`micro`* — the first cut, replaced because the
names were not one axis (`terse` is a register, the others are sizes), because
`terse` labelled the *largest* preset, and because `micro` collided with a
vendor tier label and lost. *Do nothing and document that ~3B is unsupported* —
defensible, and the measurement says the gap is one variant file and one
registration filter, not an architecture change.

**Where it lives.** `src/zrb/llm/prompt/profile.py` (preset table,
`DEFAULT_MODEL_PROFILES`, `resolve_profile`, `register_model_profile`),
`src/zrb/llm/prompt/manager.py` (preset → section list + variant threading),
`src/zrb/llm/common_tools.py` (preset → tool surface gate),
`src/zrb/config/mixins/llm_prompt.py` (`LLM_PROFILE`),
`src/zrb/llm/prompt/markdown/workflow.minimal.md`, `AGENTS.md` (LLM Prompt
System).
