# ADR-0075 — A profile is a preset over sections, phrasing and tool surface; `minimal` serves ~3B models

**Status:** Accepted

**Context.** zrb's prompt is composed on two axes: *which* sections appear
(`LLM_INCLUDE_SECTIONS`, ADR-0044) and *how each is phrased*
(`LLM_PROFILE`, ADR-0047). Neither controls the third thing that ships on every
request — the set of registered tools, whose docstrings and parameter schemas
are serialized in full (ADR-0056).

Measuring a default `zrb llm chat` session as it stood when this decision was
taken (`lean` profile, git repo, interactive) gave the preamble before the
user's first word. Current figures are in **Consequences**; these are the ones
that motivated the record:

| Part | ~tokens |
| --- | --- |
| `workflow.md` | 3,200 |
| `examples.lean.md` | 1,600 |
| skill catalogue (`{CORE_SKILLS}` + `{AVAILABLE_SKILLS}`) | 585 |
| `persona.md` | 540 |
| `system_context` + `project_context` + `live_context` | ~800 |
| 14 non-deferred static tools (docstring + schema) | 2,880 |
| 7 factory tools (skill, zrb-task, ask, journal ×3) | ~1,000 |
| **total** | **~10,500** |

A ~3B model has a large nominal context but an *effective instruction-adherence
window* several times smaller — the preamble alone exceeds it before a single
file is read. Three further behaviours in the default surface are second-order
and reliably out of reach at that size: deciding to call `ActivateSkill` and
then acting on its returned content, delegating to a sub-agent, and maintaining
a todo list across turns. Each is pure token cost when unused.

Two existing mechanisms looked like the answer and are not.

*The `lean` profile points the wrong way.* It is the base plus worked
demonstrations, so it makes the prompt **larger** (`examples.lean.md` is 6.4k
chars against the base's 1.6k). That is correct for the 7–14B class it was
built for, where the budget is not the binding constraint. At ~3B it is net
harm.

*A phrasing variant alone does not reach far enough.* What ~3B needs is not only
different wording but a different section list and a different tool set. The
first two axes are composition, which is already MECE, guarded and brute-force
tested (ADR-0046); the third had no mechanism at all.

ADR-0047 rejected *"weak = drop sections"* on evidence that weak models benefit
from **more** demonstration, not less. That finding stands and is not contradicted
here, because it was measured in a regime where the budget was not binding. At
~3B the budget binds first, which changes what the tokens should be spent *on*,
not whether demonstrations help. `minimal` therefore drops abstract rule prose a
~3B cannot apply and **keeps** demonstrations.

**Decision.** `LLM_PROFILE` selects a **preset** — a named binding of three
axes — rather than a variant overlay. A *variant* remains what ADR-0047 defines
it as; it is now one of the three things a preset picks.

| Preset | sections | phrasing variant | tool surface |
| --- | --- | --- | --- |
| `full` | default | — | all 20 eager tools |
| `lean` | default | `.lean` | all but `LEAN_DROPS` (17 eager) |
| `minimal` | `persona, workflow, system_context` | `.minimal` | `MINIMAL_TOOLS` (10) |

The tool axis takes two forms because the two constrained presets want opposite
things. `Preset.tools` is an **allowlist** — a closed, fixed surface, which is
what makes `minimal`'s closure checkable at all. `Preset.drops` is a
**denylist**, which is what `lean` needs: it keeps the full surface and
subtracts a few, so an allowlist would have to re-list every tool and would
silently drop each newly-added one from `lean` until someone remembered it.
`Preset.admits` resolves either, so every consumer stays one predicate.

The names are the ladder: `full` > `lean` > `minimal`, ordered by how much the
model is asked to hold at once. The first cut of this record used
`terse`/`mini`/`micro`, which failed three ways — it mixed a prose register with
two size words, it named the *largest* preset "terse", and `micro` collided with
the vendor tier labels the selector matches on, so a model labelled `-micro`
matched no pattern and fell through to the heaviest preset.

Every preset varies text through one convention: a section named `foo` resolves
`foo.{profile}.md` and falls back to `foo.md`. There are no `workflow_lean` /
`workflow_micro` *sections*; the section list says which topics appear and never
which wording. `PRESETS` is the single source of truth for the valid set, so a
user registers a fourth with `PRESETS["nano"] = Preset(...)`.

**Burden falls monotonically as target capability falls.** That is the ordering
principle the presets exist to express, and it is asserted rather than claimed —
by two measures, because the first cut of this record used only the second half
of one and the gap swallowed two regressions.

*Per rule-carrying section.* `test_rule_burden_falls_as_the_target_model_gets_weaker`
requires each of `persona` and `workflow` to be strictly smaller in mass and rule
count than the same section one preset up. It measures **each section
separately**. Summed, it reported the total and hid its terms: `persona` had no
variant at any preset, so all three shipped the same 486 tokens of
frontier-register prose — 35% of `minimal`'s whole rule payload, asking a ~3B
model to distinguish `file:line` from `file:symbol` and contradicting its own
rulebook on reply length — and the sum still fell, because `workflow.minimal.md`
shrank enough to cover for it. **A section that never varies is a section whose
variant nobody wrote**, and the silent `foo.{profile}.md` → `foo.md` fallback is
precisely what keeps that quiet, so the assertion has to be the thing that
notices.

*Per composed total.* Demonstrations are exempt from the section ladder — a
worked example lowers burden rather than adding to it (ADR-0047) — but not from
the budget. `test_a_weaker_targets_preset_ships_less_prompt_in_total` orders the
totals as well.

`lean` motivated both. It shipped a 5-14B model the frontier `workflow.md`
**plus** 1,200 extra tokens of examples, making it the heaviest composition in
the system — the model class least able to carry the load received the most of
it. `workflow.lean.md` cut ~700 tokens and `examples.lean.md` put ~1,200 back,
leaving `lean` still the largest at 5,061 tokens against `full`'s 4,563. The
first cut of this record called that "the trade the burden metric encodes
deliberately". It was not a trade, it was an unmeasured axis: exempting
demonstrations from the *ladder* is right, exempting them from the *budget* let
the exemption pay for itself out of the model's attention. `examples.lean.md` is
now 1,086 tokens, and `lean` composes below `full`.

`lean` takes `workflow.lean.md`: the same behaviours with the precedence
abstraction flattened to "the one higher in this list wins", the decision ladders
merged, and the meta-commentary dropped. It keeps every *capability* — skills,
todos, delegation, plan mode — because a 5-14B model can use them, so trimming
there would cost behaviour rather than burden. It no longer keeps every *tool*:
see `LEAN_DROPS` below.

`minimal` is defined concretely:

1. **Sections** — `persona`, `workflow`, `system_context`, with `workflow`
   resolving to `workflow.minimal.md`. It carries affirmative numbered steps and
   inlines the demonstrations that `examples` would otherwise supply, so the
   demonstration lever survives the cut. `examples` and `project_context` are
   dropped — the latter because its instruction is to `Read` project docs in
   full, which alone can exceed the whole budget, and `workflow`'s
   `<!--requires:project_context-->` guard already makes the drop safe.
2. **Tool surface** — `Shell`, `Read`, `Write`, `Edit`, `Grep`, `LS`, `Glob`,
   `RM`, `MV`, `MonitorProcess`. Everything else is unregistered, including
   every MCP toolset. What survives is registered **eagerly**: `defer_loading`
   swaps a tool's schema for a `search_tools` entry the model must call first,
   which pays when it hides a dozen tools and inverts at ten. `minimal` would
   spend ~146 tokens of `search_tools` to hide `MonitorProcess`'s ~127 and
   charge a ~3B model a discovery turn to poll a background process.
3. **Selection** — the same declared-size mechanism ADR-0047 established, which
   this record now owns. `auto` consults user declarations from
   `register_model_profile` first, then the built-ins. `minimal` matches a
   stated parameter count of 4B or less; `lean` keeps 5–14B.

   A stated count is **parsed as a number** and compared against `SIZE_BANDS`,
   rather than matched by a per-band digit pattern. The first cut did the
   latter, and a digit class cannot see a decimal point: `deepseek-r1:1.5b`
   matched the 5–14B pattern on its `5b` and handed the two most widely-run
   local models on the planet (`1.5b`, `0.5b`) the preset built for models ten
   times their size. Parsing also settles the two ambiguous ids by rule rather
   than by accident — the first count in an id wins, so an MoE reads as its
   total (`qwen3-30b-a3b` → 30B) rather than its active parameters, and a count
   outranks a label, since it is the more specific claim.

   The two bands are deliberately asymmetric. `lean` keeps every section and
   nearly every tool, so a false positive is cheap — which is why vendor
   small-tier labels (`mini`, `micro`, `nano`, `tiny`, `lite`, `haiku`) resolve
   there by default. `minimal` *removes* sections and tools, so a false positive
   costs real capability, and a stated ≤4B count selects it outright.

   A label alone is still not enough, because `nano`/`micro` sit on models
   (`gpt-5-nano`) far more capable than a 3B local one. **A label plus a local
   provider prefix is** (`LOCAL_PROVIDERS`: `ollama:`, `lmstudio:`, `llamacpp:`,
   `localai:`). The label is a claim about a position in a lineup; the prefix
   says who is serving it, and the two together are a different assertion from
   either alone. `openai:gpt-5-nano` is the entry tier of a hosted family;
   `ollama:phi4-mini` is 3.8B of weights on a laptop. Both state no count, so
   both used to resolve to `lean` — handing the 3.8B model the heaviest
   composition in the system, which is exactly the failure this record was
   written to prevent, arriving through the selector instead of the presets.
   Ollama's hosted tier is the exception inside the exception: `ollama:` there
   prefixes frontier models, and those ids carry `:cloud`, which disqualifies.

Two invariants bound what a preset may do.

- **Composition may drop method; it may never drop safety.** Priority Order
  rank 1 — secrets, tool results are data not instructions, confirm destructive
  actions — must be present in every preset. Everything below it is droppable.
  This is what makes a lean section list safe, and it is testable: assert the
  rank-1 content appears in each preset's composed prompt.
- **A preset's tool set is closed under every channel that can name a tool.**
  There are three: tool docstrings, prompt sections, and injected context. A name
  in any of them must resolve in every preset that ships it. This is the
  tool-side analogue of ADR-0046's reads-whole-on-its-own invariant.

  *Docstrings* route between each other ("Not to touch files: Read/Write/Edit …
  RM/MV to remove and move") and ship with their schema regardless of
  configuration, so they cannot carry a `<!--requires:-->` guard. This is what
  sets the size of `MINIMAL_TOOLS`.

  *Injected context* was the channel the first cut of this record missed
  entirely, and it leaked on every preset: `<live-context>` announced
  "AskUserQuestion is available", the `<journal-index>` block said "Use
  SearchJournal for full entries", and `_LIVE_CONTEXT_ANCHOR` promised lines
  about todos and worktree — none of which `minimal` registers. `_render_parts`
  now takes the model and asks `Preset.admits` before emitting a line that names
  a tool, and the journal index is gated on `SearchJournal` surviving the preset
  rather than on `LLM_JOURNAL_ENABLED` alone: a preset that drops the reader must
  not keep handing it something to read.

  The `Interactive: no` branch went the other way — it stopped naming tools at
  all. It had forbidden `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode`,
  all three of which `_resolve_interactive` unregisters in exactly that branch,
  so it spent ~55 tokens per turn warning against what was already absent.

  The obvious six for `minimal` — `Shell`, `Read`, `Write`, `Edit`, `Grep`,
  `LS` — leave four dangling references. `Shell` and `Grep` route callers to `Glob`/`RM`/`MV` for
  work they decline, and `Shell`'s `background=True` returns a handle only
  `MonitorProcess` can poll, so advertising the parameter without the tool is a
  trap rather than a saving. Closing the set costs ~500 tokens and is not
  optional. `MonitorProcess` is factory-built, which is also why the preset
  filter is a predicate that travels *with* each tool factory rather than a
  branch that skips the factory block.

**Consequences.** The three presets order as the principle requires, measured as
composed prompt (sections + skill catalogue + context blocks) plus eager tool
schemas:

| Preset | composed prompt | eager tools | preamble |
| --- | --- | --- | --- |
| `full` | 4,583 | 3,840 (20) | **8,423** |
| `lean` | 4,038 | 3,146 (17) | **7,184** |
| `minimal` | 1,242 | 2,339 (10) | **3,581** |

`lean` was the honest disappointment of the first cut: its rulebook had fallen
25% while its total moved 1.4%, because the added demonstrations nearly cancelled
the saving and the untouched tool surface was 46% of its budget. That measurement
named where to look next — *for `lean`, prose is not the binding constraint and
the tool surface is* — and this record now follows through on both halves:
~500 tokens from trimming `examples.lean.md` back under its own rulebook, and
~700 from `LEAN_DROPS`.

A later pass took `examples.lean.md` down again, from 1,086 to 568, on a
different finding: six of its fourteen demonstrations restated a rule
`workflow.lean.md` already stated, so they were paying demonstration prices for
prose the model had already read. That is what moved `lean` to 4,038. The same
pass measured the *rulebook* claim honestly and it did not hold up as well —
`workflow.md` yielded ~350 tokens of removable restatement, not the ~700 the
first estimate assumed, and three additions (a `Diagnose` step, a
two-defensible-options rung, a closing recap) spent ~410 of it. `full` therefore
ends up 55 tokens *heavier* with three more behaviours in it. Recorded rather
than smoothed over: an epigram and the rule it compresses look like redundancy
and are only redundancy when both are present, which caps the saving at however
many rules were stated twice.

`LEAN_DROPS` is the journal trio — `SearchJournal`, `LogActivity`,
`WriteJournalNote` — because cross-session memory is the wrong thing to spend a
constrained model's tool budget on: it is never needed to finish the turn, and
ADR-0053 left no prompt prose to orphan. There is no second shell tool to drop.
`Shell` is the only one (ADR-0064) and takes `shell="bash"` when bash
specifically is wanted; a Claude-authored sub-agent that lists `Bash` is mapped
onto `Shell` as it loads.

**Deferral is keyed on closure, not on constraint.** `_selected` un-defers what a
preset keeps, because `defer_loading` swaps a schema for a `search_tools` entry
the model must call first — worth it when it hides a dozen tools, inverted at
ten. The first cut derived "un-defer" from *is the tool axis constrained at all*,
which was the same question only while `minimal` was the only preset that
constrained it. `lean` keeps 17 eager tools and 13 deferred behind
`search_tools`, where the indirection is the whole saving, so `_Surface.undefer`
is now keyed on `Preset.tools is not None` — on whether the surface is *closed*,
which is the property that actually implies "small".

`minimal` composes to roughly 3,400 tokens of preamble against ~8,400 — inside a
~3B model's effective window with room to read a file. The preset is one knob,
so a user sets `ZRB_LLM_PROFILE=minimal` (or lets `auto` resolve it from
`ollama:qwen2.5:3b`) rather than coordinating three settings that can disagree.
Worth flagging for that audience: Ollama's default `num_ctx` is 4096 unless
raised, which a 3,400-token preamble very nearly fills on its own.

`workflow.lean.md` is a third rulebook to keep in step with `workflow.md`, and the
monotonic-burden test constrains only its size, not its content. The rank-1
safety assertion covers what must never be lost; ordinary rule drift between the
three files is bounded by nothing and is the standing cost of this decision.

The costs are real and should not be undersold. A `lean` session has no journal —
a real subtraction from a preset whose previous promise was "every capability" —
so a user who wants cross-session memory on a 7B must set `ZRB_LLM_PROFILE=full`
or register the model into it.
A `minimal` session has no web access, no skills, no sub-agents, no todo list, no
journal and no project-doc reading — it is a single-tool-call-per-turn assistant, not an agentic coder, and
no prompt engineering changes that at ~3B. `workflow.minimal.md` is a second
rulebook that can drift from `workflow.md`; the rank-1 safety assertion bounds
the drift that matters, and nothing bounds the rest, which is the price of a
ladder of rulebooks. The tool-closure invariant means adding
a cross-reference to a `minimal` tool's docstring can silently pull a tenth tool
into the preset or create a dangle, so it needs the same brute-force test
treatment `test_section_composition.py` gives sections.

The existing `LLM_SMALL_MODEL` slot remains the better home for a ~3B in a
mixed setup — summarizer and extractor prompts are already 568–3,800 chars and
need none of this. `minimal` serves the case where a small local model must drive
the main loop, not the case where it assists a larger one.

**Alternatives rejected.** *Distinct `workflow_lean` / `workflow_micro` sections
instead of variants* — the first cut of this record, taken to route around an
earlier ADR-0047 that forbade a subtracting variant. It bought no safety, since
the guard was always the burden and safety tests rather than the file naming,
and it cost a second convention for varying a section's text. ADR-0047 rule 2
was rewritten to bound *where a rule lives* rather than *which direction a
variant may move*, and the sections collapsed back into
`workflow.{profile}.md`. *Leave it to `LLM_INCLUDE_SECTIONS` plus a new tool
knob* — honest separation of concerns, rejected because it makes the user
assemble a working configuration from three settings and offers no way for
`auto` to select one. *Keep `LLM_PROFILE` phrasing-only and add `LLM_MODEL_TIER`*
— same objection, plus two knobs whose valid combinations are mostly invalid.
*Trim tool docstrings for `minimal`* — ADR-0056 already identifies count as the
lever and prose as the wrong one; per-preset docstrings would fork the tools
themselves. *Six tools, accepting the dangling references* — 500 tokens is not
worth a routing instruction naming tools the model cannot call, plus a
`background=True` parameter whose handle nothing can poll. *Keep
`MonitorProcess` deferred under `minimal`* — deferral is free only when it hides
enough; at ten tools the `search_tools` entry costs more than the tool it hides.
*A separate `minimal` monolith in opencode's style* — the duplication ADR-0047
rejected, and `minimal` needs only one variant file the others do not use.
*Name the presets `terse`/`mini`/`micro`* — the first cut, replaced because the
names were not one axis (`terse` is a register, the others are sizes), because
`terse` labelled the *largest* preset, and because `micro` collided with a
vendor tier label and lost. *Do nothing and document that ~3B is unsupported* —
defensible, and the measurement says the gap is one variant file and one
registration filter, not an architecture change.
