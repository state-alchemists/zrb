# ADR-0107 — Voice runs on Pipecat's pipeline, and the meaning stays zrb's

**Status:** Accepted

**Context.** zrb's voice was hand-rolled: `src/zrb/llm/dictation/` held a microphone cutter, a barge-in state machine and the transcript guards; `src/zrb/llm/speech/` a speaker that plays in process so speech can be paused (ADR-0103, ADR-0105); a wake-word gate sat in front of both. The question was whether to hand that to a framework instead of carrying it.

Whether zrb's audio can run inside Pipecat's pipeline at all was settled by measurement before adoption: the imports and Silero VAD cost tens of megabytes and a fraction of a second, a `PipelineTask` runs inside an asyncio loop that is already running (Pipecat's `TaskManager` binds to the running loop, so no second event loop is needed), and zrb can keep the microphone — an upstream-pushed `InputAudioRawFrame` takes the same path as device audio once a small transport subclass marks itself ready, so PortAudio and Pipecat's local transport are not required.

The remaining question was whether the *whole* voice can be Pipecat's with nothing lost. It cannot. What Pipecat provides is a media pipeline: frames, voice-activity detection, turn signalling, streaming transcription and synthesis, interruption propagation, and metrics.

What it has no notion of is what any of that *means*. A transcript of "no" is a denial of a tool call if a prompt is waiting, a stop if it was said over speech, an instruction if neither, and a transcriber's guess if the microphone only heard a cough. That mapping depends on zrb's prompt state, turn state, session state and word lists — none of which crosses into Pipecat.

**Decision.** zrb adopts Pipecat for the **models its voice runs** — the speech-to-text a session listens through and the text-to-speech it speaks through are Pipecat services — and keeps every **decision** about meaning in zrb. The boundary is a rule, not a hope: Pipecat answers *what audio event is happening*; zrb answers *what that means for this chat session*.

The service is named, not built. `ZRB_LLM_DICTATION_BACKEND` names an STT service (`whisper`, `moonshine`, `funasr`) and `ZRB_LLM_SPEECH_BACKEND` a TTS one (`kokoro`, `piper`, `pocket`), resolved through ADR-0090's registry-and-manager shape in `zrb.llm.voice` (`stt_registry`, `tts_registry`, `stt_manager`, `tts_manager`), so a project registers its own service from `zrb_init.py` without forking zrb.

zrb owns the microphone device and everything decided from what it hears: the cutter's boundaries, the transcript guards (wake words, stop words, approvals, minimum words, transcriber guesses), prompt and approval routing, the pydantic-ai agent, its stream events and hooks, per-session speech control, and the transcript semantics of every backend.

zrb still cuts the utterance. `UtteranceCutter` decides where speech begins and ends, and the service is handed a finished segment — told, in Pipecat's own terms, that speech spanned it (`VADUserStartedSpeakingFrame`, the audio, `VADUserStoppedSpeakingFrame`) — and answers with a `TranscriptionFrame`. Pipecat's voice-activity detection is not in that path.

Playback stays zrb's, and stays in process. zrb asks the TTS service for a sentence's audio (`TTSSpeakFrame`, answered with `TTSAudioRawFrame`) and plays it through `PcmUtterance`: pause, resume, interrupt, external-player fallback and session isolation are zrb requirements, and no Pipecat output transport is involved. vosk stays zrb's own backend rather than a custom STT service, because its offline model, its partials and its per-word confidence are what the guards read, and Pipecat's transcription frames carry text only.

A pipeline's lifetime is zrb's, and idle is its normal state. A service loads its model in its constructor, so one pipeline is built per backend and kept for the session, handed one utterance at a time. Pipecat's idle watchdog is therefore off (`idle_timeout_secs=None`) on every worker zrb builds: by default it cancels a worker that has heard nothing for a few minutes, after which every later utterance fails with "the Pipecat worker stopped". zrb closes a pipeline itself, at the session's teardown.

A pipeline that stops without that close — a processor ending the worker, or a failure its run task does not survive — counts as stopped, and is not kept either. `STTPipeline.is_closed` reads the worker's own run task beside the flag `close` sets, so the backend starts another before the next utterance rather than failing every one after it, at the price of loading the model again.

That close is scheduled onto the loop that owns the pipeline rather than run where the teardown happens. A teardown is synchronous, and a session may be served on a thread that is not the pipeline's: a worker is a task of its own loop, and awaiting it from another one fails with a cross-loop error that is only logged, leaving the worker, the model and the pipeline running after the session that owned them is gone.

So a backend names its loop (`AnyDictationBackend.owner_loop`), the close is handed to it thread-safely, and a backend whose loop has stopped is released rather than closed: what it holds is dropped, so the model behind its pipeline can be collected, and the teardown says the worker could not be cancelled. A loop that stops in the window between being asked whether it is running and being handed the close takes that same release, because a closed loop refuses the hand-off where the question cannot see it.

zrb does not run Pipecat's own turn detection: there is no Pipecat VAD or semantic turn-end stage in front of the cutter, and no flag that feeds capture to one. Reintroducing one means building the latency instrument (speech-end to final transcript, transcript to first token, first token to first audio) before it can be judged against the cutter.

What shipped keeps `UtteranceCutter` where it is and puts a Pipecat service behind it, so the boundary a listener gets is unchanged from the hand-rolled voice, with a service that can be swapped under the guards without changing what a user's words mean.

**Consequences.** ADR-0102's backend seam carries this unchanged. `config.backend` is still a built-in name or an object, `get_dictation_backend` and `get_speech_backend` still resolve it, and a Pipecat service is one more name in that lookup rather than a second mechanism beside it; what lets a *project* add a name is ADR-0090's registry.

ADR-0103 stands as written: zrb asks a TTS service for a sentence's audio and plays it itself, so pause, resume, interrupt and the fallback to an external player are zrb's code, and an interrupted reply is still not spoken again when the turn ends.

Costs:

- **Third-party churn is in the critical path.** Pipecat deprecates and renames pipeline classes between releases, and some of its documentation lags its API (`VADAnalyzer.analyze_audio` returns a `VADState`, not a confidence). A Pipecat upgrade is a change to test, not a lockfile bump.
- **Heavy dependencies in the `voice` extra.** `pipecat-ai` pulls `openai`, `onnxruntime`, `numba`, `soundfile`, `soxr` and `resampy`, whether zrb uses them or not. The core install does not carry them.
- **Text-only transcription frames.** `TranscriptionFrame` and `InterimTranscriptionFrame` carry no confidence and no word list, so anything that depends on per-word confidence has to be rebuilt at the STT service — which is why vosk stays zrb's own backend.
- **An adapter layer zrb owns.** The code between Pipecat's frames and zrb's policy is new code the framework would otherwise have supplied. What it buys is that a user-visible behavior cannot change as a side effect of an audio refactor.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Full generic replacement: Pipecat owns capture, turn policy, dictation, the agent, the UI routing and playback | The simplest shape and the one a framework's own examples suggest. Rejected because it gives up behavior users already have: spoken approvals answering the prompt they were asked, wake words, push-to-talk's editable transcript, vosk's offline confidence, per-session speech control, and the rule that an interrupted reply is not spoken again when the turn ends. That is a new voice product, not a migration. |
| Keep zrb's stack and borrow only the models (Silero VAD, a smart-turn ONNX model) | Cheaper, and dependencies stay out. Rejected because zrb would still own the cutter, the state machine, the guards and the playback, and every edge case they encode would have to be re-derived against models that change under it — the larger cost. |
| LiveKit | Needs a room and a server — a bigger cut than zrb's in-process, single-user voice. |
| pydantic-ai's `[livekit]` / `[pipecat]` extras | They invert the architecture: zrb's voice is a peripheral that plugs into the chat task (ADR-0102), while pydantic-ai's voice extras make the voice pipeline the centre and embed the agent inside it. |
| WebRTC echo cancellation | No wheel for Termux, musl Linux or Windows on ARM, so it could not ship; ADR-0105 already rejected it for the same reason. |

**Where it lives.** The services are named and resolved in `src/zrb/llm/voice/` (`spec.py`, `registry.py`, `manager.py`, `builtin.py`); the speech-to-text half is `src/zrb/llm/dictation/pipecat_stt.py` behind `src/zrb/llm/dictation/backend/pipecat.py`; the text-to-speech half is `src/zrb/llm/speech/pipecat_tts.py` behind `src/zrb/llm/speech/backend/pipecat.py`; and every pipeline zrb stops or unwinds is torn down through `src/zrb/llm/util/teardown.py`. The voice design page — the boundary, the parts and their invariants — is [`voice-on-pipecat.md`](../architecture/3-peripheral-flow/voice-on-pipecat.md). Pipecat is the `voice` extra rather than a core dependency, so an install that never turns voice on does not pay for the stack.
