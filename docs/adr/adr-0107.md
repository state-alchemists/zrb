# ADR-0107 — Voice runs on Pipecat's pipeline, and the meaning stays zrb's

**Status:** Accepted

**Context.** zrb hand-rolls its voice. `src/zrb/llm/dictation/` (about 3,100 lines with its backends) holds a microphone cutter, a barge-in state machine and the transcript guards; `src/zrb/llm/speech/` (about 2,600 lines with its backends) holds a speaker that plays in process so speech can be paused (ADR-0103, ADR-0105); a wake-word gate sits in front of both. The maintainer asked whether that should be handed to a framework instead of carried by zrb.

The first question — can zrb's audio run inside Pipecat's pipeline at all — was settled by measurement, not by reading. Everything below was reproduced in an isolated throwaway venv (pipecat-ai 1.12.0, Python 3.13, macOS arm64), and nothing was merged:

- `import pipecat` takes 0.068 s; the pipeline, task and frames imports take 0.396 s; RSS after imports is 58.4 MB.
- Silero VAD loads in 0.142 s; RSS after load is 95.2 MB; a 32 ms frame costs about 0.33 ms, roughly 1 % of one core.
- A `PipelineTask` ran to completion inside an asyncio loop that was already running, while another coroutine kept ticking (37 iterations during the run). Pipecat's `TaskManager` binds to the running loop, so no second event loop is needed.
- zrb does not have to give up the microphone. `BaseInputTransport.process_frame` feeds an upstream-pushed `InputAudioRawFrame` through the same path as device audio; the only gap is that the base `start()` never calls `set_transport_ready()`. A four-line subclass fixes it, so PortAudio and Pipecat's local transport are not required.

The second question, asked later, was whether the *whole* voice can be Pipecat's with nothing lost. It cannot. What Pipecat provides is a media pipeline: frames, voice-activity detection, turn signalling, streaming transcription and synthesis, interruption propagation, and metrics.

What it has no notion of is what any of that *means*. A transcript of "no" is a denial of a tool call if a prompt is waiting, a stop if it was said over speech, an instruction if neither, and a transcriber's guess if the microphone only heard a cough. That mapping depends on zrb's prompt state, turn state, session state and word lists — none of which crosses into Pipecat.

**Decision.** zrb adopts Pipecat for the **models its voice runs** — the speech-to-text a session listens through and the text-to-speech it speaks through are Pipecat services — and keeps every **decision** about meaning in zrb. The boundary is a rule, not a hope: Pipecat answers *what audio event is happening*; zrb answers *what that means for this chat session*.

The service is named, not built. `ZRB_LLM_DICTATION_BACKEND` names an STT service (`whisper`, `moonshine`, `funasr`) and `ZRB_LLM_SPEECH_BACKEND` a TTS one (`kokoro`, `piper`, `pocket`), resolved through ADR-0090's registry-and-manager shape in `zrb.llm.voice` (`stt_registry`, `tts_registry`, `stt_manager`, `tts_manager`), so a project registers its own service from `zrb_init.py` without forking zrb.

zrb owns the microphone device and everything decided from what it hears: the cutter's boundaries, the transcript guards (wake words, stop words, approvals, minimum words, transcriber guesses), prompt and approval routing, the pydantic-ai agent, its stream events and hooks, per-session speech control, and the transcript semantics of every backend.

zrb still cuts the utterance. `UtteranceCutter` decides where speech begins and ends, and the service is handed a finished segment — told, in Pipecat's own terms, that speech spanned it (`VADUserStartedSpeakingFrame`, the audio, `VADUserStoppedSpeakingFrame`) — and answers with a `TranscriptionFrame`. Pipecat's voice-activity detection is not in that path.

Playback stays zrb's, and stays in process. zrb asks the TTS service for a sentence's audio (`TTSSpeakFrame`, answered with `TTSAudioRawFrame`) and plays it through `PcmUtterance`: pause, resume, interrupt, external-player fallback and session isolation are zrb requirements, and no Pipecat output transport is involved. vosk stays zrb's own backend rather than a custom STT service, because its offline model, its partials and its per-word confidence are what the guards read, and Pipecat's transcription frames carry text only.

A pipeline's lifetime is zrb's, and idle is its normal state. A service loads its model in its constructor, so one pipeline is built per backend and kept for the session, handed one utterance at a time. Pipecat's idle watchdog is therefore off (`idle_timeout_secs=None`) on every worker zrb builds: its 300 s default cancels a worker that has heard nothing that long, after which every later utterance fails with "the Pipecat worker stopped". zrb closes a pipeline itself, at the session's teardown.

A pipeline that stops without that close — a processor ending the worker, or a failure its run task does not survive — counts as stopped, and is not kept either. `STTPipeline.is_closed` reads the worker's own run task beside the flag `close` sets, so the backend starts another before the next utterance rather than failing every one after it, at the price of loading the model again.

That close is scheduled onto the loop that owns the pipeline rather than run where the teardown happens. A teardown is synchronous, and a session may be served on a thread that is not the pipeline's: a worker is a task of its own loop, and awaiting it from another one fails with a cross-loop error that is only logged, leaving the worker, the model and the pipeline running after the session that owned them is gone.

So a backend names its loop (`AnyDictationBackend.owner_loop`), the close is handed to it thread-safely, and a backend whose loop has stopped is released rather than closed: what it holds is dropped, so the model behind its pipeline can be collected, and the teardown says the worker could not be cancelled.

The plan below moved in stages, each behind a flag, with both paths green, and only after the old path's boundaries had been shown to match the new one's on recorded audio. Measurements were to come before replacement, because what a listener wants to know is speech-end to final transcript, transcript to first token, and first token to first audio, and zrb had none of it. The services needed none of that: zrb already knows where an utterance ended, because it cut it.

The migration landed as those two services rather than in the stage order planned below, and it is worth recording why the order changed and what happened to what the plan put first. Stage 1's tap — `ZRB_LLM_DICTATION_PIPECAT_ENABLED=on` fed the capture to its own `[transport, detector, metrics stage, counter]` — ran behind its flag for one release and was then removed. The detector that was to replace the cutter's loudness bars, and the semantic turn end that was to follow it, were abandoned; with no stage after it depending on the tap, the flag turned nothing on that a session acted on.

That closes the plan rather than pausing it. What the tap measured is gone with it, so reopening the detector's turn means rebuilding the instrument before it can be judged — the one cost of the removal, and cheaper than a flag that promises a migration nobody is making.

What shipped keeps `UtteranceCutter` where it is and puts a Pipecat service behind it, so the boundary a listener gets is unchanged from the hand-rolled voice, with a service that can be swapped under the guards without changing what a user's words mean.

**Consequences.** ADR-0102's backend seam survives, and it is what carried the migration. `config.backend` is still a built-in name or an object, `get_dictation_backend` and `get_speech_backend` still resolve it, and a Pipecat service is one more name in that lookup rather than a second mechanism beside it. The clause this record expected to die — "A new service needs no change to zrb" — is the one it leans on: what the seam could not do is let a *project* add a name, which is ADR-0090's registry, and that is the shape the services are resolved through.

ADR-0103 stands as written. Its ownership clause was expected to die — playback reached through a Pipecat output transport instead of zrb's own loop — and it did not: zrb asks a TTS service for a sentence's audio and plays it itself, so pause, resume, interrupt and the fallback to an external player are the same code they were, and an interrupted reply is still not spoken again when the turn ends.

Third-party churn moves into the critical path, and it is not quiet. `WakeCheckFilter` is deprecated since 0.0.106 and removed in 2.0.0; `PipelineTask` is deprecated since 1.3.0 in favour of `PipelineWorker`; and `VADAnalyzer.analyze_audio` returns a `VADState`, not a confidence, which is what most documentation still says. All three are already carried in 1.12.0, so the pinned version has known churn inside it.

Its worker also cancels itself after five idle minutes — a sound rule for a transport-driven call, and the wrong one for a pipeline kept across a session's utterances, which is how it took both pipelines down mid-session before zrb passed `idle_timeout_secs=None`.

Adoption adds hard dependencies: the core install pulls `openai`, `onnxruntime`, `numba`, `soundfile`, `soxr` and `resampy`, whether zrb uses them or not.

`TranscriptionFrame` and `InterimTranscriptionFrame` carry text only — no confidence, no word list — so anything that depends on vosk's per-word confidence has to be rebuilt at the STT service, not read off the frame.

Keeping the guards in zrb has a cost of its own, and this record does not hide it: the adapter layer between Pipecat's frames and zrb's policy is new code that the framework would otherwise have supplied. What it buys is that a user-visible behavior cannot change as a side effect of an audio refactor.

Honesty clause. The recommendation was to keep zrb's stack and borrow only the models — Silero VAD and a smart-turn ONNX model — which is cheaper and meets the same goal. The maintainer weighed it and overrode it: borrowing the models still leaves zrb owning the cutter, the state machine, the guards and the playback, and every edge case they encode then has to be re-derived by zrb against models that change under it.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Full generic replacement: Pipecat owns capture, turn policy, dictation, the agent, the UI routing and playback | The simplest shape and the one a framework's own examples suggest. Rejected because it gives up behavior users already have: spoken approvals answering the prompt they were asked, wake words, push-to-talk's editable transcript, vosk's offline confidence, per-session speech control, and the rule that an interrupted reply is not spoken again when the turn ends. That is a new voice product, not a migration. |
| Keep zrb's stack and borrow only the models (Silero VAD, a smart-turn ONNX model) | The cheaper option and the one recommended: dependencies stay out, and the microphone, cutter, guards and playback stay zrb's. Rejected by the maintainer — owning the turn-management layer against models that change under it was judged the larger cost. |
| LiveKit | Needs a room and a server — a bigger cut than zrb's in-process, single-user voice. |
| pydantic-ai's `[livekit]` / `[pipecat]` extras | They invert the architecture: zrb's voice is a peripheral that plugs into the chat task (ADR-0102), while pydantic-ai's voice extras make the voice pipeline the centre and embed the agent inside it. |
| WebRTC echo cancellation | No wheel for Termux, musl Linux or Windows on ARM, so it could not ship; ADR-0105 already rejected it for the same reason. |

**Where it lives.** The services are named and resolved in `src/zrb/llm/voice/` (`spec.py`, `registry.py`, `manager.py`, `builtin.py`); the speech-to-text half is `src/zrb/llm/dictation/pipecat_stt.py` behind `src/zrb/llm/dictation/backend/pipecat.py`; the text-to-speech half is `src/zrb/llm/speech/pipecat_tts.py` behind `src/zrb/llm/speech/backend/pipecat.py`; and every pipeline zrb stops or unwinds is torn down through `src/zrb/llm/util/teardown.py`. The plan, the boundary table, the stages and the regression gates are `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`. Pipecat is the `voice` extra rather than a core dependency, so an install that never turns voice on does not pay for the stack.
