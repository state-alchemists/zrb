# ADR-0074 — `ask_user_choice` is an optional protocol method with a text fallback

**Status:** Accepted

**Context.** The question tool rendered each question as numbered text and read the answer through `UIProtocol.ask_user(prompt: str) -> str`. Arrow-key selection was wanted in the terminal UIs, against two hard constraints: `ask_user` has six implementers and is *also* used for tool approval and sub-agent prompts, so its `-> str` contract cannot move; and the default UI is a single full-screen prompt-toolkit `Application`, which cannot host a nested `Application` — only one owns the terminal and the event loop.

**Decision.** Add one *optional* protocol method, `ask_user_choice(spec: ChoiceSpec) -> str`, alongside the unchanged `ask_user`. `BaseUI` provides a default implementation that formats the spec as the same numbered text and delegates to `self.ask_user`, so every non-terminal implementer keeps working untouched, and the question tool routes through it guarded by `hasattr`.

Terminal UIs override it: StdUI uses prompt-toolkit's dialog helpers, since it has no running `Application`; the default UI renders an in-layout float driven by a selection part — **not** a nested `Application`. To keep one serialization path, the confirmation queue was generalized from `(future, prompt)` to `(future, prompt, spec)`: a `None` spec renders as text, a `ChoiceSpec` renders the widget, and both share the single active slot, so a parallel sub-agent's text confirmation and a choice can never contend for input. A synthetic "type my own answer" row drops to free text through the existing input field, and in multi-select the checked labels are carried as a prefix and combined with the typed text.

**Consequences.** Arrow-key selection in both terminal UIs with zero changes to the web, simple and multi-UI, and sub-agent paths, which inherit the text fallback. `ChoiceSpec` is a plain `TypedDict` and the return stays `str`, so the existing number-to-label resolution still applies and a widget returning a label is idempotent through it. Costs: the confirmation ordering contract — render before marking pending, or the output-buffer guard swallows the prompt — now governs choice rendering too; the app-level Enter and newline bindings are gated by a filter so the widget owns those keys while a choice is shown; and the free-text combine path overrides the confirmation handler ahead of it in the MRO.

**Alternatives rejected.** *A nested dialog inside the default UI* — fights the running `Application` for the terminal; unsupported. *Overload `ask_user` to accept structured input* — breaks the `-> str` contract that tool approval and sub-agent callers rely on, and forces all six implementers to branch. *A separate choice queue* — two competing "active input" states that can contend when a parallel sub-agent's approval prompt coincides with a choice. *One multi-question panel* — higher effort and more edge cases; questions render sequentially through the existing per-question loop.

**Where it lives.** `src/zrb/llm/tool_call/ui_protocol.py` (`ask_user_choice`, `ChoiceSpec`), `src/zrb/llm/ui/base/ui.py` (the fallback), `src/zrb/llm/ui/default/selection.py`, `src/zrb/llm/ui/default/confirmation.py`, `src/zrb/llm/tool/ask.py`.
