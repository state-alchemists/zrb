# ADR-0018 — Three-tier context: SharedContext, Session, Context

**Status:** Accepted

**Context.** A run needs both run-wide shared state (env, inputs, XCom, logs)
and per-task isolation, so one task's env edits do not leak to its siblings —
and the same task may run more than once within a single run.

**Decision.** Three layers. **SharedContext** holds run-wide shared data.
**Session** holds mutable run state — statuses, upstream/downstream maps,
per-task contexts, deferred coroutines. **Context** is per-task: attempt count,
task name, a *copy* of env, display colour and icon. An action receives its own
`ctx`.

**Consequences.** Tasks cannot clobber each other's env or inputs, shared data
lives in exactly one place, and ownership of mutable state is explicit. The
cost is three concepts to keep distinct.

**Alternatives rejected.** *A single global context* — needs defensive copying
at every call site, and one forgotten copy is a cross-task bug. *Implicit-only
access* — hard to trace what a task actually read.

**Where it lives.** `src/zrb/session/session.py`, `src/zrb/context/context.py`,
`src/zrb/context/shared_context.py`,
`docs/core-concepts/session-and-context.md`.
