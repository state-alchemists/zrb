# ADR-0035 — Compose large classes from parts via explicit collaborators, not multiple inheritance

**Status:** Accepted

**Context.** `BaseUI` had become a god object — `ui.py` at ~1,019 lines and its slash-command companion at ~907 — each mixing unrelated concerns. The original fix (see history in git/changelog) kept every attribute on one shared `self` and split cohesive method clusters into classes the host combined via **multiple inheritance** (`class LLMChatTask(ChatBuilding, ChatRunning, ChatExecution, BaseTask)`), each part declaring a `TYPE_CHECKING` "host-contract" block naming what it assumed the host provided. That fixed the file-size problem, but `class Owner(Part1, Part2, Part3)` reads as inheritance ("Owner IS-A Part1 AND a Part2 AND a Part3") when the real relationship is "Owner HAS-A Part1, a Part2, ...". A reader has to already know the codebase's convention to see that these parts are not reusable bases — nothing else in the tree calls this out, so the class statement itself is misleading. Every part's `TYPE_CHECKING` host-contract block was also a second, hand-maintained copy of the host's real attribute types.

**Decision.** Replace multiple inheritance with composition: the owner constructs each part and holds it as a named attribute, and the owner alone keeps a normal single-inheritance base (`BaseTask`, `BaseUI`, ...) where that is a genuine is-a relationship.

1. **A part becomes a class instantiated by its owner**, not a base class: `self._building = LLMTaskBuilding(self)` instead of `class LLMTask(LLMTaskBuilding, ...)`. `TYPE_CHECKING` host-contract blocks disappear — a part's constructor parameter is typed as the real owner class, so a type checker verifies every access directly against it instead of a hand-maintained duplicate.
2. **How a part reaches what it needs is chosen per part, not by one blanket rule:**
   - *Pure data, no cross-part calls* (e.g. `SubAgentManagerSearch`, `LSPManagerLifecycle`'s own caches): passed directly as constructor/method arguments.
   - *Needs one specific sibling's behavior* (e.g. `LSPManagerQuery` needs `LSPManagerLifecycle`): holds a direct reference to that already-constructed sibling.
   - *Needs behavior spread across several siblings and the owner's own directly-defined methods, or state reachable through a public setter the owner may reassign after construction* (e.g. `BaseUICommands`'s conversation/model/exec collaborators, which call into `BaseUIReplay`, `BaseUISystemInfo`, and `BaseUI` itself; `LLMTaskBuilding`, whose `history_manager` has a public setter): holds a reference to the **owner**, and reaches its state **only through a public property or method** — never the raw underscored attribute (`self._owner.x`, not `self._owner._x`). If the owner has no public accessor yet, add one; this is a one-line cost per piece of state, the same shape as the delegators in point 3. The owner is the single facade every part calls through, so an instance-level patch or subclass override of a method (`patch.object(ui, "append_to_output", ...)`, a test double overriding `stream_btw_response`) is honored uniformly, regardless of which composed part actually implements it — and the public accessor means a test reaching the same state does too, without touching a private name.
3. **The owner re-exposes every previously-inherited public method/property as a one-line delegator** (`def append_tool(self, *t): self._building.append_tool(*t)`), so every external call site keeps working unchanged. A method that was reachable under the old inheritance only because it happened to be `_`-prefixed but is in fact called from outside the owner (a sibling part, or a test) gets its delegator — and the part's own method — **promoted to public** rather than kept private: "private" under single-object inheritance meant "module-internal by convention," but under composition the same name is a cross-object reach, which case 3 above (point 2) treats as a defect. The owner's own pre-existing methods that called an inherited part method by bare name need no changes, since the new delegator provides the same name.
4. **`Mixin` stays reserved for classes that are actually reusable** — they read no state they do not set, so any class can mix them in (`BufferedOutputMixin`, the `CFG` mixins under `config/mixins/`). This is unaffected by this decision: those classes were never part of the multiple-inheritance-per-owner pattern being replaced.
5. **A part is still named `<Owner><Aspect>`**, in a file named for the aspect: `ChatExecution` in `task/chat/execution.py`, `BaseUICommands` in `ui/base/commands.py`. No `_mixin` suffix, no leading underscore.
6. **`X/manager/manager.py` flattens** to `X/manager.py` plus `X/manager_<aspect>.py`, unchanged from before.

**Consequences.** Every constructor and public method signature is unchanged — this was a pure internal restructuring, verified by the full existing test suite passing without modification to test *intent* (a handful of tests that subclassed a part directly, e.g. `class MockLLMChatTask(ChatRunning)`, `class MockUI(BaseUICommands)`, were adapted to construct the real composed collaborator with a stand-in owner instead — the behavior each test checks is unchanged). State **is** encapsulated behind public accessors: a part reaches its owner (or a sibling) only through a public property or method, never a raw underscored attribute — `self._owner._attr` two-hop reaches (and the mirror-image `self._part._attr` reach from the owner down into a part) are a defect to fix, not an accepted shape, and the test suite enforces this at zero tolerance (`zrb-test.sh`'s private-access ratchet). This was tightened after the initial composition pass shipped with `self._owner._attr` reaches throughout and a "not encapsulated" caveat here — a later pass swept every one of them to a public accessor instead. Costs: an owner now carries one delegator per part method (mechanical, but real line count), a part reaching several collaborators takes the whole owner rather than a narrower interface, and each piece of cross-part *state* (not just behavior) costs one small get/set property pair where a bare attribute would have done — same mechanical trade as the method delegators.

A subtler cost surfaced converting `UI` in `llm/ui/default/ui.py`: two of its seven parts (`UISelection`/`UIConfirmation`) cooperated through `super()` calls that only resolved correctly because MRO flattened them onto one `self` — `UISelection.handle_confirmation` fell through to `UIConfirmation`'s base case via `super()`, and `UIConfirmation` called `self.begin_choice`/`self.end_choice` expecting `UISelection`'s override (declared as no-ops on `UIConfirmation` "so it works standalone"). Composition has no MRO to fall back on, so `UISelection` now holds a **direct reference to its `UIConfirmation` sibling** (case 2) purely for that one base-case call — routing it through `self._owner` would loop back into `UISelection`'s own owner-level delegator — while `begin_choice`/`end_choice`/`resolve_current` are all public methods that route through the owner (case 3), so a test double or subclass overriding any of them is honored uniformly, and a test asserting on the same call goes through the public name too. The no-op defaults moved off `UIConfirmation` entirely: a standalone owner that composes only `UIConfirmation` (as several tests do) now supplies its own trivial `begin_choice`/`end_choice`, the same way any test double supplies whatever collaborator state its composed part expects.

Also worth naming: state that lives on one part but is read (or written) by a sibling through the owner needs a **public** forwarding property *on the owner*, not just on the part that owns it, and not a private one either. `UIAgentPicker`'s `viewing_agent_id`/`saved_main_output` are read by `UIOutput`/`UIKeybindings`/`UIConfirmation` via `self._owner.viewing_agent_id` — without a `viewing_agent_id`/`saved_main_output` property on `UI` itself forwarding to `self._agent_picker`, that owner attribute doesn't exist, so the read silently falls back to `getattr(..., default)` (or, for an outright assignment, pyright catches it as `reportAttributeAccessIssue`). An earlier version of this same fix made that forwarding property private (`_viewing_agent_id` on `UI`, mirroring the part's own backing field) — but a private property on the owner is exactly as unreachable to an external caller (or a test) as no property at all, so it does not satisfy case 3's "reach state only through a public accessor" rule; it just relocates the violation from "no accessor" to "private accessor". The fix is the same three-case pattern applied one level up, with the accessor public both ends: since several parts need this state and one of them writes it, the owner exposes it as a real **public** get/set property over the part that actually holds it.

**Alternatives rejected.** *Extract real collaborator objects with a narrower interface per part* (e.g. `LSPManagerQuery` takes a `Callable[[str], Awaitable[LSPServer | None]]` instead of the whole `LSPManagerLifecycle`) — more decoupled, but was not needed to satisfy the actual constraint (public API preservation) and would have made the "owner passes exactly what a part needs" judgment call harder to apply uniformly across parts with very different needs. *Collapse each family's constructor into config objects* — a breaking change to public surface, out of scope for a behavior-preserving refactor. *Leave the multiple-inheritance form and rely on the naming discipline alone* — the naming already existed and did not resolve the underlying complaint that the class statement itself reads as multiple inheritance.

**Where it lives.** `src/zrb/llm/ui/base/`, `src/zrb/llm/ui/default/`, `src/zrb/llm/task/`, `src/zrb/llm/task/chat/`, `src/zrb/llm/lsp/`, `src/zrb/llm/agent/subagent/manager.py`, `src/zrb/llm/ui/polling_ui.py`, `src/zrb/llm/ui/event_driven_ui.py`, `src/zrb/llm/ui/queue_based_input.py`, `src/zrb/task/base/` (`BaseTask`'s own parts — `BaseTaskContext`, `BaseTaskExecution`, `BaseTaskLifecycle`, `BaseTaskMonitoring`, `BaseTaskOperators`), `AGENTS.md` (Code Style).
