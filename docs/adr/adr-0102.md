# ADR-0102 — Runtime rules move into the tools, not into tool policies

**Status:** Accepted (applies ADR-0098's ladder)

**Context.** ADR-0098 sorts every rule by what can make it true: the runtime
first, then the tool's docstring, then the prompt, then a skill. Two rules were
sitting in the prompt that the runtime can enforce, and a benchmark run showed
both being ignored by models that had read them.

**1. Overwriting a file the model has not seen since it last changed.**

`Edit` carries `old_text`, so it fails loudly when the model's memory has
drifted. `Write` carries nothing — it replaces the whole file on the strength of
the model's recollection. A trial read `worker.py`, edited it, received a
`[DIAGNOSTIC]` reporting three errors, and answered by rewriting the file whole
from memory. The rewrite flipped the worker's empty-queue exit from `return` to
`continue`, shipping an infinite loop; the validator subprocess hung and the
cell was recorded as an error.

Note what a plain read-before-write precondition — the rule opencode and Claude
Code both enforce — would have done here: nothing. The model *had* read the
file. What was missing was not a read but a **current** one.

Worse, `post_write_check`'s own `[SYSTEM SUGGESTION]` steered into it: on a
second failing edit it said "stop patching it — rewrite the whole file with
`Write` instead", without saying to re-read first.

**2. Repeating an attempt that has stopped producing new evidence.**

`workflow`'s Recovery ladder says "By the third, change what you are testing — or
stop and report what you cannot get past." One trial spent 89 tool calls across
**four files** — 32 shell runs, 45 writes — re-running the same simulation until
its 600s budget expired, having written mid-run that "the changes made to the
logic did not yield the intended results" and then continuing anyway. It is the
clearest single rule violation in the run, from a model that had the rule in
context the whole time.

**Decision.** Enforce both rules **inside the tools themselves**. Neither is a
`tool_policy`: the policy chain is an *approval* chain, so a policy can deny a
call but never annotate its result, and it is only consulted when a
`ToolCallHandler` is bound — which a headless run does not do.

`write_file` refuses a whole-file overwrite of a file the model has not seen
since it last changed. `zrb.llm.tool.file_freshness` records, per path, the
fingerprint of the content the model last saw in full across three transitions —
a **complete** `Read` → fresh, `Write` → fresh (the model authored every byte),
`Edit` → stale — and re-stats the file to answer the question, so a change made
by anything else counts too. Deliberately narrow: `Edit` is never gated,
appending is never gated, creating a new file is never gated, and a *partial*
read does not grant a whole-file write (a 20-line window says nothing about the
other 380). The refusal names the one action that unblocks it — **specifically**,
including the span the last read actually covered and the fact that the read must
carry no line range. "`Read` it" alone was not enough: with numbered lines a
ranged read is the norm, and a model that had read lines 1-21 of 48 read that
instruction as already satisfied and re-sent the same write four more times. A
repeated refusal escalates, since re-issuing a refused write cannot succeed.

> **This is in the tool, not in a tool policy — and that is the whole point.**
> It was a policy first. Across 125 benchmark cells it refused nothing, while a
> replay of its own logic over one trial's trace predicted 37 refusals.
> `check_tool_policies` is only reached when `effective_tool_confirmation`
> resolves to a `ToolCallHandler`, which `--interactive false` does not bind —
> so the guard evaporated in exactly the mode the benchmark used, and its unit
> tests passed throughout. `bash_safe_command_policy` inherits the same
> limitation; that predates this record and is still open.

A second counter in the same module names a **blind edit streak**: consecutive
`Edit`s to one path with no read of it and no command run in between, default 8
(`LLM_BLIND_EDIT_STREAK_THRESHOLD`). One benchmarked cell spent 68 calls making
59 edits to a single file, ran nothing, produced no diagnostic, and exhausted
its 600s budget — invisible to both the shell-only repetition counter and the
diagnostic-gated post-write escalation. Consecutiveness on one path is what
separates this from legitimate breadth: a 44-site migration makes hundreds of
edits across dozens of paths, never many in a row on one.

The repeated-attempt counter lives **in the shell tool**, not in a policy
(`zrb.llm.tool.command_repetition`, appended by `run_shell_command`). It counts
runs keyed by `(cwd, command)` whose **outcome** repeats — same exit code, same
output digest — and, on the
`LLM_REPEATED_ATTEMPT_THRESHOLD`-th (default 3, matching the prose ladder),
appends a `[SYSTEM SUGGESTION]` to the result. It never denies — an agent
legitimately re-runs a test suite many times, and blocking that would be worse
than the loop it prevents — and it fires once per signature, not on every
subsequent call. `run_bash_command` delegates to `run_shell_command`, so both
share one counter.

> **Counting invocations was wrong and shipped.** `debug-loop` asks the agent to
> run, fix, run, fix, run; keyed on the invocation, every *passing* cell of that
> challenge across four models was told to stop. Measured over the run that
> straddled the fix: 26 nudges in 173 cells before, 24 of them on EXCELLENT
> cells; **0 nudges in 115 cells after**. Re-running a command after changing
> the code is new evidence — re-running it and getting the same answer is not.
> A second ground covers what the digest cannot: same command with nothing at
> all happening in between (no write, no edit, no other command), which catches
> a nondeterministic command whose output can never repeat.

> **A tool policy cannot do this.** The first implementation was one, and it was
> dead code: `check_tool_policies` is an *approval* chain returning
> `ToolApproved | ToolDenied | None`, so a policy's `next_handler` yields the
> next policy's decision, never the tool's output. The note was appended to
> `None`, silently dropped on every call, and emitted nothing across 32
> benchmark cells. Response handlers are no better — they process the *user's*
> approval text. Annotating a result requires the tool itself.

`post_write_check` appends **one** suggestion, at most twice per file, asking for
a re-read and *one targeted fix*. It deliberately does not recommend a whole-file
rewrite, and it deliberately stops talking rather than escalating — see the
measurement in Consequences.

**Consequences.**

- The failure mode that produced the shipped regression is now unreachable
  rather than discouraged.
- A model that has genuinely lost track of a file pays one extra `Read`. That is
  the intended cost.
- The Recovery observation arrives *during* the loop, on the result the model is
  about to read, instead of in a rule it read hundreds of calls earlier.
- Neither guard depends on a host capability: both run inside the tool, so they
  hold on every host (`LLMChatTask`, programmatic `LLMTask`, `SubAgentManager`)
  and in every mode, interactive or not.
- **Open, and now confirmed by measurement:** the tool-policy chain does not run
  under `--interactive false`. `bash_safe_command_policy` — which carries the
  git approval rule — is therefore inert in headless runs. That predates this
  record and needs its own fix.
- The shell-side counters (`command_attempts`, `command_attempts_warned`,
  `workspace_revision`) are `ContextVar`s: their writer is `async`, and a
  sub-agent's own commands are not the parent's attempts.
- **The escalating post-write ladder is withdrawn, on measurement.** It made
  `gpt-4o-mini` worse. A paired A/B (6 cells x 3 trials, one model, identical
  env, only the zrb tree swapped) put the pre-ladder build at 11/18 and 215 tool
  calls against 8/18 and 366 calls with it, controls unchanged. Mechanism: rung
  two prescribed "`Read` the file in full, then replace it in a single `Write`",
  and a small model's whole-file rewrite regenerates the diagnostic that
  re-issues the instruction — on `refactor`, 10 calls became 51. A "stop and
  report" rung did not help either; one trial ignored it 22 times. What remains
  is a single suggestion asking for *one targeted fix*, capped at two
  appearances per file, after which the errors are reported with nothing
  appended. **Invariant: an injected instruction must be bounded, and must not
  prescribe an action that regenerates its own input.** The repetition counter
  and blind-edit nudge satisfy both by firing once per streak, which is why
  neither showed up in the regression.
- **The freshness state is not, and was wrong to be.** As `ContextVar`s
  `file_freshness` and `edit_streaks` recorded nothing at all: their principal
  writer is `read_file`, which is *synchronous*, so `create_safe_wrapper`
  dispatches it via `asyncio.to_thread` — a **copied** context, whose
  `ContextVar.set` calls are discarded on return. `Read` therefore never marked
  a file fresh, `refuse_stale_write` refused *every* whole-file `Write` to an
  existing file with "you have not read it" however many times it had just been
  read, and the blind-edit nudge fired claiming "nothing read in between" after
  a read before every edit. Both are plain module-level dicts now. The
  per-context isolation this bullet used to advertise was also backwards on the
  merits: a sub-agent's write is a change the *parent* must see before it
  overwrites the file.
- **Freshness is verified against the file, not remembered.** What is stored per
  path is the fingerprint (`st_mtime_ns` + `st_size`) of the content the model
  last saw in full, and `is_file_fresh` re-stats and compares. A remembered bit
  only ever described what these three tools did, while the refusal text claims
  something stronger — that the file has not changed since the last full read.
  `sed -i`, a formatter, `git checkout`, a build step, and a sub-agent all left
  the bit reading fresh and the overwrite went through, which is this record's
  own failure mode with a different author.

**Alternatives considered.**

- *Strengthen the prompt instead.* Both rules are already in the prompt, and
  `gpt-4o-mini` resolves to the `mini` profile, so it also received the worked
  demonstrations ("Do it, don't announce it", "'Almost done' is not done"). More
  text was not the missing ingredient.
- *Gate `Edit` too.* `old_text` matching already enforces currency; a
  precondition there is friction without cover.
- *Deny the repeated command rather than annotate it.* Rejected. There is no
  reliable way to tell a diagnostic re-run from a stuck loop, and a false denial
  costs more than a false nudge.
- *Fuzzy-match "the same attempt".* Rejected. A model that varies its command is
  changing what it tests, which is precisely the behaviour being asked for.
- *Count invocations rather than outcomes.* Tried, shipped, and reverted — see
  the note above. It punished the one challenge whose task **is** to iterate.
- *Deny a blind edit streak rather than annotate it.* Rejected for the same
  reason as the command case: there is no reliable way to tell deliberate
  shaping of one region from a stall, and a false denial costs more.
- *Inject via `live_context`.* It renders once per user turn. A non-interactive
  run is a single turn, so it cannot reach a loop mid-flight; a tool result can.

**Evidence.** `llm-challenges` run of 2026-08-05, 156 cells. `bug-fix/trial-3`
(gpt-4o-mini): `Read worker.py` → `Edit worker.py` → `Write worker.py`, the
write reverting `return` to `continue`. `integration-bug/trial-2` (gpt-4o-mini):
89 calls, 4 distinct paths, 32 `Shell`, timeout at 600s.
