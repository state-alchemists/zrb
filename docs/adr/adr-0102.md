# ADR-0102 — Runtime rules move into the tools, not into tool policies

**Status:** Superseded — the whole mechanism was removed in 2.55.0 before
release and never shipped. (Was: Accepted, applies ADR-0098's ladder.)

**Context.** ADR-0098 sorts every rule by what can make it true: the runtime
first, then the tool's docstring, then the prompt, then a skill. A benchmark
run of 156 cells showed two rules already in the prompt being ignored by models
that had read them:

- **Whole-file `Write` over a stale file.** `Edit` carries `old_text` and fails
  loudly on drift; `Write` replaces the whole file on the strength of the
  model's recollection. One trial read `worker.py`, edited it, and answered a
  diagnostic by rewriting the file whole from memory — flipping the empty-queue
  exit from `return` to `continue` and shipping an infinite loop.
- **Repeating an attempt that stopped producing new evidence.** `workflow`'s
  Recovery ladder already said "by the third, change what you are testing".
  One trial re-ran the same simulation for 89 tool calls until its 600s budget
  expired, having written mid-run that the changes "did not yield the intended
  results".

**Decision (reverted).** Enforce both rules inside the tools. `write_file`
would refuse an overwrite of a file the model had not seen since it last
changed (`zrb.llm.tool.file_freshness`); `Edit` would name a blind edit streak;
the shell tool would count repeated-outcome runs and append a
`[SYSTEM SUGGESTION]` (`zrb.llm.tool.command_repetition`). Neither guard was a
`tool_policy`: the policy chain is an *approval* chain that never sees a
result, and it is only consulted when a `ToolCallHandler` is bound — which
`--interactive false` does not do.

**Why it was reverted.** The mechanism's own evidence argued against shipping
it:

- An injected instruction is the weakest lever for exactly the model that needs
  it — an escalated "stop and report" was ignored **22 times** in one trial.
- The stale-write refusal is a hard block carrying the most cross-tool
  accounting state in the tool layer, and it deadlocked against
  `post_write_check`'s own recovery guidance.
- Every component that measurably made models worse — invocation-counting, the
  post-write escalation ladder — was already reverted within this same
  design's history. The prompt's Recovery ladder stands on its own again.

**Lessons that survive.** These hold regardless of the mechanism:

- **A tool policy cannot annotate a result.** `check_tool_policies` is an
  approval chain returning `ToolApproved | ToolDenied | None`; its
  `next_handler` yields the next policy's decision, never the tool's output.
  A note appended there is dropped on every call.
- **A synchronous tool cannot keep cross-call state in a `ContextVar`.**
  `read_file` is synchronous, so `create_safe_wrapper` dispatches it via
  `asyncio.to_thread` — a *copied* context whose `set` calls are discarded on
  return.
- **An injected instruction must be bounded, and must not prescribe an action
  that regenerates its own input** — a whole-file rewrite by a small model
  regenerates the diagnostic that issued the instruction.
- **Outcome repetition, not invocation counting, is the right key for a loop
  detector** — re-running a command after changing the code is new evidence,
  re-running it and getting the same answer is not.

**Evidence.** `llm-challenges` run of 2026-08-05 (156 cells): `bug-fix/trial-3`
and `integration-bug/trial-2`, and the paired A/B on the post-write ladder
(6 cells × 3 trials, one model). See the 2.55.0 changelog's "Reverted" entry.
