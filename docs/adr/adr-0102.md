# ADR-0102 — Optional chat features install through `LLMChatTask`'s extension points, configured when a session starts

**Status:** Accepted

**Context.** `/photo` and `/voice` were built into the UI. `UIConfig` carried their aliases, `BaseUI` their handlers and voice state, the default UI a push-to-talk keybinding, a status-bar badge and completer entries. Twelve files knew about two secondary features, and changing either meant editing the UI.

An example that added speech and hands-free dictation from a `zrb_init.py` showed most of this needs no UI code. `LLMChatTask` already takes slash commands (`append_custom_command`), triggers (`append_trigger`) and hook factories (`append_hook_factory`), and resolves all three when a session starts. What the example could not do was reach the UI: `ActionCommand`'s action got only the parsed arguments, so it could not queue an attachment or put text in the input box. It could not run while the model was thinking, run async work, or complete its argument. A trigger's text could only start a turn, never answer the approval being asked.

**Decision.** A feature the chat can do without is a function that registers on those extension points: `enable_camera(chat, CameraConfig)`, `enable_dictation(chat, DictationConfig)`, `enable_speech(task, SpeechConfig)`. The built-in `llm_chat` calls all three. The UI has no code for any of them.

1. **`enable_` is the verb.** The call switches a feature on for a task; it is not a collection operation, so ADR-0098's `add_`/`append_` would misname it.
2. **Config is read when a session starts, never at import (R3).** `enable_*` registers factories only. Each config dataclass field mirrors one `CFG` knob by name (`CameraConfig.device` is `CFG.LLM_CAMERA_DEVICE`), and `None` means "use the knob". `resolve()` fills the `None` fields inside the factory, so a `zrb_init.py` that sets a knob after importing zrb still applies, and `CameraConfig(device="1")` does not freeze the other fields at the line that built it.
3. **Every behavior is a knob**, both as a `CFG` variable and as a config field: timeouts, thresholds, the phrase said after a cut reply, the words that approve. Nothing tunable is a module constant.
4. **A backend is a name or an object.** Each feature defines `Any<Feature>Backend` (`AnyCameraBackend`, `AnyDictationBackend`, `AnySpeechBackend`) under its `backend/` package, one implementation per module. `config.backend` is either a built-in name, mapped by `get_<feature>_backend`, or an instance of the interface, used as given. A new service needs no change to zrb.
5. **The seams are generic, and each has one meaning.**
   - `ActionCommand`'s action receives `(kwargs, ui)`, where `ui` is `None` when there is none (the initial message of a non-interactive run; an interactive one runs it once the UI exists). An action returning an awaitable runs as one of the UI's `background_tasks`, which the UI cancels on exit, and its result is shown when it finishes. `can_run_while_thinking` lets the command through mid-turn. `complete_arg` completes the first argument.
   - `BaseUI.insert_input_text` puts text at the cursor. A UI with no input box submits it instead.
   - `BaseUI.is_waiting_for_answer`, `pending_answer_since`, `is_waiting_for_choice` and `submit_answer` report, date and answer a pending approval or question.
   - A trigger yielding `TriggerReply` answers what was pending when the user spoke, else starts a turn (ADR-0076 says why only a `TriggerReply` may).
   - `AnyUI.set_status_badge(key, text)` shows a feature's one-line state in the status bar; `None` takes it away. Output is no place for it: the default UI holds output back while an approval is pending mid-turn, which is when dictation most needs to say it heard the answer. A feature owns its key (`"dictation"`) and nothing else about the status bar.
   - `get_session_ui()` returns the UI serving the session asking, bound for the length of a run: the main UI in the terminal, the first attached UI in a non-interactive or web run. A hook runs on a pool thread with the ambient UI cleared, and a trigger is called with no arguments, so neither is handed the UI; this is how speech tells that the approval it is reading out has been answered, and how hands-free dictation reaches the status bar when it was switched on by config rather than by a command. Only the event loop writes to the UI; a hook or the speaker thread only reads from it.
6. **A command with an alias is always offered** (ADR-0093). There is no `ENABLED` gate for camera or dictation; `commands=[]` in the config leaves a command out. For speech, `LLM_SPEECH_ENABLED` sets whether a session starts speaking, and `/speech` is offered either way.
7. **Enabling a feature again replaces it.** `enable_*` remembers what it registered on each task and removes it before registering again, so a `zrb_init.py` can call `enable_speech(llm_chat, SpeechConfig(backend=...))` after the built-in call without a second speaker. Replacement covers the config too, not only the registrations: `replace_feature_sessions` installs the new factory on the registry the first call made, so the sessions started after it are built from the new config, and the sessions the earlier one left running are closed — no speaker thread, no open microphone, no registered hook.
8. **A session is the unit of state, and its key is the chat session, not the task.** One task serves many sessions — the web runner holds one task and scopes `current_chat_session_id` per connection. So `replace_feature_sessions(task, name, create, close)` keys sessions by `(task, name, session_key)`, where the session key is `get_session_ownership_key()`; an interactive CLI run has one session and so has one key. Each session gets its own speaker, microphone, hands-free flag and recorder, and its hooks act only on its own session's events, since a task given a `hook_manager` shares it between sessions. Anything shared between them is keyed by name and reference-counted, so it is forgotten when the last holder goes: the speech lock file a `Speaker` claims is released by `Speaker.close`.
9. **A session's state is closed where the session ends, not by a hook.** `close_feature_sessions(session_key)` closes that session's value in every feature; the interactive CLI's teardown and the web runner's `remove_session` call it. A `SESSION_END` hook would not do: the web runner never fires it, and the `LLM_HOOKS` allowlist can filter it out. Registering a session's hooks is idempotent per manager, so re-applying the factory (`execution.py` does this on every run) cannot leave a second set behind. Speech needs hooks, so `CFG.HOOKS_ENABLED = False` makes it inert, and enabling it logs a warning naming the knob rather than silently doing nothing.
10. **Anything named after the product follows `ROOT_GROUP_NAME`**: the speech lock file, temp-file prefixes, the Termux photo file, the speech thread's name.

**Consequences.** The UI shrank: no voice state, keybinding, photo handler, or command fields for them, and a status-bar badge that any feature can set in place of the one voice owned. A user can replace a feature's backend, move its commands, or leave it out from `zrb_init.py` without forking anything, and a custom `LLMChatTask` gets the same features with one call each. The seams serve other extensions too: any command can now run async, mid-turn, or reach the UI.

The cost is that a feature is no longer one object per task but one per session, so it has to be written to be torn down: a long-lived server would otherwise keep a speaker, a microphone and a set of hooks for every session it ever served. Audio state is the part that cannot be shared — two sessions on one machine would take turns as two *processes* do, and within one task the state a user changes is the state they changed for their own conversation.

The cost is an API break. The action signature changed from `(kwargs)` to `(kwargs, ui)`, `AnyCustomCommand.handle` gained `ui`, and the `LLM_VOICE_*` and `LLM_UI_COMMAND_VOICE/PHOTO` knobs are gone without aliases.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Keep the features in the UI | Every change to a secondary feature is a change to the UI, and a custom UI inherits or reimplements them. |
| A plugin registry (`chat.add_extension(Feature())`) | A second registration mechanism next to the four `LLMChatTask` already has, for three callers. |
| Config dataclasses with `default_factory` reading `CFG` | Building `DictationConfig(mode="ptt")` in `zrb_init.py` would snapshot every other field at that line, before later settings apply. |
| A keybinding extension point | Command-driven push-to-talk (ADR-0076) does not need one. |
| Printing mic state to the output | Held back during a pending approval, and it would fill the transcript with a line per utterance. |
| An `ENABLED` gate per feature | It hides a command instead of letting it explain itself (ADR-0093), and for speech, it would hide `/speech` exactly when speech is off. |
| Aliases for the renamed knobs | A clean break, recorded in the changelog. |

**Where it lives.** `src/zrb/llm/camera/`, `src/zrb/llm/dictation/`, `src/zrb/llm/speech/`, `src/zrb/llm/util/feature_config.py` (`resolve_from_cfg`, `get_feature_sessions`, `FeatureSessions`, `replace_registration`, `set_session_ui`, `get_session_ui`), `src/zrb/llm/custom_command/action_command.py`, `src/zrb/llm/custom_command/any_custom_command.py`, `src/zrb/llm/ui/base/ui.py` (`insert_input_text`, `is_waiting_for_answer`, `pending_answer_since`, `is_waiting_for_choice`, `submit_answer`, `set_status_badge`, `status_badges`), `src/zrb/llm/ui/default/output.py` (the status bar), `src/zrb/llm/ui/trigger.py`, `src/zrb/builtin/llm/chat.py`.
