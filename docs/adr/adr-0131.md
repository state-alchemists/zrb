# ADR-0131 — Speech's player defaults meet the measured machine, and its threads ask to be scheduled above the work that starved them

**Status:** Accepted

**Context.** A borg session's log (`~/.zrb/zrb.log`, October 25, 2026) held 38 `Speech stuttered:` warnings, and every one read the same: the device was left un-fed by a single block of 1024 frames (~43 ms at Pocket's sample rate), mid-sentence, while `PocketTTSService` took 8–43 s to generate a few seconds of audio — sentences generated *while the same chat ran its own tools* ("Let me test it before choosing a side", "Now the wider suites"), the same backend rendering in 1–2 s minutes later without one stutter. The then-defaults (block 1024 frames, cushion 0.4 s, read-ahead 32 chunks) left the callback one scheduling hiccup away from an empty buffer, and no cushion answers a generator that falls tens of seconds behind: prebuffering absorbs only spikes shorter than itself.

**Decision.**

- *The defaults take the measured shape.* `ZRB_LLM_SPEECH_PLAYER_BLOCK_FRAMES` 1024 → 2048 — twice the block is twice the slack each callback has to fill in, and halves how often the device asks; free to the listener. `ZRB_LLM_SPEECH_PLAYER_PREBUFFER_SECONDS` 0.4 → 0.5 — headroom over the worst measured start spikes, costing ~100 ms more pause before each sentence's first word. `ZRB_LLM_SPEECH_PLAYER_READ_AHEAD` 32 → 64 — ~5 s of chunks standing by, which bridges the bursty-but-on-average-faster-than-realtime case in memory (a couple of MB), the one class buffering genuinely covers.
- *Synthesis and the reader ask for priority, best-effort.* `raise_priority` (`src/zrb/llm/util/priority.py`) is called once at the top of the TTS pipeline thread (`TTSPipeline`'s loop in `pipecat_tts.py`) and of each sentence's source-reader thread (`PcmUtterance._read_source` in `pcm_player.py`). On macOS the ask is a thread raising its own QoS to user-initiated — above the classes a chat competes in, below the interactive class a UI holds, and a thread may do that unprivileged. On POSIX it is `setpriority(PRIO_PROCESS, 0, -5)`, which Linux answers about the *calling thread* (threads are tasks there) and declines for an unprivileged caller unless an rlimit grants it — Termux, proot-distro included, is declined with the rest. Platforms with no ask (Windows) and every rejection (EPERM, a library that will not load) answer False, said once at debug, and nothing raises: speech keeps speaking at whatever priority the machine would otherwise grant it.
- *No config knob.* The ask changes nothing unless the machine grants it, and its grant only shortens the wait a listener hears nobody record — so there is nothing to turn off that anyone could want off, and the knob would rename behaviour Unix policy already governs.

**Consequences.** A loaded machine's chat keeps speaking without the one-block clipping that tool-heavy minutes produced — where the contention is *scheduling* (the common case), an outranked generator simply keeps up. The simplification has edges: the 8–43 s class is a generator outrun by its whole platform, and where the machine declines the raise (unprivileged Termux, a hardened rlimit) those sentences stutter as before, said in the log they always said. On Linux the ask is per-thread, so the chat and the tools it spawns keep their own priorities; on the BSDs it names the whole process, so the chat itself rides ahead of whatever else runs that moment — an ask, still bounded by what `setpriority` grants. Nothing is asked of audio *playback*: CoreAudio's callback runs at PlatformAudio's own real-time priority, which no QoS raise would strengthen.

**Alternatives rejected.**

| Alternative | Why rejected |
|---|---|
| Raise the cushion until even 20–43 s of lag is absorbed | A cushion is only as long as the *pause before the first word* nobody complains about is willing to grow; a sentence whose audio is 20 s behind its own playback cannot be cushioned at all, and the "fix" would be minutes of speech arriving minutes from the words. |
| Run Pocket out of process at a raised priority (the ADR-0115 emotion-child shape) | Doubles the machinery (spawn, queue, teardown) for the sentence path to solve what a thread's own QoS ask solves, and pays a child process's chunk latency for every sentence. The out-of-process shape stays a load *memory* answer, which is what it was built for. |
| `nice` the whole speech process down or the whole chat up | Lowering zrb's nice only makes the stutter worse; raising it sweeps the chat's own tools (the tests lading the same log) up with the synthesis — the opposite of the needed split, and children spawned later would inherit it. |
| Deprioritize the tools instead | The chat's tools are the user's work arriving through the same process; speech's ask reads both ways (per-thread) and lands on the side whose absence is *heard*. |

**Where it lives.** `src/zrb/llm/util/priority.py` (`raise_priority`, the macOS and POSIX asks), `src/zrb/llm/speech/pipecat_tts.py` and `src/zrb/llm/speech/pcm_player.py` (the two ask sites), `src/zrb/config/mixins/llm_speech.py` (the three defaults), `docs/configuration/llm-voice-camera.md` (the config rows), `test/llm/util/test_priority.py`.
