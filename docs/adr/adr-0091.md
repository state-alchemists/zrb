# ADR-0091 — Three configuration channels, five component families, one mental model

**Status:** Accepted

**Context.** ADR-0090 gave the LLM subsystem the vocabulary of *registry* (canonical collection) and *manager* (per-occasion resolver) and one resolution order. The split has landed for skills, sub-agents, hooks, and prompts. Tools — the family users touch most ("make my CLI a tool", "drop the worktree tools") — are still hardwired in `common_tools.py`, and the four finished families each expose slightly different mutation shape, so the reader still has to learn five near-miss APIs.

Nor is the *configuration story* told anywhere in user terms: the three channels people actually use (environment variables, `zrb_init.py` appending, `zrb_init.py` replacing) are real but scattered across env-var reference lists, an extending-the-LLM page, and an upgrade guide.

This record consolidates the story. It names the five component families, fixes one uniform mutation surface, connects each family's registry to a `CFG`/env-var twin, and states *when to use which channel*.

**Decision.**

**Part 1 — There are exactly five component families, each with the same shape.**

| Family | Registry (canonical set) | Manager / resolved consumer | CFG twin |
| --- | --- | --- | --- |
| Prompts | `prompt_registry` | `PromptManager` | `CFG.LLM_PROMPT` |
| Tools | `tool_registry` | the task's tool lists (`LLMTask.tools`, …) | `CFG.LLM_TOOLS` |
| Skills | `skill_registry` | `SkillManager` (catalogue + activation) | `CFG.LLM_SKILLS` |
| Sub-agents | `sub_agent_registry` | `SubAgentManager` (roster + delegation) | `CFG.LLM_AGENTS` |
| Hooks | `hook_registry` | `HookManager` (hydration + dispatch) | `CFG.LLM_HOOKS` |

Every registry is **name-registered** (`skill_registry`, `tool_registry`, …), is the **source of defaults**, holds **manual plus discovered** content, supports **deferred values** (ADR-0090 Part 3), and answers queries. Every manager starts from its registry and lets a task pin something narrower.

**Part 2 — One mutation surface, chosen by collection shape.**

- **Ordered pipeline** (order is the semantics — tools, prompts): `append_X`, `prepend_X`, `set_X` (wholesale), `remove_X` (by value).
- **Unordered, name-keyed set** (a key owns its entry — skills, agents, hooks): `add_X`, `set_X` (wholesale), `remove_X(name)` (by key).
- `set_X` accepts a concrete list **or** a deferred callable producing one at use time (ADR-0090 Part 3). There is no `add_X` alias on ordered collections: position is the whole semantics, and `add_` cannot say front or back.

**Part 3 — Every registry has a `CFG` twin, and the twin is a name allowlist over the default layer.**

An env var can only round-trip strings, and most registry content is code or files — so a twin *names* the members it touches. The rule is uniform:

> **When a twin is non-empty, only the named members of the registry's default (discovered) layer are visible — for prompts, only the named prompt strings.** An empty twin means "everything" and is the shipped default.

| Twin | Name key | Semantics when set |
| --- | --- | --- |
| `CFG.LLM_PROMPT` | prompt text | The default appended prompts (strings). The one content twin, because a prompt is a string. |
| `CFG.LLM_TOOLS` | registered tool name | Only these tools are available to agents. |
| `CFG.LLM_SKILLS` | skill name | Only these skills are visible in the catalogue (`LLM_ENABLE_BUILTIN_SKILLS` still gates built-ins independently). |
| `CFG.LLM_AGENTS` | agent name | Only these agents are in the roster. |
| `CFG.LLM_HOOKS` | hook config name | Only these hooks are dispatched. |

A twin is a *coarse filter over the discovered/default layer only* (ADR-0090 Part 2): env names the baseline that stays visible. Content registered manually — `zrb_init.py` `add_*`/`set_*` — layers on top and is always visible; the two compose as "env sets the baseline, code builds on it." The fine-grained, dynamic path is `zrb_init.py` on the registry; a manager or task overrides everything at its own layer. Where a family has no manual/discovered split (tools, hooks), the twin filters the whole single-layer registry rather than only a discovered layer.

**Part 4 — The three channels, stated in user terms.**

**1. Environment variables — scalars and coarse name sets.** Set `ZRB_LLM_*` outside code. For scalars this is `CFG.LLM_*` as today; for component collections it is the name allowlist of Part 3. Channel choice rule: **env vars name things; `zrb_init.py` builds things.**

**2. `zrb_init.py` — appending.** Reach the global registry and add on top of whatever env configured:

```python
# zrb_init.py
tool_registry.append_tool(my_cli_tool)      # ordered: appended last
skill_registry.add_skill(team_skill)         # name-keyed
prompt_registry.append_prompt("Remind me to update the changelog.")
```

Adding layers a delta: appends run last, prepends first, and the delta ops are replayed over the registry's *current* default on every resolved read, so later env changes stay visible (ADR-0090 Part 2 — no freeze).

**3. `zrb_init.py` — replacing.** Either swap a manager on the task (`LLMChatTask(prompt_manager=PromptManager(prompts=[...]))`), or replace a registry's collection wholesale (`prompt_registry.set_prompts(lambda: ...)`). This is how a custom UI, a custom registry, or a fully custom prompt wings in.

**Consequences.** A new reader hears one sentence — "registries hold the defaults, managers read them, env names the allowed members, `zrb_init.py` builds or swaps them" — and can predict the API of the next family they meet. Tools gain the same mutation surface as the other four. The cost: five env twins adds named surface (`ZRB_LLM_TOOLS`, …) whose usual value is zero (defaults are full) — a deliberate trade named here so it reads as a decision, not a missing feature.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Give every twin content semantics (an env-var JSON list becomes the whole set) | JSON-in-env is hostile to edit and to quoting; shipping `ZRB_LLM_PROMPT='["a", "b"]'` invites the sprawl this record exists to end. Name lists and the single prompts exception stay representable and greppable. |
| Make `LLM_TOOLS` a denylist | A denylist inverts the meaning of "twin" (it mirrors `remove_` rather than the set) and reads ambiguously (`LLM_TOOLS` carrying "excluded" was judged worse). Name-allowlist is uniform across all four collection families; per-item exclusion belongs to `zrb_init.py`'s `remove_`. |
| Wire twins by eager copy at startup | Copying `CFG` into the registry at import freezes it before `zrb_init.py` has run. Each twin is read lazily at resolution, inside the deferred-default machinery, so env, `zrb_init.py` mutation order, and later `CFG` edits all compose. |
| Register the five families' five shapes without the ordering rule | Mixed `add_`/`append_` per family re-opens the confusion ADR-0035 addressed; one rule keyed on whether order matters is teachable and checkable. |

**Where it lives.** `src/zrb/llm/tool/registry.py` (`ToolRegistry`, the split this record completes), `src/zrb/llm/prompt/registry.py`, `src/zrb/llm/skill/registry.py`, `src/zrb/llm/agent/subagent/registry.py`, `src/zrb/llm/hook/registry.py`; the twins in `src/zrb/config/mixins/{llm_prompt,llm_search,llm_tool,hooks}.py`; the deferred-default wiring in each registry module; the user-facing story in `docs/configuration/llm-config.md` and `docs/advanced-topics/extending-the-llm.md` (ADR-0090, ADR-0035, ADR-0026).
