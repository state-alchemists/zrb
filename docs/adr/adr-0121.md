# ADR-0121 — A command that outruns its timeout moves to the background instead of dying

**Status:** Accepted

**Context.** `Shell` runs a foreground command under a timeout (120s by default). When the timeout expired, zrb killed the process and reported `(timed out)`, with a suggestion to run it again with `background=True`. Everything the command had produced or done was discarded, and the suggestion cost a second full run of the same work. A user who typed while the command was running paid for it twice over: zrb queues the message and delivers it when the running tool call finishes, so the answer waited for the timeout *and* for the re-run.

Nothing in the tool was missing except the decision. `_ShellBackgroundRegistry` already starts background processes, hands out handles, and offers `MonitorProcess(handle, wait=N, kill=True)`; `cancel_all`, `cancel_for_session` and an `atexit` backstop already reap whatever it holds; `StreamCapture` already spills the full output to disk. The one thing a timed-out process had that a background process did not is a caller still holding its pipes.

The reference harness made the same call from the other end: a foreground Bash command that hits its timeout is *moved to the background* ("Command did not complete within its 120s timeout and was moved to the background"), and gets 30 minutes from the move. It excludes commands that begin with `sleep` — a sleep is a delay, and backgrounding it would let the next command run before the wait finished. Its `Ctrl+B` and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` are the manual and opt-out forms of the same mechanism. Worth stating plainly, because it was the hypothesis being tested: an incoming *message* never backgrounds anything in that harness. Messages queue; only a command's own timeout moves it.

**Decision.**

1. **A timeout adopts the process instead of killing it.** `_ShellBackgroundRegistry.adopt` registers the still-running process under a new handle, with the caller's captures and fresh readers (the caller's own readers were cancelled at the timeout). The output produced before the timeout is still in those captures, so the model reads one continuous stream across the boundary.

2. **`sleep`-like commands are still killed.** A command whose first word is `sleep` is a wait: moving it to the background would let the next command run before the wait it was waiting for was over, and nothing would be gained, because the delay is the work.

3. **The time in the background is bounded.** `LLM_SHELL_TIMEOUT_BACKGROUND_SECONDS` (default 1800 — the reference harness's 30 minutes) is the allowance; at the deadline zrb terminates the process, leaves a line in its stderr capture saying why, and keeps the entry so a later poll explains itself instead of reporting an unknown handle. `0` disables adoption and restores kill-at-timeout.

4. **The result says what happened, and what not to do.** `Exit Code: (moved to background after 120s)`, a `Handle:` line, and a `[SYSTEM SUGGESTION]` naming `MonitorProcess(handle=…)`, its `wait=` and its `kill=True` — plus the instruction not to run the command again, since a re-run is what the old message caused.

5. **The captures outlive the call.** `_format_output` skips `discard()` and the caller skips `_close_transport_if_started` when a handle was returned: the spill file and the pipes now belong to the background entry.

**Consequences.** The work a timed-out command had already done survives, and a queued user message waits for one timeout instead of a timeout plus a second run. A process that would have been killed now outlives the tool call — bounded by the allowance and by `cancel_for_session`/`cancel_all`/`atexit`, and still capped in memory by `LLM_MAX_OUTPUT_CHARS` per stream (on disk it spills without a cap until the deadline, as every truncated stream already did). The `Exit Code` line no longer promises an exit code, so anything parsing `Shell` output must accept `(moved to background after Ns)`. `sleep 300` still costs a full timeout, deliberately.

**Alternatives rejected.**

- *Background the running command when a message arrives* — the hypothesis this ADR replaces. No harness does it: the message is queued until the tool call finishes, and wiring an interrupt to an arrival would take the decision away from the model while diverging from every reference implementation.
- *Automatically re-run the command with `background=True`* — starts the work a second time. A build that hit 120s would begin again from the first file.
- *Keep killing, improve only the message* — the message already told the model what to do and recovered nothing; it was the loss, not the wording, that hurt.
- *Adopt every timed-out command, `sleep` included* — a delay is the work; backgrounding it silently reorders the sequence the caller wrote.
- *No deadline* — a runaway outlives the session. The reference harness bounds a moved command at 30 minutes for the same reason.
- *A second tool for "promote to background"* — the model cannot act during the very tool call it would need to promote; the promotion has to happen at the timeout, inside the tool.

**Where it lives.** `src/zrb/llm/tool/shell.py` (`_adopt_timed_out`, `_is_deliberate_wait`, `_moved_to_background_note`, the timeout branch of `run_shell_command`, `_format_output`), `src/zrb/llm/tool/shell_background.py` (`adopt`, `_arm_deadline`, `_expire`), `src/zrb/config/mixins/llm_limits.py` (`LLM_SHELL_TIMEOUT_BACKGROUND_SECONDS`), `test/llm/tool/test_shell_adopt.py`. See ADR-0066 for `background=True` itself, ADR-0059 for the output cap the adopted process keeps using, and ADR-0077 for the message queue that makes the first response wait.
