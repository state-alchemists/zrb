# ADR-0063 — Opt-in two-layer filesystem sandbox

**Status:** Accepted

**Context.** The permission layer controls *intent* — which tool calls a human
approves — but nothing constrains *blast radius*: an approved or
allowlist-approved shell command, and every in-process file tool, can touch
anything the user can. Containment is needed against prompt injection and model
mistakes, across macOS, Linux and Windows. The file tools cannot themselves be
OS-sandboxed: they run inside the agent process, which needs the network for
the LLM loop and broad read access for discovery.

**Decision.** One opt-in `SandboxPolicy`, off by default, driving two
enforcement layers.

1. **A Python-level filesystem gate**, immediately after the permission gate.
   It realpaths salient path arguments, blocks writes outside the writable roots
   for `EDIT` and `UNKNOWN` tools, and blocks reads inside a credential
   deny-list for all tools, returning the same blocked result shape the model
   already understands.
2. **An OS wrapper for shell subprocesses** — `sandbox-exec` with generated SBPL
   on macOS, `bwrap` on Linux (read-only bind of root, read-write binds of the
   writable roots, tmpfs and `/dev/null` masks over deny-read paths). Neither
   unshares PID or network, so both exec in place and the existing
   process-group, timeout and PID-tracking machinery survives.

Network stays open in v1. Where no mechanism exists — Windows, or Linux without
bwrap — the policy's `fallback` applies: `warn` (run, with a visible warning in
the tool output) or `deny`, never a silent passthrough. The escape hatch,
`dangerously_skip_sandbox`, exists on the shell tools only, is never
auto-approved, and can be disabled entirely. The policy flows exactly like
permissions: an explicit task argument, then the `current_sandbox_policy`
ContextVar for sub-agent inheritance, then `CFG.LLM_SANDBOX_*`.

**Consequences.** An approved-but-injected command cannot write outside the
workspace or read `~/.ssh`-class secrets on macOS and Linux, and MCP or unknown
tools get write checks by default. Costs: the Python layer has check-to-use
TOCTOU (the OS layer does not); a Seatbelt-sandboxed process cannot exec
set-uid binaries, notably `/bin/ps`, so the PID-tracking wrapper needed a
fallback and `sudo` is unavailable by construction; `sandbox-exec` is
deprecated-but-functional, with Chrome, Bazel and Codex as precedent; and
Windows gets no OS-level shell isolation in v1.

**Alternatives rejected.** *Sandbox the whole agent process* — kills the LLM
network loop and the read-everything discovery the agent depends on. *Landlock
on Linux* — kernel ≥5.13, an extra dependency and `preexec_fn` plumbing;
deferred, since bwrap is ubiquitous through flatpak. *Docker or WSL2 on
Windows* — an install burden incompatible with the deployment constraints.
*Per-tool path checks instead of a central gate* — touches every tool and misses
future and MCP tools, which is exactly the population that most needs it. *Add
the escape hatch to the file tools too* — considered and rejected: sandbox
escape stays a shell-only concept, so the Python gate has no bypass and the
credential deny-read protection holds unconditionally.

**Where it lives.** `src/zrb/llm/sandbox/`, `src/zrb/llm/agent/common.py`
(`_sandbox_gate`), `docs/advanced-topics/sandbox.md`, `test/llm/sandbox/`
(platform-conditional integration tests for write containment, deny-read, the
escape hatch, timeout-kill survival and PID tracking under the wrapper).
