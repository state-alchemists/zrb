# ADR-0104 — Stream observers see an agent run's events beside the UI

**Status:** Accepted

**Context.** Speech needed to read a reply while the model was still writing it (ADR-0103). Everything a run streams — text deltas, tool calls, the final result — went to exactly one consumer: the event handler `run_agent` builds from the UI (`setup_print_and_events` → `StreamEventHandler`), or one passed in by the caller. `LLMTask` passes none, so the UI's handler is the only one there is.

Hooks were no fit. They are awaited inline, dispatched through a registry with matchers, and mirror Claude Code's events; a delta event would pay all of that hundreds of times a turn. A UI hook was no fit either: speech works on an `LLMTask` too, including `zrb llm chat --message`, where no interactive UI runs.

**Decision.** A stream observer is a callable taking one `AgentStreamEvent` (`zrb.llm.stream_observer.StreamObserver`), which may return an awaitable.

1. **`LLMTask` and `LLMChatTask` hold an ordered collection of them** — `append_stream_observer`, `prepend_stream_observer`, `remove_stream_observer` and `set_stream_observers`, with a read-only `stream_observers` property (R7: `set_stream_observers` is the one way to replace the list); both classes expose the same surface, and both copy a list they are given, so the caller's list stays its own — following the collection rules in AGENTS.md. `LLMChatTask` copies its list onto the inner `LLMTask` it builds for each turn.
2. **`run_agent(stream_observers=...)`** wraps its effective event handler with `create_observed_event_handler`: each event goes to the handler first, then to every observer in order. With no observers the handler is returned unchanged.
3. **An observer cannot break the run.** One that raises is logged and skipped; cancellation still propagates.
4. **A delegated sub-agent's run does not inherit them.** Only the main run's events reach a task's observers, as only the main turn's reply is the user's.
5. **Observers read events by their tags** where they can (`event_kind`, `part_kind`, `part_delta_kind`), so a feature module need not import pydantic-ai to use one.

**Consequences.** A feature can act on a reply while it streams through a public extension point, the same way ADR-0102's features use `append_hook_factory` and `append_trigger`. Observers run on the event loop, on the hot path: one must return quickly and hand slow work to a thread (speech queues text on its speaker). A stream round that fails and is retried has already shown its partial events to observers; the UI has the same property.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| A `TextDelta` hook event | Hooks are awaited inline and matched through a registry, and are Claude Code's vocabulary; per-delta dispatch is the wrong cost for the wrong audience. |
| Speech subclassing or wrapping the UI's `StreamEventHandler` | Couples a feature to one UI's rendering internals, and there is no UI handler to wrap when no interactive UI runs. |
| A `ContextVar` holding extra handlers | Ambient state for something a task owns and configures; a task-level collection is visible, ordered and removable. |
| A constructor keyword on `LLMTask` | `LLMTask`'s constructor is at its parameter budget (`test_constructor_surface.py`), and observers are registered after construction anyway, as hook factories are. |

**Where it lives.** `src/zrb/llm/stream_observer.py` (`StreamObserver`, `create_observed_event_handler`), `src/zrb/llm/agent/run/runner.py` (`run_agent`), `src/zrb/llm/task/llm_task.py`, `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/task/chat/execution.py`.
