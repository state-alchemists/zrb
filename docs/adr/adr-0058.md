# ADR-0058 — Tools carry a capability tag

**Status:** Accepted

**Context.** Plan mode and permission rules need to reason about what a tool
*does* — read, mutate, execute, reach the network, delegate — but zrb tools are
bare functions with no such metadata. The only precedent was an ad-hoc "is this
a delegate tool" attribute.

**Decision.** Generalize it: an optional `zrb_capability` tag
(`READ | EDIT | EXECUTE | NETWORK | DELEGATE | META | UNKNOWN`), applied
centrally in `common_tools.py`. An untagged tool resolves to `UNKNOWN`, and each
consumer decides how to treat unknown — the plan-mode gate denies it, which is
the safe reading, while a permission ruleset can match it with `*`.

**Consequences.** Fine-grained policy without touching a single tool signature,
and untagged third-party or MCP tools keep working conservatively. The cost is
that built-in tools must be tagged for accurate behaviour, and an untagged new
tool is silently the strictest case.

**Alternatives rejected.** *Infer capability from the name* — fragile, and
wrong for anything general-purpose. *A parallel registration file* — drifts from
the tool list. *Parse the docstring* — fragile, and the docstring is written for
the model, not for a policy engine.

**Where it lives.** `src/zrb/llm/permission/capability.py`,
`src/zrb/llm/common_tools.py`, `src/zrb/llm/agent/common.py`.
