# ADR-0103 — Speech reads a reply aloud as it streams or at the end, cut or summarized, and stops when talked over

**Status:** Accepted

**Context.** A user away from the screen, or talking hands-free (ADR-0076), needs to hear the reply, and to hear that a tool is waiting for approval. Before this, the way to get that was an external tool such as peon-ping, installed as a Claude Code hook: it plays sounds on events, but cannot read what the agent said.

An example did it with Python hooks on `Stop`, `PermissionRequest` and `Notification`. Two problems showed up. zrb awaits a Python hook inline, so a hook that spoke would hold up the turn. And a long reply was cut at a fixed character count, stopping mid-sentence with no sign that more existed.

Speaking only at `Stop` had a third cost, which showed once hands-free was used as a conversation: nothing was heard until the whole turn was over, tool calls included, so a turn that ran tests was tens of seconds of silence and then a reply. And the user could not stop a reply that had gone wrong except by keyboard.

**Decision.** `enable_speech` (ADR-0102) registers the hooks, a stream observer and a `/speech` command.

1. **Hooks and observers only queue.** Each puts text on a `Speaker`'s queue and returns. The `Speaker` runs two threads: one makes each queued text's audio, the other plays it, at most one utterance waiting ready, so the next sentence is synthesized while the current one plays. At exit, queued speech gets `drain_timeout` seconds, since `zrb chat --message` exits right after its reply.
2. **What is spoken is chosen by `events`.**
   - `reply`: the reply (never a sub-agent's), at `Stop`, or as it streams with `stream` (item 4).
   - `approval`: "I need to write a file /tmp/a.py. I need your approval." This is a template, not a model call, since the user is waiting on it. It is skipped if the prompt is answered before its turn comes, and cut off if it is answered while being read.
   - `question`: notifications that wait on an answer (`elicitation_dialog`, `permission_prompt`).
   - `progress`: a tool call that starts after `progress_interval` seconds with nothing said is announced ("Running a command."), from a template for the same reason. It is dropped if the call ends first, and never said while speech is playing.
3. **A reply at `Stop` (with `stream` off) is cleaned, then fitted.** Code blocks, tables, URLs, markup and emoji are removed. A reply over `max_chars` is cut at the last sentence end in the second half of the window, else the last clause break, else the last whole word, and followed by `on_screen_note` ("The full answer is on screen."). A dot inside a word such as `main.py` is not a sentence end. With `summarize`, a long reply is summarized by `summary_model` (the small model by default, prompt `speech_summarizer`) on the speaker's thread, with an event loop of its own, since a hook's loop closes once the hook returns. If summarizing fails, the cut opening is spoken.
4. **With `stream`, a reply is spoken a sentence at a time while it is written.** A stream observer (ADR-0104) feeds the run's text deltas to `SpeechChunker`, which hands back whole sentences, cleaned, as soon as each is complete, never inside a code fence or table. Text written before a tool call is spoken when the call starts, so "Let me run the tests." is heard before they run. `max_chars` caps what one turn speaks: the sentence crossing it is finished, then `on_screen_note`, then nothing more that turn. `summarize` does not apply. A turn that streamed nothing (a provider that does not stream) is spoken at `Stop` as in item 3.
5. **The model is told its reply is heard.** While speech is on, a live-context provider (`speech_live`) asks the model to open with the answer in a sentence or two of plain speech and put detail after it, since a reply written to be read opens with a table.
6. **Talking over speech stops it.** `interrupt_speech(session_key)` — called by hands-free dictation on a barge-in (ADR-0076) — drops that chat session's queue, stops the utterance playing, drops audio already made for it, and mutes the rest of the response being streamed; the model's next response is spoken again. The speaker stays open, unlike `close`. A turn that was talked over, or cancelled (a `Stop` naming a `reason`: Esc, a barge-in), is not spoken at `Stop`.
7. **Sessions take turns.** Playback holds `lock_file` through `hold_file_lock` (flock on POSIX, msvcrt on Windows). An utterance that cannot get the lock within `lock_timeout` is dropped, since speaking a stale reply late is worse than not speaking it. `is_speaking` reports a count of utterances playing in this process, then the default lock file and every lock file a `Speaker` in this process uses, so dictation ignores zrb's own voice however speech was configured, and two speakers playing at once never hide each other.
8. **Backends are local first.** `auto` is `termux` (Termux:API's `termux-tts-speak`) on Termux, `say` on macOS, else `espeak-ng`: each a binary, no Python package. A backend that needs one (pyttsx3) lives in zrb-extras. `openai` and `gemini` go over `urllib`, so no package is needed, and play the returned WAV with `wav_player` or the first of `afplay`, `paplay`, `aplay`, `ffplay`. Synthesis happens before the lock is taken, so a slow cloud request does not hold it. A failing backend falls back to the local engine, without the configured voice, which names a voice of the requested backend.
9. **`LLM_SPEECH_ENABLED` is the starting state**, off by default. Once speech is on, `stream` and the `progress` event are on by default: a user who turned speech on wants to hear the answer soon and hear that a long turn is working, and hands-free plus speech is then a voice conversation with no separate mode. `/speech` switches speech during a session, runs mid-turn, and drops whatever is still queued when switching off.

**Consequences.** Replies, approvals and questions are heard without an external tool, which is what peon-ping was used for. Speech never delays a turn. With `stream`, the first sentence is heard about when it appears on screen, and a long tool call is announced rather than silent. Two sessions on one machine never talk over each other, though which one speaks first is not defined. A streamed sentence is spoken as written, so one the model would have revised is heard anyway; `stream=off` reads the finished reply instead. Summarizing costs one model call per long reply, which is why it is off by default.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Speak inside the hook | zrb awaits Python hooks, so speech would delay every turn. |
| A hook event per streamed text delta | Hooks are awaited inline and Claude-compatible; hundreds of deltas a turn would each pay a hook dispatch. A stream observer is a plain call. |
| Cut at a fixed character count | It stops mid-word, and the listener cannot tell the reply was longer. |
| Always summarize | A model call and its latency on every long reply, for users who may not want either. |
| Narrate tool calls with a model | The call is under way by the time a model answers; a template says it at once. |
| A summary through a separate OpenAI client | It needs its own key and model config; zrb's model resolution already knows the user's small model. |
| Queue speech instead of dropping it when the device is busy | A backlog plays replies minutes after they were current. |
| `stream` off by default, with a `/live` mode turning it on | Hearing the reply only once the turn ends is the worse default for anyone who turned speech on, and a mode that exists to fix the defaults is a second way to say the same thing. |
| Synthesize each sentence only once the one before has played | A cloud backend's request then sits as a gap between every two sentences. |
| Require an audio package (pyttsx3, simpleaudio) | Local engines and a WAV player already cover every platform through a subprocess. |
