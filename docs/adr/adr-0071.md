# ADR-0071 — Lifecycle hooks are Claude-compatible, including the control protocol

**Status:** Accepted

**Context.** Cross-cutting concerns — audit, approval gates, command rewriting, notifications — should not be hardcoded into the agent loop or into individual tools. Claude Code already has a hook format with a real ecosystem, so compatibility means drop-in reuse rather than translation.

Structural compatibility was not enough. A gap analysis found the events *fired* but the *control* capabilities were not honoured, so a drop-in hook could observe and not act: `PreToolUse` fired only for approval-gated calls and read proprietary keys; `PostToolUse` fired on approval outcome rather than real execution and could neither block nor transform; `UserPromptSubmit` and `Stop` were observe-only; and `SessionEnd` fired once *per turn*, so consumers expecting a terminal signal got a false one every turn. Separately, real third-party tools read their event from **stdin** and register themselves in `.claude/settings.json` — neither of which zrb supported, so they parsed empty input and were never discovered.

**Decision.** Fire at Claude's lifecycle events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SessionStart`/`SessionEnd`, `UserPromptSubmit`, `Pre`/`PostCompact`, `Stop`, `StopFailure`, `SubagentStart`/`SubagentStop`, `Notification`, `PermissionRequest`, plus zrb's own `Pre`/`PostCommand`). Hook types are shell `command`, LLM `prompt`, and multi-step `agent`.

- **One tool chokepoint.** The function toolset is wrapped so `call_tool` is the single method *every* tool call passes through. `PreToolUse` fires there for calls that did not already fire it pre-approval; the deferred path keeps its pre-approval fire, so a hook can deny **before** the user is prompted rather than after they approved. `PostToolUse` fires after a successful call and `PostToolUseFailure` in its `except` branch.
- **The Claude protocol is honoured and the proprietary keys are gone.** `PreToolUse` honours `permissionDecision` allow/deny/ask and `updatedInput`; `PostToolUse` honours `decision: "block"` and `updatedToolOutput`; `PermissionRequest` honours `decision.behavior`; `PreCompact` can block compaction and inject `additionalContext`; `continue: false` halts the turn.
- **`Stop` is the per-turn signal.** It fires once when a turn completes and control returns to the user, and is the block-to-continue and turn-extension point: a blocking `Stop` re-runs the agent with the reason injected, capped at 8 consecutive blocks. Manual interrupts still fire `Stop` from the TUI, and the paths are mutually exclusive, so there is no double fire.
- **`SessionEnd` is terminal.** It fires once at interactive teardown, not inside the run loop.
- **Command hooks get the payload on stdin.** The event JSON is written to the subprocess' stdin; the `CLAUDE_*` env vars are retained additively but size-capped so a large payload cannot overflow the exec limit. `.claude/settings.json` and `settings.local.json` are hook sources alongside `hooks.json`.
- **Async command hooks are fire-and-forget on the persistent loop**, never awaited, with the timeout enforced by killing the subprocess. The earlier design created the task inside a short-lived worker loop that cancelled it on return and then awaited the subprocess, so a per-chunk hook stalled every turn up to its timeout.
- **Flood control.** Fire-and-forget hooks run under a concurrency semaphore with a backlog ceiling (excess shed), because high-frequency events could otherwise exhaust file descriptors and back a serialized tool into a timeout storm.
- **Attention events.** `PermissionRequest` fires from the approval cascade at the moment a call reaches an interactive prompt — after every auto-resolve path, so it never false-positives — and the question tool fires a `Notification` instead, since it is auto-approved (ADR-0062).
- **Selective blocking.** A `BLOCKING_EVENTS` set means an exit-2 or `decision: "block"` halts the chain only for blocking-capable events; a block on an observe-only event is ignored and the remaining hooks still run. `continue: false` remains an unconditional halt.

The execution model stays zrb's: sequential by priority, first-decisive-result-wins.

**Consequences.** Unmodified Claude command hooks work under zrb with no translation, and gate, rewrite and continue behaviour actually takes effect. `SessionEnd` consumers get one terminal event instead of a per-turn false positive. **Breaking:** hooks relying on the old proprietary keys must use the Claude fields, and anything keyed on `SessionEnd` for per-turn work must move to `Stop`. Deliberately not adopted: Claude's parallel execution with most-restrictive merge, and the `http` / `mcp_tool` handler types — both separate axes.

**Alternatives rejected.** *Hardcode approval logic in the loop* — tight coupling, and no way for a non-programmer to add a gate. *Per-tool middleware* — scales poorly and misses MCP tools. *Code-only hooks* — excludes the shell-script users the ecosystem is made of. *Fire `PreToolUse` only in `call_tool`* — loses pre-approval denial, so a hook would block *after* the user already approved. *A dedicated `TurnEnd` event* — Claude has none; `Stop` is the turn-end signal, so a new event would diverge rather than converge. *Keep both legacy and Claude keys* — a clean Claude-only surface was chosen deliberately. *Translate third-party hook configs into zrb's own format by hand* — per-user, brittle, and it defeats "drop-in". *Pass the payload only through env vars* — stdin-only tools never see it. *Rename `SessionEnd` to `Stop`* — breaks the session-extension contract built on `SessionEnd`.

**Where it lives.** `src/zrb/llm/hook/`, `src/zrb/llm/agent/common.py` (`SafeToolsetWrapper.call_tool`), `src/zrb/llm/agent/run/hook_result_extractor.py`, `src/zrb/llm/agent/run/session_extension.py`, `src/zrb/llm/agent/run/deferred_calls.py`, `docs/advanced-topics/hooks.md`.
