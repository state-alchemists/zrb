# ADR-0081 — Web chat renders markdown/math/diagrams client-side; the non-interactive loop finalizes its output

**Status:** Accepted

**Context.** The web chat showed LaTeX math and Mermaid diagrams as raw `$...$`/```` ```mermaid ```` source, though ADR-0079/0080 made the CLI render both. A CSS fix (monospace font on the assistant bubble) was assumed sufficient, but a live server, a captured SSE stream and runtime instrumentation (monkeypatching `render_markdown`/`append_markdown`/`_stream_ai_response`) showed the real cause: **the web chat's per-message flow never runs a markdown-finalization step.**

A message POSTed to `/api/v1/chat/sessions/{id}/messages` goes through `run_chat_session` (`src/zrb/runner/chat/chat_session_runner.py`) → `LLMChatTask._run_non_interactive_session` (`src/zrb/llm/task/chat/running.py`), which calls `llm_task_core.async_run(session)` **directly**, bypassing `BaseUI._process_messages_loop` → `_submit_user_message` → `_stream_ai_response`. `append_markdown`/`render_markdown` — the only callers of `convert_math_to_unicode`/`convert_mermaid_to_art` (ADR-0079/0080) — live only inside `_stream_ai_response` (`src/zrb/llm/ui/base/ui.py`), which runs only for the **interactive** (CLI) loop.

A live SSE capture of a math-only response showed `thinking` → `streaming` (raw `$A = \pi r^2$`) → `usage`, then nothing. Separately, `chat.js`'s `usage` handler only stripped the `.streaming` CSS class and never replaced the bubble's content, so a render step would have had nowhere to land.

**Decision.**

1. **`_run_non_interactive_session` gets the finalization pass `_stream_ai_response` gives the CLI.** After `result = await llm_task_core.async_run(session)`, a string `result` goes to every attached UI that implements `append_markdown` (`for ui in llm_task_core.get_uis(): ... ui.append_markdown(result)`). `LLMTask.get_uis()` is a new thin public accessor beside `append_ui`, so `running.py` doesn't reach into `_uis`. This fixes every non-interactive consumer, not just the web — any `EventDrivenUI` subclass (a Telegram-style bot, say) is finalized the way the CLI always was.

2. **The web UI renders client-side, not through the CLI's ANSI/Unicode-art pipeline.** `HTTPUI.append_markdown` (`src/zrb/runner/chat/http_ui.py`) overrides `BaseUI.append_markdown` to broadcast the **raw, unconverted** markdown under a new SSE kind, `"markdown"`. The browser uses [`marked`](https://github.com/markedjs/marked) for markdown → HTML, [KaTeX](https://katex.org/) (+ its `auto-render` extension) for math, and `mermaid.min.js` (already vendored for the task-monitor Gantt page) for SVG diagrams. This beats the CLI's Unicode approximation and lifts the `\frac`-isn't-a-real-fraction limitation ADR-0079 accepted for the terminal. [DOMPurify](https://github.com/cure53/DOMPurify) sanitizes `marked`'s output before `innerHTML` — **non-negotiable**, since the content is LLM-generated and may echo untrusted tool/web output; modern `marked` dropped its own `sanitize` option in favor of exactly this.

3. **`chat.js` keeps the just-settled streaming bubble across the `usage` event** (`lastAnswerBubble`), so the following `"markdown"` event replaces its raw content in place — rather than leaving raw text as the final answer, or duplicating it (as reusing the CLI pipeline would). With no live bubble (e.g. a reconnect mid-turn), it appends a fresh rendered bubble instead of losing the answer.

4. **Live streaming deltas are untouched** — still plain text. Parsing a partial code fence or LaTeX span is unreliable; only the settled bubble gets the rich render, as the CLI commits fully only at turn end (ADR-0079's point 1).

5. **Reopening a past session renders like live chat.** `loadMessages()` runs persisted assistant messages through the same `marked` → DOMPurify → KaTeX → Mermaid pipeline instead of `escapeHtml`, mirroring the CLI's `replay_history` symmetry between live and resumed turns.

6. **Mermaid fences are tagged, not auto-scanned.** `marked`'s renderer overrides `code()` to emit ` ```mermaid ` blocks as `<pre class="mermaid">`, and `mermaid.run({nodes: ...})` targets exactly those. With `mermaid.initialize({startOnLoad: false, ...})`, diagrams render per finalized message, not by scanning the page.

**Consequences.** Web chat renders math and Mermaid — live and in reopened sessions — with real browser rendering, and every non-interactive UI is now finalized with `append_markdown`. Vendoring `marked`, KaTeX (+ fonts, + auto-render) and DOMPurify adds roughly 400KB to the chat page (self-hosted, no CDN, no build step, like `mermaid.min.js`/Pico CSS). The CLI path (`render_markdown`, `convert_math_to_unicode`, `convert_mermaid_to_art`) is untouched and remains correct for the CLI and any non-JS `EventDrivenUI` subclass. DOMPurify is the security boundary for rendering untrusted, LLM-authored HTML; no future change may remove or bypass it.

**Alternatives rejected.**
- *Extend `render_markdown`'s Unicode-art conversion to the web UI* — the original plan; it doesn't fix the actual bug (finalization never ran) and gives worse output than client-side rendering.
- *Only fix the CSS (monospace font)* — fixes nothing, since no rendering reached the browser.
- *Render markdown to HTML on the server* — saves nothing: real typesetting and diagrams would still need client-side KaTeX/Mermaid, and the browser has purpose-built renderers for markdown too.

**Where it lives.** `src/zrb/llm/task/llm_task.py`/`building.py` (`get_uis`), `src/zrb/llm/task/chat/running.py` (`_run_non_interactive_session`), `src/zrb/runner/chat/http_ui.py` (`append_markdown` override), `src/zrb/runner/web_route/chat_page/chat.js`/`chat.css`/`view.html`, `src/zrb/runner/web_route/static/resources/` (`marked.js`, `katex/`, `dompurify.min.js`).
