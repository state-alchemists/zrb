# ADR-0081 — Web chat renders markdown/math/diagrams client-side; the non-interactive loop now finalizes at all

**Status:** Accepted

**Context.** The web chat UI never rendered LaTeX math or Mermaid diagrams — it showed raw `$...$`/```` ```mermaid ```` source verbatim, even though ADR-0079/0080 already made the CLI render both. A CSS fix (monospace font on the assistant bubble) was assumed sufficient, but a live server, a captured SSE stream, and runtime instrumentation (a monkeypatch on `render_markdown`/`append_markdown`/`_stream_ai_response`) found something more fundamental: **the web chat's per-message flow never calls any markdown-rendering finalization step at all.**

A message POSTed to `/api/v1/chat/sessions/{id}/messages` is driven by `run_chat_session` (`src/zrb/runner/chat/chat_session_runner.py`) → `LLMChatTask._run_non_interactive_session` (`src/zrb/llm/task/chat/running.py`), which calls `llm_task_core.async_run(session)` **directly** — bypassing `BaseUI._process_messages_loop` → `_submit_user_message` → `_stream_ai_response` entirely. `append_markdown`/`render_markdown` (the only place `convert_math_to_unicode`/`convert_mermaid_to_art`, ADR-0079/0080, ever run) live exclusively inside `_stream_ai_response` (`src/zrb/llm/ui/base/ui.py`), which only runs for the **interactive** (CLI) session loop. Verified directly: a live SSE capture of a math-only response showed `thinking` → `streaming` (raw `$A = \pi r^2$`) → `usage`, then nothing — confirmed by tracing that `render_markdown`/`append_markdown` never fire for a web-submitted message. Separately, `chat.js`'s `usage` handler only stripped the `.streaming` CSS class from the live bubble and never replaced its content, so even a render step would have had nowhere to land without further changes.

**Decision.**

1. **`_run_non_interactive_session` gets the same finalization pass `_stream_ai_response` already gives the CLI.** After `result = await llm_task_core.async_run(session)`, if `result` is a string, every attached UI that implements `append_markdown` receives it (`for ui in llm_task_core.get_uis(): ... ui.append_markdown(result)`). `LLMTask.get_uis()` is a new thin public accessor (next to the existing `append_ui`) so `running.py` doesn't reach into `_uis` across a module boundary. This fixes the root bug for **every** non-interactive UI consumer, not just the web — any other `EventDrivenUI` subclass (a Telegram-style bot, say) now gets the same finalize-with-markdown treatment the CLI always had.
2. **The web UI renders client-side, not through the CLI's ANSI/Unicode-art pipeline.** `HTTPUI.append_markdown` (`src/zrb/runner/chat/http_ui.py`) overrides `BaseUI.append_markdown` to broadcast the **raw, unconverted** markdown under a new SSE kind, `"markdown"`, instead of running it through `render_markdown`. The browser has real renderers available: [`marked`](https://github.com/markedjs/marked) for markdown → HTML, [KaTeX](https://katex.org/) (+ its `auto-render` extension) for real math typesetting, and `mermaid.min.js` (already vendored, previously used only by the task-monitor Gantt page) for actual SVG diagrams — strictly better than the CLI's Unicode approximation, and it resolves the `\frac`-doesn't-render-as-a-real-fraction limitation ADR-0079 accepted for the terminal, since KaTeX typesets real fractions. [DOMPurify](https://github.com/cure53/DOMPurify) sanitizes `marked`'s output before it reaches `innerHTML` — **non-negotiable**, since the rendered content is LLM-generated text that may echo untrusted tool/web output, and modern `marked` dropped its own `sanitize` option in favor of exactly this pattern.
3. **`chat.js` keeps a reference to the just-settled streaming bubble across the `usage` event** (`lastAnswerBubble`) so the `"markdown"` event that follows can replace its raw content in place, instead of the previous bug where the raw text would have been left as the permanent "final" answer (or duplicated, had the CLI's pipeline been reused instead). No live bubble to replace (e.g. a page reconnect mid-turn) falls back to appending a fresh rendered bubble rather than losing the answer.
4. **Live streaming deltas are untouched** — they keep rendering as plain text exactly as before. Incrementally parsing a partial code fence or LaTeX span is unreliable; only the settled final bubble gets the rich render, mirroring how the CLI only fully commits at the end of a turn too (ADR-0079's point 1).
5. **Reopening a past session renders the same way live chat does.** `loadMessages()` (loading persisted history) now runs assistant messages through the same `marked` → DOMPurify → KaTeX → Mermaid pipeline instead of `escapeHtml`, mirroring the CLI's `replay_history` symmetry between a live turn and a resumed one.
6. **Mermaid fences are tagged, not auto-scanned.** `marked`'s renderer overrides `code()` to emit ` ```mermaid ` blocks as `<pre class="mermaid">` instead of a generic code block; `mermaid.run({nodes: ...})` then targets exactly those elements. `mermaid.initialize({startOnLoad: false, ...})` — diagrams render on demand per finalized message, not by scanning the whole page.

**Consequences.** Web chat now renders LaTeX math and Mermaid diagrams — both live and in reopened sessions — via real browser-native rendering, not Unicode approximation. Every non-interactive UI (not just the web) is now finalized with `append_markdown`, closing the same gap uniformly. Vendoring `marked`, KaTeX (+ fonts, + auto-render), and DOMPurify adds roughly 400KB to the chat page (self-hosted, no CDN, no build step, matching how `mermaid.min.js`/Pico CSS are already vendored). The CLI/terminal path (`render_markdown`, `convert_math_to_unicode`, `convert_mermaid_to_art`) is untouched — it remains correct for the CLI and any non-JS-capable `EventDrivenUI` subclass. Sanitization (DOMPurify) is the security boundary for rendering untrusted, LLM-authored HTML in a browser and must not be removed or bypassed by a future change to this pipeline.

**Alternatives rejected.** *Extend `render_markdown`'s Unicode-art conversion to the web UI* — was the original plan, but doesn't fix the actual bug (the finalize step never ran at all) and produces strictly worse output than real client-side rendering when a browser is available. *Only fix the CSS (monospace font)* — addresses nothing, since no rendering pipeline was reaching the browser in the first place. *Have the server render markdown to HTML too* — unnecessary; the browser already has (or can vendor) better-suited, purpose-built renderers for exactly this, and server-side HTML generation would still need the same client-side KaTeX/Mermaid libraries to produce real typesetting/diagrams, so nothing is saved by doing markdown→HTML server-side instead of in the browser.

**Where it lives.** `src/zrb/llm/task/llm_task.py`/`building.py` (`get_uis`), `src/zrb/llm/task/chat/running.py` (`_run_non_interactive_session`), `src/zrb/runner/chat/http_ui.py` (`append_markdown` override), `src/zrb/runner/web_route/chat_page/chat.js`/`chat.css`/`view.html`, `src/zrb/runner/web_route/static/resources/` (`marked.js`, `katex/`, `dompurify.min.js`).
