# ADR-0116 — A send-now action hands the queue to the live run, falling back to cancelling the turn

**Status:** Accepted

**Context.** ADR-0077 gives the user a queue they can inspect and edit; ADR-0078 once tried to keep that queue empty by steering each message into the live run at submit time — a default withdrawn in its 2026-10-22 revision, and replaced on 2026-10-23 by a checkpoint that hands the ready entries to the run by itself. A queued entry can still wait with no way to say "and now", and the reasons are mostly the ones a checkpoint holds it for:

- the entry is the one being edited, or younger than `EARLY_DELIVERY_GRACE_SECONDS`, which a checkpoint skips by design — exactly when the user means the words now;
- no `RunContext` is registered yet (the turn has started but the first stream event has not arrived) or has already been cleared (`agent.run()` returned while the UI is still finalizing);
- the run is suspended on a pending tool approval — ADR-0078 registers no run context there, correctly, because there is no model turn to steer into, but the user may have answered and sent follow-up messages in the meantime;
- `enqueue()` lost a race with a run that ended between the check and the call;
- the next checkpoint is a long way off, or there is none: one tool call that takes minutes delivers nothing until it returns;
- the entry is an `/exec` job (ADR-0078 §3), which never steers.

Those entries wait even though the user is watching and asking for them now. Claude Code exposes this as a dedicated send-now key; zrb had no equivalent.

**Decision.**

1. **Delivery is a module of free functions, not a part on `BaseUI`.** `llm/ui/base/queue_delivery.py` exports `send_queued_messages_now(...) -> DeliveryReport` plus a `DeliveryOutcome` enum and `describe_delivery(report)`. It takes every dependency as an argument (live run context, queue, the two state questions, a `cancel_turn` callback), so `BaseUI`, `MultiUI` and the inert `UIStateDefaultsMixin` default each call it with their own state. This keeps the ladder, which must read identically wherever it is invoked, in one testable place.

2. **`AnyUI.send_queued_messages_now()` is part of the UI contract**, returning the report rather than a bool: the caller's next step is a line of prose ("sent 2 queued message(s)..."), and the report carries the counts that line needs. A UI with no queue of its own (the mixin default) answers `NOTHING_MOVED`.

3. **The ladder runs in one order, first match wins.** A dialog owns the input → `WAITING_ON_DIALOG`, and nothing is cancelled or delivered. Otherwise a live run → steer the queued *messages* into it with `priority="asap"`, removing each from the queue in the same synchronous drain. Otherwise a turn running with no live run to steer into → `cancel_current_turn("send_now")`, so the message loop picks the queue up right away. Nothing running → `NOTHING_MOVED`. `held` counts whatever is still queued.

   The key asks for *everything*: the drain takes every queued entry, where a checkpoint passes `only_ready=True` and leaves the one being edited and any younger than the grace (ADR-0078 §3), so a message a checkpoint is holding back goes now. Nothing else differs — one ladder serves both callers.

   A drain that hands over every message it reached reports `DELIVERED_EARLY`. A drain that stopped because `enqueue` failed — the run finished between two calls, the very race this action exists for — is *partial* only when it left entries behind, and every partial drain says so: when a turn is still running the attempt cancels it (`FELL_BACK_TO_CANCEL`, carrying the delivered count), and when there is no turn left to cancel it reports `DELIVERED_PARTIAL`. Reporting either `DELIVERED_EARLY` or `NOTHING_MOVED` there would misstate the run — the failed enqueue is itself the signal that the fallback is needed, and the delivered count the line renders must not contradict its outcome. A failed `enqueue` on the entry that empties the queue is not partial: everything was delivered and nothing remains for a cancel to free, so it reports `DELIVERED_EARLY`.

   The dialog is checked *before* the live run, and that order is the whole of it: while a turn is suspended on an approval or a question, the streaming handler keeps the run context registered (`agent/run/runner.py` re-registers it on every event), so a live run is present precisely when the model *cannot* read a steering message — the turn is blocked on the user. A ladder that asked "is there a live run?" first would enqueue the queue ahead of the answer the turn is waiting for.

4. **`/exec` jobs are never steered, and one stops the drain.** A queued `/exec` job is an ordering barrier: the drain delivers the messages *before* it and stops there, rather than skipping it to reach later ones. The queue is FIFO and the message loop drains it head-first, so steering a later message past an `/exec` job would run that message before a command the user queued first — and a follow-up like "report the command's result" most needs the command it refers to to have run. An `/exec` job at the head therefore delivers nothing, and the attempt falls through to the cancel below, which runs the whole queue in its original order.

5. **The TUI binds Ctrl+G at the application level**, filtered by `no_active_choice & ~has_completions & ~has_selection`. prompt_toolkit builds its merged registry as control → parents → global → `app.key_bindings` → mouse → defaults, then reverses it so the focused control matches last, and its key processor takes the last match. Both of zrb's text panes are `TextArea`s whose control bindings are an empty `KeyBindings` (`app/layout.py`), and the default emacs `c-g` (cancel completion / cancel selection) lives in `app._default_bindings`, which lands *below* `app.key_bindings` — so an application binding takes the key, and the completion/selection guards let those keep it. The handler does not touch the input field: Ctrl+G is not a submit.

**Consequences.** A checkpoint delivers the ready entries by itself (ADR-0078 §2), so what is left for the key is what a checkpoint will not do: send a message still being edited or inside its grace, and send the queue during a long tool call with no boundary in sight. The transcript immediately says what happened — there is no silent case, and a partial drain names both halves ("sent N …, then the run ended — interrupted the turn so the rest run next"). A delivered message leaves the queue and so stops being recallable with Up (accepted; ADR-0077's recall covers entries that are still waiting), and its echo line changes marker to `⏩` rather than disappearing. A cancelled turn's queue is untouched, so it runs intact as the next turn, minus anything already delivered. The web chat has no such action yet.

**Alternatives rejected.**

- *Queue first, always, and promote into the live run only on demand* — Claude Code's own shape, rejected when this record was written because it would regress the then-current ADR-0078 default: every mid-turn message would first become a queue entry the user watches, then be delivered anyway. **Adopted later**: ADR-0078 was revised on 2026-10-22 to queue every submission, and again on 2026-10-23 so a checkpoint delivers the ready entries without a key; `delivered_at`/`DELIVERED_MARKER` mark what either path hands over, so the transcript says what the model read instead of the entry vanishing. The split this record predicted held: the ladder did not change, only who asks for it and when.
- *Only deliver when a live run exists* — the common "no live run" case is a turn that *is* running with its context gone or never registered; refusing there would make the key a no-op exactly when the user needs it. Cancelling hands the turn over to the message loop, which is the same outcome one keystroke later anyway.
- *Delivering through a turn waiting on an approval or a question* — the dialog owns the input, and the run context is still registered while the turn is suspended, so this is the mistake the ladder's order exists to prevent: the queue would reach the model before the answer the turn is blocked on. Cancelling the dialog to run the queue would silently deny a tool call (ADR-0085 makes an edited call tell the model what ran — a denied one says something else again). Waiting is the honest answer.
- *Submitting the input draft as part of the key* — the draft is not in the queue, so flushing it means re-running Enter's dispatch: classify the token as a command or a message, answer a pending approval first, route to a viewed sub-agent. Duplicating that in a second path invites divergence; the draft stays in the input field where it is already editable.

**Where it lives.** `src/zrb/llm/ui/base/queue_delivery.py`, `src/zrb/llm/any_ui.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/multi_ui.py`, `src/zrb/llm/ui_fallback/state_defaults.py`, `src/zrb/llm/ui/default/keybindings.py` (Ctrl+G).
