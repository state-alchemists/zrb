# ADR-0082 — Photo capture is a one-shot command, not a toggled mode, and carries no enable gate

**Status:** Accepted

**Context.** `/voice` (ADR-0076) gives push-to-talk dictation: a toggle command plus a dedicated keybinding, because recording has a start/stop lifecycle a terminal can only approximate with press-to-start/press-again-to-stop. A photo has no lifecycle — one press, one photo — so a second toggled mode would import machinery (mode state, a keybinding, a status-bar indicator) that nothing needs.

Camera access is more fragmented than audio. Desktop OSes use OS-specific device APIs (v4l2 on Linux, AVFoundation on macOS, DirectShow on Windows); Termux has no `/dev/video*` and must use `termux-camera-photo`, a Termux:API Android-intent binary; WSL2 has no camera passthrough unless the user sets up `usbipd-win`.

Field-testing found a proot-in-Termux gotcha (Decision 4): `termux-camera-photo` run inside a `proot-distro` guest *does* reach the Termux:API app, which replies with a structured error — the app is a separate, non-prooted Android process and cannot see the guest's `/tmp`/`$HOME` paths (e.g. `/tmp/test.jpg`).

Should `/photo` have an enable gate like `LLM_VOICE_ENABLED`? Per `llm_voice.py`'s docstring, ADR-0076 and the 2.44.0 changelog, that gate exists for one reason: voice needs **Python packages** (`sounddevice`, `vosk`, `numpy`) that may be absent, so it is opt-in (by declaration, or implicitly by installing vosk — ADR-0076's auto-enable) rather than failing at runtime. Nothing ties it to privacy or operator control.

Photo capture needs no Python dependency, only external binaries (`ffmpeg`, `termux-camera-photo`) run via subprocess, returning `None` plus a `missing_tool_hint()` message on failure — the shape of clipboard-image-paste (`zrb/llm/util/clipboard.py`, the Ctrl+V handler), which has no gate.

**Decision.**

**1. `/photo [device]` is a one-shot command**, modeled on `/attach` rather than `/voice`.

`_handle_photo_command`/`_submit_photo` in `zrb/llm/ui/base/conversation_commands.py` capture a JPEG and append it to `_pending_attachments` as a `BinaryContent`, via the same three steps as the Ctrl+V clipboard-paste handler (`get_camera_photo()` → `scale_image_bytes()` → `BinaryContent`). No mode state, keybinding or status-bar indicator.

**2. The optional trailing argument is the camera device** (index, path, or name depending on platform), matching `/attach <path>`, so device selection needs no config knob.

**3. No enable gate.** `/photo` is available whenever `LLM_UI_COMMAND_PHOTO` resolves a command token, same as `/attach`. Failure (missing `ffmpeg`, no camera, permission denied) degrades to a graceful error plus a platform-specific hint, never a crash.

**4. Capture shells out to external binaries — no new Python dependency.** `zrb/llm/util/camera.py` mirrors `clipboard.py`'s structure exactly: a documented per-platform priority order, a public `get_camera_photo(device=None) -> bytes | None` that never raises, private per-backend functions, and a `missing_tool_hint()`.

| Platform | Backend |
| --- | --- |
| Termux (native or proot) | `termux-camera-photo`, writing to the fixed absolute path `/data/data/com.termux/files/home/.zrb_camera_photo.jpg`, read back and unlinked |
| macOS | `ffmpeg -f avfoundation` |
| Windows | `ffmpeg -f dshow`, auto-detecting the first video device from `ffmpeg -f dshow -list_devices true -i dummy`'s stderr output when no device is given |
| Linux / WSL | `ffmpeg -f v4l2`, defaulting to `/dev/video0` |

Termux does **not** use `tempfile.gettempdir()`: the Termux:API app resolves the path in its own Android filesystem, where a proot guest's `/tmp` does not exist, so capture fails with a `FileUtils Error`. Termux's home is at that one fixed location whether the invoking shell is native or prooted, so one path works everywhere with no proot detection.

**5. WSL gets no special-cased code.** To `ffmpeg` it is Linux: `usbipd-win` passthrough makes `/dev/video0` exist, and without it capture fails with a hint. In field-testing, `usbipd-win` attach often fails even after binding because Windows' Frame Server holds an exclusive handle on a laptop's *built-in* camera; an external USB webcam attaches far more reliably. That limitation has no zrb-side workaround and is documented in the troubleshooting guide.

**Consequences.** `/photo [device]` works in the chat TUI and any UI built on `BaseUI`, including the non-interactive/simple UI path (it follows `attach_commands`' wiring, not `voice_commands`' TUI-only wiring), with no new dependency and no effect when unused. With no gate it is always advertised in help/completion. Windows auto-detection is best-effort — multi-camera machines or unusual driver naming may need an explicit device name, found via `ffmpeg -f dshow -list_devices true -i dummy`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| A toggled mode with a dedicated keybinding, like voice | A snapshot has no start/stop lifecycle to key off; the machinery would exist for nothing. |
| An `opencv-python` (or similar) dependency | `ffmpeg` and `termux-camera-photo` already cover every platform via subprocess, matching how `clipboard.py` avoids an image-clipboard library. |
| An `LLM_ENABLE_PHOTO_CAPTURE` gate mirroring `LLM_VOICE_ENABLED` | Voice's gate is specifically about undeclared Python dependencies, a concern that doesn't apply to a dependency-free, subprocess-based, gracefully-degrading feature; the closer precedent (clipboard-image-paste) has no gate either. |
| A config knob for the camera device | The command argument already covers per-call overrides; a config default would only duplicate it. |

**Where it lives.** `src/zrb/llm/util/camera.py`, `src/zrb/llm/ui/base/conversation_commands.py` (`_handle_photo_command`, `_submit_photo`), `src/zrb/config/mixins/llm_ui_commands.py` (`LLM_UI_COMMAND_PHOTO`).
