# ADR-0082 — Photo capture is a one-shot command, not a toggled mode, and carries no enable gate

**Status:** Accepted

**Context.** `/voice` (ADR-0076) gives push-to-talk dictation: a toggle command plus a dedicated keybinding, because recording has a start/stop lifecycle a terminal can only approximate with press-to-start/press-again-to-stop. A camera photo has no such lifecycle — one press, one photo — so modeling it as a second toggled mode would import machinery (mode state, a keybinding, a status-bar indicator) that nothing here needs.

Camera capture is also more fragmented across platforms than audio. Desktop OSes expose the camera through OS-specific device APIs (v4l2 on Linux, AVFoundation on macOS, DirectShow on Windows); Termux has no `/dev/video*` at all and must go through `termux-camera-photo`, a Termux:API Android-intent binary; WSL2 has no camera passthrough unless the user has separately set up `usbipd-win`.

Field-testing a first implementation surfaced a real proot-in-Termux gotcha, verified interactively rather than assumed: `termux-camera-photo`, run from inside a `proot-distro` guest, *does* reach the Termux:API app (the app replies with a real, structured error) — the app is a separate, non-prooted Android process with its own real filesystem view, so it fails only because the guest's own `/tmp`/`$HOME` paths (e.g. `/tmp/test.jpg`) don't exist there. A fixed absolute path under Termux's real home directory works identically from native Termux and from inside proot, since it's the same real location either way.

A second question was whether `/photo` needed an enable gate like `LLM_VOICE_ENABLED`. Checking the actual evidence — `llm_voice.py`'s docstring, ADR-0076, and the 2.44.0 changelog entry — the gate exists for one stated reason: voice requires **Python packages** (`sounddevice`, `vosk`, `numpy`) that may not be installed, so it is opt-in (by declaration, or implicitly by having installed vosk — see ADR-0076's auto-enable) rather than failing at runtime for anyone who hasn't installed them. Nothing ties the gate to privacy or operator control.

That reasoning doesn't transfer here: photo capture needs no new Python dependency, only external binaries (`ffmpeg`, `termux-camera-photo`) invoked via subprocess with a graceful `None` return and a `missing_tool_hint()` message on failure — exactly the shape of the existing clipboard-image-paste feature (`zrb/llm/util/clipboard.py`, the Ctrl+V handler), which has no enable gate at all.

**Decision.**

**1. `/photo [device]` is a one-shot command**, modeled on `/attach` rather than `/voice`.

It runs `_handle_photo_command`/`_submit_photo` in `zrb/llm/ui/base/conversation_commands.py`, capturing a JPEG and appending it to `_pending_attachments` as a `BinaryContent` — the same three steps (`get_camera_photo()` → `scale_image_bytes()` → `BinaryContent`) the Ctrl+V clipboard-paste handler already uses. No mode state, no keybinding, no status-bar indicator.

**2. The optional trailing argument is the camera device** (index, path, or name depending on platform), matching how `/attach <path>` takes its argument. This covers device selection without a config knob.

**3. No enable gate.** `/photo` is available whenever `LLM_UI_COMMAND_PHOTO` resolves a command token, same as `/attach`. Failure (missing `ffmpeg`, no camera, permission denied) degrades to a graceful error plus a platform-specific hint, never a crash.

**4. Capture shells out to external binaries — no new Python dependency.** `zrb/llm/util/camera.py` mirrors `clipboard.py`'s structure exactly: a documented per-platform priority order, a public `get_camera_photo(device=None) -> bytes | None` that never raises, private per-backend functions, and a `missing_tool_hint()`.

| Platform | Backend |
| --- | --- |
| Termux (native or proot) | `termux-camera-photo`, writing to the fixed absolute path `/data/data/com.termux/files/home/.zrb_camera_photo.jpg`, read back and unlinked |
| macOS | `ffmpeg -f avfoundation` |
| Windows | `ffmpeg -f dshow`, auto-detecting the first video device from `ffmpeg -f dshow -list_devices true -i dummy`'s stderr output when no device is given |
| Linux / WSL | `ffmpeg -f v4l2`, defaulting to `/dev/video0` |

Termux is **not** `tempfile.gettempdir()`: the Termux:API app process resolves the target path in its own real Android filesystem, so a proot guest's own `/tmp` (what `tempfile.gettempdir()` would return from inside `proot-distro`) doesn't exist from the app's point of view and the capture fails with a `FileUtils Error`. Termux's home directory is always at that one fixed location regardless of which shell (native or prooted) invoked the command, so no proot detection is needed — one universal path just works everywhere.

**5. WSL gets no special-cased code.** It's just Linux from `ffmpeg`'s point of view; `usbipd-win` passthrough makes `/dev/video0` exist, its absence makes capture fail with a hint.

In practice, `usbipd-win` attach can fail even after binding — Windows' Frame Server frequently keeps an exclusive handle on a laptop's *built-in* camera, per field-testing; an external USB webcam attaches far more reliably. This is a Windows/usbipd-win limitation with no zrb-side workaround, documented in the troubleshooting guide rather than coded around.

**Consequences.** A `/photo [device]` command in the chat TUI (and any UI built on `BaseUI`, including the non-interactive/simple UI path, since it follows `attach_commands`' wiring rather than `voice_commands`' TUI-only wiring) with no new dependency and no effect when unused. Because there is no gate, `/photo` is always advertised in help/completion; a failed capture is always a graceful error, never a crash. Windows device auto-detection is best-effort — multi-camera machines or unusual driver naming may require the user to pass a device name explicitly, discovered via `ffmpeg -f dshow -list_devices true -i dummy`.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| A toggled mode with a dedicated keybinding, like voice | A snapshot has no start/stop lifecycle to key off; the machinery would exist for nothing. |
| An `opencv-python` (or similar) dependency | `ffmpeg` and `termux-camera-photo` already cover every platform via subprocess, matching how `clipboard.py` avoids an image-clipboard library. |
| An `LLM_ENABLE_PHOTO_CAPTURE` gate mirroring `LLM_VOICE_ENABLED` | Voice's gate is specifically about undeclared Python dependencies, a concern that doesn't apply to a dependency-free, subprocess-based, gracefully-degrading feature; the closer precedent (clipboard-image-paste) has no gate either. |
| A config knob for the camera device | The command argument already covers per-call overrides; a config default would only duplicate it. |

**Where it lives.** `src/zrb/llm/util/camera.py`, `src/zrb/llm/ui/base/conversation_commands.py` (`_handle_photo_command`, `_submit_photo`), `src/zrb/config/mixins/llm_ui_commands.py` (`LLM_UI_COMMAND_PHOTO`).
