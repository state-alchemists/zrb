# ADR-0079 — LaTeX math renders as Unicode via masked pre-parse, not a Rich `Markdown` subclass

**Status:** Accepted

**Context.** Assistant output routes through one choke point, `render_markdown` (`src/zrb/util/cli/markdown.py`), which wraps `rich.markdown.Markdown` — backed by `markdown-it-py`, which has no notion of `$...$` math. Every render path (live-turn history replay, sub-agent result blocks, tool-call diff/arg previews) shows `$...$` as literal text, and any new handling must keep that as the fallback when conversion fails.

Two designs were considered:

- **Subclass `Markdown`.** Rich dispatches node types through a `ClassVar[dict]` named `elements` (`fence` → `CodeBlock`, etc., read via `self.elements.get(token.type)`), so a subclass could add a `math` element — but `markdown-it-py` emits no math token to dispatch on. Adding one means forking inline-parsing rules inside a third-party parser, for deep AST integration this feature doesn't need.
- **Convert math spans in the raw string before Rich sees it.** No parser hook, at the cost of its own masking so a `$` inside code isn't mistaken for math.

Mermaid/PlantUML are **out of scope here**: at design time both appeared to need external tooling (`mmdc`/Node+Chromium, or `plantuml.jar`/Java), and terminal image protocols are unreliable, especially over WSL2. Plain-fence rendering is already a safe fallback — `CodeBlock.__rich_console__` builds a `Syntax(code, lexer_name, ...)`, and `Syntax.lexer` catches pygments' `ClassNotFound` (`rich/syntax.py`), so an unknown fence language degrades to unhighlighted text without crashing. Mermaid later got a pure-Python, no-subprocess renderer (ADR-0080); PlantUML has none and stays deferred (ADR-0080's Alternatives rejected).

**Decision.** `render_markdown` calls `convert_math_to_unicode` (`src/zrb/util/cli/latex_math.py`) on the raw markdown string before constructing `Markdown(...)`, gated by `CFG.LLM_UI_ENABLE_MARKDOWN_MATH` (default on).

1. **Mask before matching.** Fenced code blocks and inline code spans become placeholders before any `$` scanning, so code containing `$` (shell variables, prices in a snippet) is never touched. This is why call sites that render a whole fenced payload (diff previews, YAML tool-args previews) need no opt-out: the payload is masked out wholesale.

2. **A Pandoc-style heuristic picks inline math out of prose.** A `$...$` span counts as math only when its content doesn't start/end with whitespace and the closing `$` isn't immediately followed by a digit — the standard fix for "I have $5 and $10".

3. **Conversion is pure-Python and in-process** (`pylatexenc`, no subprocess). It is a core dependency, not an extra: unlike `rag`/`voice`/the provider SDKs it has zero transitive dependencies and a footprint under 1MB, and making it optional would contradict the toggle's default — a bare `pip install zrb` would silently render nothing while claiming to. (It was briefly the `math` extra, until the footprint was measured.)

   The import stays lazy and memoized (`functools.lru_cache`-wrapped `_get_latex_tools`) purely for cold-start latency, like the lazy imports of the core dependencies `markdownify`/`pyperclip`/`bs4`. The `try/except ImportError` fallback is a defensive backstop, since the package is always present.

4. **Fallback is per-span.** Each match is parsed with `pylatexenc.latexwalker.LatexWalker(..., tolerant_parsing=False)`; a `LatexWalkerParseError` (malformed LaTeX) keeps that span as raw text. An unrecognized but syntactically valid macro can silently convert to an empty string instead of raising, so an empty result also counts as failure and keeps the raw span. One bad span neither blanks itself nor affects any other. A top-level `try/except` around the whole function returns the original text unchanged as the last line of defense.

5. **`^exp`/`_sub` become Unicode super/subscripts, only inside an already-converted math span.** `pylatexenc.latex2text` maps named macros/symbols to Unicode (`\alpha` → `α`, `\int` → `∫`) but leaves `^`/`_` as ASCII (`x^{2}` → `x^2`). `_convert_super_sub` (`src/zrb/util/cli/latex_math.py`) runs a second pass over each span's converted output — never the raw document — turning a maximal run after `^`/`_` into Unicode when every character has a super/subscript form, and leaving it ASCII otherwise (`x^2` → `x²`, but `x^q` stays `x^q` — Unicode has no superscript "q", and subscript covers only 16 Latin letters).

   The scoping is a correctness requirement, not an optimization: markdown's `_italic_` emphasis is built from underscores, so running the substitution over the whole text would mangle real prose (e.g. `_am_` — both characters are subscript-mappable).

6. **A ` ```latex `/` ```tex ` fenced block is treated as math, not code.** Models wrap LaTeX in a fence at least as often as `$...$`/`$$...$$`. Pygments has a real `latex`/`tex` lexer, so such a fence rendered as highlighted "code", which reads as a regression next to inline math rendered as Unicode. The real fix is `example.md` (a composed prompt section, `LLM_INCLUDE_SECTIONS`), which shows the model the expected `$...$`/`$$...$$` form directly.

   `_mask_fence` in `latex_math.py` is the defense-in-depth backstop for when a fence appears anyway (a non-compliant model, pasted content, non-zrb history): it converts the fence body like a block-math span, but on failure restores the *original* fence verbatim, so a broken `latex` block keeps its syntax-highlighted box.

**Consequences.** LaTeX math in assistant markdown renders as Unicode wherever `render_markdown` is used, with no change to any non-math render (diffs, tool-arg previews, plain prose, non-latex fences) because masking makes the conversion a no-op there. A bare `pip install zrb` renders math out of the box, matching the toggle's default.

Super/subscript coverage is inherently partial (Unicode's gap) — a run with any unmappable character stays ASCII rather than partially converting. Prompt wording is a soft constraint; the fence fallback is what keeps a non-compliant model's output safe rather than broken.

**Alternatives rejected.** *Subclass `Markdown`'s `elements` map / hook `markdown-it-py` inline parsing* — the deeper integration point, but there is no math token to hook without extending the third-party parser's inline rules; masking+regex gets the same visible result in a small, local, testable function.

*Render math as an image via a terminal graphics protocol* — sixel/Kitty/iTerm2 support is inconsistent (especially over WSL2); Unicode works in every terminal. *Handle Mermaid/PlantUML in the same change* — assumed to need an external binary and a terminal-compatible output path; deferred, then revisited for Mermaid once a pure-Python option appeared (ADR-0080).

**Where it lives.** `src/zrb/util/cli/latex_math.py`, `src/zrb/util/cli/markdown.py`, `src/zrb/config/mixins/llm_ui_styles.py` (`LLM_UI_ENABLE_MARKDOWN_MATH`).
