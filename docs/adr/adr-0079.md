# ADR-0079 — LaTeX math renders as Unicode via masked pre-parse, not a Rich `Markdown` subclass

**Status:** Accepted

**Context.** Assistant output routes through one choke point, `render_markdown` (`src/zrb/util/cli/markdown.py`), which wraps `rich.markdown.Markdown` — itself backed by `markdown-it-py`, with no notion of `$...$` math. Every render path (live-turn history replay, sub-agent result blocks, tool-call diff/arg previews) already falls back to showing `$...$` as literal text, which is the behavior any new handling must preserve when conversion isn't possible.

Two designs were considered for adding LaTeX math. Rich's `Markdown` dispatches node types through a `ClassVar[dict]` named `elements` (`fence` → `CodeBlock`, etc., read via `self.elements.get(token.type)`), so a subclass could add a `math` element type — but `markdown-it-py` has no math token to dispatch on in the first place; teaching it one means forking inline-parsing rules inside a third-party parser, for a payoff (deep AST integration) this feature doesn't need. The alternative — converting math spans in the raw markdown string before Rich ever sees it — needs no parser hook at all, at the cost of doing its own masking so a `$` inside code isn't mistaken for math.

Mermaid/PlantUML were considered together with LaTeX but are **out of scope here**: at design time both appeared to need external tooling (`mmdc`/Node+Chromium, or `plantuml.jar`/Java) and terminal image protocols are unreliable, especially over WSL2. Confirmed while designing this: today's plain-fence rendering is already a safe fallback — `CodeBlock.__rich_console__` builds a `Syntax(code, lexer_name, ...)`, and `Syntax.lexer` catches pygments' `ClassNotFound` for an unrecognized language (`rich/syntax.py`) — so an unknown fence language already degrades to unhighlighted text with no crash. A follow-up spike found a pure-Python, no-subprocess renderer for Mermaid after all — see ADR-0080. PlantUML has no equivalent and stays deferred (ADR-0080's Alternatives rejected).

**Decision.** `render_markdown` calls `convert_math_to_unicode` (`src/zrb/util/cli/latex_math.py`) on the raw markdown string before constructing `Markdown(...)`, gated by `CFG.LLM_UI_ENABLE_MARKDOWN_MATH` (default on).

1. **Mask before matching.** Fenced code blocks and inline code spans are replaced with placeholders before any `$` scanning happens, so code containing `$` (shell variables, prices in a snippet) is never touched. This is also why every existing `render_markdown` call site that renders a whole fenced payload (diff previews, YAML tool-args previews) needs no opt-out: the payload is masked out wholesale and the render is unaffected.
2. **A Pandoc-style heuristic picks inline math out of prose.** A `$...$` span only counts as math when the content doesn't start/end with whitespace and the closing `$` isn't immediately followed by a digit — the standard fix for "I have $5 and $10" not being read as a math span.
3. **Conversion is pure-Python** (`pylatexenc`), no subprocess, in-process. It's a core dependency, not an extra: unlike `rag`/`voice`/the provider SDKs, it has zero transitive dependencies and a footprint under 1MB, so there's no install-weight reason to gate it — and gating it would fight the toggle's own default: `LLM_UI_ENABLE_MARKDOWN_MATH` defaults on, so an optional dependency would mean a bare `pip install zrb` silently renders nothing while claiming to. (An earlier revision of this decision made it the `math` extra; reverted once the footprint was actually measured.) The import stays lazy and memoized (`functools.lru_cache`-wrapped `_get_latex_tools`) purely for cold-start latency, the same reason `markdownify`/`pyperclip`/`bs4` — also core dependencies — are lazy-imported elsewhere; the `try/except ImportError` fallback is now a defensive backstop rather than a designed path, since the package is always present.
4. **Fallback is per-span, not all-or-nothing.** Each match is parsed with `pylatexenc.latexwalker.LatexWalker(..., tolerant_parsing=False)`; a `LatexWalkerParseError` (malformed LaTeX) keeps that one span as raw text. An unrecognized-but-syntactically-valid macro can silently convert to an empty string instead of raising, so a converted-empty result is also treated as a failure and the raw span is kept — one bad span doesn't blank itself out, and doesn't affect any other span in the same document. A top-level `try/except` around the whole function is the last line of defense, returning the original text unchanged.
5. **`^exp`/`_sub` become real Unicode super/subscripts, but only inside an already-converted math span.** `pylatexenc.latex2text` maps named macros/symbols to Unicode (`\alpha` → `α`, `\int` → `∫`) but leaves `^`/`_` as literal ASCII (`x^{2}` → `x^2`). `_convert_super_sub` (`src/zrb/util/cli/latex_math.py`) runs a second pass over each span's *already-converted* output — never over the raw document — turning a maximal run after `^`/`_` into Unicode when every character in it has a super/subscript form, and leaving the run as ASCII otherwise (`x^2` → `x²`, but `x^q` stays `x^q` — Unicode has no superscript "q", and subscript covers only 16 Latin letters). Scoping this to converted math-span output only is not an optimization, it's a correctness requirement: markdown's `_italic_` emphasis syntax lives in the same document and is built entirely from underscores, so running this substitution over the whole text would occasionally mangle real prose (e.g. `_am_` — both characters happen to be subscript-mappable).
6. **A ` ```latex `/` ```tex ` fenced block is also treated as math, not code.** In practice a model reaches for a fenced code block around LaTeX at least as often as `$...$`/`$$...$$` — pygments already has a real `latex`/`tex` lexer, so that fence rendered as syntax-highlighted "code" before this feature existed, which reads as more of a regression once inline math nearby is rendering as Unicode. `example.md` (a composed prompt section, `LLM_INCLUDE_SECTIONS`) now shows the model the expected `$...$`/`$$...$$` form directly, which is the real fix — the model controls its own output and should not reach for a fence in the first place. `_mask_fence` in `latex_math.py` is the defense-in-depth backstop for whenever it does anyway (a model that doesn't follow the instruction, pasted content, non-zrb history): it converts the fence body the same way as a block-math span, but on failure restores the *original* fence verbatim rather than falling through to plain text, so a broken `latex` block keeps its syntax-highlighted box instead of losing it.

**Consequences.** Assistant markdown containing LaTeX math renders as Unicode wherever `render_markdown` is used, with zero behavior change for every existing non-math render (diffs, tool-arg previews, plain prose, non-latex fences) because masking makes the conversion a no-op there. A bare `pip install zrb` renders LaTeX math out of the box — no extra to remember, matching the toggle's own default. Super/subscript coverage is inherently partial (Unicode's own gap, not this feature's) — a run with any unmappable character stays ASCII rather than partially converting. Prompt wording is a soft constraint, not an enforced one — the fence fallback is what keeps a non-compliant model's output safe rather than broken.

**Alternatives rejected.** *Subclass `Markdown`'s `elements` map / hook `markdown-it-py` inline parsing* — the deeper integration point, but there is no math token to hook without first extending the third-party parser's inline-rule set; masking+regex gets the same visible result with a small, local, testable function. *Render math as an image via a terminal graphics protocol* — sixel/Kitty/iTerm2 support is inconsistent (especially over WSL2), and Unicode is portable everywhere a terminal already works. *Handle Mermaid/PlantUML in the same change* — assumed at the time to need an external binary and a terminal-compatible output path; deferred, then revisited separately once a pure-Python option for Mermaid was found (ADR-0080).

**Where it lives.** `src/zrb/util/cli/latex_math.py`, `src/zrb/util/cli/markdown.py`, `src/zrb/config/mixins/llm_ui_styles.py` (`LLM_UI_ENABLE_MARKDOWN_MATH`).
