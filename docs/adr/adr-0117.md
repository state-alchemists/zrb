# ADR-0117 — The `/btw` panel holds the focus while it is shown, and a typed character still starts a message

**Status:** Accepted

**Context.** `/btw` answers a question off to the side, and the answer lands in a panel docked above the input (`UISideQuestion`). The panel scrolls: a side answer can run well past the twelve rows it shows. Whichever pane holds the focus receives the movement keys, and the input field's Up is not a cursor move — it recalls a queued message, then walks the loaded conversation and the cross-session history (ADR-0077). So with a long answer on screen and the focus in the input, Up meant "show me the message I sent two minutes ago" and the answer could not be scrolled at all.

An earlier iteration of the panel did take the focus. It was reverted because the panel then owned the keyboard until Esc: a second `/btw` — the documented way to replace the panel — could not be typed, and `/btw` is routed ahead of a pending approval or question (ADR-0093), so the answer field of a dialog underneath it went out of reach. Taking the focus again is only correct with both of those costs paid.

**Decision.**

1. **Opening the panel moves the focus to it** (`UISideQuestion.begin`), so the movement keys reach the panel's own bindings. The input field's bindings are control-local, so while the panel is focused they cannot fire at all: the queue recall and prompt_toolkit's history walk are unreachable, not merely filtered.

2. **The panel binds the movement keys itself** — Up/Down one line, PageUp/PageDown a panel page (ten of its twelve rows), Home/End the ends of the answer. Like the output pane's, they move the read-only buffer's cursor; the window follows the cursor, so a scroll is a cursor move and streamed text cannot snap the view back.

3. **A printable key starts a message instead of scrolling.** While the panel is focused, an application-level catch-all forwards each printable character — Unicode included — to `UI.insert_input_text`, so it lands in the input field while the focus stays on the panel. The catch-all is registered on the application, not as a `Keys.Any` on the panel's control: the panel is read-only and binds only its own movement and dismissal keys, so Enter, Ctrl+X, Ctrl+G and every other exact binding still win over the catch-all instead of being swallowed by it. The focus is deliberately *not* handed back on the first keystroke: that would put Up/Down back on the queue recall with the answer still on screen, which is the defect this record fixes. Enter keeps the rule the rest of the UI already follows for a submit pressed outside the input field — it returns the focus and does not submit the pane it was pressed in.

4. **A prompt waiting for the user keeps the focus.** `begin` skips the focus move while `is_waiting_for_answer` is true: `/btw` runs ahead of a pending approval or question, and that field is what the turn is blocked on. The panel is still shown and still one Esc away; it does not take the keyboard from a dialog it opened over.

5. **Esc closes the panel and gives the focus back** to the input field, exactly as before: the panel binds `escape` itself, the application binding dismisses the same panel when the key reaches it first, and both end in `dismiss()`.

**Consequences.** A long answer is read with the keys that belong to it, and the input's recall is unaffected once the panel is closed. The cost is two keystrokes for the next message: typing lands in the input while the panel holds the focus, so the cursor is not visible there until Enter (which only refocuses) or Esc (which closes the panel) hands it back. Over a pending dialog the panel does not take the focus, so Up/Down there still recall messages — the dialog owns the keyboard by the same rule that gives it to the panel here.

**Alternatives rejected.**

- *Leave the focus in the input and filter its Up while the panel is up* — the panel is what is being scrolled, so the filter would have to reach from a pane that is not focused into one that is, and it would have to cover prompt_toolkit's own history walk plus every other movement key the panel wants (PageUp, PageDown, Home, End), each in a second place. "Which pane receives this key" is what prompt_toolkit's focus already answers.
- *Take the focus and leave the keyboard there until Esc* — the iteration this record replaces. A read-only answer view holding the keyboard makes the panel modal: the input is unusable, and `/btw` itself cannot be typed again.
- *Hand the focus back on the first printable key, as the output pane does* — typing would then silently end the mode the user opened the panel for: the answer is still on screen, but Up recalls messages again. The output pane can afford it because it is not the reason the user pressed the key.
- *A modal overlay that dims the input* — the same loss of the input as the iteration above, plus a screen that no longer looks like a chat.

**Where it lives.** `src/zrb/llm/ui/default/side_question.py` (the panel, its key bindings and `begin`), `src/zrb/llm/ui/default/ui.py` (`_create_side_question_float`), `src/zrb/llm/ui/default/keybindings.py` (Esc dismisses the panel before anything underneath), `src/zrb/llm/ui/default/app/focus.py` (`focus_widget`), `src/zrb/llm/ui/default/app/keybinding.py` (the output pane's own movement keys, which this mirrors), `test/llm/ui/default/test_side_question.py`. See ADR-0093 for `/btw` running ahead of a pending dialog, and ADR-0077 for what the input's Up recalls.
