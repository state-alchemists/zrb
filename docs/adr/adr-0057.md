# ADR-0057 — Tool output is capped twice: per tool, then a global backstop

**Status:** Accepted

**Context.** Only the read and shell tools capped their own output. Grep, code
analysis, web fetches and MCP results were uncapped, so one large result could
flood the context window.

**Decision.** Two cooperating deterministic layers.

1. **Per-tool self-capping** against `CFG.LLM_MAX_OUTPUT_CHARS` (default 100k).
   The file, list, search and shell tools bound their own output
   *directionally*: `Read`, `List` and `Grep`-style tools keep the head, while
   `Shell`/`Bash` keep the tail, where errors and exit summaries land. Cuts snap
   to a line boundary, and the shell tools additionally dump full stdout and
   stderr to a temp file whose path is surfaced, so the model can recover the
   rest with Grep or Read.
2. **A global backstop** against `CFG.LLM_MAX_TOOL_RESULT_CHARS` (default 100k;
   `0` disables), applied in the tool wrapper to *every* tool's model-facing
   result — which is what catches the tools that do not self-cap. It keeps head
   **and** tail with a middle marker describing how to re-fetch a narrower
   slice.

A typical result is under both caps and untouched.

**Consequences.** A pathological output can no longer degrade the model, and
recovery is always available — a narrower query, or the temp file. Above the
cap the model sees a truncated view and must narrow its request. Note the
interaction with ADR-0043: because the backstop historically applied only to a
duplicated field, making it bite on the real payload is a deliberate future
decision, not something to enable silently.

**Alternatives rejected.** *Chunked streaming of tool results* — runner surgery
for a problem two caps solve. *Per-tool caps only* — every tool differs, and new
or MCP tools arrive uncapped. *No cap* — a latent context-flooding bug that
fires on the first large repository.

**Where it lives.** `src/zrb/util/truncate.py`,
`src/zrb/llm/agent/truncate.py` (`truncate_tool_content`),
`src/zrb/config/mixins/llm_limits.py`.
