# ADR-0126 — zrb keeps its own model capability table, because pydantic-ai's profiles assume capability

**Status:** Accepted

**Context.** `ModelCapabilities` answers one question for the whole framework: is this model able to read an image, a PDF, a video, audio, and how large a context will it accept? zrb built it before pydantic-ai had an answer, and it has three parts — a pattern table on the bare model name, a user-extensible `register()` override list, and a conservative default of `False` for everything.

pydantic-ai 2.61 ships something that looks like the same thing. `ModelProfile` carries 34 fields resolved per provider (`openai_model_profile`, `anthropic_model_profile`, `google_model_profile`, and eleven more), merged over `DEFAULT_PROFILE`. The overlap with zrb's seven fields is close enough that keeping both looks like duplication, and the obvious simplification is to source zrb's answers from upstream and delete the pattern table.

Measured on 2026-10-24 against pydantic-ai 2.61.0, across 22 models in 8 provider families — resolving both sides for the same bare name and comparing field by field:

| Field | Agree | Differ |
|---|---|---|
| `supports_image_input` | 16/22 | 6 |
| `supports_audio_input` | 18/22 | 4 |
| `supports_video_input` | **3/22** | **19** |
| `supports_document_input` | 14/22 | 8 |
| thinking | 12/22 | 10 |
| `context_window` | 12/22 | 10 |

The disagreements are not drift in either table; they are the two systems answering differently on purpose.

`DEFAULT_PROFILE` declares `supports_image_input`, `supports_document_input` and `supports_video_input` all `True`. A provider profile names only the keys it is sure about, so everything else inherits that optimistic default. `openai_model_profile('gpt-3.5-turbo')` and `anthropic_model_profile('claude-instant-1')` set nothing about input modalities at all, which means the resolved profile claims all three of `gpt-3.5-turbo`, `gpt-4-0613` and `claude-instant-1` read images, PDFs and video. zrb's `_IMAGE_DENY` exists for exactly those names, and its default is `False` so an unlisted model is under-declared rather than over-declared.

Two more differences are semantic rather than numerical. zrb's `supports_thinking_summary` asks a narrower question than upstream's `supports_thinking`: not "can it reason" but "does it always reason while summarizing only when asked" — Gemini's `include_thoughts`. Adopting the broader flag switches the `thinking=True` default on for Anthropic, where extended thinking is billed. And `context_window` is the reverse case: upstream's profiles leave it `None` for most models (`meta` is the notable exception), while zrb's table carries documented values, so here zrb is ahead rather than behind.

Finally, the narrow form of adoption — take only the keys a provider profile sets *explicitly*, never `DEFAULT_PROFILE` — was measured too. Across 24 models it yields three: `supports_video_input` for Gemini 2.5, Gemini 3 and Gemma 3. The first two already agree; the third has upstream claiming video input for an image-only model.

**Decision.**

1. **`ModelCapabilities` stays the source of truth.** The pattern table, the `register()` override layer and `supports_modality` are unchanged. It answers a question upstream does not: what may zrb *send* a model before the provider rejects it.

2. **Only an explicit provider-profile key would be admissible upstream input — never `DEFAULT_PROFILE`.** The optimistic default is the failure mode, not the data. Measured today, that rule admits nothing zrb lacks, so nothing is adopted.

3. **The conservative default is the point, not an oversight.** Under-declaring costs a refused attachment the user can see and correct; over-declaring produces a provider 400 in the middle of a turn, after the tokens have been spent.

4. **No change to tool deferral.** zrb does not hand-roll it: its tools pass `defer_loading=True` to pydantic-ai's own `Tool`, and `search_tools` is pydantic-ai's auto-injected capability. There was no custom deferral to replace.

5. **This is re-opened by an upstream change, not by a date.** If a future pydantic-ai minor starts populating `context_window` per model, or makes the modality defaults conservative, the balance moves and this decision is revisited against the same measurement.

**Consequences.** Two tables continue to exist, and zrb's can lag for a model upstream happens to know — a model released after zrb's last table edit is under-declared until someone adds it. The `register()` API is the escape hatch, and `test/llm/util/test_capabilities.py` already pins the conservative contract (text-only models denied images and documents, video limited to Gemini-class models, thinking summaries limited to Gemini 2.5+), so a future "just adopt upstream" change fails in CI rather than in a chat.

**Alternatives rejected.**

- *Swap zrb's table for upstream's resolved profiles* — the table above: 19/22 models would gain video support they do not have, and text-only models would gain images and documents. That is a behaviour regression, not a simplification.
- *Merge `DEFAULT_PROFILE` under zrb's answers* — identical outcome for any model neither side names, which is most of them.
- *Take only explicitly-set provider keys* — measured at 3 of 24 models, one of them wrong; the plumbing would cost more than it returns.
- *Delete the table and let the provider error* — turns a pre-flight "I cannot read that" into a mid-turn 400 with the tokens already spent, and loses `context_window`, which upstream mostly does not carry.

**Where it lives.** `src/zrb/llm/util/capabilities.py` (patterns, registry, defaults), `test/llm/util/test_capabilities.py` (the pinned contract), `src/zrb/llm/common_tools.py` and `src/zrb/builtin/llm/chat.py` (`defer_loading=True`, which is upstream's mechanism, not zrb's). See ADR-0125 for the pydantic-ai 2.61 move this was measured against, and ADR-0038 for the deny-list policy the defaults belong to.
