# ADR-0112 — Emotion travels as an emoji in the text and leaves zrb as the `Emotion` hook

**Status:** Accepted

**Context.** An avatar such as zrb-face should show how the user sounds and how zrb answers. No standard carries emotion between a speech stack and an agent. W3C EmotionML (2014) is unused, SSML has no emotion element, and every vendor has its own control: OpenAI's `instructions`, Gemini's style prompt, ElevenLabs' `[excited]` tags, Cartesia's `emotion` enum, Azure's `express-as`. On the detecting side, SenseVoice (zrb's `funasr` service) writes `<|HAPPY|>`-style tokens that FunASR turns into emoji, and a multimodal model can be asked for the tone along with the words.

Two other problems remained. A tag such as `[happy]` in the reply would show in every UI unless each UI stripped it from the stream. A per-feature callback would reach Python code loaded in the same process, but nothing else.

**Decision.** `enable_emotion(task, EmotionConfig)` follows ADR-0102. The built-in `llm_chat` calls it, and `ZRB_LLM_EMOTION_ENABLED` (off by default) switches it on.

1. **Both emotions are state, never text the user reads.** The model can only say how it feels in what it writes, so the `emotion_live` live context asks it to open each reply with one of 😊 😢 😠 😮 😌 🙂. A pydantic-ai capability (`ReplyEmotion`), added per run through `LLMChatTask.append_capability_factory` while emotion is on, takes the emoji out of both copies of the reply: the streamed events every UI, speech and observer read (`wrap_run_event_stream`, which holds a text part's events until its first visible character and passes them on in order), and the finished response that the output, history, final render and hooks are made from (`after_model_request`). The emotion is kept as `current_reply_emotion` in the run's context instead, which speech reads for the voice. With emotion off, the factory adds no capability and a run is unchanged. The user's tone is never written into their words either: dictation hears it and sets `InputProvenance.tone` and `tone_score`, which the live context renders on the Input line (`microphone/dictation, sounding sad (0.82)`). Emoji in the text were tried first and dropped on both sides: on the user's, a typed emoji read as a detected tone, the detector's confidence was lost, and the user's words were changed in the history; on the model's, the user saw an emoji they had no use for.
2. **The names are VRM 1.0's preset expressions:** `happy`, `sad`, `angry`, `surprised`, `relaxed`, `neutral`. An avatar maps them one to one. Each name accepts a family of emoji (`label.py`). Emoji built with a variation selector are left out, since they draw narrow in terminals.
3. **Emotion leaves zrb as a hook event, `Emotion`** (zrb-specific, observe-only), carrying `emotion` and `emotion_source` (`user` or `assistant`). A hook factory, a `hooks.json` command hook (`CLAUDE_EMOTION`) or an agent hook all receive it, so a tool in any language can consume it. Matchers match on `emotion_source`.
4. **Both fire from the stream observer, on the run's event loop.** The `UserPromptSubmit` hook that reads the prompt runs on a pool thread, where firing another event would nest hook execution. So it only queues the user's emotion, and the reply's first stream event fires it, just before the reply's own.
5. **The voice follows the reply's emotion through a voice per emotion, not a style.** `ZRB_LLM_SPEECH_EMOTION_VOICES` maps an emotion to a voice, and speech reads a reply's opening emoji from the same stream (`ReplyOpening`) to pick it. With Pocket TTS a voice is a clip to clone, and a clip spoken in an emotion carries it over: cloned from OpenAI-made happy, sad and angry clips, the same sentence came out at 205, 164 and 244 Hz (references 201, 161 and 228), at 3.5× real time on a CPU. Chatterbox's `exaggeration` was as expressive but ran at a tenth of real time there. The voice reaches the backend as the ambient `current_speech_voice`, bound by the speaker's worker around each utterance, because an extension may wrap the backend (zrb-face does), and a parameter on `create_audio` would stop at the wrapper. A Pipecat pipeline sends `TTSUpdateSettingsFrame` only when the voice changes.
6. **Dictation owns the detection, beside the transcriber.** `DictationSession` runs `EmotionDetector` (emotion2vec+) on each hands-free utterance's audio while the backend transcribes it, so it works with any backend, a streaming one (vosk) included, and costs no time when it finishes first. Measured on RAVDESS (180 actor clips, CPU only), emotion2vec+ base was right 97% of the time at ~0.3 s a clip, and SenseVoice's own emotion tag 18%, nearly always "unknown" on English. SenseVoice is still the fast local transcriber (`sensevoice`, on sherpa-onnx): no word errors on clean 9–11 s clips in ~360 ms, where Moonshine `medium-streaming` took 4.8 s. funasr and torch, which emotion2vec+ runs on, are imported by name and not declared, like sherpa-onnx, which has no Termux wheel. Push-to-talk puts its text in the input box, where it is sent as typed text, so it carries no tone.

**Consequences.** An avatar needs one hook to show both sides. The emoji costs a token or two per reply and is visible in the transcript, which is the point. Recognition is weak beyond happy, angry and sad, so an emotion is a hint, not a fact. Detection is opt-in twice, since the EU AI Act prohibits emotion recognition in the workplace.

Only the Pipecat services switch voice per reply. OpenAI's `instructions` and Gemini's style would take an emotion directly, but their style is still fixed when the backend is built. Pocket TTS needs the gated voice-cloning weights (`kyutai/pocket-tts`), and each change of voice re-derives its voice state from the clip.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Stripping a tag in each UI and in the history | Every UI (TUI, web, CLI), the history and the hooks would each have to strip it, from a stream that arrives in fragments; the capability does it once, where pydantic-ai produces both copies. |
| An `ExpressEmotion` tool | A tool call costs the model a round trip before its first word, which a spoken reply cannot afford. |
| The user's tone as an emoji appended to the transcript | A typed emoji read as a detected tone, the confidence was lost, and the user's words changed in the history. |
| A callback on `EmotionConfig` | It reaches only Python in the same process; the hook reaches commands and agents too. |
| A side classifier (emotion2vec, Hume) | A model or vendor added for little over what the transcriber and SenseVoice already give. Hume's Expression Measurement API was retired in June 2026. |
| EmotionML or SSML | No engine zrb uses reads either. |
| A `voice` parameter on `create_audio` | A wrapping backend (zrb-face's `QuietSpeech`) would drop it. |
| One backend per voice | A Pocket model loaded once per emotion, on machines with a few GB. |
