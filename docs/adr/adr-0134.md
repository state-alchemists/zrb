# ADR-0134 — Journal usage is measured per prompt and per automatic search, so a retrieval change can be judged

**Status:** Accepted.

**Context.** The journal's usage log already records eight kinds of event, and `/usage` reports what they add up to: index cost per injection, search quality, note reuse, judge runs, and HUD notes that were injected and never read. Measured over 2026-10-26 → 2026-10-30 that was 74 searches and 38 injections across 15 sessions, 69% of written notes never read again, and every injection truncated.

Those numbers cannot answer the one question a memory system has to answer: **does the agent have to look it up?** A session is not a question — one of those 15 ran 18 searches over an afternoon — so searches per session has no denominator, and the improvement target (lookups per answer ≤ 1.5) could not be checked even after the change.

The second gap was narrower and deliberate. The opening-message auto-search calls `find_in_journal` rather than `search_journal` so that a search the agent never asked for is not counted as its own (journal.py:88-93). The consequence is that a mechanism which costs a ripgrep on every session start had no measurement at all: neither how often it found something, nor whether what it found was ever used.

**Decision.**

1. **One `prompted` event per user message**, recorded in `run_agent` where `nested_run` is already resolved — a nested run is a tool call, not a question, and the runner is the only place that knows the difference. It is not recorded in the `UserPromptSubmit` hook: the same event, but the hook would need to re-derive the guard the runner already holds.

2. **One `auto_searched` event per automatic retrieval**, carrying the same `terms`, `results` and `hits` fields as `searched` but as a separate kind, so the agent's own search count stays a count of searches it chose. It is recorded even when it finds nothing: a miss is the measurement.

3. **`/usage` gains two lines.** `turn` reports prompts and lookups per prompt, where a lookup is a `searched` or a `read` — a search that returns a note the agent then opens costs two, and that is the cost the user pays. `auto` reports auto-searches and the share that found something. Both lines are absent when the window holds no event to divide by, rather than dividing by a guess.

**Consequences.** The log gains one line per prompt and one per session start, which is negligible beside the injection and search events already there. A window recorded before this change has no `prompted` events, so its ratios are absent rather than zero — an old window reads as unmeasured, which is true. Every later change to retrieval (ranked injection, recency scoring, consolidation) is judged on lookups per prompt and auto-search yield, with the offline paired eval cross-checking the same claim on a fixed question set; the two are deliberately different measurements of the same thing, one lived and one controlled.

**Alternatives rejected.**

- *Count model rounds as turns* — a turn that makes six tool calls is still one question, and counting rounds would make an agent that searches once look cheaper than one that searches once and reads twice.
- *Fold the auto-search into `searched`* — it would make an automatic miss read as a search the agent chose and gave up on, which is exactly the confusion the original split avoided.
- *Derive prompts from the history file instead of recording them* — the transcript is written by another layer, on its own schedule, and a metric that needs a second file parsed to be computed is one that will not be looked at.

**Where it lives.** `src/zrb/llm/journal_usage_log.py` (`PROMPTED`, `AUTO_SEARCHED`, `record_prompted`, `record_auto_searched`), `src/zrb/llm/agent/run/runner.py` (the `nested_run` guard and the call), `src/zrb/llm/prompt/live_context.py` (`_render_possibly_related`), `src/zrb/llm/custom_command/usage_command_journal.py` (`_turn_line`, `_auto_search_line`). See ADR-0055 for the journal itself and who may write it.
