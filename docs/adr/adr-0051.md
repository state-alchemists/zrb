# ADR-0051 — Capability and profile are keyed differently and are not merged

**Status:** Accepted

**Context.** zrb carries two model registries with the same shape — a list of
user-registered regex overrides, most-recently-registered first, falling back to
a built-in pattern table, returning a conservative default for unknown names:

- `model_capabilities` (`llm/util/capabilities.py`) — model → image/audio/video
  input support, parallel-tool-call support (ADR-0038).
- `model_profile_registry` (`llm/prompt/profile.py`) — model → prompt profile
  (ADR-0049).

`profile.py` said so in a comment: *"Mirrors `model_capabilities`."* Read as an
invitation to merge, which is the obvious refactor and the reason this record
exists. The pressure to merge is also conceptual: the argument that *model size
is a proxy for capability, not capability itself* makes "capability → profile"
sound like the natural architecture, with one registry as its natural home.

Both registries were measured before the merge. They key on different things,
and each key is load-bearing:

| | `model_capabilities` | `model_profile_registry` |
|---|---|---|
| Matches against | the **bare** name (`_bare_name` strips `provider:`, lowercases) | the **full** id, nothing stripped |
| Because | a capability is a property of the *weights* | a profile is a property of the *deployment* |
| So | `gpt-4o` takes images via `openai:` or `azure:` alike | `ollama:phi4-mini` is 3.8B on a laptop; `openai:gpt-5-nano` is a hosted entry tier |

The evidence is direct. `builtin_profile("ollama:phi4-mini")` returns `minimal`
and `builtin_profile("phi4-mini")` returns `lean` — the provider prefix *is* the
signal (`LOCAL_PROVIDERS`), and `ollama:kimi-k2.6:cloud` returns `None` because
the `:cloud` tier suffix disqualifies it (`_HOSTED_TIER`). Meanwhile the
capability table's deny patterns are `^`-anchored against the stripped name
(`^claude-haiku-3$`, `^gpt-3\.5`), which only works because the prefix is gone.

A merge must pick one key, and both choices regress **silently**:

- **Bare name** destroys `LOCAL_PROVIDERS` and `_HOSTED_TIER`, dropping every
  locally-served small model from `minimal` back to `lean` — reintroducing
  exactly the defect ADR-0049 records fixing.
- **Full id** un-anchors the image deny-list, so `^claude-haiku-3$` stops
  matching `anthropic:claude-haiku-3` and a text-only model is handed image
  support.

Neither failure raises. Both produce a working system that is quietly wrong.

**Decision.** The two registries stay separate. The similarity is shape, not
substance, and the comment asserting otherwise is replaced by the distinction
above in `ModelProfileRegistry`'s docstring.

`prompt_profile` is **not** added as a field of `ModelCapabilities`, and the
capability record is **not** extended with an `instruction_following` /
`tool_use` / `reasoning` / `autonomy` taxonomy. No composition step reads such a
field, and no source populates one; a registry of scores nothing consults is
config for a value that never changes. A capability field is added when
something composes on it.

`test_profile.py::test_profile_and_capability_registries_key_on_different_things`
pins both halves, so a future merge fails loudly instead of regressing quietly.

**Consequences.** A plugin author declaring both facts about one model makes two
calls against two module paths. That is the cost, and it is the honest one: the
two calls mean different things, and a single call taking one pattern would
apply that pattern under two different matching rules.

The user-facing fix for the two paths is exposure, not unification — both are
exported from the top-level package and documented together as "what you can
declare about a model" (ADR-0049 governs the profile half).

A real consequence for future work: **"capability → profile" is not currently
implementable**, because no field in `ModelCapabilities` implies a profile.
Parameter count remains the built-in heuristic, `register_model_profile` remains
the escape hatch, and a measured capability signal — not a richer type — is what
would change that.

**Alternatives rejected.** *Merge on the bare name* — the regression above,
silent, on the two most-run local model families. *Merge on the full id* —
the mirror-image regression, silent, on image support. *Merge with a per-field
matcher* — one `register_model()` whose pattern means different things depending
on which keyword you passed; strictly more surprising than two functions.
*Keep the registries and add `prompt_profile` to `ModelCapabilities` anyway* —
puts the field where the wrong matcher would read it, for a value the other
registry still owns. *Leave the "Mirrors" comment* — it is what makes the
unsound merge look like tidying.

**Where it lives.** `src/zrb/llm/prompt/profile.py` (`ModelProfileRegistry`,
`builtin_profile`, `LOCAL_PROVIDERS`, `_HOSTED_TIER`),
`src/zrb/llm/util/capabilities.py` (`ModelCapabilityRegistry`, `_bare_name`,
`_IMAGE_DENY`),
`test/llm/prompt/test_profile.py`
(`test_profile_and_capability_registries_key_on_different_things`),
`AGENTS.md` (LLM Prompt System).
