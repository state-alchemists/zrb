# ADR-0122 — Live context reports the background processes this session owns

**Status:** Accepted

**Context.** A `Shell` command can now outlive its call twice over: `background=True` starts one deliberately, and a command that outruns its timeout is moved to the background rather than killed (ADR-0121). Either way the handle is named exactly once — in the tool result that created it, or in the timeout report that adopted it.

Every later turn depends on that one message. It is ordinary history, so compaction can replace it; and even without compaction, a handle mentioned five turns ago competes with everything said since. The process does not stop being real: it keeps running, keeps holding its port, and keeps consuming whatever it consumes. The most expensive available mistake is starting a second copy because the first has become invisible.

zrb's live context already exists for exactly this kind of fact — the time, the git state, the worktrees, the todos, the agent mode: state the agent cannot otherwise see, rendered on the user turn so the cached system prefix stays byte-stable (ADR-0042, ADR-0044). ADR-0050 says the prompt states the risky runtime state rather than its absence. A running process the agent has forgotten is that risk.

**Decision.**

1. **One line per handle, every turn it exists.**

   ```
   - Background processes (Shell handles this session still owns):
     - tender-thicket-7 (running, 4m12s): uvicorn app:app --port 8000
     - quiet-otter-3 (exited, code 1, 1m03s): make test
     MonitorProcess(handle) reads one; kill=True stops it.
   ```

   Handle, status, elapsed, and the description clipped to 80 characters. The closing line names the two calls that act on a handle: the point of reporting a process is that the agent does something about it.

2. **Scoped to the session that started it.** The registry records the `ChatSessionManager` session id, and the section filters on the same key. Another chat's handle is not this chat's business, and naming it would invite the agent to poll or kill a process it never started. Outside a web chat both sides are the empty string, which is correct: one terminal session owns every local process.

3. **Read-only.** A new `summary()` reads the registry without touching it. `poll()` is the wrong call here: it retires an entry once the process has finished and its output has been drained, so a prompt render would silently consume the handle the model was about to ask about.

4. **A standing condition, not a delta.** The git section renders as a diff against the previous turn's block; this one does not. "This is running" is true every turn until it is not, and a delta would show it once and then fall silent — the failure mode it exists to prevent.

5. **Omitted when empty.** A session that never backgrounds anything renders exactly as it did before, which is most sessions.

6. **A failed read costs the section, not the turn.** An unimportable registry or a registry mutated mid-read is logged at debug and renders nothing.

**Consequences.** While anything is running, every turn carries a few lines about it — bounded by the real number of live handles, since the registry only holds processes that exist. Elapsed time counts from when the registry took the process over: for `background=True` that is its start, and for an adopted command it is the moment it outran its timeout, which is the number a reader wants anyway ("how long has this been in the background"). A finished process stays listed until something polls it, so the section can briefly say `exited` about work whose output nobody has read — that is accurate, and the alternative was making the render consume it.

**Alternatives rejected.**

- *Trust the tool result* — it is a normal message: compaction replaces it, and a turn that never revisits it has no reminder at all.
- *Put it in the system prompt* — it changes every time a process starts or exits, and the system prompt is the cached prefix (ADR-0042); the whole reason live context exists on the user turn.
- *Push a message when a process exits* — needs a channel into a running turn, would interleave with tool results, and still says nothing about a process that started and is quietly still running.
- *Report the whole registry* — simpler, and wrong: other sessions' handles are not this session's to act on.
- *Have the render call `poll()`* — it would retire handles as a side effect of asking a question.

**Where it lives.** `src/zrb/llm/tool/shell_background.py` (`_BackgroundProcess.started_at`, `_ShellBackgroundRegistry.summary`), `src/zrb/llm/prompt/live_context.py` (`_background_process_lines`, `_format_elapsed`, wired into `_render_parts`), `test/llm/prompt/test_live_context_background.py`. See ADR-0121 for how a process ends up in the registry and ADR-0050 for the reporting principle.
