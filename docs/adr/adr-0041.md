# ADR-0041 — zrb owns conversation history, with two-tier summarization

**Status:** Accepted

**Context.** Conversations outgrow the context window, so older history must be compressed and the compressed form must persist into later requests.

pydantic-ai offers a native `ProcessHistory` capability (passed via `capabilities=`) that writes its result back into the live run history. It has no equivalent of zrb's two-tier summarization — state-snapshot condensation plus per-result compression — so it cannot replace zrb's pipeline as is. Moving any part of the pipeline onto it would need an equivalence test plan first.

**Decision.** zrb owns history. Processors are stored on the agent and applied by zrb itself, before the first model call and between tool-loop iterations, where it controls the history reference. Summarization is two-tier: an oversized individual tool result is compressed by the message summarizer, and when total tokens cross 75% of the prompt budget the older portion is condensed into a `<state_snapshot>` while recent turns are kept verbatim. History is re-sanitized after compression.

The split is token-first. The trigger threshold is the budget to stay under; the kept tail is the newest turns that fit 40% of it, so a compaction leaves room for the conversation that follows rather than triggering again on the next request. `LLM_HISTORY_SUMMARIZATION_WINDOW` (300 messages) is a backstop for histories of many small messages, not the rule that decides the split. The split lands on a turn boundary when one keeps at least half the tail budget; otherwise the earliest safe split wins, so one long tool loop is not summarized whole to reach a user message. Tool call/return pairs are never separated.

Compression is lossy in the model's view but not on disk: the messages a summary replaces are appended word for word, human-readably, to `<history dir>/verbatim/<session>.md` — the directory the history manager stores the conversation in, not a fixed one. The file is append-only across compactions and sessions of the same conversation, and the summary names its path in a paragraph written by zrb — never by the summarizer model, which can mangle or invent a path. The agent reads that file when the summary lacks a detail. What is archived is the history as the conversation held it: the processor snapshots it before oversized tool results are reduced to summaries, and a session name that is omitted is derived from the conversation's opening message, so callers that cannot name themselves still do not share a file.

Context fitting uses the lower of `LLM_MAX_TOKEN_PER_REQUEST` and a known model's registered context window; unknown models retain the configured cap. When a retained `ModelResponse` reports usage, its input plus output tokens anchor the estimate through that response; only later messages use the local tokenizer/heuristic.

**Consequences.** Summaries persist, and long sessions stay in budget while keeping recent fidelity. A 75% trigger with a 40% tail spends fewer tokens than a 60% trigger with a 70% tail did, and compacts less often, because each compaction frees about a third of the window instead of a sliver. When the archive write succeeds, its verbatim text remains recoverable even if the summary omits details; a failed write yields no archive pointer and logs a warning, rather than promising recovery that did not happen — and a write that lost the race for the archive lock says so, naming `LLM_ARCHIVE_LOCK_TIMEOUT`, because "no pointer" and "nothing was dropped" are different news. The cost is a parallel history pipeline that must be maintained against pydantic-ai's own behaviour — the guards in ADR-0040 exist because that pipeline interacts with the deferred-tool loop — plus an archive file per conversation, which is collected with the conversation: the retention pass deletes an archive only when no history file in that directory, live or backup, still carries its pointer, and only once it is older than `LLM_HISTORY_RETENTION`. Age is part of the rule because compaction writes the archive before the history that references it, so a fresh archive is briefly referenced by nothing.

The summary is handed over as a fenced block, and its size is bounded. Role alternation merges it into the same user turn as the real user messages that follow, so the block opens with its own header, says it is derived data rather than the user speaking, and closes with an end marker: a sentence inside it that reads like an instruction has to be checkable against the user's own words, which arrive after the marker. `LLM_SUMMARY_MAX_TOKENS` (2000, the budget the summarizer prompt already asked for in prose) bounds one summary, and it is measured on the block as it will be inserted — the framing zrb writes, the snapshot, the journal index and the archive pointer — because a cap that measured the model's text alone lets the turn it lands in run past it. A block over the cap is shortened at most twice, then truncated by exactly what it overflows by, and the rule applies to a summary that lost its schema as well: too much prose costs the same as too much snapshot. When the framing and the notes fill the cap on their own, the snapshot is dropped and the warning says to raise the cap — an over-cap block is the failure the cap exists to prevent, and what has to go is the part zrb can regenerate. An empty summary leaves the history unsummarized.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Rely on pydantic-ai's native history processing (`ProcessHistory`) | Has no equivalent of zrb's two-tier summarization (state-snapshot condensation, per-result compression). |
| Naive truncation | Drops decisions the model still needs. |
| No summarization | The provider eventually rejects an over-long history. |
| Keep the 60% trigger with a 70% tail | The tail ate most of the headroom, so a compaction could be followed by another almost at once; the tail budget disagreed with the trigger, which is what left the splitter searching for a split point it could not find. |
| Message-count retention (`keep the last N messages`) | Message size varies by orders of magnitude; a count says nothing about whether the request fits, and a fixed count either overflows with large tool results or compacts needlessly with small ones. |
| Summarize in the background and swap later | Compaction already runs before a request on the exact history about to be sent; a background pass would summarize a snapshot the conversation can diverge from, and the swap would need a divergence check that costs more than the compaction saves. The append-only archive already gives the agent access to text newer than the summary. |
| Model-authored archive path in the summary | A generated path can be wrong; the path is machine-specific and known exactly where the archive is written. |
| A `genai-prices` context-window registry | zrb already owns a user-extensible model capability registry; adding a second dependency and source of truth buys no correctness. |
| Clearing old tool results before summarization | The proposed zero-LLM tier discards evidence before zrb's snapshot can preserve it, so it trades correctness for token recovery; spill and summary already provide lossless/reconstructive alternatives. |
| Reject a malformed or over-long summary and keep the history verbatim | The moment a summary is needed is the moment the history is over budget, so refusing it turns a poor summary into a failed request; the archive keeps the originals either way, and the cap bounds the cost of keeping the bulky one. |

**Where it lives.** `src/zrb/llm/summarizer/` (including `verbatim_archive.py` and `history_splitter.py`), `src/zrb/llm/agent/common.py` (comment on why `history_processors` is omitted), `src/zrb/llm/prompt/markdown/conversational_summarizer.md`, `message_summarizer.md`.
