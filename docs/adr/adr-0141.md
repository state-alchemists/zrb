# ADR-0141 — A shell judge annotates the approval prompt, and may skip it only where no rule already answered

- **Status:** Accepted
- **Date:** November 14, 2026

## Context

Go reported that he no longer reads the command on every approval prompt — "I tend to not fully read the shell command every time you ask for approval" — and the research in `docs/0009-whether-a-judge-should-vet-shell-commands.md` found that this is not a personal failing: Anthropic measures a human block rate falling from ~17% to ~5% after fifty prompts in a session, against 75% of METR's developers reporting they read every line.

That research concluded with an order: sandbox, then a deterministic classifier, then a judge for the middle band only. This ADR builds the judge first, and the reason it is defensible is that it builds the half that can only *inform*. A judge that adds a line to a prompt cannot widen anything; the version that removes prompts is the one carrying Anthropic's ~17% false-negative rate on real overeager actions.

Four production harnesses ship a command-safety LLM — Codex auto-review, Cursor's classifier, Copilot's assisted permissions, OpenHands' `LLMSecurityAnalyzer` — and all four say in their own docs that it is not a security boundary. The boundary remains the sandbox (ADR-0065). What this adds is a prompt filter that fails closed.

## Decision

**Two knobs, two different grants.**

| Setting | Default | What it grants |
| --- | --- | --- |
| `LLM_SHELL_JUDGE_ENABLED` | `off` | One small-model call per judged command; one line in the prompt saying what it saw |
| `LLM_SHELL_JUDGE_AUTO_APPROVE_ENABLED` | `off` | That a `safe` verdict skips the prompt |

The second is meaningless without the first. Kept apart because they are not the same trade: the first buys *informed approval* and costs a call, the second buys *fewer prompts* and costs the judge's misses.

**It sits at priority 3b** — after the tool policies, the permission ruleset, the non-interactive settle, the default approvals, YOLO and the `PermissionRequest` hook, and immediately before the approval channel and the CLI prompt. That is the last position from which a person has not yet been asked, and it is below every rule on purpose: a permission `ask` someone wrote down and a hook's `permissionDecision: "ask"` both outrank a model's opinion, and `force_ask` blocks the auto-approve knob, and so does a call that sets
`dangerously_skip_sandbox` — the invariant every other approval path in the
cascade keeps: a request to leave the sandbox is a request for a human, however
ordinary the command is behind it.

**Only `safe` may skip the prompt.** The four levels are `safe`, `caution`, `dangerous` and `unknown`; `caution`, `dangerous` and a judge that failed all still ask. A boolean would have folded "I could not judge this" into "unsafe" and lost the line that says so, which is the line that tells a person their knob is not working.

**Reasoning-blind input.** The judge reads the command, the working directory, whether the sandbox is off, and how many uncommitted files the repository holds. It does not read the conversation, the assistant's own text, or earlier tool results. Anthropic reports that including them *lowered* classifier accuracy, and the mechanism is plain: the model being judged would be writing part of its own input, and "the user approved something like this earlier" is the argument a bad command needs to survive. The dirty-file count is there because misses cluster on blast radius — the judge sees `git reset --hard` correctly and still cannot know what it would destroy.

**Fail closed, always.** A model error, a timeout, an unreadable answer and a command over 10,000 characters are all `unknown`, which asks. The function returns a verdict and never raises: an exception here would abort an approval that is otherwise fine.

**The line travels by `tool_call_id`.** The verdict is decided in `agent/run/deferred_calls.py` and drawn by `tool_call/handler.py::format_approval_message`, which receives only the `ToolCallPart`. `tool_call/judge_note.py` holds the record keyed by the per-call-unique id — the same shape `override_registry` uses, and for the same reason: the two ends of one approval sit in different layers. The four level constants live there rather than in the judge because `agent/` may import `tool_call/` and not the reverse.

## Consequences

- **The judge's own tokens are not in `/usage` yet.** Only the turn runner writes usage records (`agent/run/runner.py::_record_run_usage`), and this call sits beside the turn rather than under it — the same gap that hides the memory reviewer. It is logged at debug and nowhere else. M0 — component attribution — is what makes it visible, which is why it is being built after this feature rather than before: the vocabulary M0 introduces has to include a component that exists.
- **With the second knob on, false negatives become exposure.** Anthropic's honest number is 17% on 52 real cases, and no independent, sequence-aware measurement of any command-safety judge exists. A per-command judge is also structurally blind to a sequence: the attack is often the order and the intent, neither of which is in the command about to run.
- **The deterministic tier is still unbuilt.** The eight high-severity Claude Code advisories were all *parser* bypasses, and a judge layered above a shell parser inherits every one of them. This ADR does not close that work; it defers it again.
- **The prompt gains one line, and only for shell commands.** Non-shell calls are untouched, and with the judge on and auto-approve off, the only observable change is that line.

## Alternatives

- **A `PermissionRequest` hook built on the existing agent-hook machinery.** Rejected: a hook can `allow` — which would let a model widen — and it has no channel for a line that reaches the prompt the human answers.
- **Structured output instead of a parsed line.** pydantic-ai's structured output is not uniform across the eight providers zrb speaks, and a text line parsed with a fail-closed fallback is portable to all of them. Claude Code and Codex both parse text for the same reason.
- **Judging every tool, not just `Shell`.** A `RunZrbTask` carries a task name, and a rubric about shell commands reads a task name as noise. The gate is `Capability.EXECUTE` *and* a non-empty `command` argument, which is `Shell` and nothing else today.
- **Making this the security boundary.** Rejected on the evidence in `docs/0009`: no filter running significantly faster than the model it guards can universally distinguish adversarial from benign input, and a judge's precision collapses from 0.96 to about 0.5 moving to the 20:1 benign:risky ratio real command streams have.
