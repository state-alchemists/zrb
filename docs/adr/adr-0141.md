# ADR-0141 — A shell judge annotates the approval prompt, and may skip it only where no rule already answered

- **Status:** Accepted
- **Date:** November 14, 2026

## Context

The prompt this annotates had stopped being read. Anthropic measures a human block rate falling from ~17% to ~5% after fifty prompts in a session, against 75% of METR's developers reporting they read every line — so the complaint that opened the research in `docs/0009-whether-a-judge-should-vet-shell-commands.md` is not a personal failing but the ordinary shape of approval fatigue.

That research concluded with an order: sandbox, then a deterministic classifier, then a judge for the middle band only. This ADR builds the judge first, and the reason it is defensible is that it builds the half that can only *inform*. A judge that adds a line to a prompt cannot widen anything; the version that removes prompts is the one carrying Anthropic's ~17% false-negative rate on real overeager actions.

Four production harnesses ship a command-safety LLM — Codex auto-review, Cursor's classifier, Copilot's assisted permissions, OpenHands' `LLMSecurityAnalyzer` — and all four say in their own docs that it is not a security boundary. The boundary remains the sandbox (ADR-0065). What this adds is a prompt filter that fails closed.

## Decision

**Two knobs, two different grants.**

| Setting | Default | What it grants |
| --- | --- | --- |
| `LLM_SHELL_JUDGE_ENABLED` | `off` | One small-model call per judged command; one line in the prompt saying what it saw |
| `LLM_SHELL_JUDGE_AUTO_APPROVE_ENABLED` | `off` | That a `safe` verdict skips the prompt |

The second is meaningless without the first. Kept apart because they are not the same trade: the first buys *informed approval* and costs a call, the second buys *fewer prompts* and costs the judge's misses.

**Only the first is a session's to flip.** Inside a conversation, `/judge` (`LLM_UI_COMMAND_JUDGE`) turns consultation on or off for that session alone, read per command so a flip reaches a turn already running, and it leaves both settings as the deployment wrote them. `/judge on` also withdraws the auto half for that conversation, even where a launch flag or the environment granted it: every keystroke can move the judge towards asking, and none can hand a prompt away.

**The second is reachable by launch, not by keystroke.** `zrb chat --judge auto-approve` writes both settings for the run. A command line typed out and left in shell history is the distance the paragraph above asks for — a keystroke is not. The info bar says which state is in force, `AUTO` in the red pair the YOLO badge uses or `On `/`Off`, so the grant is visible for the whole session rather than said once at its start.

**The line carries the facts it judged with.** The prompt draws the level, then the facts that *raise* the risk — a sandbox that is off, a non-empty count of uncommitted files — then the sentence. A sandbox that is on and a clean repository are what a reader already assumes, so naming them would crowd out the two that matter. The facts come from the call's own arguments and from `git status`, never from the model, so they are the half of the line a reader can check; the sentence is model output and may be confident and empty at once.

**It sits at priority 3b** — after the tool policies, the permission ruleset, the non-interactive settle, the default approvals and YOLO, and before the `PermissionRequest` hook, the approval channel and the CLI prompt. That is the last position from which a person has not yet been asked, and it is below every rule on purpose: a permission `ask` someone wrote down and a hook's `permissionDecision: "ask"` both outrank a model's opinion, and `force_ask` blocks the auto-approve knob, and so does a call that sets
`dangerously_skip_sandbox` — the invariant every other approval path in the
cascade keeps: a request to leave the sandbox is a request for a human, however
ordinary the command is behind it.

**It settles before the `PermissionRequest` hook, not after it.** That event's own contract is "fires now that the call will prompt", and a hook that announces a prompt — the speech feature reads it aloud — must not be told about one a `safe` verdict is about to remove. Before it was moved, an auto-approved call was announced to the hook and then never asked, so a person heard a question nobody was waiting to have answered.

**Only `safe` may skip the prompt.** The four levels are `safe`, `caution`, `dangerous` and `unknown`; `caution`, `dangerous` and a judge that failed all still ask. A boolean would have folded "I could not judge this" into "unsafe" and lost the line that says so, which is the line that tells a person their knob is not working.

**A level with no reason is not a verdict.** `SAFE:` alone — a truncated answer, or a model that ignored the format — parses to `unknown`, and `ShellVerdict.is_safe` asks for the level *and* a reason. The one word is not enough to skip a prompt.

**It is identified by the tool's name, not by capability metadata.** A deferred `ToolCallPart` carries no capability tag — `tool_capability` answers `UNKNOWN` for one, because the tag lives on the registered callable — so the first version of this gate asked a question that was always answered "unknown", and the judge never ran at all. `shell_formatter` and `bash_safe_command_policy` already match on `"Shell"` for exactly this call, and that shape now lives in one module, `tool_call/shell_call.py`, which all three read: the name, the command argument, and the sandbox flag are the same three facts for every component that has to recognise a shell call, and three copies of them drift.

Those last two were caught by the review of the pull request, not by the tests written beside the code, which is why they are written down here.

**Reasoning-blind input.** The judge reads the command, the working directory, whether the sandbox is off, and how many uncommitted files the repository holds. It does not read the conversation, the assistant's own text, or earlier tool results. Anthropic reports that including them *lowered* classifier accuracy, and the mechanism is plain: the model being judged would be writing part of its own input, and "the user approved something like this earlier" is the argument a bad command needs to survive. The dirty-file count is there because misses cluster on blast radius — the judge sees `git reset --hard` correctly and still cannot know what it would destroy.

**Fail closed, always.** A model error, a timeout, an unreadable answer, a command over 10,000 characters and a level with no reason behind it are all `unknown`, which asks. `judge_shell_command` raises `ShellJudgeError` and `judge_or_unknown` turns it into the pessimistic verdict, so an approval cannot abort on a flaky model and the handler is not one the broad-except ratchet counts as swallowing.

**The answer is typed.** The judge is asked for a `JudgeVerdict` — a `level` from three words and a `reason` — rather than for a line of prose with a verdict at the front of it. The difference is where the checking happens: a schema is enforced by the model call itself, so an answer that fits has already been validated, and one that does not is a failed call, which is `unknown`, which asks. A model that answers in text anyway still reaches `parse_verdict`, which keeps its own fail-closed rules; the old regular expression is the road for a provider without tool calling, not the only road.

**The line travels by `tool_call_id`.** The verdict is decided in `agent/run/deferred_calls.py` and drawn by `tool_call/handler.py::format_approval_message`, which receives only the `ToolCallPart`. `tool_call/judge_note.py` holds the record keyed by the per-call-unique id — the same shape `override_registry` uses, and for the same reason: the two ends of one approval sit in different layers. The four level constants live there rather than in the judge because `agent/` may import `tool_call/` and not the reverse.

## Consequences

- **The judge's own tokens are in `/usage`, under `shell_judge`.** `judge_shell_command` writes a usage record per judged command beside the turn runner's own, so the small-model call is visible as its own component; on 2026-11-16 it cost 0.02M fresh tokens over 67 records. This bullet said the opposite when the ADR was written, and stopped being true the same day, in `27ae01c34` — component attribution landed with the vocabulary that could name a call outside the turn.
- **With the second knob on, false negatives become exposure.** Anthropic's honest number is 17% on 52 real cases, and no independent, sequence-aware measurement of any command-safety judge exists. A per-command judge is also structurally blind to a sequence: the attack is often the order and the intent, neither of which is in the command about to run.
- **The deterministic tier is still unbuilt.** The eight high-severity Claude Code advisories were all *parser* bypasses, and a judge layered above a shell parser inherits every one of them. This ADR does not close that work; it defers it again.
- **The prompt gains one line, and only for shell commands.** Non-shell calls are untouched, and with the judge on and auto-approve off, the only observable change is that line.
- **The line leads with a circle, then says the level in words.** The word is what a decision is made on, and it stays. The circle was added on 2026-11-15, and it answers the same problem the judge exists for: the prompt had stopped being read, and a colour is what an eye catches before a word is. The earlier objection was width — a symbol turned emoji by a variation selector is counted two columns and drawn one, so the letter after it is overwritten — and the answer is to use only glyphs that are wide by default. These four circles are East Asian Wide and `wcwidth` answers two for each; `test_every_circle_is_wide_by_default` is what keeps a fifth one from being added carelessly. The white circle is the one terminals present differently: counted at two columns and drawn at one, it leaves a gap rather than taking the word with it.

## Alternatives

- **A `PermissionRequest` hook built on the existing agent-hook machinery.** Rejected: a hook can `allow` — which would let a model widen — and it has no channel for a line that reaches the prompt the human answers.
- **Structured output instead of a parsed line.** pydantic-ai's structured output is not uniform across the eight providers zrb speaks, and a text line parsed with a fail-closed fallback is portable to all of them. Claude Code and Codex both parse text for the same reason.
- **Judging every tool, not just `Shell`.** A `RunZrbTask` carries a task name, and a rubric about shell commands reads a task name as noise. The gate is the tool's name — `"Shell"` — plus a non-empty `command` argument, and `Shell` is the only tool registered under that name, so the line reaches shell approvals and nothing else. A model-facing `Bash` name is not a second entry point: it is accepted only in an agent definition that asks for it, and resolves to `Shell` there.
- **Making this the security boundary.** Rejected on the evidence in `docs/0009`: no filter running significantly faster than the model it guards can universally distinguish adversarial from benign input, and a judge's precision collapses from 0.96 to about 0.5 moving to the 20:1 benign:risky ratio real command streams have.
