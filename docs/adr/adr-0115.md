# ADR-0115 — The microphone opens before the tone loads, and a heavy model's load spike lands outside the chat

**Status:** Accepted

**Context.** Two features load a large model into the chat process, and a third measure says what that costs. Measured on a 6.8 GB WSL2 machine (20 shared vCPUs, 2 GB swap), with the models cached:

| piece | load time | resident after | peak while loading |
|---|---|---|---|
| SenseVoice on sherpa-onnx (`model.int8.onnx`, 229 MB) | 2.3 s | 372 MB | 396 MB |
| emotion2vec+ base via funasr (1.1 GB checkpoint) | 8.1 s warm, 19.5 s cold | 977 MB (+517 MB for torch) | **2993 MB** |
| Pocket TTS `load_model` | 0.9 s | 753 MB | 920 MB |

Three things went wrong with that:

- **The microphone waited for the tone.** `DictationSession._prepare_models` gathered the transcriber's `prepare` and the emotion detector's, then opened the microphone, so hands-free listening began after `max(2.3 s, 8–20 s)` — the emotion model, every time a chat started.
- **Two spikes stacked.** Speech's warm-up trigger and dictation's prepare both run at session start, so Pocket TTS's model and emotion2vec+ loaded at once, on top of a process already holding ~1.8–2.2 GB. funasr loads the checkpoint and then copies it into the model, so its load transiently costs ~2 GB more than the model keeps. A live chat peaked at 4.09 GB (`VmHWM`) against a 6.8 GB machine, and the kernel's OOM killer killed `zrb` four times in three days, each time at 2.75–3.51 GB of anonymous memory, with the failed allocation inside zrb.
- **A warm-up thread per turn.** `Speaker.warm_up` was called at the start of every turn and spawned a thread every time, with no guard. One live chat had 38 `zrb-speech-warm-up` threads parked behind the same load.

**Decision.**

1. **The microphone waits for the transcriber alone.** `_prepare_models` awaits the backend's `prepare` and starts the emotion model's on a task of its own (`_start_emotion_load`, one per session). `EmotionDetector` takes its load lock without waiting (`_get_classify`): an utterance heard while the model loads carries no tone, which is what an utterance heard before the model loaded always got. The load is marked synchronously (`begin_loading`) before that task is scheduled, because the microphone opens first: without the mark, the first utterance could take the load on itself and wait out all 8–20 s of it.
2. **One heavy model loads at a time.** `zrb.llm.util.model_load.heavy_model_load(purpose)` is a context manager over a process-wide slot, taken by emotion2vec+ (`load_classifier`, `EmotionWorker.start`) and by every *local* Pipecat service build (`SpeechServiceManager.create_service`; a remote service builds a client, not a model, and never queues). The wait is bounded (`WAIT_SECONDS`, 120 s), so a load that wedges costs the other feature a delay, not its model.
3. **The tone's model can load in a child process.** With `LLM_DICTATION_EMOTION_OUT_OF_PROCESS` on, `EmotionWorker` (`src/zrb/llm/dictation/emotion_model.py`) starts a child with `multiprocessing`'s `spawn` — the chat holds torch threads, and forking a process with native threads is the shape that crashes — and the child loads the model there, answering `("ready", "")` or `("error", reason)` over a pipe, then one clip per request. The child asks to be picked first if the machine runs out (`oom_score_adj` 1000, written where Linux allows it), so what dies is the tone's process, not the conversation. A child that dies is forgotten and the next utterance starts another, up to `MAX_DEATHS` (3); after that the tone is given up on for the session rather than restarting into the same kill. `MemoryError` is in `MODEL_ERRORS`, so a machine that cannot hold the model costs only the tone. The worker is kept only while something can reach it: `EmotionDetector` keeps it *before* its model loads, so a session that ends mid-load can close it, and `EmotionWorker.start` waits for readiness in `READY_POLL_SECONDS` slices rather than in one call that would ignore the close until the model was in; a child that says nothing for a clip (30 s, against a measured 0.3 s) is stopped like a dead one rather than asked again for every later clip; a child that cannot classify a clip is kept, since the next clip is other audio, and one that cannot classify two in a row is treated like a dead one, so a model that fails on everything does not leave the session without tones; and a detector whose child is gone drops the callable that talks to its pipe, which is what makes the restart above reachable at all.
4. **One warm-up per backend set.** `Speaker.warm_up` starts a thread only when none is running and none has finished since the set was built; `restart_backends` clears that, since a fresh set holds other models. A warm-up that a restart overtook says nothing about the set that replaced it: its completion is checked against the set's generation, so the next `warm_up` warms the set that is there now. A warm-up that fails still counts as done: the first sentence retries anyway.
5. **A stutter says how much of it there was.** The underrun warning ADR-0114 owns now carries the count and the block size, and names `ZRB_LLM_SPEECH_PLAYER_BLOCK_FRAMES` as the knob that lengthens a block.

**Consequences.** Hands-free listening starts in ~2.5 s instead of 8–20 s, and the first one or two utterances carry no tone; from then on, tones arrive as before. The two session-start loads no longer peak together, and with the knob on, the chat's own peak is what the transcriber and the voice cost (~1.5–2 GB) instead of 4 GB. `funasr`'s 2 GB spike still happens, in the child, which asks to be the one killed. The price is one resident process (~1 GB with the model loaded) while a session hears tones, and a failure mode where a machine too small for both loses the tone silently, by design: a tone is a hint (ADR-0112) and a killed chat is not.

**Alternatives rejected.**

| Alternative | Why rejected |
|---|---|
| Keep the two prepares gathered | It is exactly what made listening wait, and what made the two load spikes land together. |
| Cap the child with `RLIMIT_AS` | Address space is no measure here: the chat's `VmPeak` is 8 GB while its resident set is 2 GB, so a cap low enough to bound memory fails torch's import long before the machine is out. |
| `fork` instead of `spawn` | The parent has torch, onnxruntime and PortAudio threads; a forked child of that process is the known crash shape, and a dead child costs the tone. |
| Load emotion2vec+ in the chat and free it between utterances | The model is 977 MB resident and ~0.3 s a clip; reloading per utterance costs the 2 GB spike every time. |
| Turn the tone off | It is the feature ADR-0112 exists for; the point was to keep it on a small machine. |
| One output stream kept open, or a player daemon, against the stutter | A larger change to ADR-0114's player, and the underrun count now says whether a block size is the cheaper answer. |
| Load every model in a child process | The voice is the one whose latency the user hears first, and its model's spike is a fifth of the tone's; the slot is the cheap part of the fix and covers both. |
