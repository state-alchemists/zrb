# ADR-0044 — The system prompt is composed from ordered sections, and custom sections are config-positioned

**Status:** Accepted

**Context.** A monolithic system prompt accretes duplicate and contradictory
rules, and cannot be audited or partially replaced. But a fixed set of sections
is not enough either: the only downstream extension point used to be
`append_prompt`, which always lands **last**. A downstream needing an always-on
section positioned *among* the built-ins — company context before the workflow
rules, a live deploy-status block — had no declarative way to get one. Some
such content is static text; some must reflect runtime state.

**Decision.** `PromptManager` composes the prompt from ordered, single-concern
sections through a chain of middlewares. Order is configuration —
`include_sections` or `ZRB_LLM_INCLUDE_SECTIONS`, comma-separated and
order-sensitive.

**Each section is MECE**: one behaviour lives in exactly one section, so a rule
has a single home and cannot contradict itself.

A name in the list that is **not** a built-in resolves as a custom section
composed at its configured position, with precedence *built-in > registered
provider > markdown file*:

- `register_section(name, provider)` registers a `Callable[[AnyContext], str]`
  called with the active context at compose time — for content that reflects
  runtime state. A built-in name is never shadowed. Returning `""` emits
  nothing.
- Otherwise the name resolves through `get_prompt(name)` (project override →
  env → base prompt dir → package) with `{PLACEHOLDER}` substitution.

Ordering is declarative in config; dynamic *behaviour* is registered explicitly
in Python, typically from `zrb_init.py`. Config never names a file to execute.

**Consequences.** A rule has exactly one home; sections are independently
testable, replaceable and droppable; downstreams add positioned sections
without editing `PromptManager`. `register_section` is also the documented
extension point for anything that used to reach for a bespoke registry
(ADR-0045). The cost: a misspelled section name resolves to `""` rather than
erroring — a warning is logged at compose time, but a typo'd built-in is still
an invisibly dropped section.

**Alternatives rejected.** *Free-form concatenation* — duplication and
conflicts, which is what this replaced. *One mega-prompt* — nothing can be
shared, overridden, or dropped. *A nested section hierarchy* — overkill for a
list this short. *Execute a `.py` file named by the section* — turns a
declarative, widely-copied config string into a code-execution trigger, with
the file sourced through a parent-directory walk; the skill format
(ADR-0051) gets away with a `.py` entrypoint only because skills resolve from a
project-controlled directory with a fixed entrypoint. *Markdown-only custom
sections* — cannot express runtime state, the motivating case. *Keep
`append_prompt` and its always-last position* — position is the entire point.

**Where it lives.** `src/zrb/llm/prompt/manager.py`,
`src/zrb/config/mixins/llm_prompt.py` (`DEFAULT_LLM_INCLUDE_SECTIONS`),
`src/zrb/llm/prompt/markdown/`, `AGENTS.md` (LLM Prompt System).
