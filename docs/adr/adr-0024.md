# ADR-0024 — Config reads `os.environ` only; `.env` files are the task layer's job

**Status:** Accepted

**Context.** Should the global config auto-load `.env` files the way many
frameworks do?

**Decision.** No. `CFG` reads `os.environ` and `DEFAULT_*` and nothing else.
`.env` loading is an application concern handled by the task-level `EnvFile`,
which loads into a task's context rather than into global config.

**Consequences.** Config has no filesystem dependency, so it works unchanged in
serverless and container environments; env-var precedence stays unambiguous;
and framework config (ports, model) is cleanly separated from application
secrets (database passwords). The cost is that a user who wants `.env` for
framework config must wire it themselves.

**Alternatives rejected.** *Load `.env` in `CFG.__init__`* — couples config to
the filesystem and to cwd. *A `CFG.load_env_file()` method* — easy to call
after something already read the value. *Lazy auto-load on first read* —
magical, and shadowing becomes very hard to debug.

**Where it lives.** No dotenv import exists anywhere under `src/zrb/config/`;
`docs/core-concepts/environments.md` documents the task-level alternative.
