# ADR-0011 — Retry, fallback and successor are tasks, not exception handlers

**Status:** Accepted

**Context.** Recovery logic — alert, roll back, clean up — is itself automation, so it should compose with the rest of the graph rather than hide inside a `try` block.

**Decision.** A task declares `retries` and `retry_period`; on permanent failure its `fallback` tasks run, and on success its `successor` tasks run. Fallbacks and successors are ordinary tasks in the DAG.

**Consequences.** Recovery is declarative, reusable and visible in the graph. The cost is that recovery flows are modelled as tasks even where a two-line inline handler would do.

**Alternatives rejected.** *Inline try/except* — couples recovery to the action and hides it from the graph. *Auto-fallback on the first failure* — too aggressive; transient failures should retry first. *No fallback concept* — users then build error pipelines out of `execute_condition`, which reads worse.

**Where it lives.** `src/zrb/task/base_task.py`, `src/zrb/task/base/execution.py` (retry loop), `docs/core-concepts/tasks-and-lifecycle.md`.
