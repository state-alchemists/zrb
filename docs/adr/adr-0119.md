# ADR-0119 — Compaction re-attaches the newest skill bodies, bounded per skill and in total

**Status:** Accepted

**Context.** An activated skill lives in the conversation as a `<ACTIVATED_SKILL>` block. Compaction replaces the messages that carry those blocks with a summary, so the body is gone from the history while the work it governs continues. The state snapshot does have an `active_skills` field, but it holds *names* — and it is the third entry in `_SUMMARY_DROP_ORDER`, so on a tight cap it is dropped first. A name is not the instructions: the next turn keeps the role it was given and loses the procedure that role came with.

The reference harness solves this after compaction rather than at activation: Claude Code re-attaches the most recent invocation of each skill, 5,000 tokens each and 25,000 tokens combined, and has no way to unload a skill.

**Decision.**

1. **Re-attach at compaction, from the messages being dropped.** `_assemble_summarized_history` hands `build_reattach_message` the messages whose content is about to be replaced, so the blocks are still available at the moment they would be lost.

2. **The newest block per skill wins.** Scanning newest-first means an older activation of the same skill cannot resurrect a superseded body, and the result is one block per skill.

3. **A skill that survives in the kept tail is skipped.** Its block is still in the history verbatim; re-attaching it would send the same instructions twice. Only names absent from the kept tail are re-attached.

4. **Two caps, mirroring the harness this follows.** `SKILL_TOKEN_CAP` (5,000) bounds one skill; `TOTAL_TOKEN_CAP` (25,000) bounds all of them. A skill over its own cap is truncated to it; the walk stops at the total cap, keeping the newest skills.

5. **It arrives as its own turn after the summary.** A `ModelRequest` carrying a `## Skills re-attached after compaction` section, which `ensure_alternating_roles` merges into the same user turn the summary occupies.

6. **No skills to re-attach means no change.** A history without activation blocks compacts exactly as before, which keeps the change invisible to every run that never used a skill.

7. **A body cannot fake the tag that wraps it, and the reader pairs by position.** `build_activation_block` neutralises `<ACTIVATED_SKILL` and `</ACTIVATED_SKILL>` inside a body and leaves markdown and code fences alone, so new history is unambiguous. History written before that is genuinely ambiguous — a body quoting a *closing* tag and a body quoting an *opening* tag demand opposite pairings — so the reader bounds a block only by a tag that opens a line, which is where a rendered block always starts. The one shape it cannot resolve is a quoted tag that itself opens a line inside a body: that merges the block with the next one rather than dropping either.

**Consequences.** A compacted session keeps the methodology it was working under, at a bounded cost of at most 25,000 tokens. The summary's `active_skills` line remains the index of what is active; the re-attached blocks are the content, and they are re-derived at each compaction rather than stored, so a session that activates a skill afterwards is unaffected. The cost is real on a small window: 25,000 tokens is a large share of it, which is why the caps are constants and not a ratio — compaction frees far more than that on any window where it triggers, but a future model with a tiny window would want them sized like `LLM_SUMMARY_MAX_TOKEN_RATIO` instead.

**Alternatives rejected.**

- *Render the bodies into the system prompt via `active_skills`* — re-sends them on every request, including the ones where the block is still in the history, paying repeatedly for content already paid for.
- *Append the blocks to the summary text* — the summary's size is already measured against its cap (`_fit_summary_block`), so text added afterwards would exceed the bound the cap approved and change what the schema-aware truncation removes.
- *Re-attach every activation found in the history* — unbounded, and it would resurrect superseded bodies from earlier in the session.
- *Trust the snapshot's `active_skills` names* — survives as a list, not as instructions, and is the first section dropped under pressure.

**Where it lives.** `src/zrb/llm/skill/reattach.py` (extraction, deduplication, caps), `src/zrb/llm/summarizer/history_summarizer.py` (`_assemble_summarized_history`), `test/llm/skill/test_reattach.py`. See ADR-0118 for how a skill's body is rendered in the first place, and ADR-0041 for the compaction this repairs.
