# ADR-0060 — One approval chain: permission policy, then tool policy, then yolo

**Status:** Accepted

**Context.** Three authorization mechanisms had accumulated with overlapping
and sometimes contradictory logic — a system-configured **permission policy**
returning allow/ask/deny per tool, capability or argument; **tool policies**
registered programmatically (`auto_approve("Tool")`, command validation); and
**yolo**, a session toggle that is `True`, `False`, or a set of exempt tool
names. They were evaluated in an ad-hoc order, the execution gate caught denials
*after* the user had already been prompted, and the wiring existed only on one
of the two task classes, so a bare `LLMTask` with `yolo=True` bypassed the
permission policy entirely.

**Decision.** One flat delegation chain, evaluated top to bottom. Each level
answers: do I have a rule for this tool? `allow` → approved, `deny` → blocked,
`ask` or no rule → delegate to the next level.

```
always-auto-approve ──yes──→ ✅ approved
perm_policy ──allow──→ ✅ approved
            ├─deny───→ 🚫 blocked (execution gate, always)
            └─ask────→ tool_policy
                         ├─allow──→ ✅ approved
                         ├─deny───→ 🚫 blocked
                         └─ask────→ yolo
                                      ├─True───→ ✅ approved
                                      └─False──→ ❓ prompt the user
```

Semantics per level: permission-policy `deny` is a hard block enforced at
execution time and overridable by nothing — it is the admin's safety boundary.
Permission-policy `allow` is an unconditional bypass of every lower check.
Permission-policy `ask` means "I have no opinion; check the tool-level rules",
identical to having no rule. Yolo only controls the last-resort default.

`_resolve_approval` is the single choke point for **every** path — main agent,
sub-agents, web — which is what makes the following two branches reliable
rather than per-runner.

**Priority 0: intrinsic always-auto-approve.** `AskUserQuestion` *is* the user
interaction: the model proposes a question and the tool renders it, blocking
until answered. Approving it is meaningless — the user is asked "allow tool
execution?" *before* the question they would be approving has rendered, and the
banner shows only raw YAML. A per-runner `auto_approve("AskUserQuestion")` entry
kept this tolerable in the builtin CLI but did not travel: delegated
sub-agents, the web runner and any bare `LLMTask` still gated the question
behind a redundant prompt, or worse left it un-surfaced after the deferred
round-trip. So auto-approval became intrinsic to the tool: a dependency-free
leaf registry (`tool_call/always_approve.py`) that the tool registers its own
model-visible name into at definition time, consulted as Priority 0.

**Non-interactive runs resolve hard-ASK deterministically.** A permission policy
can return an ASK that yolo cannot override; plan mode uses exactly one such
rule so that leaving plan mode always shows the plan to a human. Under
`--interactive false` the chat task still wires a confirmation UI, so that ASK
fell through to a CLI prompt and blocked on stdin for a "Y" that never arrives —
a 600-second hang. In an 8-model benchmark this single interaction caused **16
of 21 timeouts**. So when the policy returns ASK and interactive mode is false:
`ExitPlanMode` is **approved** (the gate's only purpose is to show a plan to a
human; with no human it is a no-op), and any other hard-ASK tool is **denied**
with an explanatory message. That preserves the hard-ASK safety intent — a
genuinely sensitive tool is never silently auto-run unattended — while
guaranteeing the cascade cannot block on stdin.

**Validation tool policies run at execution time**, orthogonal to approval.
`bash_safe_command_policy` and the file-edit validators are argument-level
technical checks, not policy decisions: a failure returns a
`[SYSTEM SUGGESTION]` hint, and they block even when the permission policy says
`allow`.

**Background sub-agents short-circuit at the yolo level** — anything not denied
by the permission policy is auto-approved, so they never block the main agent
(ADR-0067).

**Consequences.** One predictable decision path; no wasted prompts, since a
denial stops at the gate before the cascade; and both task classes converge on
identical behaviour. `AskUserQuestion` never renders an approval prompt in any
runner, and its auto-approval is discoverable next to the tool rather than
buried in a per-runner list. Costs: a tool that self-registers for Priority 0
bypasses *all* approval layers including an explicit `deny` — acceptable only
because an interaction tool has no external side effect and self-disables when
non-interactive; the always-approve registry is process-global module state, so
registration must be idempotent and order-independent; a non-`ExitPlanMode`
hard-ASK in an unattended run is denied rather than prompted, so callers needing
it must ALLOW it explicitly; and tool policies that assumed they ran *before*
the permission layer now come second.

**Alternatives rejected.** *Flat last-match-wins across one merged ruleset*
(opencode's model) — conflates rules of different authority (admin, code,
session) into one namespace, so "who set this rule?" becomes unanswerable.
*Let `yolo=True` override permission `deny`* — `deny` is the admin's boundary
and must be absolute. *Treat permission-policy `ask` as "prompt immediately"* —
too rigid; `auto_approve("Read")` would be skipped whenever the policy has no
opinion. *Keep relying on the per-runner `auto_approve` entry* — silently absent
for sub-agents, web and bare tasks, which was the reported bug. *Auto-approve
the whole `META` capability* — too broad; `ExitPlanMode` is also
harness-control but must keep asking. *Render the formatted question inside the
approval banner* — still two interactions for one, and it does not fix the
missing question in non-CLI runners. *Auto-approve every ASK when
non-interactive* — `--interactive false` is not an authorization to run
anything. *Install a null approval channel in the non-interactive branch* —
localized, but the same blanket auto-approve semantics. *Guard inside
`exit_plan_mode` itself* — too late; the prompt fires in the cascade before the
tool body runs. *Fix only the prompt text so models avoid the gate* — necessary
but insufficient; any other prompt that nudges toward the gate would still hang.

**Where it lives.** `src/zrb/llm/agent/run/deferred_calls.py`
(`_resolve_approval` — the whole chain),
`src/zrb/llm/tool_call/always_approve.py`, `src/zrb/llm/tool/ask.py`
(self-registration), `src/zrb/llm/agent/subagent/yolo.py`,
`src/zrb/llm/agent/common.py` (`_permission_gate`),
`src/zrb/llm/tool_call/tool_policy/`.
