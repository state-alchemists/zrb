# ADR-0085 — An edited tool call tells the model what actually ran

**Status:** Accepted

**Context.** Approval lets a human edit a tool call's arguments before it runs (`e`/`edit` in `response_handler/default.py`, `replace_in_file_response_handler.py`, and `TerminalApprovalChannel._handle_edit`), returning `ToolApproved(override_args=...)`. pydantic-ai's `_tool_execution.py::_validate_approved_call` swaps in `override_args` for validation and execution — but only there. The `ToolCallPart` the model itself wrote is already fixed in `message_history` by the time approval runs (the graph needs the complete `ModelResponse` before it can process tool calls from it), and nothing rewrites it. So on its next turn the model reads its own original request next to a `ToolReturnPart` produced from different arguments, with no signal a human intervened — the exact "this is what I wrote, but the reading is different now" confusion. This is a pydantic-ai contract gap (matches its documented behavior — `override_args` is scoped to execution, not history), not a zrb bug, but zrb has to close it since the model has no other way to find out.

**Decision.** A tiny process-global correlation table, `tool_call/override_registry.py`, bridges the two points in the call's lifecycle that know about the edit but don't otherwise talk to each other:

- **`record_override(tool_call_id, original_args, override_args)`** — called from `agent/run/deferred_calls.py::process_deferred_requests`, right after `_resolve_approval` (ADR-0062's single choke point for every approval path) returns a `ToolApproved` whose `override_args` is set. `original_args` comes from the call the model wrote (`tool_call/args.py::parse_tool_args`), so this is the one place both values are in scope together.
- **`pop_override_note(tool_call_id)`** — called from `agent/common.py::SafeToolsetWrapper.call_tool`, the actual execution boundary, once per call regardless of outcome (success, hook-modified, or exception). Consumes the entry and returns a `[SYSTEM SUGGESTION]`-adjacent but distinct `[SYSTEM NOTE]`-prefixed string naming only the *changed* keys (a diff against `original_args`, truncated the same way `truncate_tool_args_values` truncates for display) — not a full dump of both arg sets, so an edit to one field of a large payload (e.g. `Write`'s `content`) doesn't double the token cost of the very payload the note is about. `None` when nothing was edited (the overwhelming common case) or the edit was a no-op.

The note reaches the model through the existing `_append_tool_context` (ADR-0043's `_merge_content`, already used for a `PostToolUse` hook's `additionalContext`) — appended to `return_value`, never a second message. Keyed by `tool_call_id`, which is unique per call, so no per-run scoping is needed; an entry nothing ever consumes (an edited call that never reaches execution) is a couple of small dicts, not a real leak.

`[SYSTEM NOTE]` rather than reusing `[SYSTEM SUGGESTION]` (ADR-0057): that prefix is reserved for a tool *failure* the model must recover from. An override note rides on an otherwise-successful (or independently-failed) result and states a fact, not a recovery hint — conflating the two would make `[SYSTEM SUGGESTION]` mean two different things.

**Consequences.** The model's next turn sees, in the same tool-result message, both what actually executed and (via the diff) how that differs from what it wrote — closing the loop without duplicating unedited, potentially large argument values. Cost: one more tiny piece of ambient-adjacent state (a plain dict, not a `ContextVar` — `tool_call_id` uniqueness already gives it the isolation a `ContextVar` would otherwise buy) to keep in sync with the approval cascade if a new approval path is added; `_record_override_if_edited` reads `result.override_args` via `getattr(..., None)` rather than a direct attribute access specifically so a future duck-typed approval result that doesn't define `override_args` degrades to "no note" instead of an `AttributeError`.

**Alternatives rejected.** *Patch pydantic-ai to rewrite the historical `ToolCallPart`* — out of zrb's control, and mutating a message already handed to (and possibly cached by) the model's own turn is a correctness hazard of its own. *Show the note to the human only (already done — "✅ Execution approved (with modification).")* — doesn't solve the model's confusion, only the human's visibility into it. *Dump both full arg dicts into the note* — restates unedited, potentially large values (e.g. `Write`'s `content`) twice in the same tool result, the exact duplication ADR-0043 measured as a real token cost. *A `ContextVar` instead of a plain module dict* — `tool_call_id` is already globally unique per call; a `ContextVar` would add scoping machinery with no isolation benefit, since the registry never needs to distinguish which run an id belongs to.

**Where it lives.** `src/zrb/llm/tool_call/override_registry.py`, `src/zrb/llm/agent/run/deferred_calls.py` (`_record_override_if_edited`), `src/zrb/llm/agent/common.py` (`SafeToolsetWrapper.call_tool`), `test/llm/tool_call/test_override_registry.py`, `test/llm/agent/run/test_deferred_calls.py`, `test/llm/agent/test_common.py`.
