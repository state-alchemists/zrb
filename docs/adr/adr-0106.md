# ADR-0106 — Voice is built on Pipecat's pipeline

**Status:** Accepted

**Context.** zrb hand-rolls its voice. `src/zrb/llm/dictation/` (about 2,520 lines) holds a microphone cutter, a barge-in state machine and the transcript guards, and `src/zrb/llm/speech/` (about 2,840 lines) holds a speaker that plays in process so speech can be paused (ADR-0103, ADR-0105); a wake-word gate sits in front of both. The maintainer asked whether that should be handed to a framework instead of carried by zrb.

The question was settled by measurement, not by reading. Everything below was reproduced in an isolated throwaway venv — pipecat-ai 1.12.0, Python 3.13, macOS arm64 — and nothing was merged into the repo:

- `import pipecat` takes 0.068 s; the pipeline, task and frames imports take 0.396 s; RSS after imports is 58.4 MB.
- Silero VAD loads in 0.142 s; RSS after load is 95.2 MB; a 32 ms frame costs about 0.33 ms, roughly 1 % of one core.
- A `PipelineTask` ran to completion inside an asyncio loop that was already running, while another coroutine kept ticking (37 iterations during the run). Pipecat's `TaskManager` binds to the running loop, so no second event loop is needed.
- zrb does not have to give up the microphone. `BaseInputTransport.process_frame` feeds an upstream-pushed `InputAudioRawFrame` through the same path as device audio; the only gap is that the base `start()` never calls `set_transport_ready()`. A four-line subclass fixes it — pushing 50 chunks (51,200 bytes) from outside put all 50 downstream — so PortAudio and `LocalAudioTransport` are not required.

**Decision.** zrb adopts Pipecat's Pipeline/Frame/transport model for its voice. vosk stays, but only for its wake-word and per-word-confidence behaviour, behind a custom `STTService`; the hand-rolled dictation and speech path yields stage by stage under `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`.

**Consequences.** This supersedes the clauses of ADR-0102 and ADR-0103 that make zrb own the audio path outright. ADR-0102's backend seam dies as written: "A backend is a name or an object. Each feature defines `Any<Feature>Backend` … one implementation per module. `config.backend` is either a built-in name … or an instance of the interface, used as given. A new service needs no change to zrb." With Pipecat the dictation backend is a pipeline whose speech-to-text is a `STTService`, and Pipecat ships no vosk service at all, so zrb writes vosk as a custom service and "a new service needs no change to zrb" no longer holds. The rest of ADR-0102 survives: the `enable_*` extension points, config read at session start, state keyed by chat session, and one feature reaching another by session key. ADR-0103's ownership clause dies: "a backend that can render audio … is played by zrb itself through sounddevice (`PcmUtterance`), which can pause while the user talks over it." Playback becomes a `BaseOutputTransport` subclass and the pipeline owns its lifecycle; ADR-0103's actual requirement — that speech pause and stop when talked over, and that `spoken_log` still tell zrb's voice from the user's (ADR-0105) — survives, carried by that subclass into `PcmUtterance`.

Third-party churn moves into the critical path, and it is not quiet. `WakeCheckFilter` is deprecated since 0.0.106 and removed in 2.0.0; `PipelineTask` is deprecated since 1.3.0 in favour of `PipelineWorker`; and `VADAnalyzer.analyze_audio` returns a `VADState` (`QUIET`/`STARTING`/`SPEAKING`/`STOPPING`), not a confidence, which is what most documentation still says. All three are already carried in the 1.12.0 source, so the version being pinned has known churn in it.

Adoption adds hard dependencies to zrb: the core install pulls `openai`, `onnxruntime`, `numba`, `soundfile`, `soxr` and `resampy`, whether zrb uses them or not.

`TranscriptionFrame` and `InterimTranscriptionFrame` carry text only — no confidence, no word list — so any guard that depends on vosk's per-word confidence (ADR-0105's guard 2) has to be rebuilt at the STT service, not read off the frame.

Honesty clause. The recommendation was to keep zrb's stack and borrow only the models — Silero VAD and a smart-turn ONNX model — which is the cheaper option and meets the same goal. The maintainer weighed it and overrode it: borrowing the models still leaves zrb owning about 5,400 lines of cutter, state machine, guards and playback, and every edge case those encode then has to be re-derived by zrb and kept in step with models that change under it. Adopting the pipeline moves that turn-management layer into a maintained library and accepts the churn and dependency weight above as the price. The two options were not equal in cost, and this record does not pretend they were.

**Alternatives rejected.**

| Alternative | Why rejected |
| --- | --- |
| Keep zrb's stack and borrow only the models (Silero VAD, a smart-turn ONNX model) | The cheaper option and the one recommended: dependencies stay out, and the microphone, cutter, guards and playback stay zrb's. Rejected by the maintainer for the reason above — owning about 5,500 lines of turn management against models that change under it was judged the larger cost. |
| LiveKit | Needs a room and a server — a bigger cut than zrb's in-process, single-user voice. |
| pydantic-ai's `[livekit]` / `[pipecat]` extras | They invert the architecture: zrb's voice is a peripheral that plugs into the chat task (ADR-0102), while pydantic-ai's voice extras make the voice pipeline the centre and embed the agent inside it. |
| WebRTC echo cancellation | No wheel for Termux, musl Linux or Windows on ARM, so it could not ship; ADR-0105 already rejected it for the same reason. |

**Where it lives.** The migration plan is `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`. As each stage lands, it replaces the hand-rolled pieces ADR-0105 names — `src/zrb/llm/dictation/listen.py` (`UtteranceCutter`), `src/zrb/llm/dictation/feature.py` (the hold and the guards), `src/zrb/llm/speech/player.py` (`Speaker`, `PcmUtterance`) — behind a Pipecat pipeline installed through `enable_dictation` and `enable_speech` (ADR-0102). Stage 1's input transport has landed in `src/zrb/llm/dictation/pipecat_input.py`, held up by its own tests; nothing calls it, and no hand-rolled piece has come out yet. Pipecat is the `voice` extra rather than a core dependency for now, so an install that never turns voice on does not pay for the stack.
