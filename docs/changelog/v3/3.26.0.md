## 3.26.0 (October 23, 2026)

- **Feature: a skill preloads the skills it depends on** (`src/zrb/llm/skill/preload.py`, `src/zrb/llm/skill/activation.py`, `src/zrb/llm/skill/manager.py`, `src/zrb/llm/tool/skill.py`, `src/zrb/llm/custom_command/skill_command_factory.py`, `src/zrb/llm_plugin/skills/*/SKILL.md`): a `preload: [core-coding]` frontmatter list renders the dependency's body in the same `<ACTIVATED_SKILL>` response, deepest first, cycle-safe, with an unknown or user-only name reported as a `[SYSTEM SUGGESTION]` instead of failing the activation. Both the slash-command path and `ActivateSkill` resolve it, so `/refactor`, `/debug`, `/review`, `/testing` and `/research` no longer spend a round trip re-activating `core-coding`/`core-research`. Activation also stops re-sending the YAML frontmatter to the model.

- **Feature: LS honors `.gitignore` and takes `depth` and `summary` knobs** (`src/zrb/llm/tool/file_list.py`): `gitignore=True` (the default) filters the walk through `git ls-files --cached --others --exclude-standard`, falling back to the unfiltered walk outside a checkout; `depth` bounds the descent; `summary=True` returns per-directory file counts instead of every path. On this repository an orientation listing drops from ~1,400 generated coverage files to the repository's real shape.

- **Fix: core-coding's trigger covers read-only coding work, and its LS advice names a real parameter** (`src/zrb/llm_plugin/core_skills/core-coding/SKILL.md`): the description said "changes source, test, or config files", so a deep read-only code evaluation skipped it; it now reads "any coding work — reading, writing, editing, debugging, reviewing, testing, or refactoring". `Use LS with limited depth` pointed at a parameter LS did not have; it now says `summary=True` (or a small `depth`).

- **Feature: live context sends git as a delta and always sends the time** (`src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/prompt/manager.py`, `src/zrb/llm/task/building.py`, `src/zrb/llm/task/llm_task.py`): the previous block is read from the run's current message history, so `/rewind` and `/load` diff against the state at the rewound point; unchanged git renders one line, a new commit shows only the new commit, and a status/branch/worktree change shows that section. The time stays in full every turn.

- **Fix: `/btw` states that its answer carries no emoji and no spoken preamble** (`src/zrb/llm/prompt/markdown/side_question.md`): a side answer is shown in its panel, never voiced and drives no avatar state, but the prompt never said so; the absence is now explicit rather than an inconsistency with the main reply contract.

- **Fix: the journal index names the categories its character cap hid** (`src/zrb/llm/prompt/live_context.py`): the truncation used to end at `(...more)`, which reads as "nothing important"; it now emits one line per hidden category with a count and the newest title, and points at `SearchJournal`.

- **Feature: compaction renders the kept tail to text instead of resending it as structured messages, so the split no longer has to dodge a tool call/return pair** (`src/zrb/llm/summarizer/history_splitter.py`, `src/zrb/llm/summarizer/history_summarizer.py`, `src/zrb/llm/message.py`): a pair spanning nearly the whole history (a call near the start, its return near the end) could leave no split point both within the tail budget and safe for the pair, so the fallback search degenerated into summarizing the entire history as one chunk. The kept tail is now rendered with the same lossless `message_to_text` conversion used to prepare a summarized chunk, folded into the compaction turn as its own section after the `<state_snapshot>` and uncapped by `LLM_SUMMARY_MAX_TOKEN_RATIO`, so the split is a plain token-budget cut — `find_safe_split_index`, `find_best_effort_split` and `is_split_safe` are gone. A tool call still awaiting its result (a pending deferred call) is the one exception: `pending_tail_start` finds it and the kept tail is widened to cover it, so it still reaches the model as a real `ToolCallPart`, resumable as before. A tail that fails even the tight 40% budget now gets a second attempt at a looser 80% (`FALLBACK_BUDGET_RATIO`) before falling back to keeping nothing ([ADR-0041](../../adr/adr-0041.md), revised).

- **Fix: a summary's size bound is a share of the threshold, not 2000 tokens** (`src/zrb/llm/summarizer/history_summarizer.py`, `src/zrb/config/mixins/llm_content.py`, `src/zrb/llm/prompt/markdown/conversational_summarizer.md`): `LLM_SUMMARY_MAX_TOKENS` (2000) was measured on the whole inserted block — zrb's framing, the journal index and the archive pointer — while the summarizer prompt asked the model to keep the `<state_snapshot>` under 2000 on its own, so a compliant summary was over the cap by construction: shortened twice, then truncated mid-word, with `<task_state>` — last in the schema — the first thing lost. The same 2000 was under 1% of what a compaction frees on a 500,000-token window, and about a quarter of a small model's. It is now `LLM_SUMMARY_MAX_TOKEN_RATIO` (0.05 of the trigger threshold — 18,750 tokens on that window — with a 1,000-token floor), so the bound follows the model instead of meaning something different on every one. The cut is schema-aware as well: whole sections go from the least durable end first and the closing tag survives, instead of a mid-word truncation that took `<task_state>` first. `LLM_SUMMARY_MAX_TOKENS` is retired and reported at startup, and the summarizer prompt asks for density rather than a token count ([ADR-0041](../../adr/adr-0041.md), revised).

- **Feature: compaction re-attaches the skill bodies it replaces** (`src/zrb/llm/skill/reattach.py`, `src/zrb/llm/summarizer/history_summarizer.py`): an activated skill lives in the messages as an `<ACTIVATED_SKILL>` block, and compaction replaced those messages with a summary that only *names* the skills — so a long session kept the role it had been given and lost the procedure that came with it. The newest block per skill is now re-attached in its own turn after the summary, skipping any skill whose block survives in the kept tail, bounded at 5,000 tokens per skill and 25,000 in total, and an oversized skill is truncated to its own cap. A history with no activation blocks compacts exactly as before ([ADR-0119](../../adr/adr-0119.md)).

- **Fix: Glob and AnalyzeCode honor `.gitignore`, the way LS already did** (`src/zrb/llm/tool/git_visible.py`, `src/zrb/llm/tool/file_list.py`, `src/zrb/llm/tool/code.py`): LS hid what the repository ignores while Glob returned it and `AnalyzeCode` walked, read and billed for it, so one directory had two shapes depending on which tool asked — visible only for repository-specific ignores, since `DEFAULT_EXCLUDED_PATTERNS` already covered `htmlcov` and friends. All three now share one `git_visible.py` filter and a `gitignore=True` default, computing the visible set once per analysis run, and falling back to the unfiltered walk outside a checkout ([ADR-0120](../../adr/adr-0120.md)).

- **Security: 11 of the 54 open Dependabot advisories are closed by a lock bump, and the other 43 cannot be** (`pyproject.toml`, `poetry.lock`): the floors now demand `certifi>=2026.10.19` (7.22.0 bundled emSign roots whose intermediate keys are compromised — critical), `aiohttp>=3.14.4` (pure-Python parser request smuggling, file-descriptor exhaustion in multipart, no initial request/header timeout, connector-pool exhaustion, cookie-scope and Host-Only bypass, `Request.scheme` spoofing), `black>=26.10.1` (the GitHub Action installed an unvalidated `required-version`) and `opentelemetry-api>=1.45.1` (unbounded `tracestate` parsing). The lock moves those four families and nothing else: `aiohttp`, `black`, `certifi`, the five `opentelemetry-*` packages, `yarl` and one new `opentelemetry-exporter-otlp-common`. **The remaining 43 are recorded, not fixed.** 39 are against Pillow, and every one of them is closed only by 13.0.0, which `pipecat-ai` 1.12.0 forbids (`Pillow>=11.1.0,<13`) — the resolver rejects the fix outright, so the floor stays at 12.3.0 until pipecat allows 13; 4 are against `chromadb`, whose critical advisories have no patched release. Both are annotated at the pins in `pyproject.toml`.

- **Feature: a failed `Shell` command keeps the beginning of its output too** (`src/zrb/llm/tool/shell.py`, `src/zrb/llm/tool/stream_capture.py`): the cap kept the tail, which is right for a command that succeeds — its result is at the end — and wrong for one that fails, where the cause is announced first (the first traceback line, the first compiler error) and only summarized last. A failed command now shows 40% of its retention budget from the head and the rest from the tail, joined by one `… [N characters elided] …` marker, and the note names what was kept. The head is read back from the spill file `StreamCapture` already writes, so the excerpt costs no second copy, and a spill that could not be opened degrades to the tail rather than to no output. `Shell(background=True)` and `MonitorProcess` stay tail-only: they report a running process, not a finished result ([ADR-0059](../../adr/adr-0059.md), revised).

- **Fix: runtime notices name the CLI the user actually runs, not `zrb`** (`src/zrb/cmd/command.py`, `src/zrb/group/task_diagnostics.py`, `src/zrb/llm/tool/shell_background.py`): three notices printed into a command's own output were prefixed `[zrb]` — the one reporting output the drain grace could not capture, the one reporting dropped output lines, and the one reporting a backgrounded process stopped at its deadline — and the unregistered-task diagnostic told the user to run ``zrb <task>``. Those are the strings a white-labeled distribution cannot change: a user of `acme` saw `[zrb] dropped 3 stdout line(s)`, a prefix naming a program they do not have, and was handed a command they cannot type. All three now read `CFG.ROOT_GROUP_NAME`, the setting the rest of the CLI-facing text already uses, so the `ENV_PREFIX`/`ROOT_GROUP_NAME` rebrand in [White-labeling](../../advanced-topics/white-labeling.md) reaches them too. Nothing changes for a stock install, where the name is still `zrb`.

- **Feature: a command that outruns its `Shell` timeout keeps running in the background** (`src/zrb/llm/tool/shell.py`, `src/zrb/llm/tool/shell_background.py`, `src/zrb/config/mixins/llm_limits.py`): the timeout used to kill the process, discarding everything it had already done, and told the model to run it again with `background=True` — a second copy of the same work, and a queued user message that then waited through both. The process is now adopted into the background registry under a handle: same process, same pipes, same output captures, so the report carries a `Handle:` line, `Exit Code: (moved to background after 120s)`, and a `[SYSTEM SUGGESTION]` naming `MonitorProcess` (read it, `wait=N`, or `kill=True`) and saying not to re-run. A command whose first word is `sleep` is still killed — a delay is the work — and `LLM_SHELL_TIMEOUT_BACKGROUND_SECONDS` (1800s by default) bounds how long an adopted process may run, with `0` restoring the old behaviour ([ADR-0121](../../adr/adr-0121.md)). A command that is flooding keeps one spill file for its whole life — the report names it and it keeps growing — instead of a dump that stops at the timeout plus a second file that starts there.

- **Fix: the CLI's own help text stops calling itself `zrb`** (`src/zrb/config/mixins/*.py`, `src/zrb/config/retired.py`): every `doc=` string shown by `<cli> config explain` that named the program as the actor — "whether zrb runs under Termux", "every zrb command is its own process", "while zrb speaks", "speech over zrb" — now says "the CLI" or "the assistant", whichever the sentence is about. 64 mentions across nine files; identifiers are untouched on purpose (`zrb_init.py`, `zrb.llm.voice`, the `zrb[voice]` extra, `src/zrb/...`), because those are paths a white label keeps rather than strings it rebrands. This completes the white-label pass begun in the two runtime-notice fixes above: what a user reads is now the configured name, and what a user *types* is the package's real path.

- **Feature: live context names the background processes the session still owns** (`src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/tool/shell_background.py`): a handle was named exactly once — in the tool result that created it, or the timeout report that adopted it — so a later turn had only that message to go on, and compaction can replace it while the process keeps running and holding its port. The live-context block now carries `- Background processes (Shell handles this session still owns):` with one line per handle (name, `running` or `exited, code N`, elapsed, description clipped to 80 characters) plus the two calls that act on one, filtered to the chat session that started it. It reads a new read-only `summary()` rather than `poll()`, because `poll` retires a drained handle and a prompt render must not consume it; the section renders every turn while it is non-empty (a standing condition, not a git-style delta) and disappears entirely when nothing is running ([ADR-0122](../../adr/adr-0122.md)).

- **Fix: compaction records which skill bodies it re-attached** (`src/zrb/llm/skill/reattach.py`): the decision left no trace, and the transcript cannot supply one — zrb's own tests, ADRs and code samples contain `ACTIVATED_SKILL` tags, so finding one in a saved conversation proves nothing about whether a compaction re-attached anything. `build_reattach_message` now writes one debug line naming what it attached and what it deliberately did not (`skipped_kept` = a newer copy is still in the kept tail, `skipped_cap` = it did not fit the 25,000-token total), with the token cost. A session that never used a skill still logs nothing, so an ordinary compaction stays silent ([ADR-0119](../../adr/adr-0119.md)).

- **Feature: Ctrl+G moves a running `Shell` command to the background, so the message is read in the same turn** (`src/zrb/llm/shell_cut.py`, `src/zrb/llm/tool/shell.py`, `src/zrb/llm/agent/run/runner.py`, `src/zrb/llm/ui/base/queue_delivery.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/multi_ui.py`): a message handed to the live run was read at the next model request, which is only assembled after the running tool call returns — so `Ctrl+G` during a five-minute build still waited out the build. The key now cuts the run's signal as well, and the shell holding the turn adopts its process through the same registry path its own timeout uses, reporting `(moved to background so the turn could continue)` and telling the model to read the message first rather than run the command again. The signal is per run and counts cuts, so a keypress sent during an earlier tool call never moves a command that had not started; only an explicit send-now cuts (speech submits with `may_interrupt=False` and moves nothing), and a `sleep` or a command with adoption turned off keeps waiting — a cut is not a kill ([ADR-0123](../../adr/adr-0123.md)).

- **Feature: a voice-first session can let a spoken message move a running `Shell` command** (`src/zrb/config/mixins/llm_limits.py`, `src/zrb/llm/ui/base/triggers.py`, `src/zrb/llm/ui/base/queue_delivery.py`, `src/zrb/llm/shell_cut.py`): speech never interrupts a turn, so a command that was running still had to finish before the words were read. `LLM_VOICE_MOVES_SHELL` (off) lets a dictated message move that command aside the way `Ctrl+G` does — `/set LLM_VOICE_MOVES_SHELL 1` turns it on. It is a separate permission from `may_interrupt`, because that one also arms the fallback that cancels a turn. A sub-agent, and a helper run behind `AnalyzeCode`/`WebFetch`, now share the turn's signal instead of minting their own, so a `Shell` started inside one is reachable by the same key ([ADR-0123](../../adr/adr-0123.md), revised).

- **Feature: the verbatim tail's share is a setting, and the retry follows it** (`src/zrb/config/mixins/llm_content.py`, `src/zrb/llm/summarizer/history_splitter.py`, `src/zrb/llm/summarizer/history_summarizer.py`, `docs/configuration/llm-context.md`): the tail budget was a constant — 40% of the trigger threshold, invisible in the config — although it is the number that decides how lossy a compaction is. Measured on a real session, it governed a block of 87,508 tokens: 86% of everything the compaction left behind, and 17 times the summary beside it. It is now `LLM_HISTORY_TAIL_BUDGET_RATIO` (`0.4` by default), clamped into `0.05`–`0.8` rather than obeyed, because `0` would summarize the newest message too and a tail filling the threshold would free nothing. The retry that fires when even the newest message overflows its budget used to hold a fixed 80%, which could be four times a deliberately small setting; it is now twice the configured ratio, capped at 0.8, so the default still retries at exactly 0.8 and a smaller budget cannot be undone by it. The page now walks through the mechanics a reader needs before changing the number: the turn-boundary preference that makes 0.3 and 0.4 produce the same tail, the 300-message window, the retry, and the `char/4` estimate running about a tenth low unless `ENABLE_TIKTOKEN` is on ([ADR-0041](../../adr/adr-0041.md), revised).

- **Feature: sending a message hushes a reply that is still being read aloud** (`src/zrb/llm/ui/base/message_queue.py`, `test/llm/ui/base/test_submit_hushes_speech.py`, `docs/configuration/llm-voice-camera.md`): a reply arrives twice, as text and as voice, and the two run at different speeds — a long answer is read in a fraction of the time it takes to speak, so it can be answered while the voice is still on its first paragraph. From that moment the voice is describing a turn the user has moved past, and zrb kept talking: talking over it stopped it (`interrupt_speech`, from barge-in), but typing at it did not, because nothing under `llm/ui` reached the speaker. `submit_user_message_via_queue` — the one place every submission lands, whichever UI and whichever channel — now hushes the session before it queues the message: the sentence in flight is cut and the queue is dropped, while the turn goes on and the words are read as usual. A hush, not a cancel; a child UI leaves it to its `MultiUI` so one message interrupts once ([ADR-0103](../../adr/adr-0103.md), revised). Nothing shortens a reply — a long one is still read in full, unless `LLM_SPEECH_SUMMARIZE_ABOVE_CHARS` asks for a summary.

- **Fix: answering a prompt hushes the question being read aloud** (`src/zrb/llm/speech/feature.py`, `test/llm/speech/test_feature_question.py`, `docs/configuration/llm-voice-camera.md`): the last gap in the same story — a message you send cuts the voice, but answering an `AskUserQuestion` prompt cut nothing. The spoken question is queued before its dialog appears, so by the time you pick an option it may still be playing, and neither way of answering went near `submit_user_message_via_queue`: a highlighted option resolves the prompt through `resolve_current`, and a typed answer through `submit_user_answer`, which resolves the same future. An approval request already told the speaker what made it stale (`is_answered_since`); the question asked for nothing, so the voice read on. It now carries the same predicate, dropped before it starts or cut mid-sentence the moment the answer lands — the player polls it (`_stop_when_stale`). The check watches the prompt's future rather than a keystroke, so one predicate covers both ways of answering, and no `interrupt_speech` is raised: answering a prompt is the turn continuing, not moving past it ([ADR-0103](../../adr/adr-0103.md), revised).

- **Security: the 39 Pillow advisories are closed by moving `pipecat-ai` to 1.14.0** (`pyproject.toml`, `poetry.lock`): the earlier lock bump recorded 43 of the 54 open Dependabot advisories as unfixable, 39 of them against Pillow, because every one is closed only by 13.0.0 and `pipecat-ai` 1.12.0 declared `Pillow>=11.1.0,<13` — the resolver rejected the fix rather than merely deferring it. `pipecat-ai` 1.14.0 raises that ceiling to `<14`, so the floors move: `Pillow>=13.0.0` and `pipecat-ai>=1.14.0,<1.15.0`. The two minora differ in nothing else that costs anything here — the same 24 base dependencies, with `aiohttp`'s floor at 3.14.4 (already locked), `sentencex` at 1.0.32, and `onnxruntime` loosened from `~=1.24.3` to `<2`, so nothing new has to build on any platform, Termux included. Every symbol zrb imports still resolves on 1.14.0: `PipelineWorker`, `PipelineParams`, `WorkerParams`, `FrameProcessor`, `TaskManager`, the `TTS*` and `Frame` types, and the STT/TTS service classes. The 4 advisories left are `chromadb`'s, which have no patched release.

- **Fix: a TTS start that never returns can no longer silence the session, and no longer parks a thread per turn** (`src/zrb/llm/speech/backend/pipecat.py`, `src/zrb/llm/speech/player.py`): a chat came up completely silent — no reply, no approvals, no progress — with speech switched on. Its process held **38 threads parked on one lock**: the warm-up probe, queued behind a model load that never finished, with every sentence waiting behind the same lock. Two defects made that permanent rather than transient. The wait for a pipeline start was unbounded, so a load that never returned held every sentence with no error anywhere; it now gives up after `PIPELINE_START_TIMEOUT_SECONDS` (120 s) and raises, which is the speaker's cue to speak with the local engine — audible, where silence is not. And `restart_backends()` cleared `_is_warming_up`, so after a dead backend every turn armed another warm-up thread behind the same stuck load, defeating the guard written for precisely that pile-up; the flag now stays up until the thread ends and the thread always lowers it, so a stuck load costs one parked thread, not one per turn.

- **Removed: the RAG tool and its `chromadb` extra** (`src/zrb/llm/tool/rag.py`, `src/zrb/config/mixins/rag.py`, `src/zrb/config/retired.py`, `pyproject.toml`, `poetry.lock`): `create_rag_from_directory` was a factory a user had to register by hand, so no session loaded it unless it asked for it — but it carried the `rag` extra, and with it 21 packages and four Dependabot advisories against `chromadb` 1.5.9 that no release patches. The tool, its re-export from `zrb.llm.tool`, and its six `RAG_*` settings are gone; the settings are reported at startup as retired rather than silently ignored. `poetry lock` removes those 21 packages and adds or changes none. The two pins that existed only for that tree leave with it, except `opentelemetry-api>=1.45.1`: `pydantic-ai-slim` and `mistralai` still pull the package, so its floor moves to the base dependencies with the advisory it closes named inline. Breaking for anyone importing `create_rag_from_directory` ([ADR-0124](../../adr/adr-0124.md)).

- **Feature: pydantic-ai 2.61.0, and its typed model errors now answer before zrb's heuristics** (`pyproject.toml`, `poetry.lock`, `src/zrb/llm/agent/run/error_classifier.py`): 2.59 added a typed taxonomy decided where the provider answer is received — and not only for native providers: `_model_errors.openai_compatible_category` reads OpenAI's `context_length_exceeded` and the wording OpenRouter, vLLM and Groq use, with Bedrock and Google mapped by their own codes. `classify_error_type`, `is_retryable_error`, `is_permanent_error` and `is_prompt_too_long_error` now check those types first and keep the status-code and keyword branches for errors that arrive untyped. That fixes a real defect: an exhausted quota or spend limit arrives as a 429, so `is_retryable_error` retried a wall until the budget ran out; `ModelQuotaExceededError` is now permanent. The `StopFailure` token vocabulary is unchanged — a quota still reports as `rate_limit` — because that is the hook's contract. The pins move together: `pydantic-ai-slim>=2.61.0,<2.62.0` and `openai>=3.26.0`, since we take `pydantic-ai-slim[mcp]` and the resolver never enforced the `openai` extra's own floor (it stayed at 3.19.0 across a pydantic-ai minor-and-a-half). `poetry lock` moves four packages and adds or removes none: pydantic-ai-slim and pydantic-graph 2.54.0→2.61.0, genai-prices 0.1.9→0.1.13, openai 3.24.0→3.37.0 ([ADR-0125](../../adr/adr-0125.md)).

- **Fix: a retried tool call is a `ToolReturnPart` with `outcome='retried'`, and history reads it that way** (`src/zrb/llm/agent/run/history_utils.py`, `src/zrb/llm/message.py`, `src/zrb/llm/util/history_formatter.py`, `src/zrb/llm/ui/base/replay.py`, `src/zrb/llm/history_manager/file_history_manager.py`, `src/zrb/llm/agent/types.py`): pydantic-ai 2.60 deprecated `RetryPromptPart` — removed in v3 — in favour of that part and, for a retry that answers no call, `RetryFeedbackPart`. The change was not cosmetic: a history saved by zrb came back from pydantic-ai's validation as the new part, so `isinstance(part, RetryPromptPart)` failed on zrb's own files. Orphan detection, the request normaliser, the formatter, the replay path and the content cleaner now read the new shapes, and the formatter words a retry as feedback rather than as a result and marks it 🔄 instead of ❌. Readers dispatch on `part_kind`, accepting `retry-feedback` alongside `retry-prompt`, so history written before 2.60 still renders without importing the deprecated class. Breaking for anyone importing `RetryPromptPart` from `zrb.llm.agent.types`.

- **Docs: ADR-0126 records why zrb keeps its own model capability table** (`docs/adr/adr-0126.md`): pydantic-ai 2.61 ships `ModelProfile` — 34 fields resolved per provider — which looks like a replacement for `ModelCapabilities` and is not one. Measured across 22 models in 8 provider families, the two agree on image input (16/22), audio (18/22), document (14/22) and context window (12/22), but only **3/22 on video**: `DEFAULT_PROFILE` declares image, document and video support `True`, a provider profile names only the keys it is sure of, and so `gpt-3.5-turbo`, `gpt-4-0613` and `claude-instant-1` all resolve to "reads images, PDFs and video". zrb's conservative default and its `_IMAGE_DENY` list exist for exactly those names, so adopting upstream would send text-only models content the provider rejects. zrb's `supports_thinking_summary` is also a narrower question than upstream's `supports_thinking` — adopting the broader flag switches the `thinking=True` default on for Anthropic, where extended thinking is billed — and `context_window`, which upstream's profiles mostly leave `None`, is documented in zrb's table. Tool deferral needed no change either: zrb already passes `defer_loading=True` to pydantic-ai's `Tool`, and `search_tools` is pydantic-ai's auto-injected capability, not zrb code ([ADR-0126](../../adr/adr-0126.md)).
