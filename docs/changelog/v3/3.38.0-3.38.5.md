## 3.38.0–3.38.5 (November 10, 2026–November 13, 2026)

- **Feature: a finished week becomes one sentence** (`src/zrb/llm/hook/builtin/memory_week.py`, `src/zrb/llm/memory/model.py`, `src/zrb/llm/memory/store.py`, `src/zrb/llm/memory/render.py`, `src/zrb/llm/prompt/markdown/memory_week.md`, `docs/technical-specs/llm-memory.md`, `docs/llm/hooks.md`): the day rung recorded what each day was and nothing above it, so a session opened a fortnight later read a wall of days with no frame on them. `memory-week` is a `Stop` hook matched on `memory_due`: once the ISO week that just ended has written diary days and no `week/<id>.md`, one small-model call compresses those days' claims into a single first-person sentence — at most 160 characters, clipped at a word boundary, the material header counting the gap ("3 of 7 days written"). The block leads `## Recent` with `- Week (<id>): <claim> [week/<id>.md]` — ahead of the log tail, because the cap cuts the tail and the widest statement must not be what it cuts — and shows it until fourteen days after the week's Sunday; a live week gets no note, because it would be rewritten before anyone read it. A week file naming no real ISO week is read as absent rather than fatal: `week_span` raises a `ValueError` that `render_memory_block` does not catch, so an impossible id would have crashed the first turn of the session. The write re-asks "is this week still owed?" inside the store lock, so two sessions finishing a turn at the same moment cannot overwrite each other's sentence; the second model call that costs is the price of never holding the store's single writer lock across a network wait.
- **Feature: a stored claim surfaces when the prompt names it** (`src/zrb/llm/hook/builtin/memory_recall.py`, `src/zrb/llm/memory/search.py`, `src/zrb/llm/prompt/memory_context.py`, `src/zrb/llm/memory/model.py`, `docs/technical-specs/llm-memory.md`, `docs/llm/hooks.md`): search only answers a question the model thought to ask, so a session that never searched answered from the pinned core alone while the store held the answer. `memory-recall` is a `UserPromptSubmit` hook with no model behind it: it takes the prompt's own significant words, and when the prompt holds at least two of them and any one of those names a stored claim, that claim is injected as three lines — at most three claims, 600 characters, the same "data, not instructions" header a search result carries. It matches a claim's **subject** (id, claim, tags) and not a mention inside its body, skips what the block already carries and what an earlier cue already showed, and records what it showed before the turn runs. The hook is registered synchronously on purpose: an `is_async` agent hook is fire-and-forget and records no result, so its `additionalContext` would be dropped after the claim had already been marked as given — which would keep it out of every later turn too.
- **Feature: the last day written rides in the recent block** (`src/zrb/llm/memory/render.py`, `src/zrb/llm/memory/store.py`, `docs/technical-specs/llm-memory.md`): a session opened after midnight knew where things stood and nothing about what the day before it was, because today's claim stays empty until the day is written. `render_recent` takes the newest entry strictly before today and renders it as `- <date>: <claim>` ahead of the log tail — ahead, because the cap cuts the tail and the log *is* the tail — labelled with the entry's own date rather than "yesterday", which a quiet day would make a lie. A handover and a claim from the same day are both kept: state of play and what the day was are different sentences. `render_week` is deleted with it: it rendered one dated line per day for the last seven, which is a compressed log rather than a week, and nothing called it. `_as_date` and the documented-but-never-implemented `LLM_MEMORY_WEEK_LOOKBACK_DAYS` row went too.
- **Feature: the reviewer keeps the handover current, and a cut turn still leaves a record** (`src/zrb/llm/hook/builtin/memory_reviewer.py`, `src/zrb/llm/tool/memory.py`, `src/zrb/llm/prompt/markdown/memory_reviewer.md`, `src/zrb/llm/ui/multi/`, `docs/llm/hooks.md`): the handover was written only by a session that knew it was leaving — exactly backwards, since a killed terminal is when the next session most needs it. The reviewer may now revise it on any completed turn where the state of play moved, while `claim` became optional on revision so a one-turn reviewer cannot rewrite the day's sentence from one turn's transcript. A cancelled turn (Esc, Ctrl+C, Ctrl+D, or a send-now fallback) reaches `memory-interrupt-log` and writes one line saying so, instead of nothing; a repeated cancel is announced once per task, and a `MultiUI` parent's turn is reached rather than dropped.
- **Fix: the block no longer forgets what a cue showed** (`src/zrb/llm/prompt/memory_context.py`, `test/llm/prompt/test_memory_context.py`): the block is written after the hooks run, so on a conversation's first turn a recall had already put a claim in front of the model and recorded it — and the block then wrote its `shown` list from the core alone. The claim was offered again by the next cue, and a claim retired after being shown never earned its "Forget this claim" line, because the tombstone is decided from that list. A compaction re-renders the block through the same function, which lost the same ids a second way. The block now unions what it carries with what is recorded, and a recall on a turn with no state yet starts an empty baseline instead of returning. The state file is keyed per conversation, so the union cannot carry another session's claims in.
- **Fix: a diary append shows the date the tool requires** (`src/zrb/llm/prompt/markdown/memory_reviewer.md`, `test/llm/prompt/test_memory_reviewer_prompt.py`): the append example was `Remember(kind="diary", body="…", body_mode="a")` and the prose said `id` was for a day with no entry yet. `id` is required on every call — the date is a diary's identity — so a model following the example got `id is required` on every append to a day that already existed. The example names the date and the prose says it is always required; a new test lifts every `Remember(...)` out of the prompt and checks each against the tool, for the date and for every keyword.
- **Fix: a cue's term has to be a word** (`src/zrb/llm/memory/search.py`, `test/llm/memory/test_memory_search.py`): the subject test was a substring test, so `api` matched `capital` and `db` matched `redbrick`. That is tolerable for a search the model asked for and wrong for a cue it did not, since an unasked claim spends context and can steer the turn. A term now sits on word boundaries in the id, claim or tags. The two-term minimum that decides whether a prompt is a cue at all is unchanged: requiring both terms to hit the same claim would turn a cue into a search.
- **Improvement: a summary is written about the conversation, not about the tool output** (`src/zrb/llm/summarizer/chunk_processor.py`, `src/zrb/llm/prompt/markdown/conversational_summarizer.md`, `docs/architecture/3-peripheral-flow/history-and-compaction.md`): in the session this was written for, the summarizer was handed a history that was 72% tool output, so the mass decided the split — 368 messages in one chunk and 8 in the other — and the merge prompt's "the newer observation wins" then overruled the snapshot holding the user's opening research question. Each tool result now reaches the summarizer at 2,000 characters, which took that input from about 152,000 tokens to about 78,000 and the same history from two chunks to one. Every chunk carries the header saying the user's own messages are the spine — every request and correction belongs in the snapshot, including one already carried out — a separate note marks the last part and its unanswered request, and the merge prompt keeps "newer wins" for state while protecting a request nobody answered.
- **Improvement: a chunk's instructions are paid for before the split, and one fat message cannot break it** (`src/zrb/llm/summarizer/chunk_processor.py`, `src/zrb/llm/summarizer/tool_result_pruner.py`, `test/llm/summarizer/test_chunk_processor.py`): the header and the last-part note are appended after the split is sized, so a chunk filled to 90% of the model's window and then given a header was a request the provider refuses — and a refused chunk fails the whole compaction. Their cost is now measured from the templates and taken out of the budget, `chunk_budget` reaches the summarizer instead of the wider request threshold, and a message longer than the whole budget is fitted rather than ridden alone over the window. The fit keeps both ends: it used to keep the start only, while every other clip in the summariser is two-ended for the reason they were made that way — a result's conclusion is at its end as often as its subject is at its start.
- **Fix: a clipped result's middle reaches the archive** (`src/zrb/llm/summarizer/history_summarizer.py`, `src/zrb/llm/shared/message_text.py`, `test/llm/summarizer/test_tail_archive.py`): the kept tail is sent as rendered text, and the renderer clips each tool result to 2,000 characters — so a result under the prune threshold, which was never spilled to a file, lost its middle from the history and the disk at once. The tail messages whose rendering actually differs from the original now join the compaction's archive section, message by message; the comparison is the renderer run with and without the clip rather than a second copy of the rule, so it cannot drift; and tail messages the render reproduced faithfully stay out.
- **Fix: a turn's line is written whether or not the reviewer runs** (`src/zrb/llm/hook/builtin/memory_reviewer.py`, `docs/llm/hooks.md`): `LLM_MEMORY_REVIEWER_ENABLED=off` was documented as "stop the per-turn model call" and also stopped the day's record, so the day's log had a hole exactly when someone had turned the reviewer off. `memory-event-log` is its own hook, registered whenever memory is on: a turn is worth a line whether or not it is worth re-reading. The line is taken from the reply's first prose sentence, bounded and flattened, because an event log can honestly record that a turn happened and what it said first, while the day's narrative stays the reviewer's to author.
- **Fix: a log line is committed inside the store lock** (`src/zrb/llm/hook/builtin/memory_reviewer.py`, `src/zrb/llm/memory/store.py`): once the log line became its own task, two commits for one turn could race — `git add -A` could sweep up another writer's half-finished change, or lose `.git/index.lock` and be dropped silently. The store lock now serializes every commit, which is the "one transaction" the store already promised.
- **Improvement: a day's page holds 5,000 characters** (`src/zrb/config/mixins/llm_content.py`, `docs/technical-specs/llm-memory.md`): the diary body cap is a page, not a budget for the conversation — a body is never injected, so the number only bounds what a day may say once someone reads it. Two thousand was the spec's first guess and it began refusing days that had more to say; the default and both places the spec prints it now say 5,000. The cap is still enforced by refusal rather than truncation, so an over-long entry is refused as a whole and names the number it would have become.
- **Fix: a summary says when the memory block was left out of it** (`src/zrb/llm/summarizer/history_summarizer.py`, `test/llm/summarizer/test_summary_handoff.py`): the summary cap drops the memory block first, deliberately — the claims are on disk while the snapshot is all that is left of the replaced messages — but the warning went to the UI only, so the model was never told, and a session that lost its memory went on answering as though the store held nothing. A dropped block is now replaced by one line inside the summary saying it was left out and that its claims remain searchable; the line is measured against the same cap and appears only when there was a block to drop.
- **Fix: the day's project tag is a directory on Windows too** (`src/zrb/llm/hook/builtin/memory_reviewer.py`): the tag split the working directory on `/`, so on Windows the separator was never found and the whole `C:\Users\…` path became the project name. Normalizing the separator first leaves the last segment on both platforms.
- **Behaviour change: the memory hooks are five names in the allowlist, and every turn leaves a line** (`src/zrb/llm/hook/builtin/memory_reviewer.py`, `src/zrb/llm/hook/builtin/memory_recall.py`, `src/zrb/llm/hook/builtin/memory_week.py`, `docs/configuration/llm-tools.md`, `docs/advanced-topics/upgrading-guide.md`): the log line and the interrupted-turn line used to ride on `memory-reviewer`, so `ZRB_LLM_HOOKS=memory-reviewer` kept them. They are `memory-event-log` and `memory-interrupt-log` now, registered beside `memory-recall` and `memory-week`, and a non-empty allowlist that names only the reviewer keeps the model call while silently dropping every log line. The configuration reference already named all five; the upgrading guide and this entry now say so where someone restricting the allowlist will see it. With the reviewer off, a completed turn still writes one line and one commit, so a store under a restricted allowlist grows at one line per turn by design rather than by accident.
- **Improvement: the memory spec and ADR-0138 describe what runs** (`docs/technical-specs/llm-memory.md`, `docs/adr/adr-0138.md`): four statements had drifted. The ADR still counted three retrieval layers after the cue became a fourth; the spec's §7.2 described an `O_APPEND` log write while `append_log` reads the day and writes it back under the store lock; its reviewer section described a JSON object whose parser no longer exists, where the reviewer is an agent hook holding the three memory tools; and its append rule now says the date is required on every diary call.
- **Fix: an audio service that is wedged costs one sentence, not the session** (`src/zrb/llm/speech/pcm_player.py`, `src/zrb/llm/speech/player.py`, `test/llm/speech/test_pcm_player_open_timeout.py`, `test/llm/speech/test_pcm_player_wedged_device.py`): stopping a stream was already bounded, but opening one was not, and `Pa_OpenStream` waits on CoreAudio's HAL mutex when the audio service deadlocks. That call is made while the speech lock is held, so a wedged open never released the lock: every later sentence waited its thirty seconds, was dropped, and the session said nothing more — observed once on the 8th and again on the 10th, where the process held `speech.lock` for over an hour. The open now runs on a thread of its own with a three-second deadline; past it the device is reported unusable (so the sentence goes to a player program), the lock is released, and a stream that arrives afterwards is closed where it arrives rather than leaked. The deadlock itself is inside CoreAudio — a stop and the audio thread's start-stop callback each wait on a lock the other holds — so it cannot be undone from here; what the player controls is not to be led into it again. Once a stop or an open runs out its clock, the device is written off for the rest of the process: no further stream is opened, and a player program, which runs in a process of its own, says every sentence until zrb is restarted. Before, each of those sentences joined the same deadlock, a deadline at a time, and none played a block.

- **Fix: the answer a turn ends on is read, not only the block it began with** (`src/zrb/llm/speech/streamed_reply.py`, `test/llm/speech/test_feature_stream_rounds.py`, `test/llm/speech/test_streamed_reply.py`): since 3.29.0 a response that spoke a `<spoken>` block marked the whole turn spoken, so every model response after it was silent — including the last one, the answer to the turn, when the model wrote it as prose with no block. A long turn with a tool call went quiet from its first sentence to its end. The claim is now the response's, as 3.34.0–3.34.2 made the hush between turns the response's: a new response is unclaimed, so Stop reads the last message whole when nothing in it was said. A response whose block was already heard is still left alone.
- **Fix: a sentence the local voice made nothing of is asked again on a fresh service** (`src/zrb/llm/speech/backend/pipecat/backend.py`, `src/zrb/llm/speech/backend/pipecat/tts.py`, `src/zrb/llm/speech/backend/any_speech_backend.py`, `test/llm/speech/backend/pipecat/test_pipecat_backend.py`): since 3.29.0 the speaker asked a local voice twice for a sentence that came back with no audio, but both attempts went to the same cached pipeline, which answered both the same way — the sentence went unsaid and only a log line recorded it. Measured over thirteen days of one session log, twelve sentences were lost that way, four within eighteen seconds. A render that produced no audio at all now raises `SpeechMadeNoAudio`, and the backend lets that pipeline go before re-raising, so the second attempt is the fresh service the log shows speaking the next sentence anyway. One voice is still the rule: nothing is spoken in a stand-in's voice.

- **Feature: a compaction says why it ran, in the log and in `/usage`** (`src/zrb/llm/shared/usage_log.py`, `src/zrb/llm/summarizer/history_summarizer.py`, `src/zrb/llm/custom_command/usage/command.py`, `src/zrb/llm/task/llm_task.py`, `test/llm/shared/test_usage_log.py`, `test/llm/summarizer/test_compaction_fire_log.py`, `test/llm/custom_command/usage/test_usage_command_sections.py`): `/usage` could say what a compaction cost and never why it ran, and a compaction fires on three different things — the token threshold (the configured trigger *less the system prompt*), a message-count window that can fire on its own, and `/compress`, which answers no limit at all. Every compaction now writes a WARNING line when it fires, and a limit-triggered one that replaced something logs a second line saying how much smaller the history came out; a fire that reached no model says the history was left as it was, so a fire in the log with no line in `/usage` is explained rather than missing. Its record carries the reason beside the history size and the room the system prompt had already spent: `forced`, `token`, `message`, or both when a history crosses both checks at once. `/usage` prints the last five fire lines. A forced compaction has no limit to report, so its token fields are zero and are rendered as unknown rather than as nothing — a zero that meant "not measured" would read as a compaction that cost nothing. Recorded as decision 11 in ADR-0127.
- **Behaviour change: the verbatim tail kept after a compaction is capped at 12,000 tokens** (`src/zrb/config/mixins/llm_content.py`, `docs/configuration/llm-context.md`, `test/llm/summarizer/test_summarization_policy.py`): the kept tail is the smaller of `LLM_HISTORY_TAIL_BUDGET_RATIO × trigger` and `LLM_HISTORY_TAIL_MAX_TOKENS`, and on the default 200,000-token trigger the ratio allows 80,000 — so the ceiling, not the ratio, is what decides how much conversation survives a compaction, and every later round re-reads all of it. The default ceiling is now 12,000 instead of 24,000, which halves that handover. Nothing is lost by it: the messages the tail drops are summarized, and the originals stay archived under `LLM_HISTORY_DIR/verbatim/`. A value you set still wins, and `0` still leaves the ratio in charge.
- **Improvement: the batch reminder counts a streak that mixes lookups** (`src/zrb/llm/tool_call/batch_nudge.py`, `test/llm/tool_call/test_batch_nudge.py`, `docs/configuration/llm-context.md`): three lookups issued one round apart are the same waste whether or not they use the same tool, so `Read` then `Grep` then `Glob` — invisible to the old rule, which asked for one tool throughout — now counts. Replayed over three weeks of real transcripts (256 conversations, 14,970 rounds), the conversations a streak qualifies in rise from 24 to 36. The tool is part of what was asked: `Grep x` after `Glob x` is two lookups even though their arguments render identically, while the same tool on the same arguments is still one lookup repeated. Writes and shell commands still end a streak.
- **Improvement: `Grep`, `Glob` and `LS` ask for their calls to be batched where the tool is chosen** (`src/zrb/llm/tool/file/search.py`, `src/zrb/llm/tool/file/listing.py`): `Read` already ended with that sentence; the other three lookups now say it too, so the four are consistent. It sits in the text a model reads immediately before it emits the call — the one place an instruction can land before the wasted round rather than after it, which is why it exists beside the reminder rather than instead of it. It costs about a hundred tokens on every request, and a model whose System Context has withdrawn the batch rule is told so in the same sentence.
- **Chore: the prose added since the October sweep is swept of narration** (`src/zrb/llm/{agent,config,custom_command,dictation,emotion,hook,memory,prompt,shared,skill,speech,subagent,summarizer,tool,tool_call,ui}/`, `src/zrb/config/`, `src/zrb/builtin/llm/`): the standard is the one the three October commits set — mechanism in, narration out — so the unswept prose was whatever has landed since `30973d838`, 539 files carrying 4,518 added comment and docstring lines, and every added block was read against that standard. Removed: the incident that produced a constant retold end to end (`src/zrb/llm/summarizer/chunk_processor.py`), the alternative a decision passed over re-argued inside the docstring that made the decision (`src/zrb/llm/hook/builtin/memory_reviewer.py`, `src/zrb/llm/memory/migrate.py`), a rationale that had been copied into five files and is now stated once where the placement is computed (`src/zrb/llm/ui/default/app/layout.py`), past-tense narration of a fixed bug turned back into the constraint it states (`src/zrb/llm/prompt/memory_context.py`), and the word-level residue — "only ever" (5), emphatic "very"/"really" (6), "simply" (3), "the whole point"/"the whole reason" (3), "robust" as a compliment (2), filler "just" (1). Kept on purpose: "deliberately", "entirely" where it is precise, "no longer"/"used to" about runtime state rather than history, tool-schema docstrings, and the "X rather than Y" clauses that name an ordering, a cap or a placement a future editor could violate. Nothing executable changed, and that is checked rather than asserted: in each of the 39 files the AST equals the previous commit's with every bare string statement removed, `flake8 --select=F` is clean, and `pytest test/llm test/architecture test/test_public_api_docs.py` gives 8,622 passed and 29 skipped. One defect fell out of the read: `memory/migrate.py` promised "Four rules" over a list of five.

- **Feature: zrb loads the skills Claude Code syncs from claude.ai and the skills inside the plugins it installs** (`src/zrb/llm/skill/manager.py`, `src/zrb/util/dir_search.py`, `test/llm/skill/test_skill_manager_search_dirs.py`, `test/util/test_dir_search.py`, `docs/llm/claude-compatibility.md`): two of Claude Code's real skill locations fell outside zrb's scan. Downloads sit two levels deep, `synced/<bucket>/<name>/SKILL.md`, and the walk stopped one directory short; plugin discovery wanted a manifest directly under the plugins root, which none of Claude Code's installed layouts provides. On one machine zrb found 21 skills while Claude Code had 43. Each `synced/*` bucket is now its own scan root — bounded by the number of buckets, not by the size of the tree — and is scanned before `~/.claude/skills`, so a skill you wrote wins a name the same download also has. Plugin discovery reads a checked-out plugin, every plugin a marketplace checkout publishes, and the `installPath` of each entry in `installed_plugins.json`; the installed copy comes last, so a marketplace checkout wins the name. Synced skills are remote files Anthropic ships and rewrites — they carry the same trust as anything else on disk, and zrb does not sandbox the commands a skill asks for. `.staging` and `.trash` are skipped like any other dot directory.
- **Feature: a marketplace checkout publishes its plugins from the paths its own manifest names** (`src/zrb/util/dir_search.py`, `test/util/test_dir_search.py`, `docs/llm/claude-compatibility.md`): a `.claude-plugin/marketplace.json` lists its plugins with a `source`, which is often `plugins/<name>/` and sometimes `./` for a marketplace that publishes from its own root — and an entry can name a directory that carries no manifest of its own. Reading only `plugins/*/` therefore missed both. Declared sources are read first, then `plugins/*/` children that carry a manifest, and the checkout root last. A declared source is also data that arrives with the checkout rather than a grant on the machine: an absolute path, a `..` that climbs out, or a symlink pointing elsewhere would let a marketplace make zrb import a `SKILL.py` or an agent from anywhere on disk, and override discovered definitions by name. Every candidate is resolved against the checkout and dropped when it escapes.
- **Feature: a config dir list may name an absolute path, so zrb can follow `$CLAUDE_CONFIG_DIR`** (`src/zrb/util/dir_search.py`, `src/zrb/config/mixins/llm_search.py`, `src/zrb/llm/skill/manager.py`, `src/zrb/llm/subagent/manager/search.py`, `src/zrb/llm/hook/hook_loader.py`, `src/zrb/llm/prompt/claude.py`, `test/util/test_dir_search.py`, `test/llm/skill/test_skill_manager_search_dirs.py`, `test/llm/subagent/manager/test_manager_search.py`, `test/llm/hook/test_hook_loader.py`, `test/llm/prompt/test_claude.py`, `docs/llm/claude-compatibility.md`, `docs/configuration/llm-tools.md`): Claude Code reads its config directory from `$CLAUDE_CONFIG_DIR` when it is set and from `~/.claude` otherwise, so a user who moved it was invisible to zrb — skills, sub-agents, hooks and the user-level `CLAUDE.md` all stayed on the old path. An entry in `LLM_CONFIG_DIR_NAMES` that is absolute is now a root in its own right: it is scanned once, as a user tier, and never appended to a project directory, where it would come after the project's own config dirs and let a user skill win a name collision the documented order gives to the project. `~` is expanded, so either spelling reaches the same directory. One `export ZRB_LLM_CONFIG_DIR_NAMES=".claude:.zrb:$CLAUDE_CONFIG_DIR"` now covers all four readers. Two things about that line are stated in the docs because both bite silently: the variable *replaces* the default list rather than extending it, so `.claude` and `.zrb` have to be named to keep them — appending to an unset variable drops both; and zrb's own `.<ROOT_GROUP_NAME>` hooks are still read when the list omits that name, since they are zrb's config, not the user's to switch off. Hook discovery previously ignored the list entirely and looked for `.claude` only.

- **Feature: `/usage` says what picking a large conversation back up costs, instead of leaving it to a habit** (`src/zrb/llm/custom_command/usage/resume.py`, `src/zrb/llm/custom_command/usage/command.py`, `src/zrb/config/mixins/llm_ui_commands.py`, `test/llm/custom_command/usage/test_usage_resume.py`, `docs/adr/adr-0127.md`, `docs/configuration/llm-limits.md`, `docs/configuration/llm-context.md`): every number `/usage` printed described a turn already paid for, so the one decision that costs the most had no measurement behind it. Past a provider's prompt-cache lifetime the whole history is re-sent as fresh input: on the 2026-11-12 log, three turns began 37, 21 and 127 minutes after the previous one, at 67.0%, 49.9% and 49.8% cached, and paid 351,517 fresh input tokens to produce 5,484 output — a fifth of that day's fresh input — where a cold session pays 18–24k before the first word. When the conversation's saved history holds more than `ZRB_LLM_UI_USAGE_RESUME_HISTORY_TOKENS` (default 100,000) and its newest message is older than `ZRB_LLM_UI_USAGE_RESUME_GAP_SECONDS` (default 1,200 — four times the five-minute lifetime a prompt cache has by default), `/usage` adds one line under the footer: `resume  last turn 2h 7m ago · 405.0k tokens of history · ~405.0k fresh to resume vs ~20.0k to start over`. It is computed from what is already in hand — the saved history and the timestamp on its newest message, scanned back past an unstamped `ModelRequest` — so it costs no model call and never touches the usage log, and it answers after a restart, which is when the question gets asked. The gap is judged before the history is counted, because counting is the expensive half; a turn still running gets no line; and the estimate charges the whole history, so a provider that still holds part of the prefix cached makes resuming cheaper than the line says, never dearer. Either knob at `0` turns the line off. Recorded as decision 12 in ADR-0127.
- **Fix: the batch reminder is said at most once per user turn, and no longer goes quiet at a turn boundary** (`src/zrb/llm/tool_call/batch_nudge.py`, `test/llm/tool_call/test_batch_nudge.py`, `docs/configuration/llm-context.md`): the module promises to say the reminder "once rather than every round after", and the walk behind it delivered neither half. `_single_call_streak_tools` collected three consecutive single-call rounds and returned `None` the moment it met the injected marker on the way, so a turn that kept issuing one lookup per round was reminded again every third round — the marker only suppressed a reminder while it still sat within three rounds of the tail — and a streak that crossed a new user prompt never reached the model at all: two rounds, the reminder they earned, a new prompt, one more lookup, and the old marker stopped the walk before it had its three. A reminder now silences the rest of its own turn and nothing past it. - **Fix: an MCP server's tools carry the `purpose` line and never receive it** (`src/zrb/llm/tool/mcp.py`, `src/zrb/llm/tool/purpose.py`, `src/zrb/llm/agent/common.py`, `test/llm/tool/test_mcp.py`, `docs/llm/mcp-support.md`, `docs/architecture/3-peripheral-flow/mcp-and-lsp.md`): 3.38.4 gave every tool zrb builds a slot for `purpose`, the line the narrator reads aloud instead of the tool's generic sentence — by extending the function's `inspect.signature` in `create_safe_wrapper`. An MCP server's tools were the one edge that could not reach. Their schema is JSON the server publishes, not a Python signature, so there was nothing to extend, and zrb forwarded the model's arguments to the server untouched: a call that obeyed the standing instruction came back as `1 validation error for call[echo] · purpose · Unexpected keyword argument`, which costs the round and re-sends the whole context with it. `add_purpose_to_mcp_tools` now wraps each `MCPToolset` that `load_mcp_config` builds. On the way in it rewrites every tool definition whose `inputSchema` is an object and does not already declare `purpose`, adding a **required** string property with the shared description and marking the definition (`DECLARED_PURPOSE_KEY`); on the way out it drops the argument before forwarding, but only for a definition it marked. Required rather than optional for two reasons: the description says "Always fill this", and a schema with an optional property is not strict-compatible, which turns a provider's strict mode off for that whole tool. A server that declares `purpose` itself is left alone — its schema is not touched and the value is forwarded, because that parameter is the server's own meaning, which is why the drop is keyed to what zrb added rather than to the argument's name. A schema that cannot be extended safely is also left alone: a `$ref` or a union, or properties that are not a mapping. The wrapper forwards the server's `id`, so its tools keep the name the server gave them. Measured against a FastMCP 3.4.11 stdio server with two tools, `echo(text)` and `log(text, purpose: str = "")`, driven by a `FunctionModel` so the arguments were chosen rather than sampled: declaring alone was still refused, dropping alone left the model no reason to write the line, and both together returned `echo: hi`; `log`'s own `purpose` kept its schema (`{"default": "", "type": "string"}`, no description added) and received `Probing`. Eight tests, none needing a live server.
