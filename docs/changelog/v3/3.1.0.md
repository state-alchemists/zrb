## 3.1.0 (September 12, 2026)

- **Reliability: the initial readiness wait is bounded by default** (`src/zrb/task/base/execution.py`, `src/zrb/task/base/base_task.py`, `src/zrb/config/mixins/task_runtime.py`, `src/zrb/task/{cmd_task,rsync_task,scaffolder,scheduler,base_trigger,make_task}.py`, `test/task/base/test_execution_readiness.py`, `docs/core-concepts/make-task.md`): a task whose readiness check never succeeded waited forever with no output — measured at 180s and still running against a `TcpCheck` on a closed port, so a hung health check held a CI job indefinitely. Two knobs were in play and neither bounded that wait: `readiness_timeout` defaulted to a reassuring `60` but was read only by the `monitor_readiness` re-check loop in `monitoring.py`, while the initial wait in `execution.py` read `CFG.TASK_READINESS_TIMEOUT`, which defaulted to `0` ("no cap"). 2.50.0 documented the split rather than closing it. Both paths now read `task.readiness_timeout`, whose default moved into `ZRB_TASK_READINESS_TIMEOUT` (now `60000` ms, was `0`); the constructor parameter defaults to `None` across all nine task classes -- `BaseTask`, `CmdTask`, `RsyncTask`, `Scaffolder`, `Scheduler`, `BaseTrigger`, `make_task`, `LLMTask` and `LLMChatTask` -- so the environment variable is a real global default instead of one shadowed by a re-declared `60`. An explicit `0` or negative value still removes the cap. **Breaking:** a readiness check that never completes now fails its task after 60s instead of hanging; set `ZRB_TASK_READINESS_TIMEOUT=0` to restore the old unbounded behavior.
- **Security: `zrb server start` refuses an unsecured non-loopback bind** (`src/zrb/runner/cli.py`, `test/runner/test_cli.py`, `docs/advanced-topics/web-ui.md`): binding beyond `127.0.0.1` publishes task execution — arbitrary command execution — to everyone who can route to the host, and `_warn_if_insecure_bind` only printed a warning ("Warn (never refuse)") before starting anyway, so `ZRB_WEB_HTTP_HOST=0.0.0.0` served happily on the documented `admin`/`admin` credentials and the documented `zrb` signing key. `_refuse_insecure_bind` now exits `1` before the app is built when a non-loopback bind has authentication off, or still carries the default `WEB_SUPER_ADMIN_PASSWORD` or `WEB_SECRET_KEY`; the refusal names the offending knobs and the two supported fixes. The effective `WebAuthConfig` is still what gets inspected, so programmatic overrides are honored — which matters because it treats only `None` as "fall back to CFG", so an explicitly empty password is a real override that no longer equals the shipped default and would otherwise have passed a check that only asked whether the value had changed. Credentials are therefore validated rather than merely compared: empty or whitespace-only is rejected, as is anything below a 12-character floor for `WEB_SUPER_ADMIN_PASSWORD` or a 32-character floor for the JWT-signing `WEB_SECRET_KEY`, and every failing requirement is listed in one message instead of revealing itself one restart at a time. Loopback is decided by parsing the address (`ipaddress.ip_address().is_loopback`) rather than matching three strings, so `127.0.0.2` and the expanded `0:0:0:0:0:0:0:1` are recognised; a hostname that cannot be proven loopback-only still fails closed. There is deliberately no override flag. **Breaking:** an existing unauthenticated public deployment stops starting until auth is enabled with unique credentials, or the bind moves back to loopback.
- **Fix: `SystemExit` from an action body is no longer retried as a task failure** (`src/zrb/task/base/execution.py`, `test/task/base/test_execution_task_chain.py`): the retry loop already passed `CancelledError`, `KeyboardInterrupt` and `GeneratorExit` through untouched, but `SystemExit` fell into the generic `except BaseException` below them — so a deliberate `sys.exit(1)` was logged as `Attempt 1/N failed: 1` (the exit *code* printed where the error message goes), retried up to `retries` times, and then marked permanently failed. It now joins the passthrough tuple, which is what makes the refused-bind message above read cleanly.
- **Tests: `./zrb-test.sh` is hermetic** (`zrb-test.sh`): coverage fragments land in the repo root as gitignored `.coverage.*` files, one per xdist worker, and pytest-cov combined whatever it found there — so an interrupted run, or a second run started concurrently, could fail the whole command with `Can't combine branch coverage data with statement data` *after* the tests had already passed. The script now points `COVERAGE_FILE` at a per-run temporary directory removed on exit, which is the whole fix: fragments are written and combined there, and anything an older run or another tool left in the repo root is ignored rather than deleted. `--cov-report=html` still writes to the shared `./htmlcov` on purpose, so the report stays at a predictable path.
