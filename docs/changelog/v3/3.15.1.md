## 3.15.1 (October 8, 2026)

- **Fix: the mistyped-variable warning no longer calls a project's own env vars typos** (`src/zrb/config/config.py`, `src/zrb/config/mixins/foundation.py`, `docs/configuration/env-vars.md`, `docs/advanced-topics/white-labeling.md`, `AGENTS.md`, `test/config/test_config_env_warnings.py`, `test/test_main.py`): the warning gated on the prefix alone and reported any `<ENV_PREFIX>_*` variable scoring 0.85 or better against a setting name, and that cutoff cannot separate the two cases it faces — a real typo (`MAX_TOKEN_PER_MINUTE` written for `LLM_MAX_TOKEN_PER_MINUTE`, 0.92) and a variable the project reads itself through its own code (`LLM_PROXY_BASE_URL` beside `LLM_BASE_URL`, 0.864) are one segment apart, indistinguishable at any threshold. Measured against the 29 `ARASAKA_*` variables bsim-agent reads, 4 were reported; only the project knows which names are its own, so it can now say so. The new `PROJECT_ENV_KEYS` setting takes prefix-relative names — exact (`LLM_PLUGIN_DIR`) or a `*` glob (`LLM_PROXY_*`) — and both the mistyped and the retired report skip the names it claims, so one list serves any prefix. A name is skipped only when the project claims it, so an unclaimed typo is still reported and the feature loses nothing. The list is silence only: a claimed name never enters the suggestion candidate pool, so a claim cannot make zrb advise setting a variable nothing reads. The warning runs after the init sources are loaded, which is what lets a distribution claim its keys from `zrb_init.py`, and a test pins that ordering.
- **Fix: a `str` assigned to a config field is stored as the env text rather than serialized** (`src/zrb/config/env_field.py`, `src/zrb/config/mixins/foundation.py`, `test/config/test_env_field.py`, `test/config/test_config_env_warnings.py`): `EnvField.__set__` ran every assigned value through the field's `serialize` before the round-trip check, and skipped that check when the value was a `str`, on the assumption that a string is already the canonical env form — which holds for a scalar cast and not for a value serializer, since `",".join` on a `str` iterates its characters. `CFG.LLM_TOOLS = "Shell,Read"` therefore wrote `S,h,e,l,l,,,R,e,a,d` and read back as a list of single letters, with no error and no warning, and a bool field failed the other way, because `serialize=on_off` turned the non-empty string `"off"` into `"on"` and `CFG.LLM_SHOW_TOOL_CALL_DETAIL = "off"` read back as `True`. Introduced with the 3.0 configuration rewrite, it affected every list- and mapping-valued setting (`LLM_TOOLS`, `LLM_SKILLS`, `LLM_AGENTS`, `LLM_HOOKS`, `LLM_PLUGIN_DIRS`, `INIT_MODULES`, `PROJECT_ENV_KEYS`, `LLM_SPEECH_PROGRESS_PHRASES`) and the path lists. A string is now stored as written, since it is the env text — the same thing the env var carries — and only a non-`str` value is serialized first; the cast still validates the string, so `CFG.WEB_HTTP_PORT = "abc"` keeps failing loudly, and the round-trip rejection for non-`str` values is unchanged, so a tuple on a list field is still refused. No zrb code path reached the old behavior, so no shipped feature was reading a mangled value: env var reads never call `__set__`, `/set` converts through `CFG.convert_setting_value` before it assigns, and no `CFG.<NAME> = ...` assignment exists anywhere under `src/`. The exposure was a project's own bootstrap code in `zrb_init.py` or a white label's init module, where the trap is a value that looks accepted and is silently wrong.
