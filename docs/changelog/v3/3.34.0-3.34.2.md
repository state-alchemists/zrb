## 3.34.0–3.34.2 (November 4, 2026–November 5, 2026)

- **Feature: a shipped tool can be approved by default, below your rules** (`src/zrb/llm/tool_call/always_approve.py`, `src/zrb/llm/agent/run/deferred_calls.py`, `src/zrb/llm/common_tools.py`, `docs/llm/permission-policy.md`): the approval cascade gains a stage at priority 2c — after the permission policy, before YOLO — for tools whose blast radius is already bounded. Your own `ask` or `deny` rule still wins, and a `PreToolUse` hook's `ask` still forces the prompt; only a tool that *is* the user interaction is approved above the rules. `apply_common_tools` registers the defaults, so `LLMTask` and `SubAgentManager`, which have no policy list, get them too. See [ADR-0139](../adr/adr-0139.md).
- **Fix: the memory reviewer's writes now land** (`src/zrb/llm/hook/memory_reviewer.py`, `src/zrb/llm/hook/schema.py`, `src/zrb/llm/hook/creator.py`): the stop hook that records what a turn taught builds its agent with no approval channel, so every `Remember` it called came back as a deferred request — counted as a tool call, never executed, and nothing written. Shipped that way in 3.33.0. `AgentHookConfig.auto_approve` now runs such an agent without deferring, safe because the hook's own config fixes its tool list.
- **Fix: the memory verbs and six ordinary tools stop prompting** (`src/zrb/llm/common_tools.py`): `SearchMemory` was the only read of the notes directory that asked, while `Read` and `Grep` on the same directory were approved. `Remember`/`Forget`, `ReadToolResult`, `SendMessageToSubagent`/`SendMessageToParent` and `EnterWorktree` no longer ask either; `LspRenameSymbol` is approved only for `dry_run=true`, and `ExitWorktree` still asks. 3.33.0's note that "mutating the memory store asks" still holds for a raw `Write`, `Edit`, `RM` or `MV` inside `LLM_MEMORY_DIR`; the two verbs are the store's own interface.
- **Fix: the self-review gate reads the turn, and a JSON agent hook can opt in** (`src/zrb/llm/hook/self_review.py`, `src/zrb/llm/hook/manager_loading.py`, `docs/llm/hooks.md`): the same defect in the other built-in agent hook — the self-review reviewer was built without approval too, so its `Read`/`Grep`/`Glob` calls were deferred and the gate judged a turn it never read. Off by default; with `ZRB_LLM_SELF_REVIEW_ENABLED` on, it now reads. A user-configured agent hook sets the same switch as `"auto_approve": true` in its `config`.
- **Chore: pydantic-ai 2.65.0** (`pyproject.toml`, `poetry.lock`, `docs/technical-specs/llm-history-sanitization.md`): `pydantic-ai-slim` moved from 2.61.0 to `>=2.65.0,<2.66.0`, and the provider extras that repeat its own floors moved with it — `anthropic>=1.15.0` (was 1.12.1), `mistralai>=3.1.0` (was 2.9.2, a major SDK bump: pydantic-ai's Mistral model reads the `ResourceChunk`/`ResourceLinkChunk` content types 3.1.0 introduced) and `openai>=3.31.0` (was 3.26.0, a core dependency here, so no extra enforces it). `mistralai` 3.7.0 requires `httpx2>=2.13.0`, which carried `httpx2` and `httpcore2` to 2.16.0. One behavior change reaches the user: a Z.ai balance or plan-limit 429 is now an exhausted quota rather than a rate limit, so the turn stops instead of retrying it.
- **Chore: four transitive dependencies take their security floors** (`pyproject.toml`, `poetry.lock`): `authlib>=1.9.1` (was 1.8.0), carrying one critical advisory (an empty signature passes JWS JSON deserialization), two high-severity forgery advisories and five mediums; `joserfc>=1.7.6` (was 1.7.5); `dnspython>=2.9.0` (was 2.8.0); and `pyasn1>=0.6.5` (was 0.6.4), declared in both the `google` and `vertexai` extras rather than in the base dependencies: google-auth reaches it down two optional paths, so a floor in only one leaves the other installation free to resolve 0.6.4, and an install that touches no Google API should not carry pyasn1. That closes four high-severity quadratic-time decoding advisories. All four are transitive — authlib rides `pydantic-ai-slim[mcp]` → `fastmcp-slim[client]`, dnspython rides `email-validator`, pyasn1 rides `google-auth` → `pyasn1-modules` — so each floor is stated as a dependency with the advisories that require it, as the other transitive pins in `pyproject.toml` do. `poetry lock` moved only those four: to 1.9.3, 1.8.0, 2.9.2 and 0.6.5.

- **Fix: a queued sentence waits its turn instead of being dropped** (`src/zrb/llm/speech/player.py`, `src/zrb/config/mixins/llm_speech.py`, `docs/configuration/llm-voice-camera.md`): sessions of one user take turns speaking by a lock file, and a sentence that could not have it within `ZRB_LLM_SPEECH_LOCK_TIMEOUT` (30 s) was discarded — with two `zrb` chats in one directory, measured here, the waiting side lost its answer while the other spoke. A queued sentence — a reply or a narration line — now waits for the device however long the other session holds it, and says so once in the log; a new message or an interrupt drops it at once. `Speaker.speak` keeps the timeout and still raises `FileLockTimeout`, and the variable's docstring and voice-doc row now say which of the two it governs. `drain()` also keeps a sentence that is still waiting, which used to be read as no longer wanted, so a reply is no longer lost at exit; and a player's own `FileLockTimeout` is a failed sentence rather than contention to retry.
- **Fix: a hush between turns no longer silences the next reply** (`src/zrb/llm/speech/streamed_reply.py`): `interrupt_speech` runs when the user submits a message, which is exactly between turns, and it marked the *next* streamed reply as one the user had talked over — a claim nothing cleared when that reply started. At Stop, `has_claimed_turn` was therefore true and a reply carrying no `<spoken>` block, which is spoken only at Stop, was never read at all: three replies in a row went unspoken while the one that carried a block was heard, because a block is spoken while it streams. A new response now clears the claim; a barge-in inside a response still claims it.
- **Fix: a shipped tool keeps its capability when passed by reference** (`src/zrb/llm/tool/*`, `src/zrb/llm/lsp/tools.py`, `src/zrb/llm/agent/spill.py`, `src/zrb/llm/common_tools.py`): tags were applied in `_seed_default_tools`, so a tool had one only if something had resolved the built-in registry first. `LLMTask(tools=[read_file])` never does, so the tool arrived as `Capability.UNKNOWN`, and the sandbox checks an unknown tool's path arguments as writes: a read outside the writable roots was refused where the same read in a chat was allowed. Every shipped tool, and every factory product, now tags itself where it is defined. The tagged surface is unchanged — the same 26 static tools and the same factory products resolve to the same capabilities.
- **Fix: every hook payload says which run it belongs to** (`src/zrb/llm/hook/manager.py`, `src/zrb/llm/agent_state.py`, `src/zrb/llm/agent/run/runner.py`, `src/zrb/contextvars.py`): `nested_run` existed in the Stop payload only, so a hook that paints state from a turn's events — the avatar's face is the one that showed it — could not tell a run started inside another one (a hook's reviewer, a sub-agent) from the user's own turn. Measured on a running face: the turn ends and the face is told idle, then the reviewer's run announces its prompt and the face is told thinking and tool, and nothing tells it idle again, so the window reports the last turn still running until the user speaks. `current_nested_run` is now bound for the run's life beside `current_agent_run_scope`, and every event carries it; a caller that states it explicitly still wins. A face plugin that predates the key behaves exactly as before.
- **Fix: a day file keeps one line per event** (`src/zrb/llm/memory/store.py`): the file already ended with a newline, so `append_log` pasting another one in front of the event left a blank line under every appended line — the 2026-11-04 file collected four by 19:03. Whole lines are joined now, and a blank line an earlier writer left is dropped, so an old day heals as it grows.

- **Fix: a hook's own run carries the nested mark** (`src/zrb/llm/hook/creator.py`): 3.34.1 put `nested_run` on every hook payload, but the mark itself was bound only by the runner (`src/zrb/llm/agent/run/runner.py`), and an agent hook never goes through it — `run_llm_hook` builds its own agent and calls `agent.run` — so a hook's own run inherited the enclosing turn's value, which at top level is `False`. In a real session, then, no hook payload ever carried `nested_run: true`, and a listener that paints state from a turn's events still could not tell the memory reviewer's run from the user's own turn. Measured on a running face with 3.34.1 and a plugin written against it: the turn ends and the face is told idle, the reviewer's prompt and tool events repaint thinking and working, and nothing tells it idle again, so the window reports the last turn still running until the user speaks. `run_llm_hook` now binds `current_nested_run` for the run's life and clears it in a `finally`, so a hook that raises cannot leave the mark behind and mute a listener for the rest of the session.
