## 3.3.0 (September 13, 2026)

- **Fix: a chat session id from the request path could place uploads outside the upload root** (`src/zrb/runner/chat/chat_api_route.py`, `test/runner/chat/test_chat_api_uploads.py`): `save_uploaded_attachment` joined `session_id` — the `{session_id}` path parameter of `POST /api/v1/chat/sessions/{session_id}/attachments`, straight off the request — into the upload path with no validation, while `filename` beside it was already reduced to a basename. `session_id=".."` resolved the upload directory to the shared temp directory itself, so the bytes landed outside the per-session root and the directory's mode was restated to 0700, locking every other user on the machine out of it. The id now goes through `to_safe_filename` (alphanumerics, `-` and `_` — what `get_random_name` and the `<parent>-sub-<agent>-<id>` delegated form already produce, both verified to survive it unchanged), an empty result is rejected, and the joined path is asserted to sit directly under the root in case that helper's contract ever loosens. Covered by a parametrized test over `..`, `.`, nested traversal, an absolute path, mixed separators and an empty id, each asserting containment and that the temp directory's mode is untouched.

- **Fix: the GPIO example reused one photo path, and web-chat uploads trusted a fixed temp directory** (`examples/chat-gpio-ptt/{zrb_init.py,README.md}`, `src/zrb/runner/chat/chat_api_route.py`, `test/runner/chat/test_chat_api.py`): `capture_photo` wrote every frame to the same `zrb-gpio-photo.jpg` under the shared temp directory and yielded that path. An attachment path is read when the turn reaches the model — `normalize_attachments` in `agent/run/prompt_content.py`, not at submit time — so a second press while the first turn was still queued handed the first turn the second photo; and a fixed name in shared temp is one a local user can pre-create as a symlink to redirect the write. Each capture now gets its own `tempfile.mkstemp` file: unique, created atomically, mode 0600. The path is kept rather than switched to `BinaryContent`, because `normalize_attachments` passes a `BinaryContent` through untouched — no size check, no image scaling — so a full-resolution frame would count against the attachment limit whole; the example's docstring and README said resolution happened at submit time and now say otherwise. The same fixed-name pattern was in `save_uploaded_attachment`, which built `<tmp>/zrb_web_chat_uploads/<session>` with `makedirs(exist_ok=True)` and no check on what was already there, so a symlinked root took delivery of every web-chat upload. It now creates each level 0700 and refuses a root that is not a real directory owned by the current user, mirroring `llm/agent/spill.py::_ensure_root`, which already had exactly this guard.

- **Fix: a failed trigger submission no longer leaves its attachments staged for the next turn** (`src/zrb/llm/ui/base/triggers.py`, `test/llm/ui/base/test_base_ui.py`): `trigger_loop` extends `pending_attachments` and then calls `submit_user_message`, which drains the list — but only after echoing the message, and the drain is skipped entirely if the submission raises. Under `MultiUI` the echo broadcasts to every child, so a backend that errors (a Telegram send, an SSE write) raises before anything is drained. The staged attachments then survive into whatever turn came next, so a camera frame from a failed GPIO trigger could arrive attached to a message typed minutes later. Staging is now transactional: the loop records the list length before extending and truncates back to it if the submission raises, which is exact because nothing awaits in between. Reproduced against the real `BaseUI` with a raising `submit_user_message` and pinned by a regression test.

- **Refactor: four `BaseUI` state parts are public attributes instead of 22 forwarders** (`src/zrb/llm/ui/base/{ui,voice_state,confirmation_state,persona_state,usage}.py`, `src/zrb/llm/ui/default/{output,keybindings,lifecycle,agent_picker}.py`, `AGENTS.md`, `test/architecture/test_facade_size_budget.py`, 14 test modules): `BaseUIVoiceState` holds four fields and `BaseUI` wrapped them in eight property accessors so `keybindings.py` could write `ui.voice_mode_active`; `BaseUIConfirmationState`, `BaseUIPersonaState` and `BaseUIUsage` were the same shape. The convention that produced them said a part reaches the owner's state only through a public property, which meant every field a sibling part touched became a permanent public name on `BaseUI` — 60 of its 102 public names existed for no caller outside `llm/ui`. The four parts are now `self.voice`, `self.confirmation`, `self.persona` and `self.usage`, reached as `ui.voice.mode_active` and `ui.confirmation.current`; `UIOutput`'s own second-level `current_confirmation` forwarder went with them, as did two hand-rolled copies of the same shape in the test doubles. `BaseUI.accumulate_usage` stays a named method: `docs/llm/llm-custom-ui.md` lists it as an enrichment hook and `MultiUI`/`BufferedUI` implement it too. The `getattr(ui, "voice_mode_active", False)` shims that tolerate a non-`BaseUI` implementation now reach the part (`getattr(ui, "voice", None)`), so `StdUI` and `MultiUI` are unaffected. `AnyUI` is untouched at 16 methods, and `SimpleUI`/`EventDrivenUI` — the documented extension levels — keep their 8 and 7. `ui.py` drops 1307 → 1206 lines and 102 → 89 public names, its facade budget tightens to match, and repo-wide pure delegators fall from 636 to 621.

- **Chore: the coverage gate is 94%** (`zrb-test.sh`, `AGENTS.md`, `docs/adr/{adr-0034,README}.md`, `docs/contributing/maintainer-guide.md`, `docs/advanced-topics/testing-tasks.md`): the full run has measured above 94% for some time, so `--cov-fail-under` now sits at the number the suite actually holds rather than four points below it, where a real regression could hide. Every place that stated the old bar — ADR-0034's title and Decision, its index entry, the maintainer guide's gate table, the testing guide's prose, and AGENTS.md's test principles — names 94 now. Scoped runs (`./zrb-test.sh <path>`) still skip the gate entirely, since they exercise only part of the tree.

- **Refactor: the agent barrel resolves lazily, and import safety is asserted per module** (`src/zrb/llm/agent/__init__.py`, `test/architecture/test_circular_import_allowlist.py`, `.coveragerc`, `AGENTS.md`, `docs/llm/llm-chat-lifecycle.md`, `docs/adr/{adr-0086,adr-0088,adr-0096}.md`): a package `__init__` runs before any of its submodules, so `zrb/llm/agent/__init__.py`'s four eager re-exports meant `common.py`, `run/runner.py` and `summarizer.py` — and through them most of `zrb.llm` — loaded whenever *anything* under `zrb.llm.agent` was imported. Measured over the module graph (`if TYPE_CHECKING:` excluded), that made the tree's largest strongly connected component 87 modules spanning `llm.tool`, `llm.ui`, `llm.agent`, `llm.task`, `runner.chat` and `runner.cli` — every one able to reach every other. Deferring each package barrel in turn showed it was almost entirely this one file: `zrb.llm.agent` lazy takes the number to 23, `zrb.llm.ui` to 82, `zrb.llm.tool` to 87 (no change at all — which is why restoring it to eager in 2.67.0 was right). The blocker was the safety net, not the barrel: `test_every_package_imports_with_its_parents_stubbed` imported 27 packages and nothing deeper, so the tree's 419 other modules were reachable by it only through whatever their barrel re-exported, and any barrel made lazy silently shrank the check. That check now parametrizes over every name an `import` statement can spell — 444 targets, the 417 modules plus the 27 packages, excluding the hyphenated skill tool scripts under `llm_plugin/*_skills/<skill>/tools/` — so it asserts directly what it used to assert by proxy. Both halves earn their place: a stubbed-parent import of `zrb.llm.agent.common` never runs `zrb/llm/agent/__init__.py`, so the barrel this change makes lazy is covered only by naming the package itself. The agent barrel then resolves through PEP 562 `__getattr__`, caching into `globals()`, with the names mirrored under `if TYPE_CHECKING:` for pyright; `hook_agent`'s builder registration moved into that same `__getattr__`, firing on first use of an agent name instead of on package load — still earlier than any hook-manager read, since every entry point resolves one of the four while building its agent. Import spellings are unchanged everywhere: `from zrb.llm.agent import create_agent` is an attribute access, which is what `__getattr__` answers, and all 14 call sites are untouched. Net: largest SCC 87 → 23, modules in any cycle 102 → 23, `zrb.llm.agent`'s eager closure 338 of 447 modules → 1, isolated-import coverage 27 packages → 417 modules (+392 tests, 5,774 → 6,166). `import zrb` is unchanged at 0.22s — the win is structural, not latency. `.coveragerc`'s skill-tool-script omit named only `skills/` and now also names `core_skills/`; the per-module check surfaced the gap. See ADR-0096.

- **Feature: a chat trigger can attach files and photos, not just text** (`src/zrb/llm/ui/trigger.py`, `src/zrb/llm/ui/base/triggers.py`, `src/zrb/llm/ui/{__init__,base/ui}.py`, `src/zrb/{__init__.py,llm/task/chat/task.py}`, `examples/chat-gpio-ptt/`, `examples/README.md`, `test/llm/ui/base/test_base_ui.py`, `test/architecture/test_facade_size_budget.py`): `LLMChatTask(triggers=[...])` lets an external source — a GPIO button, a webhook, a message queue — drive a chat session by yielding items that become user turns, but `trigger_loop` submitted every item as `str(result)`, so text was all a trigger could ever send. A trigger that wanted the agent to *look* at something had no way to say so; the only workaround was reaching a UI reference through `ui_factory` to stage `pending_attachments` by hand. An item may now also be a `TriggerMessage(text, attachments)` — a `NamedTuple`, so a bare `(text, attachments)` tuple works without importing anything — whose attachments are staged on the UI and drained by the same `submit_user_message` path `/attach` and `/photo` use. That means the attachments accept whatever those commands accept: a file path, resolved and size-checked and PDF-extracted and image-scaled at submit time, or an already-built `BinaryContent`. Attachments without text are valid (`TriggerMessage(attachments=[photo])` submits an empty turn carrying the image), and an item with neither text nor attachments is skipped, so a voice trigger can yield its transcription unguarded and silence costs nothing. Plain strings behave exactly as before. Running the loops moved out of `BaseUI` into a `BaseUITriggers` part, re-exposed as the same `trigger_loop` method, which drops `ui.py` from 1330 lines to 1307 and tightens its facade budget to match. The new `examples/chat-gpio-ptt/` drives the built-in chat task from two Raspberry Pi buttons — one push-to-talk, one that attaches a camera frame to the turn it was held for — and is the worked version of all of the above.
