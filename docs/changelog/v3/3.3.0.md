## 3.3.0 (September 13, 2026)

- **Fix: upload storage names, Windows write safety, trigger teardown, and two wrong install commands** (`src/zrb/runner/chat/chat_api_route.py`, `src/zrb/llm/ui/base/triggers.py`, `examples/chat-gpio-ptt/{README.md,zrb_init.py}`, `examples/chat-telegram/README.md`, `test/architecture/test_posix_mode_assertions.py`, `test/runner/chat/*`): the upload write's non-POSIX branch opened the destination by path with no `O_EXCL`, so a planted entry could be followed or truncated; it now creates the file exclusively, the part Windows can guarantee without `dir_fd` or `O_NOFOLLOW`. The stored filename no longer carries the client's: only a length-capped, character-checked extension survives, so control characters, NULs, reserved device names and over-long names never reach the filesystem; the original is returned as a display name. `save_uploaded_attachment`'s expected failures map to a status at the route boundary — `ValueError` to 400, `OSError` (ENOSPC, EACCES, ENAMETOOLONG) to 507 — instead of a 500. `trigger_loop` now closes the async iterator it drives in a `finally`, so a generator holding a socket or subscription is released at cancellation rather than at collection, and re-raises `CancelledError` instead of swallowing it (which made a cancelled background task look finished); its attachment rollback removes the items it staged by identity rather than deleting a tail slice of a list `/attach`, `/photo` and every other trigger share. Both examples said `pip install zrb[llm]`, an extra `pyproject.toml` does not define — the GPIO one needs `zrb[voice]` for vosk and sounddevice, the Telegram one no extra. A new architecture test targets the recurring cause of Windows-only CI failures: a test asserting POSIX permission bits must carry a platform guard, since there `os.chmod` toggles only the read-only flag and directories report 0o777 regardless.
- **Fix: four input-handling defects on the chat API and the trigger loop** (`src/zrb/runner/chat/chat_api_route.py`, `src/zrb/llm/ui/{trigger.py,base/triggers.py}`, `test/runner/chat/{conftest,test_chat_api,test_chat_api_uploads}.py`, `test/llm/ui/base/test_base_ui.py`): (1) The attachment route called `await file.read()` with no argument before checking `LLM_MAX_ATTACHMENT_BYTES`; Starlette spools the multipart body to disk, but that read materialized it as one `bytes`, so an oversized upload was allocated whole before rejection. It now reads one byte past the cap and refuses on overflow. (2) `save_uploaded_attachment` validated the upload directory by path, then opened the file inside it by path, leaving a window for a local user to swap the directory for a symlink; the write now happens relative to a descriptor on the validated directory with `O_NOFOLLOW`/`O_EXCL` (POSIX only — Windows has neither `dir_fd` nor the flags and keeps the by-path write). (3) `post_chat_message` accepted any JSON value for `message` and sliced it for logging, so `{"message": null}` or `{"message": 123}` returned 500 (`TypeError`) instead of 400. (4) `BaseUITriggers._split` treated every tuple as `(text, attachments)`: a 3-tuple lost its third element silently, a bare string in the attachments slot became a list of characters, and `None` or an int raised out of `list()`, which ended the trigger for good. A tuple must now be exactly two elements with a non-string sequence of attachments (`None` reads as none, matching `TriggerMessage`'s default); a malformed item is reported against that item alone and the loop carries on, since one bad item from a button or queue must not stop every later one. Upload tests moved to their own module with shared app/client fixtures in `conftest.py`, keeping `test_chat_api.py` under the 500-line split rule.
- **Fix: a chat session id from the request path could place uploads outside the upload root** (`src/zrb/runner/chat/chat_api_route.py`, `test/runner/chat/test_chat_api_uploads.py`): `save_uploaded_attachment` joined `session_id` — the `{session_id}` path parameter of `POST /api/v1/chat/sessions/{session_id}/attachments`, straight off the request — into the upload path unvalidated, while `filename` was already reduced to a basename. `session_id=".."` resolved the upload directory to the shared temp directory itself, so bytes landed outside the per-session root and the directory's mode was reset to 0700, locking every other user on the machine out. The id now goes through `to_safe_filename` (alphanumerics, `-` and `_` — what `get_random_name` and the `<parent>-sub-<agent>-<id>` delegated form already produce, both verified to survive unchanged), an empty result is rejected, and the joined path is asserted to sit directly under the root in case that helper's contract loosens. A parametrized test over `..`, `.`, nested traversal, an absolute path, mixed separators and an empty id asserts containment and an untouched temp-directory mode.
- **Fix: the GPIO example reused one photo path, and web-chat uploads trusted a fixed temp directory** (`examples/chat-gpio-ptt/{zrb_init.py,README.md}`, `src/zrb/runner/chat/chat_api_route.py`, `test/runner/chat/test_chat_api.py`): `capture_photo` wrote every frame to the same `zrb-gpio-photo.jpg` in shared temp and yielded that path. An attachment path is read when the turn reaches the model (`normalize_attachments` in `agent/run/prompt_content.py`, not at submit time), so a second press while the first turn was queued handed the first turn the second photo; and a fixed name in shared temp can be pre-created by a local user as a symlink to redirect the write. Each capture now gets its own `tempfile.mkstemp` file: unique, created atomically, mode 0600. The path is kept rather than switched to `BinaryContent`, because `normalize_attachments` passes a `BinaryContent` through untouched — no size check, no image scaling — so a full-resolution frame would count against the attachment limit whole; the example's docstring and README, which said resolution happened at submit time, are corrected. `save_uploaded_attachment` had the same fixed-name pattern, building `<tmp>/zrb_web_chat_uploads/<session>` with `makedirs(exist_ok=True)` and no check, so a symlinked root received every web-chat upload. It now creates each level 0700 and refuses a root that is not a real directory owned by the current user, mirroring the existing guard in `llm/agent/spill.py::_ensure_root`.
- **Fix: a failed trigger submission no longer leaves its attachments staged for the next turn** (`src/zrb/llm/ui/base/triggers.py`, `test/llm/ui/base/test_base_ui.py`): `trigger_loop` extends `pending_attachments` and then calls `submit_user_message`, which drains the list only after echoing the message, and not at all if the submission raises. Under `MultiUI` the echo broadcasts to every child, so an erroring backend (a Telegram send, an SSE write) raises before the drain, and the attachments survive into the next turn — a camera frame from a failed GPIO trigger could arrive attached to a message typed minutes later. Staging is now transactional: the loop records the list length before extending and truncates back to it on failure, exact because nothing awaits in between. Reproduced against the real `BaseUI` with a raising `submit_user_message` and pinned by a regression test.
- **Refactor: four `BaseUI` state parts are public attributes instead of 22 forwarders** (`src/zrb/llm/ui/base/{ui,voice_state,confirmation_state,persona_state,usage}.py`, `src/zrb/llm/ui/default/{output,keybindings,lifecycle,agent_picker}.py`, `AGENTS.md`, `test/architecture/test_facade_size_budget.py`, 14 test modules): `BaseUIVoiceState` holds four fields and `BaseUI` wrapped them in eight property accessors so `keybindings.py` could write `ui.voice_mode_active`; `BaseUIConfirmationState`, `BaseUIPersonaState` and `BaseUIUsage` had the same shape. The convention required a part to reach the owner's state only through a public property, so every field a sibling part touched became a permanent public name on `BaseUI` — 60 of its 102 public names had no caller outside `llm/ui`. The four parts are now `self.voice`, `self.confirmation`, `self.persona` and `self.usage`, reached as `ui.voice.mode_active` and `ui.confirmation.current`; `UIOutput`'s second-level `current_confirmation` forwarder went too, as did two hand-rolled copies of the shape in the test doubles. `BaseUI.accumulate_usage` stays a named method: `docs/llm/llm-custom-ui.md` lists it as an enrichment hook and `MultiUI`/`BufferedUI` implement it. The `getattr(ui, "voice_mode_active", False)` shims for non-`BaseUI` implementations now reach the part (`getattr(ui, "voice", None)`), so `StdUI` and `MultiUI` are unaffected. `AnyUI` is untouched at 16 methods, and `SimpleUI`/`EventDrivenUI` — the documented extension levels — keep their 8 and 7. `ui.py` drops 1307 → 1206 lines and 102 → 89 public names, its facade budget tightens to match, and repo-wide pure delegators fall from 636 to 621.
- **Chore: the coverage gate is 94%** (`zrb-test.sh`, `AGENTS.md`, `docs/adr/{adr-0034,README}.md`, `docs/contributing/maintainer-guide.md`, `docs/advanced-topics/testing-tasks.md`): the full run has measured above 94% for some time, so `--cov-fail-under` now sits at that number rather than four points below, where a real regression could hide. Every statement of the old bar — ADR-0034's title and Decision, its index entry, the maintainer guide's gate table, the testing guide, and AGENTS.md's test principles — now says 94. Scoped runs (`./zrb-test.sh <path>`) still skip the gate, since they exercise only part of the tree.
- **Refactor: the agent barrel resolves lazily, and import safety is asserted per module** (`src/zrb/llm/agent/__init__.py`, `test/architecture/test_circular_import_allowlist.py`, `.coveragerc`, `AGENTS.md`, `docs/llm/llm-chat-lifecycle.md`, `docs/adr/{adr-0086,adr-0088,adr-0096}.md`): a package `__init__` runs before any of its submodules, so `zrb/llm/agent/__init__.py`'s four eager re-exports loaded `common.py`, `run/runner.py` and `summarizer.py` — and through them most of `zrb.llm` — whenever *anything* under `zrb.llm.agent` was imported. Over the module graph (`if TYPE_CHECKING:` excluded), the tree's largest strongly connected component was 87 modules spanning `llm.tool`, `llm.ui`, `llm.agent`, `llm.task`, `runner.chat` and `runner.cli`. Deferring each barrel in turn showed it was almost entirely this file: `zrb.llm.agent` lazy gives 23, `zrb.llm.ui` 82, `zrb.llm.tool` 87 (no change — which is why restoring it to eager in 2.67.0 was right). The blocker was the safety net: `test_every_package_imports_with_its_parents_stubbed` imported 27 packages and nothing deeper, reaching the other 419 modules only through their barrels' re-exports, so making any barrel lazy silently shrank the check. It now parametrizes over every name an `import` statement can spell — 444 targets, the 417 modules plus the 27 packages, excluding the hyphenated skill tool scripts under `llm_plugin/*_skills/<skill>/tools/`. Both halves are needed: a stubbed-parent import of `zrb.llm.agent.common` never runs `zrb/llm/agent/__init__.py`, so the now-lazy barrel is covered only by naming the package itself. The agent barrel resolves through PEP 562 `__getattr__`, caching into `globals()`, with names mirrored under `if TYPE_CHECKING:` for pyright; `hook_agent`'s builder registration moved into that `__getattr__`, firing on first use of an agent name instead of on package load — still before any hook-manager read, since every entry point resolves one of the four while building its agent. Import spellings are unchanged: `from zrb.llm.agent import create_agent` is an attribute access, which `__getattr__` answers, and all 14 call sites are untouched. Net: largest SCC 87 → 23, modules in any cycle 102 → 23, `zrb.llm.agent`'s eager closure 338 of 447 modules → 1, isolated-import coverage 27 packages → 417 modules (+392 tests, 5,774 → 6,166). `import zrb` is unchanged at 0.22s — the win is structural. `.coveragerc`'s skill-tool-script omit, which named only `skills/`, now also names `core_skills/`, a gap the per-module check surfaced. See ADR-0096.
- **Feature: a chat trigger can attach files and photos, not just text** (`src/zrb/llm/ui/trigger.py`, `src/zrb/llm/ui/base/triggers.py`, `src/zrb/llm/ui/{__init__,base/ui}.py`, `src/zrb/{__init__.py,llm/task/chat/task.py}`, `examples/chat-gpio-ptt/`, `examples/README.md`, `test/llm/ui/base/test_base_ui.py`, `test/architecture/test_facade_size_budget.py`): `LLMChatTask(triggers=[...])` lets an external source — a GPIO button, a webhook, a message queue — drive a chat session by yielding items that become user turns, but `trigger_loop` submitted every item as `str(result)`, so a trigger could send only text; the only workaround was reaching a UI reference through `ui_factory` to stage `pending_attachments` by hand. An item may now also be a `TriggerMessage(text, attachments)` — a `NamedTuple`, so a bare `(text, attachments)` tuple works without an import — whose attachments are staged on the UI and drained by the same `submit_user_message` path `/attach` and `/photo` use, accepting what those accept: a file path (resolved, size-checked, PDF-extracted and image-scaled at submit time) or a built `BinaryContent`. Attachments without text are valid (`TriggerMessage(attachments=[photo])` submits an empty turn carrying the image), and an item with neither is skipped, so a voice trigger can yield its transcription unguarded. Plain strings behave as before. Running the loops moved from `BaseUI` into a `BaseUITriggers` part, re-exposed as the same `trigger_loop` method, dropping `ui.py` from 1330 to 1307 lines and tightening its facade budget. The new `examples/chat-gpio-ptt/` drives the built-in chat task from two Raspberry Pi buttons — one push-to-talk, one attaching a camera frame to the turn it was held for — as the worked example.
