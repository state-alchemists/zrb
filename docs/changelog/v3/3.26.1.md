## 3.26.1 (October 25, 2026)

- **Feature: a dictated turn says how long it spoke and whether it cut in** (`src/zrb/llm/input_source.py`, `src/zrb/llm/dictation/feature.py`): the listener already knew — `Utterance` carries `started_at`, `ended_at`, `is_barge_in` (it paused zrb's speech) and `is_over_speech` (any of it was said over zrb's voice) — but the turn kept only the channel, the modality and the tone, one line before the model read it. A message that interrupted a reply therefore arrived indistinguishable from one spoken into silence, which is the single fact a resumed agent most needs and cannot recover from the transcript. The live-context line now names it: `- Input: user via microphone/dictation, sounding tired (0.81), 6.4s spoken, talked over the reply`, with `partly over the reply` for words that crossed zrb's voice without pausing it. Those are different facts and are read differently: one paused the reply, the other did not.

- **Feature: a message says how long the chat was quiet before it** (`src/zrb/llm/input_source.py`, `src/zrb/llm/ui/base/message_queue.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/multi_ui.py`): a turn carries no timestamp of its own, so a reply to a sentence the model has just read and a reply to one written an hour earlier looked like the same act, and the interval — the half of "time" the transcript never had — could only be guessed from a clock reading per turn. `MessageQueue` now records when each turn finished, and the next submission measures the gap into `InputProvenance.idle_seconds`, rendered as `- Input: user via keyboard, after 3m14s of silence`. Two shapes would otherwise lie: a message submitted *while* a turn is running measures from the end of the turn before it, which can be hours old while the model has been working for seconds, so no gap is reported while `turn_started_at` is set; and the keystroke path (`submit_message`) had been passing `None` for the source, so an ordinary typed turn carried no provenance at all — it now defaults to `KEYBOARD_INPUT`, while the callers that submit something other than the user's own words (a subagent's report, a startup message, an unnamed backend channel) pass `None` explicitly and keep none. The record lives on the queue rather than in a module global, so two chat sessions in one process do not read each other's silences, and nothing is measured before a session's first turn, which leaves the paste-merge rule that compares against `KEYBOARD_INPUT` unchanged.

- **Fix: a correct write outside any project is no longer reported as broken** (`src/zrb/llm/tool/post_write_check.py`, `src/zrb/llm/lsp/manager_lifecycle.py`, `src/zrb/llm/lsp/manager.py`, `test/llm/tool/test_post_write_check.py`): since 2.30.2a1 the post-write check asked the language server about every file it wrote, and outside a project there is no import graph to resolve against, so a helper in `/tmp` came back with `Import "zrb.llm.tool" could not be resolved` — a fact about where the file sits, not what was written — and `Write` reported a correct file as `FAILED`. The server is still asked everywhere, because for a language with no static fallback here (JavaScript, TypeScript, C++) it is the only thing that can see a parse error; what changed is that outside a project the diagnostics describing the file's *surroundings* are dropped — unresolved imports, missing includes, missing type definitions, recognised by LSP code or wording — while an intrinsic parse or syntax error is kept, and an unrecognised message is kept too, since noise is recoverable and a hidden syntax error is not. `LSPManager.has_project_context` decides which rule applies, through a new fallback-free `LSPManagerLifecycle.detect_project_marker_root`; `detect_project_root` keeps its fallback and cache. The `ast`/`pyflakes` check is unchanged, so a syntax error or undefined name in Python still fails anywhere.

- **Fix: a journal write says which HUD line the section cap evicted** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_hud_pinning.py`): `_cap_section_entries` kept the newest `LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION` lines under a root-index section and returned text alone, so an older one-line constraint vanished while the call still answered `Wrote technical/x.md` — migrating eight constraints into a section already at its cap dropped eight others in silence. The capper now returns the text with the lines it dropped, and `WriteJournalNote` appends `Evicted from ## Active Constraints (cap 20): "<line>" — re-pin with pinned=True or raise LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION.` to that result. A write that evicts nothing returns the same string as before.

- **Feature: `pinned=True` holds a HUD line through the section cap** (`src/zrb/llm/tool/journal_write.py`): `WriteJournalNote` gained a `pinned` keyword. A pinned line carries a `📌 ` marker in the index line, and the cap evicts the oldest unpinned line first, dropping a pinned one only when every line in its section is pinned — so a section of pinned constraints may stay over the cap rather than lose one. The marker travels in the line because the capper only ever reads index text, never the note file; a marker echoed back in a revision is stripped, so the argument decides the pin state. `DeleteJournalNote` still removes the line, marker included.

- **Feature: `journal_transaction` batches journal changes under one lock and one commit** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_transaction.py`): each tool's body became a lock-free, commit-free `_log_activity_locked` / `_write_note_locked` / `_delete_note_locked` returning exactly the string the tool returns; `journal_transaction(message=None)` enters the journal lock once and commits once at the end with `message or "batch: N change(s)"`, committing nothing when the body changed nothing. A body that raises makes no commit: every file it touched is put back as it was — the bytes it held, or its absence — before the exception continues. The snapshot is taken by the writes themselves rather than from git, because git has no baseline for an ignored or untracked note; it starts once the journal is open, so the tree and repository a first-time journal needs, and the root index an older one needs, are setup rather than body writes. Only files the body touched are restored, so a journal somebody had already edited keeps its own edits. It is a Python seam for scripts and imports, not a model-facing tool: the model keeps writing one note per call, because each write has to be confirmed by its own result.

- **Fix: two notes that pin the same words keep one line each** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_hud_pinning.py`): `_is_own_hud_line` fell back to matching the line's text for *any* line whose wording matched, so a note whose supplied `hud_line` echoed the line it had read from the index — `([note](…))` and all — deleted the other note's HUD entry and inherited its link. The fallback now applies only to a line carrying no note link at all; a line linked to another note is that note's, however alike the words. A supplied line that reproduces an existing one — same prose, same trailing link — is treated as a line read back from the index, so that link is dropped instead of being copied onto the new note's own line.
