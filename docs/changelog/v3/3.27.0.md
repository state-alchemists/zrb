## 3.27.0 (October 26, 2026)

- **Feature: `ZRB_LLM_SPEECH_PLAYER_PREBUFFER_SECONDS` starts each sentence on a cushion of audio** (`src/zrb/llm/speech/pcm_player.py`, `src/zrb/llm/speech/config.py`, `src/zrb/llm/speech/player.py`, `src/zrb/config/mixins/llm_speech.py`, `docs/configuration/llm-voice-camera.md`, `test/llm/speech/test_pcm_player_prebuffer.py`): the device started playing a sentence on a hardcoded tenth of a second of audio, which is fine for an engine that keeps up and is not for one that does not. The local `pocket` engine is fast on average and spiky at the edges — 4,793 decoded chunks in one session, a median 15 ms to make 80 ms of audio, but 5% of them slower than realtime and the worst 675 ms — and the spikes are what a thin cushion cannot absorb: the sentence starts, the engine stalls, the device asks for a block nothing is standing by to fill, and the listener hears the word's beginning clipped. The cushion is now a setting, defaulting to `0.4` seconds, which covers the 200-450 ms spikes measured in the minutes under load and costs that pause before each sentence's first word; `0` starts on whatever has arrived. The wait that holds playback off for the cushion had to grow with it — it was a flat second, which would have capped any cushion above about half a second back to itself, silently under-delivering on exactly the loaded machine the setting is for — so it is now twice the cushion and never under a second. The stutter line names both levers, cushion first. `SpeechConfig.player_prebuffer_seconds` mirrors the setting for callers that build a speaker themselves, and the tests pin that a 400 ms stall in the source is heard on a tenth of a second and no longer heard on four tenths. Two things the setting met on the way out: a cushion of zero must still wait for the first audio, or the device opens the sentence on silence it counts as a stutter; and the read ahead is a count of chunks, which cannot bound a cushion counted in seconds, so the reader now keeps filling while the cushion is still short — a backend streaming small chunks would otherwise stop at `_read_ahead` chunks, and the sentence would start under its cushion once the wait ran out.

- **Feature: `ZRB_LOGGING_FILE` keeps the log lines a repainting terminal loses** (`src/zrb/config/log_file.py` new, `src/zrb/config/mixins/foundation.py`, `src/zrb/__main__.py`, `docs/advanced-topics/logging.md`, `docs/configuration/env-vars.md`, `test/config/test_log_file.py`): zrb configured a `StreamHandler` and nothing else, so every internal warning existed only as a line on stderr. Where stderr is a repainting full-screen UI that is not a record — the chat paints over its own log lines with the next frame — which is how a speech stutter reproducible only "while the machine is busy" stayed undiagnosed for weeks: the player had been counting and naming those underruns all along, into a screen that erased them. `ZRB_LOGGING_FILE` adds a `RotatingFileHandler` to `CFG.LOGGER` at CLI startup, before any init source loads, so startup warnings are kept too; `ZRB_LOGGING_FILE_LEVEL` sets the file's own verbosity so it can carry `DEBUG` while the screen stays quiet — which needs the logger's level lowered too, since a logger drops a record before any handler sees it, so every other handler is pinned to the level the terminal had; `_handle_uncaught` now gates its traceback on `ZRB_LOGGING_LEVEL` rather than the logger's level, so a file asking for `DEBUG` cannot turn a failed task into a raw traceback., and `ZRB_LOGGING_FILE_MAX_BYTES` / `ZRB_LOGGING_FILE_BACKUP_COUNT` bound it at 10 MiB and three backups (0 never rotates). File lines carry the logger name as well, because a file is read out of context. Empty (the default) writes nothing, the directory is created when missing, an unopenable file is reported rather than fatal, and installing twice adds no second handler.

- **Feature: a dictated turn says how long it spoke and whether it cut in** (`src/zrb/llm/input_source.py`, `src/zrb/llm/dictation/feature.py`): the listener already knew — `Utterance` carries `started_at`, `ended_at`, `is_barge_in` (it paused zrb's speech) and `is_over_speech` (any of it was said over zrb's voice) — but the turn kept only the channel, the modality and the tone, one line before the model read it. A message that interrupted a reply therefore arrived indistinguishable from one spoken into silence, which is the single fact a resumed agent most needs and cannot recover from the transcript. The live-context line now names it: `- Input: user via microphone/dictation, sounding tired (0.81), 6.4s spoken, talked over the reply`, with `partly over the reply` for words that crossed zrb's voice without pausing it. Those are different facts and are read differently: one paused the reply, the other did not.

- **Feature: a message says how long the chat was quiet before it** (`src/zrb/llm/input_source.py`, `src/zrb/llm/ui/base/message_queue.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/multi_ui.py`): a turn carries no timestamp of its own, so a reply to a sentence the model has just read and a reply to one written an hour earlier looked like the same act, and the interval — the half of "time" the transcript never had — could only be guessed from a clock reading per turn. `MessageQueue` now records when each turn finished, and the next submission measures the gap into `InputProvenance.idle_seconds`, rendered as `- Input: user via keyboard, after 3m14s of silence`. Two shapes would otherwise lie: a message submitted *while* a turn is running measures from the end of the turn before it, which can be hours old while the model has been working for seconds, so no gap is reported while `turn_started_at` is set; and the keystroke path (`submit_message`) had been passing `None` for the source, so an ordinary typed turn carried no provenance at all — it now defaults to `KEYBOARD_INPUT`, while the callers that submit something other than the user's own words (a subagent's report, a startup message, an unnamed backend channel) pass `None` explicitly and keep none. The record lives on the queue rather than in a module global, so two chat sessions in one process do not read each other's silences, and nothing is measured before a session's first turn, which leaves the paste-merge rule that compares against `KEYBOARD_INPUT` unchanged.

- **Fix: a correct write outside any project is no longer reported as broken** (`src/zrb/llm/tool/post_write_check.py`, `src/zrb/llm/lsp/manager_lifecycle.py`, `src/zrb/llm/lsp/manager.py`, `test/llm/tool/test_post_write_check.py`): since 2.30.2a1 the post-write check asked the language server about every file it wrote, and outside a project there is no import graph to resolve against, so a helper in `/tmp` came back with `Import "zrb.llm.tool" could not be resolved` — a fact about where the file sits, not what was written — and `Write` reported a correct file as `FAILED`. The server is still asked everywhere, because for a language with no static fallback here (JavaScript, TypeScript, C++) it is the only thing that can see a parse error; what changed is that outside a project the diagnostics describing the file's *surroundings* are dropped — unresolved imports, missing includes, missing type definitions, recognised by LSP code or wording — while an intrinsic parse or syntax error is kept, and an unrecognised message is kept too, since noise is recoverable and a hidden syntax error is not. `LSPManager.has_project_context` decides which rule applies, through a new fallback-free `LSPManagerLifecycle.detect_project_marker_root`; `detect_project_root` keeps its fallback and cache. The `ast`/`pyflakes` check is unchanged, so a syntax error or undefined name in Python still fails anywhere.

- **Refactor: the journal indexes are rendered from the notes, and a hand-written line in one is left alone** (`src/zrb/llm/tool/journal_write.py`, `src/zrb/llm/tool/journal_index.py`, `src/zrb/llm/tool/journal_index_migration.py`, `src/zrb/llm/tool/journal_note.py`, `test/llm/tool/test_journal_index_render.py`, `test/llm/tool/test_journal_index_migration.py`, `test/llm/tool/test_journal_note.py`, `docs/adr/adr-0055.md`, `docs/technical-specs/llm-context.md`): `index.md` was both the store and the view, edited as text by about twenty-five helpers, while a note's status lived in its frontmatter and its pin lived only in the index, so every fix in the last round was two files claiming one fact. A note's frontmatter now holds `hud_line`, `pinned` and `updated` beside `status` and `applies_when`, and one render produces the HUD sections (capped as before, oldest and unpinned first), the `Recent Insights` catalog and every category index from the notes, so a write, supersede, delete or refile changes the note and renders again, and rendering twice yields the same bytes. A line in a generated region that no note accounts for (no link to a note that owns a line) is a hand edit: it is kept in place, never evicted, and not counted toward the cap. A journal written earlier is migrated on its first call by reading each pin and line into the note it links, and `journal_write.py` shrank from 1568 to about 950 lines. Behaviour changes: revising a note now refreshes its place in the cap order, an unlinked line identical to a new `hud_line` is kept beside it instead of replaced, and an evicted line comes back if the cap is raised.

- **Fix: a journal write says which HUD line the section cap evicted** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_hud_pinning.py`): `_cap_section_entries` kept the newest `LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION` lines under a root-index section and returned text alone, so an older one-line constraint vanished while the call still answered `Wrote technical/x.md` — migrating eight constraints into a section already at its cap dropped eight others in silence. The capper now returns the text with the lines it dropped, and `WriteJournalNote` appends `Evicted from ## Active Constraints (cap 20): "<line>" — re-pin with pinned=True or raise LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION.` to that result. A write that evicts nothing returns the same string as before.

- **Feature: `pinned=True` holds a HUD line through the section cap** (`src/zrb/llm/tool/journal_write.py`): `WriteJournalNote` gained a `pinned` keyword. A pinned line carries a `📌 ` marker in the index line, and the cap evicts the oldest unpinned line first, dropping a pinned one only when every line in its section is pinned — so a section of pinned constraints may stay over the cap rather than lose one. The marker travels in the line because the capper only ever reads index text, never the note file; a marker echoed back in a revision is stripped, so the argument decides the pin state. `DeleteJournalNote` still removes the line, marker included.

- **Feature: `journal_transaction` batches journal changes under one lock and one commit** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_transaction.py`): each tool's body became a lock-free, commit-free `_log_activity_locked` / `_write_note_locked` / `_delete_note_locked` returning exactly the string the tool returns; `journal_transaction(message=None)` enters the journal lock once and commits once at the end with `message or "batch: N change(s)"`, committing nothing when the body changed nothing. A body that raises makes no commit: every file it touched is put back as it was — the bytes it held, or its absence — before the exception continues. The snapshot is taken by the writes themselves rather than from git, because git has no baseline for an ignored or untracked note; it starts once the journal is open, so the tree and repository a first-time journal needs, and the root index an older one needs, are setup rather than body writes. Only files the body touched are restored, so a journal somebody had already edited keeps its own edits. It is a Python seam for scripts and imports, not a model-facing tool: the model keeps writing one note per call, because each write has to be confirmed by its own result.

- **Fix: two notes that pin the same words keep one line each** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_hud_pinning.py`): `_is_own_hud_line` fell back to matching the line's text for *any* line whose wording matched, so a note whose supplied `hud_line` echoed the line it had read from the index — `([note](…))` and all — deleted the other note's HUD entry and inherited its link. The fallback now applies only to a line carrying no note link at all; a line linked to another note is that note's, however alike the words. A supplied line that reproduces an existing one — same prose, same trailing link — is treated as a line read back from the index, so that link is dropped instead of being copied onto the new note's own line.

- **Fix: a speech service that stopped is replaced, instead of answering every later sentence with silence** (`src/zrb/llm/speech/pipecat_tts.py`, `src/zrb/llm/speech/backend/pipecat.py`, `src/zrb/llm/speech/backend/any_speech_backend.py`, `src/zrb/llm/speech/player.py`, `test/llm/speech/test_pipecat_tts.py`, `test/llm/speech/backend/test_pipecat_backend.py`): Pipecat marks a service unusable after three consecutive TTS contexts that produce no audio, and then refuses every sentence it is given. Measured on one stalled reply, the three contexts closed without audio while their audio only materialised about twenty seconds later, generation stepping at 262–534 ms instead of ~20 ms — and the remaining 36 sentences of that reply were each reported as one more failed render with the session mute until the next turn rebuilt the pipeline. `TTSPipeline.speak` now raises `SpeechServiceStopped` when the service behind it has stopped, and `PipecatSpeechBackend` lets that pipeline go, so the next sentence starts a fresh service and reloads its model instead of asking a dead one again. `Speaker.restart_backends` also names what it was answering — `Replacing the speech backend after N sentence(s) it could not render` — because a replacement that leaves no line is a silence that cannot be diagnosed.

- **Feature: journal search ranks by what a file is, and reads a question as words** (`src/zrb/llm/tool/journal.py`, `test/llm/tool/test_journal.py`): `SearchJournal` took a regex, so a question was matched as one literal string — measured on eight questions about notes that exist, 0 were found, and the one flat list it returned for a keyword put the right note about seventh, behind 30–58 rows of which several were `index.md` or the activity log. Several plain words are now a query: the words that say nothing about the subject are dropped, the matches are grouped per file, and files are ranked by what they are — a note whose title carries the words, another note, an index, the activity log — then by how many words they hold. The same eight questions now find the note 8 of 8 times, in the top three 7 of 8, in at most 15 rows. Several words mean *any* of them, not all of them, and that is a measurement rather than a preference: requiring every word found 2 of the 8 against 8 of 8, because a question is prose and no note repeats its words verbatim — the precision comes from the ranking instead, which puts the file holding more of the words first, and a test pins the difference so the AND gate is not quietly reintroduced as a fix. `did_you_mean` was dead as well: it compared the whole query to whole titles through `difflib` at a 0.6 bar, where a six-letter word against a ninety-character title scores about 0.12, so the one mechanism meant to turn a zero-hit search into a lead answered nothing, for every realistic query — it now matches the query's words against titles and file names, so a zero hit still names somewhere to look.

- **Feature: the index splits by owner and by firmness, and a note says when it stops applying** (`src/zrb/llm/tool/journal_write.py`, `src/zrb/llm/tool/journal.py`, `test/llm/tool/test_journal_hud_sections.py`, `test/llm/tool/test_journal_hud_pinning.py`, `test/llm/tool/test_journal_note_expiry.py`): the injected HUD held every `projects` and `technical` headline in one 20-line queue called `## Active Constraints`, and filed the user's preferences and the agent's own standing rules together under `## Preferences` — two headings that each mixed what they promised. It is now `## User` (who the user is, and how they want to be worked with), `## Constraints` (a fact that must keep holding; a pinned `projects`/`technical` line goes here), `## Agent` (who the agent is), and `## Recent` (a headline that may age out). The category decides the section (`pinned` only moves a `projects`/`technical` line from `## Recent` to `## Constraints`), and a line moves rather than copies when pinning it changes its section. Every note's frontmatter now carries `applies_when` — the condition under which the finding still holds — and `status`; a write that names no condition is told so in its result, because a note that cannot say when it stops applying can never be retired, only re-read. The new `SupersedeJournalNote` retires one: the file stays as evidence, marked `status: superseded` with the reason in its `## History`, and its line leaves the index in the same call. Migrating an older index moves `## Preferences` into `## User` and `## Active Constraints` into `## Recent`, keeping every line.

- **Fix: a journal tool called from inside a journal write re-enters the lock** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_transaction.py`): the root lock is a file lock, so a tool called from a `journal_transaction` body — or any helper that logs after writing — waited the whole `LLM_JOURNAL_LOCK_TIMEOUT` and then failed with "journal is busy", a message about another writer when the writer was the caller itself. The lock is now re-entered on the thread that already holds it: nested calls share the outermost one's lock and its single commit, and a lock held by another process still costs a wait rather than an immediate failure.

- **Fix: a journal tool called inside a transaction no longer commits on its own** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_transaction.py`): `journal_transaction` promises one commit, and none at all when its body raises. A public tool called inside the body committed immediately instead — the change reached history before the transaction ended, and the transaction's own commit was then skipped entirely whenever the body used tools rather than the transaction object, so `batch` never appeared and the writes arrived as one commit each; on a rollback the files went back while those commits stayed, and the inverse deletion sat in the working tree. A tool now hands its change to the open transaction (`_commit_or_defer`) and the body commits once, under its own message. Nesting two transactions is refused with a message saying what to do instead: the snapshot is one per thread, so a nested block would discard the outer one's and the outer body could no longer put back what it had changed — a loud error where before the rollback merely lied.

- **Fix: `SupersedeJournalNote` reaches the model** (`src/zrb/llm/common_tools.py`, `src/zrb/builtin/llm/chat.py`, `src/zrb/llm/prompt/live_context.py`, `src/zrb/config/mixins/llm_content.py`, `test/llm/test_common_tools.py`): the retirement tool shipped documented in the journal prompt and named in three tool descriptions, and was never registered in `zrb.llm.common_tools` — so the journal could describe how to retire a stale note and give the model no way to do it, which is exactly the stale line the feature exists to remove. It is now registered with the other journal writers under `LLM_JOURNAL_ENABLED`, tagged `EDIT` like them, deferred for the main agent like them, auto-approved in the chat UI like them, and named where the prompt and the settings docs list the journal tools. A slug is free text interpolated into a path, and `supersede` — like `DeleteJournalNote` before it — built that path without the kebab-case check the writer applies, so `../index` reached the root index instead of a note; both now go through the same `_check_slug`. Both are also exported from `zrb.llm.tool`, which listed neither.

- **Improvement: speech's player defaults meet the measured machine, and its synthesis threads ask for scheduling priority** (`src/zrb/config/mixins/llm_speech.py`, `src/zrb/llm/speech/pcm_player.py`, `src/zrb/llm/speech/pipecat_tts.py`, `src/zrb/llm/util/priority.py` new, `docs/configuration/llm-voice-camera.md`, `test/llm/util/test_priority.py`, ADR-0131): a loaded session's log held 38 `Speech stuttered:` warnings and every one was the device left un-fed by a single block of 1024 frames while Pocket took 8–43 seconds to generate a few seconds of audio — sentences generated while the same chat ran its own tools, the same backend rendering in 1–2 seconds minutes later without one stutter. The defaults take what the log asked for: `ZRB_LLM_SPEECH_PLAYER_BLOCK_FRAMES` 1024 → 2048 (twice the callback's slack, twice as few asks), `ZRB_LLM_SPEECH_PLAYER_PREBUFFER_SECONDS` 0.4 → 0.5 (headroom over the measured start spikes, ~100 ms more pause before a sentence's first word), `ZRB_LLM_SPEECH_PLAYER_READ_AHEAD` 32 → 64 (≈5 s of chunks bridging the bursty-but-on-average-faster case in memory). What no cushion answers — a generator tens of seconds behind its own playback — is scheduling, not buffering: `raise_priority` runs once on the TTS pipeline thread and on each sentence's source-reader thread, asking unprivileged where an ask exists (macOS: the thread's own QoS class, user-initiated; POSIX: `setpriority(PRIO_PROCESS, 0, -5)`, which Linux answers per-thread and the unprivileged caller is declined — Termux with it) and declining silently everywhere else (EPERM, a library that will not load, Windows), so speech keeps speaking at whatever priority the machine grants and nobody must configure the ask to keep it from doing something else.

- **Fix: a refused journal write leaves nothing behind, and `applies_when` stays one line** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_hud_sections.py`): `WriteJournalNote` checked a note's category and slug only after the journal tree, note file, backlinks and index entries were being written, so a refusal reported failure over a journal it had already changed — and, on a first use, over a journal tree it had just created. Category and slug are now checked before the journal is opened. `applies_when` is model-written text interpolated into the YAML frontmatter, so a multiline value could close the frontmatter early and inject its own `status`; it is now collapsed to a single line. `JournalTransaction.write_note` also accepts `applies_when`, and `SearchJournal` leaves the regex dialect to ripgrep when it is installed, so a pattern valid there (`\p{L}`) is no longer rejected by Python's `re`.

- **Fix: a case-sensitive search ranks by case** (`src/zrb/llm/tool/journal.py`, `test/llm/tool/test_journal.py`): `SearchJournal` matched with `case_sensitive=True` and then ranked with a lowercase fold, promoting a note whose title only matched in lowercase over the one that held the query as written.

- **Fix: a superseded note leaves everything the model is shown** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_note_expiry.py`): `SupersedeJournalNote` removed the note's HUD line but left its `## Recent Insights` catalog link in the root index, which is injected with the rest of it, so a retired note was still announced every turn. The root index now drops both; the category index keeps its link, so the note stays findable as evidence.

- **Fix: `pyright` passes on macOS for the hook process helpers** (`src/zrb/llm/hook/process_io.py`): `os.waitid` is declared for Linux only, so `./zrb-test.sh` failed on a Mac even behind a `hasattr` guard that CI's Ubuntu never needed. The helpers now read it with `getattr` at call time, which behaves the same at runtime on every platform.

- **Docs: the core prompt's waiting rule is two short lines** (`src/zrb/llm/prompt/markdown/workflow.md`): step 2 spent two paragraphs, about 730 characters, on waiting and concurrency. It now says the same in about 460: run independent work at once, reach what blocks through the harness's waiting primitive rather than a long sleep, wait in short increments and stop when the result arrives, and keep chunks that share a file or hang on one choice in sequence.
