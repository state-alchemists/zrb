## 3.27.0 (October 26, 2026)

- **Improvement: speech's player defaults meet the measured machine, and its synthesis threads ask for scheduling priority** (`src/zrb/config/mixins/llm_speech.py`, `src/zrb/llm/speech/pcm_player.py`, `src/zrb/llm/speech/pipecat_tts.py`, `src/zrb/llm/util/priority.py` new, `docs/configuration/llm-voice-camera.md`, `test/llm/util/test_priority.py`, ADR-0131): a loaded session's log held 38 `Speech stuttered:` warnings and every one was the device left un-fed by a single block of 1024 frames while Pocket took 8–43 seconds to generate a few seconds of audio — sentences generated while the same chat ran its own tools, the same backend rendering in 1–2 seconds minutes later without one stutter. The defaults take what the log asked for: `ZRB_LLM_SPEECH_PLAYER_BLOCK_FRAMES` 1024 → 2048 (twice the callback's slack, twice as few asks), `ZRB_LLM_SPEECH_PLAYER_PREBUFFER_SECONDS` 0.4 → 0.5 (headroom over the measured start spikes, ~100 ms more pause before a sentence's first word), `ZRB_LLM_SPEECH_PLAYER_READ_AHEAD` 32 → 64 (≈5 s of chunks bridging the bursty-but-on-average-faster case in memory). What no cushion answers — a generator tens of seconds behind its own playback — is scheduling, not buffering: `raise_priority` runs once on the TTS pipeline thread and on each sentence's source-reader thread, asking unprivileged where an ask exists (macOS: the thread's own QoS class, user-initiated; POSIX: `setpriority(PRIO_PROCESS, 0, -5)`, which Linux answers per-thread and the unprivileged caller is declined — Termux with it) and declining silently everywhere else (EPERM, a library that will not load, Windows), so speech keeps speaking at whatever priority the machine grants and nobody must configure the ask to keep it from doing something else.
