## 3.2.0 (September 12, 2026)

- **Fix: a permanent provider error no longer burns every retry, and per-turn retries no longer multiply** (`src/zrb/task/base/{base_task,execution}.py`, `src/zrb/task/{cmd_task,rsync_task,scaffolder,scheduler,base_trigger,make_task,http_check,tcp_check}.py`, `src/zrb/llm/task/{llm_task,chat/task,chat/execution}.py`, `src/zrb/llm/agent/run/error_classifier.py`, `test/task/base/test_base_task.py`, `test/llm/task/chat/test_llm_chat_task_wiring.py`, `test/llm/agent/run/test_error_classifier.py`): `zrb llm chat` with no `OPENAI_API_KEY` set ran the agent three times and printed the same "Set the `OPENAI_API_KEY` environment variable" message five times. Two independent causes. First, `BaseTask`'s retry loop retried every failure alike, with no way to say a failure was unfixable — `error_classifier.is_retryable_error` already existed and was already used by the agent's own in-run `retry_loop`, but nothing above it consulted anything. `BaseTask` now accepts `retry_if`, a predicate called with the exception whose falsy result skips the remaining attempts; it defaults to `None` (retry everything, the previous behavior) and is forwarded by `CmdTask`, `RsyncTask`, `Scaffolder`, `Scheduler`, `BaseTrigger` and `make_task`. `HttpCheck` and `TcpCheck` deliberately do not take it, for the same reason they fix `retries` at 0. `LLMTask` and `LLMChatTask` default it to the new `error_classifier.retry_unless_permanent`, which refuses only what `is_permanent_error` positively identifies — pydantic-ai's `UserError` (missing credentials, an unresolvable model, a bad agent setup) plus the `authentication_failed`, `model_not_found`, `invalid_request` and `context_length` categories. It is deliberately *not* the inverse of `is_retryable_error`: an LLM provider is intermittently flaky the way HTTP is, so a 429, a 5xx, or anything unrecognized (a connection blip) keeps the retries it had. Second, the inner per-turn `LLMTask` that `LLMChatTask` builds for each turn was constructed without `retries=`, so it silently took `LLMTask`'s default of 2 and multiplied against the outer chat task's own retry loop — a chat declaring `retries=2` ran the agent 3×3 = 9 times, and one declaring `retries=0` still ran it 3 times. The inner task is now fixed at `retries=0`: the outer chat task owns the task-level policy, and the agent's `retry_loop` separately handles transient provider errors inside a single run.
- **Breaking: the stateless data utilities moved under `zrb util`** (`src/zrb/builtin/group.py`, `docs/task-types/builtin-helpers.md`): `zrb` opened on 29 top-level groups, so the first thing a new user saw was a wall in which `llm`, `git` and `python` sat between `hex`, `md5` and `ulid`. The fourteen groups that are stateless data transformations -- they read their input and print a result, touching no network and mutating no store -- are now subgroups of a single `util` group: `base64`, `case`, `cron`, `hash`, `hex`, `json`, `jwt`, `md5`, `number`, `random`, `time`, `ulid`, `url` and `uuid`. That takes the top level from 29 to 15. `http` stays out because `request` performs network I/O, and `todo` stays out because it reads and writes a store under `ZRB_TODO_DIR`; reading a file as *input* is not disqualifying, which is why `hash sum` moved with the rest. Only the CLI path changes: `zrb base64 encode` becomes `zrb util base64 encode`, the task objects and their `from zrb.builtin import ...` names are untouched, and `ZRB_ENABLE_BUILTIN_TASKS=0` still suppresses all of it. There is no alias for the old paths -- `zrb base64 encode` now reports an invalid subcommand.
- **Types: `pyright --strict` is enforced on seven packages, and the first root fixes cleared a quarter of the tree's strict debt** (`pyrightconfig.json`, `src/zrb/{dot_dict,xcom,callback,group,input,session,session_state_logger}`, `src/zrb/util/cli/style.py`): the project type-checks at pyright's `standard` mode, which accepts an unannotated parameter or an unparameterized generic and silently infers `Unknown` -- so "0 errors" was a weaker guarantee than it read as. `pyrightconfig.json` now carries a `strict` array naming the packages held to `strict`, which the existing `pyright src/zrb` call in `zrb-test.sh` already gates; the list is meant to grow one package at a time. Seven are in: `callback`, `dot_dict`, `group`, `input`, `session`, `session_state_logger` and `xcom`. Whole-tree strict errors went from 4196 to 3720, which is far more than the 123 those packages held -- `remove_style` in `util/cli/style.py` was a single unannotated `(text)` parameter that poisoned every caller's inference, and typing it took `builtin/` from 460 strict errors to 125 on its own. Three genuine defects surfaced rather than just missing annotations: `Xcom.__setitem__` narrowed `deque`'s slice overload away, `Group.extract_node` carried an `isinstance` branch the checker proves dead, and `FileSessionStateLogger` bound a loop variable it never read.
- **Docs/tests: MultiUI's nine optional enrichment hooks are named, pinned and documented** (`test/architecture/test_multi_ui_fanout_surface.py`, `docs/llm/llm-custom-ui.md`): `MultiUI` forwards nine richer output events to child UIs by *string* name -- `accumulate_usage`, `mark_text_block_start`, `collapse_text_block`, `mark_thinking_block_start`, `collapse_thinking_block`, `update_tool_prepare`, `update_shell_output`, `finish_shell_output` and `replay_history`. None is part of `AnyUI`, deliberately: the fan-out skips any child that lacks the method, which is what lets a Telegram channel ignore the terminal's block-collapsing and still receive everything through `append_to_output`, and a chat channel has no thinking block to collapse. What that shape could not survive is a typo -- a misspelled name silently does nothing on every child, forever, and no type checker sees a string. The names are now pinned by a test that parses the call sites out of the module and fails if they drift from the recorded list or name something the default TUI does not implement. Seven of the nine had no mention anywhere in the custom-UI guide, so they were discoverable only by reading `multi_ui.py`; the guide now lists all nine with what fires each, marked explicitly optional.
- **Cleanup: `BaseUI` no longer shadows nine of `UIStateDefaultsMixin`'s defaults with identical copies** (`src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/{simple_ui_base,default/ui}.py`, `src/zrb/runner/chat/http_ui.py`, `test/architecture/test_facade_size_budget.py`): `UIStateDefaultsMixin` supplies `_uidefaults_`-backed implementations of the `AnyUI` contract for UIs that keep none of that state, and its prefix exists so a host can implement a member "for real" without a field-name collision. `BaseUI` mixed it in and then overrode eight of its ten members -- but five of those overrides (`is_thinking`, `llm_task`, `model`, `multi_ui_parent` and the no-op `invalidate_ui`) were the same trivial get/set the mixin already provided, differing only in the backing field's name, so `BaseUI` inherited a mixin for two methods while shadowing nine members' worth of it. Those nine are gone; `__init__` seeds `llm_task` and `model` through the properties, and the handful of places that read the private backing fields directly -- including the `SimpleUI` and `UI` subclasses and the HTTP UI, which were reaching into their base class's privates -- now use the public accessors, which is what AGENTS.md asks for anyway. `yolo` (routed through xcom), `tool_call_handler` and `background_tasks` genuinely differ and stay. `BaseUI` drops from 134 public members to 125 and `ui.py` from 1380 lines to 1330, so its facade budget tightens to match.
