## 3.24.0 (October 21, 2026)

- **Improvement: hands-free dictation listens before the tone model loads** (`src/zrb/llm/dictation/feature.py`, `src/zrb/llm/dictation/emotion.py`): `_prepare_models` awaited two model loads before opening the microphone, so listening began after `max(2.3 s, 8–20 s)` — the emotion model every time. It now awaits the transcriber alone (~2.5 s measured) and loads emotion2vec+ on a task of its own; an utterance heard while that loads carries no tone, as one heard before the load always did. The load is marked synchronously before that task is scheduled, since the microphone opens first: otherwise the first utterance could take the load on itself and wait out all of it (ADR-0115).
- **Feature: `ZRB_LLM_DICTATION_EMOTION_OUT_OF_PROCESS` loads the tone's model in a child process** (`src/zrb/llm/dictation/emotion_model.py`, `src/zrb/config/mixins/llm_dictation.py`): funasr copies the 1.1 GB checkpoint into the model, so the load peaks ~2 GB above what the model keeps — measured 2993 MB peak against 977 MB resident — and on a small machine that spike was what the kernel's OOM killer picked the chat for. The child takes the spike and asks to be killed first, so a machine that runs out loses the tone rather than the conversation. Off by default (ADR-0115).
- **Fix: the tone's worker outlived the session that closed it, or answered nothing forever** (`src/zrb/llm/dictation/emotion.py`, `src/zrb/llm/dictation/emotion_model.py`): the model loads on a thread of its own, so a session could end mid-load and the thread then published a child nobody could reach, keeping its share of the machine for the rest of the chat; the detector now keeps the worker from before its model loads and marks itself closed, so `close` reaches a worker that is still loading. That close used to be invisible until the model was in: `start` now waits for readiness in 0.2 s slices and terminates the child it started, and a child that cannot answer a polite stop (it reads nothing from the pipe until the model is in) is terminated after a one-second grace rather than five. A child that said nothing for a clip left the worker marked started and was asked again for every later clip, each waiting out the same 30 s; it is now stopped like a dead one, after 5 s (measured 0.3 s a clip), since the turn's reply waits for its tone. A clip the child answered with an error is kept, since the next clip is other audio, but a child that fails on two clips in a row is restarted like a dead one — the count is per child — so a model that fails on everything does not leave the session without tones and holding its share of the machine. A detector whose child had died kept the callable that talked to its pipe, so the restart `MAX_DEATHS` promises never happened — and, once it did restart, every attempt built a fresh worker whose death count started at zero, so the limit never came either; the worker now outlives its children and the count with it. A child killed while it loaded its model, where its memory peaks and the OOM killer most likely takes it, turned the tone off for the session without spending a death; it is now a death like one under a clip (`ChildDiedError`), and the next clip starts another, while a model the child reports it cannot load still turns the tone off. The restart runs on a thread of its own: the clip that finds the child dead carries no tone rather than holding its turn's reply for the whole model load. `close` stops the child on a thread of its own too, so a child that does not answer costs the session's teardown nothing (ADR-0115).
- **Fix: `zrb chat` could be OOM-killed while two models loaded at once** (`src/zrb/llm/util/model_load.py`, `src/zrb/llm/voice/manager.py`): speech's warm-up and dictation's prepare both load a model at session start, and their peaks stacked on a process already holding ~2 GB. `heavy_model_load` is now one process-wide slot taken by emotion2vec+ and by every local Pipecat service build; a remote service never queues behind it. The tone's load takes the slot before it imports funasr, not after — torch comes in with that import (517 MB), so an import outside the slot was half a spike stacking on the speech service's load. A load that waits longer than 120 s for the slot fails with `ModelLoadBusyError` instead of loading beside the one that holds it, which would stack the two spikes all the same. Four OOM kills in three days were all `zrb`, at 2.75–3.51 GB of anonymous memory (ADR-0115).
- **Fix: a warm-up ran a thread per turn** (`src/zrb/llm/speech/player.py`): `Speaker.warm_up` spawned a thread on every call and never reused or capped it — one live chat had 38 `zrb-speech-warm-up` threads parked behind the same model load. It now warms once per backend set, and `restart_backends` clears that so a fresh set warms again. A warm-up that a restart overtook warmed models the fresh set does not hold, so it no longer marks that set warm: the completion is checked against the set's generation, and an overtaken warm-up warms nothing at all, rather than probing the fresh set beside the warm-up the next turn starts for it.
- **Improvement: the stutter warning says how much stutter** (`src/zrb/llm/speech/pcm_player.py`): the underrun line carried no count, so a hiccup and a broken device read alike. It now names the number of blocks the device got early and the block length, and points at `ZRB_LLM_SPEECH_PLAYER_BLOCK_FRAMES` as the knob that gives each callback more time (ADR-0114, ADR-0115).
- **Fix: a timed-out command hook could leave a descendant running on macOS** (`src/zrb/llm/hook/creator.py`, `src/zrb/llm/hook/process_kill.py`): the hook's process group was signalled once, and a child the shell was forking as that SIGKILL landed could miss it — macOS does not hold a fork back for a pending kill, as Linux does — and live on with the hook's pipes. The group is now signalled again once the shell has exited, with no fork left in flight, and before it is reaped: while the shell is an unreaped zombie its pid, and so the group id, cannot be reused, so the second signal cannot reach an unrelated group. The output reader no longer reaps the shell (it watches for the exit with `waitid(WNOWAIT)`), and a group kill no longer calls `Popen.kill`, which polls and would reap it; `reap_killed_process` signals the group again and then reaps. `kill_process_group` never falls back to a kill by pid.
- **Feature: `Ctrl+G` sends the queued messages into the running turn now** (`src/zrb/llm/ui/base/queue_delivery.py`, `src/zrb/llm/ui/default/keybindings.py`): a message submitted while a turn ran but could not be steered into it — no live run registered yet, a suspended approval, or a `enqueue` that lost its race with a run that ended — waited out the whole turn, however many tool-call rounds, with no way to ask for it sooner. `send_queued_messages_now` hands every queued message to the live run when there is one (`priority="asap"`, so the model reads them at its next request and they leave the queue), waits instead while an approval or a question owns the input, and otherwise interrupts the turn so the queue runs as its own turn right after; one muted line says which of the four happened and how many messages moved, and a queued `/exec` job is never handed to the model. The binding is application-level, so it takes `c-g` from prompt_toolkit's default completion-cancel — which an open completion menu, an active choice widget or a selection still keep — and it does not submit the draft, which stays in the input box (ADR-0116).
