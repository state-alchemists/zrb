## 3.0.0

First stable 3.x release. Everything in the 3.0.0bN entries below ships here.

- **`ZRB_LLM_API_KEY` now reaches only the provider it was configured for** (`src/zrb/llm/config/model_resolver.py`, `docs/adr/adr-0094.md` rewritten, `test/llm/config/test_model_resolver_credentials.py` new, `test/llm/config/test_model_resolver.py`): 3.0.0b11 let a vendor's own variable outrank the generic knob, probed by constructing the provider with no arguments. That inverted explicit-over-ambient — a forgotten exported `DEEPSEEK_API_KEY` silently displaced a freshly set `ZRB_LLM_API_KEY`, surfacing as a 401 zrb could not override. The probe was also wrong: `OllamaProvider()` constructs with nothing set, so an explicit key was dropped for a vendor that was never "already configured".

  The question is now answered one layer up. `ZRB_LLM_API_KEY` belongs to the provider named by `ZRB_LLM_PROVIDER`, else by `ZRB_LLM_MODEL`'s prefix; `resolve_configured_model` / `_small_model` / `_multimodal_model` withhold it from a model naming a *different* provider, returning the bare name so pydantic-ai reads that vendor's variable — the only credential that could be right. `ModelResolver` is literal again: credentials handed to `resolve()` are used. Only the config layer reads `ZRB_LLM_MODEL`, so only it knows whose key the generic one is; pushing this into the resolver would make it read `CFG` to reinterpret its own arguments (ADR-0023). An explicit `ZRB_LLM_BASE_URL` disables the check — one endpoint serving every tier is the LiteLLM/OpenRouter gateway case — and a bare model name has no vendor to mismatch. `_build_from_vendor_env` is gone.

  Also fixed: a `base_url` a native provider cannot accept (`DeepSeekProvider` declares none) fell through to `_resolve_model` with the raw `provider` argument, and a plain `ZRB_LLM_PROVIDER` string turned back into a bare `"deepseek:model"` name, dropping the endpoint the fallback exists to preserve. It now builds the OpenAI-compatible provider explicitly.

- **Fix: an explicit `ZRB_LLM_PROVIDER` no longer discards the credentials configured with it** (`src/zrb/llm/config/model_resolver.py`, `docs/adr/adr-0094.md`, `docs/configuration/llm-config.md`, `test/llm/config/test_model_resolver_credentials.py`, `test/llm/config/test_model_resolver.py`): a provider *name* carries no credentials. `ZRB_LLM_PROVIDER=anthropic` with unprefixed `ZRB_LLM_MODEL=claude-sonnet-4-5` routed to the OpenAI branch, whose only outcome for a string provider was the bare name `"anthropic:claude-sonnet-4-5"` — dropping `ZRB_LLM_API_KEY` and, worse, `ZRB_LLM_BASE_URL`, so a user pointed at a private gateway silently called the vendor's public endpoint. The same hole swallowed credentials for an unknown provider given as an explicit string, and ignored a fully-configured `Provider` instance passed without separate `api_key`/`base_url`. Three changes: an explicit provider supplies the prefix when the model name has none, so routing follows the named vendor instead of defaulting to OpenAI; the two branches that would hand a bare provider *name* to `_resolve_model` first build the OpenAI-compatible provider from the credentials; and a `Provider` instance counts as a credential, so branches no longer gate solely on `api_key or base_url`. Present since the first 3.x beta. The `Which API Key Gets Used` tables are unaffected — they leave `ZRB_LLM_PROVIDER` unset.

- **Fix: an OpenAI key no longer follows a foreign-vendor model to a custom endpoint** (`src/zrb/llm/config/model_resolver.py`, `docs/adr/adr-0094.md`, `docs/configuration/llm-config.md`, `test/llm/config/test_model_resolver_credentials.py`): `ZRB_LLM_MODEL=deepseek:…` plus `ZRB_LLM_BASE_URL` takes the OpenAI-compatible path (`DeepSeekProvider` declares no `base_url`), which built `OpenAIProvider(api_key=None)`. `None` is not "no key": the OpenAI SDK then reads `OPENAI_API_KEY`, so the user's OpenAI secret went silently as a bearer token to whatever host `ZRB_LLM_BASE_URL` named. Any *prefixed, non-openai* target now gets pydantic-ai's `api-key-not-set` placeholder, so a keyless local gateway still works and a real endpoint rejects loudly. An unprefixed name still inherits `OPENAI_API_KEY` — no prefix means the OpenAI backend (ADR-0037) — so the common `ZRB_LLM_BASE_URL` + bare-name setup is untouched.

- **Docs: which API key gets used is now written down** (`docs/configuration/llm-config.md`, `docs/adr/adr-0094.md`): how `ZRB_LLM_API_KEY`, `ZRB_LLM_BASE_URL`, `ZRB_LLM_MODEL`'s prefix and a vendor's own variable interact was only discoverable in `model_resolver.py`. A new "Which API Key Gets Used" section has a decision flowchart and three tables — single vendor, a natively-supported non-OpenAI vendor, and the mixed-vendor setup where the key is withheld. Two surprises are called out: a base URL with no key anywhere sends an unauthenticated request carrying `api-key-not-set`, and a withheld key goes unmentioned in the error, which names only the vendor variable. ADR-0094 carries the flowchart (it states the decision); the tables live in the configuration reference, where users configuring zrb need them.

- **Fix: a leading backslash no longer triggers path completion on POSIX** (`src/zrb/llm/ui/default/app/completion/completer.py`): 3.0.0b11 added `\` to `_is_path_navigation`'s path-start prefixes for Windows. On POSIX a leading backslash is an escape, so it handed the fuzzy repo walk's job to a `PathCompleter` that never matched — typing one offered nothing. The drive-letter form and bare `\` root are now Windows-only; `/`, `.` and `~` stay universal.

- **CI: the code-review workflow skips cleanly when no API key is configured** (`.github/workflows/code-review.yml`, `.github/workflows/test.yml`, `zrb_init.py`): a repo without `OPENAI_API_KEY` failed the review job on every pull request. The guard cannot be a job-level `if:` (no `secrets` context there), so it is a step guard that exits 0 with a note. Also: `zrb code review`'s script gained the `set -e` `CmdTask` does not supply, so an unresolvable `git diff --stat` range no longer sends the reviewer to review "Changed files: ."; `zrb submit-comment` drops to `retries=0`, since the POST is not idempotent and a 502 after GitHub created the comment would repost it; and the test matrix gained `timeout-minutes: 30`, since the suite drives real subprocesses and GitHub's default ceiling is six hours.

- **Chore: `zrb_init.py` reads `pyproject.toml` with stdlib `tomllib`** (`zrb_init.py`): it used dev-only `tomlkit`. The CI container's `zrb` installs `--without dev` and resolved the import only because the image's `pip install poetry` drags `tomlkit` in — an accident `ZRB_INIT_STRICT=1` had just turned from a silent skip into a hard abort of every CI `zrb` invocation.

- **Chore: `# lazy: platform-only` is a recognized import category** (`AGENTS.md`, `test/architecture/test_lazy_import_categories.py`, `src/zrb/util/cli/terminal.py`): `is_real_console`'s Windows-only `msvcrt`/`ctypes` imports fit none of the four existing justifications — `msvcrt` does not exist off Windows, and `ctypes` costs ~14ms at every POSIX start for a branch POSIX never reaches. The fifth category is now written in both places, as that test's docstring prescribes.

## 3.0.0b11

- **Windows: the default shell is a real POSIX shell, and shell settings are compared by name** (`src/zrb/config/helper.py`, `src/zrb/util/cmd/command.py`, `src/zrb/task/cmd_task.py`, `docs/adr/adr-0095.md` new, `test/config/test_config_platform_detection.py`, `test/util/cmd/test_command_resolve_shell.py`, `test/task/test_cmd_task.py`): `CFG.SHELL` resolved to `pwsh`/`powershell`/`cmd` on Windows, though nearly everything zrb runs — builtin tasks, scaffolded templates, agent-written scripts — is POSIX. It now prefers Git for Windows' `bash` via `get_windows_posix_shell()`, not `shutil.which("bash")`: Windows ships `System32\bash.exe`, the WSL *launcher*, which wins the stock PATH lookup — with no distro it prints a UTF-16 error and exits 1, so commands fail while appearing to produce output; with one, the caller's `D:\…` directory does not exist in its namespace. Git's own prefix is checked first, then standard install roots, then PATH excluding anything under the Windows directory. The lookup is memoized: `EnvField` re-runs `default_factory` on *every* `CFG.SHELL` read (ADR-0023) and `resolve_shell` asks again for a bare `bash`/`sh`, which uncached meant a PATH scan plus four filesystem probes per command. The setting's value is now a path (`C:\Program Files\Git\bin\bash.exe`), which broke two word comparisons: `shell.endswith("bash")` gated the unrecommended-command lint, silently disabling it where Git Bash is now the default, and the `{"pwsh": "-Command", "cmd": "/c"}` flag table would have handed `…\pwsh.exe` the POSIX `-c`. Both now use the new `get_shell_name()`, which reduces `bash`, `/bin/bash` and `…\bash.exe` to `bash`, splitting on both separators on any platform. Set `ZRB_SHELL` to keep PowerShell.

- **Fix: a vendor's own API-key variable now outranks the generic `ZRB_LLM_API_KEY`** (`src/zrb/llm/config/model_resolver.py`, `docs/adr/adr-0094.md` new, `test/llm/config/test_model_resolver.py`): for a natively-supported provider prefix the resolver returned the bare name, silently dropping an explicit `ZRB_LLM_API_KEY` and then asking for a `DEEPSEEK_API_KEY` the user had deliberately not set. Injecting the generic key everywhere breaks a commoner case: `ZRB_LLM_API_KEY` is provider-*agnostic*, so with `ZRB_LLM_MODEL=openai:gpt-5` and `ZRB_LLM_SMALL_MODEL=anthropic:claude-haiku-…` the OpenAI key went to Anthropic and 401-ed every summarization. Credentials are now chosen by specificity: a `Provider` instance for that same vendor wins (matched on `Provider.name`, so the `OpenAIProvider` built upstream from `ZRB_LLM_API_KEY` never qualifies for another prefix, and a caller's fully-configured provider keeps its `base_url`); then the vendor's own variable; then `ZRB_LLM_API_KEY`/`ZRB_LLM_BASE_URL`, passed as whichever keywords that constructor declares; then the bare name, so pydantic-ai raises its own "set `<VENDOR>_API_KEY`". An explicit `ZRB_LLM_BASE_URL` skips the vendor rung — a custom endpoint is a deliberate override — and falls through to the OpenAI-compatible path when the native provider takes no `base_url`. The vendor rung is probed by constructing the provider with no arguments: pydantic-ai providers read their variable in `__init__` and raise when missing, so success is the answer and that instance is used.

- **Fix: `UI(...)` no longer needs a terminal to exist** (`src/zrb/llm/ui/default/ui.py`, `test/llm/ui/test_ui_base.py`): `__init__` built the prompt_toolkit `Application` eagerly, and `prompt_toolkit.output.create_output` needs a real console — on Windows without a Win32 console screen buffer it raises `NoConsoleScreenBufferError`. So constructing a `UI` failed under Git Bash or mintty, in redirected runs, and in tests wanting only post-construction logic. The `Application` is now built on first access to the `application` property, which nothing between `__init__` and `UILifecycle` reads — the point where the UI really takes over the terminal. The render handlers move with it and are still attached exactly once.

- **Fix: `is_tty` was true for a run with stdin redirected from NUL on Windows** (`src/zrb/util/cli/terminal.py`, `src/zrb/context/shared_context.py`, `test/util/cli/test_terminal.py`, `test/context/test_shared_context.py`): the CRT's `_isatty` is true for any character device, NUL included, so `zrb … < NUL` (or `subprocess.DEVNULL`) was treated as interactive and prompted into a void. `is_real_console()` disambiguates with `GetConsoleMode`, which succeeds only on a genuine console handle; POSIX `isatty()` already distinguishes and short-circuits. The Windows branch is tested with fake `msvcrt`/`ctypes` modules rather than skipped off-platform, since neither the ubuntu nor macOS CI job would otherwise execute it.

- **Fix: the journal's `## Related` links used backslashes on Windows** (`src/zrb/llm/tool/journal_write.py`): every other journal link goes through `_posix_relpath` for cross-platform portability, but the `## Related` builder called `os.path.relpath` and emitted `- [note](..\note.md)`, which most markdown renderers do not treat as a link. Link-scrubbing on delete resolved either form, so nothing broke — the files were just wrong.

- **CI: the code-review workflow passes the git range as a value, not as command text** (`.github/workflows/code-review.yml`, `zrb_init.py`): the workflow avoided `${{ }}` interpolation of `$GITHUB_BASE_REF` because the pull-request author controls ref names, but the value was then rendered into the `zrb llm chat --message "…"` string — and git ref names may contain `$`, backticks, quotes and parentheses. The range and output path now reach the script as `link_to_os=False` environment variables referenced as `"$REVIEW_RANGE"`/`"$REVIEW_OUTPUT"`; a parameter expansion is not re-parsed for metacharacters. Unreachable in practice — the workflow is gated on a same-repo PR from an owner, member or collaborator, with `branches:` pinning the base to `main` — but the guarantee now holds end to end.

- **Perf: `import zrb` no longer loads pydantic's model machinery** (`src/zrb/__init__.py`, `src/zrb/config/web_auth_config.py`, `src/zrb/session/session.py`, `src/zrb/session_state_logger/file_session_state_logger.py`, `test/architecture/test_eager_pydantic_models.py` new, `test/test_public_api_contract.py`): a module-level `BaseModel` subclass eagerly pulls in `pydantic.main` and schema construction, and two eagerly imported modules declared one — `runner/web_schema/user.py` (via `zrb/__init__.py`'s `User` export and `config/web_auth_config.py`) and `session_state_log/session_state_log.py` (via `session/session.py` and `file_session_state_logger.py`). Every `zrb` invocation paid for it. `import zrb` measures **~218ms → ~197ms**, and `pydantic.main` is absent from `sys.modules` after a bare `import zrb`.

  The fix defers the *declaring module*, not the model: these stay pydantic on purpose (`web_schema/token.py`'s `RefreshTokenRequest` and `web_schema/session.py`'s `NewSessionResponse` are FastAPI schemas). `web_auth_config.py` and both session-log callers already used string annotations, so only the construction sites needed `_user_cls()` / `_state_log_models()` accessors. `zrb.User` resolves through a PEP-562 `__getattr__` paired with `__dir__`, keeping it in `dir(zrb)` and REPL/IDE completion — `__getattr__` alone silently drops a name from tab-completion while `from zrb import User` still works, which no signature snapshot catches. Three new contract tests pin that a lazy export is indistinguishable from an eager one (`__all__`, `dir()`, identity stability, `from zrb import *`), that `__all__` promises nothing unresolvable, and that a bogus attribute still raises `AttributeError`.

  The new architecture test walks `src/` for module-level `BaseModel` declarations and fails if one re-enters the eager closure. Out of scope: the 23 `llm/tool/*.py` modules doing `from pydantic import Field` still cost ~31ms for `pydantic.fields` and `pydantic.types` — `Field` is evaluated at `def` time inside `Annotated[...]` tool signatures so it cannot move into a function body, and it does not pull `pydantic.main`.

- **Fix: a typo'd quote in a slash command sent the raw text to the model** (`src/zrb/llm/custom_command/resolver.py`, `test/llm/custom_command/test_resolver.py`): `resolve_custom_command` wrapped `shlex.split` in `except Exception: return None`, so `/greet "alice` — one unbalanced quote — resolved to no command and went to the LLM as chat, with no error. It now catches `ValueError` (shlex's only failure mode here) and falls back to whitespace splitting, so `/greet "alice` renders `Hello "alice!`. The narrower clause also stops hiding unrelated failures as quoting problems.

- **Chore: `create_agent`'s two mutable default arguments are gone** (`src/zrb/llm/agent/common.py`): `tools` and `toolsets` defaulted to one process-wide `[]`. Not a live bug — the body only copies them via `wrap_tool`/`wrap_toolset` — but `create_agent` is public and one `append` away from cross-agent tool leakage. Both are now `| None = None` with `or []` at use.

- **Docs: 8 dead code paths across `AGENTS.md` and the ADR log, plus a ratchet for the next one** (`test/architecture/test_doc_code_references.py` new, `AGENTS.md`, `docs/adr/adr-0035.md`, `adr-0055.md`, `adr-0084.md`, `adr-0085.md`, `adr-0090.md`): an audit found eight backticked `.py` paths that no longer exist and one dead directory in `AGENTS.md`'s orientation table (`llm/app/`, moved to `llm/ui/default/app/`). Each was a rename or test split that missed the prose: `test_code.py` → `test_code_analyze.py`, `test_journal.py` → `test_journal_notes.py` + `test_journal_backlinks.py`, `test_file.py` → `test_file_write.py`, `test_deferred_calls.py` → `test_deferred_calls_policy.py` + `test_deferred_calls_denials.py`, `test_common.py` → `test_common_tool_overrides.py`, and `ui/polling_ui.py` deleted. `AGENTS.md` is read first and an ADR's "Where it lives" is the only index from decision to code, so a stale path there is worse than none. The `llm/` table also gained its two missing rows (`util/`, and the `agent_state.py`/`agent_tool_result.py` leaf modules under ADR-0088).

  The new test asserts every backticked path in live docs resolves, allowlisting third-party paths cited to explain *their* behavior (pydantic-ai's `models/openai.py`, rich's `markdown.py`) and guides' placeholder paths. Changelogs are excluded: a path correct when its entry was written stays correct as a record.

## 3.0.0b8

- **`UIDefaultsMixin` is now `UIStateDefaultsMixin`, in `llm/ui/state_defaults.py`** (`src/zrb/llm/ui/state_defaults.py` renamed from `defaults.py`, `any_ui.py`, `base/ui.py`, `std_ui.py`, `multi_ui.py`, `buffered_ui.py`, `test/llm/ui/test_state_defaults.py` renamed, `test_buffered_ui.py`): `UIConfig`, in the same package, holds the user-facing defaults (assistant name, greeting, slash-command aliases), so `UIDefaults` read like a second one. The mixin defaults the other half of `AnyUI`: the ten state members and side-effect hooks `MultiUI` broadcasts, answering `None`/`False`/no-op for a UI that keeps no such state. The `Mixin` suffix is earned under ADR-0035: every value it reads is a `_uidefaults_`-prefixed attribute it sets itself, it has no `__init__` a host must call, and `background_tasks` builds its own set on first access. Class-only rename, no behavior change; nothing was exported from `zrb.llm.ui`.

- **Fix: `create_ui_factory` raised `TypeError` for two of the three documented UI extension levels** (`src/zrb/llm/ui/ui_factory.py`, `src/zrb/llm/ui/simple_ui_base.py`, `src/zrb/llm/ui/event_driven_ui.py`, `src/zrb/runner/chat/http_ui.py`, `src/zrb/llm/ui/ui_config.py`, `test/llm/ui/test_extension_levels.py` new, `test/llm/ui/test_ui_factory.py`, `docs/llm/llm-custom-ui.md`): the factory passed `config=`, which only `SimpleUI` accepted; `BaseUI` and its descendants take `ui_config=`, so a Level-3 registration failed with `BaseUI.__init__() got an unexpected keyword argument 'config'`. The keyword is now `ui_config` everywhere, including `create_ui_factory`'s own parameter (`create_ui_factory(MyUI, config=cfg)` → `ui_config=cfg`) and `SimpleUI`/`EventDrivenUI`'s constructors. `SimpleUI` no longer keeps a duplicate `self._config`; `BaseUI.ui_config` is the accessor. 5641 tests missed this because `test_ui_factory.py` used `SimpleUI` three times and `BaseUI` never.

- **Docs: the custom-UI contract is executable instead of counted** (`test/llm/ui/test_extension_levels.py` new, `src/zrb/llm/ui/base/ui.py`, `docs/llm/llm-custom-ui.md`): `BaseUI`'s docstring had an ASCII "Extension Levels" box contradicting `docs/llm/llm-custom-ui.md` (`BaseUI` was Level 1 in source, Level 3 in the guide) and called `AnyUI` "minimal, 4 methods" when a 4-method subclass will not instantiate (it needs 6, or 16 without `UIDefaultsMixin`).
