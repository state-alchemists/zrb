## 3.0.0a4 (unreleased)

- **Fix: five sources of test-suite flakiness, one of them reproduced and eliminated** (`test/conftest.py`, `test/architecture/test_sys_modules_patch_allowlist.py`, `src/zrb/llm/prompt/system_context.py`, `src/zrb/llm/prompt/prompt.py`, `src/zrb/llm/prompt/claude.py`, `test/llm/lsp/test_configs.py`, `test/llm/lsp/test_manager.py`, `test/llm/util/test_llm_git.py`): `./zrb-test.sh` failed roughly one run in five with an unrelated-looking `ImportError` in `test/llm/voice/test_engine.py`. Every cause below is the same shape — process-wide state a test mutates and a later test on the same `pytest-xdist` worker reads — which is why they surfaced as *intermittent* failures in tests that never touched the state themselves.
  - **`patch.dict("sys.modules", ...)` deletes real imports.** It restores by `clear()` + `update(snapshot)`, so any module first imported *inside* the block is absent from the snapshot and gets evicted on exit. `VoiceEngine.record` lazily imports numpy inside such a block; the eviction left numpy's single-phase-init C extension loaded but unlisted, so the next `import numpy` raised `ImportError: cannot load module more than once per process` (a hard error since CPython 3.12). Intermittent because `--dist load` distributes tests individually — whether the one `TestRecord` test that imports numpy *before* the patch landed on the same worker as the other two was a coin flip. Fixed by warming numpy once per worker in `test/conftest.py`; the existing `pydantic_ai.toolsets` warm-up (the same bug, fixed pointwise earlier) is folded into the same fixture. A new ratchet, `test_sys_modules_patch_allowlist.py`, requires each shadowed module name to be reviewed and listed — it found three shadows a manual grep had missed.
  - **An `lru_cache` keyed more narrowly than its inputs.** `_which(cmd)` memoized tool availability but `shutil.which` reads `$PATH`, which was not part of the key — so `test_system_context.py`, which stubbed `shutil.which` to return a path for everything, left a fabricated answer memoized for the rest of the worker. Every *other* probe in that module already keys on everything it reads (`cwd`, `home`), which is exactly why none of them had this failure mode. Fixed at the cause: `_which(cmd, path)` now keys on `$PATH` too — more correct in production (a `$PATH` change re-detects) and immune by construction in tests. The two tests that stubbed stdlib globals now drive real inputs instead — a real executable on a throwaway `$PATH`, a real `Dockerfile` in a `tmp_path` CWD — which also let their assertions tighten from a bare `"Tools:"`/`"Project:"` substring check to naming the tool and marker they expect.
  - **Clear-on-entry-only fixtures leak outward.** The two LSP fixtures cleared `lsp_server_configs` before each test with no teardown, protecting themselves from everyone else while leaking their own registrations — and the `$PATH` scan they cache under a mocked `shutil.which` — into whichever unrelated test ran next. Both now clear on the way out too.
  - **`current_agent_mode`'s default is a shared mutable instance.** `set_current_agent_mode` mutates it in place (deliberately — that is how an in-run `ExitPlanMode` reaches pydantic-ai's per-tool-call tasks), so a test calling it without first binding a run-local scope writes to the process-wide default. Restoring `BUILD` in a `finally` is correct only while `BUILD` stays the default and only while the body reaches the `finally`; a miss left the whole worker in plan mode, flipping `get_effective_policy()` for every later test. An autouse fixture now binds a fresh `AgentModeState` per test, so those writes land on a per-test object.
  - **Two of three unscoped ambient `ContextVar`s were unguarded.** `test/conftest.py` restored `set_current_session` only; `set_active_worktree` and `set_interactive_mode` are equally unscoped and were safe purely because every caller happened to restore the literal that equals the var's default. All three are restored now.
  - Also: `test/llm/util/test_llm_git.py` swapped a bare `os.chdir` in `try/finally` for `monkeypatch.chdir`, matching the rest of the suite. Verified with ten consecutive full `-n auto --dist load` runs, plus eight module-order-shuffled runs. Deliberately *not* changed: `--dist loadfile` would have masked the numpy bug by keeping each file's tests on one worker, at +31% wall time (23.9s → 31.3s) and without fixing anything.

## 3.0.0a3

- **Fix: a permanently-failed task no longer dumps a raw traceback to the console twice** (`src/zrb/task/base/execution.py`, `src/zrb/__main__.py`, `test/task/base/test_execution.py`): the retry loop's final-failure branch always followed its clean `Attempt N/M failed: {e}` summary with a full `traceback.format_exc()` via `ctx.log_error`, and the re-raised exception then also escaped `serve_cli()` uncaught — nothing there caught bare `Exception`, and some real exception types (e.g. `pydantic_ai.exceptions.ModelHTTPError`) are `RuntimeError` subclasses that hit the existing `except RuntimeError` branch and were unconditionally re-raised — so Python's own handler printed a second traceback on exit. Both now route through `log_debug` / a new `_handle_uncaught` helper gated on `CFG.LOGGER.isEnabledFor(logging.DEBUG)`: silent by default, still available with `ZRB_LOGGING_LEVEL=DEBUG`.
- **Fix: `src/zrb/py.typed` restored** (`src/zrb/py.typed`): the empty PEP 561 marker file 2.58.0 added was accidentally deleted as unrelated collateral in a later "Refactor default UI" commit, silently making every downstream `mypy`/`pyright` treat `zrb` as untyped again.
- **Fix: `CFG.LLM_PROFILE`'s own doc string named the wrong default** (`src/zrb/config/mixins/llm_prompt.py`): described `'standard'` as the default; the actual default (and `docs/configuration/llm-config.md`'s table) is `'auto'`.
- **Documentation: fixed several stale/incorrect references found during a docs/example audit** (`docs/advanced-topics/ci-cd.md`, `docs/advanced-topics/upgrading-guide.md`, `docs/configuration/llm-config.md`, `docs/configuration/llm-collections.md`, `docs/task-types/llmchat-task.md`, `docs/task-types/basic-tasks.md`, `docs/task-types/custom-tasks.md`, `docs/adr/adr-0036.md`, `docs/adr/adr-0055.md`, `docs/advanced-topics/web-ui.md`): the CI/CD guide showed `zrb test`/`zrb lint` as if built in — bare `zrb test` silently prints help and exits 0, so a copied CI step would never fail on a real test failure — and now shows how to define both as project tasks first; `from zrb import llm_chat` (the manager-reassignment example) was broken, since `llm_chat` only exports from `zrb.builtin`; the upgrading guide's `ZRB_LLM_INCLUDE_SECTIONS` example had a plural `examples` typo (an unrecognized name silently resolves to nothing) and a false claim about positioning content added via `append_prompt`; `llm-config.md` had three stale defaults (`LLM_MODEL`, `LLM_PROFILE`, `LLM_UI_COMMAND_PHOTO`); `llmchat-task.md`'s constructor-parameter table understated six parameter types that actually accept a deferred callable or `*Attr` union; two ADRs cited a renamed/nonexistent file; and `Task` was described as an alias for `BaseTask` rather than the plain subclass it is.

## 3.0.0a2

- **New capability: `model_resolver.model_getter`/`model_renderer` — a global fallback for the task-scoped hooks of the same name** (`src/zrb/llm/config/model_resolver.py`): the per-task `model_getter`/`model_renderer` 3.0.0a1 moved onto `LLMTask`/`LLMChatTask` only reach that one task's own agent — sub-agent delegation (`SubAgentBuilding.resolve_agent_build`) and any other `resolve_configured_model`/`resolve_configured_small_model`/`resolve_configured_multimodal_model` call site had, and still have, no per-task hook to set. `model_resolver` (the already-exported singleton whose job this extends) gained the same settable, type-checked pair — `model_resolver.model_getter = f` / `model_resolver.model_renderer = f` — applied inside `ModelResolver.resolve()` after ordinary provider resolution, so every one of those call sites picks it up with no code change of its own. This is not `LLMConfig` reborn: it is two callable slots on a resolver, not a scalar-override object, so it does not trip the R12 "exactly one configuration object" ratchet (`model_resolver` does not end in `_config`). A task's own `model_getter`/`model_renderer`, when set, still applies on top of (after) this global default for that task, matching the existing `model_getter`-then-`model_renderer` order. See [Upgrading to 3.0.0](../../advanced-topics/upgrading-guide.md#upgrading-to-300).

## 3.0.0a1

- **Behavior change: `CFG` assignments fail fast** (`src/zrb/config/config.py`, `src/zrb/config/env_field.py`): assigning an unknown `CFG.UPPERCASE` name now raises `AttributeError` naming the closest real knob (via `difflib`), instead of silently creating a new attribute that no reader ever consumes. Assigning a value the field's `cast` cannot round-trip (e.g. `CFG.LLM_MAX_REQUEST_PER_MINUTE = "nope"`) now raises `ValueError` at the assignment site instead of at the next unrelated read. `DEFAULT_*` constants and read-write properties like `ROOT_GROUP_NAME` are unaffected. The error message names the real CLI command (`{ROOT_GROUP_NAME} config explain`), so a white-labeled deployment sees its own command name, not `zrb`.
- **Fix: `CFG.TODO_VISUAL_FILTER` and `CFG.SEARXNG_PORT` now respond to `zrb_init.py`** (`src/zrb/builtin/todo.py`, `src/zrb/builtin/searxng/start.py`): both were read once at import time — before `zrb_init.py` loads — so assigning them from `zrb_init.py` was a silent no-op. Both are now resolved lazily via a callable default.
- **Fix: `start-server`'s CLI description no longer bakes in a stale root group name** (`src/zrb/runner/cli.py`): the same import-time-read bug, on the `start-server` task's `--help` text. The description is now static text; the branded name never rendered correctly there for a white-labeled CLI (it's imported before white-labeling's env override runs) even before this fix.
- **Behavior change: a broken `zrb_init.py` (or `ZRB_INIT_SCRIPTS`/`ZRB_INIT_MODULES` entry) is reported precisely, not hidden** (`src/zrb/__main__.py`, `src/zrb/util/load.py`): previously the failure was logged as one line with no file/line/type, and the CLI continued regardless. It now prints the file, line and exception type to stderr via `_load_or_warn`. `load_file` gained an opt-in `raise_on_error` parameter (default `False`, so its existing lenient callers — plugin/skill/hook discovery — are unaffected) that the init-loading call site uses to get the real exception instead of `load_file`'s own generic one-liner.
  - **Landed fatal first, then reverted to non-fatal in the same unreleased version.** The first cut (`_load_or_die`) exited 1 on any init failure, on the reasoning that a half-applied config is worse than none because the symptom shows up somewhere unrelated. Revisited: the error message already carries the file/line/type needed to fix it, so refusing to run at all costs the user the ability to even retry — and only the code *after* the failure point in that one source is skipped; whatever ran before it stays in effect either way, fatal or not. `_load_or_die` → `_load_or_warn`; it no longer calls `sys.exit`.
