## 3.35.0 (November 6, 2026)

- **Feature: every switch ends in `_ENABLED`, and its old name still works** (`src/zrb/config/env_field.py`, `src/zrb/config/config.py`, `src/zrb/config/mixins/`, `src/zrb/__main__.py`, `docs/contributing/framework-conventions.md`, `docs/configuration/env-vars.md`, `docs/advanced-topics/upgrading-guide.md`): a boolean setting could be spelled `LLM_ENABLE_REWIND`, `LLM_REWIND` or `LLM_REWIND_ENABLED` with no rule saying which, and the shapes were not a historical layer — five `ENABLE_` knobs landed in October and November. All thirty switch-shaped booleans now end in `_ENABLED`; a predicate (`IS_TERMUX`) and two modes (`LLM_SPEECH_STREAM`, `LLM_DICTATION_BARGE_IN_HOLD`) keep their name, because `_ENABLED` says nothing on top of a predicate, and a mode is not a switch. Nothing breaks. Each old spelling stays as a deprecated alias, read after the current name and warned about once per alias per process; `CFG.<old>` redirects on read and on write, because `__setattr__` rejects unknown uppercase names and an older `zrb_init.py` must survive a rename; `/set` accepts the old name for the same reason; and a startup line lists the deprecated names beside the retired settings, while they are kept out of the mistyped-variable report — a deprecated name is not a typo. The rule is R13 in `docs/contributing/framework-conventions.md`, and the whole rename table is under "Upgrading to 3.35.0". One switch merged days ago loses a word instead of gaining one: `LLM_SPEECH_MISSING_BLOCK_NOTICE_ENABLED` becomes `LLM_SPEECH_BLOCK_NOTICE_ENABLED` (41 to 34 characters), its previous name kept as an alias. `docs/adr/` and this directory keep the names of their time; a deprecation alias is what connects an old name to a new one, and rewriting a decision record would make it describe a past that never happened.
- **Fix: three old names the sweep dropped, and a test that finds the next one** (`src/zrb/config/`, `test/config/test_deprecated_settings.py`, `test/architecture/test_switch_knobs_are_named_enabled.py`, `docs/advanced-topics/upgrading-guide.md`): review found three settings whose old spelling had stopped being read, each by a different accident — `LLM_SHOW_TOOL_CALL_RESULT`, declared on one line that the sweep's block-match walked past while reporting the field done, so `on` in an environment file left the UI hiding full results; `WEB_ENABLE_SECURE_COOKIES`, an alias that predated the rename and was lost when the field's `aliases=` list was folded into `deprecated_aliases`, so a plain-HTTP deployment set Secure cookies the browser rejects and nobody stayed logged in; and `LLM_BACKGROUND_WAKE_MAX_CONSECUTIVE`, renamed to `..._ENABLED_MAX_CONSECUTIVE` because the switch beside it took the suffix, so a configured `2` read as the default `5` — three more unattended wake-ups than the operator allowed. `test/config/test_deprecated_settings.py` now pins the whole rename table and fails by name when a knob forgets one of its old names, so a rename is judged by the table rather than by the script that performed it, and `test/architecture/test_switch_knobs_are_named_enabled.py` gains the rule the count broke: `_ENABLED` is a suffix on a switch, never a word inside a name. The upgrade table also gives `WEB_ENABLE_SECURE_COOKIES` a row of its own: it was an alias in its own right, not a second spelling of a name the table already lists.
- **Fix: an extension's old config keyword still builds the feature** (`src/zrb/llm/camera/config.py`, `src/zrb/llm/screenshot/config.py`, `src/zrb/llm/dictation/config.py`, `src/zrb/llm/speech/config.py`, `test/llm/util/test_feature_config.py`): the four feature configs renamed their constructor fields along with the switches — `CameraConfig(enable_tool=...)`, `ScreenshotConfig(enable_tool=...)`, `DictationConfig(enable_echo_cancel=... / detect_emotion=... / emotion_out_of_process=...)`, `SpeechConfig(missing_block_notice_enabled=...)` — so an extension built against the previous name died with `TypeError` when it was imported, where an environment file only warns. `accepts_renamed_fields` maps each old keyword onto the field that replaced it, and gives the old attribute a read and a write onto the same field; each name warns once, and the current keyword wins when both are passed.
- **Fix: `/set` refreshes on an old name** (`src/zrb/llm/custom_command/usage_command.py`, `test/llm/custom_command/test_usage_command.py`): `/set LLM_SHOW_OLLAMA_MODELS=off` wrote the environment and reported success while the running session kept showing the models: `model_visibility_field` knew only the current names, so the refresh found no field to act on. It resolves the legacy name through `CFG.get_field_renamed_from` first, exactly as the setting itself does.
- **Feature: a batch nudge that notices lookups issued one per round** (`src/zrb/llm/tool_call/batch_nudge.py`, `src/zrb/llm/task/chat/execution.py`, `src/zrb/llm/subagent/building.py`, `src/zrb/llm/custom_command/usage_command.py`, `docs/configuration/llm-context.md`): the rule to batch independent calls sits in the prompt three times over — the capable profile, the `Read` docstring and the session's own workflow — and was still ignored: across eight days of saved conversations, 3,206 of 4,802 tool-using responses carried exactly one call (67%), 1.40 calls per round. That matters because every round re-sends the whole conversation, so a turn's input grows with its round count rather than with the output it produces. `create_batch_nudge_processor` appends one `[SYSTEM SUGGESTION]: batching` reminder when three consecutive rounds each carried a single `Read`, `Grep`, `Glob` or `LS` call on different arguments; `Shell`, `Write` and `Edit` are never counted, because there the next call usually depends on what the previous one printed. A round that already carried several calls, a final answer, a change of tool, or a reminder already in the history each end the streak, so it speaks once per pattern instead of every round after it. It is wired after the summarizer, for the user's conversation and for sub-agents alike. `/usage`'s footer reports tool calls per round as well — the number that shows whether calls were batched at all. Nothing new is recorded for it: `requests` is the round count and `tool_calls` the calls, both already in each log line.
- **Fix: a reply that left its spoken block out is told so** (`src/zrb/llm/speech/text.py`, `src/zrb/llm/speech/feature.py`, `test/llm/speech/test_feature_missing_block.py`): the `<spoken>` rule was prose only. Nothing observed the reply, so a model that dropped the block had a table read aloud and never learned it had happened. The speech session's Stop hook is the one place that sees both sides, and it now records whether the reply wanted a block and opened none, logs it, and says so in the next turn's live context — the first moment the writer can still do something about it. `needs_spoken_block` lives beside the cleaning it has to agree with: a reply that opens a block needs nothing more, even an empty one; one that opens none is judged on what the voice would actually receive — `clean_for_speech(without_blockquotes(reply))` past 400 characters — or on leaning on what that cleaning removes, a table's numbers or a fenced block's command. A quoted log counts for neither, since it is shown and never said. The notice states the omission and the rule, never what was heard: a reply can be summarized, cut by a barge-in or muted between being written and listened to, so any delivery it named would be wrong in some of those. It describes this turn's reply or nothing — every stop of the session's own run resets it first, so an older miss never carries over — and nothing is recorded while speech is off.
- **Feature: a switch for each reminder, and the batching one asks the model first** (`src/zrb/config/mixins/llm_speech.py`, `src/zrb/config/mixins/llm_content.py`, `docs/configuration/llm-context.md`, `docs/configuration/llm-voice-camera.md`): both reminders arrived with no way to turn them off, and each one costs the next request a line. They are two switches now, both on by default: `LLM_SPEECH_BLOCK_NOTICE_ENABLED` for the "your last reply opened no `<spoken>` block" line, and `LLM_BATCH_TOOL_CALL_NUDGE_ENABLED` for the "three rounds, one lookup call each" line. Separate rather than one umbrella — the speech notice is about how a reply was written, the batching one about how tools were called, and a machine may want one silent and not the other. Off means no line at all: the speech notice stops logging its warning too, and a notice already standing is cleared. The batching reminder also asks the capability question now, which it did not. `supports_parallel_tool_calls` is a deny-list (`minimax-m2.7`, `glm-4.7`), and for a model on it the System Context already says "issue exactly one tool call per response; this overrides every batching instruction", so the reminder was arguing the other way, inviting a model that malforms parallel calls to make one. It is withheld for exactly the models the System Context speaks to, and kept for a model the list does not name: `None` is unknown, not incapable.
- **Fix: the flaky transport test asserted a property it never owned** (`test/llm/tool/test_shell_output.py`): `test_a_timed_out_command_leaves_no_unclosed_transport` ran the command and `gc.collect()` inside one warning recorder, then asserted the process had warned nothing about an unclosed transport. `gc.collect()` breaks every unreachable cycle in the process, so the assertion covered transports `Shell` never touched, and the CI failure that kept reopening this was a `_SelectorSocketTransport` — the Shell path opens pipes, never sockets. It would not have been fixed by waiting either: the transport is already `_closed` when `run_shell_command` returns, so the `await asyncio.sleep(0)` this was going to get would have been a no-op. The race was in what the test measured, not in the tool. The test now records the transport the Shell path closes and asserts the invariant the helper exists for: `is_closing()` when the call returns, `_closed` after one loop turn, and exactly one close for the command. No `gc`, no process-wide warning capture, so nothing another test leaves behind can fail it.
