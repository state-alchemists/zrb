## 3.13.0 (October 4, 2026)

- **Feature: the live context lists the repository's worktrees** (`src/zrb/llm/prompt/live_context.py`): the `<live-context>` block gained a line that tells the model what it is actually looking at. `_collect_worktree_lines` runs `git worktree list --porcelain` on the same thread pool as the existing git reads and renders each linked worktree as `- branch @ path`, marking the one zrb was started in `, current` and leaving a prunable worktree out; a repository with a single checkout adds nothing.
- **Feature: every chat turn records which channel its input came from** (`src/zrb/llm/input_source.py` new, `src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/tool/ambient_state.py`, `src/zrb/contextvars.py`, `src/zrb/llm/ui/`, `src/zrb/runner/chat/`, `docs/technical-specs/context-propagation.md`): the block's second new line, `- Input: user via keyboard`, names the channel the turn came from, and a dictation turn renders `microphone/dictation` and appends a second line saying the transcript may be inaccurate, so the model verifies names, paths, symbols and commands before acting on them. `InputProvenance` (`input_source.py`, new) is the value — channel, modality, and whether transcription was involved — and the new `input_provenance` `ContextVar`, the nineteenth, carries the current turn's (indexed in `src/zrb/contextvars.py` and `docs/technical-specs/context-propagation.md`). It is bound per turn rather than inferred: `MessageQueue` records the source on its `QueuedMessage` and sets the variable around that entry's run, `ChatSessionManager.submit_message` tags a web turn `WEB_INPUT` and `chat_session_runner` scopes it around the message it drives, a dictation turn puts `DICTATION_INPUT` on the `TriggerReply` it produces, and the new `TriggerInput` (`src/zrb/llm/ui/trigger.py`) carries one for a trigger that yields it. `BaseUI`, `MultiUI`, `QueueBasedInput` and the HTTP chat UI now forward the source instead of dropping it, and `http_ui.handle_incoming_message` says in its docstring that it is only the ask-user answer seam. Two behaviours fall out of knowing the source: a queued message is steered into a live run only when it came from the keyboard, since a web or dictation turn is a turn of its own rather than an interruption, and only a keyboard message is eligible to coalesce with a paste.
- **Security: a tool's `cwd` no longer moves the sandbox's writable boundary** (`src/zrb/llm/sandbox/`, `src/zrb/llm/tool/shell.py`, `src/zrb/llm/tool/shell_background.py`, `src/zrb/llm/tool/worktree.py`, `docs/llm/sandbox.md`): with `LLM_SANDBOX_WRITABLE_PATHS` empty, the OS wrapper used the model-supplied `cwd` of `Shell` (foreground and background) as the writable root, so `cwd="/"` made the whole filesystem writable inside bwrap or Seatbelt. The worktree tools anchored the same way to the repository their arguments named. The automatic root is now always the directory zrb was started in, as the docs already said. `resolved_writable_roots`, `check_write`, `build_bwrap_argv`, `build_sbpl` and `build_sandboxed_argv` no longer take a `cwd`, and `EnterWorktree` checks the target repository and the worktree destination (which `branch_name` could steer with `..`) against the sandbox before creating anything.
- **Documentation: a design section for new maintainers** (`docs/architecture/` new, `test/architecture/test_architecture_docs.py` new): fifteen pages, plus an index and a change map, that explain zrb part by part, from the whole system down to single features. Each page has two halves. *Design* covers the problem, the principles (each linked to its ADR) and the invariants (each linked to the test that guards it, or marked unpinned). *Realization* covers the parts, the flow, and which file to open for a given change. The test checks the shape and the diagram limits, and also checks that every path and identifier a page names still exists under `src/` or `test/`. A rename that leaves a page stale fails the build.
- **Fix: a Ctrl+C while speech drains at exit no longer hangs the exit** (`src/zrb/llm/speech/player.py`): since 3.10.0, a Ctrl+C while `Speaker.drain` waited for queued speech skipped cutting off what was playing, so the audio stream stayed open and the interpreter's exit stalled. `drain` now cuts off playback whatever ends the wait, and lets a Ctrl+C propagate; only the exit hook stays quiet about it.
- **Fix: a Ctrl+C during interactive chat teardown no longer stops it partway** (`src/zrb/llm/task/chat/execution.py`): under `asyncio.run` a first Ctrl+C cancels the main task, and that cancellation cut `teardown_interactive_resources` short wherever it landed (the `SessionEnd` hook, LSP shutdown, the background-hook drain), leaving the speaker's exit drain, language servers and detached hooks running. Teardown now runs in its own task behind `asyncio.shield`, finishes, then re-raises the cancellation. A second Ctrl+C still forces exit; the `atexit` backstops reap what is left.
- **Security: a task's own PreToolUse hooks can no longer be bypassed** (`src/zrb/llm/agent/common.py`, `src/zrb/llm/hook/manager.py`, `src/zrb/llm/ui/base/ui.py`): tool hooks fired on the process-wide `hook_manager`, so a task with its own hooks (`append_hook_factory`) had its PreToolUse denials skipped, and its PostToolUse hooks never fired, for every tool that ran without an approval prompt. The PreCommand hook and AskUserQuestion's notification had the same flaw. All of them now go through `get_run_hook_manager()` or the turn's manager, and `test/architecture/test_run_scoped_singletons.py` fails on a direct `execute_hooks` call on the singleton.
- **Security: a failing UI no longer approves a tool call in a multi-UI chat** (`src/zrb/llm/ui/multi_ui.py`): when the first child UI to answer raised (a Telegram UI with the network down), when no child could be asked, or during shutdown, `MultiUI`'s input race returned `""`, which `ToolCallHandler` reads as approval, and cancelled the human's pending terminal prompt. A failed child now drops out of the race, and with no child left to answer the race raises, as `MultiplexApprovalChannel` already did. Answering one approval also no longer cancels a concurrent sub-agent's prompt; `clear_pending_confirmations_except` was removed.
- **Fix: a multi-UI chat read its state from the main UI** (`src/zrb/llm/ui/multi_ui.py`): `MultiUI` took `UIStateDefaultsMixin`'s inert defaults for the session name, model, yolo state, plan mode, history and snapshot managers and `llm_task`, so the exit report lost the session name, the model `LLMTask` set never reached the TUI, and sub-agents saw no yolo. It now reads and writes them on its main child, forwards `invalidate_ui` (formerly `invalidate_all_uis`) and `cancel_pending_confirmations` to its children, and the terminal approval prompt goes to `main_ui` rather than the first child (`src/zrb/llm/agent/run/setup.py`).
- **Fix: an approved tool no longer runs twice when the next model call fails** (`src/zrb/llm/agent/run/runner.py`, `src/zrb/llm/agent/run/retry_loop.py`, `src/zrb/llm/agent/run/history_utils.py`): after a resumed approval, pydantic-ai ran the approved tool before its model call, and a transient error, an invalid tool call or an opaque 400 on that call retried with the same deferred results, running the tool again. The round is now committed through the tool returns before any retry (ADR-0040), and the text-only fallback clears pending results instead of failing the turn.
- **Fix: retries keep the turn's prompt and work** (`src/zrb/llm/agent/run/runner.py`, `src/zrb/llm/agent/run/retry_loop.py`): the invalid-tool-call retry dropped a prompt carrying an attachment, and regenerating an empty completion dropped the turn's earlier rounds from the Stop hook's `turn`/`wrote_files`/`changed_paths` payload.
- **Fix: a task's own limiter covers the model calls its tools make** (`src/zrb/llm/config/limiter.py`, `src/zrb/llm/agent_state.py`): delegation, web and file summarization, code analysis and image description used the process-wide `llm_limiter`, not the run's. `run_agent` binds `current_llm_limiter`, and those tools read `get_run_llm_limiter()`.
- **Fix: the terminal UI keeps its transcript intact** (`src/zrb/llm/ui/default/output.py`, `src/zrb/llm/ui/default/confirmation.py`, `src/zrb/llm/ui/tracked_spans.py`): a resize left the open thinking block and live shell lines at stale offsets, so later collapses overwrote earlier text; while a sub-agent's view was shown, main-agent span edits landed in the sub-agent's pane; an approval answer was echoed behind the output held during the prompt; and that held output replayed with an extra newline and without its kind, escaping its block.
- **Fix: `/exec` waits its turn in a multi-UI chat** (`src/zrb/llm/ui/base/exec_commands.py`): it queued on the child's own queue instead of the shared one, so a message sent next started an LLM turn alongside the command.
- **Fix: a directory beside `$HOME` is not treated as inside it** (`src/zrb/llm/ui/base/system_info.py`, `src/zrb/llm/tool/mcp.py`): `/home/alice2` showed as `~2`, and MCP config was loaded from `~` and `/home` for a cwd outside `~`.
- **Fix: `HttpCheck(interval=0)` passes against a live endpoint** (`src/zrb/task/http_check.py`): each probe's timeout equalled the interval, which requests rejects at 0; it now has a one-second floor.
- **Fix: WebFetch's plain-HTTP fallback decodes UTF-8 pages** (`src/zrb/llm/tool/web.py`): a page with no charset in its `Content-Type` was decoded as ISO-8859-1; its detected encoding is now used.
- **Tests: a full run no longer collects worktree copies** (`pyproject.toml`): `norecursedirs` replaced pytest's defaults, dropping `.*`, so `./zrb-test.sh` also collected the checkouts under `.zrb/worktree/` and failed with import-file-mismatch errors.
- **Fix: the Shell tool and `/exec` return when the shell exits** (`src/zrb/util/cmd/command.py`, `src/zrb/llm/tool/shell.py`, `src/zrb/llm/ui/base/exec_commands.py`): a backgrounded child (`server &`) held the output pipes open, so a command that exited 0 was reported as timed out after the full timeout and the child was left running, and `/exec` kept the UI busy until the child exited. Both now end at the shell's exit, give the output half a second to drain, and report the background PIDs. `CmdTask` still waits for its pipes like `subprocess.run`, but a timeout now kills the command's whole process group, so a background child that ignored SIGINT no longer outlives it.
- **Fix: a task whose action fails no longer waits out its readiness timeout** (`src/zrb/task/base/execution.py`): readiness checks kept polling after the action had already failed permanently, so a server that crashed on start failed only after `readiness_timeout`. The wait now ends when the action fails, and an action that fails as its checks pass is never marked ready.
- **Fix: a failing successor no longer re-runs its parent** (`src/zrb/task/base/execution.py`): successors ran inside the parent's retry loop, so a successor's failure re-ran the parent's already-successful action (a deploy or migration twice) and was then swallowed. Successors now run after the retry loop and their failure propagates.
- **Fix: `max_output_line=0` captured nothing instead of everything** (`src/zrb/util/cmd/command.py`, `src/zrb/task/cmd_task.py`): the cap documents "a non-positive value keeps every line", and `__StreamState` translated that to `deque(maxlen=0)` — which `collections.deque` reads as a zero-length deque that discards every append, not as "unbounded" (`maxlen=None` is what says that). A command run with `max_output_line=0` therefore returned an empty result, silently, under the one value documented to mean "no limit"; the same mistake in `display_lines` is fixed with it. Dropped lines are also counted and reported now: `__report_dropped` prints `[zrb] dropped N stdout line(s), keeping the last M. Pass max_output_line=0 to keep every line.` once the command ends, on the stream the reader was printing to, so `zrb deploy > deploy.log` is never a confidently-successful, quietly-incomplete artifact. Never fatal — the command's own exit code stays the answer to "did this work?".
- **Fix: a task's advertised callable signature marked every input positional** (`src/zrb/task/base/base_task.py`): `BaseTask.__signature__` reported each input as `POSITIONAL_OR_KEYWORD`, so `help()`, an IDE and any CLI builder reading the signature were told `fn("value")` works — while the wrapper it describes, `task_runner_fn(**kwargs)`, takes no positional argument at all and raises `TypeError`. Inputs are `KEYWORD_ONLY` now.
- **Improvement: `readiness_timeout` is annotated as a float** (`src/zrb/task/base/base_task.py`, `src/zrb/task/base/params.py`, `src/zrb/task/make_task.py`): the constructor parameter, its entry in `BaseTaskParams`, and the `make_task` decorator all said `int | None`, so a sub-second readiness budget was rejected by the type checker even though nothing in the framework required a whole number of seconds. All three now say `float | None`.
- **Fix: a skill's frontmatter `hooks:` block fires in `zrb llm chat`** (`src/zrb/llm/hook/skill_frontmatter.py` new, `src/zrb/llm/skill/manager.py`, `src/zrb/llm/hook/manager.py`, `docs/llm/hooks.md`): the skill scan registered them on the process-wide `hook_manager` singleton, which the fresh per-run manager a chat session builds (`LLMChatTask`) never reads — its registry is its own — so a skill's hooks fired in a plain `LLMTask` run and never under `zrb llm chat`, while a `.zrb/hooks/` file did (every manager re-scans the filesystem). The scan now also records the parsed configs, and a factory seeded on *every* manager replays them, the seam the journal-compliance and self-review hooks already use; a manager over the canonical `hook_registry` is skipped, since the scan registers into that registry directly and replaying would fire each hook twice.
- **Fix: a nested run inherits the hook manager its parent runs on** (`src/zrb/llm/agent/run/setup.py`, `src/zrb/llm/agent/run/authority_snapshot.py`): `resolve_context_dependencies` fell straight through to the process-wide `hook_manager` when a run named none, so a delegated sub-agent's own PreToolUse and Stop fired on the singleton and a deny rule a task registered with `append_hook_factory` did not bind that sub-agent's tools. The run now reads `current_hook_manager` before falling back, the way it already inherits the UI, the confirmation mode and the approval channel, and `AuthoritySnapshot` captures the manager alongside the sandbox policy and the YOLO state, so a continuation that starts after the parent's scope has exited still fires on the same one.
- **Fix: a skill's frontmatter hooks are retired when the source that registered them is replaced** (`src/zrb/llm/hook/skill_frontmatter.py`, `src/zrb/llm/hook/registry.py`, `src/zrb/llm/hook/manager_loading.py`, `src/zrb/llm/skill/manager.py`): the replayer seeded a skill's hooks on every manager but had no way to take a registration back, so a re-scan left the previous parse's hooks in place — firing the same rule twice, and keeping one alive after it had been edited out of the file. `register_config` now returns the hydrated hook callable (or `None` when the config is disabled and nothing was registered) so a caller can hand it to `remove_hook`, and `HookRegistry.has_hook_config` answers by identity rather than equality: a re-parse mints a fresh `HookConfig` for the same rule and the generated names differ per parse, so name-keyed bookkeeping could not tell "this manager already has it" from "this manager's registry was just cleared".
- **Fix: an `arg_pattern` permission rule is judged with the call's own arguments** (`src/zrb/llm/agent/common.py`, `src/zrb/llm/task/shared_getters.py`, `src/zrb/llm/task/llm_task.py`, `src/zrb/llm/task/chat/execution.py`, `src/zrb/llm/agent/subagent/yolo.py`, `docs/llm/permission-policy.md`): the approval gate hands the tool call's arguments to `pydantic-ai`'s `approval_required` callback, but passed only the tool definition on to a per-call `yolo` callable, and `get_policy_skip_decision` decided the policy with `{}`. A rule carrying an `arg_pattern` therefore matched nothing there, and the caller fell through to YOLO — so an `arg_pattern` `ASK` was auto-approved under YOLO instead of being the Strict ASK the docs promise, and an `arg_pattern` `ALLOW` cost an approval round-trip. The arguments are now threaded through; a `yolo` callable may take `(tool_def, args)`, and the single-argument form keeps working (arity read from its signature, never from a caught `TypeError`).
- **Fix: a task name where a task object belongs is rejected at construction** (`src/zrb/task/base/base_task.py`): `upstream=["build"]` — the natural wrong guess, and what a hand-written `zrb_init.py` is most likely to pass — loaded fine and failed much later, inside the dependency walk, as `AttributeError: 'str' object has no attribute 'upstreams'`, naming no line of user code. `_ensure_task_list` now refuses a string member the way it already refused a whole-value string, for `upstream`, `fallback`, `successor` and `readiness_check` alike, on the constructor and on `append_*`.
- **Fix: a task reached only through a trigger's `Callback` is no longer reported as unreachable** (`src/zrb/group/task_diagnostics.py`, `src/zrb/callback/callback.py`): the startup diagnostic followed only upstream/fallback/successor/readiness-check edges, so a task a `Callback` runs on every fired event was named as "not registered and no task references it". The walk now follows callbacks too — transitively, like every other edge — and `Callback.task` is a public accessor for the task it wraps.
- **Fix: a task the CLI will not offer is named at startup instead of silently missing** (`src/zrb/group/task_diagnostics.py` new, `src/zrb/group/group.py`, `src/zrb/util/load.py`, `src/zrb/__main__.py`, `src/zrb/__init__.py`, `docs/core-concepts/make-task.md`): two mistakes shared one symptom — a task declared at the top level of a `zrb_init.py` and never registered (or referenced as an edge of one that is), which is a live object with a name and no CLI word, and two of the project's own tasks registered under the same alias in the same group, which `Group.add_task` replaced silently by design. `zrb` now reads back what each init source declared, once every source has loaded and before dispatch, and names both on stderr. `Group.add_task` records a `TaskReplacement` per overwrite and the diagnostic reads that log rather than grouping declared tasks by `name`, because an alias is a per-group word and the same task object may be exposed under several — two tasks sharing a name under distinct aliases are valid, and shadowing a *built-in* is intended, so a replacement whose victim is a built-in object the pre-init tree already held is left quiet (`cli`'s built-in identities are frozen at the end of `zrb/__init__.py` for exactly that comparison, so a project task an earlier run registered on the same process-wide tree cannot be mistaken for one). Seeing a *partially* executed source is the other half of it: `load_file_with_result` and `load_module_with_result` return `(module, error)` instead of raising, and keep the module whose body failed part-way, since the declarations that ran before the failure are already live in the tree and are precisely what a `zrb_init.py` typo leaves unreachable — `sys.modules` cannot serve that, as every `zrb_init.py` registers under the same module name. Warnings are never fatal: the tasks that are registered still run.
- **Fix: `zrb util uuid <version> validate` checks the version instead of rewriting it** (`src/zrb/builtin/uuid.py`): `uuid.UUID(value, version=N)` *sets* the version bits of whatever it parses, so every versioned validator accepted every other version's UUID (a v4 string passed `validate-uuid-v1`). The parsed value's version is compared now, and the unversioned `zrb util uuid validate` — which inherited the same rewrite — accepts any well-formed UUID.
- **Fix: `LSPServerConfig.initialization_options` reaches the server** (`src/zrb/llm/lsp/server.py`): the field was declared and never read, so a server configured with `initializationOptions` started without them. They are now sent, and omitted entirely when unset — servers that validate the field's shape reject an explicit null.
- **Fix: three config docstrings described behavior they do not have** (`src/zrb/config/mixins/llm_core.py`, `src/zrb/config/mixins/llm_limits.py`, `src/zrb/config/mixins/llm_content.py`, `docs/configuration/llm-config.md`): `LLM_MULTIMODAL_MODEL` claimed a fallback to `LLM_MODEL` that the resolver deliberately does not make (a text-only main model cannot read the attachment), `LLM_MCP_MAX_RETRIES` read as a connection retry when it bounds a failing tool call, and `LLM_HISTORY_SUMMARIZATION_WINDOW` said "turns" where the count is messages.
- **Fix: a typed input's rejected value named neither the flag nor an acceptable answer** (`src/zrb/input/base_input.py`, `src/zrb/input/int_input.py`, `src/zrb/input/float_input.py`, `src/zrb/input/bool_input.py`): `zrb <task> --count=abc` reported `invalid literal for int() with base 10: 'abc'` — true, and naming neither the option the user typed nor a value that would have worked, against R10's "names the setting, the bad value and the accepted values". `BaseInput.update_shared_context` now wraps the cast and names all three, so an input that adds a type through the documented `_parse_str_value` seam gets the naming without each subclass having to remember it; `IntInput` and `FloatInput` supply their phrase, and `BoolInput` derives its list from `TRUE_STRS`/`FALSE_STRS` so it cannot drift from `to_boolean`. Covered per type and again through the real CLI in `test/input/test_non_interactive.py`, since the CLI reaches the wrapping via `runner/common_util.py`, one layer above any single input's own test.
- **Documentation: the README's Mermaid example handed the agent a literal as its prompt** (`README.md`, `test/architecture/test_doc_tpl_placeholders.py` new, `docs/task-types/basic-tasks.md`): `Tpl` is opt-in — a plain `str` is a literal and is never rendered — so the example's `LLMTask(message=...)` sent the model the text `{ctx.input.dir}` instead of the path it names. The same block wraps `cmd` and `cwd` in `Tpl` two lines below and every module under `examples/` had it right, but nothing executed the README, so nothing could say so. The `message` is wrapped, `basic-tasks`' comparison table names `Tpl` where it implied a bare `cmd` would render, and the new architecture test reads every `.py` under `examples/` plus the python fences of `README.md` and the live `docs/` tree, failing on a placeholder that reaches no renderer.
- **Documentation: Basic Tasks never said that a blocking action stalls its siblings** (`docs/task-types/basic-tasks.md`): an `action` runs on the event loop, so ten sibling tasks that each wait a second finish in 1.3s when the action is `async` and 10.4s when it is a plain `def`. Nothing fails and nothing warns — the work simply stops overlapping. The page taught `Task(action=...)` and `@make_task` and left the constraint to `custom-tasks.md`'s `_exec_action` section, which a reader writing a plain action never reaches.
- **Fix: `/compress` ignored `/model small`, and sized a chunk by the wrong window** (`src/zrb/llm/task/llm_task.py`, `src/zrb/llm/agent/run/setup.py`, `src/zrb/llm/summarizer/chunk_processor.py`): `/compress` is handled by the task *before* `run_agent` exists, so the model bindings a run publishes were not in scope and the summarizer resolved its model against `CFG` — which is why `/model small` never reached the consumer users most expect it to. New `session_model_scope` (`agent/run/setup.py`) binds a session's model overrides around a path that resolves one outside a run, combining a UI list exactly as `resolve_context_dependencies` does and binding only non-`None` values, so an enclosing run's binding is never replaced by nothing. The chunk budget had the same shape of mistake: it was derived from `token_threshold` — the conversational budget taken from the global `LLM_MAX_TOKEN_PER_REQUEST` cap — and handed to a model with a smaller window, which is what made `/compress` fail with a provider `context_length_exceeded` on a single 422-message chunk. It is now reduced to the summarization model's own window when that is known, as `LLMLimiter.fit_context_window` already did for the main model.
- **Documentation: every page and example was read against the source it describes** (`docs/`, `examples/`, `docs/adr/adr-0087.md`, `src/zrb/task/make_task.py`): each page under `docs/` (the changelog excepted) and each example was checked against the code it points at. The examples were the worse half — `llm-hooks` called the removed `HookManager.register` and kept its hook module outside `.zrb/hooks/`, so it crashed or never loaded; `chat-minimal-ui` ran alongside the default TUI; `web-auth`'s `"*"` access had no wildcard support; and `task-groups`, `basic-task`, `cmd-task` and `live-context` all documented commands that fail as written. In the docs: wrong env var names and defaults, stale module paths and symbol names, snippets missing imports or passing a bare string where `Tpl` is required, hook matcher fields that do not exist, an outdated sanitization pipeline description, and missing install extras. ADR-0087 was rewritten to the refuse-to-start behaviour the CLI has had since 3.1.0, and stale paths and renamed symbols were corrected across the rest of the log.
- **Chore: dependencies — `pydantic-ai-slim` 2.41 → 2.54** (`pyproject.toml`, `poetry.lock`, `src/zrb/llm/agent/run/openai_patch.py`, `docs/technical-specs/llm-history-sanitization.md`): a V2 minor jump, which the version policy keeps free of intentional breaking changes, and the API surface zrb imports (`Agent`, `DeferredToolRequests`, `MCPToolset`, `capabilities`, `usage`, the message classes) is unchanged. Provider floors moved with it: `openai>=3.8.0` → `>=3.19.0` (pydantic-ai-slim's own `openai` extra floor), `anthropic>=1.3.0` → `>=1.9.0`, `google-genai>=2.18.0` → `>=2.25.0`. Re-audited the `content: null` serializer patch against 2.54.0 — `OpenAIChatModel._MapModelResponseContext._into_message_param` still writes `content = None` beside `tool_calls`, so the patch is unchanged and still load-bearing — and re-confirmed the sanitization spec's claims (both deferred-mismatch `UserError` strings, `ModelHTTPError.headers`/`retry_after`, `known_model_names()`, `_map_user_message`'s `assert_never`).
- **Security: PyJWT, urllib3 and oauthlib pins bumped for GHSA advisories** (`pyproject.toml`): PyJWT `>=2.13.0` → `>=2.15.0` (critical asymmetric-PEM detection bypass GHSA-ffc3-869f-jxw9, plus the high/medium HS-vs-asymmetric confusion and PyJWKClient issues patched in 2.14.0 and GHSA-42vr-xj54-vc7v patched in 2.15.0); urllib3 `>=2.7.0` → `>=2.8.0` (GHSA-8988-9cw3-xx77, GHSA-vxq7-64xx-v4gw, GHSA-gh4c-6fx4-qh6g); `oauthlib>=4.0.0` added to the `rag` extra (GHSA-hj66-6f7g-4r5v, GHSA-xpv3-w29h-x7cv), reaching it via chromadb → kubernetes → requests-oauthlib. chromadb's own advisories have no upstream fix and are left as-is.
- **Tests: adapted to pydantic-ai 2.54's `UserPromptPart` validation** (`test/llm/agent/run/test_history_utils_drop_turn.py`, `test/llm/summarizer/history_processor/test_history_summarizer_fat_results.py`): 2.54 raises at construction when `UserPromptPart.content` is neither a `str` nor a sequence of `UserContent` (upstream #8595), so the two sanitizer tests that built `UserPromptPart(content=None)` now pass an empty string — the reachable nil content for that part — and the transcript test's deliberately-illegal `123` item becomes a `CachePoint()`, a valid `UserContent` that still exercises `format_multimodal_item`'s unknown-item fallback. The other part types (`TextPart`, `ThinkingPart`, `ToolReturnPart`, `SystemPromptPart`) still accept `None`, and production only ever builds `UserPromptPart` with a string, so no sanitizer path changed.
