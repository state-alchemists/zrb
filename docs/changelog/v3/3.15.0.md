## 3.15.0 (October 6, 2026)

- **Fix: a blocked STT initializer no longer keeps zrb alive after Ctrl+C** (`src/zrb/util/async_thread.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `src/zrb/llm/dictation/backend/vosk.py`, `src/zrb/llm/hook/process_io.py`, `src/zrb/config/mixins/llm_dictation.py`, `docs/configuration/llm-config.md`, `test/util/test_async_thread.py`, `test/llm/dictation/backend/test_pipecat_backend.py`, `test/llm/dictation/backend/test_pipecat_backend_load.py`, `test/llm/dictation/backend/test_vosk_download.py`, `test/llm/dictation/test_feature_teardown.py`): Pipecat and vosk loaded models, decoded audio and downloaded or extracted models through `asyncio.to_thread()`, whose default-executor workers are non-daemon — cancelling the coroutine stopped waiting but left a blocking call in a thread interpreter shutdown waited to join, so Ctrl+C could leave zrb running. Those calls now run on daemon threads through one shared runner, so a call still inside native code cannot hold process exit. Such a call cannot be stopped at all, so a result that lands after its caller was cancelled is still landed, and the runner now hands that orphan to whoever asked for it rather than dropping it: a Pipecat service whose model finished loading for a `prepare` that was cancelled is cleaned up (`STTService.cleanup`) instead of being left to the collector, and a Vosk response opened after its download was cancelled is closed instead of holding its socket until collection; only the call's own result is handed over, because a disposer that closes what a call built has no use for the exception that stopped it being built. A Pipecat service is closed on a loop of its own when the loop that was waiting for it is already gone, rather than dropped for the collector, and a service no pipeline could be started around is closed as well: `prepare` owns the service from the moment its load returns until a pipeline has adopted it. Vosk's model archive is removed by the extractor itself rather than only by the caller, which a cancellation returns past while the extractor is still reading the file — a removal that fails, silently, wherever an open file cannot be deleted. The Vosk connection is now bounded whatever the knob says — `ZRB_LLM_DICTATION_VOSK_DOWNLOAD_TIMEOUT=0` means the transfer is not capped, not that a socket may wait forever — so a server that never answers cannot pin a thread for the life of the process.
- **Feature: cloud dictation keeps the language it was spoken in, and takes a hint** (`src/zrb/config/mixins/llm_dictation.py`, `src/zrb/llm/dictation/config.py`, `src/zrb/llm/dictation/backend/builtin.py`, `src/zrb/llm/dictation/backend/openai.py`, `docs/configuration/llm-config.md`, `test/llm/dictation/backend/test_builtin.py`, `test/llm/dictation/backend/test_openai.py`): the `google` and `multimodal` backends were asked to "Transcribe this audio to text. Return only the transcription.", which a multilingual model is free to answer in translation, so an utterance spoken in one language could come back in another and steer the turn in words the user never said. The default `ZRB_LLM_DICTATION_TRANSCRIBE_PROMPT` is now "Transcribe exactly what is spoken. Do not translate or paraphrase. Return only the transcription.", and the setting still replaces it. `ZRB_LLM_DICTATION_LANGUAGE` (empty: detect) is new — an ISO-639-1 code such as `en` or `id`, which `OpenAIDictationBackend` passes to the transcription API as its `language` hint, so `whisper-1` and `gpt-4o-transcribe` no longer guess at a short utterance. The hint reaches the backend through `DictationConfig.language` and applies to the streaming and the whole-utterance call alike.
- **Performance: a task run no longer pays the state logger's 100 ms tick** (`src/zrb/task/base/lifecycle.py`, `test/task/test_lifecycle.py`): `execute_root_tasks` ended a run by terminating the session and then awaiting `log_session_state`, which was parked in its 100 ms interval and could not observe the flag until it woke, so every `Task.run()` paid whatever was left of that tick — and a no-op task, which terminates immediately, paid all of it. The run now creates an `asyncio.Event`, hands it to the logger and sets it the moment the session is terminated; the loop waits on the event with the same 100 ms timeout, so the logging cadence is unchanged (a 0.55 s task still wrote 9 state lines), and a session terminated from anywhere else keeps the `asyncio.sleep` fallback. The `finally` block already cancelled the logger, so the await had bought nothing but the sleep. Measured on Python 3.14: a no-op `Task.run()` went from 103.0 ms median (n=20, min 101.8, max 123.4) to 1.3 ms, and an eight-task serial `CmdTask` DAG from 123 ms to 39 ms.
- **Documentation: the decision numbers and the editorial asides left the surfaces a user reads** (`docs/configuration/llm-config.md`, `docs/configuration/llm-collections.md`, `docs/llm/extending-the-llm.md`, `docs/llm/hooks.md`, `docs/llm/llm-chat-lifecycle.md`, `docs/llm/permission-policy.md`, `docs/llm/programming-the-prompt.md`, `docs/llm/sandbox.md`, `docs/llm/voice-camera.md`, `docs/task-types/llmchat-task.md`, `docs/advanced-topics/upgrading-guide.md`, `examples/themes/monokai/README.md`, and 37 then 44 files under `src/zrb`): `ADR-NNNN` citations were removed from everything a user reads and kept where a decision is defended — `docs/adr/`, `docs/architecture/`, `docs/contributing/` and `docs/technical-specs/` are contributor-facing by definition. Twelve went from the configuration pages, 29 from `docs/llm`, the `llmchat` task type and the upgrading guide, one from an example README, and 58 from comments and docstrings across 37 source files. Where a citation was the whole sentence ("See ADR-0065 for the full design rationale") the sentence is gone; where it was a trailing parenthetical, only the parenthetical went. The visible one was `ZRB_LLM_DICTATION_PIPECAT_ENABLED`, which described itself as "Stage 1 of the migration (ADR-0107)" in both its own doc and its row in `llm-config.md` — a user can act on neither the number nor the stage — and was rewritten to say what the flag did instead. It described a stage that no longer exists as of this release either — the setting itself is removed below. The second sweep took the comments that editorialize instead of stating mechanism, across 44 source files: "the whole reason/point" (5 sites) rewritten to state the reason, "only ever" (22) reduced to "only", and "simply", "truly" and emphatic "very"/"really" (21) dropped. "Deliberately" (46, kept on purpose) states an intent that stops a future reader from "fixing" a decision, and stays with it; so does "entirely" where it is precise. Every changed line is a comment, docstring or Markdown line — the second commit was checked by tokenizing HEAD and the working tree and comparing the code-only token stream — so no behavior changed.
- **Fix: a side question is told that "you" means the main agent** (`src/zrb/llm/prompt/markdown/side_question.md`): `/btw` asks about the conversation the user is having, and the side agent read "can you explain that?" as addressed to itself — the one agent in the exchange that ran nothing. `side_question.md` now says that "you", "your" and anything else referring to the main agent mean the main agent in that conversation context, and to answer from the inherited history accordingly.
- **Performance: the shell's live output and its console echo are capped lower** (`src/zrb/llm/tool/shell.py`, `src/zrb/config/mixins/llm_limits.py`, `docs/configuration/llm-config.md`): `_LIVE_UPDATE_INTERVAL`, how often the Shell tool repaints the output of a command that is still running, went from 0.1 s to 0.5 s, and `ZRB_LLM_MAX_CONSOLE_OUTPUT_CHARS` — what a command's output may cost the console before the rest is dropped — from 1,000,000 to 100,000, the cap the model already reads it under. A build that scrolled in full still scrolls in full; what is gone is the echo of output the model never sees, which a runaway command could spend minutes printing.
- **Fix: a recalled message that has already run needs a second Enter** (`src/zrb/llm/ui/default/message_editing.py`, `docs/adr/adr-0077.md`, `test/llm/ui/default/test_keybindings_history_nav.py`, `test/llm/ui/default/test_queued_messages.py`): Up Arrow recalls a queued message into the input for editing, and Enter submitted whatever the box held — so a recall made only to read a message sent it again, and when its turn had already started the same text ran twice. The first Enter now warns and leaves recall mode with the text still editable; only a second, deliberate Enter resubmits an already-started or already-sent message. In-place editing of a queued message, and the `Ctrl+X` that drops the recalled one, are unchanged, and ADR-0077 records the rule beside the recall it belongs to.
- **Fix: a hook that will not finish no longer holds the interpreter open** (`src/zrb/llm/hook/executor.py`, `test/llm/hook/test_executor.py`): hooks ran on a `concurrent.futures.ThreadPoolExecutor`, whose non-daemon workers keep the interpreter alive, so a hook that was cancelled or stuck, or a worker that never returned, left `zrb` needing a second Ctrl+C to exit. The executor is now `_DaemonHookExecutor`, a fixed pool of daemon worker threads draining one `queue.Queue`, with the same `max_workers`, the same future-per-submission contract, and the same refusal to schedule new futures after shutdown. A subprocess test pins the shutdown behavior.
- **Fix: `/set` wrote a value the next read did not see** (`src/zrb/config/env_field.py`, `test/config/test_config_llm.py`): `EnvField.__set__` writes only the field's write key while reads resolve its aliases in declared order, and `ZRB_LLM_MAX_TOKEN_PER_MINUTE` declares `[singular, plural]` with `write_key="LLM_MAX_TOKENS_PER_MINUTE"` — the singular being the name the docs advertise. With `ZRB_LLM_MAX_TOKEN_PER_MINUTE=7`, `/set LLM_MAX_TOKEN_PER_MINUTE 11` wrote the plural key, reads kept returning `7`, and the command printed success anyway. `__set_name__` now orders the configured write key first among the readable aliases without dropping any of them, so the value a write lands is the value a read sees, and a legacy alias is still read when nothing else is set.
- **Fix: speech queued before an interrupt is no longer played after it** (`src/zrb/llm/speech/player.py`, `test/llm/speech/test_player.py`): `Speaker.interrupt()` documents that it drops queued speech and bumps a generation for the stale check, but the worker took an item off the queue and only then read the current generation — so an item dequeued just before the bump could be stamped with the generation that came after it, and `_play_prepared`'s comparison let it through. The generation is now captured where the item is enqueued, inside `_enqueue` while it already holds the speaker lock, and carried with the item; the stale check compares the item's own generation with the current one. Pause, resume, drain, close, backend selection and the two-thread design are untouched.
- **Fix: background output that was dropped is reported** (`src/zrb/util/cmd/command.py`, `src/zrb/llm/tool/shell.py`, `src/zrb/llm/ui/base/exec_commands.py`, `test/llm/tool/test_shell_command.py`, `test/llm/ui/base/test_commands_shell.py`): when a command left a child holding the output pipes open — `(sleep 1; echo LATE) &` — `wait_for_exit_and_drain` waited for the shell's exit and then at most `PIPE_DRAIN_GRACE_SECONDS` (0.5 s) for the readers, cancelled the ones still running, and said nothing: everything that child wrote afterwards was discarded in silence, so a run that lost output could be read as a complete one, while the capture cap reports its own loss. `wait_for_exit_and_drain` now takes an optional `reporter` and says what it dropped, which the Shell tool includes in the output it returns and `/exec` writes to the UI. The exit code is still the return value, and the shell's pipes are still not waited on for longer.
- **Fix: a progress line queued by a turn is not read aloud after it** (`src/zrb/llm/speech/progress.py`, `test/llm/speech/test_progress.py`): `ProgressNarrator` discarded a call id only on `function_tool_result`, so a call interrupted or raising before it produced a result left its id in `_running` and the queued line stayed eligible — "Running a command." could be spoken after the tool call, and the turn, had ended. `reset()` now clears the pending call ids and `handle_stop` calls it. Because a tool-call id can come back in a later turn, every queued line also carries the turn generation it was queued in, and `_is_finished` compares that generation: a line from an earlier turn stays stale even when the id is used again, and one still being decided on when the turn stops is never queued at all. The announcement interval, the silence check, the silent-tool list and the phrase templates are untouched.
- **Fix: cancelling a turn stops the progress announcement it is speaking** (`src/zrb/llm/speech/feature.py`, `test/llm/speech/test_feature.py`, `test/llm/speech/test_feature_stream.py`): `handle_stop` was registered only for a session that speaks replies, and its cancel branch interrupted the speaker only for one too — so a session with `progress` and no `reply` in `ZRB_LLM_SPEECH_EVENTS`, which narrates tool calls without ever reading a reply, kept talking after Escape or a barge-in. A queued line was dropped either way, since `progress.reset()` runs first, but the line already being spoken is not in the queue. A `progress`-only session now registers the stop hook, which is where a turn's queued lines are invalidated, and `speaker.interrupt()` is no longer conditional on the reply event while `streamed_reply.reset()` still is.
- **Fix: history written while the file lock was held is flushed at teardown** (`src/zrb/llm/ui/default/previous_message_history.py`, `src/zrb/llm/ui/default/lifecycle.py`, `test/llm/ui/default/test_previous_message_history.py`, `test/llm/ui/default/test_lifecycle.py`): the previous-message history tries its file lock exactly once (`_LOCK_TIMEOUT_SECONDS = 0.0`), and a write that lost the race was kept in memory "for the next write" — of which there might be none, so a session that ended before another submission lost those messages for good. `PreviousMessageHistory.close()` makes one short, bounded (0.25 s) attempt to persist what is pending, and the default UI calls it during teardown. That teardown's `finally` is now nested, so the capture stop, the buffered output, the background-task cleanup and the flush each get their chance even when an earlier step fails — a closed stdout pipe used to skip both the cleanup and the flush. Submitting stays non-blocking, writes stay atomic and best-effort, a damaged file still reads as empty, and nothing raises out of persistence.
- **Tests: the scheduler's minute-boundary flake is pinned out** (`test/task/test_scheduler.py`): `test_scheduler_triggers_on_match` failed on a Windows job, asserting that `match_cron` had been called once when it had been called twice 10 ms apart — on either side of a real minute boundary. The loop sleeps only as far as the next minute, and `* * * * *` matches in both, so firing twice across a boundary is correct and the test was wrong: it never pinned its clock, unlike its neighbour in the same file, which already did and said why. The clock is pinned inside one minute now, and the assertions stay as strict as they were. Test-only.
- **Feature: `prune` removes the merged branches' worktrees with them** (`src/zrb/builtin/git.py`, `src/zrb/util/git/commands.py`, `test/util/git/test_commands.py`, `test/builtin/test_git_diff.py`): `prune-local-git-branches` (alias `prune`) deletes the local branches already merged into HEAD, and `git branch -d` refuses one that is checked out in a linked worktree — so a branch this command exists to remove stayed behind, silently, with its directory. The command now lists the worktrees first and, for each merged branch, removes each worktree before deleting the branch: `get_worktrees` maps every checked-out local branch to all of its worktree paths, and `remove_worktree` runs `git worktree remove` on each. The listing is read whole rather than through `run_command`'s output-line cap, and read with `-c core.quotePath=true`: a quoted path is decoded from Git's escaping, so a directory whose name carries a non-ASCII byte arrives as that name instead of octal escapes; a `+`-prefixed branch line, which is how `git worktree list --porcelain` marks a branch checked out elsewhere, is parsed as the branch it names rather than as `+name`; and a branch with more than one worktree keeps all of them instead of only the last.
- **Breaking: the stage-1 Pipecat input tap is removed** (`src/zrb/llm/dictation/pipecat_input.py`, `src/zrb/llm/dictation/listen.py`, `src/zrb/llm/dictation/feature.py`, `src/zrb/llm/dictation/config.py`, `src/zrb/config/mixins/llm_dictation.py`, `src/zrb/config/retired.py`, `docs/adr/adr-0107.md`, `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`, `docs/configuration/llm-config.md`, `docs/advanced-topics/upgrading-guide.md`, `test/llm/dictation/test_listen.py`, `test/llm/dictation/test_pipecat_input.py`, `test/llm/dictation/test_pipecat_metrics.py`, `test/llm/dictation/test_feature_pipecat.py`, `test/llm/dictation/test_listen_tap.py`): 3.14.0 shipped `ZRB_LLM_DICTATION_PIPECAT_ENABLED`, which fed every block the microphone captured to a Pipecat pipeline beside the hand-rolled path, and it is gone. The pipeline decided nothing: stage 1 existed so that the detector inside it could be measured against the boundaries `UtteranceCutter` draws, before a later stage replaced the cutter with it. That later stage was never built — the cutter still cuts, so the tap measured a path no session took — and a setting that turns on a measurement nothing acts on is not worth carrying. Removed with it: the `[transport, detector, metrics stage, counter]` pipeline it owned, the `on_captured` hand-off `listen` grew for it, the `_CaptureTap` that fed that hand-off from the audio callback on a queue of its own, `AudioPipeline`, `SpeechMetricsRecorder` and the one line a listening ended with. Nothing zrb hears or says changes, and none of it was ever in the decision path. The setting is reported at startup for one release through `retired.py`, and the upgrading guide says the same. If you were reading that line to check a device, `zrb voice mic-test` in `examples/voice-interaction` measures the microphone against the same threshold dictation uses. The services that did ship — Pipecat speech-to-text behind `ZRB_LLM_DICTATION_BACKEND` and text-to-speech behind `ZRB_LLM_SPEECH_BACKEND` — are untouched, and ADR-0107 now records the detector-driven stages as abandoned rather than pending.
- **Documentation: the guides and examples lost the marketing adjectives and empty emphasis no other page used** (`docs/llm/llm-integration.md`, `docs/llm/permission-policy.md`, `docs/llm/llm-custom-ui.md`, `docs/task-types/file-ops.md`, `docs/task-types/readiness-checks.md`, `docs/core-concepts/environments.md`, `docs/core-concepts/cli-and-groups.md`, `docs/core-concepts/session-and-context.md`, `docs/core-concepts/tasks-and-lifecycle.md`, `docs/contributing/architecture.md`, `docs/advanced-topics/white-labeling.md`, `examples/chat-sse/README.md`, `examples/chat-telegram/README.md`, `examples/chat-minimal-ui/zrb_init.py`): an audit of every comment under `src/zrb` and every live page found the comment corpus clean — no comment names a file, symbol, setting or test that no longer exists, and none carries filler — and fourteen lines of prose that said nothing. `zrb` came with "a powerful, built-in AI assistant" and "a robust, first-match-wins permission system"; `Scaffolder` was "a powerful templating engine"; `Env` "a powerful way to configure"; `zrb_init.py` was "your magic file"; and `docs/contributing/architecture.md` headed a section "Robust LLM Integration". The standard the repository already ships forbids exactly that language (`core-writing/templates/readme.md`: no marketing adjectives, cut "powerful", "modern", "elegant"), so the adjectives are gone and every claim they qualified survives. Emphasis carrying no fact went the same way — "Just 2 methods to implement!", "Register - ONE line!", "first response wins!", "No polling, no missed messages!", and a trailing "!" on four sentences. No page changed meaning.
- **Fix: the SSE example's UI could not be handed an input source** (`examples/chat-sse/zrb_init.py`): `SSEUI.handle_incoming_message` overrode `EventDrivenUI`'s with one parameter, where the base method and the `chat-telegram` example both take `(text, source=None)`, so a caller naming a provenance — the Telegram handler does — would have raised on the SSE path. The parameter is forwarded to `super()`. Nothing in CI could see it: `pyright src/zrb` excludes `examples/`, and `test_example_imports.py` resolves imports only. `pyright examples/` reports it, and this file now reports one error rather than three — the remaining one is a `hasattr(msg, "model_dump")` guard on `ModelRequest | ModelResponse`, left as written.
- **Feature: dictation and speech run Pipecat services, chosen by name** (`src/zrb/llm/voice/spec.py`, `src/zrb/llm/voice/registry.py`, `src/zrb/llm/voice/manager.py`, `src/zrb/llm/voice/builtin.py`, `src/zrb/llm/dictation/pipecat_stt.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `src/zrb/llm/speech/pipecat_tts.py`, `src/zrb/llm/speech/backend/pipecat.py`, `src/zrb/llm/speech/player.py`, `src/zrb/llm/util/teardown.py`, `src/zrb/config/mixins/llm_dictation.py`, `src/zrb/config/mixins/llm_speech.py`, `docs/adr/adr-0107.md`, `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`, `docs/configuration/llm-config.md`, `test/llm/voice/`, `test/llm/dictation/test_pipecat_stt.py`, `test/llm/dictation/backend/test_pipecat_backend.py`, `test/llm/speech/test_pipecat_tts.py`, `test/llm/speech/backend/test_pipecat_backend.py`, `test/public_api_snapshot.json`): `ZRB_LLM_DICTATION_BACKEND` now names a Pipecat speech-to-text service — `whisper`, `moonshine` or `funasr` — and `ZRB_LLM_SPEECH_BACKEND` a text-to-speech one — `kokoro`, `piper` or `pocket` — resolved through ADR-0090's registry-and-manager shape (`stt_registry`, `tts_registry`, with a manager each), so a project registers its own service from `zrb_init.py` and a built-in of the same name can be replaced without giving up the ones beside it. zrb still cuts the utterance: `UtteranceCutter` decides where speech begins and ends, the service is handed a finished segment — told, in Pipecat's own terms, that speech spanned it — and answers with a `TranscriptionFrame`, so Pipecat's voice-activity detection is not in the decision path and every transcript guard (wake words, stop words, approvals, minimum words) reads a service it cannot tell from vosk. A segment a local service finds no words in is answered as an empty transcript rather than silence, because a segmented service yields no frame at all for one and the caller would otherwise wait out its own timeout. Playback is unchanged: zrb asks the TTS service for a sentence's audio (`TTSSpeakFrame` → `TTSAudioRawFrame`) and plays it through `PcmUtterance`, so pause, resume, interrupt and the external-player fallback are the same code and no output transport is involved, and closing a sentence's audio interrupts the synthesis rather than letting it run to its end. vosk, the OpenAI/Google/multimodal and the `say`/espeak-ng/Termux backends are untouched. `piper` and `kokoro` make the voice mandatory, so an unset `ZRB_LLM_SPEECH_VOICE` now falls back to `en_US-ryan-high` and `af_heart` instead of raising from the service's constructor, and each model is downloaded once on first use and runs offline afterwards. Measured on Python 3.14: piper renders 24 kHz audio with a 0.31 s first chunk and synthesizes with no network once its model is cached (115 MB in the Pipecat cache); moonshine transcribes with no network once its model is cached (138 MB), provided the architecture it resolves to is the one cached — its own default resolution picks the newest model, which is a download. kokoro-onnx declares `requires_python <3.14` and will not install on this interpreter, though its wheel is pure Python and imports there under `--ignore-requires-python`; pocket installs and drags PyTorch.
- **Fix: a Pipecat pipeline is no longer taken away between utterances** (`src/zrb/llm/dictation/pipecat_stt.py`, `src/zrb/llm/speech/pipecat_tts.py`, `docs/adr/adr-0107.md`, `docs/architecture/3-peripheral-flow/voice-on-pipecat.md`): a service loads its model in its constructor, so one pipeline is built per backend and kept for the session, and between utterances it receives nothing. Pipecat's `PipelineWorker` cancels itself after `IDLE_TIMEOUT_SECS` (300 s) with no frame from `idle_timeout_frames` — armed by the last `TranscriptionFrame` or `BotSpeakingFrame` — so both pipelines were killed five minutes after the last thing said, and every utterance after that failed at once with "the Pipecat worker stopped" and no way back, since the backend kept the dead pipeline. Every worker zrb builds now passes `idle_timeout_secs=None`, which leaves the monitor unstarted rather than merely muting it (`cancel_on_idle_timeout=False` logs "Idle timeout detected" every interval and carries on), and zrb closes the pipeline itself at the session's teardown. Reproduced from a real session log: `PipelineWorker#1` cancelled at 21:59:19 and `PipelineWorker#0` at 21:59:43, five minutes after their last activity at 21:54:20 and 21:54:43, with three "Hands-free transcription failed" lines after it.
- **Fix: a Pipecat sentence that timed out is stopped, not abandoned** (`src/zrb/llm/speech/pipecat_tts.py`, `test/llm/speech/test_pipecat_tts.py`): a sentence whose first chunk did not arrive within the timeout gave up the pipeline's claim on speaking and nothing else — no close, no interruption. The service went on synthesizing audio nobody would hear, and because asking for the next sentence is what moves the sink onto it, a chunk arriving late for the abandoned one was read as that next sentence's own: the sentence before played under the sentence after. The timeout now takes the path a sentence the user talked over takes — the sentence is closed, the service is told to stop, and the claim is given up only after that — so the sentence after it is asked of a service that has been told.
- **Fix: a sentence a Pipecat service rendered survives a device that will not open** (`src/zrb/llm/speech/player.py`, `src/zrb/llm/speech/backend/pipecat.py`, `src/zrb/llm/speech/backend/any_speech_backend.py`, `test/llm/speech/test_player_in_process.py`): playing in process falls back to a player program when the output device cannot be opened, and the fallback was the backend's own `create_utterance` — which a Pipecat service can only refuse, because it renders audio and plays nothing itself. It raised where the device failure was already being handled, and the sentence went unsaid even though the speaker was holding the local voice it would have used anyway. A backend now says whether it has a program of its own (`needs_zrb_playback`, true for Pipecat), and one that does not hands its sentence to the next backend the speaker holds. The same fact keeps a service from being asked for a sentence it can only fail on: with a player program configured, a Pipecat backend is stepped over rather than logged as a failure of its own.
- **Fix: a speaker that never started its threads still lets its backends go** (`src/zrb/llm/speech/player.py`, `test/llm/speech/test_player.py`): `Speaker.speak` says a sentence on the calling thread and never starts the worker and player threads `say` starts, while making the same backends either way — a Pipecat service being a loaded model, a running pipeline, and a loop on a thread of its own. Ending the speaker returned early when it found no worker thread to stop, so both `close()` and the exit `drain()` left everything behind them: the model stayed resident and the pipeline's thread stayed up for the life of the process. The backends are closed whether or not there was a thread to stop, and a speaker closed twice still closes them once.
- **Fix: a dictation backend is let go on the loop that owns its pipeline** (`src/zrb/llm/dictation/feature.py`, `src/zrb/llm/dictation/backend/any_dictation_backend.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `test/llm/dictation/test_feature.py`, `test/llm/dictation/backend/test_pipecat_backend.py`): a session's teardown is synchronous, so with no loop of its own to schedule the close on it ran the backend's close to completion on a loop of the teardown's making. A Pipecat pipeline's worker is a task of the loop that started it, and awaiting it from another loop fails — with the cross-loop error `close_quietly` logs, a failure nobody reads — so the session reported the backend closed while the worker, the model and the pipeline ran on, and re-enabling dictation mid-session was enough to reach it. A backend now names the loop it is bound to (`owner_loop`, `None` for one that holds nothing a loop owns) and the close is handed to that loop thread-safely; a backend whose loop has stopped is released rather than closed — what it holds is dropped, so its model can be collected — and the teardown names the worker it could not cancel.
- **Fix: a session that ends mid-recording builds no second backend** (`src/zrb/llm/dictation/feature.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `test/llm/dictation/test_feature.py`, `test/llm/dictation/backend/test_pipecat_backend.py`): recording, hands-free listening and transcription each read the session's backend when they reached it, and `close()` cleared that reference, so audio the teardown released reached a property that built a backend for a session already over — a Pipecat one building a second service and a second pipeline, with nothing left to close either. Each operation now takes the backend once and holds it for its whole length, a closed session refuses to build another, a recording whose session ended is not transcribed (the input box it would be edited in is gone, and the backend was let go), and a Pipecat backend that has been let go refuses to start a pipeline again.
- **Documentation: the voice guide names the Pipecat services a session can listen or speak through, and what each takes to install** (`docs/llm/voice-camera.md`, `docs/llm/voice-photo-troubleshooting.md`, `examples/voice-interaction/README.md`): the guide predated the services, so its two backend tables listed only `vosk`/`openai`/`google`/`multimodal` and `auto`/`termux`/`say`/`espeak-ng`/`openai`/`gemini`, and the advice for a transcriber that mangles technical speech was a cloud key — while `whisper`, `moonshine` and `funasr` transcribe offline through Pipecat, and `kokoro`, `piper` and `pocket` speak that way. Both tables now carry all six, and a table lists what each takes to install, because the `zrb[voice]` extra brings Pipecat but none of its model packages: `pip install 'pipecat-ai[whisper]'`, `[moonshine]`, `[funasr]`, `[kokoro]`, `[piper]` or `[pocket-tts]`. What each platform can run is recorded with it — `piper` on Linux glibc 2.17 and newer, both macOS architectures and Windows; `moonshine` with no x86-64 macOS wheel; none of the six with a native-Termux wheel, so Termux keeps vosk for dictation and the local engines for speech — and so is `kokoro` being uninstallable on Python 3.14, since `kokoro-onnx` declares `requires_python <3.14`. The guide also documents registering a service of your own through `tts_manager`/`stt_manager`, which it did not mention at all, and the troubleshooting page and the `voice-interaction` example name a local service beside the cloud ones they recommended alone.
- **Fix: a Pipecat sentence is not cut off by the end of the session that spoke it** (`src/zrb/llm/speech/player.py`, `test/llm/speech/test_player_lifecycle.py`): the worker thread let the backends go the moment its queue ran out, which is not the moment they stop being read — synthesis runs ahead of playback, so the last sentence is already in the player's hands. For a Pipecat service that backend is a live pipeline: it renders a sentence's audio while the player reads it, and `TTSPipeline.close` cancels the worker and records a failure on the sentence being read, so ending a session during its final sentence cut that sentence off where its audio stopped arriving. The exit `drain`, whose whole purpose is to let queued speech finish, had the same hole, and `SpeechAudio` hands out only its first chunk before playback starts, so the audio was still arriving for as long as the sentence lasted. The player now sets a flag as it stops reading and the worker — the thread that may still be synthesizing when `close` returns — waits for it before letting the backends go; `speak`, which never starts a player, still closes them itself.
- **Fix: a segment that timed out does not answer the segment after it** (`src/zrb/llm/dictation/pipecat_stt.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `test/llm/dictation/test_pipecat_stt.py`, `test/llm/dictation/backend/test_pipecat_backend.py`): `STTPipeline.transcribe` waited for its segment under a 120 s timeout and, on expiry, released the pipeline while the service was still transcribing that segment. A `TranscriptionFrame` names no segment — the recorder can tell one answer from another only by the order they arrive in — so the answer the abandoned segment was still owed was read as the answer to whatever segment was asked for next: a user's previous words taken for their current ones, and acted on by every guard that reads a transcript. Pipecat has no per-segment fix for that: an `InterruptionFrame` only resets the service's own TTFB state, and cancelling the service's segment task would leave it with nothing to transcribe with for the rest of the session. The pipeline is retired instead, which is what does cancel a transcription in flight, and the backend starts another one for the segment after, because a session that is still listening is better served by a fresh pipeline than by one that would fail every segment to come.
- **Fix: a dictation pipeline whose worker stopped is replaced, not kept** (`src/zrb/llm/dictation/pipecat_stt.py`, `src/zrb/llm/dictation/backend/pipecat.py`, `test/llm/dictation/test_pipecat_stt.py`): `PipecatDictationBackend.prepare` asked the pipeline it held whether it was closed before handing it a segment, and `STTPipeline.is_closed` answered for a pipeline zrb had closed itself and nothing else — so a worker that ended on its own was invisible to that question. Pipecat ends a worker without going through `close` in more than one way: a processor pushing an `EndWorkerFrame` upstream takes the pipeline down from the source, a fatal error cancels it from there, and a failure the worker's run task does not survive ends it where it stands. The backend then kept the dead pipeline, `transcribe` saw a finished worker task and raised "the Pipecat worker stopped", and every segment after it failed the same way: hands-free dictation was gone for the rest of the session. That is the case the idle-timeout entry above closed for one cause only; this one closes it for all of them. `is_closed` now reads the worker's own run task beside the flag `close` sets, so a stopped pipeline counts as no pipeline and `prepare` starts the next one before the next recording, at the price of loading the model again. The recording in flight is unaffected: it holds its backend for its whole length, and a session that is still listening is better served by a fresh pipeline than by one that would fail every segment to come.
- **Fix: a dictation teardown survives the loop that owns its backend stopping under it** (`src/zrb/llm/dictation/feature.py`, `test/llm/dictation/test_feature_teardown.py`): `DictationSession.close` asks whether the loop that owns the backend is running before handing that loop the backend's close, and the answer is stale the moment it is given — a loop that shuts down between the two takes no callback, and `call_soon_threadsafe` raises for it. The backend is off the session by then, so the failure escaped with a model and a pipeline running and nothing left to reach them, and it ended the session's own teardown with it. The hand-off now falls back to the release an already-stopped loop takes, which is what keeps a synchronous teardown best-effort; the warning that names the worker it could not cancel is unchanged.
- **Fix: a sentence whose interruption fails does not take the speech pipeline with it** (`src/zrb/llm/speech/pipecat_tts.py`, `test/llm/speech/test_pipecat_tts.py`): a sentence holds the one-sentence lock from the moment it is asked for until its audio has been read or dropped, and `_drop` gave that lock back only after the interruption had been queued. Its handler named `RuntimeError` and `TimeoutError`, so anything else that came out of telling the service to stop escaped with the lock still held — and every later `speak` waited for a sentence that was already over, leaving the pipeline unusable for the rest of the session. The lock is given back in a `finally` now, so that failure reaches whoever dropped the audio as a report about one sentence rather than as a voice that stops working. The types caught are unchanged on purpose: `finally` covers what catching `Exception` would not — a future the loop cancelled, say — and widening the handler would raise the count of swallowed broad handlers that `test_broad_except_ratchet.py` pins at 313.
