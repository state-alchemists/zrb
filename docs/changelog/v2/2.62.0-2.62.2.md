## 2.62.0 (August 13, 2026)

- **Feature: LaTeX math renders as Unicode in assistant markdown** (`src/zrb/util/cli/latex_math.py`, `src/zrb/util/cli/markdown.py`, `src/zrb/config/mixins/llm_ui_styles.py`, `pyproject.toml`): `render_markdown` now converts `$...$` / `$$...$$` LaTeX math spans to Unicode (via `pylatexenc`, a new core dependency) before handing the text to Rich, gated by the new `LLM_UI_ENABLE_MARKDOWN_MATH` toggle (default on), including `^exp`/`_sub` becoming real Unicode super/subscript characters (`x^2` → `x²`) where every character in the run has one. A ` ```latex `/` ```tex ` fenced block is treated the same way -- converted and inlined as flowing text, or left as its original syntax-highlighted fence if it can't be converted -- since a model reaches for a fence around LaTeX at least as often as `$...$`. Fenced code blocks and inline code spans are masked out first so a `$` in a shell snippet is never touched, ambiguous prose like "$5 and $10" is left alone, markdown's own `_italic_` underscores are never touched (super/subscript conversion only ever runs on already-converted math-span output), and any unparseable/unrecognized LaTeX falls back to the raw source instead of failing the render. See ADR-0079.
- **Improvement: the assistant is now shown the expected math syntax** (`src/zrb/llm/prompt/markdown/example.md`): a new example teaches the model to write math between `$...$`/`$$...$$` rather than inside a fenced ` ```latex ` code block, since only the former renders as math in the terminal.
- **Feature: Mermaid diagrams render as Unicode art in assistant markdown** (`src/zrb/util/cli/mermaid_diagram.py`, `src/zrb/util/cli/markdown.py`, `src/zrb/config/mixins/llm_ui_styles.py`, `pyproject.toml`): `render_markdown` now renders ` ```mermaid `/` ```mmd ` fenced blocks as Unicode box-drawing diagrams (via `termaid`, a new core dependency), gated by the new `LLM_UI_ENABLE_MARKDOWN_MERMAID` toggle (default on), entirely in-process with no subprocess or external binary. A fence `termaid` can't parse falls back to the original fence instead of failing the render. Both `pylatexenc` and `termaid` are core dependencies rather than extras: zero transitive dependencies each, and gating a default-on toggle behind an extra would mean it silently renders nothing on a bare install. PlantUML rendering was investigated and deferred: no pure-Python, no-subprocess, no-network option exists for it today. See ADR-0080.
- **Improvement: the assistant is now shown that Mermaid diagrams render** (`src/zrb/llm/prompt/markdown/example.md`): a new example encourages a fenced ` ```mermaid ` block whenever a diagram clarifies structure or flow better than prose, now that it renders as Unicode art instead of raw text.
- **Fix: a Mermaid diagram no longer gets corrupted across a terminal resize** (`src/zrb/util/cli/mermaid_diagram.py`, `src/zrb/util/cli/markdown.py`): Rich's `Syntax(..., word_wrap=True)` -- used unconditionally for every fenced code block -- was word-wrapping a diagram wider than the console mid-line, splitting box-drawing characters across lines; this showed up as diagrams breaking when the terminal was resized narrower, since `rewrap_output` re-renders tracked blocks from source at the new width. `convert_mermaid_to_art` now takes the target console width and shrinks the diagram's gap/padding to fit, mirroring termaid's own CLI `--width` auto-fit, before Rich ever gets a chance to wrap it. See ADR-0080.
- **Improvement: the assistant is now shown to declare a shared Mermaid edge only once** (`src/zrb/llm/prompt/markdown/example.md`): a new example steers away from repeating a parent edge as a prefix for every child in a chain (`P --> G --> G1`, `P --> G --> G2`, ...) -- termaid doesn't dedupe identical edges, so the repeats render as separate, overlapping, tangled arrows into the same node. Declaring the shared edge once and chaining each child separately renders cleanly.
- **Fix: web chat now renders math and diagrams at all** (`src/zrb/llm/task/llm_task.py`, `src/zrb/llm/task/building.py`, `src/zrb/llm/task/chat/running.py`, `src/zrb/runner/chat/http_ui.py`, `src/zrb/runner/web_route/chat_page/chat.js`/`chat.css`/`view.html`, `src/zrb/runner/web_route/static/resources/`): the web chat's non-interactive per-message loop never called any markdown-rendering finalization step, so `$...$` LaTeX and ` ```mermaid ` fences always showed as raw source -- confirmed with a live SSE capture and runtime tracing. `_run_non_interactive_session` now finalizes every attached UI with `append_markdown` (a new `LLMTask.get_uis()` accessor), the same pass the CLI's interactive loop already had; `HTTPUI.append_markdown` sends the raw markdown to the browser (a new `"markdown"` SSE kind) instead of the CLI's ANSI/Unicode-art `render_markdown`, and the browser renders it with `marked` (markdown → HTML, sanitized by DOMPurify), KaTeX (real math typesetting -- solves the `\frac`-as-plain-text limitation the CLI's Unicode approximation can't), and the already-vendored `mermaid.min.js` (real SVG diagrams). Reopening a past session renders the same way. See ADR-0081.

## 2.62.1 (August 14, 2026)

- **Documentation: termaid's authoring hazards mapped from parser source, including a silent-garbage failure mode** (ADR-0080): the significant finding is that an **unsupported diagram type is never rejected** -- type dispatch is a `startswith` chain whose fall-through is the flowchart parser, so `requirementDiagram`, `sankey`, `C4*`, `radar` and `zenuml` render as boxes containing the author's own Mermaid source instead of erroring or returning empty. Alongside it: inline edge labels are unsafe in every arrow style (`-- "t" -->` drops the label, `-- t -->` and `== t ==>` inflate the edge's computed length and stretch the diagram, `-.t.->` fails to parse and collapses the statement into one node), leaving `-->|t|` and its `-.->|t|`/`==>|t|` siblings as the only safe form; an unquoted label containing `>` such as `A[Line1<br/>Line2]` silently loses text because the asymmetric-node pattern matches before the rectangle pattern; `<br/>` becomes a line break only inside a sequence or state `Note`; an `erDiagram` relationship without `: label` renders the entire diagram empty; a `sequenceDiagram` `title` is dropped, `box … end` corrupts block nesting, and a multi-line state `note … end note` injects phantom states. Unrecognized statements go into a parser `warnings` list that nothing ever displays, which is why all of these fail quietly. Each was confirmed against rendered output content, not merely a non-empty return.
- **Refactor: Mermaid syntax rules move from `example.md` into a skill with per-family reference companions** (`src/zrb/llm_plugin/skills/mermaid-diagrams/SKILL.md`, `.../reference/{sequence,class,state,er,charts}.md`, `src/zrb/llm/prompt/markdown/example.md`): 2.62.0's shared-edge-dedup rule and the hazards above now live in a model-invocable `mermaid-diagrams` skill loaded only when the model is about to emit a `mermaid` fence, instead of `example.md` -- one of the seven fixed, always-on prompt sections (ADR-0044) paid for on every turn whether or not a diagram is ever drawn. `SKILL.md` carries the universal rules, the list of diagram types that actually render, and one verified worked example, and is complete for flowcharts so the most-emitted type needs no companion read; per-type syntax is pulled on demand, one companion per diagram family, the progressive-disclosure shape ADR-0053 endorses. Granularity follows section size rather than type count -- sequence/class/state/ER get their own files, the thirteen small chart and layout types share one -- which cut the cost of writing a sequence diagram from 306 lines to 162 against an earlier single-file draft. Because an unread companion is its own failure mode, `SKILL.md` also lists the per-type traps that destroy output silently. The skill states what termaid *supports* as well as what breaks: an errata-only draft left the model guessing whether ordinary constructs like `subgraph` were safe, so it spent tool calls investigating instead of emitting. `example.md` keeps only the general behavioral example (reach for a mermaid fence when it clarifies structure over prose).

## 2.62.2 (August 14, 2026)

- **Feature: attachments are capped and content-sniffed before they reach the model** (`src/zrb/llm/util/attachment.py`, `src/zrb/config/mixins/llm_limits.py`, `src/zrb/llm/ui/base/conversation_commands.py`, `src/zrb/runner/chat/chat_api_route.py`, `examples/chat-telegram/zrb_init.py`): every attachment entry point -- the CLI's `/attach`, the new web chat upload endpoint, and the Telegram example's photo/document handlers -- now rejects a file over the new `LLM_MAX_ATTACHMENT_BYTES` (default 20MB, `0`/negative disables) before reading it, and checks the file's magic bytes against its declared media type (`sniff_mismatch`/`check_attachment_bytes`) so a renamed file can't masquerade as an image or PDF. Path-based callers check size against the file on disk (`get_oversized_by`); callers that already hold the bytes in memory (web upload, Telegram) use `check_attachment_bytes` instead.
- **Feature: web chat supports file attachments** (`src/zrb/runner/chat/chat_api_route.py`, `chat_session_manager.py`, `chat_session_runner.py`, `src/zrb/runner/web_route/chat_page/{chat.js,chat.css,view.html}`): a new `POST /api/v1/chat/sessions/{id}/attachments` endpoint saves an uploaded file to a per-session temp dir after the same size/sniff checks, and the chat page gained an attach button, a pending-attachment chip list, and per-message attachment display. Queued messages now carry `{message, attachments}` end to end (input queue, `send_input`, the `attach` CLI-input key) instead of message text alone.
- **Feature: `chat-telegram` example accepts photo and document attachments** (`examples/chat-telegram/zrb_init.py`, `README.md`): a Telegram photo or document (with optional caption) is downloaded, run through the same size cap and magic-byte check as the CLI and web paths, and queued as a pending attachment for the turn.
- **Feature: replayed and web-displayed history separates auto-appended live context from what the user actually typed** (`src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/ui/base/replay.py`, `src/zrb/runner/chat/chat_session_manager.py`, `src/zrb/runner/web_route/chat_page/{chat.js,chat.css}`): a new `split_live_context` pulls the trailing `<live-context>` block off a stored user message, since history persists it inline appended to the user's own text with no structural tag. The CLI's replay and the web chat's message list both render it as separate, de-emphasised metadata rather than inside the user's bubble.
- **Feature: document input is a tracked model capability** (`src/zrb/llm/util/capabilities.py`): `ModelCapabilities` gained `supports_document_input` (PDF/docx/xlsx/doc/xls as opaque binary; plain-text formats like txt/csv/html/md are unaffected since any model reads those as text regardless), tracking the same provider pattern list as image support.
- **Improvement: more models registered in the vision/audio capability pattern lists** (`src/zrb/llm/util/capabilities.py`): added image support for `claude-fable-5`, `claude-mythos`, `claude-opus-5`, `claude-sonnet-5`, `grok-3`/`grok-4` (with a `grok-3-mini` deny override), `glm-4.5v`/`glm-4.6v`/`glm-5v`, `moonshot-v1-*-vision`, and `computer-use`; added audio support for `whisper`.
- **Refactor: the Mermaid-authoring skill moves from `skills/` to `core_skills/`** (`src/zrb/llm_plugin/{skills/mermaid-diagrams → core_skills/core-diagram}/`, ADR-0054, ADR-0080): its rules are the difference between a diagram the user can read and one silently mangled by termaid's fall-through parsing on every `mermaid` fence the agent emits, not an optional convenience -- so it now loads regardless of `LLM_ENABLE_BUILTIN_SKILLS`, alongside the other correctness-critical `core-*` skills.
