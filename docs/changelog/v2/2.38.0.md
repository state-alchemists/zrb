## 2.38.0 (June 20, 2026)

- **Refactor: configurable semantic CLI color layer** (`src/zrb/config/mixins/cli_style.py`, `src/zrb/util/cli/style.py`, ADR-0027): physical color helpers (`stylize_yellow`, `stylize_red`, etc.) are unchanged; the semantic layer (`stylize_warning`, `stylize_error`, `stylize_muted`, `stylize_highlight`, `stylize_info`, `stylize_success`, `stylize_todo_project/context/keyval`) now reads from a new `CLIStyleMixin` so colours are configurable via `ZRB_CLI_COLOR_*` / `ZRB_CLI_STYLE_*` env vars. Defaults reproduce prior behaviour. `stylize_faint` and `stylize_log` remain as backward-compat aliases for `stylize_muted`. All ≈90 call sites across 21 files migrated from physical to semantic helpers; git-diff colours preserved as intentional physical calls.
- **Feature: uniform task-level hook registration** (`src/zrb/llm/task/llm_task.py`, ADR-0072): `LLMTask` gains `add_hook_factory`/`append_hook_factory`, matching `LLMChatTask` — both task types now register hooks through the same verb (`task.add_hook_factory(lambda mgr: mgr.register(hook, events=[...]))`). To prevent leaks, an `LLMTask`'s first `add_hook_factory` call swaps the shared global hook manager for a fresh per-task one, so its hooks stay isolated by default; pass `hook_manager=` at construction to opt into a specific (or the global) manager instead. `LLMTask` also gains a `history_manager` get/set property (symmetric with `LLMChatTask`). New `examples/lsp-config` and `examples/live-context` exercise the prompt-manager and LSP-registry surfaces.
- **Feature: user-extensible LSP server registry** (`src/zrb/llm/lsp/configs.py`, `src/zrb/llm/lsp/manager/manager.py`): a new `LSPServerConfigRegistry` (module singleton `lsp_server_configs`) seeds from the built-in `LSP_SERVER_CONFIGS` table and accepts user overrides. Call `lsp_manager.register_lsp_server(name, LSPServerConfig(...))` from `zrb_init.py` to add a language the built-in catalogue doesn't cover (or override a built-in of the same name). The detection/selection helpers (`detect_available_lsp_servers`, `get_lsp_config_for_file`, `detect_language_from_file`) and the `LspListServers` tool now resolve through the registry, so registered servers participate in auto-detection, file-extension matching, and `ZRB_LLM_LSP_PREFERRED_SERVERS` ordering. Documented in [LSP Support → Custom LSP Servers](../../llm/lsp-support.md#custom-lsp-servers).
- **Feature: partial-run retry context** (`src/zrb/llm/agent/run/partial_run.py`, `agent/run/runner.py`, `task/llm_task.py`): when a turn is cancelled (Escape) or fails on an unrecoverable error, zrb captures the tool calls and results streamed before the interruption (`PartialRunAccumulator`) and appends a `[SYSTEM: PREVIOUS ATTEMPT FAILED]` summary to the saved history: completed tool calls (args and truncated results), whether a text response was cut off, and the error. The next turn continues from that work instead of repeating it. The summary is added only when at least one tool completed; the list is public as `PartialRunAccumulator.completed_tools`.
- **Feature: programmable per-turn live context** (`src/zrb/llm/prompt/live_context.py`, `prompt/manager.py`, `prompt/__init__.py`): the volatile `<live-context>` block (time, git, todos, worktree, mode) — split out of `system_context.py` into its own `live_context` module — is now extensible. `prompt_manager.add_live_context(name, provider)` registers a `Callable[[AnyContext], str]` whose output is appended to the block on every user turn (return `""` / `None` to emit nothing; re-registering a name replaces it). Unlike `register_section` (which adds to the cached system prompt), live-context providers carry runtime state that changes each turn without invalidating the cacheable prefix. Documented in [Programming the Prompt → Rung 6 — sections that reflect live state](../../llm/programming-the-prompt.md#rung-6--sections-that-reflect-live-state).
- **Feature: Shift+Tab cycles interaction modes** (`src/zrb/llm/ui/base/model_commands_mixin.py`, `src/zrb/llm/ui/default/keybindings_mixin.py`, `src/zrb/llm/app/layout.py`, `src/zrb/llm/app/keybinding.py`, ADR-0075): in the default chat UI, `Shift+Tab` cycles `normal -> auto-accept-edits -> plan -> normal`, as in Claude Code. Auto-accept-edits auto-approves `Write` and `Edit`; shell, delegation and fetch still prompt. The status bar shows a mode badge (`normal`/`accept-edits`/`plan`, or `yolo`/`custom-yolo` off-cycle) and a `shift+tab to cycle` hint; off-cycle yolo re-enters the cycle at `normal`. CLI only: the web UI and MultiUI keep `/plan` and `/yolo Write,Edit`.
- **Change: `F6` is the sole focus toggle and `Ctrl+P` is retired** (`src/zrb/llm/app/layout.py`, `src/zrb/llm/app/keybinding.py`, ADR-0075): `Tab`/`Shift+Tab` no longer move focus (Escape also returns to input). `Tab` still navigates an open completion menu, and `Shift+Tab` keeps back-tab in a completion menu and the `AskUserQuestion` choice widget. `/plan`, `/yolo`, `Ctrl+Y` and `EnterPlanMode`/`ExitPlanMode` are unchanged, and `/help` lists the new keys.
- **Feature: mode badge and info-bar colors are configurable** (`src/zrb/config/mixins/llm_ui_styles.py`, `src/zrb/llm/app/style.py`): prompt_toolkit style strings defaulting to the old hardcoded colors — `ZRB_LLM_UI_STYLE_MODE_NORMAL/ACCEPT_EDITS/PLAN/YOLO/CUSTOM`, `ZRB_LLM_UI_STYLE_INFO_YOLO_ON/PARTIAL/OFF`, `ZRB_LLM_UI_STYLE_INFO_PLAN_ON/OFF` and `ZRB_LLM_UI_STYLE_CHOICE_BG/CHOICE_SELECTED_BG`.
- **Fix: close three more Claude-Code hook contract gaps** (`src/zrb/llm/hook/hook_creators.py`, `src/zrb/llm/agent/common.py`, `src/zrb/llm/hook/matcher.py`):
  - An `exit 2` hook's block reason is read from stderr, the Claude convention: a stdout JSON `reason` wins, then stderr, then plain stdout, then `"Blocked by hook"`. `echo "reason" >&2; exit 2` used to lose its reason; stdout-based hooks are unaffected.
  - `PostToolUse` `additionalContext` is appended to the tool result the model sees; it was dropped.
  - `Notification` matchers filter on `notification_type` (e.g. `elicitation_dialog`), not the `message` text. zrb still emits `Notification` only for elicitation, not for permission prompts (those go to `PermissionRequest`) or a 60s idle timer.
- **Documentation: hooks guide states the Claude-Code incompatibilities explicitly** (`docs/advanced-topics/hooks.md`): dropped the "100% compatible with Claude Code hooks" claim and added a [Differences from Claude Code](../../llm/claude-compatibility.md#differences-from-claude-code) section covering the behavioral divergences that change outcomes (sequential+priority vs parallel+most-restrictive execution, first-only `additionalContext`, `PostToolUse` block discarding the result, `ask` degrading on the execution path, observe-only `SubagentStop`, `Notification` firing scope, ignored legacy `decision:"approve"`), matcher-value coverage gaps, and the events/types zrb does not implement.
- **Feature: four more Claude-Code hook events** (`src/zrb/llm/hook/types.py`, `agent/run/runner.py`, `agent/run/error_classifier.py`, `tool/delegate.py`, ADR-0071):
  - `PostCompact` fires after history summarization with `trigger="auto"` and honors `additionalContext`.
  - `StopFailure` fires, observe-only, when a turn ends on an unrecoverable API error. Its `error_type` is `rate_limit`, `overloaded`, `server_error`, `context_length`, `authentication_failed`, `invalid_request`, `model_not_found` or `unknown`.
  - `SubagentStart`/`SubagentStop` fire around sub-agent delegation (single and parallel; Stop always fires) with `agent_type` and a shared `agent_id`, on the parent run's hook manager.
  - New matcher fields: `agent_type` for the sub-agent events, `error_type` for `StopFailure`, `trigger` for `Pre`/`PostCompact`. Claude `settings.json` configs using these events now register instead of being skipped.
- **Fix: `UserPromptSubmit` populates the `prompt` field** (`agent/run/runner.py`): the fire now passes `prompt=`, so UserPromptSubmit matchers (mapped to `prompt`), the `CLAUDE_PROMPT` env var, and the stdin payload see the submitted text — previously `None`.
- **Fix: Claude-standard tool fields in hook payloads** (`src/zrb/llm/agent/common.py`, `src/zrb/llm/hook/`, ADR-0071): `PreToolUse`, `PostToolUse` and `PostToolUseFailure` payloads carry `tool_name`/`tool_input` (and `tool_response` on `PostToolUse`). They were missing, so tool-name matchers such as `{"matcher": "Bash"}` never matched and hooks reading `tool_input` saw nothing. `SessionEnd` matchers filter on `source`, which is always `"other"` for now. Unstructured stdout from a `SessionStart`/`UserPromptSubmit` command hook becomes `additionalContext`; a JSON object is still read as the control protocol.
- **Fix: hook decisions for overlapping events follow Claude Code** (`src/zrb/llm/agent/run/`, `src/zrb/llm/hook/`, ADR-0071): `exit 2` / `decision:"block"` halts the hook chain only for blocking-capable events. `PreCompact` can block summarization; the hard context-window prune still runs. `PreToolUse` `permissionDecision: "ask"` forces the approval prompt over tool policy, permission ALLOW and YOLO, but not an explicit DENY (with no prompt available it proceeds); `"defer"` is a no-op. `continue:false` always halts: it ends the `run_agent` turn before the model runs on `UserPromptSubmit`, and overrides any `Stop` block or `systemMessage` extension.
- **Improvement: Claude tool-name aliases for hook matchers** (`src/zrb/llm/hook/matcher.py`): zrb's built-in tools already expose Claude-compatible names via `func.__name__` (`Read`, `Write`, `Edit`, `Grep`, `Glob`, `LS`, `Bash`, `WebFetch`, `WebSearch`, `TodoWrite`, `TodoRead`, …), so most Claude hook matchers keyed on a tool name match directly. For the few zrb tools whose name still differs, a new `CLAUDE_TOOL_ALIASES` map lets a tool-name matcher also accept the Claude name: `Shell` → also matches `Bash`, and `DelegateToAgent`/`DelegateToAgentBackground` → also match `Task`. `evaluate_matchers` tests the value plus its aliases and passes if any matches; `not_equals` stays 1:1 so an exclusion filter is never widened by an alias.
- **Fix: a hook command killed by a signal is no longer logged as a failure** (`src/zrb/llm/hook/hook_creators.py`): on Ctrl+C the terminal delivers `SIGINT` to the whole process group, so a running command hook's subprocess exits with a negative return code (`-2`). That fell into the generic error branch and surfaced as a spurious `ERROR: Command hook failed: Command failed with exit code -2` during normal interrupt/teardown. Signal deaths (`exit_code < 0`) are now handled as a quiet, debug-level non-failure that names the signal (e.g. `SIGINT`).
