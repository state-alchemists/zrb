## 2.53.2a1 (August 3, 2026)

- **Fix: a wrong `agent_name` sent the model back to re-read a description it had already misread** (`src/zrb/llm/tool/delegate.py`, `src/zrb/llm/tool/delegate_background.py`, `test/llm/tool/test_delegate_tool.py`, `test/llm/tool/test_delegate_background.py`): the not-found error read *"Check DelegateToAgent's description for available sub-agents, or check agent registration in your zrb config"* — it named no agent, offered no near-match, and instructed the model to consult the very text whose misreading produced the error, so the next attempt was another guess. `agent_name` is an unconstrained `str`, so nothing upstream catches a bad one either. The new `agent_not_found_message` lists the roster and leads with the closest match, which is what the common failures need: `general-purpose` → *Did you mean 'generalist'?*, `research` → *'researcher'* — the misses are near-misses or names carried over from another harness's roster. With no agents registered at all it says so and stops, rather than inviting a retry against an empty list. **`DelegateToAgentBackground` was worse off**: its docstring said only *"REQUIRED ARGS mirror DelegateToAgent"*, so the valid names appeared nowhere in its schema and the model had to recall them from a sibling tool, and because the run detached immediately an unknown agent returned *"Started background agent 'reseacher'. Handle: …"* — the failure surfaced only at `GetDelegationResult`, if it was ever polled. It now carries the same `AVAILABLE AGENTS` roster (extracted as `agent_roster_doc`, shared by both tools) and resolves the name before detaching, so a bad name fails at call time and mints no handle.

- **Improvement: the rule for *whether* to delegate never pointed at the roster for *which* agent** (`src/zrb/llm/common_tools.py`, the `description` of all three agents under `src/zrb/llm_plugin/agents/`): skills keep their catalogue and their matching rules adjacent — `workflow.md` carries `{AVAILABLE_SKILLS}` right beside the prose that says how to match against it. Delegation split them: `tool_guidance` held ~150 words on when to delegate and named no agent, while the roster lived in the tool schema, and nothing connected the two. `DelegateToAgent`'s `key_rule` now makes the hop — pick by matching the description under `AVAILABLE AGENTS` in the tool's own schema, the names there are exact and the only valid ones, never adapt a name from another harness's roster (the last clause is the observed failure: `general-purpose` and `Explore` are Claude Code's names, not zrb's). `DelegateToAgentBackground` gets the same pointer now that it carries its own list. The three built-in descriptions all ended with a variant of *"to keep your primary context clean"* — identical across the roster, so it discriminated nothing while diluting the clause that did. Each now leads with what actually separates it: `generalist` can write and holds the full tool set, `researcher` gathers what is not in context and returns a report rather than quotable text, `code-reviewer` judges code that already exists and does not fix it. Each states its own capability only — a description cannot say it is *the only* agent that can write, since user- and project-defined agents join the same roster. `key_rule` also gained one clause and lost weight overall. The clause: *"Do NOT delegate when you need verbatim text to quote"* was being read as governing the whole turn, when it only rules out delegating **the part you quote** — so the call is now stated as **per unit of work, not per turn**, sitting immediately after the sentence it qualifies rather than several sentences away. The rest was compression: the bullet had reached 200 words across seven sentences, which is the qualifier-dropping shape that makes a rule invisible in the first place; it is now 129. No rule was added telling the model to fan out more readily on a broad request. That was drafted and dropped: how far to scope *"analyze the source code"* has no single right answer, so a rule (or a worked example) asserting one would have traded a judgment call for a reflex — over-fitting the guidance to one incident.
- **Feature: the journal HUD now carries the user's identity and preferences, not just links to them** (`src/zrb/llm/prompt/markdown/journal_mandate.md`, `src/zrb/llm_plugin/core_skills/core-journaling/SKILL.md` and its new `templates/journal-index.md`, `src/zrb/llm/prompt/live_context.py`, `src/zrb/config/mixins/llm_content.py`, `test/llm/prompt/test_live_context.py`): the root `index.md` is the only journal file that reaches a session without anyone searching for it — `render_journal_index` injects it on the first turn and at each summarization, deliberately outside the cached prefix (ADR-0082). Every description of it said so: `SKILL.md` called it *"HUD: critical user prefs, active constraints, recent insights"*, and ADR-0087 decided a stated preference should *"record on the turn it is stated, **add to the HUD**, honour immediately."* But no write path ever put a fact there. The single step touching the HUD said *"add a link from outer `index.md` under Recent Insights"*, `SKILL.md` treated *"inlined preferences"* as the **user's** hand-shaping to be preserved rather than something the model produces, and `journal_mandate` described the file as *"the map of what exists"* — navigational, contradicting its own skill. So the user's name lived in a `preferences/` note that a session had to already suspect existed in order to search for. Worse, truncation compounded it: the snapshot was capped at a hardcoded 1000 chars, sliced **head-first and mid-word**, and the only thing the model was taught to add was an unbounded list of *Recent Insights* links — which accumulate at the top and evict exactly the identity the HUD exists to carry. `journal_mandate` now names the file as the HUD, states that it is already in context (so turn 1 need not re-`Read` it), and routes a stated preference into it compressed to a line alongside its note. `core-journaling` gains a **fixed section order** — user → preferences → active constraints → recent-insight links last — chosen because overflow drops from the end: the near-static sections are cheap and the growing one costs nothing when it is last. Step 7 now inlines the fact for identity and preferences and links for everything else, and `templates/journal-index.md` gives the shape so it is not reinvented per session. On the mechanical side the cap moved to `LLM_JOURNAL_INDEX_MAX_CHARS` (default raised 1000 → 2500, since identity plus preferences plus a link list does not fit in ~150 words) and now cuts on a line boundary — a mid-word slice left the last surviving entry as a fragment, and half a sentence about the user is worse than none.

  Three follow-ups from watching a real session create a journal from scratch (`test/llm_plugin/test_core_journaling_template.py` is new):
  - **The HUD template contradicted the linter that ships beside it.** `journal-lint.py` measures NO ORPHANS as reachability *from the root index*, and the template's four prescribed sections linked to no directory index — so a HUD written exactly to spec produced one orphan per top-level directory, and the first lint of a brand-new journal reported ten issues. The model then improvised a `## Directories` section that exists in no template, after visibly deliberating over whether "order is fixed" forbade it. `Directories` is now section 4 of five — before the unbounded `Recent Insights` so its one line never grows into anything, and after the facts so it can never evict them — and both the template and `SKILL.md` now state the HUD's two jobs explicitly: sections 1–3 hold facts, 4–5 carry reachability. The new test builds a journal from the template's own worked example and lints it, with a companion test asserting the lint still fails when the directory links are removed, so the two cannot drift apart again.
  - **"It is injected into this conversation already" was stated unconditionally and is false on a fresh journal** — `render_journal_index` returns `None` when the index is missing. The model noticed the contradiction and spent a deliberation cycle on it. The claim is now conditional, and names the absent-`<journal-index>` case as "empty or not yet created" rather than leaving it to be interpreted.
  - **"Writes are silent" collided with reporting a visible change.** Creating the journal puts ten new files on the user's disk, which `persona.md` requires a closing line for, while the journal protocol forbade any sentence about a write. The rule now carves that out — creating the tree is a filesystem change and gets its one line; appending to a journal that already exists stays silent — and says explicitly that the silence covers narration *while working*, not only the final reply.
- **Fix: a self-chosen scope could reach the reader as a complete answer** (`src/zrb/llm/prompt/markdown/workflow.md`): Verify's **Completeness** criterion works by ticking stated requirements off a list — *"a numbered or bulleted ask is a checklist, not a theme"* — so a one-line request broad enough to have no enumerable requirements gives it nothing to bite on. Asked to "analyze zrb source code" (56,808 lines, no files named), the model read a ~2,400-line slice, skimmed two subsystems, and reported; the skim surfaced only when the user asked why it had not delegated, and the answer that followed described the slice as *"the exact files to read"* — a scope it had chosen, restated as one the task had given. The rationalization is downstream of the silence: a choice never stated is a choice that needs a justification invented for it once challenged. **Trade-offs named** now covers scope explicitly — a request broad enough that you had to pick its scope is a judgment call like any other, so name what you covered and what you left in the reply that delivers it, unprompted. Choosing the scope stays legitimate; letting the reader assume you covered everything does not. Deliberately *not* fixed here: how far to narrow such a request. That has no single right answer, and a rule (or worked example) asserting one would trade a judgment call for a reflex — see the delegation entry above, where the same over-fit was drafted and dropped.
- **Fix: the anti-rumination rule's escape hatch pointed back into tool-calling** (`src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/ask.py`, `test/llm/tool/test_ask.py`): the uncertainty ladder's stall-breaker read *"On a third pass over the same evidence, go back to step 1 or take the exit the ladder gives you"* — and step 1 is *make a tool call*. The one rule written to end a deliberation loop routed straight back into it, producing an alternation of tool call and re-think that nothing else bounded. Step 1 is self-graded (*"a tool call **can** settle it"*) and another `Grep` always looks like it might, while `Recovery` covers a repeating **error**, never a call that succeeds without narrowing the question. The rule now names that case as evidence-free and closes step 1 on the third pass, leaving step 2 (act on the best-supported option, assumption named) or step 3 (ask). Investigation-first is untouched: the counter resets on any call that does narrow the question — explicitly including one that *rules a candidate out*, the commonest form of progress a model might not score as progress — so a genuine multi-file investigation never trips it, and "that returned nothing useful" cannot be applied to every result as an exit. The exits are also ordered against premature bailing: step 2 *acts*, and step 3 costs the model an explicit statement of the fork it is choosing between. No step 0 for user-intent ambiguity was added — `AskUserQuestion`'s `when_to_use` in `common_tools.py` already states that condition, and `tool_guidance` composes *after* `workflow`, so by `mandate.md`'s own precedence rule it already wins in its own scope; a second copy would be the cross-section duplication `AGENTS.md` forbids. Both `[SYSTEM SUGGESTION]` short-circuits in `ask_user_question` — non-interactive mode and no-UI — offered only *"make your best judgement and continue"*, which hands an unanswerable question straight back to the deliberation that raised it. They now offer two terminal exits, decide-and-continue with the assumption named or stop-and-report the choice that could not be made, and forbid a retry, so an unavailable question cannot become a re-ask loop.
