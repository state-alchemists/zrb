## 2.55.0 (August 5, 2026)

A benchmark run of 156 cells across five models (`gpt-4o-mini`, `gemini-2.5-flash`, `gemini-3.5-flash`, `deepseek-v4-flash`, `gemma4:31b-cloud`) produced ten non-excellent outcomes. Every one traced to a rule the prompt already stated and the model did not follow, or to a harness defect no rule could reach. Per ADR-0098's ladder, the fixes go to the runtime where the runtime can hold them.

- **Reverted: the runtime anti-loop guards do not ship** (`command_repetition.py`, `file_freshness.py`, `shell.py`, `file_write.py`, `file_edit.py`, `file_read.py`, `post_write_check.py`, `llm_limits.py`, ADR-0102): the write-freshness refusal, the blind-edit-streak nudge, and the repeated-outcome counter built up in this window are all removed before release. The mechanism's own evidence argued against shipping it — an injected instruction is the weakest lever for the exact model that needs it (an escalated "stop and report" was ignored 22 times), the stale-write refusal is a hard block carrying the most cross-tool accounting state in the tool layer, and every component that measurably made models worse (invocation-counting, the post-write escalation ladder) was already reverted within this same history. The prompt's Recovery ladder stands on its own again. ADR-0102 is consolidated to a short historical record whose surviving lessons are general (a tool policy is an approval chain that never sees a result; a synchronous tool cannot keep state in a `ContextVar`; an injected instruction must be bounded and never regenerate its own input).
- **Reverted: `post_write_check` no longer tells the model to fall back to a whole-file `Write`** (`src/zrb/llm/tool/post_write_check.py`): the 2.52.0 advice to stop patching and rewrite the whole file once a file had failed twice is gone. It belongs to the same escalation family the window measured as harmful — a whole-file rewrite by a small model regenerates the diagnostic that issued the instruction — and with the freshness guard removed it had nothing to be the escape hatch for. The remaining guidance asks for a re-read and *one targeted fix*, and names the file to fix instead when the error points outside it.
- **Fix: an unbounded shell command spent minutes being printed and was killed by its own timeout** (`src/zrb/llm/tool/shell.py`, `src/zrb/config/mixins/llm_limits.py`): `_read_stream` echoed *every* line to the console and accumulated *every* line in RAM, truncating to `LLM_MAX_OUTPUT_CHARS` only at the end. Three trials ran an unscoped `git diff` in a repo carrying ~2,948 dirty changes — including previous trials' history JSONs, each holding a full serialized system prompt — and produced ~139MB apiece. The logs contained **3,777 copies of the zrb system prompt**. At roughly 1.4M lines, each costing a regex substitution, a `stylize_muted`, and a `zrb_print`, the display alone outran the 120s timeout; the model received 97,976 chars regardless. Those three cells ran at ~3× their siblings (177s vs 53–60s, 242s vs 75–93s, 249s vs 99–105s) and still scored EXCELLENT, so nothing in the report showed it. Capture is now a `_StreamCapture` with three separate budgets: a tail-biased in-memory retention bounded by `LLM_MAX_OUTPUT_CHARS`, a console echo bounded by the new `LLM_MAX_CONSOLE_OUTPUT_CHARS` (default 1,000,000 — 10× the model-facing cap, so a normal build still scrolls in full), and a spill file opened exactly when the first character would be dropped and streamed into the dump with `copyfileobj`. The full-output promise is unchanged; it just is not resident any more.
- **Fix: a command killed mid-write was diagnosed as a hung process** (`src/zrb/llm/tool/shell.py`): the `timed_out` branch fired before any output inspection, so every timeout produced "the process is still running in the background… use `ps aux | grep <process_name>`… pass `-y` or `CI=true`". For a `git diff` that emitted 139MB, all three claims are wrong and it sends the model hunting for a process that is already dead. A timeout that also truncated now reports the character count, says plainly that the command was writing rather than waiting on input, and names the remedy — scope it, add a summarizing flag, pipe through `head`, or redirect and Grep. The quiet timeout keeps the original wording. Two branches that were unreachable behind `timed_out` (`lock`, `permission denied`) are reachable again as a side effect.
- **Fix: the parallel-tool-call affordance was unreachable code** (`src/zrb/llm/prompt/system_context.py`, `src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/file_read.py`, ADR-0101): `_resolve_parallel_tool_calls` is a deny-list — it returns `False` for `minimax-m2.7` and `glm-4.7`, `None` for everything else, and `True` for nothing. So `_format_parallel_tool_call_line`'s affirmative branch could never render, while `workflow.md` gated batching on exactly that line appearing ("where System Context says the model supports it"). Every model read the rule as unsatisfied. Wall clock on the 44-site migration challenge tracks round-trips, not calls: `gpt-4o-mini` ran the same task at 7.35 calls/response in 168s and at 2.62 in 434s, and a third trial issued 236 calls and timed out at 600s. `gemini-3.5-flash` averaged 1.04 across 583 responses. Batching is now the unconditional default in `workflow`; System Context emits only the negative, so a model that cannot batch overrides the default explicitly and there is no affirmative branch left to fall out of sync. `read_file`'s docstring carries the same instruction at the point of use, plus the corollary the run also surfaced — prefer one wide range over repeated 20-line slices of the same file. Because a tool description is static and cannot be withheld per model, it names its own exception ("unless System Context says this model cannot batch"), and the override line says explicitly that it outranks the workflow rule *and* any tool description — for a deny-listed model that line is the only mechanism that works, since Ollama-cloud ignores the request-level flag.
- **Docs: "does not support parallel tool calls" is three different things** (`src/zrb/llm/util/capabilities.py`, `src/zrb/llm/agent/common.py`): `_NO_PARALLEL_TOOL_CALLS` is only for models that **malform** parallel calls — the destructive case, where two calls arrive concatenated as one and both are lost. Two neighbouring behaviours must stay off it. A model whose provider **rejects the parameter** (OpenAI's o-series: "Unsupported parameter: 'parallel_tool_calls' is not supported with this model"; kimi-k2.5 behind NVIDIA NIM: "This model only supports single tool-calls at once!") would have `_apply_capability_constraints` send the very argument that 400s every request — a worse failure than the batching it prevents; supporting those needs the field split in two. A model that simply **never emits more than one call** (gpt-oss via Ollama, most small local models) needs nothing at all: encouragement to batch is a no-op, the model issues one call and the turn proceeds.
- **Improvement: two verification instruments that running the code cannot provide** (`src/zrb/llm/prompt/markdown/workflow.md`): the two newest failures came from models that *did* run their code, which caps what "run it" buys. `gemini-3.5-flash` produced the best trajectory in the run — 22 calls, four executions, an env-override test, `py_compile`, scratch-file cleanup — and still shipped `DB_PASS = os.getenv("DB_PASS", "password123")`, documented in the module docstring; the script behaves identically either way, so no execution could catch it. `gemma4:31b` wrote a module-level `asyncio.Lock()`, which passes the first `asyncio.run()` and raises on every subsequent one — the instruction said "run it to reproduce", and one run shows green. The Verify gate's trailing grep clause is promoted to a named check covering any remove/replace/stop-using requirement, and a second names the double run, with the general cases it catches (a client bound to a dead loop, a cache, a temp file, a migration, an import-time global).
- **Improvement: `core-design` no longer swallows the document** (`src/zrb/llm_plugin/core_skills/core-writing/SKILL.md`, `core-design/SKILL.md`): both descriptions opened "Activate when the turn produces…", which reads as a partition — so an ADR, a written document *about* a design, went to `core-design` alone. On the ADR challenge the only trial that also activated `core-writing` scored 1.0; the two that took `core-design` alone scored 0.875 and 0.5, the failure being an ADR emitted with no heading markup at all. `core-writing` owns "Before finalizing, `Read` the file back" and the named-heading-level rule; `core-design` has neither, and no core skill mentioned ADRs. `core-writing` now names the case (ADR, RFC, design doc, postmortem, migration guide) and `core-design` says it covers the thinking, not the document.
- **Fix: re-writing a journal note destroyed the backlinks other notes had added** (`src/zrb/llm/tool/journal_write.py`, ADR-0099): `write_journal_note` composes the whole file from its arguments and truncates, but `## Backlinks` is written by *other* notes via `_add_backlink` and is not the caller's to supply. Linking B from A and then updating A dropped A's way back to B while B kept its forward link — the `missing-backlink` half-edge the deleted `journal-lint.py` used to catch, produced by the writer that replaced it. `## Related` had the mirror problem in the other direction. Both blocks are now merged rather than rebuilt, so a link is only ever added.
- **Fix: a cancelled response killed the `MultiUI` message loop** (`src/zrb/llm/ui/multi_ui.py`): `_process_messages_loop` re-raised every `CancelledError` from the job it was awaiting, so a cancel aimed only at the current response propagated to the loop's own handler and broke out of it — no further user message would ever be processed. Swallowing them all (the previous behaviour) was the opposite bug: a shutdown cancel arriving mid-job was discarded and `await self._process_messages_task` never returned. It now uses `current_task().cancelling()` to tell the two apart, the same guard `base/ui.py`'s twin already used. Latent rather than observed — nothing cancels `MultiUI._running_llm_task` today, since the child UI's Escape handler cancels its own.
- **Improvement: `write_todos` binds completion to verification** (`src/zrb/llm/tool/plan.py`): the docstring is read at exactly the moment a model claims something is done, so it now says an item reaches `completed` only once its work is done *and* verified — never on intent, never because the edit landed. An item awaiting verification or blocked stays `in_progress`, the latter gaining a follow-up naming the blocker.
- **Docs: corrected stale references after the parallel-tool-call and journal changes** (`AGENTS.md`, `docs/technical-specs/llm-context.md`): `system_context` no longer announces *whether* a model supports batching — ADR-0101 left it announcing only the exception, so the section description says that instead. And the journal-index note claiming `SearchJournal`'s own description tells the model that a missing index block is not proof of an empty journal is corrected to the truth, matching `render_journal_index`'s docstring: nothing tells the model that any more, a known gap that only matters when `LLM_JOURNAL_INDEX_MAX_CHARS` is `0` while the journal tools stay registered.
- **Improvement: the Working Loop stopped being a per-turn classification problem** (`src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/prompt/markdown/examples.mini.md`): the four-row routing table (`conversational` / `inquiry` / directive-you-can-specify / directive-you-cannot-yet-specify) asked the model to categorize the turn before every loop run, and its two soft rows blurred into each other. The table now has three stances defined by the deliverable — an **answer** (reply from what you know, no forced codebase tie-in), a **proposal** (investigate to a verdict, await approval before any write), a **change** (autonomous, lands per *Where the deliverable goes*) — and `Frame the turn` merely names the deliverable in those three words, so the "classification" is the frame, not a separate decision. The "can't yet specify" case and the `EnterPlanMode` trigger keep their prose; "Between the first two rows, prefer conversational" and the `Loop steps before Verify` column are gone, the loop following from the stance instead. `examples.mini.md`'s guarded row-by-row walk-through is rewritten to the three stances.
- **Improvement: three redundant rules trimmed out of `workflow.md`** (`src/zrb/llm/prompt/markdown/workflow.md`): `Turn Sequence` dropped `First look` (it existed only to classify the turn, which framing now does) and the closing *"Only step 1 may end the turn"* softened to *"Within this sequence"* — as written it contradicted *When you don't know*'s ask-one-question rule, which ends turns later. `Verify Before Done`'s `Evidence` bullet is gone: claim-to-source already lives in `persona`'s `Verify before you assert` / `Cite inline`, so the gate keeps only artifact checks — the one place the split no longer forces a reader to decide which half owns the rule. The intro now states the compress-vs-verify tie-break explicitly ("brevity shapes the report, never the check") instead of leaving it to priority inference. `Tool usage` leads with the batching rule (the most-invoked mechanic of the section, and the review that flagged it buried it last-but-one), and the stall line in *When you don't know* is compressed since `Recovery` already owns the not-converging ladder.
