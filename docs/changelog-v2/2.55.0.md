## 2.55.0 (August 5, 2026)

A benchmark run of 156 cells across five models (`gpt-4o-mini`, `gemini-2.5-flash`, `gemini-3.5-flash`, `deepseek-v4-flash`, `gemma4:31b-cloud`) produced ten non-excellent outcomes. Every one traced to a rule the prompt already stated and the model did not follow, or to a harness defect no rule could reach. Per ADR-0098's ladder, the fixes go to the runtime where the runtime can hold them.

- **Fix: an unbounded shell command spent minutes being printed and was killed by its own timeout** (`src/zrb/llm/tool/shell.py`, `src/zrb/config/mixins/llm_limits.py`): `_read_stream` echoed *every* line to the console and accumulated *every* line in RAM, truncating to `LLM_MAX_OUTPUT_CHARS` only at the end. Three trials ran an unscoped `git diff` in a repo carrying ~2,948 dirty changes — including previous trials' history JSONs, each holding a full serialized system prompt — and produced ~139MB apiece. The logs contained **3,777 copies of the zrb system prompt**. At roughly 1.4M lines, each costing a regex substitution, a `stylize_muted`, and a `zrb_print`, the display alone outran the 120s timeout; the model received 97,976 chars regardless. Those three cells ran at ~3× their siblings (177s vs 53–60s, 242s vs 75–93s, 249s vs 99–105s) and still scored EXCELLENT, so nothing in the report showed it. Capture is now a `_StreamCapture` with three separate budgets: a tail-biased in-memory retention bounded by `LLM_MAX_OUTPUT_CHARS`, a console echo bounded by the new `LLM_MAX_CONSOLE_OUTPUT_CHARS` (default 1,000,000 — 10× the model-facing cap, so a normal build still scrolls in full), and a spill file opened exactly when the first character would be dropped and streamed into the dump with `copyfileobj`. The full-output promise is unchanged; it just is not resident any more.
- **Fix: a command killed mid-write was diagnosed as a hung process** (`src/zrb/llm/tool/shell.py`): the `timed_out` branch fired before any output inspection, so every timeout produced "the process is still running in the background… use `ps aux | grep <process_name>`… pass `-y` or `CI=true`". For a `git diff` that emitted 139MB, all three claims are wrong and it sends the model hunting for a process that is already dead. A timeout that also truncated now reports the character count, says plainly that the command was writing rather than waiting on input, and names the remedy — scope it, add a summarizing flag, pipe through `head`, or redirect and Grep. The quiet timeout keeps the original wording. Two branches that were unreachable behind `timed_out` (`lock`, `permission denied`) are reachable again as a side effect.
- **Fix: the parallel-tool-call affordance was unreachable code** (`src/zrb/llm/prompt/system_context.py`, `src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/file_read.py`, ADR-0101): `_resolve_parallel_tool_calls` is a deny-list — it returns `False` for `minimax-m2.7` and `glm-4.7`, `None` for everything else, and `True` for nothing. So `_format_parallel_tool_call_line`'s affirmative branch could never render, while `workflow.md` gated batching on exactly that line appearing ("where System Context says the model supports it"). Every model read the rule as unsatisfied. Wall clock on the 44-site migration challenge tracks round-trips, not calls: `gpt-4o-mini` ran the same task at 7.35 calls/response in 168s and at 2.62 in 434s, and a third trial issued 236 calls and timed out at 600s. `gemini-3.5-flash` averaged 1.04 across 583 responses. Batching is now the unconditional default in `workflow`; System Context emits only the negative, so a model that cannot batch overrides the default explicitly and there is no affirmative branch left to fall out of sync. `read_file`'s docstring carries the same instruction at the point of use, plus the corollary the run also surfaced — prefer one wide range over repeated 20-line slices of the same file. Because a tool description is static and cannot be withheld per model, it names its own exception ("unless System Context says this model cannot batch"), and the override line says explicitly that it outranks the workflow rule *and* any tool description — for a deny-listed model that line is the only mechanism that works, since Ollama-cloud ignores the request-level flag.
- **Docs: "does not support parallel tool calls" is three different things** (`src/zrb/llm/util/capabilities.py`, `src/zrb/llm/agent/common.py`): `_NO_PARALLEL_TOOL_CALLS` is only for models that **malform** parallel calls — the destructive case, where two calls arrive concatenated as one and both are lost. Two neighbouring behaviours must stay off it. A model whose provider **rejects the parameter** (OpenAI's o-series: "Unsupported parameter: 'parallel_tool_calls' is not supported with this model"; kimi-k2.5 behind NVIDIA NIM: "This model only supports single tool-calls at once!") would have `_apply_capability_constraints` send the very argument that 400s every request — a worse failure than the batching it prevents; supporting those needs the field split in two. A model that simply **never emits more than one call** (gpt-oss via Ollama, most small local models) needs nothing at all: encouragement to batch is a no-op, the model issues one call and the turn proceeds.
- **New: a whole-file `Write` over a stale file is refused** (`src/zrb/llm/tool/file_freshness.py`, `src/zrb/llm/tool/file_write.py`, `file_read.py`, `file_edit.py`, `post_write_check.py`, ADR-0102): `Edit` has `old_text` and fails loudly on drift; `Write` replaces everything on the strength of the model's recollection. One trial read `worker.py`, edited it, received a `[DIAGNOSTIC]` naming three errors, and answered by rewriting the file whole from memory — flipping the empty-queue exit from `return` to `continue`, shipping an infinite loop, and hanging the validator. Note that a plain read-before-write precondition, which opencode and Claude Code both enforce, would have allowed it: the model *had* read the file. What was missing was a **current** read. A `file_freshness` ContextVar now tracks three transitions per path (a **complete** `Read` → fresh, `Write` → fresh since the model authored every byte, `Edit` → stale) and `write_file` refuses an overwrite of an existing file that is not fresh, naming the one action that unblocks it. Deliberately narrow: `Edit` is never gated, appending is never gated, creating a file is never gated, and a *partial* read does not grant a whole-file write. **The check is in the tool, not in a `tool_policy`** — as a policy it refused nothing across 125 benchmark cells, because `check_tool_policies` is only reached when a `ToolCallHandler` is bound and `--interactive false` does not bind one; the guard evaporated in exactly the mode the benchmark used while its unit tests kept passing.
- **New: a blind edit streak is named** (`src/zrb/llm/tool/file_freshness.py`, `file_edit.py`, `src/zrb/config/mixins/llm_limits.py`, ADR-0102): one cell spent 68 calls making 59 `Edit`s to a single file, ran no command and produced no diagnostic, and exhausted its 600s budget — invisible to both the shell-only repetition counter and the diagnostic-gated post-write escalation. `Edit` now counts consecutive edits to one path with no read of it and no command in between, and appends a `[SYSTEM SUGGESTION]` at `LLM_BLIND_EDIT_STREAK_THRESHOLD` (default 8). Consecutiveness on one path is the discriminator: a 44-site migration makes hundreds of edits across dozens of paths, never many in a row on one. `post_write_check`'s own suggestion — which said "stop patching it — rewrite the whole file with `Write` instead" and so steered *into* this failure — now requires the re-read first.
- **New: the Recovery ladder is enforced at runtime** (`src/zrb/llm/tool/command_repetition.py`, `src/zrb/llm/tool/shell.py`, `src/zrb/config/mixins/llm_limits.py`, ADR-0102): `workflow.md` says "by the third, change what you are testing — or stop and report what you cannot get past". Every timeout in the benchmark was one command re-run against one or two files until the wall clock ran out — `python3 main.py` ×24 (99 calls, 3 files), `pytest -q` ×16 (145 calls, 1 file), `pytest -q` ×6 (107 calls, one file edited 93 times). Every repeat byte-identical, from a model with the rule in context throughout. `run_shell_command` now counts runs keyed by `(cwd, command)` whose **outcome** repeats — same exit code, same output digest — and appends a `[SYSTEM SUGGESTION]` on the `LLM_REPEATED_ATTEMPT_THRESHOLD`-th (default 3, matching the prose); `run_bash_command` delegates to it, so both share one counter. It never denies — re-running a suite is ordinary, and a false block costs more than a false nudge — and fires once per signature. Matching is exact, not fuzzy: a model that varies its command is already changing what it tests. **Keying on the invocation rather than the outcome was wrong and briefly shipped**: `debug-loop` asks the agent to run → fix → run, and every *passing* cell of that challenge across four models was told to stop. Measured across the run that straddled the correction: 26 nudges in 173 cells before, 24 of them on EXCELLENT cells; 0 in the 115 cells after. A second ground covers what a digest cannot — same command with nothing at all happening in between — which catches a nondeterministic command whose output never repeats. **This deliberately is not a tool policy.** The first implementation was, and it was dead code: `check_tool_policies` is an *approval* chain returning `ToolApproved | ToolDenied | None`, so a policy's `next_handler` yields the next policy's decision, never the tool's output — the note was appended to `None` and dropped on every call, emitting nothing across 32 benchmark cells. Response handlers are no better; they process the user's approval text. Annotating a result requires the tool itself.
- **Fix: the post-write escalation argued against its own escape hatch** (`src/zrb/llm/tool/post_write_check.py`): the `[SYSTEM SUGGESTION]` on a failed write recommends escalating from partial edits to a whole-file rewrite, and a caveat added alongside it ("a `Write` built from that memory reverts the edits between") read as a reason to avoid `Write` instead. A trial then spent 93 calls and 6.07M tokens alternating `Read`/`Edit` on one file — 31 diagnostics, 45 edits, exactly one write — never escalating. The split across the run was clean: cells that reached for `Write` survived (116 diagnostics, 37 writes → EXCELLENT), cells that did not failed (74 diagnostics, 0 writes → FAIL). The ladder is now two explicit rungs driven by a per-file counter rather than by a condition the model must evaluate about its own history: the first failure says re-read then edit; the second states the count and instructs a read-then-rewrite, with the read as the rewrite's first step rather than a warning attached to it.
- **Improvement: two verification instruments that running the code cannot provide** (`src/zrb/llm/prompt/markdown/workflow.md`): the two newest failures came from models that *did* run their code, which caps what "run it" buys. `gemini-3.5-flash` produced the best trajectory in the run — 22 calls, four executions, an env-override test, `py_compile`, scratch-file cleanup — and still shipped `DB_PASS = os.getenv("DB_PASS", "password123")`, documented in the module docstring; the script behaves identically either way, so no execution could catch it. `gemma4:31b` wrote a module-level `asyncio.Lock()`, which passes the first `asyncio.run()` and raises on every subsequent one — the instruction said "run it to reproduce", and one run shows green. The Verify gate's trailing grep clause is promoted to a named check covering any remove/replace/stop-using requirement, and a second names the double run, with the general cases it catches (a client bound to a dead loop, a cache, a temp file, a migration, an import-time global).
- **Improvement: `core-design` no longer swallows the document** (`src/zrb/llm_plugin/core_skills/core-writing/SKILL.md`, `core-design/SKILL.md`): both descriptions opened "Activate when the turn produces…", which reads as a partition — so an ADR, a written document *about* a design, went to `core-design` alone. On the ADR challenge the only trial that also activated `core-writing` scored 1.0; the two that took `core-design` alone scored 0.875 and 0.5, the failure being an ADR emitted with no heading markup at all. `core-writing` owns "Before finalizing, `Read` the file back" and the named-heading-level rule; `core-design` has neither, and no core skill mentioned ADRs. `core-writing` now names the case (ADR, RFC, design doc, postmortem, migration guide) and `core-design` says it covers the thinking, not the document.
- **Fix: the stale-write guard refused every overwrite instead of the stale ones** (`src/zrb/llm/tool/file_freshness.py`, `src/zrb/llm/agent/common.py`, `src/zrb/contextvars.py`, ADR-0102): the freshness tables shipped as `ContextVar`s, and their principal writer is `read_file` — which is *synchronous*, so `create_safe_wrapper` dispatches it through `asyncio.to_thread`, running it in a **copied** context whose `ContextVar.set` calls are discarded on return. `Read` therefore never marked a file fresh. Every whole-file `Write` to an existing file was refused with "already exists and you have not read it" however many times the model had just read it, with no action available that could clear it — and that refusal is the exact recovery `post_write_check` instructs on a second diagnostic ("`Read` the file in full, then replace it in a single `Write`"), so the two new guards deadlocked against each other. The same loss made `Read`'s `clear_edit_streak` a no-op, so the blind-edit nudge fired claiming "nothing read and nothing run in between" after a read before every single edit. Both tables are plain module-level dicts now; a synchronous tool cannot keep cross-call state in a `ContextVar`. Every guard test called `read_file` inline, in the caller's context, which is why the suite stayed green — the regression tests now drive `create_safe_wrapper`.
- **Fix: the post-write escalation is reverted to one bounded suggestion** (`src/zrb/llm/tool/post_write_check.py`): the escalating ladder made `gpt-4o-mini` measurably worse and is gone. A paired A/B — 6 cells x 3 trials, one model, identical env, only the zrb tree swapped via `PYTHONPATH` against a `git worktree` of 2.54.0 — isolated it from the prompt, which is byte-identical across that window apart from 9 lines. Rung two said "`Read` the file in full, then replace it in a single `Write`", and **a whole-file rewrite by a small model regenerates the diagnostic that re-issues the instruction**: on `refactor` the pre-ladder build spent 10 tool calls and 4 diagnostics and stopped, the ladder build spent 51, took 25 diagnostics and failed. Arm totals: tool calls 215 -> 366 (+70%), pass rate 11/18 -> 8/18, both control cells unchanged. A third rung that said "stop and report" was not the fix either — one trial received it **22 times** and kept going. What remains is the pre-ladder wording, which asks for *one targeted fix* (an `Edit`, which does not restart the cycle), capped at two appearances per file; past that the errors are still reported in full and nothing is appended for the model to react to. **The general rule this cost us: an injected instruction must be bounded, and must never prescribe an action that regenerates its own input.** The repetition counter and blind-edit nudge already satisfied both — they fire once per streak — which is why neither appeared in the regression.
- **Fix: the stale-write refusal sent the model in circles on a partial read** (`src/zrb/llm/tool/file_freshness.py`, `file_read.py`): a benchmarked cell read lines 1-21 of `job_queue.py`'s 48, was refused, and re-sent the identical `Write` **four** more times before it thought to read the whole file. The refusal said only "`Read` it, confirm it says what you think it says, then write" — which the model had done as far as it could tell, so re-issuing the write was the reasonable reply to it. Once `Read` numbers its lines, ranged reads are common and "`Read` it" is ambiguous. The refusal now names the span it is rejecting ("your last read covered lines 1-21 of 48 — a whole-file write replaces all 48"), names truncation separately, and spells the remedy as `Read` **with no start_line or end_line**. A repeat of the same refusal escalates, stating the count and reducing the options to exactly two — read it whole, or use `Edit` — because re-sending a refused write can never succeed. `read_file` now reports its span through one `record_read` call rather than re-deriving the freshness condition at the call site.
- **Fix: freshness is checked against the file rather than remembered** (`src/zrb/llm/tool/file_freshness.py`, ADR-0102): the refusal text asserts the file "has changed since you last read it in full", but a remembered boolean only ever described what `Read`/`Write`/`Edit` did. A change from anywhere else — `sed -i`, a formatter, `git checkout`, a build step, or a sub-agent, whose context cannot write back to its parent's — left the bit reading fresh and the overwrite discarded it, which is ADR-0102's own failure mode with a different author. What is recorded per path is now the fingerprint (`st_mtime_ns` + `st_size`) of the content the model last saw in full, and the check re-stats the file and compares.
- **Fix: `mode="a"` was a one-step bypass of the stale-write guard** (`src/zrb/llm/tool/file_write.py`): `write_file` marked the path fresh after *any* successful write, so an append — even of empty content — against a file the model had never read granted freshness, and the very next `mode="w"` was free to replace content nobody had looked at. An append now only extends a view that was already current, and the gate matches any non-append mode: `== "w"` let the equally truncating `"wt"` and `"w+"` through ungated.
- **Fix: the repetition counter's second detection ground was unreachable** (`src/zrb/llm/tool/command_repetition.py`, `src/zrb/llm/tool/shell.py`): the fallback for a command whose output is nondeterministic — "same command, and nothing happened in between", the case a digest can never catch — never fired once. `_repetition_note` sampled the workspace revision *before* bumping it for the run being recorded, so consecutive runs of one command always looked exactly one change apart; a concurrency simulation re-run forever sat at streak 1. `record_outcome` now owns the bump and stores the post-bump value, so the next run compares the world it observed against the world as it stood when the previous run finished. No test covered the ground, which is why it shipped inert.
- **Fix: re-writing a journal note destroyed the backlinks other notes had added** (`src/zrb/llm/tool/journal_write.py`, ADR-0099): `write_journal_note` composes the whole file from its arguments and truncates, but `## Backlinks` is written by *other* notes via `_add_backlink` and is not the caller's to supply. Linking B from A and then updating A dropped A's way back to B while B kept its forward link — the `missing-backlink` half-edge the deleted `journal-lint.py` used to catch, produced by the writer that replaced it. `## Related` had the mirror problem in the other direction. Both blocks are now merged rather than rebuilt, so a link is only ever added.
- **Fix: a cancelled response killed the `MultiUI` message loop** (`src/zrb/llm/ui/multi_ui.py`): `_process_messages_loop` re-raised every `CancelledError` from the job it was awaiting, so a cancel aimed only at the current response propagated to the loop's own handler and broke out of it — no further user message would ever be processed. Swallowing them all (the previous behaviour) was the opposite bug: a shutdown cancel arriving mid-job was discarded and `await self._process_messages_task` never returned. It now uses `current_task().cancelling()` to tell the two apart, the same guard `base/ui.py`'s twin already used. Latent rather than observed — nothing cancels `MultiUI._running_llm_task` today, since the child UI's Escape handler cancels its own.
- **Improvement: `write_todos` binds completion to verification** (`src/zrb/llm/tool/plan.py`): the docstring is read at exactly the moment a model claims something is done, so it now says an item reaches `completed` only once its work is done *and* verified — never on intent, never because the edit landed. An item awaiting verification or blocked stays `in_progress`, the latter gaining a follow-up naming the blocker.
