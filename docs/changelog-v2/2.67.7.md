## 2.67.7 (August 31, 2026)

- **Fix: `MoveFile` broke moving onto an existing directory or binary file, and left the destination unrecorded** (`src/zrb/llm/tool/file_mv.py`, `src/zrb/llm/tool/file_observation.py`, `test/llm/tool/test_file_mv.py`): the overwrite guard used `check_observed`, designed for `write_file`'s text-staleness check — it unconditionally opened the destination as UTF-8 text, so moving onto an existing directory raised `IsADirectoryError` instead of nesting the source inside it, and moving onto an existing binary file was refused permanently (binaries are never `record_observed`'d). Swapped to `check_listed(recursive=False)`, the same path-identity check `RemoveFile` already uses — it doesn't require decoding the destination, so both cases now work as `shutil.move` always did. A new `record_seen` helper marks the destination as seen after a successful move, so an immediate follow-up `WriteFile`/`RemoveFile` on that path in the same turn isn't spuriously refused as "not read or listed."
- **Fix: journal git-backing could hang forever or race its own `git init`** (`src/zrb/llm/tool/journal_write.py`, `test/llm/tool/test_journal_git.py`): `_ensure_journal_git`/`_git_commit`'s `subprocess.run` calls carried no `timeout=`, unlike the existing pattern in `zrb/llm/util/git.py` — a hung `git` (a GPG-sign prompt with no TTY, a stale `index.lock`) blocked every journal-writing tool call indefinitely. Now bounded by `LLM_GIT_CMD_TIMEOUT`, swallowed the same way as a missing `git` binary. Separately, `git init` and the initial commit ran from `ensure_journal_tree()` *before* any writer acquired `_journal_lock`, letting two first-time concurrent writers race the same `git init`; the call now runs as the first line inside each writer's lock instead.
- **Improvement: journal-specific guidance moved out of the always-loaded `workflow` prompt section into the journal tools' own docstrings** (`src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/journal.py`, `src/zrb/llm/tool/journal_write.py`, `test/llm/prompt/test_prompt_mandates.py`): naming `SearchJournal`/`WriteJournalNote`/`DeleteJournalNote` in `workflow.md` cost prompt tokens even with `LLM_JOURNAL_ENABLED=false`, when those tools don't exist at all — the same "gate the tool, not the prose" principle ADR-0055 already applied to the journal's protocol description. The "don't batch a search with the write/delete it should inform" rule now lives on those three tools' own docstrings instead of the static section.
- **Fix: three skills' approval-gate text referenced a "Working Loop's Frame step" deleted in 2.59.0** (`src/zrb/llm_plugin/core_skills/core-research/SKILL.md`, `src/zrb/llm_plugin/core_skills/core-design/SKILL.md`, `src/zrb/llm_plugin/skills/research/SKILL.md`): `workflow.md`'s "Working Loop" section (and its "Frame" step) was cut when the prompt was simplified to 25 lines, but `core-research`, `core-design`, and `/research` still said their approval gate "overrides the Working Loop's Frame step" — a dangling reference to a concept that no longer exists anywhere in the prompt. Dropped the "overrides" framing; the approval gate now states the rule directly. `core-research`'s activation trigger was also narrowed — "answering a question" was broad enough to plausibly fire on a trivial conversational question needing no real investigation; it now explicitly excludes anything answerable from context already in the conversation or from general knowledge.
- **Documentation: `workflow.md`'s Tool Discovery section no longer hardcodes `search_tools` as the literal name of the deferred-tool discovery mechanism** (`src/zrb/llm/prompt/markdown/workflow.md`): pydantic-ai's `ToolSearch` capability only exposes a callable literally named `search_tools` as its local fallback — on a model with native provider-side tool search (Anthropic Sonnet/Opus/Haiku 4.5+, OpenAI Responses GPT-5.4+), discovery is handled server-side with no separate named tool at all. The section now describes the action ("search for a deferred tool") instead of asserting one fixed name that doesn't hold for every provider.
- **Documentation: two tool docstrings corrected, and `llm-config.md`'s Journal table gained four rows already shipped in code** (`src/zrb/llm/tool/mcp.py`, `src/zrb/llm/tool/file_rm.py`, `docs/configuration/llm-config.md`): `frame_mcp_result`'s docstring claimed "a single top-level pass, not recursive" while the function (and its test) recurse into every list item — corrected to describe the actual per-item framing. `remove_file`'s docstring lost the reminder to confirm a path is the *correct* one among similarly-named candidates (not just one the mechanical `check_listed` gate passed) when it was rewritten for the newer gate; restored. Separately, `ZRB_LLM_JOURNAL_HUD_MAX_ENTRIES_PER_SECTION`, `ZRB_LLM_JOURNAL_AUTO_SEARCH_ENABLED`, `ZRB_LLM_JOURNAL_AUTO_SEARCH_MAX_HITS`, and `ZRB_LLM_JOURNAL_GIT_ENABLED` each had a real `EnvField` with a real `doc=` string in `config/mixins/llm_content.py` but no row in the reference table.
- **Chore: `zrb-test.sh` parallelized via `pytest-xdist`, cutting a full run from ~90s to ~35s** (`pyproject.toml`, `poetry.lock`, `zrb-test.sh`): the suite is wait-bound, not CPU-bound — ~29s of CPU time across a ~90s wall-clock run (33% average utilization), because dozens of tests spawn real subprocesses and wait on real OS-level timeouts to verify graceful-kill/sandbox-teardown behavior (`test/util/cmd/test_command.py`, `test/llm/tool/test_shell.py`, `test/llm/tool/test_shell_background.py`, `test/llm/sandbox/test_integration.py`, `test/llm/hook/`). Parallel workers overlap those waits instead of serializing them. `poetry add pytest-xdist` also synced the venv's `pydantic-ai-slim` to the version `pyproject.toml` already pinned (2.36.0; the venv had drifted to 2.27.0).
- **Fix: a test-order-dependent import bug in agent-hook tests, exposed by parallel workers' smaller per-process import caches** (`test/conftest.py`): several agent-hook tests (`test/llm/hook/test_manager_functionality.py` and siblings) replace `sys.modules["pydantic_ai"]` with a bare `MagicMock` to avoid a real LLM call; if nothing had genuinely imported `pydantic_ai.toolsets` yet in that process, the agent-hook code path's first `from pydantic_ai.toolsets import ...` failed with "'pydantic_ai' is not a package" instead of resolving from the (already-real, already-cached) submodule. Serial runs always masked this because some earlier test in the same shared process happened to import it first; a fresh pytest-xdist worker sometimes didn't. A new session-scoped autouse fixture forces the real import once per worker before any mock can shadow it.
