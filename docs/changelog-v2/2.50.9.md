## 2.50.9 (July 29, 2026)

- **Breaking: `ActivateSkill`'s parameter is now `skill`, not `name`** (`src/zrb/llm/tool/skill.py`, `test/llm/tool/test_skill.py`): the schema was already unambiguous — one required string, `additionalProperties: false` — but `name` on a tool called `ActivateSkill` answers "name of what?" only by inference, and models resolved it to the domain noun instead. Measured across an eight-model, 288-trial benchmark: of 167 `ActivateSkill` calls, 68 named the field wrongly — `skill` (41), `skill_name` (26), `skill_id` (1) — and the misses spanned six of the eight models, so this was not one sloppy model but a broad prior fighting a generic parameter name. Each miss cost a pydantic validation retry that re-sent the whole conversation (median input ~100k tokens for these runs), and a model typically needed three round-trips to land one activation. Aliasing was rejected: accepting `skill`/`skill_name` alongside `name` would force every field optional, dropping `required` and gutting `additionalProperties: false`, which is the check that catches a genuine typo. Renaming keeps the schema exactly as strict while matching the name 41 calls already reached for. No alias, matching the `LLMTask(summarize_command=...)` rename in 2.50.8: `ActivateSkill(name=...)` now raises a validation error, and the tool description gained a `skill:` line naming where skill names come from, since pydantic-ai emits no per-field description for a bare annotation.
- **Fix: `Shell`'s `timeout` never stated its unit** (`src/zrb/llm/tool/shell.py`, `test/llm/tool/test_shell.py`): the docstring mentioned `timeout` three times without once saying seconds, and `timeout: int = 120` reads as milliseconds to a model carrying a prior from agent shells that take them (a 120000-style default is the common convention). Five calls in the same benchmark passed millisecond values — four `30000`, one `15000`. The `15000` is the instructive one: the model meant 15 seconds, got 15000, and its foreground wait outlived the harness cap, so a run whose deliverable passed every one of its nine validator checks was recorded as a timeout. The docstring now says `SECONDS, not milliseconds (default 120)` and points long-running processes (server, watcher, `tail -f`) at `background=True`, which is the correct tool for them and to which `timeout` does not apply. Documentation only — no behavior changed, and no clamp was added, since silently reinterpreting a large value would guess at intent.
- **Fix: a no-op `Edit` returned a bare status the model could not act on** (`src/zrb/llm/tool/file_edit.py`, `test/llm/tool/test_file.py`): `replace_in_file` detected that a replacement changed nothing and returned `No changes made to <path>` — the one failure path in that module without the `[SYSTEM SUGGESTION]` prefix the project reserves for errors the model has to recover from. Reading as a neutral status, it invited the identical call again: one benchmark trial received it 76 times and another 74, each costing a full round-trip. A no-op that gets this far means `old_text` *was* found, so it is never the "not found" case, and its three causes need different advice — identical `old_text`/`new_text` (fix the arguments), `count=0` (fix the count), or a fuzzy match onto a region already equal to `new_text` (the edit already landed; nothing to do). Each cause is now named with its own guidance rather than hedged between them. The classification stays at the no-op site rather than moving to a cheaper up-front check on `old_text == new_text`, because checking earlier would relabel a missing file and an absent `old_text` as an argument problem; two guard tests pin that ordering.
