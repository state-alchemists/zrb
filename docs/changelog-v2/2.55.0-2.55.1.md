## 2.55.0 (August 5, 2026)

A benchmark run of 156 cells across five models (`gpt-4o-mini`, `gemini-2.5-flash`, `gemini-3.5-flash`, `deepseek-v4-flash`, `gemma4:31b-cloud`) produced ten non-excellent outcomes. Every one traced to a rule the prompt already stated and the model did not follow, or to a harness defect no rule could reach. Per ADR-0045's ladder, the fixes go to the runtime where the runtime can hold them.

- **Reverted: the runtime anti-loop guards do not ship** (`command_repetition.py`, `file_freshness.py`, `shell.py`, `file_write.py`, `file_edit.py`, `file_read.py`, `post_write_check.py`, `llm_limits.py`): the write-freshness refusal, the blind-edit-streak nudge, and the repeated-outcome counter built up in this window are all removed before release. The mechanism's own evidence argued against shipping it — an injected instruction is the weakest lever for the exact model that needs it (an escalated "stop and report" was ignored 22 times), the stale-write refusal is a hard block carrying the most cross-tool accounting state in the tool layer, and every component that measurably made models worse (invocation-counting, the post-write escalation ladder) was already reverted within this same history. The prompt's Recovery ladder stands on its own again. The surviving lessons are general (a tool policy is an approval chain that never sees a result; a synchronous tool cannot keep state in a `ContextVar`; an injected instruction must be bounded and never regenerate its own input).
- **Reverted: `post_write_check` no longer tells the model to fall back to a whole-file `Write`** (`src/zrb/llm/tool/post_write_check.py`): the 2.52.0 advice to stop patching and rewrite the whole file once a file had failed twice is gone. It belongs to the same escalation family the window measured as harmful — a whole-file rewrite by a small model regenerates the diagnostic that issued the instruction — and with the freshness guard removed it had nothing to be the escape hatch for. The remaining guidance asks for a re-read and *one targeted fix*, and names the file to fix instead when the error points outside it.
- **Fix: an unbounded shell command spent minutes being printed and was killed by its own timeout** (`src/zrb/llm/tool/shell.py`, `src/zrb/config/mixins/llm_limits.py`): `_read_stream` echoed *every* line to the console and accumulated *every* line in RAM, truncating to `LLM_MAX_OUTPUT_CHARS` only at the end. Three trials ran an unscoped `git diff` in a repo carrying ~2,948 dirty changes — including previous trials' history JSONs, each holding a full serialized system prompt — and produced ~139MB apiece. The logs contained **3,777 copies of the zrb system prompt**. At roughly 1.4M lines, each costing a regex substitution, a `stylize_muted`, and a `zrb_print`, the display alone outran the 120s timeout; the model received 97,976 chars regardless. Those three cells ran at ~3× their siblings (177s vs 53–60s, 242s vs 75–93s, 249s vs 99–105s) and still scored EXCELLENT, so nothing in the report showed it. Capture is now a `_StreamCapture` with three separate budgets: a tail-biased in-memory retention bounded by `LLM_MAX_OUTPUT_CHARS`, a console echo bounded by the new `LLM_MAX_CONSOLE_OUTPUT_CHARS` (default 1,000,000 — 10× the model-facing cap, so a normal build still scrolls in full), and a spill file opened exactly when the first character would be dropped and streamed into the dump with `copyfileobj`. The full-output promise is unchanged; it just is not resident any more.
- **Fix: a command killed mid-write was diagnosed as a hung process** (`src/zrb/llm/tool/shell.py`): the `timed_out` branch fired before any output inspection, so every timeout produced "the process is still running in the background… use `ps aux | grep <process_name>`… pass `-y` or `CI=true`". For a `git diff` that emitted 139MB, all three claims are wrong and it sends the model hunting for a process that is already dead. A timeout that also truncated now reports the character count, says plainly that the command was writing rather than waiting on input, and names the remedy — scope it, add a summarizing flag, pipe through `head`, or redirect and Grep. The quiet timeout keeps the original wording. Two branches that were unreachable behind `timed_out` (`lock`, `permission denied`) are reachable again as a side effect.
- **Fix: the parallel-tool-call affordance was unreachable code** (`src/zrb/llm/prompt/system_context.py`, `src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/file_read.py`, ADR-0038): `_resolve_parallel_tool_calls` is a deny-list — it returns `False` for `minimax-m2.7` and `glm-4.7`, `None` for everything else, and `True` for nothing. So `_format_parallel_tool_call_line`'s affirmative branch could never render, while `workflow.md` gated batching on exactly that line appearing ("where System Context says the model supports it"). Every model read the rule as unsatisfied. Wall clock on the 44-site migration challenge tracks round-trips, not calls: `gpt-4o-mini` ran the same task at 7.35 calls/response in 168s and at 2.62 in 434s, and a third trial issued 236 calls and timed out at 600s. `gemini-3.5-flash` averaged 1.04 across 583 responses. Batching is now the unconditional default in `workflow`; System Context emits only the negative, so a model that cannot batch overrides the default explicitly and there is no affirmative branch left to fall out of sync. `read_file`'s docstring carries the same instruction at the point of use, plus the corollary the run also surfaced — prefer one wide range over repeated 20-line slices of the same file. Because a tool description is static and cannot be withheld per model, it names its own exception ("unless System Context says this model cannot batch"), and the override line says explicitly that it outranks the workflow rule *and* any tool description — for a deny-listed model that line is the only mechanism that works, since Ollama-cloud ignores the request-level flag.
- **Docs: "does not support parallel tool calls" is three different things** (`src/zrb/llm/util/capabilities.py`, `src/zrb/llm/agent/common.py`): `_NO_PARALLEL_TOOL_CALLS` is only for models that **malform** parallel calls — the destructive case, where two calls arrive concatenated as one and both are lost. Two neighbouring behaviours must stay off it. A model whose provider **rejects the parameter** (OpenAI's o-series: "Unsupported parameter: 'parallel_tool_calls' is not supported with this model"; kimi-k2.5 behind NVIDIA NIM: "This model only supports single tool-calls at once!") would have `_apply_capability_constraints` send the very argument that 400s every request — a worse failure than the batching it prevents; supporting those needs the field split in two. A model that simply **never emits more than one call** (gpt-oss via Ollama, most small local models) needs nothing at all: encouragement to batch is a no-op, the model issues one call and the turn proceeds.
- **Improvement: two verification instruments that running the code cannot provide** (`src/zrb/llm/prompt/markdown/workflow.md`): the two newest failures came from models that *did* run their code, which caps what "run it" buys. `gemini-3.5-flash` produced the best trajectory in the run — 22 calls, four executions, an env-override test, `py_compile`, scratch-file cleanup — and still shipped `DB_PASS = os.getenv("DB_PASS", "password123")`, documented in the module docstring; the script behaves identically either way, so no execution could catch it. `gemma4:31b` wrote a module-level `asyncio.Lock()`, which passes the first `asyncio.run()` and raises on every subsequent one — the instruction said "run it to reproduce", and one run shows green. The Verify gate's trailing grep clause is promoted to a named check covering any remove/replace/stop-using requirement, and a second names the double run, with the general cases it catches (a client bound to a dead loop, a cache, a temp file, a migration, an import-time global).
- **Improvement: `core-design` no longer swallows the document** (`src/zrb/llm_plugin/core_skills/core-writing/SKILL.md`, `core-design/SKILL.md`): both descriptions opened "Activate when the turn produces…", which reads as a partition — so an ADR, a written document *about* a design, went to `core-design` alone. On the ADR challenge the only trial that also activated `core-writing` scored 1.0; the two that took `core-design` alone scored 0.875 and 0.5, the failure being an ADR emitted with no heading markup at all. `core-writing` owns "Before finalizing, `Read` the file back" and the named-heading-level rule; `core-design` has neither, and no core skill mentioned ADRs. `core-writing` now names the case (ADR, RFC, design doc, postmortem, migration guide) and `core-design` says it covers the thinking, not the document.
- **Fix: re-writing a journal note destroyed the backlinks other notes had added** (`src/zrb/llm/tool/journal_write.py`, ADR-0055): `write_journal_note` composes the whole file from its arguments and truncates, but `## Backlinks` is written by *other* notes via `_add_backlink` and is not the caller's to supply. Linking B from A and then updating A dropped A's way back to B while B kept its forward link — the `missing-backlink` half-edge the deleted `journal-lint.py` used to catch, produced by the writer that replaced it. `## Related` had the mirror problem in the other direction. Both blocks are now merged rather than rebuilt, so a link is only ever added.
- **Fix: a cancelled response killed the `MultiUI` message loop** (`src/zrb/llm/ui/multi_ui.py`): `_process_messages_loop` re-raised every `CancelledError` from the job it was awaiting, so a cancel aimed only at the current response propagated to the loop's own handler and broke out of it — no further user message would ever be processed. Swallowing them all (the previous behaviour) was the opposite bug: a shutdown cancel arriving mid-job was discarded and `await self._process_messages_task` never returned. It now uses `current_task().cancelling()` to tell the two apart, the same guard `base/ui.py`'s twin already used. Latent rather than observed — nothing cancels `MultiUI._running_llm_task` today, since the child UI's Escape handler cancels its own.
- **Improvement: `write_todos` binds completion to verification** (`src/zrb/llm/tool/plan.py`): the docstring is read at exactly the moment a model claims something is done, so it now says an item reaches `completed` only once its work is done *and* verified — never on intent, never because the edit landed. An item awaiting verification or blocked stays `in_progress`, the latter gaining a follow-up naming the blocker.
- **Docs: corrected stale references after the parallel-tool-call and journal changes** (`AGENTS.md`, `docs/technical-specs/llm-context.md`): `system_context` no longer announces *whether* a model supports batching — ADR-0038 left it announcing only the exception, so the section description says that instead. And the journal-index note claiming `SearchJournal`'s own description tells the model that a missing index block is not proof of an empty journal is corrected to the truth, matching `render_journal_index`'s docstring: nothing tells the model that any more, a known gap that only matters when `LLM_JOURNAL_INDEX_MAX_CHARS` is `0` while the journal tools stay registered.
- **Improvement: the Working Loop stopped being a per-turn classification problem** (`src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/prompt/markdown/examples.mini.md`): the four-row routing table (`conversational` / `inquiry` / directive-you-can-specify / directive-you-cannot-yet-specify) asked the model to categorize the turn before every loop run, and its two soft rows blurred into each other. The table now has three stances defined by the deliverable — an **answer** (reply from what you know, no forced codebase tie-in), a **proposal** (investigate to a verdict, await approval before any write), a **change** (autonomous, lands per *Where the deliverable goes*) — and `Frame the turn` merely names the deliverable in those three words, so the "classification" is the frame, not a separate decision. The "can't yet specify" case and the `EnterPlanMode` trigger keep their prose; "Between the first two rows, prefer conversational" and the `Loop steps before Verify` column are gone, the loop following from the stance instead. `examples.mini.md`'s guarded row-by-row walk-through is rewritten to the three stances.
- **Improvement: three redundant rules trimmed out of `workflow.md`** (`src/zrb/llm/prompt/markdown/workflow.md`): `Turn Sequence` dropped `First look` (it existed only to classify the turn, which framing now does) and the closing *"Only step 1 may end the turn"* softened to *"Within this sequence"* — as written it contradicted *When you don't know*'s ask-one-question rule, which ends turns later. `Verify Before Done`'s `Evidence` bullet is gone: claim-to-source already lives in `persona`'s `Verify before you assert` / `Cite inline`, so the gate keeps only artifact checks — the one place the split no longer forces a reader to decide which half owns the rule. The intro now states the compress-vs-verify tie-break explicitly ("brevity shapes the report, never the check") instead of leaving it to priority inference. `Tool usage` leads with the batching rule (the most-invoked mechanic of the section, and the review that flagged it buried it last-but-one), and the stall line in *When you don't know* is compressed since `Recovery` already owns the not-converging ladder.

A follow-up run widened the grid to 180 cells and 12 challenges. Twelve timeouts and eight failures; five cells traced to the harness rather than the model, two of them to defects a mock could never have caught.

- **Fix: the shell PID-tracking wrapper corrupted any command whose last line could not absorb a trailing `; }`** (`src/zrb/llm/tool/shell.py`): `_prepare_command` spliced itself onto the model's command as `{ <command> ; }; __code=$?; …`, all on one line. A heredoc therefore lost its terminator — `EOF ; }` is not a delimiter alone on its line, so the shell swallowed the rest of the wrapper hunting for one — and so did a trailing comment (`# …` ate the wrapper), a trailing `;`, and, on bash and `sh`, a command merely ending in a newline. Six of thirteen tested command shapes were broken; models write all four of those constantly. The failure reached the model as `zsh:13: parse error near '\n'` — a line number in a string it never wrote, with no `[SYSTEM SUGGESTION]` attached — and 13 such errors landed across 11 of the 180 cells. One killed `deepseek-v4-flash`'s `refactor` trial outright. Every wrapper token now sits on its own line, so nothing the model writes can run into it, and an empty command skips the wrapper rather than being turned into a `{ }` syntax error. The regression test drives real `bash`/`sh`/default shells: the bug was in generated shell syntax, so only an actual parse can catch it.
- **Fix: `LLM_REQUEST_TIMEOUT` was declared, documented, and never applied to an agent** (`src/zrb/llm/agent/common.py`): the knob was read only by `runner/chat/chat_session_runner.py` — the *web* session runner — so `zrb chat` gave model requests no deadline at all. A provider that accepts the connection and then stops sending therefore blocked forever: pydantic-ai waits on the stream, and `retry_loop` only fires on a raised exception, so a stall is indistinguishable from thinking. `gemini-2.5-flash`/`research` and `gemini-3.5-flash`/`grep-fest` each burned their full 600s having written 22 bytes of stdout, no history, and — confirmed by mtime — not one file in a 44-site migration. `create_agent` now applies it, so the deadline covers the main agent, sub-agents, and programmatic `LLMTask` alike; a caller-supplied `timeout` still wins and `0` disables it.
- **Fix: nothing could stop a run that had stopped converging** (`src/zrb/llm/agent/run/runner.py`, `src/zrb/config/mixins/llm_limits.py`): `run_stream_events` was passed `usage_limits=UsageLimits(request_limit=None)` — explicitly uncapped. `gpt-4o-mini` spent one `grep-fest` cell on 343 tool calls, 267 of them `Edit`, re-editing the same nine files 8–9× each from memory, and stopped only when the wall clock did. The prompt's Recovery ladder tells the model to change approach by the third attempt; the new `ZRB_LLM_MAX_REQUEST_PER_RUN` (default 300) is the half of that rule something can enforce. 300 is measured, not chosen by feel: the largest *legitimate* run in the grid was 79 tool calls. Hitting it halts with text naming the knob and warning that raising a cap on a non-converging loop only spends more tokens — and, because a cap is not transient, without burning the retry budget re-hitting the same wall. The partial history is preserved by the existing handler.
- **Fix: "batch twelve edits" read as "describe twelve edits"** (`src/zrb/llm/prompt/markdown/workflow.md`, `examples.mini.md`): `gemini-2.5-flash` did the whole 44-site migration correctly — right `scope=` per module — and then spent 9,193 output tokens printing the edits into its reply as a list of `{path, old_text, new_text}` objects. Zero `Edit` calls; 42 tool calls, 37 of them `Read`. `Edit` takes one replacement by design (and stays that way), so the prompt and the tool schema disagreed about what a batch *is*, and the model resolved the tension by writing prose. `Tool usage` now states that a batch is N tool calls and never one payload describing them, and `examples.mini.md` demonstrates both this and the neighbouring failure below.
- **Fix: a change that never reached disk** (`src/zrb/llm/prompt/markdown/examples.mini.md`): `gpt-4o-mini` failed all three `refactor` trials with one, one, and two tool calls — a single `Read` of `pipeline.py`, then the refactored module in its reply; the file's mtime never moved. *Where the deliverable goes* already covers it and `examples.mini.md` already glossed it in one line of the stance quiz, but the model resolving to the `mini` profile is exactly the one that needs a worked demonstration. Both this and the payload-batch failure are now demonstrated rather than merely stated.
- **Improvement: `Shell` and `Bash` say they are for running things, not for touching files** (`src/zrb/llm/tool/shell.py`, `src/zrb/llm/tool/bash.py`, `src/zrb/llm/prompt/markdown/workflow.md`): the routing rule lived in `workflow`'s `Tool usage`, where it applied to no tool in particular. Per ADR-0045 it belongs next to the schema it competes with, so both docstrings now name the file tools (`Read`/`Write`/`Edit` for contents, `Grep`/`Glob`/`LS` to search and list, `RM`/`MV` to remove and move) and the shell idioms that look like they would work but bypass post-write diagnostics, path validation, and per-path approval — `cat`, `head`, `sed -i`, `find`, `test -f`, `rm`, `mv`, `>` into a file. `Bash` carries its own copy because it delegates to `Shell` and many Claude skills reach for it by name.
- **Fix: `ActivateSkill`'s description pointed at a prompt section** (`src/zrb/llm/tool/skill.py`, `AGENTS.md`): it told the model to use a name "exactly as listed under Core Skills / Available Skills". Sections toggle independently via `LLM_INCLUDE_SECTIONS`, and unlike a prompt-internal cross-reference no requires-guard can strip a docstring — a tool ships with its schema regardless of which sections compose. The description now describes the argument, and an unknown or user-only name comes back with the activatable ones listed, mirroring `agent_not_found_message` for delegation: the usual failure is a misremembered name, so naming the real ones turns the retry into a correction instead of a second guess. AGENTS.md gains the invariant.
- **Fix: the batch-by-default rule pointed at a section it might not be given** (`src/zrb/llm/prompt/markdown/workflow.md`, `test/llm/prompt/test_section_composition.py`): the clause withdrawing batching for a deny-listed model read "Unless System Context says this model cannot batch" with no `<!--requires:system_context-->` guard, so a trimmed `LLM_INCLUDE_SECTIONS` left the prompt citing a section it never emitted. It fails safe — drop `system_context` and the model batches, which is the correct default — but the invariant AGENTS.md claimed ("exactly one such guard left") was simply untrue. Guarded, and `system_context` added to `OWNED_VOCABULARY` so the subset walk actually asserts it.
- **Improvement: the "Available Skills" heading disappears with its list** (`src/zrb/llm/prompt/claude.py`): a stock install has no model-invocable non-core skills — every built-in utility skill under `llm_plugin/skills/` is `disable-model-invocation`, a slash command the user reaches — so the catalogue rendered a heading over the words "(none registered)", followed by five lines telling the model how to match against it. Paying for a heading that introduces nothing teaches the model that catalogue entries are decorative. The heading now rides with the list in `AVAILABLE_SKILLS` and both vanish together.
- **Improvement: `workflow.md` trimmed by 10%** (`src/zrb/llm/prompt/markdown/workflow.md`, `src/zrb/llm/tool/delegate.py`): 14,213 → 12,717 chars, and the composed default prompt 21,068 → 19,339, *while* adding the batch-is-N-calls rule and a bound on verification. Cut: the file-tools routing rule (now in `Shell`/`Bash`, where it is enforced); "Read a tool's own description before its first use" (the description is already in context on every request — it cannot be unread); the destructive-action enumeration, which the approval cascade and `bash_safe_command_policy` already ask about; the envelope contract in `Delegating to sub-agents`, duplicated verbatim in `DelegateToAgent`'s docstring, which absorbed the comparative-axes rule with it; `Project Documentation`'s restatement of its own trigger, already in `Turn Sequence` step 4; and the standalone `Stop` heading, folded into `Recovery`. `Recovery`'s six bullets became four — "same error repeating", "not converging", and "several approaches failed" were three phrasings of one ladder. Every `OWNED_VOCABULARY` term survives; the composition suite's 7-subset walk and the 24,000-char budget still hold.
- **Improvement: verification has a finish line** (`src/zrb/llm/prompt/markdown/workflow.md`): `Verify Before Done` drove a *capable* model past its deliverable. `deepseek-v4-flash` finished the `refactor` task correctly, obeyed "Run it twice", verified the output, and then went looking for the benchmark's own validator to self-grade — running `Shell` with a `cwd` outside its workdir, where the heredoc bug above killed it. The gate now says the request defines the finish line: check what it asked for, then stop. Inventing further checks after the deliverable is complete is a second task nobody asked for. (The opposite failure is in the same run: `gemma4:31b` ignored "Run it twice", ran `main.py` once, reported "Duplicate charges: 0", and failed validator trials 2–6.)

## 2.55.1 (August 6, 2026)

- **Refactor: `hook_creators.py` split into three modules** (`src/zrb/llm/hook/creator.py`, `src/zrb/llm/hook/process_io.py`, `src/zrb/llm/hook/process_kill.py`, `src/zrb/llm/hook/manager.py`): the 739-line module held two unrelated concerns — the three `create_*_hook` factories, and roughly 310 lines of POSIX subprocess plumbing (selector-driven pipe draining, daemon-thread detaching, process-group kills) that only the command hook needs. `create_prompt_hook` and `create_agent_hook` sat at lines 620 and 681, buried behind machinery neither touches. The read side is now `process_io.read_hook_output` / `run_detached` and the kill side `process_kill.read_process_group` / `kill_process_tree`, both public in their own modules; the factories keep `creator.py`. Flat siblings rather than a `creator/` package, matching the `manager.py` + `manager_<aspect>.py` shape the `hook`, `lsp` and `subagent` managers were themselves flattened to — and the rename drops the `hook/hook_*` prefix stutter against siblings `manager.py`, `matcher.py`, `executor.py`. No behavior change.
- **Refactor: `command_hook` reduced from 256 lines to 72** (`src/zrb/llm/hook/creator.py`): the closure ran four phases in one body. `_build_hook_env`, `_encode_stdin_payload` and `_resolve_hook_cwd` now own the pre-spawn work, and `_interpret_exit` dispatches the exit code across `_blocked_result` / `_success_result` / `_signal_result` / `_failure_result`, leaving the spawn → capture-pgid → read-with-timeout core as the one genuinely linear stretch. The exit-2 and exit-0 branches deliberately keep separate stdout parsers instead of sharing one helper: only exit 2 distinguishes "stdout was a JSON control object" from "stdout was an empty dict", so folding them together would have changed what `echo '{}'; exit 2` reports as its block reason.
- **Refactor: the prompt and agent hooks stopped duplicating each other** (`src/zrb/llm/hook/creator.py`): `create_prompt_hook` and `create_agent_hook` were 58 lines each sharing roughly 40 — model resolution, the JSON-output parse and the error handler were verbatim identical, comments included. Both are now eight lines over the shared `_run_llm_hook`, differing only in where their two prompts come from (`_render_prompt_template` for placeholder substitution, `_agent_hook_input` for the event-payload fallback chain).
- **Tests: the hook tree-kill safety test never exercised the process-group guard** (`test/llm/hook/test_process_kill.py`): `test_kill_process_tree_never_targets_zrb_itself` looped over `(("own pid", os.getpid()), ("own group", os.getpid()))` — two labels over one identical value, so the case meant to cover the `killpg` vector only ever reached the `pid == os.getpid()` check and returned before the group logic ran. It is now two tests, the group case patching `os.getpgid` so a pid that is not ours still resolves into our group. Publishing the process helpers also retired the `from zrb.llm.hook.hook_creators import _kill_process_tree` private-member access the guidelines forbid.
- **Tests: `test_hook_creators.py` split by feature group** (`test/llm/hook/test_creator.py`, `test_creator_subprocess.py`, `test_creator_llm.py`, `test_process_io.py`, `test_process_kill.py`): the 922-line file was well past the 500-line split threshold. Coverage of the moved code was preserved exactly — the same 30 statements were uncovered before and after, `creator.py` landing at 100% — and then raised: `process_kill.py` 75% → 94% by covering the killpg-failure and psutil-fallback paths, `process_io.py` 87% → 90% by testing `read_hook_output` directly over real `os.pipe()` file descriptors instead of only through live subprocesses. What remains uncovered is Windows-only branches and EAGAIN races.
- **Docs: the hooks row of the chat-lifecycle file map** (`docs/advanced-topics/llm-chat-lifecycle.md`): names `creator.py` and `process_{io,kill}.py` in place of `hook_creators.py`. Historical `hook_creators.py` references in `changelog-v2/` are left as written — they record what shipped at the time.
