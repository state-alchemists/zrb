## 2.70.0 (unreleased)

- **Behavior change: `CFG` assignments fail fast** (`src/zrb/config/config.py`, `src/zrb/config/env_field.py`): assigning an unknown `CFG.UPPERCASE` name now raises `AttributeError` naming the closest real knob (via `difflib`), instead of silently creating a new attribute that no reader ever consumes. Assigning a value the field's `cast` cannot round-trip (e.g. `CFG.LLM_MAX_REQUEST_PER_MINUTE = "nope"`) now raises `ValueError` at the assignment site instead of at the next unrelated read. `DEFAULT_*` constants and read-write properties like `ROOT_GROUP_NAME` are unaffected. The error message names the real CLI command (`{ROOT_GROUP_NAME} config explain`), so a white-labeled deployment sees its own command name, not `zrb`.
- **Fix: `CFG.TODO_VISUAL_FILTER` and `CFG.SEARXNG_PORT` now respond to `zrb_init.py`** (`src/zrb/builtin/todo.py`, `src/zrb/builtin/searxng/start.py`): both were read once at import time — before `zrb_init.py` loads — so assigning them from `zrb_init.py` was a silent no-op. Both are now resolved lazily via a callable default.
- **Fix: `start-server`'s CLI description no longer bakes in a stale root group name** (`src/zrb/runner/cli.py`): the same import-time-read bug, on the `start-server` task's `--help` text. The description is now static text; the branded name never rendered correctly there for a white-labeled CLI (it's imported before white-labeling's env override runs) even before this fix.
- **Behavior change: a broken `zrb_init.py` (or `ZRB_INIT_SCRIPTS`/`ZRB_INIT_MODULES` entry) now aborts the CLI** (`src/zrb/__main__.py`, `src/zrb/util/load.py`): previously the failure was logged as one line with no file/line/type and the CLI continued with a half-applied config — the worst outcome, since the symptom then shows up somewhere unrelated. It now prints the file, line and exception type and exits 1. `load_file` gained an opt-in `raise_on_error` parameter (default `False`, so its existing lenient callers — plugin/skill/hook discovery — are unaffected) that the init-loading call site uses.
- **New test architecture ratchet: no `CFG.*` read at import time** (`test/architecture/test_deferred_config_reads.py`, R3).
- **Breaking: `LLMChatTask` now exposes the full R5 verb set on every ordered collection** (`src/zrb/llm/task/chat/task.py`): tools, tool factories, toolsets, toolset factories, history processors, triggers, custom commands, hook factories, tool policies, response handlers, argument formatters and UIs each gained whichever of `append_X`/`prepend_X`/`set_X`/`remove_X` was missing (tool policies, response handlers and argument formatters previously had only `prepend_X`; the rest previously had only `append_X`). `remove_X` is a no-op on a not-present item, matching `PromptRegistry`. Old → new: `set_ui(x)` → `set_uis([x])`; `set_ui_factory(x)` → `ui_factories = [x]` (the property was already settable — R7, one name per concept); `set_approval_channel(x)` → `approval_channels = [x]`; `set_history_manager(x)` → `history_manager = x` (a single-value slot, so it is a property, not a `set_X()` method — R7). `docs/task-types/llmchat-task.md` and `docs/advanced-topics/llm-custom-ui.md` are updated throughout.
- **Breaking: the hook family drops `register`/`clear_manual` for `add_hook`/`clear`** (`src/zrb/llm/hook/registry.py`, `src/zrb/llm/hook/manager.py`): `HookRegistry.register` → `add_hook`, matching every other family's verb (R6); `HookManager.register` → `add_hook` likewise. `HookRegistry.clear_manual()` → `clear()` — the old name claimed to clear only manually-registered hooks but always cleared the entire collection; the new name says what it does.
- **Breaking: `get_search_directories()` is gone from `HookManager`, `SkillManager`, and `SubAgentManager`** (`src/zrb/llm/hook/manager.py`, `src/zrb/llm/skill/manager.py`, `src/zrb/llm/agent/subagent/manager.py`): each now has exactly one `search_dirs` property (R7) — reading it returns the explicit override if one was set (at construction or by later assignment), else the computed defaults; assigning it invalidates any completed scan, so the next read/scan picks it up. `SkillManager`/`SubAgentManager` gained the setter for the first time (previously `search_dirs` could only be set at construction). `SubAgentManager.root_dir` → `scan_root`, so it cannot be confused with `search_dirs` — a different concept, the recursive scan target.
- **New test architecture ratchet: a uniform mutation-verb surface** (`test/architecture/test_mutation_surface.py`, R5/R6/R7).
- **New capability: `llm_chat.prompt_manager = pm` now works** (`src/zrb/llm/task/chat/task.py`), along with `hook_manager`, `llm_limiter`, and `markdown_theme` — every component slot `LLMChatTask` holds exactly one of is now a settable, type-checked property (R8), so a `zrb_init.py` can replace one wholesale on an already-defined task such as the built-in `llm_chat`. `history_manager`, `sandbox`, and `permissions` already worked this way. Assigning the wrong type raises `TypeError` naming the expected class, at the assignment site. `tool_confirmation` stays read-only for now: `AnyToolConfirmation` is not a real ABC (it resolves to plain `Any` at runtime), so it needs a proper type before it can be a type-checked slot — tracked for Phase 8 (R9). (The `llm_config` slot mentioned in this Phase 4 change is gone as of Phase 6, below — it never shipped as a slot in a released version.)
- **Breaking (narrow): `LLMChatTask.has_prompt_manager` is removed.** It always returned `True` — the constructor already builds a default `PromptManager` whenever none is passed, so `self._prompt_manager` could never actually be `None`. `prompt_manager`'s getter no longer raises either, for the same reason; both were dead code, not a real optionality. Old → new: `task.prompt_manager if task.has_prompt_manager else None` → `task.prompt_manager` (always safe now).
- **New test architecture ratchet: every declared slot is settable and typed** (`test/architecture/test_mutation_surface.py`, R8).
- **Breaking: `UIConfig` is now the single UI configuration object; `BaseUI` and `LLMChatTask` route through it instead of taking 16–20 individual parameters** (Phase 5, Option B — `src/zrb/llm/ui/ui_config.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/default/ui.py`, `src/zrb/llm/ui/simple_ui_base.py`, `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/task/chat/running.py`, `src/zrb/llm/task/chat/execution.py`):
  - `BaseUI.__init__` drops its 16 `*_commands` parameters plus `yolo_xcom_key`, `assistant_name`, `is_yolo`, `conversation_session_name` (34 → 15 parameters) in favor of one `ui_config: UIConfig | None`. `UI` (the built-in TUI) and `SimpleUI` (and therefore `EventDrivenUI`/`PollingUI`) follow. `BaseUI` gained a public `ui_config` property.
  - `LLMChatTask.__init__` drops `yolo_xcom_key`, `ui_commands: UICommands`, `show_ollama_models`, `show_pydantic_ai_models` (73 → 70 parameters) in favor of the same `ui_config: UIConfig | None`, exposed as a settable, type-checked slot (R8) — `llm_chat.ui_config = UIConfig(exit_commands=["/bye"])` works on the already-defined built-in task. `UICommands` and `UI_COMMAND_CFG_ATTRS` (`zrb.llm.task.chat.ui_commands`) are deleted; `UICommands` is removed from `zrb`'s top-level exports. Old → new: `LLMChatTask(ui_commands=UICommands(exit="/quit"))` → `LLMChatTask(ui_config=UIConfig(exit_commands=["/quit"]))`; `task.yolo_xcom_key` → `task.ui_config.yolo_xcom_key`; `task.show_ollama_models` → `task.ui_config.show_ollama_models` (same for `show_pydantic_ai_models`).
  - **Fix: `UIConfig`'s 16 command-list fields and `assistant_name` now default from `CFG` (`ZRB_LLM_UI_COMMAND_*`, `ZRB_LLM_ASSISTANT_NAME`) instead of separate hardcoded Python defaults**, so `SimpleUI`/`EventDrivenUI`/`PollingUI`/the web UI and the built-in TUI agree on the shipped command aliases and assistant name. Where the two previously disagreed, the `CFG` default wins (e.g. `exit_commands` gains `/q`, `:q`, `/bye`; `info_commands` gains `/info` and drops `/?`). `UIConfig` also gained `rewind_commands`, `btw_commands`, `voice_commands`, `show_ollama_models`, `show_pydantic_ai_models` fields — `SimpleUI`-family UIs previously never received the first three at all (a latent bug: `/rewind`, `/btw`, `/voice` silently did nothing there), now fixed as a side effect.
  - **Fix: a task-level yolo toggle and the UI built from it now agree on the xcom key.** `UIConfig.yolo_xcom_key` defaults to `"yolo"` (a stable value, not a random per-instance one) so the task's own initial-yolo-state write and the UI's read/write land on the same key.
  - `UIConfig.minimal()` is deleted (only its own tests used it) — construct `UIConfig(exit_commands=["/exit"], ...)` directly.
  - New ratchet: `test/architecture/test_constructor_surface.py` caps `LLMChatTask`/`LLMTask`/`BaseUI`'s parameter counts and asserts `LLMTask`/`LLMChatTask` agree on the relative order of their ~50 shared parameters (fixed as part of this phase: `hook_manager`, and the `ui`/`approval_channel`/`permissions`/`sandbox`/`yolo` cluster, were previously ordered differently between the two).
- **Breaking: `LLMConfig`/`llm_config` are gone — `CFG` is the only LLM configuration object** (Phase 6, R12 — `src/zrb/llm/config/config.py` deleted, `src/zrb/llm/config/model_resolver.py` new):
  - Every scalar `LLMConfig` used to hold is now a plain `CFG` knob: `llm_config.model` → `CFG.LLM_MODEL`, `llm_config.small_model` → `CFG.LLM_SMALL_MODEL`, `llm_config.multimodal_model` → `CFG.LLM_MULTIMODAL_MODEL`, `llm_config.api_key` → `CFG.LLM_API_KEY`, `llm_config.base_url` → `CFG.LLM_BASE_URL`, `llm_config.provider` → `CFG.LLM_PROVIDER` (new knob; `ZRB_LLM_PROVIDER` env var). `llm_config.model_settings` had no real reader and is dropped with no replacement.
  - `llm_config.resolve_model(base_model)` → `zrb.llm.config.model_resolver.resolve_configured_model(model)` / `resolve_configured_small_model(model)` / `resolve_configured_multimodal_model(model)` — three tier-specific functions instead of one method, each falling back through `CFG` the same way the old property getters did. The pure name-plus-credentials-to-`Model` resolution logic itself is unchanged, now living on the `ModelResolver` class (`model_resolver` singleton) `zrb`'s top-level exports.
  - `llm_config.model_getter` / `llm_config.model_renderer` → settable `model_getter` / `model_renderer` properties directly on `LLMTask`/`LLMChatTask`. These are now **task-scoped only** — the old global reach into every agent zrb creates (sub-agents, the summarizer, tool-internal agents) is gone; those call sites resolve `CFG.LLM_*` directly instead. A `zrb_init.py` that relied on setting `llm_config.model_getter` once to affect every agent process-wide must now set it per task.
  - `LLMTask(llm_config=...)` / `LLMChatTask(llm_config=...)` constructor params are gone, replaced by `model_getter=` / `model_renderer=` directly.
  - **Fix (latent bug, now closed):** `llm_config.small_model`/`multimodal_model` were process-wide global state — the `/model small ...` / `/model multimodal ...` slash commands wrote to the single shared `llm_config` singleton, so two concurrent chat sessions in one process (e.g. two web-UI users) could leak each other's model-tier choice. They are now propagated via two new per-run `ContextVar`s (`current_small_model`, `current_multimodal_model` in `src/zrb/llm/agent_state.py`), bound from the UI's own `small_model`/`multimodal_model` at the start of `run_agent()` — naturally isolated per concurrent session, same as `current_ui`/`current_yolo`. `MultiUI` does not yet proxy these two attributes to its children, so a `/model small ...` issued through a fanned-out `MultiUI` still falls back to `CFG` for now (narrow, documented limitation — not fixed in this phase).
  - New ratchet: `test/architecture/test_mutation_surface.py::test_there_is_exactly_one_configuration_object` (R12) — fails if a second `*_config` singleton is ever exported from `zrb.__all__` again. `web_auth_config` is exempted (a genuine hybrid with real user-list + callback state, not a thin `CFG` wrapper — folding it in is a separate follow-up).
  - `docs/configuration/llm-config.md`, `docs/task-types/llmchat-task.md`, `docs/configuration/llm-collections.md`, `docs/advanced-topics/hooks.md`, `docs/adr/adr-0090.md` updated throughout.
- **Refactor: the two ad-hoc registries ADR-0090's Context section named and never cleaned up are gone** (Phase 7, R12/ADR-0035):
  - `_ProviderRegistry` (`src/zrb/llm/prompt/manager.py`) is reclassified as a part, not migrated to a registry — it never had a `CFG` twin, a discovery layer, or layering, and served one call site. Renamed `LiveContextProviders`, moved to `src/zrb/llm/prompt/live_context_providers.py`, and made public (a part `PromptManager` composes, per ADR-0035 — a leading underscore was a false claim of module-privacy). Its `set`/`render` pair became the R6 verb set: `add_provider`/`remove_provider`/`set_providers`/`get_providers`/`render`. The `label` constructor argument (used only in one log line, one caller) is gone — the string is hardcoded. `PromptManager.add_live_context` keeps its name as a one-line delegator to `add_provider`, and gained the missing R6 siblings: `remove_live_context`, `set_live_contexts`, `get_live_contexts`. Anyone who imported the private class directly (`from zrb.llm.prompt.manager import _ProviderRegistry`) must switch to `from zrb.llm.prompt.live_context_providers import LiveContextProviders`.
  - **`SubAgentManager` split into roster and construction** (`src/zrb/llm/agent/subagent/manager.py`, new `src/zrb/llm/agent/subagent/building.py`): `create_agent`, `create_llm_chat_task`, `resolve_agent_build`, `get_tool_registry`, `get_tool_factories`, and `get_all_toolsets` moved to a new composed part, `SubAgentBuilding`, following the same part+delegator shape as every other family (ADR-0035) — the manager re-exposes each as a one-line delegator, so no external call site changes. `manager.py` dropped from 490 lines to 303, roster-only (`registry`, `reload`, `scan`, `search_dirs`, `add_agent`/`remove_agent`/`set_agents`/`get_agents`/`get_agent_definition`, `append_tool`/`append_tool_factory`/`append_toolset`/`append_toolset_factory`). The manager gained four new read-only accessors (`tool_registry_overrides`, `tool_factory_overrides`, `toolset_overrides`, `toolset_factory_overrides`) so the building part can reach the `append_tool*`-backed storage only through public names, never `self._owner._tool_registry` (ADR-0035's access rule).
  - New ratchet: `test/architecture/test_mutation_surface.py::test_managers_expose_the_same_roster_api` — `skill_manager`, `sub_agent_manager`, and `hook_manager` must each answer `registry`/`reload`/`scan`/`search_dirs`. `PromptManager` is deliberately excluded (ADR-0090 Part 1: a resolved per-task view, not a roster owner).
  - `test/architecture/test_facade_size_budget.py` gained a budget for `llm/agent/subagent/manager.py` (310 lines).
- **Breaking: the UI contract is `AnyUI`, and lives where it types things** (Phase 8, R9):
  - `UIProtocol` → `AnyUI`, matching the thirteen other `Any<Thing>` extension points (`AnyTask`, `AnyInput`, ...). It stays a `Protocol`, not an ABC — `StdUI`/`BaseUI` never explicitly subclass it, they satisfy it structurally, which is exactly the case a `Protocol` is for.
  - Moved `src/zrb/llm/tool_call/ui_protocol.py` → `src/zrb/llm/ui/any_ui.py` (with `ChoiceOption`/`ChoiceSpec`, its signature-support types) — it types the `ui` slot on every task, so it belongs to `llm/ui/`, not `llm/tool_call/` (a historical accident: tool confirmation was the first consumer). Exported from `zrb` for the first time: `from zrb import AnyUI`. Old → new: `from zrb.llm.tool_call.ui_protocol import UIProtocol` → `from zrb import AnyUI` (or `from zrb.llm.ui.any_ui import AnyUI` inside `zrb.llm.*` itself, `TYPE_CHECKING`-guarded — importing it eagerly now pulls in `BaseUI`'s `prompt_toolkit`-adjacent chain, which surfaced one real circular import during the move, fixed by moving ~15 call sites' imports under `TYPE_CHECKING`, quoting the annotation where the file had no `from __future__ import annotations`).
  - `src/zrb/llm/ui/__init__.py`'s class-hierarchy docstring said 4 methods (`ask_user`, `append_to_output`, `stream_to_parent`, `run_interactive_command`); `AnyUI` has always had 6 (also `ask_user_choice`, `run_async`). Fixed the diagram and every doc page repeating the stale count.
  - Two more R9 violations found by writing the ratchet (not anticipated by the phase plan): `AnyCmdVal` (`src/zrb/cmd/`) had the class name right but lived in `cmd_val.py`, not `any_cmd_val.py` — split out. `ApprovalChannel` (`src/zrb/llm/approval/`) was a genuine extension point (Terminal/Telegram/Web/Slack/WhatsApp implementers, per its own docstring) missing the `Any` prefix entirely — renamed `AnyApprovalChannel`, moved to `any_approval_channel.py` (`ApprovalContext`/`ApprovalResult` moved with it; `current_approval_channel`, the `ContextVar`, stays in `approval_channel.py`).
  - New ratchet: `test/architecture/test_boundaries.py::test_every_extension_point_is_named_any_thing_in_any_thing_py` — every ABC/`Protocol` naming a slot on a public object must be `Any<Thing>` in `any_<thing>.py`. Three named exemptions for `@runtime_checkable` Protocols used only for a local `isinstance` capability probe, never exposed as a public slot (`CommonToolHost`, `OverflowStore`, `HasActivityTracking`), plus a structural exemption for callback-signature-only Protocols (`PrintFn` and any future one shaped like it).
  - **Known, documented, not fixed here:** `LLMTask.uis` is a settable property with no `append_ui`/`prepend_ui`/`remove_ui`/`set_uis` verbs; `LLMChatTask.uis` is read-only but has the full R5 verb set instead. Both are internally R7-consistent (one name per concept within each class); the two task classes just disagree with each other. Follow-up for whichever phase next touches `LLMTask`'s collection verbs.
