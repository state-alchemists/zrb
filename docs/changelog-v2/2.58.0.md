## 2.58.0 (August 9, 2026)

**Breaking.** The Python API changes without shims — see [Upgrading to 2.58.0](../advanced-topics/upgrading-guide.md#upgrading-to-2580). Env keys are unaffected; `EnvField(aliases=...)` still covers those.

- **Fix: the prompt never said whether tool calls reach the real machine** (`src/zrb/llm/prompt/system_context.py`, `test/llm/prompt/test_system_context.py`, `AGENTS.md`, `docs/adr/adr-0076.md`): Priority Order rank 1 tells the model to confirm anything "irreversible, external, or destructive", and nothing in the composed prompt said whether *irreversible* was even true. `LLM_SANDBOX_ENABLED` defaults to `false`, so by default both enforcement layers are inactive — the Python FS gate in `agent.gates` and the OS shell wrapper — and every `Write`, `Edit` and `Shell` call lands on the user's disk; a grep of `system_context.py` and `live_context.py` for `sandbox` returned nothing. A rule whose stakes are invisible is a rule that gets under-applied, and this is the one rule where under-applying it destroys the user's work. `system_context` now emits `- Sandbox: none — file writes and shell commands take effect on this machine directly and are not contained.` There is deliberately **no affirmative branch**: a "you are sandboxed" line is a licence to relax rank 1, granted on a config the model cannot verify, so silence leaves the unconditional rule in force. That is the opposite polarity to the parallel-tool-call line beside it (ADR-0038), and for the opposite reason — that one announces the rare case, this one announces the risky one. It reads `get_effective_sandbox_policy()`, so a task built with `sandbox=True` is honoured, and it sits in the cached system context rather than `live_context` because the policy is bound once per run. See ADR-0076.
- **Fix: three relative ratchets could not see uniform prompt drift** (`test/llm/prompt/test_section_composition.py`, `AGENTS.md`): the burden ladder and the composed-total guard both pin the *ordering* across presets, and only `full` had an absolute ceiling. Adding a paragraph to all three variants at once therefore kept every ratchet green while every model got more to read. Each preset now carries its own ceiling on the composed prompt — `PRESET_BUDGETS`, currently full 24,000 / lean 20,000 / minimal 6,000 chars against 20,066 / 17,371 / 4,923 shipped. This is the enforcement arm of the rule that a more capable model buys more *autonomy*, not more *text*: `full` having headroom is not a reason to spend it.
- **Improvement: the two constrained presets get a number instead of a judgment call** (`src/zrb/llm/prompt/markdown/persona.minimal.md`, `persona.lean.md`): `persona` calibrated reply length qualitatively — "match depth to the task" — which is right for a frontier model and is precisely the kind of judgment `minimal` exists to stop asking for. opencode anchors it numerically at every tier (`default.txt` "fewer than 4 lines … One word answers are best"; `gemini.txt` "fewer than 3 lines"). `minimal` now caps the reply at four lines and says one word is often the whole answer; `lean` qualifies its existing direct-answer clause with the same number, without touching the "structured document for a plan" case it would otherwise contradict. Both fold into existing bullets rather than adding one, because the burden ladder requires the rule *count* to fall strictly across presets too.
- **Documentation: the model-family axis already existed and nothing said so** (`AGENTS.md`, `docs/adr/adr-0077.md`): opencode routes nine forked prompt files off a model-id substring; the compositional equivalent has been two existing calls since presets landed — `register_preset("gemini", Preset(variant="gemini"))` plus `register_model_profile("gemini-", "gemini")`, which ships `workflow.gemini.md` and inherits `register_preset`'s safety-floor and missing-variant checks. zrb ships **zero** family variants and should keep it that way: a family delta with no measurement behind it is the overfitting that makes `beast.txt` a liability on models that respond badly to forceful scaffolding. Capability governs how much the model is asked to hold; family stays on the escape hatch.
- **Fix: a comment invited a refactor that would have regressed two model families silently** (`src/zrb/llm/prompt/profile.py`, `test/llm/prompt/test_profile.py`, `docs/adr/adr-0077.md`): `ModelProfileRegistry` said *"Mirrors `model_capabilities`"*, and the two registries do have the same shape — user regex overrides, most-recent-wins, a built-in fallback table. They key on different things, and both keys are load-bearing. `model_capabilities` matches the **bare** name because a capability is a property of the weights (`gpt-4o` takes images under any provider), which is what lets its deny patterns be `^`-anchored. `model_profile_registry` matches the **full** id because a profile is a property of the deployment: `builtin_profile("ollama:phi4-mini")` is `minimal` while `builtin_profile("phi4-mini")` is `lean`, and `ollama:kimi-k2.6:cloud` is neither. Merging must pick one key — a bare name drops `LOCAL_PROVIDERS`/`_HOSTED_TIER` and sends every local small model back to `lean`; a full id un-anchors `^claude-haiku-3$` and grants a text-only model image support. Neither raises. The comment is replaced by the distinction, a test pins both halves, and both registries are now exported from `zrb` so the two calls at least live in one place. See ADR-0077.
- **Fix: `py.typed` was missing, so every downstream type-checker saw zrb as untyped** (`src/zrb/py.typed`): zrb is annotated throughout — `StrAttr`, `BoolAttr`, `AnyTask`, protocol classes, `TypeGuard` narrowing — and PEP 561 says none of it reaches a consumer without the marker file. `mypy` and `pyright` silently treated `from zrb import Task` as `Any`, which negated the single largest investment in the public API. One empty file.
- **Fix: `upstream=(a, b)` stored the tuple as if it were a task** (`src/zrb/task/base_task.py`, `src/zrb/task/any_task.py`, `src/zrb/task/base/operators.py`): `_ensure_task_list` narrowed with `isinstance(tasks, list)`, so any non-list sequence took the single-task branch and was stored *as* a task — surfacing much later and far away as `'tuple' object has no attribute 'name'`. The same `isinstance(..., list)` sat in `handle_rshift`, so `a >> (b, c)` was broken too. Both now discriminate on `AnyTask` — "is this one task?" has a single right answer, while "is this a collection?" has to enumerate every sequence type that is not one. `input=(...)` already worked, which is what made the inconsistency invisible.
- **Improvement: `Sequence` everywhere a task accepts a collection** (`src/zrb/task/*.py`, `src/zrb/llm/task/*.py`): `input`/`env` were `Sequence[...]` on `BaseTask` and `make_task` but `list[...]` on the other nine task classes, so a tuple type-checked against `Task` and failed against `CmdTask`; `readiness_check`/`upstream`/`fallback`/`successor` were `list[...]` even on `BaseTask` itself. All are now `Sequence`, including the public `append_upstream`/`append_fallback`/`append_successor`/`append_readiness_check` and the `>>`/`<<` operators. Widening, so no existing call breaks.
- **Improvement: `RsyncTask` now accepts what its own docstring promised** (`src/zrb/task/rsync_task.py`): it closed with "Every parameter `CmdTask` accepts is also accepted here", while omitting nine of them — the five `readiness_check_*`/`monitor_readiness` knobs (so an rsync task could declare a readiness check but never configure or monitor it), plus `shell_flag`, `render_shell_flag` and `is_interactive`. All nine are forwarded. The docstring now names the three real exclusions instead of implying none: `cmd` and `render_cmd` are generated from the path parameters, and `warn_unrecommended_command` screens a command you wrote.
- **Improvement: `LLMChatTask` accepts `hook_manager=`, like `LLMTask`** (`src/zrb/llm/task/chat/task.py`, `chat/execution.py`, `chat/state.py`): chat built a fresh `HookManager` per run with no way to supply one, so the only route to a shared manager was `append_hook_factory`. The default is unchanged and still isolating — `None` means a fresh manager per run, which is what keeps one chat session's hooks out of the next — and passing one explicitly is now the documented opt-out.
- **Removed: 21 `add_X` aliases on ordered collections** (`src/zrb/llm/task/building.py`, `src/zrb/llm/task/chat/building.py`, `src/zrb/llm/agent/subagent/manager.py`, `src/zrb/llm/prompt/manager.py`, `src/zrb/llm/common_tools.py`): each was one line forwarding to `append_X` or `prepend_X`, with a docstring saying so — double surface, no semantics. They went because `add_` had stopped meaning one thing: it forwarded to `append_` fifteen times and to `prepend_` three times, so `add_response_handler`, `add_tool_policy` and `add_argument_formatter` inserted at the *front* while every sibling appended. Position is the whole semantics of these calls, so the name states it now. The convention is written down: **ordered pipelines take `append_X`/`prepend_X`, unordered registries keep `add_X`** (`skill_manager.add_skill`, `sub_agent_manager.add_agent`, `Group.add_task`, `PromptManager.add_live_context`).
- **Removed: `AnyAttr`** (`src/zrb/attr/type.py`, `src/zrb/util/attr.py`, `src/zrb/input/base_input.py`): defined as `Any | fstring | Callable[..., Any]`, which collapses to plain `Any` — so it constrained nothing while looking like it did, and annotating a parameter with it bought silence rather than checking. Use `Any`, or the specific `*Attr` alias. `fstring` stays: it is also `str` to the checker, but in `BoolAttr = bool | fstring | ...` it documents "or a template string that renders to a bool", which `str` alone does not. `StrListAttr` is now exported — it appears in `LLMChatTask(active_skills=...)`, so users could not name the type of a parameter they must pass.
- **Breaking: task constructors are keyword-only after `name`** (`src/zrb/task/*.py`, `src/zrb/llm/task/*.py`): `LLMChatTask` had 73 positionally-passable parameters, `LLMTask` 53, `CmdTask` 45 — so inserting a parameter anywhere was a silent breaking change for anyone who had passed positionally. `Task("build")` still works; `Task("build", 5)` no longer does.
- **Breaking: `RsyncTask(auto_render_shell=)` is `render_shell=`** (`src/zrb/task/rsync_task.py`): the only site in the codebase spelling that flag with an `auto_` prefix, while its parent `CmdTask` spells the identical parameter `render_shell` — and `RsyncTask` already forwarded it under the new name internally.
- **New: 18 names exported from `zrb`** (`src/zrb/__init__.py`): the managers were exported without the types needed to call them — `hook_manager` with no `HookResult` is a registry you cannot return from. Added: `Skill`, `SubAgentDefinition`, `HookEvent`, `HookContext`, `HookResult`, `PromptManager`, `Preset`, `register_preset`, `register_model_profile`, `model_capabilities`, `register_theme`, `register_always_auto_approve`, `PermissionPolicy`, `Rule`, `ALLOW`, `DENY`, `ASK`, `StrListAttr`. No `zrb/llm/__init__.py` was added on purpose: `zrb.llm` is an implicit namespace package whose eleven children each curate their own `__all__`, and giving it an eager root would make a narrow `zrb.llm.sandbox` import pull the whole LLM stack. The curated tier is `zrb` itself.
- **Documentation: the four highest-traffic public symbols had no docstring at all** (`src/zrb/group/group.py`, `src/zrb/task/make_task.py`, `src/zrb/task/task.py`, `src/zrb/input/str_input.py`): `Group` had no module, class or member docs across twelve public members; `make_task` had none despite 22 parameters and headline billing; `Task` and `StrInput` were `class X(Base): pass` with `__doc__ is None`, and they are the first names in every tutorial. All four now carry worked examples. `Group.add_group` is also correctly typed `AnyGroup | str` — it has always accepted a bare string as shorthand — and the alias-then-name fallback in `remove_group`/`remove_task` is documented rather than left to be discovered.
