## 2.55.1 (August 6, 2026)

- **Refactor: `hook_creators.py` split into three modules** (`src/zrb/llm/hook/creator.py`, `src/zrb/llm/hook/process_io.py`, `src/zrb/llm/hook/process_kill.py`, `src/zrb/llm/hook/manager.py`): the 739-line module held two unrelated concerns — the three `create_*_hook` factories, and roughly 310 lines of POSIX subprocess plumbing (selector-driven pipe draining, daemon-thread detaching, process-group kills) that only the command hook needs. `create_prompt_hook` and `create_agent_hook` sat at lines 620 and 681, buried behind machinery neither touches. The read side is now `process_io.read_hook_output` / `run_detached` and the kill side `process_kill.read_process_group` / `kill_process_tree`, both public in their own modules; the factories keep `creator.py`. Flat siblings rather than a `creator/` package, matching the `manager.py` + `manager_<aspect>.py` shape the `hook`, `lsp` and `subagent` managers were themselves flattened to — and the rename drops the `hook/hook_*` prefix stutter against siblings `manager.py`, `matcher.py`, `executor.py`. No behavior change.
- **Refactor: `command_hook` reduced from 256 lines to 72** (`src/zrb/llm/hook/creator.py`): the closure ran four phases in one body. `_build_hook_env`, `_encode_stdin_payload` and `_resolve_hook_cwd` now own the pre-spawn work, and `_interpret_exit` dispatches the exit code across `_blocked_result` / `_success_result` / `_signal_result` / `_failure_result`, leaving the spawn → capture-pgid → read-with-timeout core as the one genuinely linear stretch. The exit-2 and exit-0 branches deliberately keep separate stdout parsers instead of sharing one helper: only exit 2 distinguishes "stdout was a JSON control object" from "stdout was an empty dict", so folding them together would have changed what `echo '{}'; exit 2` reports as its block reason.
- **Refactor: the prompt and agent hooks stopped duplicating each other** (`src/zrb/llm/hook/creator.py`): `create_prompt_hook` and `create_agent_hook` were 58 lines each sharing roughly 40 — model resolution, the JSON-output parse and the error handler were verbatim identical, comments included. Both are now eight lines over the shared `_run_llm_hook`, differing only in where their two prompts come from (`_render_prompt_template` for placeholder substitution, `_agent_hook_input` for the event-payload fallback chain).
- **Tests: the hook tree-kill safety test never exercised the process-group guard** (`test/llm/hook/test_process_kill.py`): `test_kill_process_tree_never_targets_zrb_itself` looped over `(("own pid", os.getpid()), ("own group", os.getpid()))` — two labels over one identical value, so the case meant to cover the `killpg` vector only ever reached the `pid == os.getpid()` check and returned before the group logic ran. It is now two tests, the group case patching `os.getpgid` so a pid that is not ours still resolves into our group. Publishing the process helpers also retired the `from zrb.llm.hook.hook_creators import _kill_process_tree` private-member access the guidelines forbid.
- **Tests: `test_hook_creators.py` split by feature group** (`test/llm/hook/test_creator.py`, `test_creator_subprocess.py`, `test_creator_llm.py`, `test_process_io.py`, `test_process_kill.py`): the 922-line file was well past the 500-line split threshold. Coverage of the moved code was preserved exactly — the same 30 statements were uncovered before and after, `creator.py` landing at 100% — and then raised: `process_kill.py` 75% → 94% by covering the killpg-failure and psutil-fallback paths, `process_io.py` 87% → 90% by testing `read_hook_output` directly over real `os.pipe()` file descriptors instead of only through live subprocesses. What remains uncovered is Windows-only branches and EAGAIN races.
- **Docs: the hooks row of the chat-lifecycle file map** (`docs/advanced-topics/llm-chat-lifecycle.md`): names `creator.py` and `process_{io,kill}.py` in place of `hook_creators.py`. Historical `hook_creators.py` references in `changelog-v2/` are left as written — they record what shipped at the time.
