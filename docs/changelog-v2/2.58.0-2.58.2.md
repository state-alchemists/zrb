## Unreleased

- **Improvement: one turn sequence instead of two, and the rules scale to the turn** (`src/zrb/llm/prompt/markdown/workflow.md`, `persona.md`, `examples.md`, `test/llm/prompt/test_manager.py`, `test_section_composition.py`, `llm-experiment/probes.py`): a review scored *ease of following* 5/10 and *ergonomics* 4/10, on three findings that all check out. **`Turn Sequence` and `Working Loop` were one procedure split across two headings** — four steps, then "Then run the Working Loop: Understand → Diagnose → …", then that loop as its own section 50 lines later with the stance table inside it. A reader had a ladder inside a ladder and no way to tell which one they were on. They merge into one nine-step `Turn Sequence` with the stance table under step 2; `Working Loop` is retired as a heading and `Execute` promoted to carry its own bullets. **The prompt asked for the whole ladder on every turn**, which is the ergonomics complaint and also the instruction-stacking failure mode: the sequence now opens by scaling itself — most turns are a question you can answer or a file you can read and fix end to end, and those go straight to the work, with the steps earning their keep on multi-file changes, destructive actions, suspect premises, and requests you would otherwise guess at. Running the full ladder on a one-line answer is named as its own failure. **Two contradictions are fixed:** "Frame the turn by naming the deliverable in one sentence" read as an instruction to publish a framing sentence, directly against `persona`'s *Skip preamble* — it now says the framing is a decision, not a sentence to publish; and `persona`'s closing rule, which the review said made it second-guess every turn, is cut to a mechanical test ("did anything change outside this reply?"). `examples.md` drops from 14 demonstrations to 9 — the trivial `2 + 2`, the duplicate `--dry-run` change, the redundant `file:line` citation, and the urgency demo whose rule now lives in `## Safety` — leaving three stance demos, three delivery demos, and the three that outrank the request. **`full` is 19,533 → 18,074 characters (4,489 → 4,142 tokens), −7.5% over three passes.** Deliberately left alone: the `<!--requires:system_context-->` batching caveat the review also flagged, because a model that genuinely cannot batch needs it and the marker already withdraws it everywhere else.
- **Improvement: `examples` gets a `minimal` variant, and both presets get smaller** (`src/zrb/llm/prompt/markdown/examples.md`, new `examples.minimal.md`, `workflow.minimal.md`, `workflow.md`, `src/zrb/llm/prompt/profile.py`, `llm-experiment/measure.py`, `test/llm/prompt/test_prompt_mandates.py`): `minimal` was the one preset whose demonstrations were not separable from its rules — `workflow.minimal.md` carried them inline, so they could not be toggled, the burden-ladder tests could not see them, and the two presets kept their examples in different places. They move to `examples.minimal.md` and `examples` joins `MINIMAL_SECTIONS`, so both presets now ship the same three file-backed sections and differ only by variant, which is what the variant axis is for. The base `examples.md` is compressed from twelve headings to five that mirror the rulebook's own shape (stance, scale, evidence, delivery, and the three that outrank the request), with every demonstration tightened and the duplicate branch-deletion and rename demos dropped. The rule that only `examples` stated — pressure to skip a check is the reason to run it — moves into `## Safety`, so the file's claim to add no rules of its own is now true. `Where the deliverable goes` loses the clause that repeated *When you don't know* #4. **Net: `full` 19,533 → 18,876 characters (−657, the first reduction in five passes) and `minimal` 4,387 → 4,294.** Also fixes `measure.py`, which hardcoded a copy of each preset's section list and so silently stopped counting `minimal`'s 1,013 characters of examples while the composed column beside it counted them; it now derives the list from `PRESETS`.
- **Fix: the mock filesystem discarded every write, and the scorers could not see it** (`llm-experiment/run.py`, `probes.py`, `analyze.py`, `docs/adr/adr-0049.md`, `adr-0046.md`, `test/llm/prompt/test_section_composition.py`): `Write`, `Edit`, `RM` and `MV` recorded the call, returned `"Edited /project/auth.py."`, and mutated nothing; `Read` served the original fixture forever. Probes score call sequences, so a mutable world had looked unnecessary. It is the difference between measuring the agent and measuring a lie: a model that obeys *"check the artifact, not your memory of writing it"* reads the file back, finds the typo still there, and correctly concludes the filesystem is broken — one `gemini-2.5-pro` cell spent 21 calls and 189k input tokens cycling `Edit` → `Write` → `RM`+`Write` → `sed` before reporting the file was read-only, and 22 of 101 rows in the aborted grid showed that signature across every arm including opencode's. **The penalty is directional:** it falls on whichever prompt insists hardest on verifying its own work, which is `zrb-full`. `build_tools` now takes a private mutable copy of `WORLD` per cell, `Edit` errors on a missing anchor like the shipped tool, and `Shell` refuses `sed -i`/`>`/`tee` by name instead of returning success-shaped silence. `Trace` carries the final world, and the four probes that scored call shape alone now check the deliverable — `method_read_before_edit` had been passing runs that ended *"the file remains uncorrected"*, and `method_batch` passed a model that batched three reads and named the wrong file. Rows gained `harness_sha` (the world plus every scorer) alongside `prompt_sha`, both part of the resume key and of `analyze.py`'s configuration key, because nothing had fingerprinted either: an arm name is stable across every prompt edit, so a resume was matching today's cell against rows measured under a different prompt *and* a different harness. **Consequences for the record:** ADR-0049's measured claims are withdrawn — the 44%/88% rank-1 safety gap, the 48% → 69% substitute-form re-measurement, the `persona` and `examples` ablations, and every per-rule ablation — and the corrected 610-cell grid replaces them with a result that separates nothing (`full` 76% [67–83] vs `minimal` 86% [78–91], −10pp CI [−20, +1]). Two conclusions drawn from the withdrawn numbers were wrong and had been acted on: that `full` complies with rank-1 safety at half `minimal`'s rate, and that destructive-action and secret-handling rules cannot be moved by prose and need a runtime gate — those probes now read 80% and 60%. ADR-0046 gains a third null position grid (75/65/70). A fourth harness/production mismatch is recorded and **not** yet fixed: tool retries run at pydantic-ai's default of 1 against zrb's `LLM_TOOL_MAX_RETRIES` of 3, which dropped 16 `gemini-2.5-flash-lite` cells the shipped agent would have recovered.
- **Fix: the stance table classified turns by keyword and told the model to answer from memory** (`src/zrb/llm/prompt/markdown/workflow.md`): the Working Loop keyed its three stances on surface phrasing — *an answer*: "explain…", "compare…" — and gave the answer row the stance **"Reply from what you know."** Both halves are wrong together. "Explain how our retry logic works" matches the keyword and is a claim about this repo, so the row told the model to answer a repo question from memory, contradicting rank 3 (verified before you reply), `persona`'s *Claim only what you checked*, and the Understand step — and conflicting instructions are the most-cited root cause of instruction-following failure. `examples.md` had the rule right all along ("opens no files — *the question is not about this repo*"); the table was the brittle restatement of it. Rows now key on what makes a deliverable that kind of deliverable — words are the whole product / a verdict and what you would change / the result lands on disk — and the answer row separates the two axes the keyword version had fused: how far to investigate (as far as the answer needs) is independent of where the deliverable lands (not on disk). Two smaller over-specifications went with it: the check-bypass rule generalizes from three git and unix tokens to *anything that silences a check rather than satisfying it* (keeping them as the examples, adding `--force`), and the delegation section no longer asserts that a tool named `DelegateToAgent` exists — the paragraph above it is already conditional on a delegation tool being present, so naming one unconditionally three lines later could dangle.
- **Improvement: six rules generalized to the principle that subsumes them** (`src/zrb/llm/prompt/markdown/workflow.md`, `persona.md`): a review scored *ease of following* 6/10 on redundancy and on one rule being "philosophically correct but operationally ambiguous". Both are the same defect — a principle stated as its instances. **Scope** said "approval for one file is not approval for its neighbors" and, one clause later, "a rename includes its call sites … without re-asking", leaving the boundary between them to be inferred; it now states the test instead — approval carries to whatever the change *mechanically entails*, meaning one correct edit that a search finds with no judgment left in it, and anything needing a fresh decision is a fresh ask however adjacent the file. **Recovery**'s three-strikes rule generalizes from "rewording a command is not a new approach" to *repeating an action that produced nothing new* is not, which subsumes *When you don't know*'s re-weighing stall as the same move rather than a second rule. `persona`'s **Verify before you assert** is renamed **Claim only what you checked**: it governs assertions while `Verify Before Done` governs artifacts, and the shared word made two rules read as a duplicated one — the review counted "verification in at least three places", where the prompt says "verif" nine times across four distinct rules. **Project Documentation**'s trigger gets a mechanical test (will this turn open a file in this project?) in place of "the work, not the turn number" alone, and **Delegating** drops the implementation detail it rested on ("re-pays the whole system prompt") for the fact that survives a refactor. Not a size win: **+166 characters**. A rule stated as a usable test costs more words than the instances it replaces, which is the honest trade and the third consolidation pass in a row to end up net-longer. Declined: trimming `examples`. The ablation that would justify it ran on the thin-tool 12-request configuration this release retracts, so there is no valid measurement either way, and demonstrations are the content the preset ladder exists to protect.
- **Improvement: the Priority Order stopped being two documents under one heading** (`src/zrb/llm/prompt/markdown/workflow.md`, `docs/adr/adr-0046.md`, `adr-0045.md`, `test/llm/prompt/test_section_composition.py`, `test_manager.py`): ranks 3–7 were one-line pointers at the section that owns each rule — `Quality` → *Verify Before Done*, `Method` → *Skill Activation*, `Efficiency` → the batching rules — while rank 1 carried the whole safety policy inline at 1,467 of the ladder's 2,785 characters. The ladder therefore changed genre halfway down, and safety was the only major rule area with no heading of its own: a model looking for how to handle a destructive request had to already be reading a list whose preamble says "Precedence, not sequence". Safety is now `## Safety` immediately below the ladder, and rank 1 points at it like every other rank. Three duplicate statements went with the pass: `A batch is N tool calls, never one payload describing them` merged into `Describing an action is not performing it` in `Execute` — two sections apart, repeating each other's JSON-or-table illustration — which retires the `### Tool usage` heading; `Never guess an argument` merged into *When you don't know*'s "a tool can settle it"; and `Brevity shapes the report, never the check` came out of `Verify Before Done`, since the Priority Order preamble already states the compress-don't-drop tie-break for every rule, not just that one. This is a legibility change and is claimed as one — it is **+104 characters**, not the ~800 saved that was estimated, because a heading and three paragraph breaks cost about what the duplication returned, and `safety_destructive` / `safety_secret` are the two probes no prose revision has moved.
- **Fix: the prompt harness never showed the model half of zrb's instructions** (`llm-experiment/surface.py`, `run.py`, `README.md`, `docs/adr/adr-0049.md`, `adr-0058.md`): pydantic-ai serializes every registered tool's description *and* parameter schema into every request, and ADR-0045 puts per-tool mechanics in the docstring on purpose — so a tool definition is prompt text, and it is 12,370 characters of it against 20,724 of composed `full` prompt. The harness handed its mock tools **one-line docstrings**, roughly a fifth of that, which means the one surface ADR-0045 deliberately moves rules onto was the surface no arm ever exercised, and every "rule R costs nothing" reading was taken with R's other half absent. `--tools prod` (now the default) builds each cell's tools with `Tool.from_schema` from the shipped `(name, description, parameters_json_schema)` and binds a mock executor to them, so the definitions are real and only the implementations are fakes; `--tools preset` gives each arm its own preset's surface, and `--tools thin` keeps the old behaviour so committed rows stay readable. The surface is recorded on every row and forms part of a cell's identity — without that, a resume looks at 610 thin rows and reports a production-surface grid as already finished.
- **Fix: the shipped loop guard was absent from every measured run** (`llm-experiment/run.py`): ADR-0077's `RepeatedCallDetector` refuses a byte-identical tool call repeated back to back, wired into `SafeToolsetWrapper`. The harness builds its own agent, so none of that was in the path, and the non-convergence statistics described an agent zrb no longer sends. The guard is imported from `zrb` rather than reimplemented — a copy is a second thing to keep in step — and `--no-guard` is the before-side. Wiring it in is also what showed the guard was not the issue: the cut-off cells' calls are *varied*, not repeats, so there was never anything for it to fire on.
- **Fix: `measure.py` reported tool weight with the arguments missing** (`llm-experiment/measure.py`, `surface.py`, `docs/adr/adr-0058.md`, `adr-0049.md`): it read the parameter schema off `Tool._parameters_json_schema`, a private attribute pydantic-ai does not define. `getattr(..., None)` returned `None`, the schema stringified to `"None"`, and the published figure counted every tool's name and description with none of its arguments — while looking exactly like a measurement. Reading `Tool.tool_def`, which is what pydantic-ai actually serializes, puts `full`'s eager surface at **3,860 tokens over 20 tools, not 2,482**, and `minimal`'s at 2,349 over 10. That changes the ratio the preset ladder rests on: tools are 44% of `full`'s preamble and **66% of `minimal`'s**, so the preset that drops the most prose is the one whose budget is most nearly all tool definitions. The per-tool columns were mislabelled too — pydantic-ai puts the whole docstring in `description`, so `Shell` is 2,134 characters of docstring against 474 of schema, and the table had been calling one line of it "desc" and the rest "schema".
- **Fix: every published pass rate was a bare percentage over ten runs** (`llm-experiment/analyze.py`): the tables invited a comparison the cells cannot support, and both the ADRs and an outside review took it up — in opposite directions, off the same numbers. Rates now carry a 95% Wilson interval, each ladder table is followed by its pairwise differences by Newcombe's method, and the by-probe table is followed by a line naming the probes that actually separate the arms. On the production-surface grid that line reads *no probe separates `zrb-full` from `zrb-minimal` at 95%*; on the older grid, the preset ladder, rule position and both section ablations are all not distinguishable. `analyze.py` also reports one run configuration at a time and names it in the header, rather than averaging two experiments that differ by 10,000 characters of tool text.
- **Fix: the harness's own request budget was the largest effect in it** (`llm-experiment/run.py`, `analyze.py`, `README.md`, `docs/adr/adr-0077.md`, `adr-0049.md`): cells ran at `UsageLimits(request_limit=12)`, against a shipped `LLM_MAX_REQUEST_PER_RUN` of 300, so a cell recorded as "hit the request limit" would have kept going in a real session — and a cell cut off mid-task scores as a failure of whatever probe it was on. Re-running the three probes that dominated the cut-off count at 40 requests: cut-offs fall **35/60 → 5/60** and the pass rate rises **+24pp, 95% CI [+7, +40]**, the only interval-clearing result this harness has produced. It does not cancel across arms: a shorter prompt with fewer tools reaches the same place in fewer turns, so **`minimal` has been collecting passes `full` ran out of room to earn**, in every grid published so far. The default is now 40, the value is recorded per row, and `FINDINGS.md` gained a section reporting the effect wherever two budgets overlap. ADR-0077 keeps its decision and withdraws this statistic as corroboration for it — the three transcripts behind that record show real repetition and are unaffected.
- **Fix: two probes in the same battery could not both be satisfied** (`llm-experiment/probes.py`): `hard_scope` passed when the model edited exactly one file; `hard_coupled_edits` passed only when a version bump also edited `CHANGELOG.md` nobody had named. One rewarded what the other failed, and it scored **0% in every arm and every model**. The rule it claimed to test says "a rename includes its call sites and a deletion its references" — couplings a grep *finds* — whereas whether a changelog moves with a version is a project convention no rule in the prompt states, so the 0% measured the probe. Replaced by `hard_rename_call_sites`, which renames a function called from two other files and passes when both callers move. The definition's own file is deliberately not required: renaming the symbol invites renaming the module, which is defensible and relocates the path a stricter scorer would look for.

## 2.58.0 (August 9, 2026)

**Breaking.** The Python API changes without shims — see [Upgrading to 2.58.0](../advanced-topics/upgrading-guide.md#upgrading-to-2580). Env keys are unaffected; `EnvField(aliases=...)` still covers those.

- **Fix: the prompt never said whether tool calls reach the real machine** (`src/zrb/llm/prompt/system_context.py`, `test/llm/prompt/test_system_context.py`, `AGENTS.md`, `docs/adr/adr-0050.md`): Priority Order rank 1 tells the model to confirm anything "irreversible, external, or destructive", and nothing in the composed prompt said whether *irreversible* was even true. `LLM_SANDBOX_ENABLED` defaults to `false`, so by default both enforcement layers are inactive — the Python FS gate in `agent.gates` and the OS shell wrapper — and every `Write`, `Edit` and `Shell` call lands on the user's disk; a grep of `system_context.py` and `live_context.py` for `sandbox` returned nothing. A rule whose stakes are invisible is a rule that gets under-applied, and this is the one rule where under-applying it destroys the user's work. `system_context` now emits `- Sandbox: none — file writes and shell commands take effect on this machine directly and are not contained.` There is deliberately **no affirmative branch**: a "you are sandboxed" line is a licence to relax rank 1, granted on a config the model cannot verify, so silence leaves the unconditional rule in force. That is the opposite polarity to the parallel-tool-call line beside it (ADR-0038), and for the opposite reason — that one announces the rare case, this one announces the risky one. It reads `get_effective_sandbox_policy()`, so a task built with `sandbox=True` is honoured, and it sits in the cached system context rather than `live_context` because the policy is bound once per run. See ADR-0050.
- **Fix: three relative ratchets could not see uniform prompt drift** (`test/llm/prompt/test_section_composition.py`, `AGENTS.md`): the burden ladder and the composed-total guard both pin the *ordering* across presets, and only `full` had an absolute ceiling. Adding a paragraph to all three variants at once therefore kept every ratchet green while every model got more to read. Each preset now carries its own ceiling on the composed prompt — `PRESET_BUDGETS`, currently full 24,000 / lean 20,000 / minimal 6,000 chars against 20,066 / 17,371 / 4,923 shipped. This is the enforcement arm of the rule that a more capable model buys more *autonomy*, not more *text*: `full` having headroom is not a reason to spend it.
- **Improvement: the two constrained presets get a number instead of a judgment call** (`src/zrb/llm/prompt/markdown/persona.minimal.md`, `persona.lean.md`): `persona` calibrated reply length qualitatively — "match depth to the task" — which is right for a frontier model and is precisely the kind of judgment `minimal` exists to stop asking for. opencode anchors it numerically at every tier (`default.txt` "fewer than 4 lines … One word answers are best"; `gemini.txt` "fewer than 3 lines"). `minimal` now caps the reply at four lines and says one word is often the whole answer; `lean` qualifies its existing direct-answer clause with the same number, without touching the "structured document for a plan" case it would otherwise contradict. Both fold into existing bullets rather than adding one, because the burden ladder requires the rule *count* to fall strictly across presets too.
- **Documentation: the model-family axis already existed and nothing said so** (`AGENTS.md`, `docs/adr/adr-0051.md`): opencode routes nine forked prompt files off a model-id substring; the compositional equivalent has been two existing calls since presets landed — `register_preset("gemini", Preset(variant="gemini"))` plus `register_model_profile("gemini-", "gemini")`, which ships `workflow.gemini.md` and inherits `register_preset`'s safety-floor and missing-variant checks. zrb ships **zero** family variants and should keep it that way: a family delta with no measurement behind it is the overfitting that makes `beast.txt` a liability on models that respond badly to forceful scaffolding. Capability governs how much the model is asked to hold; family stays on the escape hatch.
- **Fix: a comment invited a refactor that would have regressed two model families silently** (`src/zrb/llm/prompt/profile.py`, `test/llm/prompt/test_profile.py`, `docs/adr/adr-0051.md`): `ModelProfileRegistry` said *"Mirrors `model_capabilities`"*, and the two registries do have the same shape — user regex overrides, most-recent-wins, a built-in fallback table. They key on different things, and both keys are load-bearing. `model_capabilities` matches the **bare** name because a capability is a property of the weights (`gpt-4o` takes images under any provider), which is what lets its deny patterns be `^`-anchored. `model_profile_registry` matches the **full** id because a profile is a property of the deployment: `builtin_profile("ollama:phi4-mini")` is `minimal` while `builtin_profile("phi4-mini")` is `lean`, and `ollama:kimi-k2.6:cloud` is neither. Merging must pick one key — a bare name drops `LOCAL_PROVIDERS`/`_HOSTED_TIER` and sends every local small model back to `lean`; a full id un-anchors `^claude-haiku-3$` and grants a text-only model image support. Neither raises. The comment is replaced by the distinction, a test pins both halves, and both registries are now exported from `zrb` so the two calls at least live in one place. See ADR-0051.
- **Fix: `py.typed` was missing, so every downstream type-checker saw zrb as untyped** (`src/zrb/py.typed`): zrb is annotated throughout — `StrAttr`, `BoolAttr`, `AnyTask`, protocol classes, `TypeGuard` narrowing — and PEP 561 says none of it reaches a consumer without the marker file. `mypy` and `pyright` silently treated `from zrb import Task` as `Any`, which negated the single largest investment in the public API. One empty file.
- **Fix: `upstream=(a, b)` stored the tuple as if it were a task** (`src/zrb/task/base_task.py`, `src/zrb/task/any_task.py`, `src/zrb/task/base/operators.py`): `_ensure_task_list` narrowed with `isinstance(tasks, list)`, so any non-list sequence took the single-task branch and was stored *as* a task — surfacing much later and far away as `'tuple' object has no attribute 'name'`. The same `isinstance(..., list)` sat in `handle_rshift`, so `a >> (b, c)` was broken too. Both now test the *collection* side — `isinstance(..., Sequence)`, with `str`/`bytes` rejected outright since they satisfy `Sequence` and never satisfy `AnyTask`. Testing the task side instead (`isinstance(tasks, AnyTask)`) was the first attempt and was wrong: anything task-like that is not an `AnyTask` subclass — a stub, a `MagicMock`, a duck-typed adapter — is not an instance, so it would be handed to `list()`. `input=(...)` already worked, which is what made the inconsistency invisible.
- **Improvement: `Sequence` everywhere a task accepts a collection** (`src/zrb/task/*.py`, `src/zrb/llm/task/*.py`): `input`/`env` were `Sequence[...]` on `BaseTask` and `make_task` but `list[...]` on the other nine task classes, so a tuple type-checked against `Task` and failed against `CmdTask`; `readiness_check`/`upstream`/`fallback`/`successor` were `list[...]` even on `BaseTask` itself. All are now `Sequence`, including the public `append_upstream`/`append_fallback`/`append_successor`/`append_readiness_check` and the `>>`/`<<` operators. Widening, so no existing call breaks.
- **Improvement: `RsyncTask` now accepts what its own docstring promised** (`src/zrb/task/rsync_task.py`): it closed with "Every parameter `CmdTask` accepts is also accepted here", while omitting nine of them — the five `readiness_check_*`/`monitor_readiness` knobs (so an rsync task could declare a readiness check but never configure or monitor it), plus `shell_flag`, `render_shell_flag` and `is_interactive`. All nine are forwarded. The docstring now names the three real exclusions instead of implying none: `cmd` and `render_cmd` are generated from the path parameters, and `warn_unrecommended_command` screens a command you wrote.
- **Improvement: `LLMChatTask` accepts `hook_manager=`, like `LLMTask`** (`src/zrb/llm/task/chat/task.py`, `chat/execution.py`, `chat/state.py`): chat built a fresh `HookManager` per run with no way to supply one, so the only route to a shared manager was `append_hook_factory`. The default is unchanged and still isolating — `None` means a fresh manager per run, which is what keeps one chat session's hooks out of the next — and passing one explicitly is now the documented opt-out.
- **Removed: 22 `add_X` aliases on ordered collections** (`src/zrb/llm/task/building.py`, `src/zrb/llm/task/chat/building.py`, `src/zrb/llm/agent/subagent/manager.py`, `src/zrb/llm/prompt/manager.py`, `src/zrb/llm/common_tools.py`): each was one line forwarding to `append_X` or `prepend_X`, with a docstring saying so — double surface, no semantics. They went because `add_` had stopped meaning one thing: it forwarded to `append_` nineteen times and to `prepend_` three times, so `add_response_handler`, `add_tool_policy` and `add_argument_formatter` inserted at the *front* while every sibling appended. Position is the whole semantics of these calls, so the name states it now. The convention is written down: **ordered pipelines take `append_X`/`prepend_X`, unordered registries keep `add_X`** (`skill_manager.add_skill`, `sub_agent_manager.add_agent`, `Group.add_task`, `PromptManager.add_live_context`).
- **Removed: `AnyAttr`** (`src/zrb/attr/type.py`, `src/zrb/util/attr.py`, `src/zrb/input/base_input.py`): defined as `Any | fstring | Callable[..., Any]`, which collapses to plain `Any` — so it constrained nothing while looking like it did, and annotating a parameter with it bought silence rather than checking. Use `Any`, or the specific `*Attr` alias. `fstring` stays: it is also `str` to the checker, but in `BoolAttr = bool | fstring | ...` it documents "or a template string that renders to a bool", which `str` alone does not. `StrListAttr` is now exported — it appears in `LLMChatTask(active_skills=...)`, so users could not name the type of a parameter they must pass.
- **Breaking: task constructors are keyword-only after `name`** (`src/zrb/task/*.py`, `src/zrb/llm/task/*.py`): `LLMChatTask` had 73 positionally-passable parameters, `LLMTask` 53, `CmdTask` 45 — so inserting a parameter anywhere was a silent breaking change for anyone who had passed positionally. `Task("build")` still works; `Task("build", 5)` no longer does.
- **Breaking: `RsyncTask(auto_render_shell=)` is `render_shell=`** (`src/zrb/task/rsync_task.py`): the only site in the codebase spelling that flag with an `auto_` prefix, while its parent `CmdTask` spells the identical parameter `render_shell` — and `RsyncTask` already forwarded it under the new name internally.
- **New: 18 names exported from `zrb`** (`src/zrb/__init__.py`): the managers were exported without the types needed to call them — `hook_manager` with no `HookResult` is a registry you cannot return from. Added: `Skill`, `SubAgentDefinition`, `HookEvent`, `HookContext`, `HookResult`, `PromptManager`, `Preset`, `register_preset`, `register_model_profile`, `model_capabilities`, `register_theme`, `register_always_auto_approve`, `PermissionPolicy`, `Rule`, `ALLOW`, `DENY`, `ASK`, `StrListAttr`. That is a clean separation of form from size: rule form is the causal variable, and the presets differed on it by accident of how each was written. `test_rank_one_rules_name_the_substitute_behaviour` pins the form per preset. Byte-identical rank-1 text across presets was considered and rejected — it would delete the `Interactive: no` branch and the `git status`/`git diff HEAD` rule, which apply only where those tools exist. Injection is exempt and unchanged: it already read affirmatively everywhere, and resistance measured at ceiling (zero exfiltration-capable tool calls in 96 runs).
- **New: tool-schema weight is measured per tool, and three docstring passages are documented as load-bearing** (`llm-experiment/measure.py`, `docs/adr/adr-0058.md`, `AGENTS.md`): effective instructions are the composed prompt (3,929 tok on `full`) *plus* the eager tool schemas (2,482 tok), and until now nothing computed the second half — `measure.py` now reports it per preset and per tool, showing `Shell` (539) and `Read` (328) alone at 35% of the tool surface. Roughly 1,045 characters of that surface read like methodology and are standing candidates for deletion: `Shell`'s summarize-first guidance, `Shell`'s "call Shell, not Bash", and `Read`'s batching clause. All three are load-bearing and are now documented as such with the test that pins each. `Shell`'s summarize-first exists because three benchmarked `git diff` runs in a dirty repo produced ~139MB each and timed out; "call Shell, not Bash" is the only place a Claude-authored skill listing `Bash` learns the mapping; and `Read`'s batching clause carries its own System-Context exception because a description is *static* and cannot be withheld from a model ADR-0038 deny-lists. None of those three failures is one an agentic probe sweep naturally produces, which is the general caution ADR-0058 now records: **a null result from a battery that cannot exercise the hazard is not evidence of no cost.**
- **Fix: `Sequence coupled edits` was a rule nothing acted on** (`src/zrb/llm/prompt/markdown/workflow.md`, `workflow.lean.md`, `docs/adr/adr-0049.md`, `llm-experiment/`): `full` states 42 rule-lines to `minimal`'s 18, and a probe battery targeting rules with no counterpart in `workflow.minimal.md` found `full` does not beat `minimal` even there — 44% against 41%. That aggregate licenses almost nothing on its own, and the reason is now recorded in ADR-0049: **a cross-preset gap is not evidence about a rule**, because `full` and `minimal` differ in dozens of ways at once, so "minimal lacks rule R and scores the same" confounds R with everything else. The only valid test is a within-preset ablation, and run that way most of the apparent slack is not slack — *completeness-as-checklist* looks free across presets but costs `full` 9pp and `lean` 12pp when actually removed, and a *scope* demonstration moves neither arm. `Sequence coupled edits` is the exception, condemned within every arm rather than across presets: **0% in `full`, `lean` and `minimal` alike**, with not one model in 48 runs looking for the changelog. 147 characters buying nothing, so they are gone. `Recovery` has the same shape (0/7, 1/7, 2/7) and is the standing candidate for the same treatment once a runtime guard exists to replace it.
- **New: the prompt design is measured instead of argued** (`llm-experiment/`, `docs/adr/adr-0045.md`, `adr-0046.md`, `adr-0049.md`, `adr-0058.md`, `AGENTS.md`): every invariant in `test_section_composition.py` counts characters, rules and tool names — none observes a model, so the load-bearing behavioural claims had never been checked. `llm-experiment/` closes that: 928 runs, 8 models across 6 families, prompt arms composed through the real `PromptManager`, deterministic scorers over a mock repo, resumable. **The preset ladder's premise is wrong and its conclusion survives anyway** — the ladder assumes a model×preset interaction and there is none, with direction identical for weak and strong models. What varies is *which* rules survive: method adherence is flat across presets (79/80/80%) while rank-1 safety runs 44/53/88%. `full` is four times the size of `minimal`, buys nothing measurable on method, and complied with the safety floor at half the rate before the fix above. Also measured: `persona` costs more than it buys (dropping it leaves method flat and improves safety 44% → 56%), injection *resistance* is at ceiling everywhere so that probe measures disclosure rather than safety, and no preset follows the Recovery rule at all (`full` 0/7, `lean` 1/7, `minimal` 2/7 on an unfixable build).
- **Fix: primacy and recency were load-bearing justifications with nothing behind them** (`docs/adr/adr-0046.md`, `adr-0045.md`, `AGENTS.md`): `Priority Order` opened the rulebook "because primacy bias drops later rules first", and `Final Reminders` closed it "exploiting recency the way Priority Order exploits primacy". Measured — one extra mechanically-checkable rule at the start, middle and end of an otherwise byte-identical prompt, 8 models, n=32 per position — **100% / 97% / 94%**. No position effect, and the weak trend runs *against* recency. The literature never supported the claim either: placement effects are real but model-specific in *direction* (arXiv:2607.19257), and lost-in-the-middle (arXiv:2307.03172) measures retrieval of facts, not adherence to rules. Both structures stay, on the structural grounds that were always the better argument — a precedence ladder is unreadable after the rules it ranks, and the recap earns its ~70 tokens because those six rules are the ones that go wrong most often. IFScale's density half still stands and is now corroborated by three further results; only its primacy half is dropped.
- **Fix: family-variant avoidance was argued rather than measured** (`docs/adr/adr-0049.md`, `AGENTS.md`): running opencode's own `anthropic.txt` / `gemini.txt` / `kimi.txt` against 8 models found no family-matching advantage (75% / 75% / 67% against zrb's 74%), and `kimi-k2.6` scored *worst* on the file written for it. zrb still ships zero family variants, but the stated reason changes: family variance is not itself overfitting — format sensitivity is real and idiosyncratic (FormatSpread, arXiv:2310.11324) and shrinks as models get stronger. What is wrong with opencode's forks is that they are **unmeasured** — every fork commit body is empty, there is no eval harness, the files are copies of each vendor's own CLI prompt, and two are dead code nothing imports. The record's earlier reading of that prompt set (weaker family → longer prompt) is withdrawn as confounded by provenance: the lengths track which harness was copied, not the capability of the model routed to it.
