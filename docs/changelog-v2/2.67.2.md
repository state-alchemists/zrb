## 2.67.2 (August 29, 2026)

- **Breaking: `web_auth_config.append_user()` renamed to `add_user()`** (`src/zrb/config/web_auth_config.py`, `test/config/test_web_auth_config.py`, `docs/advanced-topics/web-ui.md`): the user list is an unordered registry keyed by username (duplicate-checked by username, never by position), matching the `add_X` verb every other unordered registry in the codebase uses (`SkillManager.add_skill`, `SubAgentManager.add_agent`, `Group.add_task`). Update any `zrb_init.py` calling `web_auth_config.append_user(...)`.
- **Fix: `ZRB_WEB_ENABLE_SECURE_COOKIES` renamed to `ZRB_WEB_AUTH_SECURE_COOKIES`** (`src/zrb/config/mixins/web.py`, `src/zrb/config/web_auth_config.py`, `test/config/test_web_auth_config.py`, `docs/configuration/env-vars.md`, `docs/advanced-topics/web-ui.md`): the knob now carries the `WEB_AUTH_` prefix shared with its siblings (`WEB_AUTH_ENABLED`, `WEB_AUTH_ACCESS_TOKEN_EXPIRE_MINUTES`), instead of standing out as `WEB_ENABLE_*`. The old env var is still read (not written) via an alias, so existing deployments keep working unchanged.
- **Breaking/Fix: `set_current_permission_policy()`/`set_current_sandbox_policy()` removed — replaced by `permission_policy()`/`sandbox_policy()` context managers** (`src/zrb/util/contextvar_scope.py`, `src/zrb/llm/permission/state.py`, `src/zrb/llm/sandbox/state.py`, `src/zrb/llm/agent/run/setup.py`, `src/zrb/contextvars.py`, `docs/advanced-topics/permission-policy.md`, `test/llm/permission/test_state_and_gate.py`, `test/llm/sandbox/test_gate.py`, `test/llm/prompt/test_system_context.py`): the two setters were bare `ContextVar.set()` calls with no reset, and `permission-policy.md` documented calling `set_current_permission_policy(policy)` directly as the way to set policy dynamically — a policy (or sandbox policy) set this way leaked into every later agent run sharing that context if an exception skipped manual cleanup, which nothing ever did. Both are now `with permission_policy(policy): ...` / `with sandbox_policy(policy): ...`, built on a new shared `zrb.util.contextvar_scope.scoped()` primitive that always resets on exit, matching how `run_agent()` already binds these same ContextVars internally. Also added a defense-in-depth backstop in `run_agent()`: `active_worktree` is now snapshotted and restored at the run boundary, so a forgotten `ExitWorktree` call can no longer leak a worktree path past the run that set it.
- **Refactor: the hook/agent circular-dependency cluster is now a DAG** (`src/zrb/llm/hook/agent_hook_registry.py`, `src/zrb/llm/agent/hook_agent.py`, `src/zrb/llm/hook/creator.py`, `src/zrb/llm/hook/manager.py`, `src/zrb/llm/agent/__init__.py`, `src/zrb/llm/task/llm_task.py`, ADR-0086, `test/llm/agent/test_hook_agent.py`, `test/llm/hook/test_creator_llm.py`): `hook/manager.py` built its `HookType.AGENT` hook by lazily importing the agent-building subsystem from inside `hook/creator.py::create_agent_hook`, `# lazy: circular`-tagged because that subsystem depends on `hook.manager` to fire `PreToolUse`/`PostToolUse` — a real circular dependency, not just a circular import, and the actual runtime call graph existed only in five scattered, partly stale comments. `create_agent_hook` (moved, unchanged, to new `agent/hook_agent.py`) now registers itself into a new dependency-free registry (`hook/agent_hook_registry.py`) as an import side effect of loading `zrb.llm.agent`; `hook/manager.py` reads it back from there instead of importing it directly, and falls back to a logged warning + failed `HookResult` if the agent package was never loaded. `hook/creator.py`'s internal `_run_llm_hook` is now public (`run_llm_hook`), since `agent/hook_agent.py` calls it from outside the file. Breaking only for code importing `create_agent_hook` from `zrb.llm.hook.creator` directly — it now lives at `zrb.llm.agent.hook_agent`.
- **Refactor: two more UI/tool import cycles closed by extracting the shared leaf they were fighting over** (`src/zrb/llm/ui/output_chunk.py`, `src/zrb/llm/ui/default/output.py`, `src/zrb/llm/ui/buffered_ui.py`, `src/zrb/llm/tool_call/choice_spec_format.py`, `src/zrb/llm/tool/ask.py`, `src/zrb/llm/ui/base/ui.py`, `test/llm/ui/test_buffered_ui.py`): `buffered_ui.py` and `ui/default/output.py` both needed `merge_output_chunk`/`CollapsibleBlockSource`, defined in the latter and reached by `buffered_ui.py` through four separate `# lazy: circular` imports; both now import them from a new stdlib-only `ui/output_chunk.py`. `ui/base/ui.py` and `tool/ask.py` had the same shape over `format_choice_spec`, now in a new `tool_call/choice_spec_format.py` — `ui/base/ui.py` no longer depends on `zrb.llm.tool` at all for this call site. Same rationale `zrb.llm.factory_resolver` already established for sharing a helper without risking a cycle.
- **Refactor: the agent run loop's turn state is now a `TurnCursor`, and `sanitize_history`'s step order is an explicit pipeline** (`src/zrb/llm/agent/run/turn_cursor.py`, `src/zrb/llm/agent/run/runner.py`, `src/zrb/llm/agent/run/history_utils.py`, `src/zrb/llm/agent/run/retry_loop.py`, `src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/hook/turn_evidence.py`, ADR-0040, `test/llm/agent/run/test_turn_cursor.py`, `test/llm/hook/test_turn_evidence.py`): `_execution_loop` threaded 7 loose variables across 5 exit paths, with two fragile invariants (never reapply the summarizer mid-deferral; accumulate each round's new messages rather than slicing once at turn end) enforced only by a comment each — the function's own comment admitted a "naive" simplification would silently drop approved tool calls. Both variables and both invariants now live on a new `TurnCursor` (sibling to `RetryState`/`ExtensionState`/`PartialRunAccumulator`), with `carry_forward()`/`commit_round()` as the only methods allowed to perform either transition. `drop_oldest_turn`'s `min_turns` is now a named `TurnPruneFloor` enum instead of a bare `0`/`1`. `sanitize_history`'s 4 steps are now an explicit `_SANITIZE_STEPS` tuple with a DEBUG-only postcondition check, so a broken step order surfaces as a log line instead of silent corruption. Along the way, `history_utils.py` lost two functions that never belonged to history sanitization: `_append_live_context` moved (renamed public) to `prompt/live_context.py`, and `turn_wrote_files`/`FILE_MUTATING_TOOL_NAMES` moved to new `hook/turn_evidence.py`.
- **Refactor: `BaseUI`/`MultiUI`'s duplicated `submit_user_message` logic is now one shared function** (`src/zrb/llm/ui/base/message_queue.py`, `src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/multi_ui.py`, `test/llm/ui/base/test_message_queue.py`): `BaseUI.submit_user_message`'s own docstring admitted it was "mirroring `MultiUI.submit_user_message`" — two independently-maintained, ~20-line implementations of the same echo/attachment/queue mechanics, with nothing enforcing they stayed in sync. Both now call a new `submit_user_message_via_queue()`, parameterized by which targets to fan attachment-collection and echo-tracking out to (`[self]` for a standalone UI, the child list for `MultiUI`, which holds no attachments or echo buffer of its own) — `append_to_output`/`active_run_context`/`stream_ai_response` stay owner-called either way, since both classes already implement those polymorphically. Investigating the fuller `multi_ui_parent` back-reference this session's design also flagged: it's a widely-used public property (a production dependency of `default/message_editing.py`, and a named contract in several existing tests), so removing it in favor of an injected collaborator was judged too invasive for the payoff and left alone — the duplication was the part worth fixing, and is now fixed without touching that surface.
- **Refactor: `LLMTask`/`LLMChatTask`'s history knobs are also readable as one `HistoryConfig` group** (`src/zrb/llm/task/history_config.py`, `src/zrb/llm/task/llm_task.py`, `src/zrb/llm/task/chat/task.py`, `src/zrb/llm/task/chat/execution.py`, ADR-0072, `test/llm/task/test_history.py`, `test/llm/task/chat/test_llm_chat_task.py`): `history_manager`/`conversation_name`/`render_conversation_name` are still individual constructor arguments and properties on both classes (unchanged) — `HistoryConfig` is an additive `history_config` property grouping the three (recomputed on every read, so `history_manager`'s public setter stays immediately visible through it). `chat/execution.py`'s `_create_llm_task_core` now builds the inner task's history knobs via `dataclasses.replace(llm_chat_task.history_config, ...)` instead of listing each field individually — the same three fields still get explicit chat-specific overrides there (the inner task's conversation identity is always the active session, never `LLMChatTask`'s own setting), including a newly-explicit `render_conversation_name=True` that was previously an implicit default; behavior is unchanged.
