## 2.50.7 (July 27, 2026)

- **Fix: a failing parallel task could hang the run instead of failing it** (`src/zrb/util/run.py`, `src/zrb/session/session.py`, `src/zrb/task/base/execution.py`, `test/util/test_run.py`, `test/session/test_session.py`, `test/task/base/test_execution.py`): regression introduced in 2.50.4 — affects 2.50.4 through 2.50.6. `gather_isolated` waited for every sibling to settle before re-raising, which loses `asyncio.gather`'s fail-fast. Siblings that never return on their own — a `Scheduler`/`BaseTrigger` monitoring loop, a deferred long-running task body, an `HttpCheck`/`TcpCheck` that polls until it succeeds — kept the run alive forever after another task had already failed. Two long-running tasks where one crashes (a `frontend` + `backend` start, say) used to exit non-zero immediately and now blocked until the survivor also exited. The two shapes are now separate helpers, because they are not interchangeable: `gather_isolated` keeps the settle-all contract for peer work that must not be cut short by a peer's failure (successors, fallbacks, task chains, root tasks), while the new `gather_fail_fast` fails fast *and* cancels the siblings, then bounds the cancellation settle so a sibling that shields its cleanup cannot re-create the hang. `gather_fail_fast` is used exactly where a sibling may never return: the readiness fan-out in `execute_action_until_ready`, `_wait_deferred_action`, and `_wait_deferred_monitoring`. Applying fail-fast to *every* call site would have traded this hang for a new bug — a failing fallback cancelling the sibling fallbacks that were meant to handle it.
- **Fix: timed-out command hooks leaked processes and exhausted the hook pool** (`src/zrb/llm/hook/hook_creators.py`, `test/llm/hook/test_hook_creators.py`): the timeout path called `process.kill()`, which kills only the shell spawned by `shell=True`. A forked grandchild survived it and — still holding the inherited stdout/stderr pipes — kept `communicate()` blocked in its worker thread until it exited on its own. Hooks are now started in their own session and killed by process group (with a psutil recursive-child fallback for Windows), so no descendant outlives the timeout and no pool worker stays pinned. The kill path can no longer raise either: an error escaping it was swallowed by the outer handler, turning a `CancelledError` that must propagate into an ordinary failed `HookResult`.
- **Fix: cleanup inside cancellation handlers could mask the cancellation** (`src/zrb/llm/ui/base/ui.py`, `src/zrb/llm/ui/base/exec_commands_mixin.py`, `src/zrb/llm/ui/multi_ui.py`, `test/llm/ui/base/test_commands_mixin.py`): an audit of every `except CancelledError` / `except TimeoutError` that runs cleanup found three sites where the cleanup itself could raise and convert a cancelled run into an ordinary failure. `/exec` now reaps its child process *before* writing `[Cancelled]` to the UI and catches `BaseException` around the reaping await, so a second Ctrl+C can no longer skip `process.kill()` and orphan the process. `MultiUI.run` guards the main-UI unwind instead of letting a teardown error replace the `CancelledError`. The message-queue loop's `except (CancelledError, Exception): pass` now re-raises when the cancel was aimed at the loop itself (`current_task().cancelling() > 0`, the same guard `monitoring._handle_threshold_reached` already used), so the queue cannot become uncancellable while a previous job unwinds.
- **Fix: a real style value for the prompt marker or title bar crashed the TUI** (`src/zrb/llm/app/layout.py`, `src/zrb/llm/app/style.py`): `LLM_UI_STYLE_PROMPT`, `LLM_UI_STYLE_TITLE_BAR`, and `LLM_UI_STYLE_TITLE_BAR_BG` are documented as prompt-toolkit styles but were interpolated into an HTML `color=`/`bg=` attribute, which accepts only a bare color. Any style containing a space — `bold #ff0000`, `bg:#222 #fff` — raised `ValueError: "fg" attribute contains a space` while building the layout, i.e. at startup. They now resolve through the style dict, which takes the full style grammar, so the documented contract holds. The title bar is also built with `HTML(...).format()` so a title or jargon string containing `<` or `&` is escaped rather than parsed as markup.
- **Change: the `>>>` marker is gone from the chat input box** (`src/zrb/llm/app/layout.py`): the framed input panel already shows where to type, and dropping the marker returns those columns to the first wrapped line. `ZRB_LLM_UI_STYLE_PROMPT` styled only that marker, so it is **removed** rather than left as an inert knob that silently does nothing (see the dead-config removal below).
- **Removed: four config knobs that nothing ever read** (`src/zrb/config/mixins/hooks.py`, `src/zrb/config/mixins/llm_limits.py`, `src/zrb/config/mixins/llm_ui_styles.py`, `src/zrb/config/theme.py`, `docs/`): `ZRB_HOOKS_DEBUG`, `ZRB_HOOKS_LOG_LEVEL`, `ZRB_LLM_PROJECT_DOC_MAX_CHARS`, and `ZRB_LLM_UI_STYLE_PROMPT` were defined, defaulted, documented, and covered by round-trip tests — but no code ever read them, so setting one did nothing. The first three were documented as working features ("emit verbose hook diagnostics", "log level for hooks", "maximum chars loaded from each project doc file"), which made the docs actively misleading; `LLM_PROJECT_DOC_MAX_CHARS` in particular described an older design where project docs were inlined into the prompt, whereas `project_context` now only lists their paths and lets the agent read them with tools. Their setter/default tests asserted `CFG.X` round-trips to `ZRB_X` and never that anything consumed the value, which is why the gap survived. Unknown `ZRB_*` variables are ignored rather than rejected, so a stale export keeps working silently — it just does what it already did, which is nothing.
- **Fix: `ZRB_LLM_GIT_CMD_TIMEOUT` was never applied** (`src/zrb/llm/prompt/live_context.py`, `src/zrb/llm/util/git.py`, `src/zrb/config/mixins/llm_limits.py`, `test/llm/prompt/test_system_context.py`, `test/llm/util/test_llm_git.py`): the knob documented a cap on "git commands used to build system context" but nothing read it. The live-context git calls (`branch`, `status`, `log`) hardcoded `timeout=5` instead, and the `is_inside_git_dir()` probe that gates them — plus the worktree tool registration — ran with **no timeout at all**, so a git that blocks (credential prompt on a remote, `index.lock` contention) stalled every prompt compose behind it. All four now honour the knob, a timed-out probe reads as "not a git dir" like any other failure, and the default moves from `1000` to `5000` to match the 5s these calls already used — keeping `1000` would have tightened the cap 5x the moment it started working. The knob's scope is now documented explicitly: it does not apply to agent-invoked git work (snapshots, worktrees), which is open-ended by nature.
- **Fix: detached async hooks outlived their session** (`src/zrb/llm/hook/manager/manager.py`, `src/zrb/llm/task/chat/exec_mixin.py`, `test/llm/hook/manager/test_functionality.py`): fire-and-forget (`async: true`) command hooks run in their own session/process group — required so a timeout can kill the whole tree, but it also means the terminal's Ctrl+C SIGINT never reaches them, so a slow one (an audio notifier, say) kept running after the session ended. `HookManager` gains `shutdown()`, called at session end before the worker pool is released: it cancels the pending tasks so each hook's own cancellation handler kills its process tree, bounded by a grace period so a hook that refuses to unwind cannot block exit. It also drops the loop-bound background semaphore, which a later session on a fresh loop would otherwise have awaited against a closed one. A new `has_pending_background_hooks` property exposes the state that tests previously reached for privately, and it stays truthful after the grace period expires — the pending set is no longer cleared unconditionally, which would have had the property report "nothing pending" while hooks were still running. Teardown shuts down the session's *own* manager: `_create_llm_task_core` builds a fresh `HookManager` per execution and that is the instance every hook is dispatched through, so shutting down the module-level singleton would have settled nothing.
- **Fix: oversized MCP results were not actually bounded** (`src/zrb/llm/tool/mcp.py`, `test/llm/tool/test_mcp.py`): the cap added in 2.50.2 was incomplete. `cap_mcp_result` capped each item of a sequence independently, so N parts each just under `LLM_MAX_OUTPUT_CHARS` still totalled N times the budget — the same per-request overflow the cap exists to prevent, which the rate limiter can never admit. The budget is now shared across the whole structure (nested sequences included), with a single `...[TRUNCATED N more parts]` marker once it is spent. Binary and rich content parts still pass through untouched and uncharged.
- **Fix: a raced edit-args submission denied the pending approval** (`src/zrb/runner/chat/chat_session_manager.py`, `src/zrb/runner/chat/chat_api_route.py`, `test/runner/chat/test_chat_session_manager.py`, `test/runner/chat/test_chat_api.py`): when decoded JSON args arrived with no edit slot to consume them (a client racing edit-mode entry), the response fell through to the plain approval handler, which cannot parse a dict and denied the tool call outright. The miss is now reported to the caller and the pending approval is left intact to be answered normally. The HTTP route no longer retries a dict message down the text-mode path either — doing so handed the dict straight back to that same handler, so reporting the miss alone would not have stopped the spurious denial. A dict with no pending edit *and* no pending approval still falls through to being sent as an ordinary message, as before.
- **Fix: HTTP-chat edit mode could strand the approval channel** (`src/zrb/runner/chat/http_chat.py`, `src/zrb/runner/chat/chat_session_manager.py`, `test/runner/chat/test_http_chat.py`): a cancelled run left `is_waiting_for_edit()` permanently true, so every later approval was routed down the edit path and its answer swallowed against the dead tool call. The edit slot is now released on cancellation, a stale slot is detected and cleared so a plain answer can still reach a genuinely pending approval, and the edit handlers report whether a pending call actually consumed the response instead of always claiming success while the tool call hung. Approval broadcasts also keep a strong task reference, so the loop can no longer garbage-collect one mid-flight and silently drop the client's update.
- **Fix: PDF URLs behind a JS or cookie wall failed outright** (`src/zrb/llm/tool/web.py`, `test/llm/tool/test_web_tool.py`): a narrowing introduced with PDF fetching in 2.50.2. The `.pdf` fast path skipped the browser entirely and was terminal, so a PDF served behind Cloudflare or a cookie/JS gate errored even though the Playwright path handles it. Plain HTTP is now a shortcut only — on failure the fetch falls through to the browser, which already routes `application/pdf` responses to the text extractor.
- **Fix: `copy_text` on Termux failed on large payloads** (`src/zrb/llm/util/clipboard.py`, `test/llm/util/test_clipboard.py`): follow-up to the Termux backend added in 2.50.6. The text was passed to `termux-clipboard-set` as a command-line argument, so copying anything sizeable (a whole transcript) could exceed `ARG_MAX` and fail the copy. It now goes over stdin.
- **Fix: `fstring_format` sandbox escape via dunder traversal** (`src/zrb/util/string/format.py`, `test/util/string/test_format.py`): template expressions are parsed and rejected when they reference a dunder name, closing the `().__class__.__bases__[0].__subclasses__()` route back to the real builtins — plain attribute access is not governed by the `eval` globals, so a builtins whitelist alone could not stop it. Single-underscore names remain allowed. Templates are still developer-authored; `data` values were never the trust boundary.
- **Performance: LSP server detection no longer rescans `$PATH` on every file edit** (`src/zrb/llm/lsp/configs.py`, `test/llm/lsp/test_configs.py`): `detect()` ran one `shutil.which` per configured server (~21) on every call, and `get_for_file` runs on each agent `Write`/`Edit` through the post-write diagnostics — which then probed a second time to build its no-server message. A miss walks every `$PATH` entry (~18ms where `PATH` includes WSL2's `/mnt/c/...`), so an edit paid up to ~1s of pure path scanning. The probe is now cached for the process lifetime, invalidated by `register()`/`clear()`, with a new `invalidate_detection()` for installing a language server mid-session.
- **Performance: repo analysis tokenized every file twice** (`src/zrb/llm/tool/code.py`, `test/llm/tool/test_code.py`): `_fit_file_payload` counted the payload's tokens to decide whether it fits, then the caller counted the returned string again. It now returns the count it already computed — one tokenizer pass per fitting file instead of two on every `AnalyzeCode`.
- **Performance: conversation save no longer blocks the event loop** (`src/zrb/llm/task/llm_task.py`): the summarization path's `history_manager.save` is now offloaded with `asyncio.to_thread`, matching the main turn path — it serializes, re-validates, and writes the whole conversation twice (with the backup), which must not stall the TUI.
- **Fix: `project.sh` autocomplete assumed `ps` exists** (`project.sh`): shell-completion setup probed the parent shell with `ps`, so `source project.sh` failed on minimal environments that ship without it. The probe is now guarded and skipped when `ps` is unavailable.
- **Documentation: changelog format and test-seam guidance corrected** (`docs/advanced-topics/maintainer-guide.md`, `AGENTS.md`): the maintainer guide specified nested sub-bullets for changelog entries while every release since 2.50.1 used flat bullets with inline paths — the guide now documents actual practice. `AGENTS.md`'s "never test private members" rule gains the missing half: the seam for a private helper is the public entry point plus the boundary its effect crosses, with `test/llm/tool/test_code.py` as the worked example.
- **Test suite: ~45% faster** (`test/llm/hook/test_hook_creators.py`, `test/llm/lsp/test_configs.py`): a full run drops from ~118s to ~66s. Most of it is the hook process-group fix above — the leaked grandchildren were charged to whichever later test joined the thread pool, putting 28s on a five-line `test_executor_singleton` that runs in under 5ms on its own, and ~20s more on unrelated `test_hook_creators` teardowns. Three test doubles that slept 5s in a non-cancellable executor thread were also shortened to 0.3s, which is all their timeout/cancel assertions need.
